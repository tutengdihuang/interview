# 接口幂等性全链路

> **场景定位**：高并发系统设计场景  
> **核心设计要点**：全链路幂等、分布式幂等、幂等令牌、状态机、死信队列

---

## 🎯 一句话定位

```
你以为前端加按钮禁用 + 后端加唯一主键就能保证不重复，
却没想到分布式架构下服务超时、重试、消息重投、网络重发
都会层层击穿你的防护。
```

**生活化比喻**：
就像银行转账——你在 ATM 上点了"确认转账"，如果网络卡了你又点了一次，银行不可能给你转两笔。幂等性就是保证"不管你点多少次，结果都一样"。但在分布式架构下，这远比加个按钮复杂。

---

## 💎 核心观点

**三层防御**：
1. **业务分级**：强幂等（资金链路）vs 弱幂等（非核心场景）
2. **方案落地**：幂等令牌 + 状态机 + 唯一约束三重防护
3. **架构优化**：统一网关校验、重试策略规范、降级开关

---

## 🚀 一句话精华

> **全链路幂等 = 业务分级（强/弱） + 三重防护（幂等令牌+状态机+唯一约束） + 架构优化（网关统一+重试规范+降级开关）**

---

## 一、真实事故：MQ 重复消费导致数据错乱

```
场景：
  用户支付完成 → 支付服务发 MQ → 订单服务更新状态
  
问题：
  网络抖动 → 消息重复投递
  订单服务重复执行 → 已支付订单被回退为待支付
  
  更严重的是：
  部分消息投递失败 → 钱扣了但订单没更新
  → 大量客服投诉，账务差额
```

---

## 二、三层防御详解

### 2.1 第一层：业务分级

| 级别 | 场景 | 要求 |
|------|------|------|
| **强幂等** | 支付扣款、库存扣减、账务流水 | 严格幂等，绝不允许重复 |
| **弱幂等** | 点赞、浏览、统计上报 | 轻量去重，允许极低概率重复 |

### 2.2 第二层：三重防护

**核心交易接口**：
```
1. 幂等令牌校验
   → 执行前先校验令牌是否已使用
   
2. 状态机校验
   → 只允许状态向前流转
   → 已完成状态直接忽略
   
3. 数据库唯一约束
   → 全程靠唯一主键兜底防重
```

**MQ 消费端**：
```
消费去重表 + 乐观锁：
  → 同一消息仅执行一次业务逻辑
  
失败处理：
  → 消费失败 → 死信队列
  → 人工兜底
  
定时对账：
  → 自动核对支付流水与订单状态
  → 自动修复异常数据 + 告警
```

### 2.3 第三层：架构优化

```
统一重试策略：
  → 禁止无幂等保障的盲目重试
  
网关层统一校验：
  → 核心链路幂等令牌校验前置到网关
  
降级开关：
  → 流量峰值期间非核心接口关闭强校验
  → 优先保障核心交易链路
```

---

## 三、技术方案

> "全链路幂等我分三层：资金链路做强幂等（幂等令牌+状态机+唯一约束三重防护），非核心做弱幂等。MQ 消费端建消费去重表 + 乐观锁，失败进死信队列，定时对账自动修复。架构上网关统一做令牌校验，禁止无幂等保障的盲目重试，大促期间降级非核心强校验。"
