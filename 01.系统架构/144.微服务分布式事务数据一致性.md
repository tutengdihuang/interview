# 微服务分布式事务与数据一致性保障

> **场景定位**：分布式系统核心题  
> **核心设计要点**：分布式事务选型、TCC/AT/SAGA、数据一致性、幂等设计、对账补偿

---

## 🎯 一句话定位

**分布式事务解决什么问题？**
```
电商下单流程拆分为订单服务、库存服务、支付服务三个独立微服务，
用户下单时订单创建成功，库存扣减完成，
但支付服务调用超时失败。
此时订单状态显示"待支付"，库存却已经被扣除，
导致商品超卖，用户无法下单。
回滚库存时又遇到网络异常，
最终出现订单、库存、支付三方数据完全不一致。

技术追问：
- 如何设计一套能扛住网络异常、服务宕机的分布式事务方案？
- 难道所有服务都合并成单体应用来避免分布式问题？

90% 的人答不上来！
```

**生活化比喻**：
就像跨部门办事：
- **分布式事务**：多个部门协同办事，要么全成功，要么全失败
- **数据不一致**：某个部门没办好，其他部门也不知道
- **幂等设计**：同一个申请提交多次，只处理一次
- **对账补偿**：定期检查，发现问题及时修复

**核心特点**：单纯使用分布式事务框架和真正根据业务特性选型、处理极端异常场景完全是两个技术维度！

## 💎 核心观点（5 分钟速览版）

> **快速概览**

### 核心观点（三层防御体系）

**第一层：业务分级**
```
强一致性场景（核心交易）：
- 订单创建、库存扣减、资金转账
- 必须保证强一致性
- 不允许出现中间状态

最终一致性场景（非核心）：
- 消息通知、积分发放、日志记录
- 可接受短暂数据不一致
- 采用最终一致性方案即可

生活化比喻：
就像跨部门办事：
- 强一致性：银行转账，必须同时成功或失败
- 最终一致性：发送通知，可以延迟几秒
```

**第二层：核心方案落地与多模式适配**
```
强一致性场景：
- TCC 模式：手动实现 Try、Confirm、Cancel 三个阶段
- AT 模式：Seata 自动代理，降低开发成本

最终一致性场景：
- 本地消息表 + 可靠消息队列
- 保证消息投递与本地事务原子性

长事务场景：
- SAGA 模式：通过补偿操作实现数据最终一致

生活化比喻：
就像跨部门办事：
- TCC：先预约（Try），确认办理（Confirm），取消预约（Cancel）
- AT：自动代理，不用手动处理
- SAGA：每个步骤都有对应的回退步骤
```

**第三层：生产落地的异常处理细节**
```
幂等性保障：
- 所有分布式事务操作必须实现幂等性
- 防止重复执行导致数据错误

TCC 特殊问题：
- 空回滚：Cancel 时 Try 还没执行
- 悬挂：Cancel 比 Try 先执行

事务监控：
- 实时监控事务状态、执行时长、失败次数
- 异常事务自动告警

数据对账：
- 每日定时执行数据对账任务
- 对比不同服务的数据差异
- 自动修复或人工介入处理

生活化比喻：
就像跨部门办事：
- 幂等：同一个申请提交多次，只处理一次
- 空回滚：预约还没提交就取消
- 悬挂：取消比预约还快
- 对账：每天检查各部门数据是否一致
```

## 三、第二层：核心方案落地与多模式适配

### 3.1 TCC 模式

**三阶段**：
```
Try 阶段：
- 资源预留
- 业务检查
- 不提交事务

Confirm 阶段：
- 确认执行
- 提交事务
- 不做业务检查

Cancel 阶段：
- 取消执行
- 释放资源
- 恢复数据
```

**代码示例**：
```java
// ✅ TCC 分布式事务
@TwoPhaseBusinessAction(
    name = "deductStock",
    commitMethod = "confirm",
    rollbackMethod = "cancel"
)
public interface StockService {
    
    // Try 阶段：预扣库存
    boolean tryDeduct(BusinessActionContext context, 
                      @BusinessActionContextParameter(paramName = "productId") Long productId,
                      @BusinessActionContextParameter(paramName = "count") Integer count);
    
    // Confirm 阶段：确认扣减
    boolean confirm(BusinessActionContext context);
    
    // Cancel 阶段：取消扣减
    boolean cancel(BusinessActionContext context);
}

// 实现
@Service
public class StockServiceImpl implements StockService {
    
    @Override
    public boolean tryDeduct(BusinessActionContext context, Long productId, Integer count) {
        // 1. 检查库存
        Stock stock = stockMapper.selectByProductId(productId);
        if (stock.getAvailable() < count) {
            return false;
        }
        
        // 2. 冻结库存
        stockMapper.freezeStock(productId, count);
        
        // 3. 记录操作日志
        logMapper.insert(productId, count, "FREEZE");
        
        return true;
    }
    
    @Override
    public boolean confirm(BusinessActionContext context) {
        Long productId = (Long) context.getActionContext("productId");
        Integer count = (Integer) context.getActionContext("count");
        
        // 1. 确认扣减
        stockMapper.confirmDeduct(productId, count);
        
        // 2. 记录操作日志
        logMapper.insert(productId, count, "CONFIRM");
        
        return true;
    }
    
    @Override
    public boolean cancel(BusinessActionContext context) {
        Long productId = (Long) context.getActionContext("productId");
        Integer count = (Integer) context.getActionContext("count");
        
        // 1. 释放冻结的库存
        stockMapper.unfreezeStock(productId, count);
        
        // 2. 记录操作日志
        logMapper.insert(productId, count, "CANCEL");
        
        return true;
    }
}
```

**生活化比喻**：
```
就像预约办事：
- Try：预约，预留名额
- Confirm：确认办理，正式提交
- Cancel：取消预约，释放名额
```

### 3.2 AT 模式

**原理**：
```
Seata 自动代理：
- 解析 SQL，生成前后镜像
- 一阶段：本地提交，记录 undo_log
- 二阶段：成功则删除 undo_log，失败则回滚
```

**代码示例**：
```java
// ✅ AT 模式（Seata）
@GlobalTransactional
public void createOrder(OrderRequest request) {
    // 1. 创建订单
    orderService.create(request);
    
    // 2. 扣减库存
    stockService.deduct(request.getProductId(), request.getCount());
    
    // 3. 扣减余额
    accountService.deduct(request.getUserId(), request.getAmount());
}
```

**生活化比喻**：
```
就像自动代理：
- 不用手动处理 Try、Confirm、Cancel
- Seata 自动帮你处理
```

### 3.3 SAGA 模式

**原理**：
```
长事务拆分：
- 将长事务拆分为多个短事务
- 每个短事务都有对应的补偿操作
- 失败时按相反顺序执行补偿
```

**代码示例**：
```java
// ✅ SAGA 模式
@Service
public class OrderSaga {
    
    @Autowired
    private OrderService orderService;
    
    @Autowired
    private StockService stockService;
    
    @Autowired
    private AccountService accountService;
    
    public void execute(OrderRequest request) {
        try {
            // 1. 创建订单
            orderService.create(request);
            
            // 2. 扣减库存
            stockService.deduct(request.getProductId(), request.getCount());
            
            // 3. 扣减余额
            accountService.deduct(request.getUserId(), request.getAmount());
            
        } catch (Exception e) {
            // 失败时执行补偿
            compensate(request);
        }
    }
    
    private void compensate(OrderRequest request) {
        // 按相反顺序补偿
        accountService.rollback(request.getUserId(), request.getAmount());
        stockService.rollback(request.getProductId(), request.getCount());
        orderService.rollback(request.getOrderId());
    }
}
```

**生活化比喻**：
```
就像长流程办事：
- 每个步骤都有对应的回退步骤
- 失败时按相反顺序回退
```

## 四、第三层：生产落地的异常处理细节

### 4.1 幂等性保障

**代码示例**：
```java
// ✅ 幂等设计
public void deductStock(Long productId, Integer count) {
    String lockKey = "lock:stock:" + productId;
    
    if (redisLock.tryLock(lockKey, 10, TimeUnit.SECONDS)) {
        try {
            // 检查是否已处理
            if (logMapper.exists(productId, count)) {
                log.info("重复请求，忽略");
                return;
            }
            
            // 扣减库存
            stockMapper.deduct(productId, count);
            
            // 记录操作日志
            logMapper.insert(productId, count, "DEDUCT");
        } finally {
            redisLock.unlock(lockKey);
        }
    } else {
        log.info("获取锁失败，消息重试");
    }
}
```

### 4.2 TCC 特殊问题

**空回滚**：
```java
// ✅ 空回滚处理
@Override
public boolean cancel(BusinessActionContext context) {
    Long productId = (Long) context.getActionContext("productId");
    Integer count = (Integer) context.getActionContext("count");
    
    // 检查 Try 是否执行
    if (!logMapper.existsTry(productId, count)) {
        // Try 未执行，直接返回成功
        log.info("空回滚，Try 未执行");
        return true;
    }
    
    // 释放冻结的库存
    stockMapper.unfreezeStock(productId, count);
    
    return true;
}
```

**悬挂**：
```java
// ✅ 悬挂处理
@Override
public boolean tryDeduct(BusinessActionContext context, Long productId, Integer count) {
    // 检查是否已取消
    if (logMapper.existsCancel(productId, count)) {
        // 已取消，不再执行 Try
        log.info("悬挂，已取消");
        return false;
    }
    
    // 冻结库存
    stockMapper.freezeStock(productId, count);
    
    return true;
}
```

### 4.4 数据对账

**代码示例**：
```java
// ✅ 数据对账
@Scheduled(cron = "0 0 2 * * ?") // 每天凌晨 2 点
public void reconcile() {
    // 1. 查询订单数据
    List<Order> orders = orderMapper.selectToday();
    
    // 2. 查询库存数据
    List<Stock> stocks = stockMapper.selectToday();
    
    // 3. 对比数据
    for (Order order : orders) {
        Stock stock = stocks.stream()
            .filter(s -> s.getProductId().equals(order.getProductId()))
            .findFirst()
            .orElse(null);
        
        if (stock == null || !stock.getCount().equals(order.getCount())) {
            // 数据不一致，记录日志
            log.error("数据不一致：订单 {}，库存 {}", order, stock);
            
            // 自动修复或人工介入
            reconcileService.fix(order, stock);
        }
    }
}
```

五、技术深入探讨

### Q1: 分布式事务怎么选型？

**答**：
> 选型建议：
>
> **强一致性场景**：
> - TCC 模式：核心资金交易，手动实现，精准控制
> - AT 模式：简单场景，自动代理，降低开发成本
>
> **最终一致性场景**：
> - 本地消息表 + 可靠消息队列：异步解耦，性能好
>
> **长事务场景**：
> - SAGA 模式：长流程事务，每个步骤都有补偿操作

### Q2: TCC 模式的空回滚和悬挂怎么处理？

**答**：
> 空回滚处理：
> - Cancel 时检查 Try 是否执行
> - 如果 Try 未执行，直接返回成功
>
> 悬挂处理：
> - Try 时检查是否已取消
> - 如果已取消，不再执行 Try

### Q3: 数据不一致怎么处理？

**答**：
> 数据不一致处理：
>
> 1. **实时监控**：事务状态、执行时长、失败次数
> 2. **数据对账**：每日定时对账，对比不同服务的数据差异
> 3. **自动修复**：绝大多数不一致数据自动修复
> 4. **人工兜底**：极端异常情况人工介入处理

## 六、方案总结

**方案总结**：

> "分布式事务需要**三层防御体系**：
>
> **第一层：业务分级**
> 强一致性场景（订单创建、库存扣减、资金转账）必须保证强一致性，不允许出现中间状态。最终一致性场景（消息通知、积分发放、日志记录）可接受短暂数据不一致，采用最终一致性方案即可平衡性能与可靠。
>
> **第二层：核心方案落地与多模式适配**
> 强一致性场景优先选用 TCC 模式，手动实现 Try、Confirm、Cancel 三个阶段，精准控制事务回滚。简单场景可使用 Seata 的 AT 模式，降低开发成本。最终一致性场景采用本地消息表加可靠消息队列方案，保证消息投递与本地事务原子性。长事务场景使用 SAGA 模式，通过补偿操作实现数据最终一致。
>
> **第三层：生产落地的异常处理细节**
> 所有分布式事务操作必须实现幂等性，防止重复执行导致数据错误。TCC 模式专门处理空回滚、悬挂问题，避免异常情况下数据不一致。建立完善的事务监控体系，实时监控事务状态、执行时长、失败次数，异常事务自动告警。每日定时执行数据对账任务，对比不同服务的数据差异，自动修复或人工介入处理，作为最终兜底方案。
>
> 核心是从单纯使用分布式事务框架升级为业务选型、异常处理、兜底保障的全流程工程思维。"
