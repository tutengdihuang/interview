```
RabbitMQ 的三大难题：
1. 消息丢失：快递丢了，用户收不到
```

## 三、第二层：三段式全链路优化

### 3.1 生产端优化

**代码示例（RabbitMQ 生产者）**：
```java
// 生产者配置
@Bean
public RabbitTemplate rabbitTemplate(ConnectionFactory connectionFactory) {
    RabbitTemplate template = new RabbitTemplate(connectionFactory);
    template.setMandatory(true);
    
    // ✅ Confirm 确认机制
    template.setConfirmCallback((correlationData, ack, cause) -> {
        if (!ack) {
            // 消息发送失败，本地缓存重试
            log.error("消息发送失败: {}", cause);
            retryService.addRetry(correlationData);
        }
    });
    
    // ✅ Return 回调
    template.setReturnsCallback(returned -> {
        log.error("消息路由失败: {}", returned.getReplyText());
        retryService.addRetry(returned.getMessage());
    });
    
    return template;
}

// 发送消息
public void sendMessage(String exchange, String routingKey, Message message) {
    CorrelationData correlationData = new CorrelationData();
    correlationData.setId(UUID.randomUUID().toString());
    
    rabbitTemplate.convertAndSend(exchange, routingKey, message, correlationData);
}
```

### 3.2 Broker 优化

**持久化配置**：

```java
// 交换机持久化
@Bean
public DirectExchange durableExchange() {
    return new DirectExchange("order.exchange", true, false);

        "order.exchange",

        }
```

### 3.3 消费端优化

**代码示例（手动 ACK + 幂等校验）**：
```java
@RabbitListener(queues = "order.queue")
public void processMessage(Message message, Channel channel) throws IOException {
    String orderNo = new String(message.getBody());
    long deliveryTag = message.getMessageProperties().getDeliveryTag();
    
    try {
        // ✅ 幂等校验
        if (idempotentService.isDuplicate(orderNo)) {
            log.info("重复消息，忽略: {}", orderNo);
            channel.basicAck(deliveryTag, false);
            return;
        }
        
        // 处理业务逻辑
        orderService.processOrder(orderNo);
        
        // ✅ 业务成功后手动 ACK
        channel.basicAck(deliveryTag, false);
        
    } catch (Exception e) {
        log.error("处理失败", e);
        
        // ❌ 业务失败，不确认，消息重回队列
        channel.basicNack(deliveryTag, false, true);
    }
}
```

**幂等设计（Redis）**：
```java
@Component
public class IdempotentService {
    
    @Autowired
    private StringRedisTemplate redisTemplate;
    
    public boolean isDuplicate(String orderNo) {
        String key = "idempotent:order:" + orderNo;
        
        // ✅ 使用 Redis SETNX 实现幂等
        Boolean result = redisTemplate.opsForValue()
            .setIfAbsent(key, "1", 24, TimeUnit.HOURS);
        
        return result == null || !result;
    }
}
```

## 四、第三层：架构层长效防控

### 4.1 兜底补偿机制

**本地消息表方案**：
```java
// 1. 业务消息落库
@Transactional
public void createOrder(Order order) {
    // 保存订单
    orderMapper.insert(order);
    
    // ✅ 消息落库
    MessageRecord record = new MessageRecord();
    record.setOrderNo(order.getOrderNo());
    record.setStatus("PENDING");
    record.setCreateTime(new Date());
    messageRecordMapper.insert(record);
    
    // 发送 MQ
    rabbitTemplate.convertAndSend("order.exchange", "order.routingKey", order.getOrderNo());
}

// 2. 定时任务扫描未消费的消息
@Scheduled(fixedDelay = 60000) // 每分钟执行一次
public void scanUnconsumedMessages() {
    List<MessageRecord> records = messageRecordMapper.selectPendingMessages();
    
    for (MessageRecord record : records) {
        // 补发消息
        rabbitTemplate.convertAndSend("order.exchange", "order.routingKey", record.getOrderNo());
        
        // 更新状态
        record.setStatus("SENT");
        messageRecordMapper.update(record);
    }
}

// 3. 消费成功后更新状态
@RabbitListener(queues = "order.queue")
public void processMessage(String orderNo) {
    orderService.processOrder(orderNo);
    
    // ✅ 更新消息状态
    messageRecordMapper.updateStatus(orderNo, "CONSUMED");
}
```

### 4.2 死信队列设计

**生活化比喻**：
```
死信队列就像"问题快递区"：
- 送失败的快递放到这里
- 后续人工处理
- 避免阻塞正常快递
```

**代码示例（RabbitMQ 死信队列）**：
```java
// 配置死信队列
@Bean
public Queue deadLetterQueue() {
    return QueueBuilder.durable("dead-letter-queue").build();
}

@Bean
public DirectExchange deadLetterExchange() {
    return new DirectExchange("dead-letter-exchange");
}

@Bean
public Binding deadLetterBinding() {
    return BindingBuilder.bind(deadLetterQueue())
        .to(deadLetterExchange())
        .with("dead-letter-routing-key");
}

// 配置正常队列（绑定死信交换机）
@Bean
public Queue normalQueue() {
    Map<String, Object> args = new HashMap<>();
    args.put("x-dead-letter-exchange", "dead-letter-exchange");
    args.put("x-dead-letter-routing-key", "dead-letter-routing-key");
    args.put("x-message-ttl", 60000); // 60 秒超时
    return QueueBuilder.durable("normal-queue").withArguments(args).build();
}

// 消费失败，消息进入死信队列
@RabbitListener(queues = "normal-queue")
public void processMessage(Message message, Channel channel) throws IOException {
    long deliveryTag = message.getMessageProperties().getDeliveryTag();
    
    try {
        process(new String(message.getBody()));
        channel.basicAck(deliveryTag, false);
    } catch (Exception e) {
        log.error("处理失败", e);
        
        // ✅ 拒绝消息，进入死信队列
        channel.basicNack(deliveryTag, false, false);
    }
}
```

### 4.3 全链路监控

**监控指标**：

| 指标 | 告警阈值 | 告警原因 | 生活化比喻 |
|------|---------|---------|-----------|
| **队列堆积** | > 10 万条 | 消费能力不足 | 快递堆积 |
| **消息丢弃** | > 0 | 队列满了或 TTL 过期 | 快递丢了 |
| **死信增长** | > 100 条/分钟 | 消费失败率高 | 送失败的快递增多 |

**代码示例（Prometheus 监控）**：

### Q1: 如何保证消息不丢失？

**答**：
> 三段式全链路防丢失：
>
> **生产端**：Confirm 确认机制 + Return 回调 + 本地缓存重试
> **Broker**：交换机、队列、消息全部持久化
> **消费端**：手动 ACK，业务成功后再签收
>
> 核心业务还要加兜底方案：消息落库，定时任务扫描未消费的消息补发。

### Q2: 如何保证幂等消费？

**答**：
> 基于订单唯一编号做幂等校验：
>
> 使用 Redis SETNX 实现幂等，设置 24 小时过期时间。
> 重复消息直接忽略，避免重复扣款。
>
> 推荐方案：Redis 幂等 + 数据库唯一索引，双重保障。

### Q3: 死信队列怎么设计？

**答**：
> 死信队列设计：
>
> 1. **配置死信交换机和死信队列**
> 2. **正常队列绑定死信交换机**
> 3. **消费失败，消息进入死信队列**
> 4. **定时任务处理死信队列的消息**
>
> 注意：设置有限重试次数，避免无效消息无限占用队列资源。

## 六、方案总结

**方案总结**：

> "RabbitMQ 消息可靠性需要**三层防御体系**：
>
> **第一层：业务分级**
> 核心业务消息（库存扣减、订单状态变更）全链路开启可靠性保障，零容忍丢失；非核心消息（短信推送、操作日志）可适当放宽配置。
>
> **第二层：三段式全链路优化**
> 生产端：Confirm 确认机制 + Return 回调 + 本地缓存重试。Broker：交换机、队列、消息全部持久化。消费端：手动 ACK + 幂等校验 + 失败超限转入死信队列。
>
> **第三层：架构层长效防控**
> 关键消息落地业务临时数据表，定时任务扫描未消费的消息补发。搭建 MQ 监控平台，监管队列堆积、消息丢弃、死信增长量。规范重试策略，设置有限重试次数，定期清理冗余死信数据。
>
> 核心是从会配置持久化参数，升级为生产-存储-消费全链路闭环、兜底补偿的消息中间件架构思维。"
