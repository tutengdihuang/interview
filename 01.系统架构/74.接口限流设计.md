# 接口限流设计

> **场景定位**：高并发系统设计场景  
> **核心设计要点**：限流算法、多级防护、动态调参、应急止损

---

## 🎯 一句话定位

**接口限流解决什么问题？**
```
流量突增远超服务承载上限
通过限流保护服务稳定性
防止服务雪崩
```

**生活化比喻**：
就像高速公路收费站：
- 车太多 → 堵车（服务过载）
- 收费站限制放行速度 → 车流可控（限流）
- 紧急情况下关闭部分入口 → 保住主干道（降级）

## 💎 核心观点（5 分钟速览版）

### 核心观点（5 个关键点）

**1. 单机限流 ≠ 全链路防护**
```
❌ 误区：网关加个限流就行
✅ 真相：必须网关+服务+数据层多级防护
单层失效会导致故障逐层传导
```

**2. 四类限流算法**
```
计数器：简单，但有临界问题
滑动窗口：精度更高
漏桶：平滑流量
令牌桶：允许突发（推荐）
```

**3. 分级处理策略**
```
快速拒绝：超过阈值直接返回错误
排队等待：允许等待一定时间
服务降级：返回兜底数据
```

**4. 阈值要基于容量评估**
```
❌ 拍脑袋设阈值
✅ 基于压测结果
留 20% buffer
```

**5. 动态热调整**
```
支持运行时修改阈值
无需重启服务
异常时快速扩容
```

## 一、限流算法对比

### 1.1 计数器（固定窗口）

**原理**：
```
固定时间窗口（如 1 分钟）
统计窗口内的请求数
超过阈值就拒绝
```

**代码示例**：
```go
type CounterLimiter struct {
    count    int64
    limit    int64
    window   time.Duration
    resetAt  time.Time
    mu       sync.Mutex
}

func (l *CounterLimiter) Allow() bool {
    l.mu.Lock()
    defer l.mu.Unlock()
    
    now := time.Now()
    if now.After(l.resetAt) {
        l.count = 0
        l.resetAt = now.Add(l.window)
    }
    
    if l.count >= l.limit {
        return false
    }
    
    l.count++
    return true
}
```

**问题**：
```
临界问题：
窗口边界 59 秒来 100 个请求
00 秒又来 100 个请求
1 秒内实际处理了 200 个请求（超限）
```

### 1.2 滑动窗口

**原理**：
```
把时间窗口分成多个小格
每个格子独立计数
滑动统计最近 N 个格子
```

**优势**：
```
解决临界问题
精度更高
但实现复杂
```

### 1.3 漏桶算法

**原理**：
```
请求进入桶中
桶以固定速率流出（处理）
桶满了就溢出（拒绝）
```

**特点**：
```
平滑流量
但不允许突发
```

### 1.4 令牌桶算法（推荐）

**原理**：
```
系统以固定速率生成令牌
请求需要先获取令牌
没有令牌就拒绝
```

**代码示例**：
```go
type TokenBucketLimiter struct {
    tokens     int64
    limit      int64
    rate       float64 // 每秒生成令牌数
    lastUpdate time.Time
    mu         sync.Mutex
}

func (l *TokenBucketLimiter) Allow() bool {
    l.mu.Lock()
    defer l.mu.Unlock()
    
    now := time.Now()
    elapsed := now.Sub(l.lastUpdate).Seconds()
    
    // 生成新令牌
    l.tokens = min(l.limit, l.tokens+int64(elapsed*l.rate))
    l.lastUpdate = now
    
    if l.tokens == 0 {
        return false
    }
    
    l.tokens--
    return true
}
```

**优势**：
```
允许突发流量
实现简单
性能好
```

## 二、多级防护体系

### 2.1 网关层限流

```go
// 网关层：粗粒度限流（IP/用户维度）
func GatewayRateLimit() gin.HandlerFunc {
    limiter := NewTokenBucketLimiter(1000) // 1000 QPS
    
    return func(c *gin.Context) {
        if !limiter.Allow() {
            c.JSON(429, gin.H{"error": "rate limit exceeded"})
            c.Abort()
            return
        }
        c.Next()
    }
}
```

### 2.2 服务层限流

```go
// 服务层：细粒度限流（接口维度）
func ServiceRateLimit() gin.HandlerFunc {
    limiters := map[string]*TokenBucketLimiter{
        "/api/order/create": NewTokenBucketLimiter(500),
        "/api/product/list": NewTokenBucketLimiter(2000),
    }
    
    return func(c *gin.Context) {
        path := c.Request.URL.Path
        if limiter, ok := limiters[path]; ok {
            if !limiter.Allow() {
                c.JSON(429, gin.H{"error": "rate limit exceeded"})
                c.Abort()
                return
            }
        }
        c.Next()
    }
}
```

### 2.3 数据层限流

```go
// 数据层：保护数据库
func DBRateLimit() {
    dbLimiter := NewTokenBucketLimiter(1000) // 数据库最多 1000 QPS
    
    if !dbLimiter.Allow() {
        // 降级：返回缓存数据
        return getFromCache()
    }
    
    return queryFromDB()
}
```

## 三、分级处理策略

### 3.1 快速拒绝

```go
// 超过阈值直接返回错误
func RejectStrategy() {
    if !limiter.Allow() {
        c.JSON(429, gin.H{"error": "rate limit exceeded"})
    }
}
```

### 3.2 排队等待

```go
// 允许等待一定时间
func QueueStrategy() {
    ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
    defer cancel()
    
    err := limiter.Wait(ctx)
    if err != nil {
        c.JSON(429, gin.H{"error": "wait timeout"})
    }
}
```

### 3.3 服务降级

```go
// 返回兜底数据
func DegradeStrategy() {
    if !limiter.Allow() {
        // 返回缓存数据或默认值
        c.JSON(200, gin.H{
            "data": getFromCache(),
            "msg":  "服务降级中",
        })
    }
}
```

## 四、动态调参

### 4.1 配置中心热更新

```go
type DynamicLimiter struct {
    limiter *TokenBucketLimiter
    config  ConfigCenter
}

// 监听配置变更
func (l *DynamicLimiter) WatchConfig() {
    l.config.Watch("rate_limit.order", func(newLimit string) {
        limit, _ := strconv.ParseInt(newLimit, 10, 64)
        l.limiter.SetLimit(limit)
        log.Info("限流阈值更新: %d", limit)
    })
}
```

### 4.2 基于负载自适应

```go
// 根据 CPU 使用率自动调整限流阈值
func AdaptiveLimiter() {
    cpuUsage := getCPUUsage()
    
    if cpuUsage > 80 {
        // CPU 高，降低限流阈值
        limiter.SetLimit(500)
    } else if cpuUsage < 50 {
        // CPU 低，提高限流阈值
        limiter.SetLimit(2000)
    }
}
```

type RateLimitMetrics struct {
    TotalRequests  int64 // 总请求数
    RejectedCount  int64 // 拒绝次数

    metrics := RateLimitMetrics{
        TotalRequests: limiter.GetTotalRequests(),
        RejectedCount: limiter.GetRejectedCount(),

六、技术深入探讨

### Q1: 限流阈值怎么设置？

**方案参考**：
> 限流阈值不能拍脑袋，要基于容量评估：
> 
> 1. **压测**：找到系统的最大吞吐量（如 1000 QPS）
> 2. **留 buffer**：阈值设为最大吞吐量的 80%（800 QPS）
> 3. **分级设置**：核心接口和非核心接口不同阈值
> 4. **动态调整**：支持运行时修改，无需重启
> 
> 关键是压测要真实，buffer 要留够。

### Q2: 单机限流够用吗？

**方案参考**：
> 单机限流不够，必须多级防护：
> 
> 1. **网关层**：粗粒度限流（IP/用户维度），防恶意攻击
> 2. **服务层**：细粒度限流（接口维度），保护核心接口
> 3. **数据层**：保护数据库，防止被冲垮
> 
> 单层失效会导致故障逐层传导，必须多层防护。
