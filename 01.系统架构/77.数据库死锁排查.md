# 数据库死锁排查

> **场景定位**：数据库并发控制技术场景  
> **核心设计要点**：死锁成因、排查方法、预防策略、架构优化

---

## 🎯 一句话定位

**数据库死锁解决什么问题？**
```
两个事务互相持有对方需要的锁
→ 互相等待，永远阻塞
→ 数据库触发死锁检测，回滚事务
```

**生活化比喻**：
就像两个人在窄路上相遇：
- A 从东向西，B 从西向东
- A 说"你先退"，B 说"你先退"
- 两人都不让，永远堵着

---

## 💎 核心观点（5 分钟速览版）

### 核心观点（5 个关键点）

**1. 死锁四个必要条件**
```
互斥、占有并等待、不可抢占、循环等待
破坏任一条件即可避免死锁
```

**2. 加锁顺序不一致是主因**
```
下单：先锁库存 → 再锁订单
退款：先锁订单 → 再锁库存
→ 循环等待 → 死锁
```

**3. 统一加锁顺序**
```
所有业务按相同顺序加锁
如：按表 ID 升序申请行锁
破坏循环等待条件
```

**4. 监控与自动处理**
```
死锁检测：自动回滚代价小的事务
锁等待超时：超时自动回滚
监控告警：实时追踪死锁次数
```

**5. 架构层优化**
```
热点数据分片：分散锁竞争
应用层前置锁：减少数据库压力
核心场景开关：大促关停非核心写操作
```

## 一、死锁典型案例

### ❌ 典型事故

```
电商两条核心链路：
下单：先扣库存 → 再更新订单状态
退款：先回滚订单状态 → 再返还库存

大促高峰期：
大量下单和退款请求
两条链路加锁顺序完全相反
→ 循环等待 → 死锁
→ 大面积爆仓
```

**根因分析**：
```
下单事务：
1. LOCK inventory WHERE goods_id = 1
2. LOCK orders WHERE order_id = 100

退款事务：
1. LOCK orders WHERE order_id = 100
2. LOCK inventory WHERE goods_id = 1

如果两个事务同时执行：
- 下单事务持有 inventory 锁，等待 orders 锁
- 退款事务持有 orders 锁，等待 inventory 锁
→ 死锁
```

## 二、统一加锁顺序

### 2.1 约定加锁顺序

```go
// ✅ 所有业务按表 ID 升序加锁
func ProcessOrder(orderID, goodsID int64) error {
    // 按 ID 升序加锁
    if goodsID < orderID {
        lockInventory(goodsID)
        lockOrder(orderID)
    } else {
        lockOrder(orderID)
        lockInventory(goodsID)
    }
    
    defer unlockAll()
    
    // 业务逻辑
    return nil
}
```

### 2.2 按主键排序

```go
// 同表操作按主键排序
func BatchUpdateOrder(orderIDs []int64) error {
    // 排序
    sort.Slice(orderIDs, func(i, j int) bool {
        return orderIDs[i] < orderIDs[j]
    })
    
    // 按顺序加锁
    for _, id := range orderIDs {
        lockOrder(id)
    }
    
    defer unlockAll()
    
    // 业务逻辑
    return nil
}
```

## 四、大事务拆分

### 4.1 长事务持锁问题

```go
// ❌ 长事务
func ProcessOrder() error {
    tx, _ := db.Begin()
    
    // 执行 10 秒的业务逻辑
    tx.Exec("UPDATE inventory ...") // 持有锁
    time.Sleep(10 * time.Second)     // 模拟耗时
    tx.Exec("UPDATE orders ...")     // 持有锁
    
    tx.Commit() // 10 秒后才释放锁
    return nil
}
```

### 4.2 拆分为短事务

```go
// ✅ 短事务
func ProcessOrder() error {
    // 事务 1：扣库存
    tx1, _ := db.Begin()
    tx1.Exec("UPDATE inventory ...")
    tx1.Commit() // 立即释放锁
    
    // 中间逻辑（不持锁）
    doOtherLogic()
    
    // 事务 2：更新订单
    tx2, _ := db.Begin()
    tx2.Exec("UPDATE orders ...")
    tx2.Commit() // 立即释放锁
    
    return nil
}
```

## 五、架构层优化

### 5.1 热点数据分片

```go
// 库存分片，分散锁竞争
type InventorySharding struct {
    shards int
}

// 1000 个库存拆成 10 个分片
func (s *InventorySharding) Deduct(goodsID string) error {
    shard := rand.Intn(s.shards)
    shardKey := fmt.Sprintf("%s:%d", goodsID, shard)
    
    // 只锁一个分片，降低冲突概率
    return db.Exec("UPDATE inventory SET stock = stock - 1 WHERE key = ?", shardKey)
}
```

### 5.2 应用层前置锁

```go
// 应用层分布式锁，减少数据库压力
func DeductInventory(goodsID string) error {
    // 1. 先抢分布式锁
    locked := redis.SetNX(fmt.Sprintf("lock:%s", goodsID), "1", 10*time.Second)
    if !locked {
        return errors.New("获取锁失败")
    }
    defer redis.Del(fmt.Sprintf("lock:%s", goodsID))
    
    // 2. 再执行数据库操作
    return db.Exec("UPDATE inventory ...")
}
```

六、技术深入探讨

### Q1: 死锁怎么排查？

**方案参考**：
> 死锁排查分三步：
> 
> 1. **查日志**：`SHOW ENGINE INNODB STATUS` 查看死锁日志，找到两个事务的加锁顺序
> 2. **分析代码**：找到两条业务链路的加锁顺序，确认是否存在循环等待
> 3. **修复方案**：统一加锁顺序，按表 ID 或主键升序申请锁
> 
> 关键是要有监控，实时追踪死锁次数。

### Q2: 如何预防死锁？

**方案参考**：
> 预防死锁从四个层面：
> 
> 1. **加锁顺序**：所有业务按相同顺序加锁，破坏循环等待
> 2. **短事务**：大事务拆成多个短事务，减少锁持有时间
> 3. **监控告警**：实时追踪死锁次数，设置锁等待超时
> 4. **架构优化**：热点数据分片，应用层前置锁，分散锁竞争
> 
> 核心是统一加锁顺序，破坏循环等待条件。
