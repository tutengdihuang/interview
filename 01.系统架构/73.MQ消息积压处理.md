# MQ 消息积压处理

> **场景定位**：消息队列技术场景  
> **核心设计要点**：积压原因、应急处理、架构优化、监控预警

---

## 🎯 一句话定位

**消息积压解决什么问题？**
```
消息队列堆积百万级消息
→ Broker 磁盘打满
→ 新消息无法写入
→ 整个集群不可用
```

**生活化比喻**：
就像快递站堆积了 100 万件快递：
- 快递员来不及送（消费者处理慢）
- 新快递还在不断送来（生产者持续发送）
- 快递站爆满了（Broker 磁盘打满）

---

## 💎 核心观点（5 分钟速览版）

### 核心观点（5 个关键点）

**1. 盲目扩容是隐形杀手**
```
❌ 错误：积压了就加消费者
✅ 真相：盲目扩容会打垮下游
新增消费者拉取历史消息
→ 抢占带宽和 IO
→ 正常消息无法处理
```

**2. 业务分级隔离**
```
核心实时消息：订单创建、支付结果
→ 独立队列，优先保障

离线批量消息：售后通知、统计埋点
→ 独立队列，允许延迟
```

**3. 堆积预警与应急**
```
实时监控：堆积条数、消费延迟、磁盘占用
差异化应急：
- 短时堆积：优化消费逻辑
- 长时堆积：迁移历史消息
- 极端堆积：限流 + 降级
```

**4. 消费限流管控**
```
限制单个消费者单次拉取数量
防止大量历史消息瞬间压垮下游
```

**5. 架构层优化**
```
消费逻辑轻量化
消息生命周期管控
核心场景开关
```

> **消息积压 = 业务分级（核心/离线隔离） + 堆积预警（实时监控） + 差异化应急（限流/降级/迁移）**

## 一、盲目扩容的危害

### ❌ 典型事故

```
场景：大促结束后，售后消息堆积 100 万条
运维操作：紧急新增 10 台消费实例

结果：
- 新增消费者拉取大量历史消息
- 抢占带宽和 IO 资源
- 正常实时消息得不到处理
- Broker 网卡流量打满
- 整个消息集群濒临不可用
```

**根因分析**：
```
消费者数量 10 → 20
拉取能力翻倍
但下游数据库只能抗 10 倍流量
→ 下游被打垮
→ 消息处理更慢
→ 积压更严重
```

## 二、业务分级隔离

### 2.1 核心实时消息

```go
// 订单创建、支付结果 → 独立队列
type CoreMessage struct {
    MessageID string
    BizType   string // ORDER_CREATED, PAYMENT_SUCCESS
    Data      []byte
}

// 优先保障资源
func SendCoreMessage(msg *CoreMessage) error {
    // 发送到核心 Topic
    return producer.Send("CORE_TOPIC", msg)
}

// 独立消费者组
func ConsumeCoreMessage() {
    consumer := NewConsumer("CORE_GROUP")
    consumer.Subscribe("CORE_TOPIC", func(msg *Message) error {
        // 优先处理
        return processCoreMessage(msg)
    })
}
```

### 2.2 离线批量消息

```go
// 售后通知、统计埋点 → 独立队列
type OfflineMessage struct {
    MessageID string
    BizType   string // AFTER_SALE, ANALYTICS
    Data      []byte
}

// 允许延迟，不抢占核心资源
func SendOfflineMessage(msg *OfflineMessage) error {
    return producer.Send("OFFLINE_TOPIC", msg)
}

// 独立消费者组，限制拉取数量
func ConsumeOfflineMessage() {
    consumer := NewConsumer("OFFLINE_GROUP")
    consumer.SetMaxPullSize(100) // 限制单次拉取数量
    consumer.Subscribe("OFFLINE_TOPIC", func(msg *Message) error {
        return processOfflineMessage(msg)
    })
}
```

## 三、堆积预警与应急

### 3.1 实时监控

```go
type MQMetrics struct {
    QueueSize     int64 // 堆积条数
    ConsumeDelay  int64 // 消费延迟（秒）
    DiskUsage     int64 // 磁盘占用（GB）
    PullTPS       int64 // 拉取 TPS
    ConsumeTPS    int64 // 消费 TPS
}

// 监控采集
func CollectMetrics() *MQMetrics {
    return &MQMetrics{
        QueueSize:    getQueueSize(),
        ConsumeDelay: getConsumeDelay(),
        DiskUsage:    getDiskUsage(),
    }
}

// 告警规则
func CheckAlert() {
    metrics := CollectMetrics()
    
    if metrics.QueueSize > 100000 {
        alert("消息堆积超过 10 万条")
    }
    
    if metrics.ConsumeDelay > 300 {
        alert("消费延迟超过 5 分钟")
    }
    
    if metrics.DiskUsage > 80 {
        alert("磁盘占用超过 80%")
    }
}
```

### 3.2 差异化应急

**短时堆积（< 1 小时）**：
```go
// 优化消费逻辑
func OptimizeConsume() {
    // 1. 批量处理
    consumer.SetBatchSize(100) // 每次处理 100 条
    
    // 2. 并行处理
    for i := 0; i < 10; i++ {
        go func() {
            consumer.Consume()
        }()
    }
}
```

**长时堆积（> 1 小时）**：
```go
// 迁移历史消息
func MigrateOldMessages() {
    // 1. 创建临时 Topic
    producer.CreateTopic("TEMP_TOPIC")
    
    // 2. 迁移历史消息
    messages := consumer.PullOldMessages(100000)
    for _, msg := range messages {
        producer.Send("TEMP_TOPIC", msg)
    }
    
    // 3. 新增消费者处理临时 Topic
    newConsumer := NewConsumer("TEMP_GROUP")
    newConsumer.Subscribe("TEMP_TOPIC", processMessage)
}
```

**极端堆积（> 100 万）**：
```go
// 限流 + 降级
func EmergencyHandle() {
    // 1. 限制拉取速度
    consumer.SetRateLimit(1000) // 每秒最多 1000 条
    
    // 2. 降级非核心消息
    if isNonCoreMessage(msg) {
        // 直接丢弃或写入本地文件
        saveToLocalFile(msg)
        return nil
    }
    
    // 3. 关停低优先级消息生产
    pauseLowPriorityProducer()
}
```

## 四、消费限流管控

### 4.1 限制拉取数量

```go
// 限制单次拉取数量
func ConsumeWithLimit() {
    // 每次最多拉取 100 条
    messages := consumer.Pull(100)
    
    for _, msg := range messages {
        processMessage(msg)
    }
}

// 限制消费速率
func ConsumeWithRateLimit() {
    limiter := rate.NewLimiter(1000, 10) // 每秒 1000 条
    
    for {
        limiter.Wait(context.Background())
        
        msg := consumer.PullOne()
        processMessage(msg)
    }
}
```

### 4.2 防止打垮下游

```go
// 下游限流
func ProcessWithProtection(msg *Message) error {
    // 检查下游负载
    if isDBOverloaded() {
        // 降级处理
        return saveToLocalQueue(msg)
    }
    
    return processMessage(msg)
}

func isDBOverloaded() bool {
    // 检查数据库连接池使用率
    stats := db.Stats()
    return stats.InUse > 80
}
```

## 五、架构层优化

### 5.1 消费逻辑轻量化

```go
// ❌ 复杂消费逻辑
func ProcessMessage(msg *Message) error {
    // 调用第三方接口（耗时 5 秒）
    callThirdPartyAPI()
    
    // 复杂计算（耗时 3 秒）
    doComplexCalculation()
    
    // 写入数据库（耗时 2 秒）
    saveToDB()
    
    return nil // 总耗时 10 秒
}

// ✅ 轻量化消费
func ProcessMessage(msg *Message) error {
    // 只做核心逻辑（耗时 100ms）
    saveToDB(msg)
    
    // 复杂逻辑异步处理
    go func() {
        callThirdPartyAPI()
        doComplexCalculation()
    }()
    
    return nil // 总耗时 100ms
}
```

### 5.2 消息生命周期管控

```go
// 设置消息过期时间
func SendMessage(msg *Message) error {
    // 7 天过期
    msg.SetExpireTime(time.Now().Add(7 * 24 * time.Hour))
    
    return producer.Send(msg)
}

// 自动清理过期消息
func CleanExpiredMessages() {
    ticker := time.NewTicker(1 * time.Hour)
    for range ticker.C {
        expiredMessages := consumer.PullExpired()
        for _, msg := range expiredMessages {
            log.Info("清理过期消息: %s", msg.MessageID)
        }
    }
}
```

### 5.3 核心场景开关

六、技术深入探讨

### Q1: 百万级消息积压怎么处理？

**方案参考**：
> 消息积压不能盲目扩容，要分三步：
> 
> 1. **业务分级**：核心消息和离线消息隔离，优先保障核心消息
> 2. **差异化应急**：
>    - 短时堆积：优化消费逻辑，批量处理
>    - 长时堆积：迁移历史消息到临时 Topic，新增消费者处理
>    - 极端堆积：限流 + 降级，关停低优先级消息
> 3. **消费限流**：限制单次拉取数量和消费速率，防止打垮下游
> 
> 核心是不能盲目扩容，要评估下游承载能力。

### Q2: 如何预防消息积压？

**方案参考**：
> 预防胜于治疗，从三个层面做：
> 
> 1. **监控预警**：实时监控堆积条数、消费延迟、磁盘占用，超过阈值自动告警
> 2. **架构优化**：消费逻辑轻量化，复杂计算异步拆分，避免单条消息处理耗时过长
> 3. **生命周期管控**：设置消息过期时间，无效消息自动清理，防止磁盘持续膨胀
> 
> 大促前要做压测，提前扩容，准备好应急预案。

## 七、总结

### 🎯 一句话总结

> **消息积压 = 业务分级（核心/离线隔离） + 堆积预警（实时监控） + 差异化应急（限流/降级/迁移）**

### 🧠 核心记忆点

1. **盲目扩容有害**：会打垮下游，加剧积压
2. **业务分级**：核心消息优先，离线消息允许延迟
3. **差异化应急**：短时优化逻辑，长时迁移历史，极端限流降级
4. **监控预警**：实时监控，提前发现问题
