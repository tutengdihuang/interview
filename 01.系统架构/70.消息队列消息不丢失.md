# 消息队列消息不丢失

> **场景定位**：分布式消息技术场景  
> **核心设计要点**：全链路保障、消息丢失防护、重复消费处理

---

## 🎯 一句话定位

**消息队列消息不丢失解决什么问题？**
```
消息从生产者到消费者，全链路保证不丢失
生产端、Broker、消费端都要有兜底方案
```

**生活化比喻**：
就像快递系统：
- 寄件人（生产者）：确认快递已收件
- 快递站（Broker）：确认快递已入库
- 收件人（消费者）：确认快递已签收

每个环节都要有确认机制，快递才不会丢。

---

## 💎 核心观点（5 分钟速览版）

### 核心观点（5 个关键点）

**1. 三类丢失场景**
```
生产端丢失：发送失败没重试
Broker 丢失：宕机前没刷盘
消费端丢失：消费失败没重试
```

**2. 全链路保障方案**
```
生产端：同步发送 + 重试机制
Broker：持久化 + 主从同步
消费端：手动 ACK + 幂等处理
```

**3. 消息积压是隐形杀手**
```
百万级积压 → Broker 磁盘打满
→ 新消息无法写入
→ 整个集群不可用
```

**4. 重复消费必须处理**
```
网络抖动 → 消息重复投递
必须：唯一消息 ID + 去重表 + 幂等
```

**5. 死信队列是兜底**
```
消费失败的消息进死信队列
人工介入或定时重试
不能直接丢弃
```

---

## 🚀 一句话精华

> **消息不丢失 = 生产端确认（同步+重试） + Broker 持久化（刷盘+主从） + 消费端 ACK（手动+幂等）**

## 一、生产端消息丢失

### ❌ 典型问题

```go
// ❌ 异步发送，不处理结果
producer.Send(msg, func(err error) {
    // Bug: 失败也不重试
})

// ❌ 超时时间太短
producer.SetTimeout(100 * time.Millisecond) // 网络抖动就丢失
```

### ✅ 正确方案

**同步发送 + 重试**：
```go
func SendMessage(msg *Message) error {
    maxRetries := 3
    for i := 0; i < maxRetries; i++ {
        err := producer.SendSync(msg)
        if err == nil {
            return nil
        }
        
        log.Warn("发送失败，重试 %d/3: %v", i+1, err)
        time.Sleep(time.Duration(i+1) * time.Second)
    }
    
    // 重试失败，写入本地消息表
    db.InsertLocalMessage(msg)
    return errors.New("发送失败，已写入本地消息表")
}

// 定时任务：扫描本地消息表，重新发送
func RetryLocalMessages() {
    messages := db.QueryLocalMessages("PENDING")
    for _, msg := range messages {
        err := producer.SendSync(msg)
        if err == nil {
            db.UpdateMessageStatus(msg.ID, "SENT")
        }
    }
}
```

**关键点**：
- ✅ **同步发送**：等待 Broker 确认
- ✅ **重试机制**：失败自动重试 3 次
- ✅ **本地消息表**：最终兜底

## 二、Broker 消息丢失

### ❌ 典型问题

```
异步刷盘：消息写入内存就返回
Broker 宕机 → 内存消息丢失

单节点：没有主从同步
节点宕机 → 所有消息丢失
```

### ✅ 正确方案

**同步刷盘 + 主从同步**：
```properties
# RocketMQ 配置
# 同步刷盘
flushDiskType = SYNC_FLUSH

# 主从同步
brokerRole = SYNC_MASTER

# Kafka 配置
# acks=all：所有副本确认
acks=all

# min.insync.replicas=2：至少 2 个副本同步
min.insync.replicas=2

# retries=3：发送失败重试
retries=3
```

**关键点**：
- ✅ **同步刷盘**：消息落盘才返回
- ✅ **主从同步**：多个副本同时写入
- ✅ **acks=all**：所有副本确认

## 三、消费端消息丢失

### ❌ 典型问题

```go
// ❌ 自动 ACK
consumer.Subscribe("topic", func(msg *Message) {
    // Bug: 处理失败也会 ACK
    processMessage(msg)
})

// ❌ 先 ACK 再处理
consumer.Subscribe("topic", func(msg *Message) {
    consumer.ACK(msg) // 先确认
    processMessage(msg) // 处理失败就丢了
})
```

### ✅ 正确方案

**手动 ACK + 幂等**：
```go
// 手动 ACK
consumer.Subscribe("topic", func(msg *Message) error {
    // 1. 幂等检查
    if db.Exists(msg.MessageID) {
        log.Info("重复消息，跳过")
        return nil
    }
    
    // 2. 处理业务
    err := processMessage(msg)
    if err != nil {
        return err // 失败不 ACK，自动重试
    }
    
    // 3. 记录已处理
    db.InsertProcessedMessage(msg.MessageID)
    
    // 4. 手动 ACK
    consumer.ACK(msg)
    return nil
})
```

**幂等处理**：
```go
func processMessage(msg *Message) error {
    // 唯一消息 ID + 去重表
    tx := db.Begin()
    
    // 插入去重表（唯一约束）
    err := tx.Exec(`
        INSERT INTO consumed_messages (message_id, created_at)
        VALUES (?, NOW())
    `, msg.MessageID).Error
    
    if err != nil {
        // 重复消息
        return nil
    }
    
    // 处理业务
    err = doBusinessLogic(msg)
    if err != nil {
        tx.Rollback()
        return err
    }
    
    tx.Commit()
    return nil
}
```

## 四、消息积压处理

### 4.1 积压原因

```
消费者太少：处理能力不足
消费逻辑慢：单条处理耗时过长
下游故障：数据库/第三方接口超时
```

### 4.2 应急方案

**临时扩容 + 限流**：
```go
// 1. 临时扩容消费者
// 增加消费实例数量

// 2. 消费限流（防止打垮下游）
func ConsumeWithRateLimit(msg *Message) error {
    // 限制每秒处理 1000 条
    limiter.Wait(context.Background())
    
    return processMessage(msg)
}

// 3. 迁移历史消息（分流）
func MigrateOldMessages() {
    // 把堆积的历史消息迁移到新 Topic
    // 用新的消费者组处理
}
```

**核心原则**：
- ✅ **分级处理**：核心消息优先，非核心消息延迟
- ✅ **限流消费**：防止打垮下游
- ✅ **历史分流**：新旧消息分开处理

## 五、死信队列兜底

### 5.1 死信队列作用

```
消费失败的消息 → 进入死信队列
人工介入 or 定时重试
不能直接丢弃
```

### 5.2 实现方案

```go
// 消费失败 3 次后进入死信队列
func ConsumeWithDeadLetter(msg *Message) error {
    err := processMessage(msg)
    if err != nil {
        if msg.RetryCount >= 3 {
            // 进入死信队列
            deadLetterQueue.Send(msg)
            log.Error("消息进入死信队列: %s", msg.MessageID)
            return nil // ACK，不再重试
        }
        
        return err // 继续重试
    }
    return nil
}

// 定时处理死信队列
func HandleDeadLetter() {
    messages := deadLetterQueue.Query()
    for _, msg := range messages {
        // 人工介入
        alert("死信队列有消息: %s", msg.MessageID)
        
        // 或定时重试
        retryDeadLetterMessage(msg)
    }
}
```

六、技术深入探讨

### Q1: 消息丢失怎么排查？

**方案参考**：
> 消息丢失要分三段排查：
> 
> 1. **生产端**：看发送日志，是否有失败记录。检查是否用了异步发送，是否配置了重试
> 2. **Broker 端**：看监控，是否有宕机记录。检查持久化配置（同步刷盘 vs 异步刷盘）
> 3. **消费端**：看消费日志，是否有处理失败。检查是否用了自动 ACK
> 
> 关键是要有全链路追踪，每个环节都有日志和监控。

### Q2: 百万级消息积压怎么处理？

**方案参考**：
> 消息积压是严重问题，处理分三步：
> 
> 1. **紧急扩容**：增加消费者实例数量
> 2. **消费限流**：限制单消费者拉取数量，防止打垮下游
> 3. **历史分流**：把堆积的历史消息迁移到新 Topic，用新的消费者组处理
> 
> 核心是不能盲目扩容，要评估下游承载能力。
