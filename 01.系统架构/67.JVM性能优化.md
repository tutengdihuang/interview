# JVM 性能优化

> **场景定位**：后端性能优化技术场景  
> **核心设计要点**：内存管控、GC 调优、监控告警、架构优化

---

## 🎯 一句话定位

**JVM 性能优化解决什么问题？**
```
服务运行一段时间后，性能逐渐恶化
接口响应越来越慢，GC 越来越频繁
最终导致服务不可用
```

**生活化比喻**：
就像人年纪大了，身体机能逐渐下降：
- 新陈代谢变慢（GC 效率下降）
- 记忆力衰退（内存泄漏）
- 反应迟钝（响应变慢）

需要定期体检（监控）+ 保健（调优）+ 治病（修复）

---

## 💎 核心观点（5 分钟速览版）

### 核心观点（5 个关键点）

**1. 调几个 GC 参数只是入门**
```
❌ 误区：调大堆内存，换个回收器就完事
✅ 真相：JVM 优化是全生命周期内存管控
对象创建 → 使用 → 回收，每个环节都要管
```

**2. 隐性对象增长是幽灵陷阱**
```
服务跑了一周，突然频繁 Full GC
Dump 一看，没有大对象，没有明显泄漏
但就是内存占用越来越高

根因：隐性对象增长（缓存无上限、集合无限扩容）
```

**3. 场景分级精细化管控**
```
核心链路：短生命周期对象严格控制在新生代
非核心链路：严控对象生成数量
长生命周期资源：池化复用（连接池、线程池）
```

**4. 监控兜底与快速止损**
```
实时监控：各分代内存占比、GC 频率、停顿时长
自动告警：指标超过阈值自动告警
快速止损：GC 恶化时自动限流降级
```

**5. 架构层优化**
```
核心低延迟场景：ZGC（亚毫秒级停顿）
热点代码路径：对象复用、零拷贝
按业务域拆分：隔离内存资源
```

## 一、隐性对象增长（幽灵陷阱）

### ❌ 典型案例

**现象**：
```
服务上线一周，突然频繁 Full GC
接口响应时间从 50ms 飙升到 5s
Dump 堆内存，没有发现明显问题：
- 没有超大对象
- 没有集合无限扩容
- 代码近期没有改动

但内存占用一路上涨，GC 回收效果越来越差
```

**根因分析**：
```go
// ❌ 隐性对象增长 1：缓存无上限
var localCache = make(map[string]*User)

func GetUser(userID string) *User {
    if user, ok := localCache[userID]; ok {
        return user
    }
    user := db.QueryUser(userID)
    // Bug: 只写不删，无限增长
    localCache[userID] = user
    return user
}

// ❌ 隐性对象增长 2：静态集合
type Metrics struct {
    history []int64 // 无限增长
}

func (m *Metrics) Record(val int64) {
    m.history = append(m.history, val) // 永远不清理
}

// ❌ 隐性对象增长 3：ThreadLocal 未清理
var threadLocal = &sync.Map{}

func ProcessRequest() {
    threadLocal.Store("session", NewSession())
    // Bug: 请求结束后未清理
    // 线程池场景下，ThreadLocal 永远不会回收
}
```

**排查方法**：
```bash
# 1. 对比正常和异常时段的 Dump
jmap -dump:format=b,file=heap_normal.hprof <pid>
# 等待一段时间后
jmap -dump:format=b,file=heap_abnormal.hprof <pid>

# 2. 用 MAT 对比分析
# 找到增长最快的对象类型

# 3. 分析代码
# 找到这些对象的创建和引用链路
```

## 二、场景分级精细化管控

### 2.1 核心链路优化

**对象生命周期管控**：
```go
// ✅ 短生命周期对象：控制在新生代
func HandleRequest(req *Request) *Response {
    // 临时对象，新生代回收
    result := &Response{}
    return result
}

// ✅ 长生命周期资源：池化复用
var connectionPool = NewConnectionPool(100)

func QueryDB(sql string) (*Result, error) {
    conn := connectionPool.Get()
    defer connectionPool.Put(conn)
    
    return conn.Query(sql)
}
```

### 2.2 非核心链路限制

```go
// ✅ 非核心链路：严控对象生成
func LogRequest(req *Request) {
    // 非核心逻辑，用简单的日志对象
    // 不要创建复杂的日志上下文
    logger.Info("request: %v", req.ID)
}

// ✅ 异步处理
func NotifyUser(user *User) {
    // 异步发送通知，不阻塞主流程
    go func() {
        notification := &Notification{...}
        sendNotification(notification)
    }()
}
```

## 三、GC 调优

### 3.1 回收器选择

**四类回收器对比**：
```
Serial：单线程，适合客户端模式
Parallel：多线程，吞吐量优先
CMS：低延迟，但有浮动垃圾问题
G1：分区回收，平衡延迟和吞吐（推荐）
ZGC：亚毫秒级停顿，超低延迟（核心场景）
```

**推荐配置**：
```bash
# G1 回收器（通用场景）
java -Xms4g -Xmx4g \
     -XX:+UseG1GC \
     -XX:MaxGCPauseMillis=200 \
     -XX:G1HeapRegionSize=8m \
     -XX:InitiatingHeapOccupancyPercent=45 \
     -jar app.jar

# ZGC 回收器（低延迟场景）
java -Xms8g -Xmx8g \
     -XX:+UseZGC \
     -XX:+ZGenerational \
     -jar app.jar
```

### 3.2 新生代比例调优

**核心原则**：
```
新生代太小 → 对象频繁晋升老年代 → Full GC 频繁
新生代太大 → 老年代太小 → 长生命周期对象没地方放

推荐：新生代占堆的 1/3 到 1/2
```

**调优示例**：
```bash
# 新生代比例调优
java -Xms4g -Xmx4g \
     -XX:NewRatio=2 \  # 老年代:新生代 = 2:1
     -XX:SurvivorRatio=8 \  # Eden:Survivor = 8:1
     -jar app.jar
```

## 四、监控告警

### 4.1 核心指标

```go
// JVM 监控指标
type JVMMetrics struct {
    // 内存指标
    HeapUsed      int64 // 堆使用量
    HeapMax       int64 // 堆最大值
    YoungGenUsed  int64 // 新生代使用量
    OldGenUsed    int64 // 老年代使用量
    
    // GC 指标
    YoungGCCount  int64 // Young GC 次数
    YoungGCTime   int64 // Young GC 耗时
    FullGCCount   int64 // Full GC 次数
    FullGCTime    int64 // Full GC 耗时
    
    // 其他指标
    ThreadCount   int64 // 线程数
    ClassCount    int64 // 类数量
}
```

**Prometheus 监控**：
```yaml
groups:
  - name: jvm
    rules:
      - alert: HighHeapUsage
        expr: jvm_memory_used_bytes{area="heap"} / jvm_memory_max_bytes{area="heap"} > 0.8
        for: 5m
        annotations:
          summary: "堆内存使用率超过 80%"
          
      - alert: FrequentFullGC
        expr: rate(jvm_gc_pause_seconds_count{action="end of major GC"}[5m]) > 1
        annotations:
          summary: "Full GC 频率过高"
          
      - alert: LongGCPause
        expr: jvm_gc_pause_seconds > 1
        annotations:
          summary: "GC 停顿时间过长"
```

### 4.2 快速止损

```go
// GC 恶化时自动限流
func GCDegradeMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        // 检查 GC 指标
        if isGCDegrading() {
            // 非核心接口直接降级
            if isNonCoreAPI(r.URL.Path) {
                w.Write([]byte(`{"code": 503, "msg": "服务降级中"}`))
                return
            }
        }
        next.ServeHTTP(w, r)
    })
}

func isGCDegrading() bool {
    // 检查 Full GC 频率
    fullGCCount := getFullGCCount()
    return fullGCCount > 10 // 1 分钟内 Full GC 超过 10 次
}
```

## 五、架构层优化

### 5.1 对象复用

```go
// ✅ 对象池复用
var bufferPool = sync.Pool{
    New: func() interface{} {
        return make([]byte, 0, 1024)
    },
}

func ProcessData() {
    buf := bufferPool.Get().([]byte)
    defer bufferPool.Put(buf[:0])
    
    // 使用 buf
    buf = append(buf, "data"...)
}
```

### 5.2 零拷贝优化

```go
// ❌ 传统 IO（多次拷贝）
func CopyFile(src, dst string) error {
    in, _ := os.Open(src)
    defer in.Close()
    out, _ := os.Create(dst)
    defer out.Close()
    
    buf := make([]byte, 1024)
    for {
        n, _ := in.Read(buf)
        if n == 0 {
            break
        }
        out.Write(buf[:n])
    }
    return nil
}

// ✅ 零拷贝（sendfile）
func CopyFileZeroCopy(src, dst string) error {
    in, _ := os.Open(src)
    defer in.Close()
    out, _ := os.Create(dst)
    defer out.Close()
    
    // 零拷贝，内核态直接传输
    inFd := in.Fd()
    outFd := out.Fd()
    syscall.Sendfile(int(outFd), int(inFd), nil, 1024*1024)
    return nil
}
```

六、技术深入探讨

### Q1: 服务跑了一周后频繁 Full GC，怎么排查？

**方案参考**：
> 这是典型的隐性对象增长问题，排查分三步：
> 
> 1. **对比分析**：Dump 正常和异常时段的堆内存，用 MAT 对比，找到增长最快的对象类型
> 2. **代码走查**：分析这些对象的创建和引用链路，常见的坑有：
>    - 本地缓存无上限（只写不删）
>    - 静态集合无限增长
>    - ThreadLocal 未清理
> 3. **修复验证**：修复后灰度发布，持续观察一周
> 
> 关键是要有监控，提前发现问题。

### Q2: G1 和 ZGC 怎么选？

**方案参考**：
> 两类回收器场景不同：
> 
> **G1**：
> - 停顿时间：100-200ms
> - 适用场景：大部分业务系统
> - 优点：平衡延迟和吞吐
> 
> **ZGC**：
> - 停顿时间：< 1ms
> - 适用场景：低延迟要求的核心链路
> - 优点：超低延迟，但吞吐略低
> 
> 推荐：核心交易用 ZGC，非核心用 G1。

## 七、总结

### 🎯 一句话总结

> **JVM 优化 = 内存管控（对象生命周期） + GC 调优（回收器选择） + 监控告警（快速止损） + 架构优化（根源治理）**

### 🧠 核心记忆点

1. **隐性对象增长是幽灵**：缓存无上限、集合无限扩容、ThreadLocal 未清理
2. **场景分级**：核心链路精细化管控，非核心链路严控对象生成
3. **监控告警**：实时监控内存和 GC 指标，自动告警
4. **架构优化**：对象复用、零拷贝、按业务域隔离
