# Spring 事务失效场景与解决方案

> **场景定位**：Spring 框架技术场景  
> **核心设计要点**：事务失效场景、AOP 代理、异常类型、传播机制、事务粒度、监控补偿

---

## 🎯 一句话定位

**Spring 事务失效问题是什么？**
```
加了 @Transactional 注解，但事务没有生效：
- 主表插入成功，附属表插入失败
- 数据一半成功一半失败
- 事务完全没有回滚
- 产生大量脏数据
```

**生活化比喻**：就像你在合同上签字（@Transactional），但合同可能是假合同（AOP 代理失效），或者签字方式不对（异常类型错误），导致合同无效。

**核心特点**：Spring 事务不仅仅是加个注解，而是 AOP 代理、异常规则、编码规范三者配合的完整可靠性体系。

## 💎 核心观点（5 分钟速览版）

> **快速概览**

### 核心观点（3 层防御）

**1. 避开基础失效场景：编码规范兜底**
```
同类内部方法调用：
- @Transactional 无效
- 只能走外部 Bean 调用
- 才能被 AOP 代理拦截

方法修饰符：
- 事务方法不能用 private、static、final 修饰
- 导致无法生成代理类
- 事务直接失效

数据库引擎：
- 必须使用支持事务的 InnoDB 引擎
- MyISAM 本身不支持事务
- 加注解也没用

生活化比喻：
同类调用 = 自己签合同（无效）
方法修饰符 = 签字方式不对（无效）
数据库引擎 = 合同纸张不对（无效）
```

**2. 异常与传播机制把控：避免隐形坑**
```
异常类型：
- 默认只捕获 RuntimeException
- 受检异常（Exception）不回滚
- 需要手动配置 rollbackFor 指定所有异常

try-catch 吃掉异常：
- 事务内部 try-catch 吃掉异常
- 不向外抛出
- Spring 感知不到异常，自然不会回滚

传播级别：
- REQUIRES_NEW、SUPPORTS 混用
- 导致事务嵌套混乱
- 回滚失效

生活化比喻：
异常类型 = 只处理某种违约（其他违约不管）
try-catch = 掩盖违约事实（Spring 不知道）
传播级别 = 合同嵌套规则混乱
```

**3. 业务架构层面优化：保障数据一致**
```
事务粒度：
- 核心支付、下单链路
- 强制拆分事务粒度
- 避免大事务长耗时占用数据库连接

事务监控：
- 关键业务增加事务状态监控
- 日志记录事务提交、回滚轨迹
- 便于线上排查

兜底补偿：
- 定时任务校对上下游数据
- 自动修复因事务失效产生的脏数据

生活化比喻：
事务粒度 = 合同拆分成多个小合同
事务监控 = 合同签订过程全程录像
兜底补偿 = 定期对账，发现问题立即修正
```

## 一、问题本质：Spring 事务的隐性风险

### ❌ 常见误区

**误区 1：加了 @Transactional 就万事大吉**
```
问题：
- 同类内部方法调用，事务失效
- 方法用 private 修饰，无法生成代理
- 数据库引擎不支持事务

解决：
- 外部 Bean 调用事务方法
- 事务方法用 public 修饰
- 使用 InnoDB 引擎
```

**误区 2：异常会自动回滚**
```
问题：
- 默认只捕获 RuntimeException
- 受检异常不回滚
- try-catch 吃掉异常，Spring 感知不到

解决：
- 配置 rollbackFor = Exception.class
- 不要 try-catch 吃掉异常
- 或者手动抛出异常
```

**误区 3：事务传播机制随便用**
```
问题：
- REQUIRES_NEW、SUPPORTS 混用
- 事务嵌套混乱
- 回滚失效

解决：
- 理解 7 种传播机制
- 根据业务场景选择
- 避免不必要的嵌套
```

## 二、第一层防御：避开基础失效场景

### 2.1 同类内部方法调用

**生活化比喻**：
```
同类调用 = 自己签合同（无效）
- A 方法调用 B 方法（同一个类）
- B 方法加了 @Transactional
- 但事务失效

原因：
- Spring AOP 代理无法拦截同类内部调用
- 只能通过外部 Bean 调用，才能被代理拦截

就像：
- 自己和自己签合同，法律上无效
- 必须和外部实体签合同
- 才能被法律认可
```

**代码示例**：
```java
@Service
public class OrderService {
    
    // ❌ 错误做法：同类内部调用，事务失效
    public void createOrder(Order order) {
        // 调用同类的事务方法
        doCreateOrder(order);
    }
    
    @Transactional
    public void doCreateOrder(Order order) {
        orderMapper.insert(order);
        stockMapper.deductStock(order.getProductId(), order.getQuantity());
    }
    
    // ✅ 正确做法：外部 Bean 调用
    @Autowired
    private OrderTransactionService orderTransactionService;
    
    public void createOrder(Order order) {
        // 调用外部 Bean 的事务方法
        orderTransactionService.doCreateOrder(order);
    }
}

@Service
public class OrderTransactionService {
    
    @Transactional
    public void doCreateOrder(Order order) {
        orderMapper.insert(order);
        stockMapper.deductStock(order.getProductId(), order.getQuantity());
    }
}
```

### 2.2 方法修饰符

**生活化比喻**：
```
方法修饰符 = 签字方式
- private、static、final 修饰的方法
- 无法生成代理类
- 事务直接失效

就像：
- 签字必须用笔，不能用其他方式
- 方法必须是 public，才能被代理
```

**代码示例**：
```java
@Service
public class OrderService {
    
    // ❌ 错误做法：private 方法，事务失效
    @Transactional
    private void createOrder(Order order) {
        orderMapper.insert(order);
    }
    
    // ❌ 错误做法：static 方法，事务失效
    @Transactional
    public static void createOrder(Order order) {
        orderMapper.insert(order);
    }
    
    // ❌ 错误做法：final 方法，事务失效
    @Transactional
    public final void createOrder(Order order) {
        orderMapper.insert(order);
    }
    
    // ✅ 正确做法：public 方法
    @Transactional
    public void createOrder(Order order) {
        orderMapper.insert(order);
    }
}
```

### 2.3 数据库引擎

**生活化比喻**：
```
数据库引擎 = 合同纸张
- InnoDB 支持事务
- MyISAM 不支持事务
- 加注解也没用

就像：
- 合同必须写在正式纸张上
- 写在餐巾纸上无效
```

**代码示例**：
```sql
-- 查看表引擎
SHOW TABLE STATUS LIKE 'orders';

-- 创建表时指定引擎
CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    user_id BIGINT,
    amount DECIMAL(10, 2)
) ENGINE=InnoDB; -- 必须用 InnoDB

-- 修改表引擎
ALTER TABLE orders ENGINE=InnoDB;
```

## 三、第二层防御：异常与传播机制把控

### 3.1 异常类型（rollbackFor）

**生活化比喻**：
```
异常类型 = 违约类型
- 默认只捕获 RuntimeException
- 受检异常（Exception）不回滚
- 需要手动配置 rollbackFor

就像：
- 合同只处理某种违约
- 其他违约不管
- 必须明确约定所有违约类型
```

**代码示例**：
```java
@Service
public class OrderService {
    
    // ❌ 错误做法：默认只回滚 RuntimeException
    @Transactional
    public void createOrder(Order order) throws Exception {
        orderMapper.insert(order);
        
        // 抛出受检异常，不会回滚
        throw new Exception("创建失败");
    }
    
    // ✅ 正确做法：指定 rollbackFor
    @Transactional(rollbackFor = Exception.class)
    public void createOrder(Order order) throws Exception {
        orderMapper.insert(order);
        
        // 抛出受检异常，也会回滚
        throw new Exception("创建失败");
    }
    
    // ✅ 正确做法：指定多个异常
    @Transactional(rollbackFor = {Exception.class, CustomException.class})
    public void createOrder(Order order) {
        orderMapper.insert(order);
    }
}
```

### 3.2 try-catch 吃掉异常

**生活化比喻**：
```
try-catch = 掩盖违约事实
- 事务内部 try-catch 吃掉异常
- 不向外抛出
- Spring 感知不到异常，自然不会回滚

就像：
- 违约了但不告诉对方
- 对方不知道，自然不会追责
```

**代码示例**：
```java
@Service
public class OrderService {
    
    // ❌ 错误做法：try-catch 吃掉异常，事务不回滚
    @Transactional
    public void createOrder(Order order) {
        try {
            orderMapper.insert(order);
            stockMapper.deductStock(order.getProductId(), order.getQuantity());
        } catch (Exception e) {
            log.error("创建订单失败", e);
            // 异常被吃掉，Spring 感知不到，事务不回滚
        }
    }
    
    // ✅ 正确做法：抛出异常，让 Spring 感知
    @Transactional(rollbackFor = Exception.class)
    public void createOrder(Order order) {
        try {
            orderMapper.insert(order);
            stockMapper.deductStock(order.getProductId(), order.getQuantity());
        } catch (Exception e) {
            log.error("创建订单失败", e);
            // 手动抛出异常
            throw new RuntimeException("创建订单失败", e);
        }
    }
}
```

### 3.3 事务传播级别

**生活化比喻**：
```
传播级别 = 合同嵌套规则
- 7 种传播机制
- REQUIRES_NEW、SUPPORTS 混用
- 导致事务嵌套混乱，回滚失效

就像：
- 主合同和子合同的关系
- 规则混乱，责任不清
```

**7 种传播机制**：
```
REQUIRED（默认）：
- 如果当前有事务，就加入
- 如果没有，就创建一个新事务

REQUIRES_NEW：
- 创建一个新事务
- 如果当前有事务，挂起当前事务

SUPPORTS：
- 如果当前有事务，就加入
- 如果没有，就以非事务方式执行

MANDATORY：
- 必须在一个已有事务中运行
- 否则抛出异常

NOT_SUPPORTED：
- 以非事务方式执行
- 如果当前有事务，挂起当前事务

NEVER：
- 以非事务方式执行
- 如果当前有事务，抛出异常

NESTED：
- 如果当前有事务，就在嵌套事务中执行
- 如果没有，就创建一个新事务
```

**代码示例**：
```java
@Service
public class OrderService {
    
    @Autowired
    private PaymentService paymentService;
    
    // 外层事务
    @Transactional
    public void createOrder(Order order) {
        orderMapper.insert(order);
        
        // 调用内层事务（REQUIRES_NEW）
        paymentService.processPayment(order);
        
        // 内层事务失败，外层事务不受影响
    }
}

@Service
public class PaymentService {
    
    // 内层事务（REQUIRES_NEW）
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void processPayment(Order order) {
        paymentMapper.insert(order.getPayment());
    }
}
```

## 四、第三层防御：业务架构层面优化

### 4.1 事务粒度

**生活化比喻**：
```
事务粒度 = 合同拆分
- 核心支付、下单链路
- 强制拆分事务粒度
- 避免大事务长耗时占用数据库连接

就像：
- 大额合同拆分成多个小合同
- 每个小合同独立处理
- 提高并发能力
```

**代码示例**：
```java
@Service
public class OrderService {
    
    // ❌ 错误做法：大事务，包含非核心操作
    @Transactional
    public void createOrder(Order order) {
        // 核心操作
        orderMapper.insert(order);
        stockMapper.deductStock(order.getProductId(), order.getQuantity());
        
        // 非核心操作（不应该在事务中）
        sendEmail(order); // 发送邮件
        saveLog(order); // 记录日志
    }
    
    // ✅ 正确做法：拆分事务粒度
    @Transactional
    public void createOrder(Order order) {
        // 只包含核心操作
        orderMapper.insert(order);
        stockMapper.deductStock(order.getProductId(), order.getQuantity());
    }
    
    // 非核心操作在事务外
    public void createOrderWithNotify(Order order) {
        createOrder(order); // 事务方法
        
        // 非核心操作在事务外
        sendEmail(order);
        saveLog(order);
    }
}
```

### 4.2 事务监控

**代码示例**：
```java
@Component
public class TransactionMonitorService {
    
    @Autowired
    private TransactionLogMapper transactionLogMapper;
    
    /**
     * 记录事务日志
     */
    public void logTransaction(String methodName, String status, String errorMessage) {
        TransactionLog log = new TransactionLog();
        log.setMethodName(methodName);
        log.setStatus(status); // SUCCESS, FAILED, ROLLBACK
        log.setErrorMessage(errorMessage);
        log.setCreatedAt(new Date());
        
        transactionLogMapper.insert(log);
    }
    
    /**
     * 监控事务失败率
     */
    @Scheduled(fixedRate = 300000) // 每 5 分钟检查一次
    public void monitorTransactionFailure() {
        // 统计最近 1 小时的事务失败率
        long totalTransactions = getTotalTransactions(1);
        long failedTransactions = getFailedTransactions(1);
        
        double failureRate = (double) failedTransactions / totalTransactions;
        
        if (failureRate > 0.05) { // 失败率超过 5%
            sendAlert("事务失败率告警：" + failureRate);
        }
    }
    
    private void sendAlert(String message) {
        System.out.println("[ALERT] " + message);
    }
}
```

### 4.3 兜底补偿

**代码示例**：
```java
@Service
public class CompensationService {
    
    @Autowired
    private OrderMapper orderMapper;
    
    @Autowired
    private StockMapper stockMapper;
    
    /**
     * 定时对账（每天凌晨 2 点）
     */
    @Scheduled(cron = "0 0 2 * * ?")
    public void compensation() {
        // 1. 查询已创建但未扣减库存的订单
        List<Order> orders = orderMapper.selectCreatedButNotDeducted();
        
        for (Order order : orders) {
            try {
                // 2. 补偿扣减库存
                stockMapper.deductStock(order.getProductId(), order.getQuantity());
                
                // 3. 更新订单状态
                orderMapper.updateStatus(order.getId(), "DEDUCTED");
                
                log.info("补偿成功，orderId={}", order.getId());
                
            } catch (Exception e) {
                log.error("补偿失败，orderId={}", order.getId(), e);
                sendAlert("补偿失败，需要人工介入，orderId=" + order.getId());
            }
        }
    }
    
    private void sendAlert(String message) {
        System.out.println("[ALERT] " + message);
    }
}
```

### 考点 1：Spring 事务什么时候会失效？

**方案参考**（30 秒版）：

**加分回答**：
> "实际生产中，我会建立完整的事务保障体系：编码规范层面，避免同类调用、方法修饰符错误、数据库引擎不支持；异常传播层面，配置 rollbackFor，不要 try-catch 吃掉异常，理解传播机制；架构优化层面，拆分事务粒度，避免大事务，增加事务监控，定时对账补偿。同时要记录事务日志，便于排查问题。"

### 考点 2：同类内部调用为什么事务失效？

**方案参考**：
> "同类内部调用事务失效是因为 Spring AOP 代理无法拦截。Spring 事务是基于 AOP 代理实现的，同类内部调用不经过代理对象，所以事务注解失效。解决方案是将事务方法抽取到另一个 Bean 中，通过外部 Bean 调用，才能被 AOP 代理拦截。"

**加分回答**：
> "除了抽取到另一个 Bean，还可以用 AopContext.currentProxy() 获取当前代理对象，然后调用事务方法。但这种方式不够优雅，推荐使用外部 Bean 调用。同时要理解 Spring AOP 的代理原理，JDK 动态代理和 CGLIB 代理的区别，才能避免类似的坑。"

### 考点 3：如何保证事务一定生效？

**方案参考**：
> "保证事务生效要三层防御：1）编码规范：外部 Bean 调用、public 方法、InnoDB 引擎；2）异常传播：rollbackFor = Exception.class、不要 try-catch 吃掉异常、理解传播机制；3）架构优化：拆分事务粒度、事务监控、定时对账补偿。"

**加分回答**：
> "我会建立完整的事务保障体系：编码规范层面，制定开发规范，避免同类调用、方法修饰符错误；异常传播层面，统一配置 rollbackFor，制定异常处理规范；架构优化层面，拆分事务粒度，避免大事务，增加事务监控，定时对账补偿。同时要记录事务日志，便于排查问题。核心是预判风险，多层兜底。"

## 六、总结（一句话带走）

### 🎯 一句话总结

> **Spring 事务三层防御 = 编码规范（避免同类调用/方法修饰符/数据库引擎） + 异常传播（rollbackFor/try-catch/传播级别） + 架构优化（事务粒度/监控/补偿）**

### 🧠 核心记忆点

1. **同类内部调用为什么失效？** AOP 代理无法拦截，必须外部 Bean 调用。
2. **方法修饰符为什么影响事务？** private、static、final 无法生成代理类。
3. **异常类型为什么影响回滚？** 默认只捕获 RuntimeException，受检异常不回滚。
4. **try-catch 为什么影响回滚？** 吃掉异常，Spring 感知不到。
5. **如何保证事务生效？** 编码规范 + 异常传播 + 架构优化，三层防御。
