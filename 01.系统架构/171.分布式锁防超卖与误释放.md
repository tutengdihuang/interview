# 分布式锁防超卖与误释放

> **场景定位**：分布式系统技术场景  
> **核心设计要点**：分布式锁、锁续期、唯一标识、可重入锁、锁降级、幂等控制、Redlock

---

## 🎯 一句话定位

**分布式锁问题是什么？**
```
锁已经过期但业务逻辑还没执行完，锁被其他线程抢占释放：
- 电商秒杀场景，用户抢购爆款商品
- 服务用 Redis 分布式锁控制库存扣减
- 出现大量超卖，主库库存直接扣成负数
- 商家被迫紧急下架商品，用户投诉直接炸锅
```

**生活化比喻**：就像公共厕所的门锁，你进去后锁上了，但超过 30 分钟没出来，锁自动开了，其他人以为没人，又进去了，结果两个人同时在里面。

**核心特点**：分布式锁不仅仅是 setnx + 过期时间，还需要锁续期、唯一标识、可重入锁等完整保障体系。

## 一、问题本质：分布式锁的隐性风险

### ❌ 常见误区

**误区 1：setnx + 过期时间就够了**
```
问题：
- 锁过期但业务未执行完
- 其他线程抢占锁
- 并发重复扣减库存

解决：
- 锁绑定唯一标识
- 锁自动续期
- 可重入锁设计
```

**误区 2：解锁直接 delete**
```
问题：
- 直接 delete 可能删除其他线程的锁
- A 线程锁过期，B 线程获取锁
- A 线程任务完成，delete 锁
- B 线程的锁被误删

解决：
- 解锁前校验唯一标识
- 只允许释放自己的锁
- 用 Lua 脚本保证原子性
```

**误区 3：分布式锁不会失效**
```
问题：
- Redis 单节点故障
- 锁服务不可用
- 核心链路崩溃

解决：
- 锁降级方案（数据库悲观锁）
- 集群高可用（Redis Cluster/Redlock）
- 异步解耦（消息队列削峰）
```

## 二、第一层防御：锁机制优化

### 2.1 锁绑定唯一标识

**生活化比喻**：
```
唯一标识 = 锁上刻你的名字
- 加锁时存入线程唯一 ID
- 解锁前校验归属
- 只允许释放自己的锁

就像：
- 厕所门锁上刻你的名字
- 只有你能开
- 别人开不了
```

**代码示例**：
```java
@Service
public class RedisLockService {
    
    @Autowired
    private StringRedisTemplate redisTemplate;
    
    /**
     * 获取分布式锁（带唯一标识）
     */
    public boolean tryLock(String lockKey, String requestId, long expireSeconds) {
        // 加锁时存入线程唯一 ID
        Boolean result = redisTemplate.execute(
            (RedisCallback<Boolean>) connection -> 
                connection.set(
                    lockKey.getBytes(),
                    requestId.getBytes(),
                    Expiration.seconds(expireSeconds),
                    RedisStringCommands.SetOption.SET_IF_ABSENT
                )
        );
        
        return result != null && result;
    }
    
    /**
     * 释放分布式锁（Lua 脚本校验归属）
     */
    public boolean unlock(String lockKey, String requestId) {
        // Lua 脚本保证原子性
        String luaScript = 
            "if redis.call('get', KEYS[1]) == ARGV[1] then " +
            "    return redis.call('del', KEYS[1]) " +
            "else " +
            "    return 0 " +
            "end";
        
        DefaultRedisScript<Long> redisScript = new DefaultRedisScript<>();
        redisScript.setScriptText(luaScript);
        redisScript.setResultType(Long.class);
        
        Long result = redisTemplate.execute(
            redisScript,
            Collections.singletonList(lockKey),
            requestId
        );
        
        return result != null && result == 1L;
    }
}

// 使用示例
@Service
public class StockService {
    
    @Autowired
    private RedisLockService lockService;
    
    public void deductStock(String productId, int quantity) {
        String lockKey = "stock:lock:" + productId;
        String requestId = UUID.randomUUID().toString(); // 唯一标识
        
        try {
            // 获取锁
            boolean locked = lockService.tryLock(lockKey, requestId, 30);
            
            if (!locked) {
                throw new BusinessException("系统繁忙，请稍后重试");
            }
            
            // 扣减库存
            stockMapper.deductStock(productId, quantity);
            
        } finally {
            // 释放锁（只释放自己的锁）
            lockService.unlock(lockKey, requestId);
        }
    }
}
```

### 2.2 锁自动续期

**生活化比喻**：
```
锁续期 = 快超时时自动续费
- 启动守护线程
- 锁即将过期时自动延长有效期
- 避免业务未执行完锁失效

就像：
- 洗澡时间可能超过 30 分钟
- 快超时时，自动续费 10 分钟
- 避免被强制开门
```

**代码示例（Redisson 看门狗）**：
```java
@Service
public class StockService {
    
    @Autowired
    private RedissonClient redissonClient;
    
    public void deductStock(String productId, int quantity) {
        String lockKey = "stock:lock:" + productId;
        RLock lock = redissonClient.getLock(lockKey);
        
        try {
            // 获取锁（自动续期）
            // Redisson 的看门狗机制会自动续期
            boolean locked = lock.tryLock(
                10,  // 等待时间 10 秒
                30,  // 锁持有时间 30 秒（会被看门狗自动续期）
                TimeUnit.SECONDS
            );
            
            if (!locked) {
                throw new BusinessException("系统繁忙，请稍后重试");
            }
            
            // 扣减库存（可能超过 30 秒）
            // 看门狗会自动续期，不会提前过期
            stockMapper.deductStock(productId, quantity);
            
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        } finally {
            // 释放锁
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }
}
```

**看门狗原理**：
```
Redisson 看门狗机制：
- 每隔 10 秒检查一次（默认锁时间的 1/3）
- 如果线程还持有锁，自动续期 30 秒
- 线程释放锁或宕机后，停止续期
- 锁过期后自动释放
```

### 2.3 可重入锁设计

**生活化比喻**：
```
可重入锁 = 你可以多次进出同一个厕所
- 同一线程支持重复加锁
- 防止嵌套调用死锁
- 适配复杂业务链路

就像：
- 你可以多次进出同一个厕所
- 不用每次都重新开门
- 但其他人不能进
```

**代码示例**：
```java
@Service
public class OrderService {
    
    @Autowired
    private RedissonClient redissonClient;
    
    @Autowired
    private StockService stockService;
    
    public void createOrder(Order order) {
        String lockKey = "order:lock:" + order.getUserId();
        RLock lock = redissonClient.getLock(lockKey);
        
        try {
            // 获取锁（可重入）
            boolean locked = lock.tryLock(10, 30, TimeUnit.SECONDS);
            
            if (!locked) {
                throw new BusinessException("系统繁忙");
            }
            
            // 创建订单
            orderMapper.insert(order);
            
            // 扣减库存（也会获取锁，可重入）
            stockService.deductStock(order.getProductId(), order.getQuantity());
            
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        } finally {
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }
}
```

## 三、第二层防御：兜底与容错

### 3.1 锁降级方案

**生活化比喻**：
```
锁降级 = 电子锁坏了用机械锁
- Redis 锁故障时，切换为数据库悲观锁兜底
- 保证核心链路不崩

就像：
- 电子锁坏了
- 用机械锁临时顶替
- 虽然慢一点，但能用
```

**代码示例**：
```java
@Service
public class StockService {
    
    @Autowired
    private RedissonClient redissonClient;
    
    @Autowired
    private StockMapper stockMapper;
    
    public void deductStock(String productId, int quantity) {
        String lockKey = "stock:lock:" + productId;
        RLock lock = redissonClient.getLock(lockKey);
        
        try {
            // 尝试获取 Redis 锁
            boolean locked = lock.tryLock(10, 30, TimeUnit.SECONDS);
            
            if (!locked) {
                // Redis 锁故障，降级为数据库悲观锁
                deductStockWithDatabaseLock(productId, quantity);
                return;
            }
            
            try {
                // 扣减库存
                stockMapper.deductStock(productId, quantity);
            } finally {
                lock.unlock();
            }
            
        } catch (Exception e) {
            log.error("Redis 锁异常，降级为数据库锁", e);
            // 降级为数据库悲观锁
            deductStockWithDatabaseLock(productId, quantity);
        }
    }
    
    /**
     * 数据库悲观锁兜底
     */
    private void deductStockWithDatabaseLock(String productId, int quantity) {
        // 使用 SELECT ... FOR UPDATE 悲观锁
        stockMapper.deductStockWithLock(productId, quantity);
    }
}

// Mapper
@Mapper
public interface StockMapper {
    
    @Update("UPDATE stock SET count = count - #{quantity} WHERE product_id = #{productId}")
    void deductStock(@Param("productId") String productId, @Param("quantity") int quantity);
    
    @Select("SELECT * FROM stock WHERE product_id = #{productId} FOR UPDATE")
    Stock selectForUpdate(@Param("productId") String productId);
    
    void deductStockWithLock(@Param("productId") String productId, @Param("quantity") int quantity);
}
```

### 3.2 库存预校验

**生活化比喻**：
```
库存预校验 = 进门前先检查有没有人
- 扣减前双重校验库存
- 即使锁失效也能拦截无效扣减

就像：
- 进厕所前先敲门
- 有人就不进
- 避免冲突
```

**代码示例**：
```java
@Service
public class StockService {
    
    @Autowired
    private StockMapper stockMapper;
    
    public void deductStock(String productId, int quantity) {
        // 1. 预校验库存
        Stock stock = stockMapper.selectById(productId);
        
        if (stock == null || stock.getCount() < quantity) {
            throw new BusinessException("库存不足");
        }
        
        // 2. 扣减库存（乐观锁）
        int updated = stockMapper.deductStockWithVersion(productId, quantity, stock.getVersion());
        
        if (updated == 0) {
            // 版本号不匹配，重试
            throw new BusinessException("扣减失败，请重试");
        }
    }
}

// Mapper
@Mapper
public interface StockMapper {
    
    @Update("UPDATE stock SET count = count - #{quantity}, version = version + 1 " +
            "WHERE product_id = #{productId} AND version = #{version}")
    int deductStockWithVersion(
        @Param("productId") String productId, 
        @Param("quantity") int quantity,
        @Param("version") int version
    );
}
```

### 3.3 幂等控制

**生活化比喻**：
```
幂等控制 = 防止重复刷卡
- 结合请求唯一 ID
- 防止重复扣减

就像：
- 刷卡进门，刷一次就够
- 重复刷卡无效
```

**代码示例**：
```java
@Service
public class StockService {
    
    @Autowired
    private StringRedisTemplate redisTemplate;
    
    @Autowired
    private StockMapper stockMapper;
    
    public void deductStock(String requestId, String productId, int quantity) {
        // 幂等控制
        String idempotentKey = "stock:deduct:" + requestId;
        Boolean isFirst = redisTemplate.opsForValue()
            .setIfAbsent(idempotentKey, "1", 10, TimeUnit.MINUTES);
        
        if (!isFirst) {
            log.info("重复请求，跳过，requestId={}", requestId);
            return;
        }
        
        try {
            // 扣减库存
            stockMapper.deductStock(productId, quantity);
        } catch (Exception e) {
            // 扣减失败，删除幂等键，允许重试
            redisTemplate.delete(idempotentKey);
            throw e;
        }
    }
}
```

## 四、第三层防御：架构层升级

### 4.1 集群高可用（Redlock）

**生活化比喻**：
```
Redlock = 多个厕所共用一套锁系统
- Redis 集群模式下，主从切换可能导致锁丢失
- Redlock 算法：在多个独立的 Redis 实例上加锁
- 大多数实例加锁成功，才算加锁成功

就像：
- 有 5 个厕所，每个都有独立的锁
- 至少在 3 个厕所加锁成功，才算加锁成功
- 避免单个厕所故障导致锁失效
```

**代码示例**：
```java
@Service
public class RedLockService {
    
    private List<RedissonClient> redisInstances;
    
    public RedLockService() {
        // 初始化多个独立的 Redis 实例
        redisInstances = Arrays.asList(
            Redisson.create(config1),
            Redisson.create(config2),
            Redisson.create(config3),
            Redisson.create(config4),
            Redisson.create(config5)
        );
    }
    
    /**
     * Redlock 算法加锁
     */
    public boolean tryLock(String lockKey, String requestId, long expireSeconds) {
        long startTime = System.currentTimeMillis();
        int successCount = 0;
        
        // 在所有实例上加锁
        for (RedissonClient redis : redisInstances) {
            RLock lock = redis.getLock(lockKey);
            
            try {
                boolean locked = lock.tryLock(0, expireSeconds, TimeUnit.SECONDS);
                
                if (locked) {
                    successCount++;
                }
            } catch (Exception e) {
                log.error("加锁失败", e);
            }
        }
        
        // 大多数实例加锁成功（N/2 + 1）
        int requiredCount = redisInstances.size() / 2 + 1;
        
        if (successCount >= requiredCount) {
            return true;
        } else {
            // 加锁失败，释放所有实例上的锁
            unlock(lockKey, requestId);
            return false;
        }
    }
    
    public void unlock(String lockKey, String requestId) {
        for (RedissonClient redis : redisInstances) {
            RLock lock = redis.getLock(lockKey);
            
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }
}
```

### 4.3 开关控制

**生活化比喻**：
```
开关控制 = 紧急情况下手动锁定
- 核心场景支持手动开启强制单机锁
- 牺牲部分性能换一致性

就像：
- 紧急情况下

- 只允许一个人进
```

```java
@Service
public class StockService {
    
    @Value("${seckill.force-single-lock:false}")
    private boolean forceSingleLock;
    
    public void deductStock(String productId, int quantity) {
        if (forceSingleLock) {
            // 强制单机锁（牺牲性能换一致性）
            deductStockWithSingleLock(productId, quantity);
        } else {
            // 正常分布式锁
            deductStockWithDistributedLock(productId, quantity);
        }
    }
    
    private void deductStockWithSingleLock(String productId, int quantity) {
        synchronized (this) {
            stockMapper.deductStock(productId, quantity);
        }
    }
}
```

五、技术深入探讨

### 考点 1：分布式锁为什么会被误释放？

**方案参考**（30 秒版）：
> "分布式锁被误释放是因为锁过期但业务未执行完，其他线程抢占锁。解决方案是三层防御：1）锁机制优化：锁绑定唯一标识，解锁前校验归属，只允许释放自己的锁；锁自动续期（Redisson 看门狗）；可重入锁设计。2）兜底容错：锁降级（数据库悲观锁）、库存预校验、幂等控制。3）架构升级：集群高可用（Redlock）、异步解耦（消息队列削峰）、开关控制。"

**加分回答**：
> "实际生产中，我会用 Redisson 实现分布式锁，它的看门狗机制会自动续期，避免业务未执行完锁已过期。锁绑定唯一标识（UUID），解锁前校验归属，避免误删其他线程的锁。对于高可用要求高的场景，会用 Redlock 算法在多个 Redis 实例上加锁。同时要锁降级方案，Redis 故障时切换为数据库悲观锁。秒杀场景用消息队列削峰，降低并发锁压力。"

### 考点 2：如何避免超卖？

**方案参考**：
> "避免超卖要三层防御：1）锁机制优化：分布式锁控制并发，锁绑定唯一标识，锁自动续期；2）兜底容错：库存预校验（扣减前检查库存）、乐观锁（版本号机制）、幂等控制（防止重复扣减）；3）架构升级：消息队列削峰、异步解耦、锁降级方案。"

**加分回答**：
> "我会建立完整的防超卖体系：秒杀请求接入消息队列削峰，消费者用分布式锁控制并发，扣减前预校验库存，扣减时用乐观锁（版本号机制），同时用幂等控制防止重复扣减。Redis 故障时降级为数据库悲观锁。关键操作用 Redisson 分布式锁，看门狗自动续期。全链路监控，发现异常立即告警。"

### 考点 3：Redlock 算法的原理？

**方案参考**：
> "Redlock 算法是在多个独立的 Redis 实例上加锁。步骤：1）依次在所有实例上加锁；2）如果在大多数实例（N/2 + 1）上加锁成功，才算加锁成功；3）加锁失败，释放所有实例上的锁。这样可以避免单个 Redis 实例故障导致锁失效。"

**加分回答**：
> "Redlock 算法要求 Redis 实例是独立的，不能是主从复制。因为主从切换可能导致锁丢失。实际生产中，Redlock 用得较少，因为实现复杂，性能开销大。大多数场景用 Redisson 的单实例锁就够了。对于高可用要求高的场景，可以用 ZooKeeper 实现分布式锁。"

## 六、总结（一句话带走）

### 🎯 一句话总结

> **分布式锁三层防御 = 锁机制优化（唯一标识/自动续期/可重入） + 兜底容错（锁降级/库存预校验/幂等控制） + 架构升级（集群高可用/异步解耦/开关控制）**

### 🧠 核心记忆点

1. **锁为什么会被误释放？** 锁过期但业务未执行完，其他线程抢占锁。解决方案：锁自动续期（Redisson 看门狗）。
2. **如何避免误删其他线程的锁？** 锁绑定唯一标识（UUID），解锁前校验归属，用 Lua 脚本保证原子性。
3. **如何避免超卖？** 分布式锁 + 库存预校验 + 乐观锁 + 幂等控制。
4. **Redis 故障怎么办？** 锁降级方案，切换为数据库悲观锁。
5. **高并发场景如何优化？** 消息队列削峰、异步解耦、Redlock 集群高可用。
