## 🎯 一句话定位

**缓存穿透解决什么问题？**
```
线上大量请求绕开缓存直接查询数据库，
数据库 CPU、负载飙升，查询响应急剧变慢，
Redis 命中率持续走低，业务接口大面积超时。

你以为给查询不到的数据也设置空缓存就能挡住穿透请求？
技术追问：
- 单纯设置空值缓存，面对海量恶意随机请求，空缓存堆积造成内存占用过高该如何处理？
- 布隆过滤器存在误判、数据更新不同步，同时高并发下如何合理搭配各类防护方案？

90% 的人答不上来！
```

**生活化比喻**：
就像图书馆：
- **缓存穿透**：读者找一本不存在的书，管理员只能去仓库一本本找
- **数据库**：仓库，承受不住大量查找
- **布隆过滤器**：入口处先查目录，书不在目录里就直接拒绝

**核心特点**：只会套单一方案和具备分布式缓存架构治理能力完全是两个技术维度！

## 一、为什么缓存穿透这么难？

### 🔍 核心问题（30 秒版）

**生活化比喻**：
```
缓存穿透的三大难题：
1. 空查询穿透：查询不存在的数据，缓存无法命中
2. 恶意攻击：海量随机请求，故意查询不存在的数据
3. 热点 Key 击穿：热点数据失效，大量请求同时打到数据库

就像图书馆：
- 空查询：找一本不存在的书
- 恶意攻击：故意找很多不存在的书，让管理员忙不过来
- 热点击穿：热门书籍被借走，大量读者等着
```

## 三、第二层：标准化排查流程 + 多场景针对性优化

### 3.1 常规空查询穿透

**问题**：
```
查询不存在的数据，缓存无法命中，请求打到数据库
```

**解决方案**：
```java
// ✅ 空值缓存
public Product queryProduct(Long productId) {
    String key = "product:" + productId;
    String value = redisTemplate.opsForValue().get(key);
    
    if (value != null) {
        if ("NULL".equals(value)) {
            return null; // 空值缓存，直接返回
        }
        return JSON.parseObject(value, Product.class);
    }
    
    // 查询数据库
    Product product = productMapper.selectById(productId);
    
    if (product != null) {
        // 缓存数据，1 小时过期
        redisTemplate.opsForValue().set(key, JSON.toJSONString(product), 1, TimeUnit.HOURS);
    } else {
        // 缓存空值，5 分钟过期（较短，避免内存占用）
        redisTemplate.opsForValue().set(key, "NULL", 5, TimeUnit.MINUTES);
    }
    
    return product;
}
```

**生活化比喻**：
```
就像图书馆：
- 记录不存在的书，下次直接拒绝
- 空值缓存 5 分钟，避免内存占用
```

### 3.2 海量随机恶意请求

**问题**：
```
海量随机请求，故意查询不存在的数据，空缓存堆积，内存溢出
```

**解决方案**：
```java
// ✅ 布隆过滤器
@Component
public class BloomFilterService {
    
    private BloomFilter<Integer> bloomFilter;
    
    @PostConstruct
    public void init() {
        // 创建布隆过滤器
        bloomFilter = BloomFilter.create(
            Funnels.integerFunnel(),
            1000000, // 预期数据量
            0.01     // 误判率
        );
        
        // 加载所有商品 ID
        List<Integer> productIds = productMapper.selectAllIds();
        for (Integer id : productIds) {
            bloomFilter.put(id);
        }
    }
    
    public boolean mightContain(Integer productId) {
        return bloomFilter.mightContain(productId);
    }
    
    // 新增商品时同步更新布隆过滤器
    public void add(Integer productId) {
        bloomFilter.put(productId);
    }
}

// 使用
public Product queryProduct(Long productId) {
    // 1. 布隆过滤器前置拦截
    if (!bloomFilterService.mightContain(productId.intValue())) {
        log.info("商品 ID 不存在，直接拒绝");
        return null;
    }
    
    // 2. 查询缓存
    // 3. 查询数据库
}
```

**生活化比喻**：
```
就像图书馆：
- 入口处先查目录，书不在目录里就直接拒绝
- 避免管理员白跑一趟
```

### 3.3 高并发热点 Key 空数据击穿

**问题**：
```
热点数据失效，大量请求同时打到数据库
```

**解决方案**：
```java
// ✅ 分布式互斥锁
public Product queryProduct(Long productId) {
    String key = "product:" + productId;
    String value = redisTemplate.opsForValue().get(key);
    
    if (value != null) {
        return JSON.parseObject(value, Product.class);
    }
    
    // 分布式锁
    String lockKey = "lock:product:" + productId;
    if (redisLock.tryLock(lockKey, 10, TimeUnit.SECONDS)) {
        try {
            // 双重检查
            value = redisTemplate.opsForValue().get(key);
            if (value != null) {
                return JSON.parseObject(value, Product.class);
            }
            
            // 查询数据库
            Product product = productMapper.selectById(productId);
            
            if (product != null) {
                // 热点数据永不过期
                redisTemplate.opsForValue().set(key, JSON.toJSONString(product));
            } else {
                redisTemplate.opsForValue().set(key, "NULL", 5, TimeUnit.MINUTES);
            }
            
            return product;
        } finally {
            redisLock.unlock(lockKey);
        }
    } else {
        // 获取锁失败，返回兜底数据
        return Product.empty();
    }
}
```

**生活化比喻**：
```
就像图书馆：
- 热门书籍被借走，读者排队等待
- 第一个人去仓库找，找到后放回前台
- 其他人直接在前台借阅
```

### 3.4 混合流量穿透

**问题**：
```
混合流量：正常请求 + 恶意请求 + 热点请求
```

**解决方案**：

public Result queryProduct(Long productId) {
    // 1. 参数校验
    if (productId == null || productId <= 0) {
        return Result.error("参数错误");
    }
    
    // 2. 频率限制
    String userId = getCurrentUserId();
    if (!rateLimiter.tryAcquire(userId, 100, TimeUnit.SECONDS)) {
        return Result.error("请求过于频繁");
    }
    
    // 3. 查询商品
    Product product = productService.query(productId);
    return Result.success(product);
}

五、技术深入探讨

### Q1: 布隆过滤器的误判怎么处理？

**答**：
> 布隆过滤器误判处理：
>
> 1. **设置合理的误判率**：如 0.01（1%）
> 2. **定期同步数据**：新增商品时同步更新布隆过滤器
> 3. **兜底方案**：布隆过滤器判断存在，但缓存和数据库都没有时，返回空数据
>
> 核心：布隆过滤器只能判断"可能存在"或"一定不存在"。

### Q2: 高并发下如何搭配各类防护方案？

**答**：
> 多方案组合：
>
> 1. **布隆过滤器**：前置拦截，判断数据是否可能存在
> 2. **空值缓存**：缓存不存在的数据，避免重复查询
> 3. **分布式锁**：防止热点 Key 击穿
> 4. **频率限制**：防止恶意请求
> 5. **热点数据永不过期**：避免热点数据失效

### Q3: 怎么从源头减少无效查询？

**答**：
> 源头管控：
>
> 1. **参数校验**：所有查询接口必须参数校验
> 2. **频率限制**：单用户每秒最多 100 次查询
> 3. **定期梳理**：清理不合理查询逻辑
> 4. **开发规范**：统一缓存策略，避免局部架构漏洞
