# 分布式事务数据一致性

> **场景定位**：分布式系统技术场景  
> **核心设计要点**：TCC/Seata、刚性一致 vs 柔性一致、事务补偿、对账兜底

---

## 🎯 一句话定位

```
你以为引入个事务框架就能解决跨服务一致性，
却没想到网络抖动、服务宕机、超时、重试
都会让数据出现偏差。
```

**生活化比喻**：
就像三人接力赛跑——第一棒（订单服务）跑完了，第二棒（库存服务）摔倒了没跑到，第三棒（积分服务）也不知道该不该跑。怎么保证要么三人都跑完，要么全部回到起点？

---

## 💎 核心观点

**三层保障**：
1. **业务分级**：刚性一致（TCC，核心交易）vs 柔性一致（最终一致性，非核心）
2. **兜底机制**：事务日志+定时重试、人工补偿队列、熔断降级
3. **架构优化**：本地消息表+事务消息、异步解耦、核心场景开关

---

## 🚀 一句话精华

> **分布式事务 = 业务分级（刚性/柔性） + 兜底机制（日志重试/人工补偿/熔断） + 本地消息表 + 异步解耦**

---

## 一、核心场景：下单链路数据不一致

```
电商下单链路：
  订单服务（创建订单）→ 库存服务（扣减库存）→ 积分服务（加积分）

问题：
  订单创建成功 ✅
  库存扣减因网络超时失败 ❌
  全局事务没完全回滚 ❌
  
  结果：订单显示已支付，但库存没扣 → 超卖！
```

---

## 二、三层保障详解

### 2.1 第一层：业务分级

| 场景类型 | 一致性要求 | 方案选择 | 示例 |
|----------|-----------|---------|------|
| **刚性一致** | 同一时间点数据必须完全对齐 | TCC / 同步强校验 | 支付、扣库存、资金转账 |
| **柔性一致** | 短暂延迟可接受 | 最终一致性 | 发积分、发短信、日志记录 |

### 2.2 第二层：兜底机制

```
事务日志 + 定时重试：
  → 每个事务分支记录执行状态
  → 失败后按日志定时重试
  → 所有接口保证幂等

人工补偿队列：
  → 无法自动回滚的异常事务进入待处理队列
  → 运营后台人工兜底

熔断降级：
  → 监控事务失败率超标时自动暂停非核心链路
  → 避免异常扩散
```

### 2.3 第三层：架构优化

```
本地消息表 + 事务消息：
  → 本地事务与消息发送绑定
  → 消费端重试实现最终一致

异步解耦：
  → 非核心操作全部异步化
  → 不阻塞主事务流程

核心场景开关：
  → 大促期间核心交易切同步强校验
  → 宁可牺牲吞吐量，也要保证数据准确
```

---

## 三、技术方案

> "分布式事务我分三层：核心链路（支付/库存）用 TCC 强一致，非核心链路（积分/通知）用本地消息表最终一致。兜底靠事务日志定时重试 + 人工补偿队列 + 熔断降级。架构上异步解耦，大促期间切强校验模式。"
