# Seata 分布式事务异常处理

> **场景定位**：分布式事务技术场景  
> **核心设计要点**：Seata AT 模式、事务回滚、异常兜底、状态校验、补偿机制、架构优化

---

## 🎯 一句话定位

**分布式事务问题是什么？**
```
Seata 事务回滚失败，库存服务未收到回滚通知：
- 网络波动导致支付服务调用超时
- 库存扣减成功，但订单状态变成待支付
- 用户无法支付也无法退款
- 商家库存异常，投诉不断
```

**生活化比喻**：就像三个人一起转账，A 扣钱了，B 加钱了，但 C 的网络断了没收到通知，结果 A 钱没了，C 也没加钱，数据不一致了。

**核心特点**：分布式事务不仅仅是套用框架，而是选型适配、异常兜底、架构优化相结合的完整体系。

## 一、问题本质：分布式事务的隐性风险

### ❌ 常见误区

**误区 1：用 Seata 框架就够了**
```
问题：
- 网络波动导致事务回滚失败
- 某些服务未收到回滚通知
- 数据不一致

解决：
- 选型适配：核心场景用 AT 模式 + 本地消息表
- 异常兜底：回滚重试 + 状态校验
- 架构优化：服务高可用 + 消息可靠投递
```

**误区 2：分布式事务就是强一致性**
```
问题：
- 强一致性性能差
- 高并发场景下事务堵塞
- 过度设计

解决：
- 核心场景用强一致性（Seata AT）
- 非核心场景用最终一致性（MQ 异步补偿）
- 高并发场景拆分事务粒度
```

**误区 3：事务回滚是自动的**
```
问题：
- 网络超时导致回滚失败
- 服务宕机导致回滚中断
- 回滚后数据不一致

解决：
- 事务回滚重试机制
- 状态校验与补偿
- 全链路日志留痕
```

## 二、第一层防御：选型适配

### 2.1 核心场景：Seata AT 模式 + 本地消息表

**生活化比喻**：
```
核心场景 = 大额转账，必须实时确认
- 订单创建、库存扣减、支付扣款
- 必须保证强一致性
- 用 Seata AT 模式 + 本地消息表

就像：
- 大额转账必须实时到账
- 不能延迟，不能失败
- 失败了必须立即回滚
```

**代码示例**：
```java
@Service
public class OrderService {
    
    @Autowired
    private OrderMapper orderMapper;
    
    @Autowired
    private StockFeignClient stockFeignClient;
    
    @Autowired
    private PaymentFeignClient paymentFeignClient;
    
    @Autowired
    private LocalMessageMapper localMessageMapper;
    
    /**
     * 创建订单（Seata AT 模式）
     */
    @GlobalTransactional(rollbackFor = Exception.class)
    public void createOrder(Order order) {
        try {
            // 1. 创建订单
            orderMapper.insert(order);
            
            // 2. 扣减库存
            stockFeignClient.deductStock(order.getProductId(), order.getQuantity());
            
            // 3. 扣减余额
            paymentFeignClient.deductBalance(order.getUserId(), order.getAmount());
            
            // 4. 记录本地消息（成功）
            saveLocalMessage(order.getId(), "SUCCESS");
            
        } catch (Exception e) {
            // 记录本地消息（失败）
            saveLocalMessage(order.getId(), "FAILED");
            
            throw e; // 触发 Seata 回滚
        }
    }
    
    private void saveLocalMessage(Long orderId, String status) {
        LocalMessage message = new LocalMessage();
        message.setOrderId(orderId);
        message.setStatus(status);
        message.setCreatedAt(new Date());
        localMessageMapper.insert(message);
    }
}
```

**生活化比喻**：
```
非核心场景 = 小额支付，可以延迟确认
- 积分增加、日志记录
- 允许短暂不一致
- 用消息队列异步补偿

就像：
- 小额支付可以延迟到账
- 先扣钱，后通知
- 失败了可以补偿
```

**代码示例**：
```java
@Service
public class OrderService {
    
    @Autowired
    private RocketMQTemplate rocketMQTemplate;
    
    @Autowired
    private OrderMapper orderMapper;
    
    /**
     * 创建订单（最终一致性）
     */
    public void createOrder(Order order) {
        // 1. 创建订单
        orderMapper.insert(order);
        
        // 2. 发送消息（异步处理积分、日志等）
        rocketMQTemplate.convertAndSend("order-topic", order);
        
        // 立即返回，不等待异步处理完成
    }
}

@Component
@RocketMQMessageListener(topic = "order-topic")
public class OrderConsumer implements RocketMQListener<Order> {
    
    @Autowired
    private PointService pointService;
    
    @Autowired
    private LogService logService;
    
    @Override
    public void onMessage(Order order) {
        try {
            // 1. 增加积分
            pointService.addPoint(order.getUserId(), order.getPoints());
            
            // 2. 记录日志
            logService.saveLog(order);
            
        } catch (Exception e) {
            log.error("订单异步处理失败，orderId={}", order.getId(), e);
            
            // 重试或进入死信队列
            throw e;
        }
    }
}
```

## 三、第二层防御：异常兜底

### 3.1 事务回滚重试

**生活化比喻**：
```
回滚重试 = 转账失败再试一次
- 对回滚失败的服务设置定时重试
- 结合幂等控制，避免重复执行

就像：
- 转账失败，再转一次
- 但要防止重复转账
- 用幂等控制
```

**代码示例**：
```java
@Component
public class TransactionCompensationTask {
    
    @Autowired
    private LocalMessageMapper localMessageMapper;
    
    @Autowired
    private StockFeignClient stockFeignClient;
    
    /**
     * 定时重试回滚失败的事务
     */
    @Scheduled(fixedRate = 60000) // 每分钟检查一次
    public void compensateFailedTransaction() {
        // 查询状态为 FAILED 的本地消息
        List<LocalMessage> failedMessages = localMessageMapper.selectByStatus("FAILED");
        
        for (LocalMessage message : failedMessages) {
            if (message.getRetryCount() >= 3) {
                // 重试次数用尽，标记为需要人工介入
                localMessageMapper.updateStatus(message.getId(), "MANUAL");
                sendAlert("事务回滚失败，需要人工介入，orderId=" + message.getOrderId());
            } else {
                // 重试回滚
                try {
                    rollbackTransaction(message);
                    
                    // 更新状态为 SUCCESS
                    localMessageMapper.updateStatus(message.getId(), "SUCCESS");
                    
                } catch (Exception e) {
                    log.error("事务回滚重试失败，orderId={}", message.getOrderId(), e);
                    
                    // 更新重试次数
                    localMessageMapper.incrementRetryCount(message.getId());
                }
            }
        }
    }
    
    private void rollbackTransaction(LocalMessage message) {
        // 幂等控制：检查是否已回滚
        if (isAlreadyRolledBack(message.getOrderId())) {
            return;
        }
        
        // 执行回滚逻辑
        Order order = orderMapper.selectById(message.getOrderId());
        stockFeignClient.rollbackStock(order.getProductId(), order.getQuantity());
    }
    
    private boolean isAlreadyRolledBack(Long orderId) {
        // 检查是否已回滚
        return false;
    }
}
```

### 3.2 状态校验与补偿

**生活化比喻**：
```
状态校验 = 定时对账，发现异常立即修正
- 定时校验各服务数据一致性
- 发现异常自动触发补偿逻辑

就像：
- 每天对账，检查银行余额和账本是否一致
- 不一致立即修正
- 避免数据不一致
```

**代码示例**：
```java
@Service
public class ReconciliationService {
    
    @Autowired
    private OrderMapper orderMapper;
    
    @Autowired
    private StockMapper stockMapper;
    
    @Autowired
    private PaymentMapper paymentMapper;
    
    /**
     * 定时对账（每天凌晨 2 点）
     */
    @Scheduled(cron = "0 0 2 * * ?")
    public void reconciliation() {
        // 1. 查询已支付的订单
        List<Order> paidOrders = orderMapper.selectPaidOrders();
        
        for (Order order : paidOrders) {
            // 2. 校验库存是否扣减
            boolean stockDeducted = stockMapper.isStockDeducted(order.getProductId(), order.getQuantity());
            
            if (!stockDeducted) {
                // 库存未扣减，触发补偿
                log.error("库存未扣减，orderId={}", order.getId());
                stockMapper.deductStock(order.getProductId(), order.getQuantity());
                sendAlert("库存补偿，orderId=" + order.getId());
            }
            
            // 3. 校验余额是否扣减
            boolean balanceDeducted = paymentMapper.isBalanceDeducted(order.getUserId(), order.getAmount());
            
            if (!balanceDeducted) {
                // 余额未扣减，触发补偿
                log.error("余额未扣减，orderId={}", order.getId());
                paymentMapper.deductBalance(order.getUserId(), order.getAmount());
                sendAlert("余额补偿，orderId=" + order.getId());
            }
        }
    }
    
    private void sendAlert(String message) {
        System.out.println("[ALERT] " + message);
    }
}
```

```java
@Service
public class MessageService {
    
    @Autowired
    private RocketMQTemplate rocketMQTemplate;
    
    /**
     * 发送事务消息
     */
    public void sendTransactionMessage(Order order) {
        // 1. 发送半消息
        rocketMQTemplate.sendMessageInTransaction(
            "order-topic",
            MessageBuilder.withPayload(order).build(),
            order.getId()
        );
    }
    
    /**
     * 事务消息监听器
     */
    @RocketMQTransactionListener
    public class TransactionListener implements RocketMQLocalTransactionListener {
        
        @Override
        public RocketMQLocalTransactionState executeLocalTransaction(Message msg, Object arg) {
            try {
                // 执行本地事务
                Order order = (Order) msg.getPayload();
                orderMapper.insert(order);
                
                return RocketMQLocalTransactionState.COMMIT; // 提交
                
            } catch (Exception e) {
                return RocketMQLocalTransactionState.ROLLBACK; // 回滚
            }
        }
        
        @Override
        public RocketMQLocalTransactionState checkLocalTransaction(Message msg) {
            // 检查本地事务状态
            Order order = (Order) msg.getPayload();
            Order existOrder = orderMapper.selectById(order.getId());
            
            if (existOrder != null) {
                return RocketMQLocalTransactionState.COMMIT;
            } else {
                return RocketMQLocalTransactionState.ROLLBACK;
            }
        }
    }
}
```

### 4.3 分布式锁

**生活化比喻**：
```
分布式锁 = 转账时锁定账户，防止重复转账

- 避免并发导致的事务冲突

- 防止同时转两次
- 保证数据一致性
```

**代码示例**：
```java
@Service
public class OrderService {
    
    @Autowired
    private RedisLockService lockService;
    
    @Autowired
    private OrderMapper orderMapper;
    
    /**
     * 创建订单（加分布式锁）
     */
    public void createOrder(Order order) {
        String lockKey = "order:lock:" + order.getUserId();
        String requestId = UUID.randomUUID().toString();
        
        try {
            // 获取分布式锁
            boolean locked = lockService.tryLock(lockKey, requestId, 30);
            
            if (!locked) {
                throw new BusinessException("系统繁忙，请稍后重试");
            }
            
            // 创建订单
            orderMapper.insert(order);
            
        } finally {
            // 释放锁
            lockService.unlock(lockKey, requestId);
        }
    }
}
```

五、技术深入探讨

### 考点 1：Seata 事务回滚失败怎么办？

**方案参考**（30 秒版）：
> "Seata 事务回滚失败要三层防御：1）选型适配：核心场景用 AT 模式 + 本地消息表，非核心场景用最终一致性；2）异常兜底：事务回滚重试机制，定时校验数据一致性，自动补偿；3）架构优化：服务高可用集群，消息队列可靠投递，分布式锁防冲突。"

**加分回答**：
> "实际生产中，我会用 Seata AT 模式处理核心场景，同时记录本地消息表。回滚失败时，定时任务重试，结合幂等控制避免重复执行。每天凌晨对账，发现数据不一致自动补偿。服务用集群部署，避免单点故障。消息队列用事务消息，保证可靠投递。关键操作用分布式锁，防止并发冲突。"

### 考点 2：如何保证分布式事务一致性？

**方案参考**：
> "保证分布式事务一致性要根据场景选择方案：1）核心场景（订单、支付）用强一致性，Seata AT 模式 + 本地消息表；2）非核心场景（积分、日志）用最终一致性，消息队列异步补偿；3）高并发场景拆分事务粒度，避免大事务堵塞。同时要异常兜底，回滚重试 + 状态校验 + 日志留痕。"

**加分回答**：
> "我会建立完整的一致性保障体系：核心场景用 Seata AT 模式，记录本地消息表；非核心场景用 MQ 异步补偿；回滚失败定时重试，结合幂等控制；每天凌晨对账，发现异常自动补偿；服务用集群部署，消息用事务消息，关键操作用分布式锁。全链路日志留痕，便于排查问题。"

### 考点 3：分布式事务和并发冲突怎么处理？

**方案参考**：
> "分布式事务和并发冲突要用分布式锁。在事务执行过程中对核心资源加锁，避免并发导致的事务冲突。比如创建订单时，用 Redis 分布式锁锁定用户 ID，防止同一用户并发创建订单。同时要合理设置锁的过期时间，避免死锁。"

**加分回答**：
> "除了分布式锁，还可以用乐观锁（版本号机制）。比如更新库存时，UPDATE stock SET count = count - 1 WHERE product_id = ? AND version = ?，如果版本号不匹配，说明已被修改，重试即可。分布式锁适合强一致性场景，乐观锁适合高并发场景。

## 六、总结（一句话带走）

### 🎯 一句话总结

> **分布式事务三层防御 = 选型适配（核心/非核心/高并发） + 异常兜底（回滚重试/状态校验/日志留痕） + 架构优化（服务高可用/MQ 可靠/分布式锁）**

### 🧠 核心记忆点

1. **选型适配**：核心场景用 Seata AT + 本地消息表，非核心场景用 MQ 异步补偿，高并发场景拆分事务粒度。
2. **异常兜底**：事务回滚重试（定时重试 + 幂等控制），状态校验与补偿（定时对账），日志留痕（全链路日志）。
3. **架构优化**：服务高可用（集群 + 熔断降级），消息队列可靠投递（事务消息），分布式锁（防并发冲突）。
4. **回滚失败怎么办？** 定时重试 + 幂等控制 + 人工介入。
5. **如何保证一致性？** 核心场景强一致性，非核心场景最终一致性，全链路日志留痕。
