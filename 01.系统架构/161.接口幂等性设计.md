# 接口幂等性设计

> **场景定位**：分布式系统技术场景  
> **核心设计要点**：幂等性实现、唯一标识、分布式锁、状态机、重试控制、数据一致性

---

## 🎯 一句话定位

**接口幂等性问题是什么？**
```
唯一索引和请求去重都生效了，但还是出现重复处理：
- 第三方支付平台反复推送支付回调
- 部分订单被重复记账
- 重复给用户加余额
- 财务对账出现大量差异
```

**生活化比喻**：就像快递签收，虽然要求一人只能签一次，但快递员可能多次配送，如果没有防重复签收机制，可能导致一个人收到多份快递。

**核心特点**：幂等性不仅仅是唯一标识 + 唯一索引，还需要场景化适配和兜底保障。

### 核心观点（3 层防御）

**1. 基础幂等实现：覆盖简单场景**
```
唯一标识去重：
- 用订单号、流水号作为唯一标识
- 请求时携带，后端校验并拒绝重复请求

数据库约束：
- 给唯一标识字段加唯一索引
- 主键约束
- 从数据库层面兜底

生活化比喻：
唯一标识 = 身份证号（一人一个）
唯一索引 = 户籍系统（不能重复登记）
```

**2. 场景化适配：解决复杂幂等问题**
```
异步回调场景：
- 结合消息队列，回调请求先入队
- 消费前校验幂等
- 避免并发回调导致的重复处理

分布式场景：
- 用 Redis 存储请求标识
- 设置合理过期时间
- 支持集群部署下的跨节点幂等校验

生活化比喻：
异步回调 = 快递先放驿站，再通知取件
分布式场景 = 多个快递员共用一个签收系统
```

**3. 兜底保障：避免幂等失效**
```
幂等日志留痕：
- 记录每笔请求的处理状态、唯一标识
- 便于后续排查重复处理问题

重复处理补偿：
- 定时校验数据一致性
- 发现重复处理，自动触发回滚、补偿逻辑

异常重试控制：
- 对重试请求做特殊标记
- 区分正常请求和重试请求
- 结合退避策略，减少重试频率

生活化比喻：
幂等日志 = 签收记录（可追溯）
重复补偿 = 定时盘点，发现多给立即收回
重试控制 = 重配送要特殊标记，避免重复签收
```

## 一、问题本质：幂等性的隐性风险

### ❌ 常见误区

**误区 1：唯一索引就够了**
```
问题：
- 并发场景下，唯一索引可能失效
- 异步回调场景，同一请求多次到达
- 分布式场景，本地缓存失效

解决：
- 分布式锁 + 唯一索引
- 状态机控制
- 异步队列 + 幂等校验
```

**误区 2：唯一标识用对了就不会出问题**
```
问题：
- 唯一标识设计不合理
- 第三方支付平台反复推送回调
- 网络重试导致重复请求

解决：
- 细粒度唯一标识（订单 ID + 操作类型 + 时间戳）
- 幂等日志留痕
- 重复处理补偿机制
```

## 二、第一层防御：基础幂等实现

### 2.1 唯一标识去重

**代码示例**：
```java
@RestController
public class PaymentController {
    
    @Autowired
    private PaymentService paymentService;
    
    @PostMapping("/callback")
    public Result paymentCallback(@RequestBody PaymentCallback callback) {
        // 校验唯一标识
        if (callback.getOrderId() == null) {
            return Result.error("订单号不能为空");
        }
        
        // 处理支付回调
        paymentService.handleCallback(callback);
        
        return Result.success();
    }
}

@Service
public class PaymentService {
    
    @Autowired
    private PaymentLogMapper paymentLogMapper;
    
    @Transactional
    public void handleCallback(PaymentCallback callback) {
        // 1. 检查是否已处理
        PaymentLog existLog = paymentLogMapper.selectByOrderId(callback.getOrderId());
        if (existLog != null) {
            log.info("支付回调已处理，orderId={}", callback.getOrderId());
            return; // 已处理，直接返回
        }
        
        // 2. 处理业务逻辑
        processPayment(callback);
        
        // 3. 记录幂等日志
        PaymentLog log = new PaymentLog();
        log.setOrderId(callback.getOrderId());
        log.setStatus("SUCCESS");
        log.setCreatedAt(new Date());
        paymentLogMapper.insert(log);
    }
    
    private void processPayment(PaymentCallback callback) {
        // 给用户加余额
        userService.addBalance(callback.getUserId(), callback.getAmount());
    }
}
```

### 2.2 数据库约束（唯一索引）

**代码示例**：
```sql
-- 支付日志表（唯一索引）
CREATE TABLE payment_log (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    order_id BIGINT NOT NULL COMMENT '订单ID',
    status VARCHAR(20) NOT NULL COMMENT '状态',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_order_id (order_id)  -- 唯一索引，防止重复处理
);

-- 插入时，如果 order_id 已存在，会抛出唯一索引冲突异常
INSERT INTO payment_log (order_id, status) VALUES (123, 'SUCCESS');
```

**Java 代码处理唯一索引冲突**：
```java
@Transactional
public void handleCallback(PaymentCallback callback) {
    try {
        // 插入幂等日志（唯一索引）
        PaymentLog log = new PaymentLog();
        log.setOrderId(callback.getOrderId());
        log.setStatus("SUCCESS");
        paymentLogMapper.insert(log);
        
        // 处理业务逻辑
        processPayment(callback);
        
    } catch (DuplicateKeyException e) {
        // 唯一索引冲突，说明已处理
        log.info("支付回调已处理（唯一索引冲突），orderId={}", callback.getOrderId());
        return;
    }
}
```

## 三、第二层防御：场景化适配

### 3.1 异步回调场景（消息队列）

**生活化比喻**：
```
异步回调 = 快递先放驿站，再通知取件
- 支付回调先入队（消息队列）
- 消费者按顺序处理
- 处理前校验幂等
- 避免并发回调导致的重复处理
```

**代码示例**：
```java
@RestController
public class PaymentController {
    
    @Autowired
    private RocketMQTemplate rocketMQTemplate;
    
    @PostMapping("/callback")
    public Result paymentCallback(@RequestBody PaymentCallback callback) {
        // 回调请求先入队
        rocketMQTemplate.convertAndSend("payment-callback-topic", callback);
        
        // 立即返回成功（避免第三方支付平台重试）
        return Result.success();
    }
}

// 消费者（幂等处理）
@Component
@RocketMQMessageListener(topic = "payment-callback-topic")
public class PaymentCallbackConsumer implements RocketMQListener<PaymentCallback> {
    
    @Autowired
    private PaymentService paymentService;
    
    @Autowired
    private StringRedisTemplate redisTemplate;
    
    @Override
    public void onMessage(PaymentCallback callback) {
        String idempotentKey = "payment:callback:" + callback.getOrderId();
        
        // 获取分布式锁（防止并发消费）
        Boolean locked = redisTemplate.opsForValue()
            .setIfAbsent(idempotentKey, "1", 10, TimeUnit.SECONDS);
        
        if (!locked) {
            log.warn("支付回调正在处理，orderId={}", callback.getOrderId());
            return; // 正在处理，直接返回
        }
        
        try {
            // 处理支付回调
            paymentService.handleCallback(callback);
        } finally {
            redisTemplate.delete(idempotentKey);
        }
    }
}
```

### 3.2 分布式场景（Redis 分布式锁）

**生活化比喻**：
```
分布式场景 = 多个快递员共用一个签收系统
- Redis 存储请求标识
- 支持集群部署下的跨节点幂等校验
- 避免本地缓存失效
```

**代码示例**：
```java
@Service
public class OrderService {
    
    @Autowired
    private StringRedisTemplate redisTemplate;
    
    @Autowired
    private OrderMapper orderMapper;
    
    /**
     * 创建订单（幂等性）
     */
    public Order createOrder(OrderRequest request) {
        String idempotentKey = "order:create:" + request.getRequestId();
        
        // 获取分布式锁
        Boolean locked = redisTemplate.opsForValue()
            .setIfAbsent(idempotentKey, "1", 10, TimeUnit.SECONDS);
        
        if (!locked) {
            throw new BusinessException("请求正在处理，请勿重复提交");
        }
        
        try {
            // 检查是否已创建
            Order existOrder = orderMapper.selectByRequestId(request.getRequestId());
            if (existOrder != null) {
                return existOrder; // 已创建，直接返回
            }
            
            // 创建订单
            Order order = new Order();
            order.setRequestId(request.getRequestId());
            order.setUserId(request.getUserId());
            order.setProductId(request.getProductId());
            order.setStatus("PENDING");
            orderMapper.insert(order);
            
            return order;
        } finally {
            redisTemplate.delete(idempotentKey);
        }
    }
}
```

### 4.1 幂等日志留痕

**代码示例**：

@Entity
@Table(name = "idempotent_log")
public class IdempotentLog {
    
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)

    private String requestId;  // 请求唯一标识

    @Column(nullable = false)

    @Column
    private String result;  // 处理结果（JSON）
    
    @Column
    private Date createdAt;  // 创建时间
    
    @Column
    private Date updatedAt;  // 更新时间
    
    // getters and setters
}

@Service
public class IdempotentLogService {
    
    @Autowired
    private IdempotentLogMapper idempotentLogMapper;
    
    /**
     * 记录幂等日志
     */
    public void log(String requestId, String requestType, String status, String result) {
        IdempotentLog log = new IdempotentLog();
        log.setRequestId(requestId);
        log.setRequestType(requestType);
        log.setStatus(status);
        log.setResult(result);
        log.setCreatedAt(new Date());
        
        idempotentLogMapper.insert(log);
    }
    
    /**
     * 查询是否已处理
     */
    public boolean isProcessed(String requestId) {
        IdempotentLog log = idempotentLogMapper.selectByRequestId(requestId);
        return log != null && "SUCCESS".equals(log.getStatus());
    }
}

### 4.2 重复处理补偿

**代码示例**：
```java
@Service
public class ReconciliationService {
    
    @Autowired
    private OrderMapper orderMapper;
    
    @Autowired
    private PaymentMapper paymentMapper;
    
    @Autowired
    private BalanceLogMapper balanceLogMapper;
    
    /**
     * 定时对账（发现重复处理）
     */
    @Scheduled(cron = "0 0 2 * * ?") // 每天凌晨 2 点
    public void reconciliation() {
        // 1. 查询已支付但未发货的订单
        List<Order> orders = orderMapper.selectPaidButNotShipped();
        
        for (Order order : orders) {
            // 检查是否重复支付
            List<Payment> payments = paymentMapper.selectByOrderId(order.getId());
            
            if (payments.size() > 1) {
                // 重复支付，触发补偿
                log.error("发现重复支付，orderId={}", order.getId());
                
                // 退还多扣的金额
                BigDecimal duplicateAmount = payments.stream()
                    .skip(1)  // 跳过第一笔
                    .map(Payment::getAmount)
                    .reduce(BigDecimal.ZERO, BigDecimal::add);
                
                userService.refund(order.getUserId(), duplicateAmount);
                
                // 发送告警
                sendAlert("发现重复支付，已自动退款，orderId=" + order.getId());
            }
        }
    }
    
    /**
     * 检查余额变动异常
     */
    @Scheduled(cron = "0 0 3 * * ?") // 每天凌晨 3 点
    public void checkBalanceAnomaly() {
        // 查询短时间内多次增加余额的用户
        List<BalanceLog> logs = balanceLogMapper.selectFrequentIncrease();
        
        for (BalanceLog log : logs) {
            log.warn("发现余额异常变动，userId={}, count={}", log.getUserId(), log.getCount());
            sendAlert("发现余额异常变动，userId=" + log.getUserId());
        }
    }
    
    private void sendAlert(String message) {
        // 发送钉钉告警
        System.out.println("[ALERT] " + message);
    }
}
```

### 4.3 异常重试控制

**代码示例**：
```java
@Service
public class RetryService {
    
    @Autowired
    private StringRedisTemplate redisTemplate;
    
    /**
     * 带重试的调用（退避策略）
     */
    public <T> T callWithRetry(Supplier<T> supplier, int maxRetries) {
        int retryCount = 0;
        Exception lastException = null;
        
        while (retryCount < maxRetries) {
            try {
                return supplier.get();
            } catch (Exception e) {
                lastException = e;
                retryCount++;
                
                log.warn("调用失败，第 {} 次重试", retryCount, e);
                
                // 退避策略：1s, 2s, 4s
                try {
                    Thread.sleep((long) Math.pow(2, retryCount - 1) * 1000);
                } catch (InterruptedException ie) {
                    Thread.currentThread().interrupt();
                }
            }
        }
        
        throw new RuntimeException("调用失败，已重试 " + maxRetries + " 次", lastException);
    }
    
    /**
     * 幂等重试（区分正常请求和重试请求）
     */
    public void idempotentRetry(String requestId, Runnable action) {
        String retryKey = "retry:" + requestId;
        
        // 检查是否是重试请求
        Boolean isRetry = redisTemplate.opsForValue().get(retryKey) != null;
        
        if (isRetry) {
            log.info("检测到重试请求，requestId={}", requestId);
            // 可以特殊处理，如跳过某些步骤
        }
        
        // 执行操作
        action.run();
        
        // 标记为重试请求
        if (isRetry) {
            redisTemplate.opsForValue().set(retryKey, "1", 1, TimeUnit.HOURS);
        }
    }
}
```

五、技术深入探讨

### 考点 1：如何实现接口幂等性？

**方案参考**（30 秒版）：
> "实现接口幂等性要分三层：1）基础实现：用唯一标识（如订单号）+ 数据库唯一索引，防止重复插入；2）场景适配：异步回调用消息队列，分布式场景用 Redis 分布式锁；3）兜底保障：记录幂等日志，定时对账发现重复处理，自动补偿。"

**加分回答**：
> "实际生产中，我会根据业务场景选择方案：下单、支付等场景用数据库唯一索引 + 分布式锁；异步回调用消息队列 + 幂等校验；重要场景还要记录幂等日志，定时对账发现重复处理，自动回滚补偿。"

### 考点 2：并发场景下幂等性如何保证？

**方案参考**：
> "并发场景下要用分布式锁 + 唯一索引。分布式锁防止并发请求同时处理，唯一索引防止重复插入。比如处理支付回调时，先用 Redis SETNX 加锁，锁的 key 是 orderId，然后查数据库是否已处理，没处理才执行业务逻辑，最后插入幂等日志（唯一索引）。"

**加分回答**：
> "除了分布式锁，还可以用状态机控制，比如订单状态从'待支付'到'已支付'，只能流转一次。同时要用乐观锁（UPDATE ... WHERE status = 'PENDING'），保证状态流转的原子性。"

### 考点 3：如何发现和处理重复处理？

**方案参考**：
> "发现重复处理要用定时对账机制。定时任务扫描数据，发现重复记录（如同一订单多笔支付），自动触发补偿逻辑（如退款）。同时要记录幂等日志，便于追溯问题原因。"

**加分回答**：
> "我会建立完整的对账体系：1）每日对账，扫描异常数据；2）实时监控，发现异常立即告警；3）自动补偿，发现问题自动修复；4）人工介入，复杂问题人工处理。同时要分析重复处理的原因，优化代码或架构。"

## 六、总结（一句话带走）

### 🎯 一句话总结

> **接口幂等性三层防御 = 基础实现（唯一标识/唯一索引） + 场景适配（异步回调/分布式） + 兜底保障（日志留痕/补偿机制/重试控制）**

### 🧠 核心记忆点

1. **基础实现**：唯一标识（订单号、流水号）+ 数据库唯一索引，防止重复插入。
2. **场景适配**：异步回调用消息队列，分布式场景用 Redis 分布式锁。
3. **兜底保障**：记录幂等日志，定时对账发现重复处理，自动补偿。
4. **并发控制**：分布式锁 + 唯一索引 + 状态机，保证并发场景下的幂等性。
5. **重试控制**：退避策略（1s、2s、4s），区分正常请求和重试请求。
