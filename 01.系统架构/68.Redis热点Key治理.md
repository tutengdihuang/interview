# Redis 热点 Key 治理

> **场景定位**：高并发缓存技术场景  
> **核心设计要点**：热点发现、多级缓存、流量分散、写热点优化

---

## 🎯 一句话定位

**热点 Key 解决什么问题？**
```
单个 Key 每秒十几万请求，集中在一个 Redis 分片
→ 单节点 CPU 跑满，缓存超时
→ 请求击穿到数据库，数据库被打垮
```

**生活化比喻**：
就像某个明星突然爆红，所有粉丝都打同一个电话咨询
→ 电话线路被打爆（单节点 CPU 跑满）
→ 打不进电话的人就去公司门口堵着（击穿到数据库）

---

## 💎 核心观点（5 分钟速览版）

### 核心观点（5 个关键点）

**1. 热点分两类**
```
读热点：高并发查询（商品详情）
写热点：高并发更新（库存扣减）

两类问题解法完全不同！
```

**2. 可预判 vs 不可预判**
```
可预判（秒杀爆款）：提前预热到全节点
不可预判（突发热搜）：动态识别 + 自动处理
```

**3. 多级缓存是基线**
```
L1：浏览器缓存
L2：网关层缓存
L3：应用本地缓存
L4：Redis 分布式缓存

层层过滤，99% 请求在本地拦截
```

**4. 写热点：库存分片**
```
单份库存拆成 N 个分片 Key
请求随机分配到不同分片扣减
大幅降低单 Key 锁竞争
```

**5. 动态热点自动发现**
```
实时监控 Key 访问频次
达到阈值自动标记为热点
秒级推送到所有节点本地缓存
```

---

## 🚀 一句话精华

> **热点治理 = 多级缓存（层层过滤） + 热点分片（分散压力） + 动态识别（自动处理） + 兜底降级（防止雪崩）**

## 一、热点类型与失效边界

### 1.1 读热点 vs 写热点

**读热点**：
```
场景：商品详情、热搜榜单
失效边界：
- 单分片 CPU 跑满
- 网络带宽占满
- 缓存失效瞬间击穿数据库
```

**写热点**：
```
场景：秒杀库存扣减、点赞计数
失效边界：
- 分布式锁竞争激烈
- 接口超时
- 库存超卖
```

### 1.2 可预判 vs 不可预判

**可预判热点**：
```
秒杀活动、爆款商品
运营提前报备
→ 提前预热到全节点
```

**不可预判热点**：
```
突发热搜、明星八卦
运营来不及报备
→ 动态识别 + 自动处理
```

## 二、读热点治理方案

### 2.1 多级缓存体系

```go
// 多级缓存架构
type MultiLevelCache struct {
    browserCache time.Duration // 浏览器缓存（5 分钟）
    gatewayCache *cache.Cache  // 网关层缓存（1 分钟）
    localCache   *cache.Cache  // 应用本地缓存（30 秒）
    redisCache   *redis.Client // Redis 分布式缓存
}

// 查询流程
func (c *MultiLevelCache) Get(key string) (interface{}, error) {
    // L1: 本地缓存（最快，零网络 IO）
    if val, ok := c.localCache.Get(key); ok {
        return val, nil
    }
    
    // L2: Redis（快，网络 IO）
    val, err := c.redisCache.Get(key).Result()
    if err == nil {
        c.localCache.Set(key, val, 30*time.Second) // 回写本地
        return val, nil
    }
    
    // L3: 数据库（慢，最后手段）
    data, err := db.Query(key)
    if err == nil {
        c.redisCache.Set(key, data, 5*time.Minute)
        c.localCache.Set(key, data, 30*time.Second)
        return data, nil
    }
    
    return nil, err
}
```

**效果**：
```
10 万 QPS 的热点 Key：
- 本地缓存抗 80%（8 万 QPS）
- Redis 抗 15%（1.5 万 QPS）
- 数据库抗 5%（5000 QPS）
```

### 2.2 热点分片（分散流量）

**核心思路**：
```
一个 Key 拆成 N 个分片
请求随机路由到不同分片
单分片压力降低 N 倍
```

**实现示例**：
```go
// 热点 Key 分片
type HotKeySharding struct {
    redis   *redis.Client
    shards  int // 分片数量
}

// 读取：随机选一个分片
func (h *HotKeySharding) Get(key string) (string, error) {
    shardKey := fmt.Sprintf("%s:%d", key, rand.Intn(h.shards))
    return h.redis.Get(shardKey).Result()
}

// 写入：所有分片都要更新
func (h *HotKeySharding) Set(key, value string) error {
    for i := 0; i < h.shards; i++ {
        shardKey := fmt.Sprintf("%s:%d", key, i)
        h.redis.Set(shardKey, value, 5*time.Minute)
    }
    return nil
}
```

### 2.3 动态热点识别

```go
// 动态热点识别
type HotKeyDetector struct {
    accessCount *sync.Map // 访问计数
    hotKeys     *sync.Map // 热点 Key
    threshold   int       // 阈值（如 10000 QPS）
}

// 统计访问频次
func (d *HotKeyDetector) RecordAccess(key string) {
    count, _ := d.accessCount.LoadOrStore(key, new(int64))
    atomic.AddInt64(count.(*int64), 1)
}

// 定期检查热点
func (d *HotKeyDetector) DetectHotKeys() {
    d.accessCount.Range(func(key, value interface{}) bool {
        count := atomic.LoadInt64(value.(*int64))
        if count >= int64(d.threshold) {
            d.hotKeys.Store(key, true)
            log.Info("发现热点 Key: %s, QPS: %d", key, count)
        }
        return true
    })
}

// 每 10 秒检测一次
func StartDetection() {
    detector := &HotKeyDetector{
        accessCount: &sync.Map{},
        hotKeys:     &sync.Map{},
        threshold:   10000,
    }
    
    go func() {
        ticker := time.NewTicker(10 * time.Second)
        for range ticker.C {
            detector.DetectHotKeys()
            detector.accessCount = &sync.Map{} // 重置计数
        }
    }()
}
```

## 三、写热点治理方案

### 3.1 库存分片

**核心思路**：
```
1000 个库存拆成 10 个分片，每个分片 100 个
扣库存时随机选一个分片
单 Key 锁竞争降低 10 倍
```

**实现示例**：
```go
type InventorySharding struct {
    redis  *redis.Client
    key    string
    shards int
}

// 扣减库存
func (s *InventorySharding) Deduct() (bool, error) {
    // 随机选一个分片
    shard := rand.Intn(s.shards)
    shardKey := fmt.Sprintf("%s:%d", s.key, shard)
    
    // Lua 脚本：原子扣减
    script := `
        local stock = redis.call('GET', KEYS[1])
        if stock == nil then
            return -1
        end
        stock = tonumber(stock)
        if stock > 0 then
            redis.call('DECR', KEYS[1])
            return stock - 1
        end
        return 0
    `
    
    result, err := s.redis.Eval(script, []string{shardKey}).Int()
    if err != nil {
        return false, err
    }
    
    if result >= 0 {
        return true, nil // 扣减成功
    }
    
    // 当前分片库存不足，尝试其他分片
    for i := 0; i < s.shards; i++ {
        if i == shard {
            continue
        }
        shardKey = fmt.Sprintf("%s:%d", s.key, i)
        result, _ = s.redis.Eval(script, []string{shardKey}).Int()
        if result >= 0 {
            return true, nil
        }
    }
    
    return false, nil // 库存不足
}

// 后台异步汇总库存
func (s *InventorySharding) SyncTotalStock() int {
    total := 0
    for i := 0; i < s.shards; i++ {
        shardKey := fmt.Sprintf("%s:%d", s.key, i)
        stock, _ := s.redis.Get(shardKey).Int()
        total += stock
    }
    return total
}
```

## 四、数据一致性保障

### 4.1 本地缓存失效机制

```go
// 更新数据时，广播失效本地缓存
func UpdateData(key string, value interface{}) error {
    // 1. 更新数据库
    err := db.Update(key, value)
    if err != nil {
        return err
    }
    
    // 2. 更新 Redis
    redis.Set(key, value, 5*time.Minute)
    
    // 3. 广播失效本地缓存（MQ）
    msg := &CacheInvalidMsg{
        Key: key,
    }
    mq.Publish("cache_invalidate", msg)
    
    return nil
}

// 消费 MQ 消息，失效本地缓存
func HandleCacheInvalidMsg(msg *CacheInvalidMsg) {
    localCache.Delete(msg.Key)
}
```

```go
// ❌ 大 Value 问题
type ProductDetail struct {
```

五、技术深入探讨

### Q1: 突发热点怎么实时发现？

**方案参考**：
> 突发热点不能靠人工预判，必须有自动化治理方案：
> 
> 1. **实时监控**：通过 Redis 的 INFO 命令或客户端统计 Key 访问频次
> 2. **阈值告警**：达到预设阈值（如 10000 QPS）自动标记为热点
> 3. **自动处理**：热点 Key 秒级推送到所有应用节点本地缓存
> 4. **兜底降级**：极端流量下直接返回静态兜底数据
> 
> 关键是从发现到处理要秒级，不能等运营报备。

### Q2: 写热点（库存扣减）怎么优化？

**方案参考**：
> 写热点的核心问题是分布式锁竞争，解决方案是库存分片：
> 
> 1. **分片存储**：1000 个库存拆成 10 个分片，每个分片 100 个
> 2. **随机扣减**：请求随机选一个分片扣减，降低单 Key 锁竞争
> 3. **跨分片重试**：当前分片库存不足时，尝试其他分片
> 4. **异步汇总**：后台定时汇总各分片库存，保证最终一致
> 
> 这样可以把单 Key 的锁竞争降低 N 倍（N 是分片数）。
