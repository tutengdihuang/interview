## 一、计算公式

### 1.1 数据库端基准值

```
通用经验公式：
最优活跃连接数 ≈ CPU核心数 × 2 + 磁盘数

示例：
8核1磁盘 → 最优连接数 = 8×2+1 = 17
```

### 1.2 业务端估算

```
核心连接数 ≈ 峰值QPS × 单条SQL平均执行时长 × 1.2

示例：
峰值QPS = 1000
SQL平均执行时长 = 10ms = 0.01s
核心连接数 = 1000 × 0.01 × 1.2 = 12
```

**核心逻辑**：
- 连接池作用是复用连接，减少建连开销
- 不是无限堆连接数
- 性能瓶颈永远在数据库本身

---

## 二、SQL类型判断

### 2.1 短查询密集型

```
特征：
- 简单单表查询
- 无大表扫描
- 执行耗时毫秒级
- CPU计算占比高
- 连接占用时间极短

配置：
- 不需要大连接数
- 少量连接支撑高QPS
```

### 2.2 长查询IO密集型

```
特征：
- 多表连查
- 大范围分页
- 排序、聚合
- 磁盘IO时间长
- 连接占用久

配置：
- 可适当提高连接数
- 但依然有明确上限
```

### 2.3 实战判断方法

```go
// 通过监控平台统计
func AnalyzeSQLType() {
    // 1. SQL平均耗时
    avgDuration := getAvgSQLDuration()
    
    // 2. 连接池活跃连接占比
    activeRatio := getActiveConnectionRatio()
    
    // 3. 数据库CPU与IO使用率
    cpuUsage := getDatabaseCPU()
    ioUsage := getDatabaseIO()
    
    // 4. 判断
    if activeRatio > 0.8 && cpuUsage < 0.3 {
        // 活跃连接打满但CPU很低
        // 优先优化SQL，而不是盲目加连接数
        alert("建议优化SQL，而非增加连接数")
    }
}
```

## 三、连接数过多后果

### 3.1 线程上下文切换

```
问题：
- 每个连接对应一个工作线程
- 连接数远超CPU核心数
- 操作系统频繁线程调度切换
- 大量CPU时间耗在保存恢复线程上下文
- 真正用于SQL执行的算力被稀释
```

### 3.2 锁竞争加剧

```
问题：
- 并发连接越多
- 争抢行锁、元数据锁概率越高
- 锁等待队列拉长
- 整体吞吐量不升反降
```

### 3.3 行业实测数据

```
常规OLTP业务：
- MySQL单实例最优活跃连接数 ≈ CPU核心数的1-2倍
- 达到4倍时性能开始明显下滑
- 超过10倍后吞吐量断崖式下跌
```

六、技术深入探讨

### Q1: 核心连接数10是怎么来的？

**方案参考**：
> 核心连接数计算公式：
> 
> 1. **数据库端**：最优活跃连接数 ≈ CPU核心数 × 2 + 磁盘数
> 2. **业务端**：核心连接数 ≈ 峰值QPS × 单条SQL平均执行时长 × 1.2（冗余）
> 
> 示例：峰值QPS=1000，SQL执行时长=10ms，核心连接数=1000×0.01×1.2=12
> 
> 不是经验值，是通过公式推导出来的。

### Q2: 连接数越多越好吗？

**方案参考**：
> 连接数过多有三大问题：
> 
> 1. **线程上下文切换**：连接数远超CPU核心数，操作系统频繁线程调度，CPU时间耗在上下文切换
> 2. **锁竞争加剧**：并发连接越多，争抢行锁、元数据锁概率越高，吞吐量不升反降
> 3. **性能断崖下跌**：行业实测，MySQL单实例最优连接数是CPU核心数的1-2倍，超过10倍后吞吐量断崖式下跌
> 
> 核心是连接池作用是复用连接，不是无限堆连接数。
