# @Transactional 与分布式事务

> **场景定位**：分布式系统技术场景  
> **核心设计要点**：分布式事务、本地事务局限、网络分区、服务隔离、数据一致性、事务补偿机制

---

## 🎯 一句话定位

**@Transactional 与分布式事务问题是什么？**
```
用了 @Transactional 注解，但跨服务调用时事务失效：
- 扣减库存成功，扣减余额成功，生成订单时服务宕机
- 库存和余额已扣，订单没生成
- 用户付了钱拿不到订单，数据不一致
- 本地事务无法回滚跨服务的操作
```

**生活化比喻**：就像你在 A 银行转账（扣余额），B 银行收款（加余额），但转账过程中网络断了，A 银行钱扣了，B 银行没收到，钱凭空消失了。

**核心特点**：分布式事务的核心不是"自动回滚"，而是如何在不可靠的分布式环境中保证数据最终一致。

### 核心观点（3 层方案）

**1. 本地消息表：适配简单场景**
```
核心思路：
- 下单服务在本地新增消息表
- 与业务操作（扣减余额）放在同一个本地事务
- 消息表记录待执行的库存扣减、订单生成任务
- 定时任务异步推送消息到其他服务
- 失败则重试，保证消息不丢失

生活化比喻：
本地消息表 = 备忘录（先记下来，再逐个执行）
定时任务 = 定期查看备忘录，完成待办事项
```

**2. 可靠消息最终一致性：基于 RocketMQ/Kafka**
```
核心思路：
- 先发送半事务消息（Half Message）
- 确认本地业务（扣减余额）执行成功后，再提交消息
- 其他服务消费消息执行对应操作
- 消费失败则不断重试，确保最终所有操作达成一致

生活化比喻：
半事务消息 = 先发消息"准备转账"
提交消息 = 确认本地成功后，通知其他银行执行
消费失败重试 = 转账失败不断重试直到成功
```

**3. TCC 补偿机制：适配高一致性要求场景**
```
核心思路：
- Try（尝试执行）：预留资源（冻结库存、冻结余额）
- Confirm（确认执行）：真正执行操作（扣减库存、扣减余额）
- Cancel（取消执行）：回滚资源（解冻库存、解冻余额）
- 全程手动控制，杜绝数据不一致

生活化比喻：
Try = 冻结资金（钱还在账户，但不能用）
Confirm = 真正转账（钱从 A 账户到 B 账户）
Cancel = 解冻资金（取消冻结，恢复正常）
```

## 详细章节

### 一、问题本质：为什么 @Transactional 无法解决分布式事务？

#### 1.1 本地事务 vs 分布式事务

```
本地事务（单服务）：
- 所有操作在同一个数据库
- 数据库事务管理器自动回滚
- @Transactional 注解有效

分布式事务（跨服务）：
- 操作分散在多个服务、多个数据库
- 网络波动、服务宕机、节点故障
- 本地事务无法回滚跨服务的操作
- @Transactional 只能管理当前服务的事务
```

#### 1.2 技术场景还原

**场景提问**：
```
用户下单要同时扣减库存、扣减余额、生成订单，
怎么保证这三个操作要么都成功要么都失败？
```

**普通回答**（60 分）：
```
加个 @Transactional 注解，事务管理器自动回滚简单得很。
```

**追问**（让候选人崩溃）：
```
如果扣减库存成功扣减余额也成功，
但生成订单时服务突然宕机，
库存和余额已经扣了，订单却没生成，
用户付了钱拿不到订单，数据不一致你怎么解决？
```

**加分回答**（90 分）：
```
@Transactionl 只能管理本地事务，
跨服务的分布式事务需要专门的方案：

1. 本地消息表：简单场景，异步重试
2. 可靠消息最终一致性：RocketMQ 事务消息
3. TCC 补偿机制：高一致性要求，手动控制

核心思路：不追求强一致性，而是保证最终一致性。
```

### 二、三种核心方案详解

#### 2.1 方案一：本地消息表

**适用场景**：简单场景，对一致性要求不高

**实现思路**：

```java
// 1. 本地消息表结构
CREATE TABLE `order_message` (
    `id` BIGINT PRIMARY KEY AUTO_INCREMENT,
    `order_id` BIGINT NOT NULL,
    `message_type` VARCHAR(50) NOT NULL,  // 库存扣减、订单生成等
    `status` TINYINT NOT NULL DEFAULT 0,  // 0-待执行，1-已完成，2-失败
    `retry_count` INT DEFAULT 0,
    `create_time` DATETIME DEFAULT CURRENT_TIMESTAMP,
    `update_time` DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);

// 2. 业务操作与消息写入同一个本地事务
@Transactional
public void createOrder(OrderRequest request) {
    // 1. 扣减余额（本地数据库）
    accountMapper.deductBalance(request.getUserId(), request.getAmount());
    
    // 2. 写入本地消息表（同一个数据库，同一个事务）
    OrderMessage message = new OrderMessage();
    message.setOrderId(request.getOrderId());
    message.setMessageType("DEDUCT_STOCK");
    message.setStatus(0);  // 待执行
    orderMessageMapper.insert(message);
    
    // 3. 写入另一条消息（订单生成）
    OrderMessage message2 = new OrderMessage();
    message2.setOrderId(request.getOrderId());
    message2.setMessageType("CREATE_ORDER");
    message2.setStatus(0);
    orderMessageMapper.insert(message2);
}

// 3. 定时任务异步发送消息（每 10 秒执行一次）
@Scheduled(fixedRate = 10000)
public void sendPendingMessages() {
    List<OrderMessage> messages = orderMessageMapper.selectPendingMessages();
    for (OrderMessage message : messages) {
        try {
            // 发送消息到其他服务（如库存服务）
            if ("DEDUCT_STOCK".equals(message.getMessageType())) {
                stockService.deductStock(message.getOrderId());
            } else if ("CREATE_ORDER".equals(message.getMessageType())) {
                orderService.generateOrder(message.getOrderId());
            }
            
            // 标记为已完成
            message.setStatus(1);
            orderMessageMapper.update(message);
        } catch (Exception e) {
            // 失败则重试次数 +1
            message.setRetryCount(message.getRetryCount() + 1);
            orderMessageMapper.update(message);
            log.error("消息发送失败，稍后重试", e);
        }
    }
}
```

**优点**：
- 实现简单，不依赖外部中间件
- 消息不丢失（本地事务保证）
- 失败自动重试

**缺点**：
- 需要额外的消息表
- 定时任务有延迟
- 需要处理消息幂等性

#### 2.2 方案二：可靠消息最终一致性（RocketMQ 事务消息）

**适用场景**：高并发场景，需要高性能

**实现思路**：

```java
// 1. 发送半事务消息
public void createOrderWithTransactionMessage(OrderRequest request) {
    // 1. 构建消息
    Message message = new Message(
        "ORDER_TOPIC",
        "CREATE_ORDER",
        JSON.toJSONString(request).getBytes()
    );
    
    // 2. 发送半事务消息（Half Message）
    TransactionSendResult sendResult = transactionProducer.sendMessageInTransaction(
        message,
        request  // 业务参数，传递给本地事务执行器
    );
    
    if (sendResult.getSendStatus() != SendStatus.SEND_OK) {
        throw new RuntimeException("消息发送失败");
    }
}

// 2. 本地事务执行器（执行本地业务逻辑）
@Component
public class OrderTransactionListener implements TransactionListener {
    
    @Autowired
    private AccountMapper accountMapper;
    
    @Override
    public LocalTransactionState executeLocalTransaction(Message msg, Object arg) {
        try {
            OrderRequest request = (OrderRequest) arg;
            
            // 执行本地事务：扣减余额
            accountMapper.deductBalance(request.getUserId(), request.getAmount());
            
            // 返回 COMMIT，提交消息
            return LocalTransactionState.COMMIT_MESSAGE;
        } catch (Exception e) {
            // 发生异常，回滚消息
            return LocalTransactionState.ROLLBACK_MESSAGE;
        }
    }
    
    @Override
    public LocalTransactionState checkLocalTransaction(MessageExt msg) {
        // 检查本地事务状态（如果 RocketMQ 没收到确认，会回调这个方法）
        // 根据业务状态返回 COMMIT 或 ROLLBACK
        return LocalTransactionState.COMMIT_MESSAGE;
    }
}

// 3. 库存服务消费消息
@Component
@RocketMQMessageListener(
    topic = "ORDER_TOPIC",
    consumerGroup = "stock-consumer-group"
)
public class StockConsumer implements RocketMQListener<String> {
    
    @Autowired
    private StockMapper stockMapper;
    
    @Override
    public void onMessage(String message) {
        OrderRequest request = JSON.parseObject(message, OrderRequest.class);
        
        // 扣减库存
        stockMapper.deductStock(request.getProductId(), request.getQuantity());
        
        // 消费失败会不断重试（RocketMQ 自动重试）
    }
}

// 4. 订单服务消费消息
@Component
@RocketMQMessageListener(
    topic = "ORDER_TOPIC",
    consumerGroup = "order-consumer-group"
)
public class OrderConsumer implements RocketMQListener<String> {
    
    @Autowired
    private OrderMapper orderMapper;
    
    @Override
    public void onMessage(String message) {
        OrderRequest request = JSON.parseObject(message, OrderRequest.class);
        
        // 生成订单
        orderMapper.insertOrder(request);
    }
}
```

**执行流程**：

```
1. 发送半事务消息（Half Message）
   ↓
2. RocketMQ 返回半消息成功
   ↓
3. 执行本地事务（扣减余额）
   ↓
4. 本地事务成功，提交消息（COMMIT）
   ↓
5. 消费者收到消息，执行各自业务（扣减库存、生成订单）
   ↓
6. 消费失败则不断重试，直到成功
```

**优点**：
- 高性能，异步解耦
- 消息可靠（RocketMQ 保证）
- 最终一致性

**缺点**：
- 依赖 RocketMQ 等中间件
- 需要处理消息幂等性
- 只保证最终一致性，不保证强一致性

#### 2.3 方案三：TCC 补偿机制

**适用场景**：高一致性要求，如金融、支付场景

**实现思路**：

```java
// 1. TCC 接口定义
@TccTransaction(
    confirmMethod = "confirm",
    cancelMethod = "cancel"
)
public void createOrder(OrderRequest request) {
    // Try 阶段：预留资源
    tryMethod(request);
}

// Try：尝试执行，预留资源
public void tryMethod(OrderRequest request) {
    // 1. 冻结库存（预扣，不真正扣减）
    stockMapper.freezeStock(request.getProductId(), request.getQuantity());
    
    // 2. 冻结余额（预扣，不真正扣减）
    accountMapper.freezeBalance(request.getUserId(), request.getAmount());
    
    // 3. 预创建订单（状态为"待确认"）
    orderMapper.insertPendingOrder(request);
}

// Confirm：确认执行，真正扣减资源
public void confirm(OrderRequest request) {
    // 1. 真正扣减库存（从冻结状态变为已扣减）
    stockMapper.confirmDeductStock(request.getProductId(), request.getQuantity());
    
    // 2. 真正扣减余额
    accountMapper.confirmDeductBalance(request.getUserId(), request.getAmount());
    
    // 3. 确认订单（状态从"待确认"变为"已完成"）
    orderMapper.confirmOrder(request.getOrderId());
}

// Cancel：取消执行，回滚资源
public void cancel(OrderRequest request) {
    // 1. 解冻库存
    stockMapper.unfreezeStock(request.getProductId(), request.getQuantity());
    
    // 2. 解冻余额
    accountMapper.unfreezeBalance(request.getUserId(), request.getAmount());
    
    // 3. 取消订单（状态从"待确认"变为"已取消"）
    orderMapper.cancelOrder(request.getOrderId());
}
```

**TCC 三阶段说明**：

```
Try 阶段：
- 预留资源（冻结库存、冻结余额）
- 资源被占用，但未真正扣减
- 业务检查（如库存是否充足）

Confirm 阶段：
- 真正执行操作（扣减库存、扣减余额）
- 不再做业务检查，只执行操作
- 要求幂等性（可能重复调用）

Cancel 阶段：
- 回滚资源（解冻库存、解冻余额）
- 释放预留的资源
- 要求幂等性（可能重复调用）
```

**优点**：
- 强一致性（Try 阶段预留资源，Confirm/Cancel 阶段保证一致性）
- 性能较好（无锁，资源预留）
- 灵活控制（手动实现三阶段）

**缺点**：
- 实现复杂（需要手动实现三阶段）
- 代码侵入性强
- 需要处理幂等性


### 考点 2：本地消息表和 RocketMQ 事务消息有什么区别？

**方案参考**（60 分）：
```
本地消息表：
- 在本地数据库建消息表
- 与业务操作放在同一个事务
- 定时任务异步发送消息
- 适合简单场景

RocketMQ 事务消息：
- 依赖 RocketMQ 的半事务消息
- 本地事务成功后提交消息
- 消费者自动重试
- 适合高并发场景
```

**加分回答**（90 分）：
```
两者的核心区别：

1. 实现机制：
   本地消息表：
   - 本地数据库消息表 + 定时任务
   - 不依赖外部中间件
   - 实现简单，但有延迟
   
   RocketMQ 事务消息：
   - 依赖 RocketMQ 的 Half Message
   - 本地事务执行器控制提交/回滚
   - 高性能，实时性更好

2. 性能对比：
   本地消息表：
   - 定时任务轮询（如每 10 秒）
   - 有延迟，不适合实时性要求高的场景
   
   RocketMQ：
   - 异步消息，实时推送
   - 高并发，适合大促等场景

3. 可靠性：
   本地消息表：
   - 依赖本地事务，消息不丢失
   - 但定时任务可能失败
   
   RocketMQ：
   - 消息队列保证可靠性
   - 自动重试，更稳定

4. 适用场景：
   本地消息表：小型项目，无消息中间件
   RocketMQ：大型项目，高并发场景

推荐：
优先使用 RocketMQ 事务消息，性能更好，可靠性更高。
如果项目没有消息中间件，可以用本地消息表。
```

### 考点 3：TCC 的三阶段是什么？怎么保证一致性？

**方案参考**（60 分）：
```
TCC 三阶段：
1. Try：预留资源（冻结库存、冻结余额）
2. Confirm：确认执行（真正扣减资源）
3. Cancel：取消执行（解冻资源）

保证一致性：
- Try 阶段预留资源，不真正扣减
- Confirm 阶段真正扣减，或 Cancel 阶段回滚
- 三阶段要么都成功，要么都回滚
```

**加分回答**（90 分）：
```
TCC 三阶段详解：

1. Try 阶段（尝试执行）：
   - 业务检查（如库存是否充足）
   - 预留资源（冻结库存、冻结余额）
   - 资源被占用，但未真正扣减
   - 返回执行结果

2. Confirm 阶段（确认执行）：
   - 不再做业务检查
   - 真正执行操作（扣减库存、扣减余额）
   - 要求幂等性（可能重复调用）
   - 所有参与者都成功，事务提交

3. Cancel 阶段（取消执行）：
   - 回滚资源（解冻库存、解冻余额）
   - 释放预留的资源
   - 要求幂等性（可能重复调用）
   - 任何一个参与者失败，所有参与者回滚

保证一致性的关键：

1. 资源预留：
   - Try 阶段冻结资源，不真正扣减
   - 避免 Confirm/Cancel 阶段的业务冲突

2. 幂等性：
   - Confirm/Cancel 可能重复调用
   - 必须保证幂等性（多次调用结果一致）

3. 空回滚：
   - Try 阶段失败，Cancel 阶段要能处理
   - Cancel 阶段发现没有预留资源，直接返回成功

4. 悬挂：
   - Cancel 阶段先于 Try 阶段执行
   - Try 阶段发现已取消，直接返回失败

适用场景：
- 高一致性要求（如金融、支付）
- 对性能要求较高（无锁，资源预留）
- 愿意承担实现复杂度

核心思路：
TCC 是手动控制的分布式事务，
通过 Try-Confirm-Cancel 三阶段，
保证所有操作要么都成功，要么都回滚。
```

## 总结

### 一句话总结

**分布式事务的核心不是"自动回滚"，而是如何在不可靠的分布式环境中保证数据最终一致。**

### 核心记忆点

```
1. 三种方案：
   - 本地消息表：简单场景，异步重试
   - 可靠消息最终一致性：RocketMQ 事务消息，高并发
   - TCC 补偿机制：高一致性要求，手动控制

2. 核心区别：
   - 本地消息表：本地事务 + 定时任务，实现简单
   - RocketMQ：半事务消息 + 消费者重试，性能高
   - TCC：Try-Confirm-Cancel 三阶段，强一致性

3. 关键要点：
   - 不追求强一致性，而是最终一致性
   - 必须处理幂等性（Confirm/Cancel 可能重复调用）
   - 根据业务场景选择合适方案

4. 技术要点：
   - 先说 @Transactional 的局限性
   - 再说三种方案的适用场景
   - 最后说核心思路（最终一致性）
```
