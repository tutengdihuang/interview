# Spring 循环依赖异常分析

> **场景定位**：Spring 框架技术场景  
> **核心设计要点**：循环依赖、三级缓存、单例 Bean、构造器注入、BeanPostProcessor、初始化时机

---

## 🎯 一句话定位

**Spring 循环依赖问题是什么？**
```
Spring 默认解决了循环依赖，但项目中还是频繁报 BeanCreationException：
- 全程用的 @Autowired 自动注入
- Bean 都交给 Spring 容器管理
- 没有手动 new 对象
- 但还是报循环依赖异常
```

**生活化比喻**：就像两个人互相借钱，A 说"你先借我 100，我再借你 100"，B 说"你先借我 100，我再借你 100"，结果谁也借不到。Spring 的三级缓存就像中间人，先给 A 打个欠条，A 再借给 B，B 再借给 A。

**核心特点**：Spring 解决的循环依赖是有条件的，不是所有场景都能解决。

---

## 💎 核心观点（5 分钟速览版）

> **快速概览**

### 核心观点（3 个本质）

**1. 本质一：Spring 解决的是「单例 Bean 的 setter 注入循环依赖」，其他场景不支持**
```
三级缓存机制：
- singletonObjects：成品 Bean 缓存
- earlySingletonObjects：半成品 Bean 缓存
- singletonFactories：Bean 工厂缓存

不支持的场景：
- 非单例 Bean（prototype）
- 构造器注入（初始化时就需要依赖对象）

生活化比喻：
三级缓存 = 中间人打欠条
单例 Bean = 只有一个人，可以打欠条
构造器注入 = 一开始就要钱，没法打欠条
```

**2. 本质二：Bean 初始化过程中触发依赖，导致三级缓存无法生效**
```
初始化方法触发依赖：
- @PostConstruct、init-method 中触发了对循环依赖 Bean 的调用
- 此时 Bean 还未完成初始化
- 三级缓存中未暴露可用实例

@Lazy 懒加载：
- 初始化时机延迟
- 可能打破循环依赖的解决逻辑

生活化比喻：
初始化触发依赖 = 欠条还没打，就要用钱
@Lazy = 延迟打欠条，但急需用钱
```

**3. 本质三：自定义 BeanPostProcessor，破坏了 Spring 循环依赖的处理流程**
```
BeanPostProcessor 问题：
- 自定义后置处理器中对循环依赖的 Bean 进行了提前调用或修改
- 打乱三级缓存的暴露和获取逻辑
- 导致 Spring 无法正常解决循环依赖

其他场景：
- @Scope("prototype")（多例）
- @DependsOn 强制依赖顺序

生活化比喻：
BeanPostProcessor = 中间人搞破坏了
提前调用 = 欠条还没打好，中间人就干预
@Scope("prototype") = 多个人，没法打欠条
```

> **Spring 循环依赖三本质 = 非单例/构造器注入不支持 + 初始化时触发依赖 + 后置处理器破坏流程**

## 一、问题本质：Spring 循环依赖的局限性

### ❌ 常见误区

**误区 1：Spring 能解决所有循环依赖**
```
问题：
- Spring 只解决单例 Bean 的 setter 注入循环依赖
- 构造器注入、prototype 作用域不支持
- 初始化方法中触发依赖也会失败

解决：
- 理解三级缓存的适用范围
- 改用 setter 注入
- 确保 Bean 为单例
```

**误区 2：用了 @Autowired 就不会有问题**
```
问题：
- @Autowired 只是自动注入
- 不能解决构造器注入的循环依赖
- 不能解决初始化时触发依赖的问题

解决：
- 区分构造器注入和 setter 注入
- 避免在初始化方法中调用依赖 Bean
```

**误区 3：循环依赖层级太深才会报错**
```
问题：
- 两层循环依赖（A→B→A）也会报错
- 如果不是单例或用了构造器注入

解决：
- 确保 Bean 为单例
- 使用 setter 注入
- 避免初始化时调用依赖 Bean
```

## 二、本质一：Spring 解决的是单例 Bean 的 setter 注入

### 2.1 三级缓存机制

**生活化比喻**：
```
三级缓存 = 中间人打欠条

singletonObjects = 成品仓库
- 存放完全初始化好的 Bean
- 可以直接使用

earlySingletonObjects = 半成品仓库
- 存放提前暴露的 Bean（还未完全初始化）
- 用于解决循环依赖

singletonFactories = 工厂仓库
- 存放 Bean 工厂
- 可以生成早期 Bean 实例

流程：
1. A 初始化时需要 B
2. A 先创建实例（半成品），放入 earlySingletonObjects
3. A 去创建 B
4. B 初始化时需要 A
5. B 从 earlySingletonObjects 获取 A 的半成品
6. B 完成初始化
7. A 拿到 B，完成初始化
8. A 放入 singletonObjects
```

**代码示例**：
```java
// Spring 三级缓存源码（简化版）
public class DefaultSingletonBeanRegistry {
    
    // 一级缓存：成品 Bean
    private final Map<String, Object> singletonObjects = new ConcurrentHashMap<>();
    
    // 二级缓存：半成品 Bean（早期暴露）
    private final Map<String, Object> earlySingletonObjects = new ConcurrentHashMap<>();
    
    // 三级缓存：Bean 工厂
    private final Map<String, ObjectFactory<?>> singletonFactories = new ConcurrentHashMap<>();
    
    protected Object getSingleton(String beanName, boolean allowEarlyReference) {
        // 1. 从一级缓存获取（成品）
        Object singletonObject = this.singletonObjects.get(beanName);
        
        if (singletonObject == null) {
            // 2. 从二级缓存获取（半成品）
            singletonObject = this.earlySingletonObjects.get(beanName);
            
            if (singletonObject == null && allowEarlyReference) {
                // 3. 从三级缓存获取（工厂）
                ObjectFactory<?> singletonFactory = this.singletonFactories.get(beanName);
                
                if (singletonFactory != null) {
                    // 4. 通过工厂创建早期 Bean
                    singletonObject = singletonFactory.getObject();
                    
                    // 5. 放入二级缓存
                    this.earlySingletonObjects.put(beanName, singletonObject);
                    
                    // 6. 从三级缓存移除
                    this.singletonFactories.remove(beanName);
                }
            }
        }
        
        return singletonObject;
    }
}
```

### 2.2 构造器注入不支持

**生活化比喻**：
```
构造器注入 = 一开始就要钱
- 创建 Bean 时就需要依赖对象
- 三级缓存无法提前暴露实例
- 必然报循环依赖异常

就像：
- A 说"你先给我 100，我再给你打欠条"
- B 说"你先给我打欠条，我再给你 100"
- 死锁了
```

**代码示例**：
```java
// ❌ 错误做法：构造器注入导致循环依赖
@Component
public class ServiceA {
    
    private final ServiceB serviceB;
    
    @Autowired
    public ServiceA(ServiceB serviceB) {
        this.serviceB = serviceB; // 创建 A 时需要 B
    }
}

@Component
public class ServiceB {
    
    private final ServiceA serviceA;
    
    @Autowired
    public ServiceB(ServiceA serviceA) {
        this.serviceA = serviceA; // 创建 B 时需要 A
    }
}

// ✅ 正确做法：setter 注入
@Component
public class ServiceA {
    
    private ServiceB serviceB;
    
    @Autowired
    public void setServiceB(ServiceB serviceB) {
        this.serviceB = serviceB; // 先创建实例，再注入依赖
    }
}

@Component
public class ServiceB {
    
    private ServiceA serviceA;
    
    @Autowired
    public void setServiceA(ServiceA serviceA) {
        this.serviceA = serviceA; // 先创建实例，再注入依赖
    }
}
```

### 2.3 prototype 作用域不支持

**生活化比喻**：
```
prototype = 多个人
- 每次获取都创建新实例
- 无法打欠条（因为每次都是新的）
- 无法解决循环依赖

就像：
- A 有多个分身
- B 也有多个分身
- 中间人不知道给哪个分身打欠条
```

**代码示例**：
```java
// ❌ 错误做法：prototype 作用域导致循环依赖
@Component
@Scope("prototype")
public class ServiceA {
    
    @Autowired
    private ServiceB serviceB;
}

@Component
@Scope("prototype")
public class ServiceB {
    
    @Autowired
    private ServiceA serviceA;
}

// ✅ 正确做法：单例作用域（默认）
@Component
public class ServiceA {
    
    @Autowired
    private ServiceB serviceB;
}

@Component
public class ServiceB {
    
    @Autowired
    private ServiceA serviceA;
}
```

## 三、本质二：Bean 初始化过程中触发依赖

### 3.1 @PostConstruct 触发依赖

**生活化比喻**：
```
@PostConstruct = 欠条还没打，就要用钱
- 初始化方法中触发了对循环依赖 Bean 的调用
- 此时 Bean 还未完成初始化
- 三级缓存中未暴露可用实例

就像：
- A 刚打欠条，还没拿到钱
- 就要用钱
- 但钱还没到
```

**代码示例**：
```java
// ❌ 错误做法：@PostConstruct 中调用依赖 Bean
@Component
public class ServiceA {
    
    @Autowired
    private ServiceB serviceB;
    
    @PostConstruct
    public void init() {
        // 初始化时调用 serviceB
        // 此时 serviceB 可能还未完成初始化
        serviceB.doSomething();
    }
}

@Component
public class ServiceB {
    
    @Autowired
    private ServiceA serviceA;
    
    @PostConstruct
    public void init() {
        // 初始化时调用 serviceA
        // 此时 serviceA 可能还未完成初始化
        serviceA.doSomething();
    }
}

// ✅ 正确做法：避免在初始化方法中调用依赖 Bean
@Component
public class ServiceA {
    
    @Autowired
    private ServiceB serviceB;
    
    @PostConstruct
    public void init() {
        // 只做自己的初始化逻辑
        // 不调用依赖 Bean
        System.out.println("ServiceA 初始化");
    }
    
    public void doSomething() {
        // 在业务方法中调用依赖 Bean
        serviceB.doSomething();
    }
}
```

### 3.2 @Lazy 懒加载

**生活化比喻**：
```
@Lazy = 延迟打欠条
- 初始化时机延迟
- 可能打破循环依赖的解决逻辑

就像：
- A 说"我先不打欠条，等需要用钱时再说"
- B 说"我也是"
- 结果急需用钱时，发现欠条还没打
```

**代码示例**：
```java
// ❌ 错误做法：@Lazy 可能导致循环依赖
@Component
public class ServiceA {
    
    @Autowired
    @Lazy
    private ServiceB serviceB;
}

@Component
public class ServiceB {
    
    @Autowired
    @Lazy
    private ServiceA serviceA;
}

// ✅ 正确做法：避免使用 @Lazy 解决循环依赖
// 应该重构代码，避免循环依赖
@Component
public class ServiceA {
    
    @Autowired
    private ServiceB serviceB;
}

@Component
public class ServiceB {
    
    @Autowired
    private ServiceA serviceA;
}
```

## 四、本质三：自定义 BeanPostProcessor 破坏流程

### 4.1 BeanPostProcessor 问题

**生活化比喻**：
```
BeanPostProcessor = 中间人搞破坏
- 自定义后置处理器中对循环依赖的 Bean 进行了提前调用或修改
- 打乱三级缓存的暴露和获取逻辑
- 导致 Spring 无法正常解决循环依赖

就像：
- 中间人本来只负责打欠条
- 但他提前干预了借钱过程
- 结果欠条打乱了
```

**代码示例**：
```java
// ❌ 错误做法：BeanPostProcessor 中提前调用 Bean
@Component
public class CustomBeanPostProcessor implements BeanPostProcessor {
    
    @Override
    public Object postProcessBeforeInitialization(Object bean, String beanName) throws BeansException {
        // 在 Bean 初始化前调用
        if (bean instanceof ServiceA) {
            ServiceA serviceA = (ServiceA) bean;
            // 提前调用 serviceB，可能导致循环依赖
            serviceA.getServiceB().doSomething();
        }
        
        return bean;
    }
}

// ✅ 正确做法：避免在 BeanPostProcessor 中调用依赖 Bean
@Component
public class CustomBeanPostProcessor implements BeanPostProcessor {
    
    @Override
    public Object postProcessBeforeInitialization(Object bean, String beanName) throws BeansException {
        // 只做增强逻辑，不调用依赖 Bean
        if (bean instanceof ServiceA) {
            System.out.println("增强 ServiceA");
        }
        
        return bean;
    }
}
```

### 4.2 @DependsOn 强制依赖顺序

**生活化比喻**：
```
@DependsOn = 强制顺序
- 强制指定 Bean 的初始化顺序
- 可能导致循环依赖

就像：
- A 说"我必须在 B 之后初始化"
- B 说"我必须在 A 之后初始化"
- 死锁了
```

**代码示例**：
```java
// ❌ 错误做法：@DependsOn 导致循环依赖
@Component
@DependsOn("serviceB")
public class ServiceA {
    
    @Autowired
    private ServiceB serviceB;
}

@Component
@DependsOn("serviceA")
public class ServiceB {
    
    @Autowired
    private ServiceA serviceA;
}
```

五、技术深入探讨

### 考点 1：Spring 如何解决循环依赖？

**方案参考**（30 秒版）：
> "Spring 通过三级缓存解决单例 Bean 的 setter 注入循环依赖：1）一级缓存 singletonObjects 存放成品 Bean；2）二级缓存 earlySingletonObjects 存放半成品 Bean（早期暴露）；3）三级缓存 singletonFactories 存放 Bean 工厂。流程：A 初始化时需要 B，A 先创建实例放入二级缓存，然后创建 B，B 需要 A 时从二级缓存获取 A 的半成品，B 完成初始化，A 拿到 B 完成初始化，最后 A 放入一级缓存。"

**加分回答**：
> "Spring 只解决单例 Bean 的 setter 注入循环依赖，构造器注入和 prototype 作用域不支持。构造器注入在创建 Bean 时就需要依赖对象，三级缓存无法提前暴露实例。prototype 每次获取都创建新实例，无法打欠条。实际生产中，我会用 setter 注入，确保 Bean 为单例，避免在初始化方法中调用依赖 Bean。"

### 考点 2：为什么构造器注入不支持循环依赖？

**方案参考**：
> "构造器注入不支持循环依赖是因为创建 Bean 时就需要依赖对象。A 的构造器需要 B，B 的构造器需要 A，Spring 无法先创建 A 的实例（因为构造器需要 B），也无法先创建 B 的实例（因为构造器需要 A），形成死锁。三级缓存只能提前暴露实例，不能提前暴露构造器参数。"

**加分回答**：
> "解决方案有三种：1）改用 setter 注入，先创建实例再注入依赖；2）用 @Lazy 注解，延迟加载；3）重构代码，避免循环依赖（推荐）。实际生产中，我推荐用构造器注入 + @Lazy，或者重构代码，将共同依赖抽取到第三个 Bean。"

### 考点 3：如何避免循环依赖？

**方案参考**：
> "避免循环依赖要从三个方面：1）代码设计：避免 A 依赖 B、B 依赖 A，可以用共同依赖抽取到第三个 Bean；2）注入方式：用 setter 注入代替构造器注入；3）确保 Bean 为单例，避免使用 prototype 作用域。"

**加分回答**：
> "我会从架构层面避免循环依赖：1）分层设计：Controller→Service→Repository，避免反向依赖；2）依赖倒置：依赖抽象而不是具体实现；3）事件驱动：用 Spring 事件机制解耦；4）如果确实需要循环依赖，用 setter 注入 + 单例作用域。同时要理解 Spring 三级缓存的原理，知道哪些场景不支持，避免踩坑。"

## 六、总结（一句话带走）

### 🎯 一句话总结

> **Spring 循环依赖三本质 = 非单例/构造器注入不支持 + 初始化时触发依赖 + 后置处理器破坏流程**

### 🧠 核心记忆点

1. **Spring 如何解决循环依赖？** 三级缓存：singletonObjects（成品）、earlySingletonObjects（半成品）、singletonFactories（工厂）。
2. **为什么构造器注入不支持？** 创建 Bean 时就需要依赖对象，无法提前暴露实例。
3. **为什么 prototype 不支持？** 每次获取都创建新实例，无法打欠条。
4. **初始化时触发依赖为什么会失败？** Bean 还未完成初始化，三级缓存中未暴露可用实例。
5. **如何避免循环依赖？** 分层设计、依赖倒置、事件驱动、setter 注入。
