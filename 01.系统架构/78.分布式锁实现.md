# 分布式锁实现

> **场景定位**：分布式系统技术场景  
> **核心设计要点**：锁可靠性、自动续约、误删防护、架构优化

---

## 🎯 一句话定位

**分布式锁解决什么问题？**
```
分布式环境下，多个节点并发访问同一资源
需要保证同一时刻只有一个节点能访问
```

**生活化比喻**：
就像公共厕所的锁：
- 进去后锁门（加锁）
- 别人看到"有人"就等（阻塞）
- 出来开门（释放锁）

---

## 💎 核心观点（5 分钟速览版）

### 核心观点（5 个关键点）

**1. SETNX + 过期时间不是万能的**
```
❌ 误区：setnx + expire 就搞定
✅ 真相：业务超时、锁误删、节点宕机
都会让锁失效
```

**2. 三大隐患**
```
业务执行时间 > 锁过期时间 → 锁提前释放
删除锁时没校验 → 误删别人的锁
Redis 节点宕机 → 锁丢失
```

**3. 看门狗自动续约**
```
业务没执行完，锁自动续期
防止锁提前释放导致并发问题
```

**4. 锁身份校验**
```
加锁时写入唯一请求标识
删锁时校验标识
只能删除自己的锁
```

**5. 锁力度优化**
```
大库存拆分为多个分片
独立加锁，缩小锁竞争范围
```

## 一、分布式锁的隐患

### ❌ 典型事故

```
秒杀活动用 Redis 分布式锁控制库存扣减

问题：
1. 锁过期时间设为 10 秒
2. 业务执行了 15 秒（网络抖动）
3. 第 10 秒锁自动释放
4. 第二个请求拿到锁，进入执行
5. 第一个请求执行完，误删了第二个请求的锁
6. 库存超卖
```

## 二、可靠分布式锁实现

### 2.1 基础实现（有问题）

```go
// ❌ 有问题的实现
func Lock(key string, expire time.Duration) bool {
    // 加锁
    ok := redis.SetNX(key, "1", expire)
    return ok
}

func Unlock(key string) {
    redis.Del(key)
}
```

### 2.2 可靠实现（推荐）

```go
type DistributedLock struct {
    key       string
    value     string // 唯一标识
    expire    time.Duration
    watchdog  *time.Timer
}

// 加锁
func (l *DistributedLock) Lock() bool {
    // 1. 加锁，设置唯一标识
    ok := redis.SetNX(l.key, l.value, l.expire)
    if !ok {
        return false
    }
    
    // 2. 启动看门狗，自动续约
    l.startWatchdog()
    
    return true
}

// 解锁
func (l *DistributedLock) Unlock() {
    // 1. 停止看门狗
    l.stopWatchdog()
    
    // 2. Lua 脚本：校验标识 + 删除锁（原子操作）
    script := `
        if redis.call("GET", KEYS[1]) == ARGV[1] then
            return redis.call("DEL", KEYS[1])
        else
            return 0
        end
    `
    redis.Eval(script, []string{l.key}, l.value)
}

// 看门狗自动续约
func (l *DistributedLock) startWatchdog() {
    l.watchdog = time.AfterFunc(l.expire/2, func() {
        // 续约
        redis.Expire(l.key, l.expire)
        // 继续续约
        l.startWatchdog()
    })
}

func (l *DistributedLock) stopWatchdog() {
    if l.watchdog != nil {
        l.watchdog.Stop()
    }
}
```

## 三、锁分片优化

### 3.1 库存分片

```go
type InventoryLock struct {
    shards int
}

// 大库存拆分为多个分片
func (l *InventoryLock) Deduct(goodsID string, amount int) error {
    // 随机选一个分片
    shard := rand.Intn(l.shards)
    lockKey := fmt.Sprintf("lock:%s:%d", goodsID, shard)
    
    // 加锁
    lock := NewDistributedLock(lockKey, 10*time.Second)
    if !lock.Lock() {
        return errors.New("获取锁失败")
    }
    defer lock.Unlock()
    
    // 扣减库存
    return db.Exec("UPDATE inventory SET stock = stock - ? WHERE goods_id = ? AND shard = ?",
        amount, goodsID, shard)
}
```

### 3.2 多级锁架构

```go
// 应用层本地锁 + 分布式锁
func ProcessOrder(orderID string) error {
    // 1. 先抢本地锁（单机并发控制）
    localLock.Lock(orderID)
    defer localLock.Unlock(orderID)
    
    // 2. 再抢分布式锁（跨机器并发控制）
    distLock := NewDistributedLock(fmt.Sprintf("lock:%s", orderID), 10*time.Second)
    if !distLock.Lock() {
        return errors.New("获取分布式锁失败")
    }
    defer distLock.Unlock()
    
    // 3. 执行业务
    return doBusiness()
}
```

四、技术深入探讨

### Q1: 分布式锁有哪些隐患？

**方案参考**：
> 分布式锁有三大隐患：
> 
> 1. **锁提前释放**：业务执行时间 > 锁过期时间，锁自动释放，导致并发问题
> 2. **误删别人的锁**：删锁时没校验身份，可能删掉别人的锁
> 3. **节点宕机**：Redis 节点宕机，锁丢失
> 
> 解决方案：看门狗自动续约、Lua 脚本校验身份、Redlock 算法多节点。

### Q2: 如何优化高并发场景下的锁性能？

**方案参考**：
> 高并发下锁竞争严重，优化方案：
> 
> 1. **锁分片**：大库存拆分为多个分片，独立加锁，降低单 Key 竞争
> 2. **多级锁**：应用层本地锁 + 分布式锁，双层防护
> 3. **锁粒度**：尽量缩小锁粒度，只锁必要的数据
> 4. **读写分离**：读多写少场景用读写锁，提高并发
> 
> 核心是缩小锁竞争范围，提高并发度。
