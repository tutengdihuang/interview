## 一、为什么微服务高可用这么难？

### 🔍 核心问题（30 秒版）

**生活化比喻**：
```
微服务高可用的三大难题：
1. 服务雪崩：一个服务挂了，其他服务也跟着挂
2. 数据不一致：多个服务协同，数据对不上
3. 幂等问题：同一个请求处理多次，数据错乱

就像城市管理：
- 交通部门罢工，整个城市瘫痪（服务雪崩）
- 多个部门数据不同步（数据不一致）
```

| 难题 | 具体表现 | 线上后果 | 生活化比喻 |
|------|---------|---------|-----------|
| **服务雪崩** | 一个服务故障，引发连锁反应 | 整个系统瘫痪 | 交通部门罢工，城市瘫痪 |
| **数据不一致** | 多个服务协同，数据对不上 | 业务逻辑错误 | 多个部门数据不同步 |

## 二、第一层：微服务高可用方案深度拆解

### 2.1 限流

**限流算法**：

| 算法 | 原理 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|---------|
| **计数器** | 固定时间内计数 | 简单 | 临界问题 | 简单场景 |
| **滑动窗口** | 滑动时间窗口计数 | 平滑 | 复杂 | 一般场景 |
| **漏桶** | 固定速率处理 | 平滑 | 无法应对突发 | 稳定流量 |
| **令牌桶** | 固定速率生成令牌 | 可应对突发 | 复杂 | 突发流量 |

**代码示例（Sentinel）**：
```java
// ✅ 限流配置
@SentinelResource(
    value = "createOrder",
    blockHandler = "createOrderBlock"
)
public Result createOrder(OrderRequest request) {
    return orderService.createOrder(request);
}

// 限流降级方法
public Result createOrderBlock(OrderRequest request, BlockException ex) {
    return Result.error("系统繁忙，请稍后重试");
}
```

**生活化比喻**：
```
就像商场限流：
- 计数器：固定时间内最多进 1000 人
- 滑动窗口：每分钟最多进 1000 人
- 漏桶：每秒最多进 10 人
- 令牌桶：每秒生成 10 个令牌，有令牌才能进
```

### 2.2 熔断

**熔断三态**：
```
关闭（Closed）：
- 正常状态
- 请求正常通过

打开（Open）：
- 失败率达到阈值
- 请求直接拒绝，快速失败

半开（Half-Open）：
- 一段时间后尝试放行少量请求
- 成功则恢复，失败则继续熔断
```

**代码示例（Sentinel）**：
```java
// ✅ 熔断配置
@SentinelResource(
    value = "queryLogistics",
    fallback = "logisticsFallback"
)
public LogisticsInfo queryLogistics(String orderId) {
    return thirdPartyApi.query(orderId);
}

// 熔断降级方法
public LogisticsInfo logisticsFallback(String orderId) {
    log.warn("物流查询熔断，返回兜底数据");
    LogisticsInfo fallback = new LogisticsInfo();
    fallback.setOrderId(orderId);
    fallback.setStatus("查询中，请稍后重试");
    return fallback;
}
```

**生活化比喻**：
```
就像电路保险丝：
- 关闭：正常供电
- 打开：电流过大，保险丝熔断，停止供电
- 半开：一段时间后尝试恢复供电
```

### 2.3 服务隔离

**隔离方式**：

| 方式 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **线程池隔离** | 每个服务独立线程池 | 完全隔离 | 线程切换开销 |
| **信号量隔离** | 限制并发数 | 轻量级 | 无法隔离超时 |

**代码示例**：
```yaml
# 线程池隔离
feign:
  client:
    config:
      logistics-service:
        connectTimeout: 3000
        readTimeout: 5000
        # 独立线程池
        maxConnections: 100
        maxConnectionsPerRoute: 50
```

## 三、第二层：分布式事务与幂等量化设计

### 3.1 分布式事务选型

**三种模式对比**：

| 模式 | 原理 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|---------|
| **XA** | 两阶段提交，强一致 | 强一致性 | 性能差、资源锁定 | 银行转账 |
| **TCC** | Try-Confirm-Cancel，补偿 | 性能好 | 开发复杂 | 电商下单 |
| **SA** | 基于消息队列，最终一致 | 性能最好 | 不保证强一致 | 大部分场景 |

**代码示例（TCC）**：
```java
// ✅ TCC 分布式事务
@TwoPhaseBusinessAction(
    name = "deductStock",
    commitMethod = "commit",
    rollbackMethod = "rollback"
)
public interface StockService {
    
    // Try 阶段：预扣库存
    boolean tryDeduct(BusinessActionContext context, 
                      @BusinessActionContextParameter(paramName = "productId") Long productId,
                      @BusinessActionContextParameter(paramName = "count") Integer count);
    
    // Confirm 阶段：确认扣减
    boolean commit(BusinessActionContext context);
    
    // Cancel 阶段：取消扣减
    boolean rollback(BusinessActionContext context);
}
```

**生活化比喻**：
```
就像跨部门办事：
- XA：两个部门同时签字，要么全签，要么全不签（强一致）
- TCC：先预约（Try），确认办理（Confirm），取消预约（Cancel）
- SA：发快递，对方收到后确认（最终一致）
```

### 3.2 幂等设计

**幂等方案**：

| 方案 | 原理 | 适用场景 |
|------|------|---------|
| **唯一索引** | 数据库唯一约束 | 插入操作 |
| **状态机** | 状态单向流转 | 状态变更 |
| **分布式锁** | 同一时间只处理一次 | 高并发场景 |

**代码示例**：
```java
// ✅ 幂等设计（Redis）
public void processOrder(String orderNo) {
    String lockKey = "lock:order:" + orderNo;
    
    if (redisLock.tryLock(lockKey, 10, TimeUnit.SECONDS)) {
        try {
            // 业务逻辑
            orderService.process(orderNo);
        } finally {
            redisLock.unlock(lockKey);
        }
    } else {
        log.info("重复请求，忽略");
    }
}
```

五、技术深入探讨

### Q1: 限流、熔断、降级怎么联动业务？

**答**：
> 联动策略：
>
> 1. **限流**：控制进入系统的流量，防止过载
> 2. **熔断**：下游服务故障时，快速失败，避免雪崩
> 3. **降级**：服务不可用时，返回兜底数据
>
> 示例：
> - 限流：每秒最多 1000 个请求
> - 熔断：物流接口失败率 > 50%，触发熔断
> - 降级：熔断后返回"查询中，请稍后重试"

### Q2: 分布式事务 TCC、XA、SA 怎么落地？

**答**：
> 选型建议：
>
> **XA**：强一致性场景，如银行转账
> **TCC**：高性能场景，如电商下单
> **SA**：最终一致性场景，如大部分业务
>
> 关键：根据业务需求选择，不要一刀切。

### Q3: 全链路幂等怎么防控？

**答**：
> 全链路幂等防控：
>
> 1. **网关层**：请求去重，防止重复提交
> 2. **服务层**：唯一索引、状态机、分布式锁
> 3. **数据层**：数据库唯一约束
>
> 核心：每一层都要有幂等保障。
