# 分布式事务实现

> **场景定位**：分布式系统技术场景  
> **核心设计要点**：事务方案选择、异常场景处理、数据一致性保障

---

## 🎯 一句话定位

**分布式事务解决什么问题？**
```
跨多个服务的数据操作，要保证原子性
要么全成功，要么全回滚
```

**生活化比喻**：
就像银行转账：
- A 账户扣 100 元
- B 账户加 100 元
这两步必须同时成功或同时失败，否则就出问题了。

---

## 💎 核心观点（5 分钟速览版）

### 核心观点（5 个关键点）

**1. 加注解不等于搞定分布式事务**
```
❌ 误区：加个 @GlobalTransactional 就完事
✅ 真相：框架宕机、网络异常都会打破原子性
必须有兜底方案
```

**2. 业务分级差异化方案**
```
核心链路（订单/支付/库存）：TCC 或本地消息表
非核心链路（积分/通知）：可靠消息最终一致性
```

**3. 异常场景是核心难点**
```
事务协调器宕机 → 悬挂事务
网络分区 → 数据不一致
幂等失效 → 重复执行
```

**4. 对账是最后一道防线**
```
跨服务数据对账系统
定时补偿流程
人工介入机制
```

**5. 柔性事务设计**
```
能本地事务就不跨服务
能异步就不强同步
最终一致性 > 强一致性
```

> **分布式事务 = 业务分级（TCC/消息表） + 异常兜底（对账补偿） + 柔性设计（最终一致性）**

## 一、分布式事务的幽灵陷阱

### ❌ Seata AT 模式的隐患

**典型事故**：
```
下单链路跨三个服务：
1. 订单服务：创建订单
2. 库存服务：扣减库存
3. 账户服务：扣减余额

大促当天有几笔订单：
- 库存扣了
- 余额扣了
- 订单状态却是"创建失败"

用户钱扣了货没订到！
```

**根因分析**：
```
全局事务已提交
三个服务的本地事务都显示成功
但订单表就是没生成有效订单
回滚也回滚不了
```

**问题本质**：
```
分布式事务框架不是万能的
协调器宕机、网络异常、幂等失效
都会打破原子性
```

## 二、业务分级差异化方案

### 2.1 核心链路：TCC 模式

**TCC 三阶段**：
```
Try：预留资源（冻结库存、冻结余额）
Confirm：确认执行（扣减库存、扣减余额）
Cancel：取消执行（解冻库存、解冻余额）
```

**实现示例**：
```go
// Try 阶段：冻结库存
func TryDeductInventory(orderID string, amount int) error {
    // 1. 检查库存是否充足
    stock := db.GetInventory(goodsID)
    if stock < amount {
        return errors.New("库存不足")
    }
    
    // 2. 冻结库存（不实际扣减）
    db.FreezeInventory(goodsID, amount)
    
    // 3. 记录 Try 日志
    db.InsertTCCLog(orderID, "TRY", amount)
    
    return nil
}

// Confirm 阶段：确认扣减
func ConfirmDeductInventory(orderID string) error {
    // 1. 查询 Try 日志
    log := db.GetTCCLog(orderID)
    if log == nil {
        return errors.New("Try 日志不存在")
    }
    
    // 2. 实际扣减库存
    db.DeductInventory(goodsID, log.Amount)
    
    // 3. 解冻库存
    db.UnfreezeInventory(goodsID, log.Amount)
    
    // 4. 更新日志状态
    db.UpdateTCCLog(orderID, "CONFIRM")
    
    return nil
}

// Cancel 阶段：取消冻结
func CancelDeductInventory(orderID string) error {
    // 1. 查询 Try 日志
    log := db.GetTCCLog(orderID)
    if log == nil {
        return nil // 幂等处理
    }
    
    // 2. 解冻库存
    db.UnfreezeInventory(goodsID, log.Amount)
    
    // 3. 更新日志状态
    db.UpdateTCCLog(orderID, "CANCEL")
    
    return nil
}
```

**关键点**：
- ✅ **业务层控制**：自己实现 Try/Confirm/Cancel
- ✅ **幂等保证**：Confirm/Cancel 可重复执行
- ✅ **空回滚处理**：Cancel 时 Try 未执行，直接返回成功

### 2.2 非核心链路：本地消息表

**核心思路**：
```
1. 业务操作 + 写入消息表（同一事务）
2. 定时任务扫描消息表，发送到 MQ
3. 消费者处理消息，保证最终一致性
```

**实现示例**：
```go
// 1. 业务操作 + 写入消息表
func CreateOrder(order *Order) error {
    tx := db.Begin()
    
    // 创建订单
    err := tx.Create(order).Error
    if err != nil {
        tx.Rollback()
        return err
    }
    
    // 写入消息表
    msg := &Message{
        BizType: "ORDER_CREATED",
        BizID:   order.ID,
        Status:  "PENDING",
    }
    err = tx.Create(msg).Error
    if err != nil {
        tx.Rollback()
        return err
    }
    
    tx.Commit()
    return nil
}

// 2. 定时任务发送消息
func SendPendingMessages() {
    messages := db.QueryMessages("PENDING")
    for _, msg := range messages {
        err := mq.Publish(msg.BizType, msg.BizID)
        if err == nil {
            db.UpdateMessageStatus(msg.ID, "SENT")
        }
    }
}

// 3. 消费者处理消息
func HandleOrderCreated(bizID string) error {
    // 发送通知
    sendNotification(bizID)
    
    // 发放积分
    grantPoints(bizID)
    
    return nil
}
```

## 三、异常场景处理

### 3.1 悬挂事务

**问题**：
```
Confirm 请求超时，实际已执行
协调器认为失败，触发 Cancel
Cancel 执行时，Confirm 还没完成
```

**解决方案**：
```go
func CancelWithProtection(orderID string) error {
    // 1. 检查事务状态
    status := db.GetTransactionStatus(orderID)
    
    if status == "CONFIRMED" {
        // 已经 Confirm，不能 Cancel
        return nil
    }
    
    if status == "CONFIRMING" {
        // 正在 Confirm，等待完成
        time.Sleep(1 * time.Second)
        return CancelWithProtection(orderID)
    }
    
    // 2. 执行 Cancel
    return doCancel(orderID)
}
```

### 3.2 幂等失效

**问题**：
```
Confirm 被重复调用
库存被扣减两次
```

**解决方案**：
```go
func ConfirmWithIdempotent(orderID string) error {
    // 1. 查询 Confirm 记录
    record := db.GetConfirmRecord(orderID)
    if record != nil {
        return nil // 已执行，幂等返回
    }
    
    // 2. 执行 Confirm
    err := doConfirm(orderID)
    if err != nil {
        return err
    }
    
    // 3. 记录 Confirm 记录
    db.InsertConfirmRecord(orderID)
    
    return nil
}
```

### 3.3 对账补偿

```go
// T+1 对账
func DailyReconciliation() {
    // 1. 查询所有订单
    orders := db.QueryOrders("created_at >= ?", yesterday)
    
    for _, order := range orders {
        // 2. 检查库存是否扣减
        inventoryLog := db.GetInventoryLog(order.ID)
        if inventoryLog == nil {
            // 库存未扣减，触发补偿
            compensateInventory(order)
        }
        
        // 3. 检查余额是否扣减
        balanceLog := db.GetBalanceLog(order.ID)
        if balanceLog == nil {
            // 余额未扣减，触发补偿
            compensateBalance(order)
        }
    }
}

// 补偿流程
func compensateInventory(order *Order) {
    // 1. 告警
    alert("订单 %s 库存未扣减", order.ID)
    
    // 2. 人工介入
    // 或自动补偿
    tryDeductInventory(order)
}
```

四、技术深入探讨

### Q1: Seata AT 模式有什么隐患？

**方案参考**：
> Seata AT 模式是自动补偿，看起来简单，但有三大隐患：
> 
> 1. **协调器宕机**：所有进行中的事务都阻塞或数据不一致
> 2. **性能问题**：全局锁导致高并发场景 TPS 急剧下降
> 3. **外部系统**：微信支付、顺丰物流无法参与全局事务
> 
> 核心链路推荐用 TCC，业务层自己控制提交与回滚逻辑，不依赖全自动 AT 模式。

### Q2: 跨 6 个微服务、8 个数据库的长链路事务怎么设计？

**方案参考**：
> 长链路事务是性能杀手，设计原则：
> 
> 1. **拆分事务**：长链路拆成多个短事务，减少资源锁定时间
> 2. **异步化**：能异步就不强同步，用可靠消息实现最终一致性
> 3. **业务分级**：核心链路强一致（TCC），非核心链路最终一致（消息表）
> 
> 能用本地事务解决就不跨服务，能异步接口就不做强同步。

## 五、总结

### 🎯 一句话总结

> **分布式事务 = 业务分级（TCC/消息表） + 异常兜底（对账补偿） + 柔性设计（最终一致性）**

### 🧠 核心记忆点

1. **加注解不等于搞定**：框架宕机、网络异常都会打破原子性
2. **业务分级**：核心链路 TCC，非核心链路消息表
3. **异常处理**：悬挂事务、幂等失效、对账补偿
4. **柔性设计**：能本地就不跨服务，能异步就不强同步
