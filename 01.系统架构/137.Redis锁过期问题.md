**第二层：生产常见坑与核心解决方案**
```
坑点 1：锁过期续期问题
- 业务执行时间超过锁过期时间 → 锁提前释放
- 解决方案：Redisson 看门狗机制
  - 加锁成功后启动定时任务
  - 每隔三分之一过期时间检查锁是否还被当前线程持有
  - 若持有则自动续期
- 注意：异步任务中使用时，主线程执行完看门狗会停止续期

坑点 2：可重入性问题
- 同一个线程多次加锁 → 死锁
- 解决方案：锁的 value 存储线程标识 + 重入次数
  - 加锁时若线程已持有锁，则重入次数加一
  - 释放时重入次数减一，次数为零时真正删除锁

坑点 3：主从架构锁丢失问题
- 主节点加锁成功后未同步到从节点就宕机 → 锁失效
- 解决方案：红锁算法（Redlock）
  - 向多个独立 Redis 节点加锁
  - 超过半数加锁成功才算成功
- 注意：红锁会牺牲性能，且无法解决节点时钟不一致问题

- 可重入：同一个人可以多次进出
- 红锁：多个商场同时确认你在使用试衣间
```

## 一、为什么 Redis 分布式锁这么难？

### 🔍 核心问题（30 秒版）

**生活化比喻**：
```
Redis 分布式锁的三大难题：
1. 原子性问题：setnx 和 expire 不是原子操作
2. 锁过期问题：业务没执行完锁就过期了
3. 主从一致性问题：主节点宕机，锁丢失

就像商场试衣间：
- 门锁和计时器不是联动的（原子性）
- 你在里面试衣服，时间到了门锁自动开了（锁过期）
- 商场停电，门锁记录丢失（主从一致性）
```

### 1.1 三大核心难题

| 难题 | 具体表现 | 线上后果 | 生活化比喻 |
|------|---------|---------|-----------|
| **原子性问题** | setnx 和 expire 分两次执行 | 加锁成功但没设置过期时间 → 死锁 | 门锁和计时器不联动 |
| **锁过期问题** | 业务执行时间超过锁过期时间 | 锁提前释放 → 并发问题 | 试衣时间到了，门锁自动开 |
| **主从一致性** | 主节点加锁后未同步就宕机 | 锁丢失 → 并发问题 | 商场停电，门锁记录丢失 |

## 二、第一层：分布式锁核心原理与正确用法

### 2.1 核心三要素

**互斥性**：
- 同一时间只能有一个线程持有锁
- 防止并发访问共享资源

**防死锁**：
- 必须设置过期时间
- 防止线程异常退出导致锁永不释放

**正确释放**：
- 只能释放自己持有的锁
- 防止误删其他线程的锁

### 2.2 基础错误用法

```java
// ❌ 错误示例 1：setnx 和 expire 分两次执行
public boolean tryLock(String key, long expireTime) {
    Boolean result = redisTemplate.opsForValue().setIfAbsent(key, "1");
    if (result) {
        redisTemplate.expire(key, expireTime, TimeUnit.SECONDS);
        return true;
    }
    return false;
}
// 问题：setnx 成功后，expire 执行前服务宕机 → 死锁

// ❌ 错误示例 2：不校验锁持有者直接 delete
public void unlock(String key) {
    redisTemplate.delete(key);
}
// 问题：线程 A 的锁过期后被自动释放，线程 B 抢到锁，
// 线程 A 执行完业务去 delete 会把线程 B 的锁删掉

// ❌ 错误示例 3：不设置过期时间
public boolean tryLock(String key) {
    return redisTemplate.opsForValue().setIfAbsent(key, "1");
}
// 问题：线程异常退出，锁永不释放 → 死锁
```

### 2.3 正确基础实现

```java
// ✅ 正确示例 1：使用 set nx ex 单命令
public boolean tryLock(String key, long expireTime) {
    String result = redisTemplate.execute(
        new DefaultRedisScript<>("SET key value NX EX seconds", String.class),
        Arrays.asList(key, "1", String.valueOf(expireTime))
    );
    return "OK".equals(result);
}

// ✅ 正确示例 2：释放锁时用 Lua 脚本校验
public void unlock(String key, String value) {
    String luaScript = 
        "if redis.call('get', KEYS[1]) == ARGV[1] then " +
        "    return redis.call('del', KEYS[1]) " +
        "else " +
        "    return 0 " +
        "end";
    
    redisTemplate.execute(
        new DefaultRedisScript<>(luaScript, Long.class),
        Arrays.asList(key),
        value
    );
}

// 完整示例
public class RedisLock {
    private StringRedisTemplate redisTemplate;
    private String key;
    private String value; // 线程标识
    
    public boolean tryLock(long expireTime) {
        String result = redisTemplate.execute(
            new DefaultRedisScript<>("SET " + key + " " + value + " NX EX " + expireTime, String.class)
        );
        return "OK".equals(result);
    }
    
    public void unlock() {
        String luaScript = 
            "if redis.call('get', KEYS[1]) == ARGV[1] then " +
            "    return redis.call('del', KEYS[1]) " +
            "else " +
            "    return 0 " +
            "end";
        
        redisTemplate.execute(
            new DefaultRedisScript<>(luaScript, Long.class),
            Arrays.asList(key),
            value
        );
    }
}
```

## 三、第二层：生产常见坑与核心解决方案

### 3.1 锁过期续期问题

**坑点**：
```java
// ❌ 问题场景
public void processOrder() {
    if (tryLock("order:123", 10)) { // 锁过期时间 10 秒
        try {
            // 业务逻辑执行了 15 秒
            // 第 10 秒时锁已过期，其他线程可以抢到锁
            // 导致并发问题
        } finally {
            unlock("order:123");
        }
    }
}
```

**解决方案：Redisson 看门狗机制**

```java
// ✅ 正确示例
public void processOrder() {
    RLock lock = redisson.getLock("order:123");
    
    try {
        // 加锁，不指定过期时间，看门狗会自动续期
        lock.lock();
        
        // 业务逻辑
        processBusinessLogic();
        
    } finally {
        lock.unlock();
    }
}
```

**看门狗机制原理**：
```
1. 加锁成功后启动定时任务
2. 每隔 lockWatchdogTimeout / 3 检查一次（默认 30 秒 / 3 = 10 秒）
3. 检查锁是否还被当前线程持有
4. 若持有则自动续期（重置过期时间为 30 秒）
```

**生活化比喻**：
```
就像试衣间管理：
- 你进入试衣间后，服务员给你 30 分钟
- 每 10 分钟服务员会问你：还在试吗？
- 如果你在，服务员帮你延长 30 分钟
- 你离开后，服务员停止询问
```

**注意**：
```java
// ❌ 异步任务中使用看门狗的坑
public void processOrder() {
    RLock lock = redisson.getLock("order:123");
    
    lock.lock();
    
    // 异步任务
    CompletableFuture.runAsync(() -> {
        // 主线程执行完，看门狗停止续期
        // 异步任务还在执行，锁已过期 → 并发问题
        processBusinessLogic();
    });
}
```

### 3.2 可重入性问题

**坑点**：
```java
// ❌ 问题场景
public void method1() {
    RLock lock = redisson.getLock("lock:123");
    lock.lock();
    
    try {
        method2(); // 同一个线程再次加锁 → 死锁
    } finally {
        lock.unlock();
    }
}

public void method2() {
    RLock lock = redisson.getLock("lock:123");
    lock.lock(); // 同一个线程再次加锁，会一直等待
    
    try {
        // 业务逻辑
    } finally {
        lock.unlock();
    }
}
```

**解决方案：Redisson 可重入锁**

```java
// ✅ 正确示例
public void method1() {
    RLock lock = redisson.getLock("lock:123");
    lock.lock(); // Redisson 自动支持可重入
    
    try {
        method2();
    } finally {
        lock.unlock();
    }
}

public void method2() {
    RLock lock = redisson.getLock("lock:123");
    lock.lock(); // 同一个线程可以多次加锁
    
    try {
        // 业务逻辑
    } finally {
        lock.unlock(); // 重入次数减一
    }
}
```

**实现原理**：
```
锁的 value 存储：线程标识 + 重入次数
- 加锁时若线程已持有锁，则重入次数加一
- 释放时重入次数减一
- 次数为零时真正删除锁
```

### 3.3 主从架构锁丢失问题

**坑点**：
```
主从架构：
1. 线程 A 在主节点加锁成功
2. 主节点还未同步到从节点
3. 主节点宕机
4. 从节点升级为主节点
5. 新主节点没有锁信息 → 锁丢失
6. 线程 B 可以抢到锁 → 并发问题
```

**解决方案：红锁算法（Redlock）**

```java
// ✅ 正确示例
public class RedLock {
    private RedissonRedisClusterClient[] clients;
    
    public boolean tryLock(String key, long expireTime) {
        int successCount = 0;
        
        // 向多个独立 Redis 节点加锁
        for (RedissonRedisClusterClient client : clients) {
            if (client.tryLock(key, expireTime)) {
                successCount++;
            }
        }
        
        // 超过半数加锁成功才算成功
        return successCount >= clients.length / 2 + 1;
    }
    
    public void unlock(String key) {
        // 向所有节点释放锁
        for (RedissonRedisClusterClient client : clients) {
            client.unlock(key);
        }
    }
}
```

**生活化比喻**：
```
就像多个商场同时确认试衣间：
- 你进入试衣间后，需要 3 个商场中的 2 个确认
- 只有超过半数确认，才算真正进入
- 避免单个商场系统故障导致的问题
```

**注意**：
- 红锁会牺牲性能（需要向多个节点加锁）
- 无法解决节点时钟不一致问题
- 适用于对一致性要求极高的场景

```java
public class SegmentedLock {
    private RLock[] locks = new RLock[16];
    
    public SegmentedLock(RedissonClient redisson) {
        for (int i = 0; i < 16; i++) {
```

>
> **第二层：生产常见坑与核心解决方案**
> 锁过期续期：Redisson 看门狗机制，每隔三分之一过期时间自动续期。可重入性：锁的 value 存储线程标识 + 重入次数。主从锁丢失：红锁算法，向多个独立 Redis 节点加锁，超过半数成功才算成功。
>
> **第三层：高并发、高可用场景的生产落地细节**
> 高并发优化：分段锁思想，读写锁。异常处理：配置锁的最大持有时间，添加分布式锁监控。极端场景兜底：Redis 集群脑裂时采用过半写入原则，核心业务增加数据库乐观锁作为最终兜底。
>
> 核心是从只会用 setnx 加锁，升级为能设计安全、可靠、高性能的分布式锁方案。"

## 七、总结（一句话带走）

### 🎯 一句话总结

> **Redis 分布式锁 = 原子性（set nx ex + Lua 脚本） + 自动续期（看门狗机制） + 高可用（红锁算法 + 数据库兜底）**

### 🧠 核心记忆点

1. **为什么分布式锁这么难？** 原子性问题、锁过期问题、主从一致性问题。
2. **怎么保证原子性？** set nx ex 单命令 + Lua 脚本释放锁。
3. **怎么解决锁过期？** Redisson 看门狗机制，自动续期。
4. **怎么解决主从锁丢失？** 红锁算法，超过半数节点加锁成功。
5. **怎么优化高并发？** 分段锁、读写锁、数据库乐观锁兜底。
