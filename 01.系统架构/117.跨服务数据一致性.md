# 跨服务数据一致性

> **场景定位**：微服务架构场景  
> **核心设计要点**：分布式事务、TCC、Seata、数据对账、服务边界设计

---

## 🎯 一句话定位

```
你以为依靠本地事务就能管控所有业务流程，
却没想到微服务拆分后事务彻底失效——
跨服务调用频繁出现数据错乱。
```

**生活化比喻**：
就像接力赛——你跑完第一棒（订单服务），把棒交给第二棒（库存服务），再交给第三棒（支付服务）。如果第三棒摔倒了（支付失败），第一棒和第二棒要不要退回来？本地事务管不了"别人"，这就是跨服务一致性的核心难题。

---

## 💎 核心观点

**三层防御**：
1. **业务分级**：强一致（支付/转账）vs 最终一致（浏览/推送）
2. **事务方案**：TCC（Try-Confirm-Cancel）、Seata AT、定时数据对账
3. **架构优化**：合理拆分服务边界、缩减事务参与服务数、故障降级

---

## 🚀 一句话精华

> **跨服务一致性 = 业务分级（强/最终一致） + 事务方案（TCC/Seata/对账） + 架构优化（服务边界+事务降级）**

---

## 一、核心场景

```
下单流程：
  订单服务（创建订单）→ 库存服务（扣库存）→ 支付服务（扣款）

问题：
  订单创建成功 ✅
  库存扣减成功 ✅
  支付服务异常失败 ❌
  
  结果：库存已减，订单未完成支付 → 脏数据
```

---

## 二、三层防御详解

### 2.1 第一层：业务分级

| 场景 | 一致性要求 | 方案 |
|------|-----------|------|
| 支付/转账/资金 | 强一致 | TCC / Seata AT |
| 浏览/推送/日志 | 最终一致 | 异步化 + 对账 |

### 2.2 第二层：事务方案

**TCC 模式**：
```
Try：预留资源（冻结库存）
Confirm：确认执行（真正扣减）
Cancel：取消释放（解冻）

三阶段完成业务回滚
```

**Seata AT 模式**：
```
基于数据源代理
自动生成回滚日志
低成本适配大多数场景
```

**定时数据对账**：
```
定时任务比对各服务数据差异
自动修复异常脏数据
发现不一致立即告警
```

### 2.3 第三层：架构优化

```
合理拆分服务边界：
  → 减少跨服务高频联动调用
  
简化核心业务流程：
  → 缩减事务参与服务数量
  
故障降级：
  → 暂停复杂跨服务流程
  → 优先保障单一服务业务正常
```

---

## 三、技术方案

> "跨服务一致性我分三层：核心场景（支付/转账）用 TCC 强一致，非核心用最终一致。TCC 通过 Try-Confirm-Cancel 三阶段回滚，Seata AT 自动生成回滚日志低成本适配。定时数据对账自动修复差异。架构上合理拆分服务边界，减少跨服务调用，故障期间降级复杂流程保核心。"
