# 线程池耗尽应急

> **场景定位**：并发编程技术场景  
> **核心设计要点**：故障分级、根因定位、参数调优、任务隔离

---

## 🎯 一句话定位

**线程池耗尽解决什么问题？**
```
所有接口响应缓慢甚至无响应
CPU使用率不高但请求全部超时
线程池被占满，服务假死
```

**生活化比喻**：
就像餐厅服务员：
- 所有服务员都在忙（线程耗尽）
- 新客人没人服务（请求超时）
- 餐厅看起来不忙但没人理你（CPU不高但超时）

## 💎 核心观点（5 分钟速览版）

### 核心观点（5 个关键点）

**1. 不是线程数不够**
```
❌ 误区：加大线程数就行
✅ 真相：线程堵塞、死锁、泄露
任务堆积都会引发灾难
```

**2. 故障分级**
```
核心链路：第一时间限流止损
非核心链路：暂停任务，滚动重启
```

**3. 标准排查流程**
```
线程dump
线程池监控
应用日志
链路追踪
```

**4. 参数调优**
```
CPU密集型：核心数+1
IO密集型：核心数*2
合理队列长度和拒绝策略
```

**5. 任务隔离**
```
多业务场景线程池隔离
单业务故障不拖垮整个服务
异步化事件驱动
```

## 🚀 一句话精华

> **线程池耗尽 = 故障分级（核心限流/非核心暂停） + 根因定位（dump/监控/日志） + 参数调优（CPU/IO密集型） + 任务隔离（独立线程池/异步化）**

## 一、故障分级

### 1.1 核心链路应急

```go
// 核心业务：下单、支付、登录
func EmergencyResponse() {
    // 1. 临时限流
    enableRateLimit()
    
    // 2. 非核心请求拒绝
    rejectNonCoreRequests()
    
    // 3. 滚动重启故障节点
    rollingRestart()
    
    // 4. 隔离问题线程池
    isolateProblemPool()
}
```

### 1.2 非核心链路

```go
// 非核心业务：统计、定时任务、数据同步
func HandleNonCore() {
    // 直接暂停任务执行
    pauseNonCoreTasks()
    
    // 优先保证主业务正常运行
    keepCoreBusinessRunning()
    
    // 低风险再优化整改
    optimizeLater()
}
```

## 二、标准排查流程

### 2.1 线程dump分析

```bash
# 获取线程dump
jstack <pid> > thread_dump.txt

# 分析线程状态
cat thread_dump.txt | grep -A 10 "BLOCKED"
cat thread_dump.txt | grep -A 10 "WAITING"

# 定位死锁
jstack <pid> | grep -A 20 "Found one Java-level deadlock"
```

### 2.2 线程池监控

```go
// 监控线程池指标
func MonitorThreadPool() {
    ticker := time.NewTicker(1 * time.Minute)
    for range ticker.C {
        // 1. 活跃线程数
        activeCount := pool.GetActiveCount()
        
        // 2. 队列长度
        queueSize := pool.GetQueueSize()
        
        // 3. 任务执行时间
        avgExecTime := pool.GetAvgExecutionTime()
        
        // 4. 拒绝次数
        rejectCount := pool.GetRejectCount()
        
        // 告警
        if activeCount > pool.GetMaxPoolSize()*0.8 {
            alert("活跃线程数过多: %d", activeCount)
        }
        
        if queueSize > 1000 {
            alert("队列堆积过多: %d", queueSize)
        }
    }
}
```

### 2.3 链路追踪

```go
// 链路追踪定位慢任务
func TraceSlowTask() {
    // 1. 开启链路追踪
    span := tracer.StartSpan("task_execution")
    defer span.Finish()
    
    // 2. 记录关键节点
    span.SetTag("task_type", "order_process")
    span.SetTag("start_time", time.Now())
    
    // 3. 执行业务
    err := doBusiness()
    
    // 4. 记录结果
    span.SetTag("error", err)
    span.SetTag("end_time", time.Now())
}
```

## 三、参数调优

### 3.1 CPU密集型任务

```go
// CPU密集型：核心数+1
var cpuPool = &ThreadPool{
    CorePoolSize: runtime.NumCPU() + 1,
    MaxPoolSize:  runtime.NumCPU() + 1,
    QueueCapacity: 100,
}
```

### 3.2 IO密集型任务

```go
// IO密集型：核心数*2
var ioPool = &ThreadPool{
    CorePoolSize: runtime.NumCPU() * 2,
    MaxPoolSize:  runtime.NumCPU() * 2,
    QueueCapacity: 1000,
}
```

### 3.3 拒绝策略

```go
// 合理拒绝策略
type RejectPolicy struct {
    // 1. CallerRunsPolicy：调用者线程执行
    // 2. AbortPolicy：直接拒绝（默认）
    // 3. DiscardPolicy：静默丢弃
    // 4. DiscardOldestPolicy：丢弃最老任务
    
    Policy: "CallerRunsPolicy",
}
```

## 四、任务隔离

### 4.1 多业务线程池隔离

```go
// 不同业务独立线程池
type ServicePools struct {
    orderPool    *ThreadPool // 订单业务
    paymentPool  *ThreadPool // 支付业务
    statsPool    *ThreadPool // 统计业务
}

// 单业务故障不拖垮整个服务
func (s *ServicePools) ProcessOrder(order *Order) error {
    return s.orderPool.Submit(func() {
        doOrderProcess(order)
    })
}
```

### 4.2 异步化事件驱动

```go
// 同步任务改异步
func ProcessOrder(order *Order) error {
    // 1. 核心流程同步执行
    err := createOrder(order)
    if err != nil {
        return err
    }
    
    // 2. 非核心流程异步执行
    go sendNotification(order)  // 异步发送通知
    go updateStats(order)       // 异步更新统计
    
    return nil
}
```

```
禁止使用 Executors 创建线程池
强制使用 ThreadPoolExecutor 手动配置
统一线程池命名规范
便于问题定位与排查
```

```go

    pool.SetCorePoolSize(coreSize)
    pool.SetMaxPoolSize(maxSize)
    
    // 无需重启服务即可优化性能
}
```

六、技术深入探讨

### Q1: 线程池耗尽怎么应急？

**方案参考**：
> 线程池耗尽应急分两层：
> 
> 1. **核心链路**：第一时间限流止损，非核心请求拒绝，滚动重启故障节点
> 2. **非核心链路**：暂停任务执行，优先保证主业务正常运行
> 
> 核心是先止损后定位。

### Q2: 如何定位线程池问题根因？

**方案参考**：
> 定位根因四步法：
> 
> 1. **线程dump**：jstack获取，分析BLOCKED/WAITING状态
> 2. **线程池监控**：活跃线程数、队列长度、执行时间、拒绝次数
> 3. **应用日志**：查看异常堆栈
> 4. **链路追踪**：定位慢任务
> 
> 核心是先定位再优化，不盲目调参。

## 七、总结

### 🎯 一句话总结

> **线程池耗尽 = 故障分级（核心限流/非核心暂停） + 根因定位（dump/监控/日志） + 参数调优（CPU/IO密集型） + 任务隔离（独立线程池/异步化）**

### 🧠 核心记忆点

1. **故障分级**：核心限流，非核心暂停
2. **根因定位**：dump + 监控 + 日志 + 追踪
3. **参数调优**：CPU密集型 vs IO密集型
4. **任务隔离**：独立线程池 + 异步化
