# 索引失效排查

> **场景定位**：MySQL 性能优化技术场景  
> **核心设计要点**：索引原理、执行计划、成本模型、性能天花板

---

## 🎯 一句话定位

**索引失效排查解决什么问题？**
```
明明加了索引，SQL 还是很慢
执行计划显示走了索引，但性能就是上不去
```

**生活化比喻**：
就像查字典：
- 索引 = 字典的拼音目录
- 走索引 = 先查目录，再翻到对应页
- 但如果要查 1000 个汉字，查目录反而更慢（回表代价大）

---

## 💎 核心观点（5 分钟速览版）

### 核心观点（5 个关键点）

**1. 走索引 ≠ 性能高**
```
❌ 误区：有索引就一定快
✅ 真相：走索引只是第一步
核心看扫描行数和回表代价
```

**2. 索引失效的深层原因**
```
范围查询 → 回表代价大 → 优化器选择全表扫描
不是索引失效，是成本模型判断全表更优
```

**3. 单表性能天花板**
```
主键索引：树高 3 层，3 次 IO
数据量破亿 → 树高 4 层 → IO 翻倍
千万级是行业经验值
```

**4. 优化器的成本模型**
```
CBO（基于成本的优化器）：
计算每个执行计划的 IO 成本 + CPU 成本
选择总成本最低的方案
```

**5. 慢查询的完整排查**
```
执行计划 → 扫描行数 → 回表代价
服务器资源 → CPU/内存/IO
事务锁机制 → 锁等待
```

## 一、索引失效的真相

### ❌ 常见误区

```
提问者：加了索引还慢？肯定是索引失效了！
比如：LIKE '%xxx'、函数运算、隐式类型转换...

场景提问：执行计划显示走了索引，为什么还慢？
提问者：...
```

**真相**：
```
不是索引失效
是优化器认为全表扫描成本更低
```

### ✅ 索引成本模型

**二级索引的回表代价**：
```
二级索引只存：索引列 + 主键
查询完整数据需要回表（随机 IO）

范围查询命中 10000 行：
- 走索引：10000 次随机 IO（回表）
- 全表扫描：顺序 IO（快得多）

优化器计算：全表扫描成本 < 走索引成本
→ 选择全表扫描
```

**成本计算示例**：
```sql
-- 查询 10000 条订单
SELECT * FROM orders WHERE created_at > '2024-01-01';

-- 执行计划 1：走索引
成本 = 10000 次随机 IO（回表）
     = 10000 × 10ms
     = 100 秒

-- 执行计划 2：全表扫描
成本 = 顺序 IO
     = 1000 次顺序 IO
     = 10 秒

优化器选择：全表扫描
```

## 二、覆盖索引优化

### 2.1 什么是覆盖索引

```
覆盖索引：查询的列都在索引中，不需要回表

普通索引：
索引列 → 主键 → 回表查完整数据

覆盖索引：
索引列 → 直接返回（无需回表）
```

### 2.2 优化示例

```sql
-- ❌ 需要回表
SELECT * FROM orders WHERE user_id = 1;
-- 索引只有 user_id，需要回表查其他列

-- ✅ 覆盖索引
SELECT user_id, order_no FROM orders WHERE user_id = 1;
-- 查询的列都在索引中，无需回表

-- 创建联合索引
ALTER TABLE orders ADD INDEX idx_user_order (user_id, order_no);
```

**效果**：
```
回表 10000 次 → 覆盖索引 0 次回表
性能提升 10 倍以上
```

## 三、单表性能天花板

### 3.1 索引树高度

```
B+ 树结构：
- 叶子节点：存储数据
- 非叶子节点：存储索引

树高度：
- 百万级：2-3 层
- 千万级：3 层
- 亿级：4 层
```

**性能影响**：
```
千万级数据：
主键查询 = 3 次 IO（树高 3 层）

亿级数据：
主键查询 = 4 次 IO（树高 4 层）
性能下降 33%
```

### 3.2 二级索引的性能衰减

```
单表数据量越大：
- 索引区分度越低
- 相同查询条件的行数越多
- 回表代价呈指数级上升

这就是为什么要分库分表
```

## 四、慢查询完整排查

### 4.1 执行计划分析

```sql
-- 查看执行计划
EXPLAIN SELECT * FROM orders WHERE user_id = 1;

-- 关键字段：
type：访问类型（const/ref/range/index/ALL）
rows：预计扫描行数
Extra：是否Using index（覆盖索引）、Using filesort（文件排序）
```

**执行类型对比**：
```
const：主键等值查询，最快
ref：索引等值查询
range：索引范围查询
index：全索引扫描
ALL：全表扫描，最慢
```

### 4.2 服务器资源排查

```bash
# CPU 使用率
top

# 内存使用率
free -h

# 磁盘 IO
iostat -x 1

# MySQL 连接数
SHOW PROCESSLIST;
```

**常见瓶颈**：
```
CPU 高：复杂计算、大量排序
内存低：缓存命中率低
IO 高：大量磁盘读写
连接数满：线程排队
```

### 4.3 事务锁排查

```sql
-- 查看锁等待
SELECT * FROM information_schema.innodb_lock_waits;

-- 查看当前锁
SELECT * FROM information_schema.innodb_locks;

-- 查看长事务
SELECT * FROM information_schema.innodb_trx 
WHERE trx_started < NOW() - INTERVAL 10 SECOND;
```

## 五、优化方案

### 5.1 索引优化

```sql
-- ❌ 低效索引
INDEX idx_status (status)
-- 区分度低，大量回表

-- ✅ 高效索引
INDEX idx_user_status (user_id, status)
-- 联合索引，区分度高
```

### 5.2 查询优化

```sql
-- ❌ 深分页
SELECT * FROM orders LIMIT 100000, 10;
-- 扫描 100010 行，返回 10 行

-- ✅ 游标分页
SELECT * FROM orders 
WHERE id > 100000 
ORDER BY id 
LIMIT 10;
-- 只扫描 10 行
```

### 5.3 架构优化

```
读写分离：查询压力分摊到从库
缓存加速：热点数据放 Redis
分库分表：突破单表性能天花板
```

六、技术深入探讨

### Q1: 为什么加了索引还慢？

**方案参考**：
> 走索引不等于快，核心看两个因素：
> 
> 1. **扫描行数**：范围查询命中大量行，回表代价大
> 2. **回表代价**：二级索引需要回表查完整数据，随机 IO 成本高
> 
> 优化器用 CBO（基于成本的优化器）计算每个执行计划的成本，选择总成本最低的方案。如果全表扫描成本更低，就会放弃索引。
> 
> 解决方案：覆盖索引（避免回表）、缩小范围查询、分库分表。

### Q2: 单表数据量为什么不能超过千万？

**方案参考**：
> 千万级是行业经验值，根因是索引性能天花板：
> 
> 1. **树高度增加**：数据量破亿，B+ 树从 3 层涨到 4 层，单次查询 IO 翻倍
> 2. **区分度降低**：单表越大，索引区分度越低，扫描行数越多
> 3. **回表代价**：二级索引回表代价呈指数级上升
> 
> 不是 MySQL 存不下更多数据，而是索引性能到了天花板。
