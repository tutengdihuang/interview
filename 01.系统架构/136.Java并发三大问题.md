## 💎 核心观点（5 分钟速览版）

> **快速概览**

### 核心观点（三大问题解决方案）

**第一层：线程安全问题**
```
三大核心场景：
1. 多线程同时操作共享变量，未作同步控制 → 数据覆盖
2. 复合操作（自增、自减）非原子操作 → 数据偏差
3. 可见性问题 → 线程之间缓存数据不一致

解决方案：
- 悲观锁：synchronized、ReentrantLock（保证串行）
- 原子类：AtomicInteger（基于 CAS，无锁并发）
- volatile：保证变量可见性，禁止指令重排
- ThreadLocal：线程本地变量，隔离数据

生活化比喻：
就像文件管理：
- 悲观锁：一次只有一个人编辑文件
- 原子类：每个人修改后自动合并
- volatile：修改后立即同步给所有人
- ThreadLocal：每个人都有自己的副本
```

**第二层：线程池问题**
```
两大核心场景：
1. 任务提交量远大于处理能力 → 线程全部占满，触发拒绝策略
2. 任务执行耗时过长 → 线程被长时间占用，新任务堆积

七大核心参数：
1. corePoolSize：核心线程数
2. maximumPoolSize：最大线程数
3. keepAliveTime：非核心线程空闲存活时间
4. unit：时间单位
5. workQueue：任务队列
6. threadFactory：线程工厂
7. handler：拒绝策略

拒绝策略选择：
- AbortPolicy：抛出异常（默认）
- CallerRunsPolicy：调用者线程执行
- DiscardPolicy：丢弃任务
- DiscardOldestPolicy：丢弃最老任务

生活化比喻：
就像公司招聘：
- 核心员工：正式员工，长期雇佣
- 最大线程数：正式 + 临时工
- 任务队列：等待处理的任务列表
- 拒绝策略：任务太多时的处理方式
```

**第三层：线程死锁问题**
```
典型触发场景：
1. 多个线程互相持有对方需要的锁
2. 嵌套加锁，加锁顺序混乱
3. 锁持有时间过长

解决方案：
- 统一全局加锁顺序（打破循环等待）
- 控制锁持有时间（拆分长事务）
- 使用 tryLock 设置超时时间
- 线上通过 jstack 抓取线程快照定位

生活化比喻：
就像部门审批：
- 统一加锁顺序：所有项目都按 A→B→C 顺序审批
- 控制锁持有时间：审批不能超过 1 天
- tryLock 超时：等待超过 1 小时就放弃
- jstack 定位：查看哪个部门卡住了
```

## 二、第一层：线程安全问题

### 2.1 三大核心场景

**场景 1：多线程同时操作共享变量**
```java
// ❌ 错误示例
class Counter {
    private int count = 0;
    
    public void increment() {
        count++; // 非原子操作
    }
}

// 多线程调用
Counter counter = new Counter();
for (int i = 0; i < 1000; i++) {
    new Thread(() -> counter.increment()).start();
}
// 结果：count 可能不是 1000
```

**场景 2：复合操作非原子**
```java
// ❌ 错误示例
count++; // 实际是三步：读取、+1、写回
```

**场景 3：可见性问题**
```java
// ❌ 错误示例
class VisibilityTest {
    private boolean flag = true;
    
    public void setFlag(boolean flag) {
        this.flag = flag;
    }
    
    public void check() {
        while (flag) {
            // 可能永远读不到最新的 flag 值
        }
    }
}
```

### 2.2 解决方案

**方案 1：悲观锁（synchronized）**
```java
// ✅ 正确示例
class Counter {
    private int count = 0;
    
    public synchronized void increment() {
        count++;
    }
}
```

**方案 2：悲观锁（ReentrantLock）**
```java
class Counter {
    private int count = 0;
    private final Lock lock = new ReentrantLock();
    
    public void increment() {
        lock.lock();
        try {
            count++;
        } finally {
            lock.unlock();
        }
    }
}
```

**方案 3：原子类（AtomicInteger）**
```java
class Counter {
    private AtomicInteger count = new AtomicInteger(0);
    
    public void increment() {
        count.incrementAndGet(); // 基于 CAS，无锁并发
    }
}
```

**方案 4：volatile**
```java
class VisibilityTest {
    private volatile boolean flag = true;
    
    public void setFlag(boolean flag) {
        this.flag = flag;
    }
    
    public void check() {
        while (flag) {
            // ✅ 能立即读到最新的 flag 值
        }
    }
}
```

**方案 5：ThreadLocal**
```java
class ThreadLocalTest {
    private ThreadLocal<Integer> count = ThreadLocal.withInitial(() -> 0);
    
    public void increment() {
        count.set(count.get() + 1);
    }
    
    public int getCount() {
        return count.get();
    }
}
```

### 2.3 对比表格

| 方案 | 适用场景 | 优点 | 缺点 | 生活化比喻 |
|------|---------|------|------|-----------|
| **synchronized** | 简单同步 | 自动释放锁 | 性能较低 | 一次只有一个人编辑文件 |
| **ReentrantLock** | 复杂同步 | 可中断、可超时 | 需手动释放 | 需要手动解锁 |
| **AtomicInteger** | 数值运算 | 无锁并发、性能高 | 只支持数值 | 每个人修改后自动合并 |
| **volatile** | 可见性 | 轻量级 | 不保证原子性 | 修改后立即同步给所有人 |
| **ThreadLocal** | 数据隔离 | 线程独立 | 内存占用 | 每个人都有自己的副本 |

## 三、第二层：线程池问题

### 3.1 七大核心参数

```java
public ThreadPoolExecutor(
    int corePoolSize,      // 核心线程数
    int maximumPoolSize,   // 最大线程数
    long keepAliveTime,    // 非核心线程空闲存活时间
    TimeUnit unit,         // 时间单位
    BlockingQueue<Runnable> workQueue,  // 任务队列
    ThreadFactory threadFactory,        // 线程工厂
    RejectedExecutionHandler handler    // 拒绝策略
)
```

**参数详解**：

| 参数 | 含义 | 配置建议 | 生活化比喻 |
|------|------|---------|-----------|
| **corePoolSize** | 核心线程数 | CPU 核心数 * 2 | 正式员工数量 |
| **maximumPoolSize** | 最大线程数 | 根据业务峰值 | 正式 + 临时工 |
| **keepAliveTime** | 非核心线程存活时间 | 60 秒 | 临时工空闲多久后解雇 |
| **unit** | 时间单位 | TimeUnit.SECONDS | 时间单位 |
| **workQueue** | 任务队列 | LinkedBlockingQueue | 等待处理的任务列表 |
| **threadFactory** | 线程工厂 | 自定义线程名称 | 招聘渠道 |
| **handler** | 拒绝策略 | CallerRunsPolicy | 任务太多时的处理方式 |

### 3.2 拒绝策略选择

| 策略 | 行为 | 适用场景 | 生活化比喻 |
|------|------|---------|-----------|
| **AbortPolicy** | 抛出异常（默认） | 不允许任务丢失 | 任务太多直接拒绝 |
| **CallerRunsPolicy** | 调用者线程执行 | 允许延迟，不允许丢失 | 经理自己处理 |
| **DiscardPolicy** | 丢弃任务 | 允许任务丢失 | 直接丢弃 |
| **DiscardOldestPolicy** | 丢弃最老任务 | 新任务优先 | 丢弃最早的任务 |

### 3.3 代码示例

```java
// ✅ 正确创建线程池
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    10,  // corePoolSize
    20,  // maximumPoolSize
    60,  // keepAliveTime
    TimeUnit.SECONDS,
    new LinkedBlockingQueue<>(1000),  // workQueue
    new ThreadFactory() {
        private final AtomicInteger threadNumber = new AtomicInteger(1);
        
        @Override
        public Thread newThread(Runnable r) {
            Thread t = new Thread(r);
            t.setName("order-thread-" + threadNumber.getAndIncrement());
            return t;
        }
    },
    new ThreadPoolExecutor.CallerRunsPolicy()  // handler
);

// 提交任务
executor.execute(() -> {
    System.out.println("处理订单");
});
```

### 3.4 线程池耗尽优化

**优化手段**：

| 手段 | 说明 | 生活化比喻 |
|------|------|-----------|
| **调大参数** | 增加核心线程数、最大线程数 | 招聘更多员工 |
| **优化任务** | 拆分耗时任务 | 任务分解 |
| **异步处理** | 使用 CompletableFuture | 外包 |
| **限流降级** | 控制任务提交速率 | 限制订单量 |
| **监控告警** | 实时监控线程池状态 | 安装监控摄像头 |

## 四、第三层：线程死锁问题

### 4.1 典型触发场景

**场景 1：互相持有对方的锁**
```java
// ❌ 死锁示例
class DeadLock {
    private final Object lock1 = new Object();
    private final Object lock2 = new Object();
    
    public void method1() {
        synchronized (lock1) {
            synchronized (lock2) {
                // 业务逻辑
            }
        }
    }
    
    public void method2() {
        synchronized (lock2) {
            synchronized (lock1) {
                // 业务逻辑
            }
        }
    }
}

// 线程 A 调用 method1，线程 B 调用 method2
// 导致死锁
```

### 4.2 解决方案

**方案 1：统一加锁顺序**
```java
// ✅ 正确示例
class DeadLockFix {
    private final Object lock1 = new Object();
    private final Object lock2 = new Object();
    
    public void method1() {
        synchronized (lock1) {
            synchronized (lock2) {
                // 业务逻辑
            }
        }
    }
    
    public void method2() {
        // ✅ 统一加锁顺序：lock1 → lock2
        synchronized (lock1) {
            synchronized (lock2) {
                // 业务逻辑
            }
        }
    }
}
```

**方案 2：使用 tryLock 设置超时**
```java
class DeadLockFix {
    private final Lock lock1 = new ReentrantLock();
    private final Lock lock2 = new ReentrantLock();
    
    public void method1() {
        if (lock1.tryLock(1, TimeUnit.SECONDS)) {
            try {
                if (lock2.tryLock(1, TimeUnit.SECONDS)) {
                    try {
                        // 业务逻辑
                    } finally {
                        lock2.unlock();
                    }
                }
            } finally {
                lock1.unlock();
            }
        }
    }
}
```

**方案 3：jstack 定位死锁**
```bash
# 抓取线程快照
jstack <pid> > thread_dump.txt

# 查看死锁信息

  waiting to lock monitor 0x00007f8b4c0035b8
  which is held by "thread-0"
"thread-0":
  waiting to lock monitor 0x00007f8b4c005f68
  which is held by "thread-1"
```

五、技术深入探讨

### Q1: synchronized 和 Lock 有什么本质区别？

**答**：
> 本质区别：
>
> 1. **synchronized**：JVM 内置，自动释放锁，不可中断
> 2. **Lock**：API 层面，需手动释放锁，可中断、可超时
>
> 选择建议：
> - 简单同步：用 synchronized
> - 复杂同步（超时、中断）：用 Lock

### Q2: 线程池七大参数每一个代表什么？

**答**：
> 七大参数：
>
> 1. **corePoolSize**：核心线程数（正式员工）
> 2. **maximumPoolSize**：最大线程数（正式 + 临时工）
> 3. **keepAliveTime**：非核心线程存活时间（临时工空闲多久后解雇）
> 4. **unit**：时间单位
> 5. **workQueue**：任务队列（等待处理的任务列表）
> 6. **threadFactory**：线程工厂（招聘渠道）
> 7. **handler**：拒绝策略（任务太多时的处理方式）

### Q3: 死锁的排查步骤和日常规避方案是什么？

**答**：
> 排查步骤：
> 1. 使用 jstack 抓取线程快照
> 2. 查看死锁信息，定位死锁位置
> 3. 分析死锁原因，修复代码
>
> 日常规避：
> 1. 统一全局加锁顺序
> 2. 控制锁持有时间（拆分长事务）
> 3. 使用 tryLock 设置超时时间

## 六、方案总结

**方案总结**：

> "Java 并发三大问题需要**三层解决方案**：
>
> **第一层：线程安全**
> 多线程同时操作共享变量导致数据覆盖、复合操作非原子导致数据偏差、可见性问题导致缓存不一致。解决方案：悲观锁（synchronized、ReentrantLock）、原子类（AtomicInteger）、volatile、ThreadLocal。
>
> **第二层：线程池**
> 任务提交量远大于处理能力或任务执行耗时过长导致线程池耗尽。七大参数：核心线程数、最大线程数、存活时间、时间单位、任务队列、线程工厂、拒绝策略。拒绝策略选择：AbortPolicy（抛出异常）、CallerRunsPolicy（调用者执行）。优化手段：调大参数、拆分任务、异步处理、限流降级。
>
> **第三层：线程死锁**
> 多个线程互相持有对方需要的锁导致死锁。解决方案：统一加锁顺序、控制锁持有时间、使用 tryLock 设置超时。线上通过 jstack 抓取线程快照定位死锁位置。
>
> 核心是从会写几行线程代码，升级为能说清楚每种问题的根源，能给出可落地的解决方案，能提前规避线上并发风险。"
