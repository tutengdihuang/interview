# 数据库连接池耗尽应急

> **场景定位**：数据库架构场景  
> **核心设计要点**：连接泄露、长事务、慢SQL、流量突增、全链路治理

---

## 🎯 一句话定位

**数据库连接池耗尽解决什么问题？**
```
业务高峰期连接池瞬间被打满
所有请求堵塞，获取连接超时
核心接口大面积不可用
```

**生活化比喻**：
就像银行柜台：
- 窗口全部被占用（连接耗尽）
- 新客户排队等待（请求堵塞）
- 有人占着窗口不办事（长事务/慢SQL）

---

## 💎 核心观点（5 分钟速览版）

### 核心观点（5 个关键点）

**1. 四类典型故障**
```
连接泄露：未释放连接
长事务占用：事务执行时间过长
慢SQL阻塞：查询慢，连接归还慢
流量突增：请求量超过连接池容量
```

**2. 止损优先级**
```
先限流、降级
再回收无效连接
最后定位根因
```

**3. 连接池参数不是越大越好**
```
❌ 误区：连接数越多越好
✅ 真相：连接数过多导致数据库性能下降
连接切换开销增大
```

**4. 五大监控指标**
```
活跃连接占比
获取连接平均等待时间
连接平均持有时长
长事务连接占比
连接创建销毁频次
```

**5. 连接池隔离**
```
核心业务独立连接池
读写分离连接池隔离
防止读连接池耗尽影响写库
```

## 一、四类典型故障

### 1.1 连接泄露

```go
// ❌ 连接泄露
func ProcessOrder() error {
    conn := db.GetConnection()
    // 忘记释放连接
    return nil
}

// ✅ 正确释放
func ProcessOrder() error {
    conn := db.GetConnection()
    defer conn.Release() // 确保释放
    return nil
}
```

### 1.2 长事务占用

```go
// ❌ 长事务
func ProcessOrder() error {
    tx := db.Begin()
    
    // 执行 10 秒的业务逻辑
    tx.Exec("UPDATE inventory ...")
    time.Sleep(10 * time.Second) // 模拟耗时
    tx.Exec("UPDATE orders ...")
    
    tx.Commit() // 10 秒后才释放连接
    return nil
}

// ✅ 短事务
func ProcessOrder() error {
    // 事务 1：扣库存
    tx1 := db.Begin()
    tx1.Exec("UPDATE inventory ...")
    tx1.Commit() // 立即释放
    
    // 中间逻辑（不持连接）
    doOtherLogic()
    
    // 事务 2：更新订单
    tx2 := db.Begin()
    tx2.Exec("UPDATE orders ...")
    tx2.Commit() // 立即释放
    
    return nil
}
```

### 1.3 慢SQL阻塞

```go
// ❌ 慢SQL
func GetOrders() error {
    // 全表扫描，执行 5 秒
    return db.Query("SELECT * FROM orders WHERE status = ?")
}

// ✅ 优化SQL
func GetOrders() error {
    // 添加索引，执行 50ms
    return db.Query("SELECT * FROM orders WHERE status = ? AND created_at > ?", 
        status, time.Now().Add(-7*24*time.Hour))
}
```

## 二、止损优先级

```go
// 1. 限流降级
func EmergencyResponse() {
    // 熔断非核心业务
    disableNonCoreAPI()
    
    // 关闭非必要查询
    disableStatsQuery()
    
    // 只保留核心交易
    keepCoreTransaction()
}

// 2. 回收无效连接
func RecoverConnections() {
    // 强制中断长时间空闲连接
    db.ForceCloseIdleConnections(30 * time.Second)
    
    // 中断未提交事务
    db.ForceCloseUncommittedTransactions(60 * time.Second)
}

// 3. 定位根因
func LocateRootCause() {
    // 查看连接池状态
    status := db.GetPoolStatus()
    
    // 查看长事务
    longTx := db.GetLongTransactions()
    
    // 查看慢SQL
    slowSQL := db.GetSlowQueries()
    
    alert("连接池耗尽根因: %v", analyzeRootCause(status, longTx, slowSQL))
}
```

## 三、连接池参数调优

### 3.1 参数配置

```go
type PoolConfig struct {
    MaxOpenConns    int           // 最大连接数
    MaxIdleConns    int           // 最大空闲连接
    ConnMaxLifetime time.Duration // 连接最大生命周期
    ConnMaxIdleTime time.Duration // 连接最大空闲时间
}

// ✅ 推荐配置
var config = PoolConfig{
    MaxOpenConns:    100,        // 根据业务QPS调整
    MaxIdleConns:    50,         // 空闲连接数
    ConnMaxLifetime: 30 * time.Minute, // 避免连接泄露
    ConnMaxIdleTime: 10 * time.Minute, // 及时回收空闲连接
}
```

### 3.2 参数不是越大越好

```
❌ 误区：连接数 500，越大越好
✅ 真相：
- 连接数过多 → 数据库CPU上下文切换开销增大
- 连接数过多 → 内存占用增大
- 连接数过多 → 性能反而下降

推荐公式：
最大连接数 = (核心数 * 2) + 磁盘数
如：8核1磁盘 → 最大连接数 = 17
```

## 四、五大监控指标

```go
// 监控连接池状态
func MonitorPool() {
    ticker := time.NewTicker(1 * time.Minute)
    for range ticker.C {
        stats := db.Stats()
        
        // 1. 活跃连接占比
        activeRatio := float64(stats.InUse) / float64(stats.MaxOpenConnections)
        if activeRatio > 0.8 {
            alert("活跃连接占比 %.2f，超过阈值", activeRatio)
        }
        
        // 2. 获取连接平均等待时间
        waitTime := stats.WaitDuration / time.Duration(stats.WaitCount)
        if waitTime > 100*time.Millisecond {
            alert("获取连接等待时间 %v，超过阈值", waitTime)
        }
        
        // 3. 连接平均持有时长
        avgHoldTime := getAvgHoldTime()
        if avgHoldTime > 5*time.Second {
            alert("连接持有时长 %v，超过阈值", avgHoldTime)
        }
        
        // 4. 长事务连接占比
        longTxRatio := getLongTransactionRatio()
        if longTxRatio > 0.1 {
            alert("长事务连接占比 %.2f，超过阈值", longTxRatio)
        }
        
        // 5. 连接创建销毁频次
        createRate := getCreateRate()
        if createRate > 10 {
            alert("连接创建频次 %d/s，超过阈值", createRate)
        }
    }
}
```

## 五、连接池隔离

### 5.1 核心业务独立连接池

```go
// 核心交易独立连接池
var corePool = NewConnectionPool(PoolConfig{
    MaxOpenConns: 50,
    MaxIdleConns: 20,
})

// 普通查询独立连接池
var queryPool = NewConnectionPool(PoolConfig{
    MaxOpenConns: 100,
    MaxIdleConns: 50,
})

// 核心交易使用独立连接池
func CreateOrder() error {
    conn := corePool.Get()
    defer conn.Release()
    return doCreateOrder(conn)
}
```

### 5.2 读写分离连接池隔离

```go
// 读连接池
var readPool = NewConnectionPool(PoolConfig{
    MaxOpenConns: 200,
})

// 写连接池
var writePool = NewConnectionPool(PoolConfig{
    MaxOpenConns: 50,
})

// 读操作走读连接池
func GetOrder() error {
    conn := readPool.Get()
    defer conn.Release()
    return doQuery(conn)
}

// 写操作走写连接池
func CreateOrder() error {
    conn := writePool.Get()
    defer conn.Release()
    return doCreate(conn)
}
```

六、技术深入探讨

### Q1: 连接池耗尽怎么应急？

**方案参考**：
> 连接池耗尽应急分三步：
> 
> 1. **限流降级**：熔断非核心业务，关闭非必要查询，只保留核心交易
> 2. **回收连接**：强制中断长时间空闲连接、未提交事务
> 3. **定位根因**：查看连接池状态、长事务、慢SQL，分析根因
> 
> 核心是先止损后排查，避免故障扩散。

### Q2: 连接池参数怎么调优？

**方案参考**：
> 连接池参数调优五个指标：
> 
> 1. **活跃连接占比**：超过 80% 告警
> 2. **获取连接等待时间**：超过 100ms 告警
> 3. **连接持有时长**：超过 5 秒告警
> 4. **长事务连接占比**：超过 10% 告警
> 5. **连接创建销毁频次**：超过 10/s 告警
> 
> 连接数不是越大越好，推荐公式：(核心数*2)+磁盘数。
