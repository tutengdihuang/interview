# 微服务链路雪崩防护

> **场景定位**：微服务架构场景  
> **核心设计要点**：熔断降级、资源隔离、异步解耦、舱壁模式

---

## 🎯 一句话定位

**微服务链路雪崩防护解决什么问题？**
```
单个服务故障顺着依赖链扩散
局部故障拖垮整条核心链路
积分服务超时 → 订单服务卡顿 → 交易雪崩
```

**生活化比喻**：
就像多米诺骨牌：
- 一个倒了（积分服务故障）
- 连锁反应（订单服务卡顿）
- 全部倒掉（交易链路雪崩）

---

## 💎 核心观点（5 分钟速览版）

### 核心观点（5 个关键点）

**1. 熔断不是万能的**
```
❌ 误区：配了熔断就完事
✅ 真相：超时设置不合理、降级逻辑过重、资源未隔离
都会让故障持续扩散
```

**2. 业务分级依赖**
```
核心强依赖：支付、库存
→ 极短超时，快速熔断，轻量降级
非核心弱依赖：积分、推送
→ 静默降级，跳过不阻滞
```

**3. 资源隔离**
```
不同依赖独立执行线程
互不抢占
单点故障不扩散
```

**4. 多维度熔断**
```
超时熔断
失败率熔断
异常比例熔断
并发数熔断
```

**5. 异步解耦**
```
非核心依赖走 MQ
不阻滞主业务线程
从调用方式杜绝慢依赖
```

## 🚀 一句话精华

> **链路雪崩防护 = 业务分级（强/弱依赖） + 资源隔离（独立线程池） + 多维熔断（超时/失败率/异常/并发） + 异步解耦（MQ） + 舱壁模式**

## 一、典型事故

### ❌ 链路雪崩

```
下单主链路依赖积分服务
积分服务依赖用户等级服务

问题：
1. 用户等级服务慢响应
2. 积分服务调用大量超时
3. 积分服务熔断触发
4. 但订单服务工作进程被超时等待和降级逻辑占满
5. 正常请求拿不到执行资源
6. 连不需要积分的普通下单也全部失败
7. 交易链路直接雪崩

根因：资源未隔离，故障扩散
```

## 二、业务分级依赖

### 2.1 核心强依赖

```go
// 支付校验：极短超时，快速熔断
func PaymentCheck(order *Order) error {
    // 超时：100ms
    ctx, cancel := context.WithTimeout(context.Background(), 100*time.Millisecond)
    defer cancel()
    
    // 调用支付服务
    err := paymentService.Check(ctx, order)
    if err != nil {
        // 快速熔断，降级返回本地缓存
        return getLocalCache(order.UserID)
    }
    
    return nil
}
```

### 2.2 非核心弱依赖

```go
// 积分发放：静默降级，跳过不阻滞
func GrantPoints(order *Order) {
    // 超时：500ms
    ctx, cancel := context.WithTimeout(context.Background(), 500*time.Millisecond)
    defer cancel()
    
    // 调用积分服务
    err := pointsService.Grant(ctx, order)
    if err != nil {
        // 静默降级，跳过不阻滞主流程
        log.Warn("积分发放失败，已降级: %v", err)
        return // 直接返回，不影响下单
    }
}
```

## 三、资源隔离

```go
// 舱壁模式：每个依赖独立线程池
type ServiceClient struct {
    paymentPool   *WorkerPool // 支付服务线程池
    pointsPool    *WorkerPool // 积分服务线程池
    userLevelPool *WorkerPool // 用户等级服务线程池
}

// 各自独立，互不抢占
func (c *ServiceClient) CallPayment(order *Order) error {
    return c.paymentPool.Submit(func() {
        // 支付服务调用
        // 即使故障，也只耗尽自身线程池
    })
}

func (c *ServiceClient) CallPoints(order *Order) error {
    return c.pointsPool.Submit(func() {
        // 积分服务调用
        // 故障不影响支付服务
    })
}
```

## 四、多维度熔断

```go
// 多维度熔断防护
type CircuitBreaker struct {
    timeoutBreaker    *Breaker // 超时熔断
    failureBreaker    *Breaker // 失败率熔断
    exceptionBreaker  *Breaker // 异常比例熔断
    concurrencyBreaker *Breaker // 并发数熔断
}

func (cb *CircuitBreaker) Execute(fn func() error) error {
    // 第一道防线：超时熔断
    if cb.timeoutBreaker.IsOpen() {
        return fallback()
    }
    
    // 第二道防线：失败率熔断
    if cb.failureBreaker.IsOpen() {
        return fallback()
    }
    
    // 第三道防线：异常比例熔断
    if cb.exceptionBreaker.IsOpen() {
        return fallback()
    }
    
    // 第四道防线：并发数熔断
    if cb.concurrencyBreaker.IsOpen() {
        return fallback()
    }
    
    // 执行业务
    err := fn()
    
    // 记录结果
    cb.RecordResult(err)
    
    return err
}
```

func OrderCreated(order *Order) {
    // 1. 核心流程：同步执行
    err := processCoreLogic(order)
    if err != nil {
        return err
    }
    
    // 2. 非核心依赖：异步 MQ
    msg := &Message{
        OrderID: order.ID,
        Type:    "GRANT_POINTS",

    return nil
}

// 消费端异步处理

    }
}

九、技术深入探讨

### Q1: 为什么配了熔断还是会雪崩？

**方案参考**：
> 熔断配置不当导致雪崩：
> 
> 1. **超时设置不合理**：超时时间过长，工作进程被占满
> 2. **降级逻辑过重**：降级内再发起远程调用，成为新故障点
> 3. **资源未隔离**：不同依赖共用线程池，单点故障扩散
> 
> 解决方案：资源隔离、降级轻量化、多维度熔断。

### Q2: 如何设计全链路故障隔离？

**方案参考**：
> 全链路故障隔离三层防御：
> 
> 1. **业务分级**：核心强依赖极短超时，非核心弱依赖静默降级
> 2. **资源隔离**：舱壁模式，每个依赖独立线程池
> 3. **异步解耦**：非核心依赖走 MQ，不阻滞主业务线程
> 
> 核心是从调用方式和资源分配上杜绝故障扩散。

## 十、总结

> **链路雪崩防护 = 业务分级（强/弱依赖） + 资源隔离（独立线程池） + 多维熔断（超时/失败率/异常/并发） + 异步解耦（MQ） + 舱壁模式**

### 🧠 核心记忆点

1. **业务分级**：核心强依赖，非核心弱依赖
2. **资源隔离**：舱壁模式，独立线程池
3. **多维熔断**：超时/失败率/异常/并发
4. **异步解耦**：非核心走 MQ
5. **降级轻量化**：预设值或本地缓存
