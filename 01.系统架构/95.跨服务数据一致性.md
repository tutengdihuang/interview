# 跨服务数据一致性

> **场景定位**：微服务架构场景  
> **核心设计要点**：分布式事务、业务分级、TCC/AT模式、兜底补偿

---

## 🎯 一句话定位

**跨服务数据一致性解决什么问题？**
```
下单流程：订单服务 → 库存服务 → 支付服务
订单创建成功，扣完库存
支付服务异常失败
库存已减，订单未支付 → 脏数据
```

**生活化比喻**：
就像转账：
- A 扣钱成功
- B 加钱失败
- 钱凭空消失了

---

## 💎 核心观点（5 分钟速览版）

### 核心观点（5 个关键点）

**1. 本地事务不够**
```
❌ 误区：本地事务就能搞定
✅ 真相：微服务拆分后
事务彻底失效
```

**2. 业务分级**
```
强一致：支付、转账、资金交易
→ 必须保证强一致性
最终一致：浏览、推送
→ 最终一致性即可
```

**3. TCC模式**
```
Try：预留资源
Confirm：确认提交
Cancel：撤销回滚
```

**4. Seata AT模式**
```
低成本适配大多数场景
自动补偿
```

**5. 定时数据校对**
```
自动比对各服务数据差异
自动修复异常脏数据
```

---

## 🚀 一句话精华

> **跨服务一致性 = 业务分级（强/最终一致） + TCC/AT模式 + 定时校对 + 架构优化（服务边界/事务降级）**

## 一、业务分级

### 1.1 强一致场景

```go
// 核心交易：必须强一致
func PaymentFlow(order *Order) error {
    // 支付、转账、资金交易
    // 决不允许数据偏差
    return tccService.Execute(order)
}
```

### 1.2 最终一致场景

```go
// 非核心：最终一致即可
func NotifyUser(order *Order) error {
    // 商品浏览、消息推送
    // 短暂延迟可接受
    return mq.Send(&Message{OrderID: order.ID})
}
```

## 二、TCC模式

```go
type TCCService struct {
    TryFunc    func() error
    ConfirmFunc func() error
    CancelFunc  func() error
}

func (t *TCCService) Execute() error {
    // 1. Try：预留资源
    err := t.TryFunc()
    if err != nil {
        return err
    }
    
    // 2. Confirm：确认提交
    err = t.ConfirmFunc()
    if err != nil {
        // 3. Cancel：撤销回滚
        t.CancelFunc()
        return err
    }
    
    return nil
}
```

**示例：下单流程**

```go
// Try：预留库存
func TryDeductStock(order *Order) error {
    return db.Exec("UPDATE inventory SET frozen = frozen + ? WHERE goods_id = ?",
        order.Amount, order.GoodsID)
}

// Confirm：确认扣减
func ConfirmDeductStock(order *Order) error {
    return db.Exec("UPDATE inventory SET stock = stock - ?, frozen = frozen - ? WHERE goods_id = ?",
        order.Amount, order.Amount, order.GoodsID)
}

// Cancel：撤销预留
func CancelDeductStock(order *Order) error {
    return db.Exec("UPDATE inventory SET frozen = frozen - ? WHERE goods_id = ?",
        order.Amount, order.GoodsID)
}
```

## 三、Seata AT模式

```go
// Seata AT 模式：自动补偿
func CreateOrder(order *Order) error {
    // 1. 开启全局事务
    tx := seata.Begin()
    
    // 2. 创建订单
    err := orderService.Create(tx, order)
    if err != nil {
        tx.Rollback()
        return err
    }
    
    // 3. 扣减库存
    err = inventoryService.Deduct(tx, order)
    if err != nil {
        tx.Rollback()
        return err
    }
    
    // 4. 提交全局事务
    return tx.Commit()
}
```

## 四、定时数据校对

```go
// 定时校对任务
func DataReconciliation() {
    ticker := time.NewTicker(1 * time.Hour)
    for range ticker.C {
        // 1. 查询订单
        orders := db.Query("SELECT * FROM orders WHERE created_at >= ?", yesterday)
        
        for _, order := range orders {
            // 2. 比对库存
            inventory := inventoryService.Get(order.GoodsID)
            if !checkInventory(order, inventory) {
                // 自动修复
                fixInventory(order, inventory)
                alert("库存数据不一致: %v", order.ID)
            }
            
            // 3. 比对支付
            payment := paymentService.Get(order.ID)
            if !checkPayment(order, payment) {
                fixPayment(order, payment)
                alert("支付数据不一致: %v", order.ID)
            }
        }
    }
}
```

## 五、架构层优化

### 5.1 合理拆分服务边界

```
原则：
- 尽量减少跨服务高频联动调用
- 核心业务流程简化
- 缩减事务参与服务数量
```

### 5.2 事务降级

```go
// 系统故障期间
func SystemFailure() {
    // 暂停复杂跨服务流程
    disableComplexTransaction()
    
    // 优先保障单一服务业务正常运行
    keepSingleServiceTransaction()
}
```

六、技术深入探讨

### Q1: 跨服务数据不一致怎么解决？

**方案参考**：
> 跨服务数据一致性三层防御：
> 
> 1. **业务分级**：强一致（支付、转账）用 TCC，最终一致（浏览、推送）用 MQ
> 2. **事务方案**：TCC 模式或 Seata AT 模式，定时数据校对自动修复
> 3. **架构优化**：合理拆分服务边界，减少跨服务调用，事务降级
> 
> 核心是根据业务场景选择方案。

### Q2: TCC 和 AT 模式怎么选？

**方案参考**：
> TCC vs AT：
> 
> 1. **TCC**：Try-Confirm-Cancel 三阶段，业务侵入性强，但灵活可控
> 2. **AT**：自动补偿，业务侵入性弱，低成本适配大多数场景
> 
> 选择：
> - 核心交易链路：TCC，精确控制
> - 普通业务场景：AT，低成本接入
