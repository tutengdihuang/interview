# 分库分表设计

> **场景定位**：后端系统设计场景  
> **核心设计要点**：拆分策略、衍生问题、平滑扩容、架构权衡

---

## 🎯 一句话定位

**分库分表解决什么问题？**
```
单表数据量太大（超过千万），查询性能急剧下降
把大表拆成多个小表，分散到不同库/表，提升性能
```

**生活化比喻**：
就像图书馆藏书太多（1 亿本书），找一个本书要翻半天。
解决方案：把书按类别分到 10 个分馆，每个分馆 1000 万本，找书快 10 倍。

**核心特点**：拆得越碎性能越好，但复杂度也越高。

---

## 💎 核心观点（5 分钟速览版）

### 核心观点（5 个关键点）

**1. 哈希取模不是万能方案**
```
❌ 误区：所有场景都按 ID 哈希取模
✅ 真相：哈希取模扩容成本高到难以接受
从 8 库扩到 16 库 → 70% 数据要迁移
```

**2. 两类拆分方案场景不同**
```
哈希取模：数据均匀，适合点查询
扩容成本极高，需要全量迁移
范围拆分：按时间/ID 区间
扩容简单（追加新分片），但容易热点
```

**3. 衍生问题才是核心难点**
```
拆分本身只完成 10% 工作
90% 工作在于解决衍生问题：
- 分布式主键
- 跨库查询
- 分页排序
- 分布式事务
```

**4. 能不拆就不拆**
```
分库分表是性能毒药
能靠索引优化、读写分离、冷热分离解决的就别拆
拆了就无法回头，复杂度会拖死团队
```

**5. 平滑扩容是高级技能**
```
停机迁移 = 下策
双倍扩容 + 双写 + 灰度切流 = 上策
全程业务不中断，数据零丢失
```

## 🚀 一句话精华

> **分库分表 = 场景匹配（哈希 vs 范围） + 衍生问题治理（主键/查询/事务） + 平滑扩容（双写 + 灰度）**

## 一、为什么哈希取模会翻车？

### ❌ 哈希取模的致命缺陷

**生活化比喻**：
```
哈希取模就像按手机号尾号分班：
- 尾号 0-7 分 8 个班
- 学生来了按 hash(手机号) % 8 分班

问题：学校要从 8 个班扩到 16 个班
→ 70% 的学生要重新分班（转学）
→ 停课两周搞分班（停机迁移）
```

**扩容成本分析**：
```
原方案：8 个库（hash % 8）
扩容后：16 个库（hash % 16）

数据路由变化：
- hash % 8 = 0 → hash % 16 = 0 或 8
- hash % 8 = 1 → hash % 16 = 1 或 9
...

70% 数据路由位置变化 → 需要迁移
```

**迁移代价**：
- 1 亿数据量，迁移 7000 万条
- 按 1000 条/秒，需要 19 小时
- 业务能接受停机 19 小时吗？

## 二、两类拆分方案对比

### 2.1 哈希取模（适合点查询）

**适用场景**：
```
✅ 按主键查询（用户查订单、商品详情）
✅ 数据分布均匀，读写压力分散
❌ 范围查询（按时间导出订单）
❌ 频繁扩容场景
```

**核心实现**：
```go
// 路由计算
func routeTable(userID int64) (dbIndex, tableIndex int) {
    dbIndex = int(userID % 8)        // 8 个库
    tableIndex = int(userID % 256)   // 每库 256 张表
    return
}

// 查询示例
func GetOrder(orderID int64) (*Order, error) {
    dbIdx, tblIdx := routeTable(orderID)
    db := getDB(dbIdx)
    return db.Table(fmt.Sprintf("orders_%d", tblIdx)).
        Where("id = ?", orderID).
        First()
}
```

### 2.2 范围拆分（适合流水数据）

**适用场景**：
```
✅ 时间属性强（订单、流水、日志）
✅ 扩容简单（追加新分片）
❌ 数据热点（新分片压力大）
❌ 冷热数据不均
```

**核心实现**：
```go
// 按年份分片
func routeByTime(orderTime time.Time) string {
    year := orderTime.Year()
    return fmt.Sprintf("orders_%d", year)
}

// 查询示例
func GetOrdersByTimeRange(start, end time.Time) ([]Order, error) {
    startYear := start.Year()
    endYear := end.Year()
    
    var allOrders []Order
    for year := startYear; year <= endYear; year++ {
        db := getDB(fmt.Sprintf("orders_%d", year))
        orders, _ := db.Where("created_at BETWEEN ? AND ?", start, end).Find()
        allOrders = append(allOrders, orders...)
    }
    return allOrders, nil
}
```

**扩容优势**：
```
2024 年数据量大了？
新增 orders_2025 分片即可
不需要迁移历史数据
```

## 三、衍生问题治理（核心难点）

### 3.1 分布式主键

**问题**：单库自增主键失效

**方案对比**：
```
雪花算法：高性能，但时钟回拨会重复
号段模式：强唯一，但依赖数据库
UUID：本地生成，但无序（索引性能差）
```

**推荐方案**：
```go
// 核心业务：号段模式
type Order struct {
    ID int64 `gorm:"primaryKey"` // 号段模式生成
    OrderNo string               // 业务唯一键
}

// 非核心：雪花算法
type Log struct {
    ID int64 `gorm:"primaryKey"` // 雪花算法生成
}
```

### 3.2 跨库查询

**问题**：原来联表查询全部失效

**方案 1：业务层拼装**
```go
// 订单 + 用户信息（跨库）
func GetOrderWithUser(orderID int64) (*OrderVO, error) {
    // 1. 查订单
    order := GetOrder(orderID)
    
    // 2. 查用户（另一个库）
    user := GetUser(order.UserID)
    
    // 3. 业务层拼装
    return &OrderVO{
        Order: order,
        UserName: user.Name,
    }, nil
}
```

**方案 2：异构索引（ES）**
```go
// 数据同步：MySQL → ES
func SyncToES(order *Order) {
    es.Index("orders", order)
}

// 复杂查询走 ES
func SearchOrders(condition SearchCondition) ([]Order, error) {
    return es.Search("orders", condition)
}
```

### 3.3 分页排序

**问题**：跨分片分页性能极差

**错误示范**：
```go
// ❌ 深分页灾难
// 每个分片查 10000 条，内存合并后取第 100 页
SELECT * FROM orders_0 LIMIT 10000, 10
SELECT * FROM orders_1 LIMIT 10000, 10
...
// 8 个分片 × 10000 条 = 80000 条 → 内存排序 → 取 10 条
```

**正确方案：游标分页**
```go
// ✅ 游标分页（上一页最后一条 ID）
func GetOrdersByCursor(lastID int64, limit int) ([]Order, error) {
    // 每个分片只查 limit 条
    var allOrders []Order
    for i := 0; i < 8; i++ {
        db := getDB(i)
        orders, _ := db.Where("id > ?", lastID).
            Order("id ASC").
            Limit(limit).
            Find()
        allOrders = append(allOrders, orders...)
    }
    
    // 内存排序取前 limit 条
    sort.Slice(allOrders, func(i, j int) bool {
        return allOrders[i].ID < allOrders[j].ID
    })
    return allOrders[:limit], nil
}
```

## 四、平滑扩容方案

### 4.1 双倍扩容法（推荐）

**核心思路**：
```
8 库 → 16 库，不停机迁移

步骤：
1. 预部署 16 个库
2. 开启双写（新旧库同时写）
3. 后台迁移历史数据
4. 灰度切读流量（10% → 50% → 100%）
5. 关闭双写，完成扩容
```

**核心实现**：
```go
type MigrationManager struct {
    oldDBs [8]*gorm.DB
    newDBs [16]*gorm.DB
    dualWrite bool // 是否双写
}

// 双写逻辑
func (m *MigrationManager) InsertOrder(order *Order) error {
    // 1. 写旧库
    err := m.oldDBs[order.UserID%8].Create(order).Error
    if err != nil {
        return err
    }
    
    // 2. 双写模式下，同时写新库
    if m.dualWrite {
        m.newDBs[order.UserID%16].Create(order)
    }
    return nil
}

// 迁移流程
func (m *MigrationManager) StartMigration() {
    // 1. 开启双写
    m.dualWrite = true
    
    // 2. 后台迁移历史数据
    go m.migrateHistoryData()
    
    // 3. 灰度切读流量（配置中心控制）
    // 10% → 50% → 100%
    
    // 4. 校验数据一致性
    m.verifyDataConsistency()
    
    // 5. 关闭双写，完成扩容
    m.dualWrite = false
}
```

五、技术深入探讨

### Q1: 什么时候不该分库分表？

**方案参考**：
> 分库分表是最后的手段，能不分就不分：
> 
> 1. **先做索引优化**：80% 的慢查询都是索引问题
> 2. **再读写分离**：主从复制，查询压力分摊
> 3. **再冷热分离**：历史数据归档，热表保持轻量
> 4. **最后才分库分表**：单表真的超过 5000 万，扛不住了
> 
> 过早分库分表会被复杂度拖死，得不偿失。

### Q2: 跨库事务怎么处理？

**方案参考**：
> 跨库事务是分布式事务问题，有三种方案：
> 
> 1. **TCC**：Try-Confirm-Cancel，业务层实现，性能最好
> 2. **本地消息表 + MQ**：最终一致性，性能较差
> 3. **Seata AT**：自动补偿，开发简单
> 
> 核心原则：能本地事务就不跨库，能异步就不强同步。
