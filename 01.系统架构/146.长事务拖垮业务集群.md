## 一、为什么长事务这么难？

### 🔍 核心问题（30 秒版）

**生活化比喻**：
```
长事务的四大难题：
1. 锁等待：长事务持有行锁，其他请求排队等待
2. 死锁频发：多个长事务互相等待，形成死锁
3. 主从延迟：长事务导致主从同步延迟暴涨
4. undo 日志：大批量数据回滚，海量 undo 日志拖垮性能

就像餐厅：
- 锁等待：一个顾客占着桌子很久
- 死锁：多个顾客互相等待对方的菜
- 主从延迟：厨房做菜慢，前台传菜延迟
- undo 日志：退菜太多，厨房忙不过来
```

### 1.1 四大核心难题

| 难题 | 具体表现 | 线上后果 | 生活化比喻 |
|------|---------|---------|-----------|
| **锁等待** | 长事务持有行锁 | 其他请求排队等待，接口超时 | 一个顾客占着桌子很久 |
| **死锁频发** | 多个长事务互相等待 | 业务堵塞，请求堆积 | 多个顾客互相等待对方的菜 |
| **主从延迟** | 长事务导致主从同步延迟暴涨 | 从库查询数据不一致 | 厨房做菜慢，前台传菜延迟 |
| **undo 日志** | 大批量数据回滚 | 海量 undo 日志拖垮性能 | 退菜太多，厨房忙不过来 |

## 三、第二层：标准排查流程加多场景落地优化

### 3.1 排查流程

**排查步骤**：

```bash
# 根据会话 ID、事务 ID 定位具体代码
```

### 3.2 常规场景：拆分事务

**问题**：
```
事务中混杂了 RPC 调用、MQ 收发、大文件处理、复杂查询等非数据库操作
```

**解决方案**：
```java
// ❌ 错误示例
@Transactional
public void createOrder(OrderRequest request) {
    // 1. 创建订单
    orderMapper.insert(order);
    
    // 2. RPC 调用（耗时 2 秒）
    UserInfo user = userService.getUser(request.getUserId());
    
    // 3. 发送 MQ（耗时 1 秒）
    mqProducer.send(order);
    
    // 4. 扣减库存
    stockMapper.deduct(order.getProductId(), order.getCount());
}
// 事务执行时间：3 秒以上

// ✅ 正确示例
public void createOrder(OrderRequest request) {
    // 1. RPC 调用（事务外）
    UserInfo user = userService.getUser(request.getUserId());
    
    // 2. 事务内只包含数据库操作
    createOrderInTransaction(order, user);
    
    // 3. 发送 MQ（事务外）
    mqProducer.send(order);
}

@Transactional
private void createOrderInTransaction(Order order, UserInfo user) {
    // 只包含数据库操作
    orderMapper.insert(order);
    stockMapper.deduct(order.getProductId(), order.getCount());
}
```

**生活化比喻**：
```
就像餐厅：
- 把长流程拆成多个短流程
- 事务内只做核心操作，其他操作放到事务外
```

### 3.3 死锁与锁等待

**问题**：
```
多个长事务互相等待，形成死锁
```

**解决方案**：
```java
// ✅ 统一 SQL 执行顺序
// 所有事务都按照相同的顺序加锁
@Transactional
public void transfer(Long fromUserId, Long toUserId, BigDecimal amount) {
    // 统一按照用户 ID 排序
    if (fromUserId < toUserId) {
        deduct(fromUserId, amount);
        add(toUserId, amount);
    } else {
        add(toUserId, amount);
        deduct(fromUserId, amount);
    }
}

// ✅ 大批量数据操作拆分为批量小事务
public void batchUpdate(List<Order> orders) {
    // 拆分为每批 100 条
    List<List<Order>> batches = Lists.partition(orders, 100);
    
    for (List<Order> batch : batches) {
        // 每批一个事务
        updateBatch(batch);
    }
}

@Transactional
private void updateBatch(List<Order> batch) {
    for (Order order : batch) {
        orderMapper.update(order);
    }
}
```

### 3.4 读写分离

**问题**：
```
长事务导致主从同步延迟暴涨
```

**解决方案**：
```java
// ✅ 梳理事务内读写逻辑
@Transactional
public void createOrder(OrderRequest request) {
    // 写操作走主库
    orderMapper.insert(order);
    
    // 读操作走从库（如果允许延迟）
    if (allowDelay) {
        UserInfo user = userMapper.selectFromSlave(request.getUserId());
    } else {
        // 强一致性读走主库
        UserInfo user = userMapper.selectFromMaster(request.getUserId());
    }
}
```

五、技术深入探讨

### Q1: 长事务持续持有行锁，高并发场景下大量请求排队、阻塞服务、雪崩如何化解？

**答**：
> 化解方案：
>
> 1. **拆分事务**：将非数据库操作剥离出事务
> 2. **统一加锁顺序**：避免交叉加锁、循环加锁
> 3. **批量拆分**：大批量数据操作拆分为批量小事务
> 4. **熔断限流**：配合熔断限流保障业务可用

### Q2: 长事务导致主从同步延迟暴涨，从库查询数据不一致又该怎么应对？

**答**：
> 应对方案：
>
> 1. **梳理事务内读写逻辑**：区分强一致性读和最终一致性读
> 2. **强一致性读走主库**：如刚写入的数据必须立即看到
> 3. **最终一致性读走从库**：如历史数据查询
> 4. **监控主从延迟**：延迟超过阈值自动切回主库

### Q3: 大批量数据的长事务一旦触发回滚，海量 undo 日志拖垮数据库性能如何处理？

**答**：
> 处理方案：
>
> 1. **严控单事务数据量**：拆分为每批 1000 条
> 2. **定期维护 undo 存储空间**：清理历史 undo 日志
> 3. **优化数据库参数**：调整 innodb_log_file_size、innodb_log_buffer_size
