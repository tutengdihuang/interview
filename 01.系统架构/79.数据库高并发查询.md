# 数据库高并发查询

> **场景定位**：数据库架构场景  
> **核心设计要点**：读写分离、主从延迟、一致性保障、架构优化

---

## 🎯 一句话定位

**数据库高并发查询解决什么问题？**
```
单库查询压力过大
通过主从复制、读写分离分摊压力
```

**生活化比喻**：
就像银行柜台：
- 主库：办理存款、取款（写操作）
- 从库：查询余额、流水（读操作）
- 分流后，排队时间大幅缩短

---

## 💎 核心观点（5 分钟速览版）

### 核心观点（5 个关键点）

**1. 主从延迟是隐形陷阱**
```
❌ 误区：读写分离就完事
✅ 真相：主从延迟导致数据不一致
刚付完款查订单，提示"订单不存在"
```

**2. 业务分级读取策略**
```
强制走主库：支付后查订单（强一致）
走从库：历史订单列表（允许延迟）
```

**3. 延迟兜底机制**
```
写入后立即查询：先查从库，查不到再查主库
主从延迟监控：延迟超标自动摘除从库
```

**4. 多级缓存兜底**
```
核心写入同步更新缓存
后续查询优先命中缓存
绕开主从延迟问题
```

**5. 核心场景开关**
```
大促高峰期核心链路强制走主库
宁可牺牲性能也要保证一致性
```

---

## 🚀 一句话精华

> **高并发查询 = 读写分离（分摊压力） + 业务分级（强制主库/走从库） + 延迟兜底（重试+监控） + 缓存加速（绕开延迟）**

## 一、主从延迟问题

### ❌ 典型事故

```
电商做了主从读写分离
订单查询全部走从库

大促当天：
用户付完款 → 查订单 → 提示"订单不存在"
刷新好几次才出来

根因：主从同步延迟 3 秒
用户查询刚好命中延迟窗口
```

```go
// 支付后查订单（强一致）
func GetOrderAfterPayment(orderID string) (*Order, error) {
    // 强制路由到主库
    return db.Master().First(orderID)

    // 强制主库查询
    return db.Master().First(userID)
```

### 2.2 走从库

```go
// 历史订单列表（允许延迟）
func GetOrderHistory(userID string) ([]Order, error) {
    // 走从库查询
    return db.Slave().Where("user_id = ?", userID).Find()
}

// 商品详情（允许延迟）
func GetProductDetail(goodsID string) (*Product, error) {
    return db.Slave().First(goodsID)
}
```

## 三、延迟兜底机制

### 3.1 延迟重试

```go
func GetOrderAfterWrite(orderID string) (*Order, error) {
    // 1. 先查从库
    order, err := db.Slave().First(orderID)
    if err == nil && order != nil {
        return order, nil
    }
    
    // 2. 查不到，等待 100ms 重试
    time.Sleep(100 * time.Millisecond)
    order, err = db.Slave().First(orderID)
    if err == nil && order != nil {
        return order, nil
    }
    
    // 3. 还是查不到，降级查主库
    return db.Master().First(orderID)
}
```

### 3.2 主从延迟监控

```go
// 监控主从延迟
func MonitorReplicationDelay() {
    ticker := time.NewTicker(1 * time.Second)
    for range ticker.C {
        delay := getReplicationDelay() // 获取延迟秒数
        
        if delay > 5 {
            // 延迟超过 5 秒，摘除从库
            removeSlaveFromPool()
            alert("主从延迟超过 5 秒，已摘除从库")
        }
    }
}
```

## 四、多级缓存兜底

```go
// 写入时同步更新缓存
func CreateOrder(order *Order) error {
    // 1. 写入主库
    err := db.Master().Create(order)
    if err != nil {
        return err
    }
    
    // 2. 同步更新缓存
    redis.Set(order.ID, order, 5*time.Minute)
    
    return nil
}

// 查询时优先命中缓存
func GetOrder(orderID string) (*Order, error) {
    // 1. 查缓存
    order, err := redis.Get(orderID)
    if err == nil {
        return order, nil
    }
    
    // 2. 查从库
    order, err = db.Slave().First(orderID)
    if err == nil {
        redis.Set(orderID, order, 5*time.Minute) // 回写缓存
        return order, nil
    }
    
    // 3. 查主库
    order, err = db.Master().First(orderID)
    if err == nil {
        redis.Set(orderID, order, 5*time.Minute)
    }
    
    return order, err
}
```

```go
// 大促高峰期
func PeakMode() {
    // 核心链路强制走主库
    config.Set("read_route", "master")

// 恢复正常
func NormalMode() {
    // 读写分离
    config.Set("read_route", "slave")
}

// 读请求路由
func RouteReadRequest() *gorm.DB {
    route := config.Get("read_route")
    if route == "master" {
        return db.Master()
    }
    return db.Slave()
}
```

六、技术深入探讨

### Q1: 主从延迟怎么处理？

**方案参考**：
> 主从延迟是读写分离的隐形陷阱，处理方案：
> 
> 1. **业务分级**：支付后查订单强制走主库，历史查询走从库
> 2. **延迟重试**：写入后立即查询，先查从库，查不到重试，再查不到查主库
> 3. **延迟监控**：实时监控延迟，超过阈值摘除从库
> 4. **缓存兜底**：写入时同步更新缓存，查询优先命中缓存
> 
> 核心是根据业务场景选择读取策略，强一致走主库，允许延迟走从库。

### Q2: 读写分离后数据不一致怎么办？

**方案参考**：
> 数据不一致是读写分离的必然问题，解决方案：
> 
> 1. **业务分级**：核心链路强制主库，非核心走从库
> 2. **缓存加速**：写入同步更新缓存，查询优先命中
> 3. **延迟监控**：延迟超标自动摘除从库
> 4. **核心开关**：大促期间强制走主库
> 
> 关键是根据业务容忍度选择策略，不能一刀切。
