# 大表查询性能优化

> **场景定位**：数据库性能优化技术场景  
> **核心设计要点**：分表策略、索引优化、分页优化、模糊查询、查询拆分、架构优化

---

## 🎯 一句话定位

**大表查询性能问题是什么？**
```
分表、索引、分页都配置到位，但查询性能还是极差：
- 管理员查询近 3 年历史订单
- 筛选条件加了时间范围 + 用户昵称模糊查询
- 接口直接超时
- 数据库 CPU 飙升到 90% 以上
- 连带其他接口卡顿，甚至出现服务熔断
```

**生活化比喻**：就像你在一个大型图书馆找书，虽然图书馆分了区域（分表），每本书有编号（索引），每次只看 20 本（分页），但你要找"书名包含'Java'的书"，图书管理员还是要翻遍所有书，累趴下了。

**核心特点**：分表、索引、分页是基础，但模糊查询、索引失效、分页过深等问题会导致性能瓶颈。

### 核心观点（3 层防御）

**1. 表结构与索引优化：从底层提升效率**
```
分表策略优化：
- 水平分表结合时间 + 用户 ID 哈希
- 避免单表数据不均
- 大表字段精简，拆分冗余字段到附属表

索引精准设计：
- 联合索引贴合查询场景
- 避免冗余索引
- 模糊查询用全文索引，避免前缀 %

避免无效字段：
- 禁止 SELECT *
- 只查询业务所需字段
- 减少数据传输和磁盘 IO

生活化比喻：
分表 = 图书馆分区域
索引 = 书的编号系统
精简字段 = 只查书名，不查全部内容
```

**2. 查询逻辑优化：规避性能坑点**
```
分页查询优化：
- 避免 LIMIT offset 过大（如 LIMIT 100000, 20）
- 改用"主键自增 + 范围查询"分页
- 减少数据库全表扫描和排序耗时

复杂查询拆分：
- 多条件筛选拆分成分步查询
- 避免多表联查（尤其大表联查）
- 用程序层面拼接结果

生活化比喻：
分页优化 = 不要从第 10 万页开始看，从当前页看
查询拆分 = 复杂问题拆成简单问题，分步解决
```

**3. 架构层优化：提升整体性能**
```
缓存优化：
- 热点数据缓存到 Redis
- 减少数据库查询

搜索引擎：
- 模糊查询用 Elasticsearch
- 全文检索性能更高

读写分离：
- 查询走从库
- 写入走主库

生活化比喻：
缓存 = 常用书放在前台，不用去仓库
搜索引擎 = 用电脑查书名，不用人工翻
读写分离 = 查询和修改分开，互不影响
```

## 一、问题本质：分表 + 索引 + 分页 ≠ 性能无忧

### ❌ 常见误区

**误区 1：分表了就万事大吉**
```
问题：
- 分表策略不当，单表数据不均
- 跨表查询性能差
- 分表键选择不当

解决：
- 结合时间 + 用户 ID 哈希分表
- 避免热点数据集中在单表
- 分表键选择查询频率高的字段
```

**误区 2：加了索引就快**
```
问题：
- 索引设计不合理，没有贴合查询场景
- 模糊查询（LIKE '%xxx%'）索引失效
- 冗余索引浪费空间

解决：
- 联合索引贴合查询场景
- 模糊查询用全文索引
- 定期清理冗余索引
```

**误区 3：分页就安全**
```
问题：
- LIMIT offset 过大（如 LIMIT 100000, 20）
- 数据库要扫描 100000 + 20 条数据
- 性能极差

解决：
- 改用主键范围查询
- 记录上次查询的最大 ID
- 下次从该 ID 开始查询
```

## 二、第一层防御：表结构与索引优化

### 2.1 分表策略优化

**生活化比喻**：
```
分表 = 图书馆分区域
- 按时间分：每年的书放在不同楼层
- 按用户 ID 分：不同读者的书放在不同房间
- 结合分：既有时间分区，又有用户分区

避免单表数据不均：
- 不能只按时间分（某年订单特别多）
- 要结合用户 ID 哈希（均匀分布）
```

**代码示例**：
```java
// 分表策略：时间 + 用户 ID 哈希
public class OrderTableRouter {
    
    /**
     * 计算表名
     */
    public String getTableName(Date createTime, Long userId) {
        // 按年月分表（如 order_202401）
        String yearMonth = new SimpleDateFormat("yyyyMM").format(createTime);
        
        // 按用户 ID 哈希分表（如 order_202401_00 - order_202401_15）
        int tableIndex = (int) (userId % 16);
        
        return String.format("order_%s_%02d", yearMonth, tableIndex);
    }
}

// 查询时，根据查询条件路由到对应表
public List<Order> queryOrders(Long userId, Date startTime, Date endTime) {
    String tableName = orderTableRouter.getTableName(startTime, userId);
    return orderMapper.selectByTableName(tableName, userId, startTime, endTime);
}
```

### 2.2 索引精准设计

**生活化比喻**：
```
索引设计 = 书的编号系统
- 单列索引：按书名编号
- 联合索引：按书名 + 作者编号
- 要贴合查询场景

模糊查询优化：
- LIKE '%xxx%'：索引失效（全表扫描）
- LIKE 'xxx%'：索引有效（前缀匹配）
- 全文索引：专门用于模糊查询
```

**代码示例**：
```sql
-- ❌ 错误做法：模糊查询索引失效
SELECT * FROM orders WHERE user_name LIKE '%张三%';

-- ✅ 正确做法 1：避免前缀 %
SELECT * FROM orders WHERE user_name LIKE '张三%';

-- ✅ 正确做法 2：使用全文索引
ALTER TABLE orders ADD FULLTEXT INDEX ft_user_name (user_name);
SELECT * FROM orders WHERE MATCH(user_name) AGAINST('张三');

-- ✅ 正确做法 3：精确查询 + 缓存
-- 先精确查询，结果缓存到 Redis
SELECT * FROM orders WHERE user_name = '张三';
```

**联合索引设计**：
```sql
-- 查询场景：按时间范围 + 用户 ID 查询
SELECT * FROM orders 
WHERE create_time BETWEEN '2024-01-01' AND '2024-12-31'
  AND user_id = 123;

-- 创建联合索引（注意字段顺序）
CREATE INDEX idx_time_user ON orders(create_time, user_id);

-- 解释：
-- 联合索引遵循最左前缀原则
-- (create_time, user_id) 可以支持：
-- 1. WHERE create_time = ?
-- 2. WHERE create_time = ? AND user_id = ?
-- 但不能支持：
-- WHERE user_id = ?（跳过了 create_time）
```

### 2.3 避免无效字段

**生活化比喻**：
```
SELECT * = 把整本书都搬过来
SELECT 需要的字段 = 只搬需要的章节

大表查询更要精简字段：
- 减少数据传输
- 减少磁盘 IO
- 提升查询速度
```

**代码示例**：
```java
// ❌ 错误做法：SELECT *
public Order getOrder(Long orderId) {
    return orderMapper.selectById(orderId); // SELECT *
}

// ✅ 正确做法：只查询需要的字段
public OrderVO getOrderVO(Long orderId) {
    Order order = orderMapper.selectFields(orderId, 
        "id", "order_no", "user_id", "amount", "create_time");
    
    return OrderVO.from(order);
}

// Mapper
@Select("SELECT id, order_no, user_id, amount, create_time " +
        "FROM orders WHERE id = #{orderId}")
Order selectFields(@Param("orderId") Long orderId, 
                   @Param("fields") String... fields);
```

## 三、第二层防御：查询逻辑优化

### 3.1 分页查询优化

**生活化比喻**：
```
LIMIT 100000, 20 = 从第 10 万页开始看，每次看 20 本
- 数据库要扫描 100020 条数据
- 然后丢弃前 100000 条
- 只返回 20 条
- 性能极差

优化方案 = 记住上次看到哪里，下次从那里开始
- 记录上次查询的最大 ID
- 下次 WHERE id > last_id LIMIT 20
- 只需要扫描 20 条数据
```

**代码示例**：
```java
// ❌ 错误做法：LIMIT offset 过大
public List<Order> getOrders(int page, int size) {
    int offset = (page - 1) * size;
    return orderMapper.selectByPage(offset, size);
}

// SQL: SELECT * FROM orders LIMIT 100000, 20
// 性能极差

// ✅ 正确做法：主键范围查询
public List<Order> getOrders(Long lastId, int size) {
    return orderMapper.selectByRange(lastId, size);
}

// Mapper
@Select("SELECT * FROM orders WHERE id > #{lastId} ORDER BY id LIMIT #{size}")
List<Order> selectByRange(@Param("lastId") Long lastId, 
                          @Param("size") int size);

// 使用示例
public PageResult<Order> queryOrders(Long lastId, int size) {
    List<Order> orders = orderMapper.selectByRange(lastId, size);
    
    // 返回结果和下一个 lastId
    Long nextLastId = orders.isEmpty() ? null : orders.get(orders.size() - 1).getId();
    
    return new PageResult<>(orders, nextLastId);
}
```

**分页优化对比**：
```sql
-- ❌ 传统分页（慢）
SELECT * FROM orders ORDER BY id LIMIT 100000, 20;
-- 扫描 100020 条，丢弃 100000 条

-- ✅ 范围分页（快）
SELECT * FROM orders WHERE id > 100000 ORDER BY id LIMIT 20;
-- 只扫描 20 条
```

### 3.2 复杂查询拆分

**生活化比喻**：
```
复杂查询 = 一次找多种条件的书
- 多表联查：图书馆 + 书店 + 出版社一起找
- 性能差，容易超时

查询拆分 = 分步找
- 先在图书馆找
- 然后在书店找
- 最后在出版社找
- 程序层面拼接结果
```

**代码示例**：
```java
// ❌ 错误做法：多表联查
public List<OrderVO> getOrders(Long userId, Date startTime, Date endTime) {
    return orderMapper.selectComplex(userId, startTime, endTime);
}

// SQL（慢）
SELECT o.*, u.user_name, p.product_name
FROM orders o
JOIN users u ON o.user_id = u.id
JOIN products p ON o.product_id = p.id
WHERE o.user_id = #{userId}
  AND o.create_time BETWEEN #{startTime} AND #{endTime};

// ✅ 正确做法：拆分查询
public List<OrderVO> getOrders(Long userId, Date startTime, Date endTime) {
    // 1. 查询订单
    List<Order> orders = orderMapper.selectByUserAndTime(userId, startTime, endTime);
    
    if (orders.isEmpty()) {
        return Collections.emptyList();
    }
    
    // 2. 批量查询用户信息
    Set<Long> userIds = orders.stream()
        .map(Order::getUserId)
        .collect(Collectors.toSet());
    List<User> users = userMapper.selectByIds(userIds);
    Map<Long, User> userMap = users.stream()
        .collect(Collectors.toMap(User::getId, Function.identity()));
    
    // 3. 批量查询商品信息
    Set<Long> productIds = orders.stream()
        .map(Order::getProductId)
        .collect(Collectors.toSet());
    List<Product> products = productMapper.selectByIds(productIds);
    Map<Long, Product> productMap = products.stream()
        .collect(Collectors.toMap(Product::getId, Function.identity()));
    
    // 4. 程序层面拼接结果
    return orders.stream()
        .map(order -> {
            OrderVO vo = new OrderVO();
            vo.setOrder(order);
            vo.setUser(userMap.get(order.getUserId()));
            vo.setProduct(productMap.get(order.getProductId()));
            return vo;
        })
        .collect(Collectors.toList());
}
```

## 四、第三层防御：架构层优化

### 4.1 缓存优化

**生活化比喻**：
```
缓存 = 常用书放在前台
- 热点数据缓存到 Redis
- 减少数据库查询
- 提升响应速度
```

**代码示例**：
```java
@Service
public class OrderService {
    
    @Autowired
    private StringRedisTemplate redisTemplate;
    
    @Autowired
    private OrderMapper orderMapper;
    
    public Order getOrder(Long orderId) {
        String cacheKey = "order:" + orderId;
        
        // 1. 查询缓存
        String cacheValue = redisTemplate.opsForValue().get(cacheKey);
        if (cacheValue != null) {
            return JSON.parseObject(cacheValue, Order.class);
        }
        
        // 2. 缓存未命中，查询数据库
        Order order = orderMapper.selectById(orderId);
        
        // 3. 写入缓存（过期时间 30 分钟）
        if (order != null) {
            redisTemplate.opsForValue().set(
                cacheKey,
                JSON.toJSONString(order),
                30, TimeUnit.MINUTES
            );
        }
        
        return order;
    }
}
```

### 4.2 搜索引擎（模糊查询优化）

**生活化比喻**：
```
搜索引擎 = 用电脑查书名
- 模糊查询用 Elasticsearch
- 全文检索性能更高
- 支持复杂查询
```

**代码示例**：
```java
@Service
public class OrderSearchService {
    
    @Autowired
    private ElasticsearchRestTemplate esTemplate;
    
    @Autowired
    private OrderMapper orderMapper;
    
    /**
     * 模糊查询订单（Elasticsearch）
     */
    public List<Order> searchOrders(String keyword, Date startTime, Date endTime) {
        // 构建查询条件
        NativeSearchQueryBuilder queryBuilder = new NativeSearchQueryBuilder();
        
        BoolQueryBuilder boolQuery = QueryBuilders.boolQuery();
        
        // 模糊查询用户名
        if (StringUtils.isNotBlank(keyword)) {
            boolQuery.must(QueryBuilders.matchQuery("userName", keyword));
        }
        
        // 时间范围查询
        if (startTime != null && endTime != null) {
            boolQuery.must(QueryBuilders.rangeQuery("createTime")
                .gte(startTime.getTime())
                .lte(endTime.getTime()));
        }
        
        queryBuilder.withQuery(boolQuery);
        
        // 执行查询
        SearchHits<Order> searchHits = esTemplate.search(
            queryBuilder.build(),
            Order.class,
            IndexCoordinates.of("orders")
        );
        
        return searchHits.getSearchHits().stream()
            .map(SearchHit::getContent)
            .collect(Collectors.toList());
    }
    
    /**
     * 同步数据到 Elasticsearch（定时任务）
     */
    @Scheduled(fixedRate = 60000) // 每分钟同步一次
    public void syncToElasticsearch() {
        List<Order> orders = orderMapper.selectRecentOrders();
        
        for (Order order : orders) {
            esTemplate.save(order, IndexCoordinates.of("orders"));
        }
    }
}
```

### 4.3 读写分离

**生活化比喻**：
```
读写分离 = 查询和修改分开
- 查询走从库
- 写入走主库
- 互不影响
```

**配置示例**：
```yaml
# application.yml
spring:
  datasource:
    dynamic:
      primary: master  # 主库（写入）
      datasource:
        master:
          url: jdbc:mysql://localhost:3306/db_master
        slave1:
          url: jdbc:mysql://localhost:3306/db_slave1
        slave2:
          url: jdbc:mysql://localhost:3306/db_slave2
      strategy:
        load-balance:
          type: ROUND_ROBIN  # 轮询负载均衡

# 代码中使用
@Service
public class OrderService {
    
    @DS("master")  # 写入走主库
    @Transactional
    public void createOrder(Order order) {
        orderMapper.insert(order);
    }
    
    @DS("slave")  # 查询走从库
    public Order getOrder(Long orderId) {
        return orderMapper.selectById(orderId);
    }
}
```

五、技术深入探讨

### 考点 1：LIMIT offset 过大为什么慢？

**方案参考**（30 秒版）：
> "LIMIT 100000, 20 需要扫描 100020 条数据，然后丢弃前 100000 条，只返回 20 条。offset 越大，扫描的数据越多，性能越差。解决方案是用主键范围查询：WHERE id > last_id LIMIT 20，只需要扫描 20 条数据。"

**加分回答**：
> "实际生产中，我会记录上次查询的最大 ID，下次查询时 WHERE id > last_id LIMIT size。这样无论查询第几页，性能都一样。对于需要跳页的场景，可以用延迟关联：先查 ID，再根据 ID 查完整数据。"

### 考点 2：模糊查询为什么慢？

**方案参考**：
> "LIKE '%xxx%' 会导致索引失效，因为要扫描全表匹配。解决方案有三种：1）避免前缀 %，用 LIKE 'xxx%'（索引有效）；2）使用全文索引（MATCH AGAINST）；3）使用搜索引擎（Elasticsearch），专门用于全文检索。"

**加分回答**：
> "实际生产中，对于复杂的模糊查询，我会用 Elasticsearch。数据通过定时任务或消息队列同步到 ES，查询走 ES，性能比 MySQL 高很多。同时要定期同步，保证数据一致性。"

### 考点 3：如何优化多表联查？

**方案参考**：
> "多表联查性能差，尤其是大表联查。解决方案是拆分查询：先查主表，再根据关联 ID 批量查询关联表，程序层面拼接结果。避免数据库层面的 JOIN，减少数据库压力。"

**加分回答**：
> "实际生产中，我会用批量查询代替 JOIN。比如查询订单和用户信息，先查订单，收集所有 user_id，然后批量查询用户信息，用 Map 存储，程序层面拼接。这样数据库只需要执行简单的单表查询，性能更好。"

## 六、总结（一句话带走）

### 🎯 一句话总结

> **大表查询优化三层防御 = 表结构索引优化（分表/索引/精简字段） + 查询逻辑优化（分页/拆分） + 架构层优化（缓存/搜索引擎/读写分离）**

### 🧠 核心记忆点

1. **LIMIT offset 过大为什么慢？** 要扫描 offset + size 条数据，丢弃前 offset 条。解决方案：主键范围查询。
2. **模糊查询为什么慢？** LIKE '%xxx%' 索引失效，全表扫描。解决方案：全文索引、Elasticsearch。
3. **多表联查为什么慢？** JOIN 操作消耗大，尤其大表联查。解决方案：拆分查询，程序层面拼接。
4. **分表策略怎么选？** 结合时间 + 用户 ID 哈希，避免单表数据不均。
5. **架构层优化有哪些？** 缓存（Redis）、搜索引擎（Elasticsearch）、读写分离。
