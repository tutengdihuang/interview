面试官：分布式全局唯一 ID 怎么实现？#java #java 面试 #后端 #后端开发 #程序员
今天面挂了一个三年后端。
我问他分布式全局唯一 id 怎么实现？
他脱口而出用雪花算法，按机器分配 workerid、时间戳、加序列号拼接，高性能还能保证全区唯一。
我点点头，笑着问了他一个真实发生的线上事故。假设你们用雪花算法生成订单主键 id，某次机房服务器时间校准后，线上陆续出现订单创建失败，数据库报主键唯一约束冲突。你排查发现冲突的 id 来自不同的服务节点，workerid 配置没有重复，可生成的 id 就是出现了重叠，连带支付流水、物流单都出现了重复号，业务权限受影响。问题出在哪？
他想了想说可能是服务器时钟回拨了。
我追问：对，那你怎么保证时钟异常、机器扩容时 id 绝对不重复？难道所有 id 都走数据库自增？
他开始吱吱呜呜。面试到这就结束了，这正是分布式 id 的隐形暗坑。
你以为用上雪花算法就能搞定全局唯一 id，却没想到时钟回拨、workerid 冲突、机器扩容都会导致 id 重复，引发核心业务故障。
如果这道题目你也不会回答，我整理了让大厂面试官沉默的必考题库，包含 java 基础、jvm 夺命连环问、spring 全家桶、mybatis、redis、微服务、分布式实战等等。只要是我粉丝，留下 pdf 直接拿走。
为什么这个问题能筛出高手？因为它考察的不是会不会写雪花算法工具类，而是有没有建立分布式场景下 id 生成的全链路可信思维。
一个能真正驾驭分布式 id 的后端必须建立三层防御。
第一层：业务分级，区分可信等级，强唯一核心场景，比如订单号、支付流水号、资金账单，采用高可靠生成方案，零容忍 id 重复。非核心场景，比如日志追踪 id、消息标识、非核心数据主键，可用轻量生成方案，极低概率重复，不影响主业务。
第二层：异常兜底与冲突防护，workerid 统一分配，搭建独立的 workerid 注册中心，服务启动时自动申请唯一标识，杜绝人工配置重复。时钟回拨容错，内置时钟检测机制，小幅回拨等待时间追上，大幅回拨自动切换备用号段，拒绝生成重复 id。生成前去重校验，核心 id 生成后先经分布式缓存校验唯一性，确认无冲突再返回业务层。
第三层：架构层优化，从根源降低风险，熔断模式兜底，核心链路引入数据库熔断生成方案作为降级策略，雪花算法异常时自动无缝切换，保证业务不中断。业务前缀隔离，不同业务线、不同机房增加独立前缀位，从维度上天然隔离跨业务、跨集群的 id 重复风险。核心场景开关，大促或服务器运维期间，核心 id 生成切换为熔断加双重校验模式，宁可牺牲一点生成性能，也要保证核心业务 id 绝对唯一。
这个就叫专业。
所以这道题考的是什么？它考的是你有没有从会实现雪花算法升级为设计高可靠分布式 id 生成方案的工程思维。普通开发以为用上雪花算法就能保证全区唯一，而高级工程师知道在分布式环境面前，雪花算法是一把双刃剑。
