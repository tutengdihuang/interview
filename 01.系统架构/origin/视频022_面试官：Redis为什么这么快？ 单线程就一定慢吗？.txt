面试官：Redis 为什么这么快？单线程就一定慢吗？
#java #java 面试 #后端 #后端开发 #程序员
面试官：redis 为什么这么快？不就是因为数据存在内存里吗？既然是单线程模型，为什么反而能扛住高并发？
你蒙了，又答不出来了。
redis 为什么快？这个问题其实经常出现在后端面试里，而且面试官往往会顺着往下追问。
先说 redis 到底是什么？redis 本质上是一个基于内存的键值数据库，常用来做缓存、分布式锁、消息队列等场景。它的核心读写采用单线程架构，但性能却能达到每秒数万甚至数十万次操作。
当你执行 redis 命令时，所有键值读写逻辑都由一个主线程串行执行，不需要加锁，也不会出现线程安全问题，处理完成后直接把结果返回给客户端。
很多人以为 redis 快就只是因为存内存，其实这是一个非常常见的误区。内存储存是基础，但同样是内存数据库，很多产品性能远不如 redis，核心差距在架构设计上。
还有人觉得单线程肯定比多线程慢，redis 用单线程是技术落后，其实恰恰相反，这是它针对场景做的最优选择。所以做性能优化时经常遇到一种情况，给服务器加了更多 cpu 核心，redis 性能却没半点提升，就是没理解它的单线程模型。
面试官接下来通常会追问：既然是单线程，为什么还能同时处理那么多客户端连接？
如果这道题你也不会回答，我整理了让大场面试官沉默的必考题库，包含 zookeeper、jvm、夺命连环问、spring 全家桶、mybatis、redis、微服务、分布式实战等等。只要是我粉丝，留下 pdf 直接打包带走。
答案是靠 io 多路复用机制。redis 用单线程来处理网络 io，通过 epoll 这类 io 多路复用技术，同时监听上万个客户端连接，哪个连接有数据就绪就处理哪个，不用阻塞等待某一个连接。单线程避开了多线程频繁的上下文切换开销和锁竞争，反而在内存操作这种 cpu 密集度不高的场景里效率更高。
准确来说，redis 的单线程指的是网络 io 和键值对读写由单线程完成，并不是整个 redis 进程只有一个线程。比如后台的 rdb 持久化、aof 刷盘、过期键清理、主从数据同步这些工作都是由额外的后台线程或子进程去做的，不会阻塞主线程的读写。
如果面试官继续深挖，你还可以补充一句：单线程不代表没有性能瓶颈，redis 的瓶颈通常不是 cpu，而是内存大小和网络带宽。如果使用不当，比如存储超大 key、执行 keys * 这类阻塞命令、主从全量同步时 fork 子进程，照样会把主线程卡住，出现大面积请求超时。
所以在生产环境里不能因为 redis 快就随意使用，要避开阻塞命令，控制 key 大小，才能真正发挥它的性能优势。
最后总结一下：
一、redis 快的基础是内存储存，读写都在内存完成，速度远快于磁盘型数据库。
二、核心读写采用单线程模型，避免了线程上下文切换和锁竞争的额外开销。
三、依靠 io 多路复用技术，单线程也能同时处理大量客户端连接，支撑高并发场景。
四、单线程仅指读写，后台任务有独立线程、进程，瓶颈在内存和网络而非 cpu。
这个就叫专业。如果在面试里能把这几个层次讲清楚，面试官基本就知道你是真的理解 redis 的设计原理，而不是只会说存内存所以快。
