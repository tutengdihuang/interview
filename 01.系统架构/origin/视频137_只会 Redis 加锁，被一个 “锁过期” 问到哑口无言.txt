面试官问这个问题考察的不是你会不会写加锁代码，而是在高并发、高可用场景下如何设计安全、可靠、高性能的分布式锁方案。真正能通过面试的 Redis 分布式锁设计必须吃透三层核心逻辑。
第一层：先明确分布式锁的核心原理和正确用法。
分布式锁核心三要素：互斥性、防死锁、正确释放。
基础错误用法：setnx 加 expire 分两次执行，不校验锁持有者直接 delete，不设置过期时间。
正确基础实现：使用 set key value nx ex seconds 单命令，保证加锁原子性。释放锁时用 Lua 脚本校验 value 是否为当前线程标识，再执行 delete，保证释放原子性。
第二层：生产常见坑与核心解决方案。
锁过期续期问题
坑点：业务执行时间超过锁过期时间，导致锁提前释放，引发并发问题。
解决方案：redisson 看门狗机制，加锁成功后启动定时任务，每隔三分之一过期时间检查锁是否还被当前线程持有，若持有则自动续期。注意：异步任务中使用时，主线程执行完看门狗会停止续期，导致异步任务锁丢失。
可重入性问题
坑点：同一个线程多次加锁会导致死锁。
解决方案：锁的 value 存储线程标识加重入次数，加锁时若线程已持有锁，则重入次数加一。释放时重入次数减一，次数为零时真正删除锁。
主从架构锁丢失问题
坑点：主节点加锁成功后未同步到从节点就宕机，新升级主节点无锁信息，导致锁失效。
解决方案：红锁算法，向多个独立 Redis 节点加锁，超过半数加锁成功才算成功。注意：红锁会牺牲性能，且无法解决节点时钟不一致问题。
第三层：高并发、高可用场景的生产落地细节。
高并发性能优化
采用分段锁思想，将大锁拆分为多个小锁，降低锁竞争力度。
使用读写锁，读多写少场景下提升并发量。
异常场景处理
配置锁的最大持有时间，防止看门狗异常导致锁永久占用。
添加分布式锁监控，统计锁等待时长、持有时长、超时次数，及时发现异常。
极端场景兜底，Redis 集群脑裂时采用过半写入原则，保证数据一致性。核心业务增加数据库乐观锁，作为最终兜底，防止超卖。
