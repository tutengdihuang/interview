@Transactional 是什么？加了注解一定能回滚吗？
加个 @Transactional 当时不就是开启事务了吗？既然注解是用来控制事务的，为什么有时候抛了异常、数据却没回滚？一追问你又答不出来了。
@Transactional 是什么？加了注解真的就万无一失吗？这个问题其实经常出现在后端面试里，而且面试官往往会顺着往下追问。
先说 @Transactional 到底是什么？
@Transactional 本质上是 spring 声明式事务的核心注解，作用是通过 aop 动态代理机制，在方法执行前后自动完成事务的开启、提交和回滚。它工作的基础不是 java 原生语法，而是 spring 的代理对象增强逻辑。只有被代理对象调用的目标方法注解才会真正生效。
当在方法上加了 @Transactional 注解时，spring 会为这个类生成动态代理对象，调用方法时代理会先开启事务，方法正常执行完成就提交事务，方法抛出符合规则的异常就回滚事务。
于是就看到很多业务代码里只要涉及数据库写操作，方法上随手加一个 @Transactional 就完事了。
很多人以为加了 @Transactional 事务就一定会生效，异常一定会回滚，其实这是一个非常常见的误区。注解存在只能说明标记了这个方法需要事务，但代理能不能拦截到异常，符不符合回滚条件，这些核心问题它一个都没保证。
比如方法是 private 的，代理根本访问不到；比如同内部直接调用不走代理对象；比如抛出的是检查型异常又没配置回滚规则，这些情况下加了注解事务也不会回滚。所以线上经常遇到一种情况，加了 @Transactional 出错了，数据却还是持久化了。
面试官接下来通常会追问：那我把方法改成 public，用外部类调用总该没问题了吧？
问题答案是还不够，因为就算代理正常生效了，还有很多场景会导致事务不回滚。
第一种是异常类型不匹配，默认情况下 spring 只对 runtimeException 和 error 触发回滚。如果抛出的是 exception 这类检查型异常，比如 io 异常、自定义业务检查异常，默认是不会回滚的，必须手动加上 rollbackFor 等于 exception.class 才行。
第二种是异常被内部捕获吃掉了，如果在方法里用 trycatch 把异常捕获住，没有继续往外抛，spring 的事务切面就感知不到异常发生，自然就不会触发回滚，会直接正常提交事务。
第三种是事务传播机制配置错误，比如用了 notsupported、never 这种非事务传播属性，或者嵌套事务里 propagation 配置不当，都会导致主方法异常时子事务不回滚，或者子异常不影响主事务。
很多开发者写业务代码的时候，不管什么方法都加个 @Transactional，其实这是非常粗糙的做法。如果面试官继续深挖，你还可以补充一句：除了回滚失效的问题，滥用 @transactional 还容易产生大事务、长事务，带来数据库连接长时间占用、行锁等待、死锁等一系列性能问题。纯查询类方法完全没必要加事务，写操作也要尽量缩小事务范围。
所以在生产环境里不要随便给方法加 @transactional 就完事了，要确认代理生效，配置正确的回滚异常，合理设计事务范围。
高并发场景下，本质是 spring 基于 aop 动态代理实现的声明式事务，用来自动管理事务的开启、提交和回滚。
单纯加注解不能保证事务生效，private 方法、同类内部调用、异常类型不匹配都会导致回滚失效。
保证事务可靠需要 public 修饰方法，外部对象调用，配置正确的 rollbackFor，不吞异常，合理设置传播属性。
生产环境不要滥用 @Transactional，避免大事务、长事务，纯查询方法无需加事务。
如果在面试里能把这几个层次讲清楚，面试官基本就知道你是真的理解 spring 事务原理，而不是只会加一个 @Transactional 注解。
