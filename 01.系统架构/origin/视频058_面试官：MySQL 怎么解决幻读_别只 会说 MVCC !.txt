面试官：MySQL 怎么解决幻读？别只会说 MVCC！#java #java 面试 #后端 #后端开发 #程序员
最近面了一个高级后端开发，简历上写着精通 mysql 事务原理，深入理解 innodb 的锁机制与 mvcc 底层实现。我上来就抛了个最经典的问题：我们都知道 innodb 默认的可重复读隔离级别可以解决幻读问题，你说说它具体是怎么做到的？
他自信满满的回答：靠 mvcc 多版本并发控制，每行数据都带隐藏的事务 id 和回滚指针，事务启动时生成一致性读视图，读取历史版本的数据，不用加锁就能保证两次查询结果一致，自然就不会出现幻读，还能实现读写不冲突。
我点了点头，但马上追问：你说的 mvcc 是基础结论，那我问你有了 mvcc 为什么还要设计间隙锁？如果 mvcc 就能彻底解决幻读，那 innodb 的 next key lock 还有存在的必要吗？比如我执行 select...for update 做当前读，这时候 mvcc 还能防幻读吗？
他愣了一下，说：当前读应该是加行锁吧，具体间隙锁和幻读的关系没太深究。
我追问：行锁只能锁住已存在的数据行，那新插入的数据怎么防？再问你幻读到底定义是什么？两次查询返回横竖不一样就算幻读吗？有没有例外场景？为什么很多人说 mvcc 管快照读，间隙锁管当前读？
他开始吱吱呜呜，最后承认：这个我确实只记住了 mvcc 的说法，没深入研究过不同读模式的区别。
这个回答就是我面试中最常见的，理解停留在表面，面试结束原因是他把解决幻读简单地归为 mvcc，只知其一不知其二。

面试官真正想听的是下面这三个层面的深度本质。
第一层：幻读的解法分场景，mvcc 只覆盖快照读，绝非通用答案。
很多人张口就说 mvcc 解决幻读，本质是没区分数据库的两种读模式。普通的不加锁 select 是快照读，基于事务启动时生成的一致性视图，读取的是数据的历史版本，全程不加锁，所以同一个事物内多次快照读的结果完全一致，天然不会出现幻读。
但数据库里还有当前读，select、update、delete、insert 这类操作读取的是数据的最新提交版本，还要加锁保证并发安全。这种场景下 mvcc 的历史版本就失效了，依然会出现幻读风险。innodb 的可重复读隔离级别从来不是单靠 mvcc 解决幻读，而是双轨制，快照读靠 mvcc 保证一致性，当前读靠 next key lock 锁范围防插入，两者分别对应不同的读写场景，缺了任何一个都不完整，只知道 mvcc 等于只懂了一半。
第二层：next key lock 是当前读防幻读的核心，间隙锁才是精髓，只靠行锁永远解决不了幻读。
因为行锁只能锁住已经存在的数据行，管不了还没插入的新数据。幻读的本质恰恰是新增数据落在了查询范围内。innodb 的解法是邻间锁，它由记录锁和间隙锁两部分组成。记录锁锁具体的索引行，间隙锁锁两个索引值之间的空隙，两者组合成左开右闭的区间锁。
比如查询 id=10 的行，加间隙锁会锁住从 10 到正无穷的整个索引区间，区间内所有空隙都不允许插入新数据，从根源上堵住了新增数据的可能，自然就不会出现幻读。这也是 rr 和 rc 隔离级别的核心区别，rc 级别只有记录锁没有间隙锁，并发症更高，但当前读会出现幻读。rr 级别引入间隙锁，牺牲了一部分并发性能，换来了当前读下的无幻读。没有谁绝对更好，本质都是一致性与性能的权衡。
第三层：面试官想听的是边界认知与工程选型思维，而不是只会背概念。
当你说完两类场景和两套解法后，面试官会考察你对隔离级别的深层次理解。这时你要能说出 rr 级别也不是绝对没有幻读，它存在非常明确的边界场景。当事务内混合使用快照读和当前读时，就会出现幻读现象。
比如事务内先做快照读，得到十条数据，另一个事务插入新数据并提交，当前事务再执行 update 更新所有符合条件的数据，会意外更新到十一条。但当前读已经能读到十一条，这就是典型的幻独特例。生产环境更关键的是选型能力，很多互联网团队会主动把默认隔离级别从 rr 改成 rc，就是因为间隙锁会大幅增加锁冲突和死锁概率，而绝大多数业务场景能接受不可重复读和极少数幻读，换来更高的并发性能。
真正的工程师不是死记标准级别，而是能根据业务的一致性要求和并发压力选择最合适的隔离级别，同时做好对应的兜底校验。这个就叫专业。
最后来播灵魂总结：下次面试官问 mvcc 怎么解决幻读，别再脱口而出 mvcc，你要先说解法分场景，快照读靠 mvcc 的一致性视图，当前读靠 next key lock 锁范围，双机制配合才是完整方案。再说间隙锁的组成与本质，用间隙锁堵插入空隙，用锁范围扩大换一致性，这也是 rr 和 rc 的核心区别。最后延伸到隔离级别的选型权衡，rr 不是银弹，rc 更适合高并发场景，懂边界会取舍才是核心能力。这才是大厂面试官想要的深度。
