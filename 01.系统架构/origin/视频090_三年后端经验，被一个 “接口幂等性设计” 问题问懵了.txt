三年后端经验，被一个 “接口幂等性设计” 问题问懵了… #java #java 面试 #后端 #后端开发 #程序员
你说你做过支付、订单这类核心业务系统，那我问你，用户网络不好，重复点提交，接口超时重试，MQ 消息重复消费，都会导致同一条业务请求执行多次，你的后端怎么从架构层面保证接口幂等，不会出现重复下单、重复扣钱？
今天刚面了一个三年经验的后端，我问他幂等性设计，看似基础，但要考虑高发冲突、分布式场景、状态流转、重复消息、防重、失效等场景，从数据库唯一约束到 token 机制怎么设计？
他想了一下说：给接口加个唯一请求号，数据库建个去重表加唯一索引，请求进来先插去重表，插成功就执行业务，失败就直接返回成功，保证只执行一次。
我顺着他的话说：高发下，同一个请求同时打进来，都去插去重表，会不会出现锁竞争甚至死锁？去重表数据越来越多，几百万条之后查询、插入性能越来越差，怎么清理？如果是 MQ 消息重复消费，每条消息都去查一次数据库做去重，消费性能直接腰斩。
如果业务是状态机流转，比如订单从待支付到已支付，只能流转一次，重复请求过来要怎么处理？光靠唯一锁也能挡住状态错误流转吗？如果是前端重复点击提交，除了后端作幂等，有没有全链路的防控方案？如果网络重传、网关重试，导致同一个请求被发了多次，怎么在入口层就拦截掉？
有没有考虑过不用去重表的幂等方案，比如乐观锁、状态机，它们各自的适用场景和局限性是什么？如果幂等机制本身失效了，比如去重表挂了，怎么保证业务数据不出问题？
他瞬间慌了，说：可以给去重表加锁，优化性能。然后说：不行的话就让前端按钮置灰，不让用户重复点。
但问到高并发去重、优化状态机、幂等、全链路防控体系，完全没思路。面试到这里基本就可以结束了，这正是只会唯一索引和能设计全链路幂等体系的关键分水岭。很多人以为建个去重表加个唯一索引就解决了幂等性，但一遇到高发冲突、状态流转、错误消息重复消费、去重机制失效这些真问题就崩了。
如果这道题目你也不会回答，我整理了让大厂面试官沉默的必考题库，包含 java 基础、jvm 夺命连环问、spring 全家桶、mybatis、redis、微服务、分布式实战等等。只要是我粉丝，留下 pdf 直接打包带走。
面试官问这个问题考察的不是你知不知道唯一索引，而是你在任何重复请求场景下都保证业务数据正确、不重、不脏。真正能通过面试的幂等性设计必须吃透三层核心逻辑。
第一层，先明确幂等性的定义和高频失效场景。
幂等不是简单的去重，而是同一条业务请求执行一次和执行 n 次结果完全一致。前端重复点击、网络超时重试、网关重发、MQ 消息重复投递、服务降级、重试、接口恶意重放都会导致重复执行。
唯一索引冲突导致接口报错、体验差、高并发引起去重带来数据库锁竞争、状态机乱序导致业务数据错误、去重表无限膨胀、性能下降、去重组件故障导致幂等防线全面失守。
第二层，选一套分级防控的核心方案落地多种场景，以入口拦截加业务层幂等加数据层兜底为全链路，按需求匹配不同业务场景。
入口层防控，前端按钮置灰加请求防重 token。网关层按请求号做短时效去重，缓存几秒内的重复请求直接拦截，挡住绝大多数重复提交。
业务层幂等，写操作优先用状态机实现，严格控制状态流转顺序，只有前置状态正确才允许执行更新。利用数据库索引保证状态变更原则性，无状态流转的场景用唯一请求号加去重表配合 redis 做前置缓存拦截，减少数据库压力。
数据层兜底，核心业务表增加唯一业务主键，从数据库层面彻底杜绝重复数据，作为最后一道防线。
MQ 消费场景用业务主键做幂等，配合 redis 布隆过滤器快速过滤已消费消息，降低数据库查压。
第三层，生产落地的异常处理与高效优化细节。
高并发优化，去重操作先查 redis 再查数据库，redis 拦截绝大多数重复请求。去重表按日期分表，定期清理历史数据，保证单表性能。
状态机幂等优化，更新语句加状态条件，通过影响行数判断是否执行成功，天然原子性。
故障兜底，redis 去重失效时降级为数据库唯一索引兜底，去重表故障时降级为状态机加业务主键约束，保证任何一层挂掉都不会出现脏数据。
监控重复请求拦截量、幂等冲突次数、去重表性能、状态流转异常率，设置多级阈值自动告警。如果幂等体系整体故障，先关闭自动重试机制，减少重复请求，同步启动数据对账任务校准脏数据，优先保证核心业务数据正确。
这个就叫专业。
讲到这里大家就明白了，面试官问接口幂等性根本不是考你会不会加唯一索引，核心考察三点：能不能识别前端重试、网络重传、消息重复等全链路重复场景，知不知道状态机、token、去重表、乐观锁等方案的适用边界，有没有分级防控、故障兜底、性能优化等工程落地经验。
普通后端只会加去重表建唯一索引，出问题，只会让前端按钮置灰。大厂后端能徒手设计一套入口、业务、数据全链路的幂等防控体系，扛得住重复提交、消息重投、高并发冲击，兼顾性能与数据准确性。
