面试官：Redis 大 Key 怎么处理？#java #java 面试 #后端 #后端开发 #程序员
最近面了一个四年后端开发，我问他 redis big key 怎么处理？他脱口而出：拆分、集合、压缩 value、定期清理，控制住内存占用就不会有问题。
我点点头，笑着问了个线上真实缓存雪崩事故。
假设你们大促预热，运营批量导入了一批活动优惠券，用一个 hash key 统一存了几十万条用户券数据，平时查询量不大，一直没出问题。可活动开场后，领券接口响应突然陡增，redis 单节点 cpu 飙升到百分之百，大量请求超时，连带下单链路也跟着卡顿。
你紧急想删这个 big key，重建结果，一条 demo 命令下去，redis 直接堵塞了近三秒，整条缓存链路短暂瘫痪，差点引发全链路雪崩。你排查发现，不只是删除慢，这个 key 的读写、过期、扩容、迁移都会拖慢整个节点，可平时根本没人留意到它的存在，问题出在哪？
他想了想说：应该提前拆分 big key。
我追问：线上几百 g 缓存，上千万个 key，你怎么提前精准找出所有隐藏的 big key？而且就算拆了 big key，过期、删除、集群迁移时照样会引发堵塞，你怎么从根源规避？难道全靠人工巡检，一个个找？
他就开始吱吱呜呜。
面试到这就结束了，这正是 redis big key 最隐蔽的幽灵陷阱。你以为 big key 只是多占点内存，却没想到 big key 的读写、删除、过期、迁移都会引发单点堵塞，平时悄无声息，峰值期一触发就是整条缓存链路的故障。
如果这道题目你也不会回答，我整理了让大厂面试官沉默的必考题库，包含 zookeeper、基础 jvm、夺命连环问、spring 全家桶、mybatis、cark、redis、微服务、分布式实战等等。只要是我粉丝，留下 pdf，直接打包带走。
为什么这个问题能筛出高手？因为它考察的不是会不会拆分 big key，而是有没有全生命周期视角下的缓存治理思维。一个能稳住缓存集群的后端必须建立三层防御。
第一层：业务分级，源头管控，写入规范。核心高频访问数据严格控制 value 大小，stream 类型不超过十 kb，集合类型控制元素数量，超过值域强制拆分，批量数据禁止单 key 打包存储，按业务维度拆分为多个小 key 或改用存储型数据库。写入侧增加大小校验，超过值域的 big key 直接拦截告警，从写入端杜绝 big key 生成。非核心冷数据不强行放入 redis，转存至 mongdb 或对象存储，避免冷数据 big key 占用缓存资源。
第二层：巡检兜底与平滑处理，部署常态化 big key 扫描机制，低峰期定期全量巡检，实时监控 big key 的内存占比、访问频次、异常自动告警。big key 删除采用渐进式分批删除，不直接执行 del 命令，避免单命令阻塞整个实例。big key 过期时间增加随机偏移，避免集中过期引发批量删除卡顿。针对高频访问的大集合拆分为多个小 key 分片存储，把单节点压力分散到整个集群。
第三层：架构层优化，从根源降低堵塞风险。缓存集群提前做好节点均衡，避免 big key 集中在单节点引发数据倾斜与性能瓶颈。核心集群开启 big key 异步删除机制，释放主线程压力。大促等重大活动前开展专项 big key 治理，提前清理、拆分历史遗留 big key，完成全量风险巡检。极端峰值场景配置 big key 降级开关，异常 big key 自动切走缓存，直查数据库或降级返回，宁可牺牲部分查询性能也决不允许单个 big key 拖垮整个缓存集群。
这个就叫专业。
所以这道题考的是什么？它考的是你有没有从遇到 big key 再拆分，升级为设计全生命周期 big key 治理体系的工程思维。普通开发以为 big key 只是占点内存的小问题，而高级工程师知道在高并发场景面前，big key 是一把双刃剑，一个不起眼的 big key 就可能成为引发缓存集群全线堵塞的导火索。
