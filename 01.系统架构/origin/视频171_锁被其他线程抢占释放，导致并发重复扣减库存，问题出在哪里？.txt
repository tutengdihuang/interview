刚面了个 5 年后端，我问他：分布式锁怎么实现？
他脱口而出：用 Redis 的 setnx 加过期时间防止死锁，简单又好用。
我点点头，笑着问了他一个真实发生的线上事故。
假设电商秒杀场景，用户抢购爆款商品，服务用 Redis 分布式锁控制库存扣减，结果出现大量超卖，主库库存直接扣成负数，商家被迫紧急下架商品，用户投诉直接炸锅。
你查日志发现，锁已经过期但业务逻辑还没执行完，锁被其他线程抢占释放，导致并发重复扣减库存。
他想了想，可能是锁超时提前释放了。
我追问：那怎么保证锁不被误释放，彻底杜绝超卖？难道不设过期时间？
他开始支支吾吾，面试到这就结束了。
这正是分布式锁的幽灵陷阱。你以为加个锁就能解决并发问题，却没考虑锁超时、误删、重入带来的一致性风险。

为什么这个问题能筛出高手？因为它考察的不是会不会写锁命令，而是有没有深入理解分布式锁在高并发下的一致性与可靠性挑战。
一个能驾驭分布式锁的后端，必须建立三层防御。
・第一层：锁机制优化，保证加锁安全。
锁绑定唯一标识：加锁时存入线程唯一 ID，解锁前校验归属，只允许释放自己的锁，杜绝误删。
锁自动续期：启动守护线程，锁即将过期时自动延长有效期，避免业务未执行完锁失效。
可重入锁设计：同一线程支持重复加锁，防止嵌套调用死锁，适配复杂业务链路。
・第二层：兜底与容错，避免锁失效引发故障。
锁降级方案：Redis 锁故障时，切换为数据库悲观锁兜底，保证核心链路不崩。
库存预校验：扣减前双重校验库存，即使锁失效也能拦截无效扣减。
幂等控制：结合请求唯一 ID。
・第三层：架构层升级，提升分布式锁可靠性。
集群高可用：用 Redis Cluster 或 Redlock，避免单节点故障导致锁服务不可用。
异步解耦：秒杀请求接入消息队列削峰，从源头降低并发锁压力。
开关控制：核心场景支持手动开启强制单机锁，牺牲部分性能换一致性。
这个就叫专业。
所以这道题考的是什么？它考的是你从简单 API 调用升级为分布式并发安全方案的工程思维。
普通开发以为分布式锁就是加个 setnx，而高级工程师知道，在高并发一致性面前，分布式锁是一套完整的安全体系。
