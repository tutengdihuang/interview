你以为用 Redis 缓存就能杜绝数据库雪崩？
刚面了个四年后端，简历上写着精通缓存设计，能应对高并发缓存场景。
我随口问了个基础题：一个电商首页商品数据频繁被访问，怎么避免数据库被压垮？
他脱口而出：用 Redis 缓存商品数据，设置过期时间，查询先查缓存，缓存 miss 再查数据库，简单高效。
我点点头，接着抛了个让他瞬间语塞的场景：如果首页上千种商品的缓存同时过期，恰逢大促高峰期百万用户同时访问，缓存全部 miss，所有请求瞬间打向数据库，数据库直接崩掉，整个首页无法访问，你怎么解决？
他想了想说：那就延长缓存过期时间或者给缓存加锁。
我再追问：延长过期时间会导致数据不一致，加锁会造成请求阻塞响应变慢，而且如果 Redis 本身宕机，所有请求还是会穿透到数据库，你怎么做到双重兜底？
他皱着眉沉默不语，面试到这就结束了。
这正是缓存设计的常见误区：以为用了 Redis 就万事大吉，却忽略了缓存过期、缓存宕机、缓存穿透带来的连锁风险。很多后端开发只会简单使用缓存，却没掌握缓存的容错设计和风险防控逻辑。
如果这道题目你也不会回答，我整理了让大厂 HR 沉默的必考题库，涵盖：JVM 夺命连环门、Spring 灵魂八股、高并发必杀场景、Redis 深度陷阱等等。
为什么这道题能区分普通开发和资深后端？因为它考察的不是会不会用缓存，而是面对高并发场景有没有完整的缓存容错思路和数据库保护方案。
一个能扛住大促高并发的缓存设计必须做好这三层防护。
第一层：缓存过期错开，避免集中失效。给不同商品的缓存设置随机过期时间，避免上千个缓存同时过期，分散数据库压力；同时给热门商品设置永不过期，定期后台异步更新，保证数据一致性。
第二层：缓存降级 + 限流兜底。当 Redis 宕机或缓存命中率极低时，启动降级策略，返回兜底数据 (如热门商品默认列表)，不直接穿透到数据库；同时对数据库查询做限流，限制每秒请求数，防止数据库被瞬时流量击垮。
第三层：多级缓存 + 穿透防护。搭建本地缓存 (Caffeine)+ 分布式缓存 (Redis) 的多级缓存架构，减少 Redis 访问压力；用布隆过滤器过滤不存在的商品 ID，杜绝缓存穿透，避免无效请求打向数据库。
所以这道题考的是什么？考的是你有没有从 "单纯使用缓存" 跳出，建立缓存与数据库的协同防护思维。普通开发会用 Redis 减轻数据库压力，而高级工程师知道缓存的核心不是 "加速查询"，而是在高并发下如何保护数据库不崩，同时保证系统可用数据一致。
