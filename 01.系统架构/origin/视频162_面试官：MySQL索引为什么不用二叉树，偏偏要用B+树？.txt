面试官：MySQL 索引为什么不用二叉树，偏偏要用 B + 树？
#java #java 面试 #java 面试题 #后端 #后端开发
最近面了一个三年经验后端开发，简历写着精通 MySQL 索引原理、慢查询优化、底层数据结构。我上来就抛了一道经典高频题：我们都知道 MySQL InnoDB 引擎索引用的是 B + 树，那为什么放着简单的二叉树不用，非要设计成 B + 树？二叉树不是逻辑更简单、理解更容易吗？
他自信满满地回答：因为二叉树高度太高、查询慢，B + 树高度低磁盘 IO 少。
我点了点头接着追问：既然二叉树太高，那平衡二叉树 AVL、红黑树不也能平衡高度吗？为什么不用红黑树做索引？而且数据库数据都是存在磁盘里的，每次查询都要磁盘页加载。你真的懂 B + 树适配磁盘存储的核心逻辑吗？
他瞬间卡壳，绕来绕去只重复高度低 IO 少，说不出底层本质区别，也讲不清磁盘页、页分裂、页合并这些关键点。最后只能坦言：平时只会用索引、建索引，底层数据结构没深究过。
其实这也是绝大多数后端的通病，只记表面结论，不懂底层设计思想，面试一被深挖连环问就直接翻车。假如这道题目你也不会回答，我整理了让大厂 HR 沉默的必考题库，包含：JVM 夺命连环问、Spring 灵魂八股、高并发必杀场景、Redis 深度陷阱等等。只要是我粉丝，留下 "666" 打包带走。
面试官真正想听的是这三层核心深度逻辑：
本质一：磁盘 IO 与页存储的适配。数据库数据和索引都存在磁盘，磁盘读写按磁盘页为单位加载。
二叉树、红黑树每个节点存储数据少、分支少，树的高度会很高；查询一条数据要频繁多次磁盘 IO 寻址，速度极慢。
而 B + 树是多路平衡搜索树，一个节点可以存大量索引键和数据指针，树的高度极低，通常三四层就能存放千万级数据，一次查询只需要 2‑3 次磁盘 IO，极大减少磁盘寻址开销。
本质二：遍历范围查询天然优势。后端开发中大量业务都是范围查询、模糊查询、分页查询。二叉树、红黑树只能逐个节点遍历，效率极低；而 B + 树所有数据都在叶子节点，叶子节点用双向链表串联，范围查询、分页、全表扫描只需要顺着链表遍历即可，不需要来回跳转树节点，范围查询性能碾压其他树结构。
本质三：非叶子节点只存索引、不存数据。B + 树非叶子节点只存索引键和子节点指针，不存完整行数据，相同磁盘页大小下能存放更多索引条目，进一步压低树的高度，让每次磁盘加载能拿到更多索引信息，查询效率拉满。
最后灵魂总结：下次面试官问你 MySQL 索引为什么用 B + 树不用二叉树、红黑树，别只说高度低、IO 少。要完整答出三点：
1. 适配磁盘页存储，多路节点降低树高度，减少磁盘 IO 次数；
2. 叶子节点双向链表，完美适配范围查询、分页遍历；
3. 非叶子节点只存索引不存数据，节点利用率更高，树高更矮。
这样回答才是大厂面试官认可的专业水平。
