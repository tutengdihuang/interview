面试官：MySQL 深分页还只会用 ID 游标？
今天面了一个高级后端开发，简历上写着精通 MySQL 性能优化，并有千万级数据量查询调优经验。
我上来就抛了个高频场景：我们都知道 MySQL 大表，深分页性能差，比如 limit 十万，越翻越慢。你一般怎么优化？
【候选人】：因为 offset 越大，MySQL 要扫描的无效行数越多。前面十万行都得扫一遍再扔掉，所以慢。优化就用主键游标法，改成 where id>100000 limit 10，走主键索引直接定位，跳过前面那行，性能提升几十倍都不止。
我点了点头。但马上追问：你说的游标法是基础方案？如果排序字段不是主键，还有多维度筛选条件，id 不是连续有序的，甚至业务要求支持用户跳页，拿不到上一页的最后一个 ID，这个方案还能用吗？
【候选人】（愣了一下）：可以给排序字段加索引，用排序字段做游标。
我追问：如果筛选条件是动态的，有十几个可选查询维度，不可能每个组合都建联合索引怎么办？如果表用的是雪花 ID 或者 UUID，业务上还有按状态，按时间倒序等多种排序规则，你要做多少个游标方案？还有运营后台经常要直接跳第几百页。这种场景游标法是不是直接失效？
【候选人】（开始支支吾吾）：那可以把数据同步到 es，用 ES 做分页就没这个问题了。
我又追问：引入 ES 的运维成本，数据一致性、延迟怎么算？如果就是单表 MySQL 查询，不允许加外部组件，还有没有通用的优化手段？
【候选人】：这些极端场景我确实没深入研究过，平时项目里游标法基本够用。
旁白：这个回答就是我面试中最常见的，理解停留在表面。面试结束的原因是他把深分页优化，简单地归因为 limit、offset 慢、用 ID 游标就行，完全没考虑方案的适用边界和复杂业务场景。
面试官真正想听的是下面这三个层面的深度本质：
深分页慢的根源，不是扫描行数多，是
无效扫描 + 频繁回表的双重损耗
。
通用场景的进阶方案：
延迟关联 + 覆盖索引
，减少回表 n 次。
当游标法不适用，比如跳页、动态筛选、多排序，工业界最通用的优化手段是延迟关联。
核心思路是：先利用覆盖索引在二级索引里查出需要的主键。这一步只扫索引，不需要回表，数据量再大也很快。再用主键 id 关联回表，只需要回表 n 次。
讲完延迟关联之后，要说出不同方案的适用边界，而不是只会一个方案套所有场景：
百万级以内的表，原生 limit 完全够用，没必要过度优化。
千万级单表，顺序翻页的 C 端场景，优先用游标；
多条件筛选，需要跳页的场景，用延迟关联加覆盖索引；
E 级数据、复杂多维查询，再考虑引入 es 等查询引擎。
还要点出一个核心误区：不是所有深分页都要优化。比如后台运营系统一个月才翻一次几百页，性能差点完全不影响，没必要为了低频场景引入复杂架构。真正要重点优化的是 C 端高频访问的列表分页。
灵魂总结：下次面试官问 MySQL 深分页优化，别再脱口而出用 id 游标代替 limit。
你要先讲深分页慢的本质是无效扫描加回表双重损耗，再讲延迟关联加覆盖索引的通用优化方案，最后拔高到不同数据量，不同业务场景的选型逻辑。这才是大厂面试官想要的深度。
