MySQL 中 type 为 ref、key 也对了，但查询依旧缓慢？
#后端开发 #程序员 #面试 #后端面试 #程序员面试
面了一个四年经验的后端，我问他慢查询怎么优化，他张口就是加索引，看 explain 走没走，我点点头，随即抛了个真实业务场景：订单查询页，按 user_id+create_time 范围筛选，建了 user_id_create_time 联合索引。explain 里 type 是 ref，key 也标了走索引，可线上查询还是慢，硬是要好几秒。问题出在哪儿？
他想了想说可能是数据量大，回表多。
我追问怎么确认是回表导致的？explain 的 rows 是预估数，用什么工具看真实扫描行数和回表次数？
他愣了一下，这可能看慢查询日志。
面试到这就结束了，其实这道题就是区分会用索引和懂索引的试金石。为什么这个问题能筛出高手？因为它考察的不是会不会加索引，而是有没有深入到索引执行细节的排查能力。
假如你对这道题目也不会回答，我整理了让面试官沉默的大厂必考题库，包含 jvm 夺命连环问、spring 灵魂八股、高并发必杀场景、redis 深度陷阱等等。只要是我粉丝点个赞，六六六打包带走。
很多开发者看到 explain 显示走索引就觉得万事大吉，却不知道走索引和高效走索引性能能差几万倍。真正能搞定慢查询的工程师都有这三层核心认知。
第一层：读懂执行计划的底层细节，别被 type 等于 ref 迷惑，const/eq_ref/ref 才是真正的高效匹配。range 有时比 ref 更快，关键看扫描范围。explain 的 rows 是抽样预估，误差能到十倍，真实扫描行数得靠 show profile 或 performance_schema 查。extra 列，更是重中之重。Using temporary，Using filesort 一出现就意味着临时表和文件排序，性能必受影响。
第二层：做线上执行的量化分析，慢查询日志要开全量，不光记耗时，还要盯 rows、examined 和 rows_sent。扫描十万行只返回十行就是索引过滤性太差。performance_schema 是硬核神器，查 events_history_long 能精准拿到真实耗时，锁等待、扫描行数和回表次数。想知道优化器为啥选这个索引，打开 optimizer_trace 看它的成本计算过程，根源一眼看穿。
第三层：从诊断到根治，找对最优解。覆盖索引是解决回表的终极方案，把查询需要的字段都纳入索引，省去回表步骤，性能直接翻倍。MySQL5.6 加的索引下推要利用好，在索引层就过滤掉不符合时间范围的数据，减少无效操作。前提是联合索引顺序要合理，等值筛选在前，范围筛选在后。复杂查询别硬刚，拆分两步更高效。先用索引查主键 id，再用 id 批量查明细，主键查询的效率远超想象。
说到底，慢查询优化从来不是简单的加索引，而是从执行计划到线上数据，一步步抽丝剥茧的破案过程。普通开发者停留在会不会用，而高级工程师胜在懂底层，能量化，会根治。
