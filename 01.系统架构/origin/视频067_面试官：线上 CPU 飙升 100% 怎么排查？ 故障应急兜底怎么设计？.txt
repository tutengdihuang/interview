面试官：线上 cpu 飙升 100% 怎么排查？故障应急兜底怎么设计？
今天刚挂了一个三年经验的后端开发，我问他：你们项目高峰期服务 cpu 突然打满，接口全线超时，你们都是怎么排查根源的？
他直接说：top 看一下进程，jstack 打线程栈，找到耗时代码改就行。
我再追问：线上机器不能随便打栈，不能重启，怎么快速止损？死循环和频繁 full gc 导致的 cpu 飙高怎么快速区分？流量洪峰导致的 cpu 饱和怎么分级降级？你遇到过的 cpu 打满引发的全链路雪崩事故能不能划个时间线还原一下？
他瞬间愣住了，迟疑了半天说：目前只能靠扩容和重启服务保底。
面试到这里基本就可以结束了，这正是普通后端和高级后端的核心分水岭。它考察的不是会不会打线程栈查问题，而是线上故障场景下的风险识别与应急防御性设计的核心能力。如果这道题目你也不会回答，我整理了让大厂面试官沉默的必考题库，包含 java 基础、jvm 夺命连环问、spring 全家桶、mysql、redis、微服务、分布式实战等等。只要是我粉丝，留下 pdf 直接打包带走。
很多后端开发者都有一个误区，觉得能定位到耗时代码就是会排查线上问题，但大家忽略了一点，本地复现问题和生产环境下的应急止损与长效治理完全是两个技术维度，不能混为一谈。一个能达到高级后端要求的工程师必须具备三层核心认知。
第一层：故障排查方案的深度拆解与对比。常见的 top、jstack、jstat、arthas、perf、火焰图工具不能停留在背诵阶段，要拆解它们各自在无侵入、排查线程状态、分析内存问题、定位内核态消耗场景下的优缺点，重点核查排查命令是否基于影响最小化原则选择，而非直接重启或全量打栈。
第二层：故障风险量化分析，拒绝凭感觉说：找到问题改了就行。重点看故障平均恢复时长、根源定位耗时、故障影响范围、年度故障频次，核心业务场景逐一核对。cpu 打满后的止损策略是先摘流量还是先扩容？故障扩散引发雪崩的风险有多高？核对是否需要建立故障分级响应机制，加全链路监控告警，构建从发现到止损再到根源定位的完整闭环。
第三层：线上故障架构的落地规范。建立线上操作准入标准，制定严禁执行的高危命令列表，划定 cpu 使用率告警红线、故障响应时长红线，实现全链路指标实时监控与秒级告警。借助可观测平台批量排查性能瓶颈与风险点，建立分级故障应急与定期演练机制。
针对订单支付、库存扣减、用户资产等金融级核心链路，沉淀团队的故障复盘知识点与防御性编码约束，形成提示词，喂给 ai，让 ai 生成的代码从源头上就内嵌故障风险防护。禁止将任何无压测、验证、降级、预警的代码直接上线。
这个就叫专业。这道题的核心就是从会用排查工具找 bug 升级为能守护线上服务的稳定性底线。普通后端觉得找到问题改完代码就行，高级后端会从故障止损速度、根源定位效率、业务容忍度、极端故障下的分级降级等维度做全方位设计。
