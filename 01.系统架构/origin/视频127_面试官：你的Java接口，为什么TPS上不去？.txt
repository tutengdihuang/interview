面试官：你的 Java 接口，为什么 TPS 上不去？
#java #java 面试 #后端 #后端开发 #程序员
刚挂了一个做交易系统的 java 开发。
我问：你们的核心交易接口压测时 TPS 到一千就上不去了，但 CPU 和内存都没打满，你怎么系统性的定位瓶颈？
他说：可能是数据库连接池不够或者缓存没生效。
我追问：你怎么验证是 IO 问题还是 CPU 问题？如果是锁竞争怎么找到热点锁？如果是序列化问题怎么证明并优化？
直接给他干沉默了，回答不上来。面试到这就结束了。
高并发接口调优需要从外到内层层深入，掌握四个关键层次。如果这道题目你也不会回答，我整理了让大厂 HR 沉默的必考题库，包含 java 基础、jvm 夺命连环问、spring 全家桶、mybatis、redis、微服务、分布式实战等等。只要是我粉丝，留下六六六打包带走。
第一步，建立全链路监控体系。
应用层 micro meter 加 prometheus 监控 qps、rt、错误率；
jvm 层 gc 频率、线程状态、堆外内存使用；
系统层 cpu 利用率、io 等待、网络流量；
中间件层数据库连接池使用率、redis/rabbitmq 的响应延迟。
第二步，识别瓶颈类型。
cpu 瓶颈使用 arthas profiler 或 icem profiler 抓取火焰图，看热点方法、锁竞争；
jstack 查看线程阻塞状态或用 arthas thread‑b 找死锁；
IO 看 iowait 指标或数据库慢查询日志；
网络瓶颈跟踪 tcp 重传率、连接数限制。
第三步，针对性优化策略。
减少锁力度，用 ConcurrentHashMap 代替 Hashtable，用 LongAdder 代替 AtomicLong；
异步化处理，CompletableFuture 实现非阻塞调用，避免线程池阻塞；
序列化优化，用 protobuf 代替 json 或用 kryo 提升序列化速度；
连接池调优，调整 hikari 的最大连接数、空闲超时时间。
第四步，压测验证与极限优化。
阶梯式压测，从低到高逐步增加并发，观察拐点；
全链路压测，使用分布式压测工具模拟真实流量分布；
极限优化，考虑无锁数据结构、堆外内存、零拷贝等技术。
这个就叫专业。
这道题考察的是对性能瓶颈的系统性分析能力和全链路优化思维，这是架构师的核心能力。
