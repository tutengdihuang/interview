布隆过滤器和空值缓存都已配置，那为什么还是出现了缓存穿透？#java #java 面试 #后端 #后端开发 #程序员
最近面试了个四年后端，我问他 redis 缓存穿透该怎么解决？他脱口而出用布隆过滤器拦截、缓存空值，再限制下非法请求就够了。我点点头笑着问了他一个真实发生的线上事故。
假设电商商品详情页用 redis 缓存商品信息，开发配置了空值缓存和布隆过滤器，用来防止缓存穿透。结果某时段有黑客批量伪造不存在的商品 id，疯狂请求商品详情接口，布隆过滤器未拦截所有非法 id，空值缓存也被频繁覆盖，大量请求直接穿透，打到 mysql 数据库。数据库连接池被打满，cpu 飙升到百分之一百，核心接口全部超时，正常商品详情也无法访问，平台损失惨重。
已经确认布隆过滤器和空值缓存都已配置，为什么还是出现了缓存穿透？
他想了想说可能是布隆过滤器配置不对，说不出具体排查和根治办法。
我追问：怎么全方位拦截非法请求，彻底杜绝缓存穿透，既保护数据库又不影响正常业务访问，难道只靠布隆过滤器和空值缓存就够了？
他开始吱吱呜呜，面试到这就结束了。
这正是 redis 缓存穿透的幽灵陷阱。你以为背两个基础方案就能应付，却忽略了布隆过滤器误判、空值缓存失效，恶意请求绕过带来的隐性风险。
假如这道题目你也不会回答，我整理了让大厂 hr 沉默的必考题库，包含 jvm 夺命连环问、spring 灵魂八股、高并发必杀场景、redis 深度陷阱等等。只要是我粉丝，留下六六六打包带走。
为什么这个问题能筛出高手？因为他考察的不是会不会罗列缓存穿透解决方案，而是有没有深入理解缓存穿透的产生本质，高并发场景下的防护逻辑和实战落地能力。
一个能真正搞定缓存穿透的后端必须建立三层防御。
・第一层源头拦截，杜绝非法请求进入布隆过滤器。
优化合理设置布隆过滤器误判率，定期更新过滤器中的合法 id 集合，避免因 id 更新导致误判漏拦非法请求。
接口参数校验：在网关层、接口层严格校验请求参数，拦截格式错误、非法范围的商品 id、用户 id，从源头减少无效请求。
ip 限流拦截：对高频请求同一非法参数的 ip 进行限流拉黑，防止黑客批量刷量，避免恶意请求冲击数据库。
・第二层缓存防护，避免缓存失效导致穿透。
空值缓存优化：给空值缓存设置合理的过期时间，避免频繁覆盖，同时定期清理过期空值，节省缓存空间。
热点缓存永不过期：核心合法商品高频访问数据不设置过期时间，通过定时任务主动刷新，确保缓存始终有效。
缓存降级兜底：redis 故障或缓存失效时，启用本地缓存临时兜底，避免请求直接穿透到数据库。
・第三层数据库防护，最后一道安全屏障。
数据库限流：给数据库设置最大连接数和请求阈值，超过阈值则拒绝请求，避免数据库被打垮。
索引优化：给查询字段建立合理索引，即使请求穿透到数据库也能快速查询，减少数据库压力。
监控预警：实时监控缓存命中率、穿透请求数、数据库负载。一旦出现异常立即推送预警，及时介入处理，这个就叫专业。
所以这道题考的是什么？它考的是从简单配置缓存防护升级为高并发场景下缓存架构数据安全的工程思维。普通开发以为缓存穿透就是加布隆过滤器和空值缓存，而高级工程师知道缓存穿透的解决是源头拦截、缓存防护、数据库兜底相结合的完整体系，核心是预判风险，多层兜底。
