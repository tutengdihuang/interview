面试官：加了索引 SQL 还慢？别只会说索引失效了！#java #java 面试 #后端 #后端开发 #程序员
今天面了一个高级后端，简历上写着精通 MySQL 性能优化，主导过千万级数据量的库表调优项目。我上来就抛了个最基础的问题：都知道给字段加索引能加快查询速度，但很多时候明明加了索引，SQL 执行还是很慢，怎么理解这个现象？
他自信满满地回答：因为索引失效了，比如用了 like 模糊，字段上做函数运算，发生了隐式类型转换，导致优化器不走索引，所以查询就慢了。
我点了点头，但马上追问：你说的这些都是最基础的索引失效场景，那我问你，如果执行计划里明确显示走了索引，为什么查询依然很慢？难道索引本身不是万能的吗？比如一个大范围查询的 count，明明走了二级索引，为什么性能还不如全表扫描？
他愣了一下，说：应该是回表的开销太大了。
我追问：回表你知道，那我再问你，同样是走主键索引，为什么单表数据量从百万涨到千万之后，查询性能会明显下滑？难道主键索引也会失效吗？还有，为什么有时候优化器会主动放弃索引，选全表扫描？它的判断依据是什么？
他开始支支吾吾，最后承认：这个我确实没深入研究过索引的底层代价模型。
这个回答就是我面试中最常见的，理解停留在表面。面试结束原因是他把 count 慢的原因简单的归因为没加索引，索引失效。如果这道题目你也不会回答，我整理了让大场面试官沉默的必考题库，包含 Java 基础、JVM 夺命连环问、Spring 全家桶、MyBatis、Redis、微服务、分布式实战等等。只要是我粉丝，留下 pdf，直接打包带走。
面试官真正想听的是下面这三个层面的深度本质：
第一层，索引的核心价值是减少磁盘 io，但走索引不等于少 io，索引生效只是第一步，真正决定性能的是扫描的行数和回表的代价。二级索引只存索引列和主键，查询完整数据需要回表做随机 io。当范围查询命中大量行时，随机 io 的总开销甚至会超过顺序读取的全表扫描，这也是优化器用索引的核心原因。基于成本的优化模型算出来全表扫描的总成本更低，MySQL 的优化器是 cbo，成本模型，它会计算每个执行计划的 io 成本和 cpu 成本，选择总成本最低的方案，而不是有索引就一定走。很多人误以为索引是性能银弹，本质是没理解索引的核心意义是降低磁盘 io 次数，而不是加了索引就一定快。
第二层，单表数据量的瓶颈与索引的性能天花板。为什么行业里普遍说单表不要超过千万级？本质是索引的高度限制，主键索引的索引高度通常在三层左右，一次主键查询只需要三次磁盘 io。当数据量破亿，树高涨到四层，单次查询的 io 次数直接翻倍，性能就会出现断崖式衰减。更关键的是二级索引，单表数据量越大，普通索引的区分度就越低，相同查询条件，扫描的行数就越多，回表的代价呈指数级上升。这也是大表要做分库分表的底层逻辑，不是 MySQL 存不下更多数据，而是索引的性能天花板到了。
第三层面，面试官想听的是生产环境慢查询的完整排查思路。当你说完索引成本模型和索引高度后，面试官会考察你解决实际问题的能力，这时你要能说出真正拖垮 MySQL 的不是有没有索引，而是全表扫描、文件排序、临时表这三类重载操作。除了索引本身，还有很多更容易被忽略的性能瓶颈，比如连接数打满导致的线程排队，缓存命中率低导致的频繁磁盘读，大事务引发的锁等待，MVCC 对应的内存占用膨胀。这些才是生产环境中更常见也更致命的慢查询根源，这个就叫专业。
最后来播灵魂总结：下次面试官问你加了索引为什么还慢，别再脱口而出索引失效，你要先说索引的本质是降低磁盘 io，走索引不一定快，核心看扫描行数与回表代价。再说索引的高度决定了单表的性能天花板，千万级是行业经验预估值。最后延伸到生产环境的完整排查维度，从执行计划到服务器资源，再到事务锁机制，这才是大厂面试官想要的深度。
