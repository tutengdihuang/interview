数据库连接池爆满！系统瞬间雪崩一个参数差点搞垮整个电商大促！#java#java 面试 #后端# 后端开发 #程序员
最近面了一个五年后端开发，简历上写着主导过数据库连接池优化。我随手问了个真实线上事故，大促期间订单系统的接口突然大面积超时，监控发现数据库连接池被打满，活跃连接数百分之百，新的请求全部排队等待，最后直接雪崩。问题出在哪里？
他自信回答：先加连接池的最大连接数，再查一下是不是有慢 sql、锁、索引，然后把长事务拆短。
我点点头继续追问：如果加了连接数，数据库 cpu 没高，连接池还是很快爆满，怎么定位是连接泄露、死锁还是事务没及时释放？用什么工具看连接池内部状态？
他想了想说：可以用 show processlist 看数据库连接，看看是哪些接口慢，也可以查应用日记里的连接获取超时。
我接着问：如果发现连接池在高峰期频繁创建和销毁连接，导致性能抖动，怎么优化？连接池的空闲连接数、最小空闲时间、最大生命周期这些参数怎么设置？
他开始背八股：可以调大最小空闲连接，减少创建开销。连接池一般用 hikaricp，性能好，但问到具体场景下如何结合业务、并发模型计算参数值，他就卡住了。
很多人对连接池的理解只停留在获取、最大连接数，遇到真实雪崩，连从哪下手排查都不知道。面试到此结束，五年经验还是水了点。
如果这道题目你也不会回答，我整理了让大厂 hr 沉默的必考题库，包含 java 基础、jvm 夺命连环问、spring 全家桶、mybatis、redis、微服务、分布式实战等等。只要是我粉丝，留下六六六，打包带走。
今天我花三分钟带你打一场连接池保卫战，记住这三板斧。
第一板斧：监控雷达，让连接池状态无处遁形。
别着急改代码，先上监控。应用层连接池监控、数据源中间件、数据库层 show processlist 抓取锁等待长事务、主机层网络 io、数据库 cpu、内存三层监控联动，一秒锁定真因，是链路慢、接口堆积还是死锁。记住 SOP：报警，查看连接池指标，抓取数据库现场分析，事务日志记录，绝不跑偏。
第二板斧：代码手术刀，根治连接滥用与事务黑洞。
找到问题精准下刀，事务边界优化 @Transactional，不要随意加在类上，只给真正需要事务的方法加。查询操作强制只读事务，减少连接占用时间。
连接池参数动态调优，HikariCP 的 maximumPoolSize、minimumIdle、maxLifetime 如何根据业务并发模型计算？
开启 leakDetection 连接泄露检测，自动打印泄露堆栈。数据源选型，驱动自带监控和防注入，HikariCP 性能优异，按场景选择。
第三板斧：架构重装甲，给数据库减负，让连接池轻松。
单机优化到顶了，那就升级架构，读写分离，主库扛写，从库扛读，分散连接压力。分库分表，拆库后每个库的连接池独立，从源头降低连接竞争。缓存扛读，Redis 集群扛住百分之八十读流量，数据库连接快速释放。异步化改造，请求进 mq，削峰填谷，数据库不再被瞬时洪峰冲垮。
这个就叫专业。这套从监控、代码、连接池参数、架构的全链路调优方法论，是 java 工程师从熟练到精通的必修课。
