MySQL 慢 SQL 堆积致使数据库 CPU 满载如何优化？#java #java 面试 #后端 #后端开发 #程序员
刚面了一个四年后端，我问他线上数据库出现 cpu 飙高怎么处理？慢 sql，他脱口而出：给查询语句添加索引，避免全表扫描就能大幅提升 sql 执行效率。
我点点头，笑着问了他一个真实发生的线上事故。
假设电商订单库日常访问平稳，大促高峰期多条件筛选订单的接口批量触发，部分查询字段未见索引，触发全表扫描，数据库 cpu 瞬间拉满至百分之百，所有新增订单、支付、入库接口全部堵塞，超时。事后给查询字段新增索引，简单查询恢复正常，但多字段联合查询依旧执行缓慢，索引失效问题反复出现，频繁造成数据库雪崩。
问题出在哪？
他想了想说：索引设计不合理。
我追问：从 coco 编辑、索引设计、架构层面完整治理慢查询，难道遇到查询慢就无脑给所有字段建立索引？
他开始吱吱呜呜。面试到这就结束了。
这正是后端数据库优化的幽灵陷阱。你以为新建几条索引就能根治慢查询问题，却忽略索引失效、规则不合理、ctrl 写法、冷热数据混杂带来的隐性性能隐患。
如果这道题目你也不会回答，我整理了让大厂 hr 沉默的必考题库，包含 java 基础、jvm、夺命连环问、spring 全家桶、myico、radis、微服务、分布式实战等等。只要是我粉丝，留下九九九，打包带走。
为什么这个问题能筛出高手？因为它考察的不是简单创建索引，而是从 sql 编码、索引规范、存储架构多维度落地优化方案。一名能治理数据库慢 sql 的后端必须建立三层防御。
第一层：业务分级，区分实时联机查询与离线统计查询。用户下单、订单详情、支付校验这类实时核心联机查询，优先保证 cico 高效执行，严控查询耗时在毫秒级。月度账单、数据大盘、历史报表这类海量统计查询，避开业务高峰执行，禁止直接在线主库运行。
第二层：索引与 cico 落地优化，兜底遵循最左前缀原则设计联合索引，式类型转换、字段运算、like 左模糊等破坏索引的写法禁用。select 星，只查询必要字段，深分页场景改用主键游标分页替代 limit 大偏移量查询，无用索引及时清理，避免索引过多拖累插入更新性能。复杂多表关联 sql 拆解拆分逻辑。
第三层：架构层优化，高效防控机制。搭建主从架构，实现读写分离，查询流量分流至从库，主库只负责新增、修改、热点高频查询。接入 redis 缓存，拦截重复请求，直达数据库。开启慢查询日志，配合监控系统实时抓取超时 sql，定时巡检优化。海量历史订单数据按年月分表，减小单表数据体量，从根源降低扫描开销。
这个就叫专业。
所以这道题考的是什么？它考的是你有没有从单一键索引优化升级为 sql 规范、索引设计、缓存、分库、分表一体化的数据库架构思维。普通后端遇到慢 sql 只会随意加索引，而高级后端清楚在大促高爆发、海量数据场景下盲目新建索引是一把双刃剑。
