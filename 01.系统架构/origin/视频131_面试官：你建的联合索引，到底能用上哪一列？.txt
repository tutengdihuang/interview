面试官：你建的联合索引，到底能用上哪一列？ #java #java 面试 #后端 #后端开发 #程序员
上周面试一个四年 Java 后端开发，项目里用了 MySQL，简历上写着精通 SQL 优化与索引调优。我给她出了一个看似简单的题：假设我们有一张用户表，表里有字段，我建了一个联合索引。现在执行一条 sql：select * from user where name=' 张三 ' and age=20，这个索引能生效吗？
她几乎不假思索：当然能生效了，因为 name 和 age 都在索引里，MySQL 会直接走这个索引。
我笑了笑，追问：如果我把条件换成 where age>18 and name=' 张三 '，索引还是全生效吗？
她犹豫了一下：age 是范围查询，后面的 name 可能就用不上了，但索引应该还是能用到 age 那部分。
我继续施压：你说的对，范围查询后面的列确实可能用不上，那我现在把条件换成 where name=' 张三 ' and age>18，这次我先写 name 条件，后写 age 条件，顺序变了，所以的生效情况会变吗？
她愣住了，明显开始纠结：这个好像顺序变了所以会失效。
我追问：为什么？联合索引不是遵循最左前缀原则吗？你把 name 写在前面，但索引第一个字段是 age，这不就相当于没有从最左边开始匹配吗？
她开始吱吱呜呜，最后承认：这个我确实把最左前缀理解成了 SQL 语句的书写顺序。
这个回答就是面试中最常见的理解停留在表面。这位候选人被问住是因为他把最左前缀原则简单地理解成了 SQL 条件的书写顺序。如果这道题目你也不会回答，我整理了让大厂 hr 沉默的必考题库，包含 Java 基础、JVM 夺命连环问、Spring 全家桶、MySQL、Database、微服务、分布式实战等等。只要是我粉丝，留下六六六打包带走。
面试官想听的是下面这三个层面的深度：
本质一：索引的本质是 B + 树，不是哈希表。
很多人以为索引就像字典的目录能瞬间定位，但实际上 MySQL 的 InnoDB 引擎使用的是 B + 树数据结构。B + 树的特性：所有数据都存储在叶子节点上，并且叶子节点之间通过指针相连，形成了一个有序链表。
为什么是 B + 树？因为它能极大减少磁盘 I/O 次数，并且非常适合范围查询。当你执行 age 值大于十八时，B + 树可以在找到第一个大于十八的记录后，顺着叶子节点的指针一路遍历下去，非常高效。理解了 B + 树才能理解为什么索引是有序的，为什么最左前缀如此重要。
本质二：联合索引的匹配规则是基于列的顺序，而非括号的顺序。
回到面试官的问题：联合索引的底层 B + 树是如何构建的？排序规则是什么？它首先按照 age 字段排序，在 age 相同的情况下再按照 name 字段排序。
最左前缀原则：查询条件必须从索引的最左列开始，并且不能跳过中间的列，索引才能生效。关键点：这个左指的是索引定义时的列顺序，而不是 SQL 语句中谓词条件的书写顺序。
对于谓词 name=' 张三 ' and age=20，MySQL 的优化器会自动重排条件顺序，将其变成 where age=20 and name=' 张三 '，因此索引完全生效。
对于 where age>18 and name=' 张三 '，因为 age 是范围查询，它后面的 name 列就无法再用于索引查找了。索引只能用于过滤 age 大于十八的记录，然后在内存中对这些记录进行 name=' 张三 ' 的过滤，这就叫索引下推。但 name 列本身并没有被用于索引的快速定位。
本质三：面试官想问的是如何通过索引快速定位数据，同时考察实战设计能力。
这时你要能说出区分度高的列放前面，联合索引中应该将区分度最高的列放在最左边，这样可以最快的过滤掉大量数据，避免无效索引。
如果你已经有了对应的联合索引，那么单独为 age 值再建一个索引就属于冗余设计，因为前者已经能覆盖后者的功能。
覆盖索引尽量设计索引让查询只需要扫描索引就能返回结果，不需要回表查询主键。例如：如果你经常查询 select age,name from user where age=20，那么这个索引就是完美的覆盖索引，能极大提升查询效率。
这个就叫专业。
最后来波灵魂总结：下次面试官问你索引，别再脱口而出它能加快查询，你要说出索引的本质是 B + 树的数据结构，决定了它的有序性和范围查询能力。再说性能优化上要遵循最左前缀原则，利用覆盖索引和索引下推减少回表开销，这才是大厂面试官想要的深度。
