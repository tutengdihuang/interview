三年后端经验，被一个 Spring 事务失效问题问哑了！#java #java 面试 #后端 #后端开发 #程序员
你说你项目里天天用 spring 事务做数据一致性保障，那我问你，方法上加了 @Transactional 注解，结果异常了数据没回滚，事务直接失效，你的后端怎么排查？根源又怎么从规范层面避免这类问题反复出现？
最近面了一个三年经验的后端，我问他事务失效问题，看似基础，但要考虑代理机制、异常捕获、传播行为、多线程、多数据源等场景，从注解、配置到底层 aop 原理怎么设计？
他想了一下说，注解加在 public 方法上，抛出 RuntimeException 就会回滚，失效基本都是异常被 try catch 吞了。
我顺着他的话继续问：
同一个类里一个没加事务的方法调用本类带事务的方法，事务直接失效了，这背后的底层原因是什么？
如果方法里捕获了异常，不想往外抛，还有什么办法能手动触发事务回滚？
如果我配置了 rollbackFor 等于 exceptionClass，方法里抛出了该类型的异常，事务会不会回滚？
如果在事务方法里新开一个线程执行数据库操作，子线程的写操作会纳入当前事务吗？
你有没有考虑过不用声明式注解的方案，比如编程式事务，它的适用场景和优势是什么？
如果两个嵌套的事务方法本该各自独立回滚，却错用了默认的 required 传播行为，会引发什么业务问题？
如果项目配了多个数据源，@Transactional 默认管哪个数据源？跨数据源的一致性怎么保障？
他瞬间慌了，说可以把异常都往上抛，然后说不行的话就整个类都加上事务注解。但问到 aop 代理失效的底层原理，编程式事务落地，多数据源事务方案完全没思路。
面试到这里基本就可以结束了，这正是会加 @Transactional 注解和能彻底吃透 spring 事务机制的关键分水岭。很多人以为贴个 @Transactional 注解就搞定了事务，但一遇到同类自调用、异常被吞、传播行为错配、多线程场景这些真问题就崩了。
如果这道题目你也不会回答，我整理了大厂面试官必考题库，包含 java 基础、jvm 夺命连环问、spring 全家桶、mybatis、redis、微服务、分布式实战等等。只要是我粉丝，留下 pdf 直接拿走。
面试官问这个问题考察的不是你知不知道这个注解，而是你能从代理机制、底层理解事务原理，线上出问题能快速定位修复。真正能通过面试的事务方案设计必须吃透三层核心逻辑。
第一层，先明确事务失效的核心场景和底层逻辑。
spring 事务不是加了注解就一定生效，它基于 aop 动态代理实现，只有通过代理对象调用的方法才会被事务切面增强。同类自调用绕过代理导致失效，异常被捕获未抛出导致切面无法感知回滚，异常类型与回滚规则不匹配导致不回滚，非 public 方法代理不生效，多线程环境下 threadlocal 事务上下文线程隔离，多数据源下注解未指定对应事务管理器。
第二层，选一套核心方案落地多种场景。
以代理调用规范、加异常管控、加传播行为匹配为基础，基线辅以编程式事务兜底，复杂场景声明式事务规范。
同类调用必须通过注入自身代理对象或 aopcontext 获取代理执行，确保走事务切面增强。
异常处理统一配置 rollbackFor 覆盖全异常类型，捕获异常后可手动标记回滚状态，避免静默吞异常。
根据业务场景正确选择传播行为，需要独立事务的用 propagation.new，需要加入当前事务的用默认 required，复杂场景用编程式事务，通过 transactiontemplate 手动控制事务的开启、提交、回滚，灵活适配多逻辑分支、动态回滚点的场景，不受代理机制限制。
多数据源场景为每个数据源配置独立事务管理器，使用注解时明确指定对应管理器。
第三层，生产落地的异常处理与高效规范细节。
手动回滚优化，捕获异常后通过 transactionaspectsupport 手动标记回滚，不用抛出异常也能触发回滚，兼顾业务异常处理与事务一致性。
失效快速排查，线上事务不回滚按四步定位，先查是否同类自调用，再查是否吞了异常，再查方法是否为 public，最后核对传播行为与异常类型，快速覆盖百分之九十的失效问题。
效能治理，建立事务开发规范，禁止同类直接调用事务方法，禁止在事务方法内静默捕获异常，长事务拆分优化，避免数据库连接长时间占用。
监控事务回滚率、异常事务占比、长事务耗时，设置长事务告警。
如果声明式事务出现难以排查的失效问题，直接替换为编程式事务，快速修复，优先保证线上数据一致性。
这个就叫专业。讲到这里大家就明白了，面试官问 spring 事务失效根本不是考你会不会加 @Transactional 注解，核心考察三点：
1. 能不能识别自调用、异常吞掉、传播错配等常见失效场景；
2. 知不知道 aop 动态代理的底层实现原理；
3. 有没有编程式事务、多数据源事务规范治理等工程落地经验。
普通后端只会加注解、抛异常，出问题只会往上抛异常，全方法加事务。大厂后端能从代理底层吃透事务原理，灵活搭配声明式与编程式事务，搭建完整事务开发规范，扛得住复杂业务、多数据源、异常场景的一致性要求。
