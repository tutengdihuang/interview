MySQL 索引为什么会失效？MySQL 索引为什么会失效？因为你用了 like 左模糊。为什么同样是模糊，右模糊就走索引？这个你蒙了，又答不出来了。
这个问题答案不是简单的背几个失效场景，而是看你懂不懂索引背后的有序匹配逻辑。这道题表面在问索引失效原因，实际上面试官想考的是你对 B + 树、索引结构和最左前缀匹配原则的理解。

数据库到底是怎么判断一条 SQL 走不走索引？很多人脑子里只有一个粗糙的印象，对索引列做运算就会失效，但真实情况下细得多。走不走索引取决于你的查询条件能不能匹配索引的有序前缀，还取决于优化器的成本估算。能把这层讲清楚，你的 MySQL 和索引优化功底就立住了。
先说最核心的底层逻辑，为什么会失效？MySQL 的索引本质上是一棵有序的 B + 树，叶子节点按索引列的值从小到大排序，先按第一个字段排，第一个相同再按第二个排，以此类推。查询的时候只有从索引最左边的列开始按顺序匹配，才能沿着树的分支快速定位。如果跳过中间列或者打乱了原值的顺序，B + 树的有序性就用不上了，只能逐行扫描，也就是大家说的索引失效。
所以在违背有序匹配的场景下，答案确实是会失效。但是这里有个关键的转折，很多人只死记硬背失效清单，却搞不清所有场景本质上都是同一个原因。
比如 like 左模糊，% xxx，字符串开头是通配符，前缀不固定，就没法按有序的索引节点定位，只能全表扫。但右模糊，xxx%，前缀是固定的，依然可以利用索引的有序性做范围查找，所以能走索引。
再比如对索引列用函数做算数运算，发生隐式类型转换，本质上都是把索引列的原始值改了，B + 树里存的是原值，优化器没法直接用计算后的值去匹配树节点，只能逐行计算后比对，自然就失效了。
还有联合索引跳字段，跳过了左边的列，后面的列就失去了排序基础，也用不上索引。
这个问题在真实项目里坑有多大，意义非常大。很多线上慢 sql 不是没建索引，而是索引建了却用不上。比如联合索引顺序建反了，查询条件里跳字段，字符串传了数字触发隐式转换，明明有索引却走全表扫描，轻则接口响应超时，重则高并发下直接拖垮数据库。
所以你看，索引失效不是数据库故意设置限制，而是所有违背索引有序匹配逻辑的写法都会导致优化器放弃走索引，坑也在这。如果你只会背七八条失效场景，却说不清最左前缀的本质，也说不出优化器成本估算的影响，面试官就知道你只是背了八股。
这种问题在 SQL 优化和线上排障场景里最容易踩到，所以面试的时候不能只罗列失效场景，标准的思路是先讲本质，先讲 B + 树索引的有序性是索引生效的核心基础，再用最左前缀原则串起所有常见失效场景，左模糊、函数运算、隐式转换、跳字段，本质都是破坏了有序前缀匹配。
再补充优化器的成本判断，就算符合匹配规则，如果优化器估算全表扫描成本更低，也会主动放弃索引。最后落回实践，怎么通过 explain 验证，怎么避免失效。
最后点一句，判断索引会不会失效的本质是看查询条件能不能利用索引的有序性做精准匹配或范围匹配，这样答就显得你是真的懂原理，而不是背结论。这种数据库加性能优化结合的题最容易暴露你是不是只停在表面，这个就叫专业。
