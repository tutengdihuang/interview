做梦都在投简历。最近面试了一个五年后端，简历写着精通 Redis，做过分布式锁。我问他一个线上真实事故，他答得我直冒冷汗。
我说：你们用 Redis 做分布式锁，保证库存扣减的原则性。结果双十一当天库存超卖了，查日志发现两个线程同时拿到了锁，你怎么排查和修复？
他张口就来：是不是没有设置过期时间，或者业务执行时间超过过期时间锁自动释放了？
兄弟，你只知道锁可能过期，但你知道 Redis 主从切换时锁会丢吗？你知道 Redis 的看门狗机制吗？你知道 Redlock 算法吗？你这个问题排查方向就偏了，真正的问题可能是 Redis 集群本身的不一致性。
真正可靠的分布式锁得从四层来设计，你记好了。

・第一层：基础实现。
最基础的 Redis 锁要满足三个条件：用 set key value nx px3000 一条命令同时设置锁和过期时间，唯一标识 value 用 uuid 或线程 id；释放锁时先判断是不是自己家的锁，防止误删别人的锁。过期时间一定要设置，防止死锁。但这只是入门版，节点没问题，集群环境就危险了。
・第二层：集群环境的问题。
Redis 主从复制是异步的，如果线程 a 在主节点加锁成功，主节点还没同步到从节点就挂了，哨兵选举新主节点，从节点没有锁数据，线程 b 也能加锁成功，两个线程同时拿到锁，数据就乱了。
解决方案：用 Redlock 算法，在多个 Redis 节点上同时锁，超过半数成功才算加锁成功。但 Redlock 性能较差，且需要独立 Redis 实例。
・第三层：看门狗机制。
业务执行时间超过锁过期时间怎么办？用看门狗，Redis 框架会启动一个后台线程，每隔十秒检查一次，如果锁还在就自动续期到三十秒，业务执行完再释放锁，这样既不会提前释放也不会死锁。
・第四层：降级方案。
分布式锁不是百分之百可靠，要有兜底方案，在最终扣减库存的数据库操作上加乐观锁，即使分布式锁失效，数据库也能挡住超卖，这叫双保险。这个就叫专业。
所以这道题考的是你有没有分布式锁的深度理解，不是你会不会用 setnx，而是你怎么在复杂的分布式环境下保证锁的安全性同时兼顾性能。在架构师眼里，分布式锁是分布式系统的命门，命门失守，整个系统都会乱套。
