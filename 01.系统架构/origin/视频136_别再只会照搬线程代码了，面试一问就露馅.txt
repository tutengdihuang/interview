你说你会扎挖多县城，那我问你三个问题：县城安全问题有哪些表现？如何解决？县城池参数怎么配置？线上县城池耗尽怎么排查处理？死县城、县城死锁如何定位修复？
最近面了一个四年经验的 java 后端，我直接把这三个并发灵魂拷问甩给他，他吱吱呜呜半天，只说现成不安全就加 synchronous，现成尺改大小，死锁用 jstack 查看。
我顺着继续问：scremlin 和 lock 有什么本质区别？乐观锁、悲观锁分别适用什么场景？现成尺七大参数每一个代表什么？拒绝策略该怎么选？行现成尺耗尽除了调大参数还有哪些优化手段？死锁的排查步骤和日常规避方案是什么？
他当场就被问住了，愣了半天只说平时都是照着网上代码照搬，从来没系统梳理过这些问题的完整解决方案。面试到这里基本就可以结束了，这正是普通 crud 开发和能扛线上问题的自身后端的核心分水岭。
现在面试早就不再只问你会不会写接口，会不会简单创建县城，更看重你能不能解决线上病发故障，能不能扛住生产环境的突发状况。好多人面试遇到 java 病发这类问题容易丢分，如果这道题目你也不会回答，我整理了让大厂 hr 沉默的必考题库，包含 java 基础、jvm 夺命连环问、spring 全家桶、myico、radis、微服务、分布式实战等等。只要是我粉丝，留下九九九打包带走。
很多 java 开发都有一个误区，以为病发问题就是背几个关键字，几段代码，面试能说出来就行。但大家一定要分清，会写几行现成代码不叫懂病发，能说清楚每种问题的根源，能给出可落地的解决方案，能提前规避线上病发风险才叫真正掌握 java 多县城，缺一不可。
第一层，先搞懂 java 病发这三个问题为什么是面试必考点。java 多县城是后端开发的基础，高病发接口、异步任务、定时任务全都依赖多县城实现。但很多开发只会简单拗县城，调用县城迟，一旦线上出现病发异常就彻底抓瞎。县城不安全会导致数据错乱，业务结果异常。县城时耗尽会直接造成接口堵塞，服务不可用。县城死锁会让业务流程彻底卡死。这些问题轻则影响用户体验，重则直接造成服务宕机，公司重大经济损失。
而普通开发遇到这些问题，要么只会重启服务，要么盲目修改参数，根本解决不了核心问题。这就是为什么面试官一定会问这三个问题，因为它直接关系到你能不能胜任线上高病发开发的核心工作。
第二层，搞清楚 java 病发三大核心问题的所有触发场景。
首先是县城安全问题，主要分为三类核心场景：多县城同时操作共享变量，未作同步控制出现数据覆盖。复合操作，自增、自减等非原子操作，并发执行产生数据偏差。可见性问题，县城之间缓存数据不一致，导致读取旧数据。
然后是县城池异常，两大核心场景：任务提交量远大于县城处理能力，核心县城最大县城全部占满触发拒绝策略。任务执行耗时过长，内部堵塞，县城被长时间占用，新任务不断堆积，最终耗尽县城资源。
最后是县城死锁，典型触发场景：多个县城互相持有对方需要的锁，又同时等待对方释放锁。嵌套枷锁，枷锁顺序混乱，循环等待形成死锁。锁持有时间过长，搭配不合理的等待逻辑诱发死锁。
第三层，方案掌握三大核心问题的标准解决方案。掌握 java 并发三大核心问题的标准解决方案，面试可以直接背诵解决方案。
现成安全问题，区分场景使用悲观锁，synchronize、retractlock，保证操作串行。简单数值运算使用 atomic 原子类，基于 cas 实现，无所并发。使用 voltage 保证变量可见性，禁止指令重排，尽量减少共享变量，采用现成本地变量 threadlocal 隔离数据。
现成池问题，根据业务类型合理选择现成池类型，禁止使用 exactors 创建默认现成池。结合 cpu 核心数、任务耗时配置核心现成、最大现成、队列长度。根据业务容忍度选择合适拒绝策略，配合熔断、限流、兜底、拆分耗时式任务，避免线损堵塞，增加线损监控与告警。
现成死锁问题，统一全局加锁，顺序从根源打破循环等待控制，锁持有时间拆分长事务、长任务，使用 trylock 设置超时时间，避免无限等待。线上通过 gtechrcs 等工具抓取线程快照，快速定位死锁位置。
这个就叫专业。
