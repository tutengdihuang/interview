面试官：
你说你处理过线上生产事故，那我问你，线上数据库连接池突然打满，所有业务请求全部超时、卡住，你怎么快速止损并根治？
今天面了一个五年经验的后端，我问他连接池耗尽，看似基础，但要考虑连接泄露、长事务占坑、慢 sql 拖死连接、突发流量冲垮、参数配置失衡等场景。从临时止损到架构根治怎么设计？
候选人：
先重启服务，临时恢复，然后调大连接池最大连接数，再加个监控告警。
面试官：
如果重启后半小时连接又被打满，总不能一直靠重启救火吧？如果是代码里拿了连接没释放导致的泄露，你怎么快速定位到具体哪段代码出了问题？ 如果是长事务一直不提交，慢 sql 执行几分钟，连接被死死锁住不归，还怎么区分是连接泄露还是 sql 问题导致的耗尽？如果盲目调大连接数，数据库端的总连接数跟着暴涨，直接把数据库的最大连接数打满，反过来拖垮整个数据库实例，这个恶性循环怎么破？ 如果核心支付链路不能停，你怎么在不重启服务的情况下临时止损？有没有不用改代码的降级方案？如果是分库、分表、多数据源场景，多个连接池策略。
候选人：
那就把连接池再设大点，不行就去数据库端杀连接。

nice！面试官问这个问题考察的不是你会不会改配置，而是你在突发事故下怎么快速止损、定位根源，并且从架构层面避免故障复现。
真正能通过面试的连接池治理方案必须吃透三层核心逻辑。
第一层，先明确连接池耗尽的故障分类和失效场景。
连接池耗尽不是简单的连接数不够用，而是要先区分是流量突增导致的合理占满，还是代码缺陷、sql 异常导致的故障性耗尽。
常见失效场景：
代码获取连接后未在 finally 里释放，造成连接永久泄露。
事务内嵌套 rpc 调用，长事务不提交，导致连接长期不归还；慢 sql 执行耗时过长，连接被占用无法释放回池。
连接池参数失衡，空闲连接数过大，等待超时时间过长，数据库端连接被打满，反向限制应用扩容。
第二层，选一套完整的治理链路，覆盖应急到根治。
以应急止损加问题定位加架构优化为核心，基线辅以监控、熔断、降级、多维度兜底。
应急止损阶段
：先在数据库端批量杀掉空闲、超时的慢连接，同时对非核心接口做熔断、降级，快速释放连接资源，无需重启服务；动态调小连接最大等待时长，让请求快速失败，避免线程堆积。
根源定位阶段
：通过连接池监控看板查看活跃连接数、等待队列长度、平均连接持有时间，开启连接池泄露检测开关，打印未释放连接的调用堆栈，配合数据库慢 sql 日志、事务监控，精准定位长事务和慢 sql 源头。
架构优化阶段
：核心内容：强制约束事务边界，严禁在数据库事务内调用 rpc 第三方接口；统一封装数据库操作层，自动管理连接释放。从编码规范层面杜绝连接泄露，建立常态化 sql 审核机制，上线前必须过锁影校验，从源头减少慢 sql。
第三层，生产落地的异常处理细节。
连接泄露问题不能只靠人工排查日志，要做自动化回收。配置连接池泄露检测参数，超时未归还的连接自动强制回收，同时输出泄露堆栈并触发告警，做到故障可追溯。
慢 sql 占坑问题不能只靠 dba 事后优化，要做端到端超时控制，设置 sql 执行最大超时时间，超过阈值自动中断语句，避免单条 sql 拖垮整个连接池。
核心接口配置 sql 异常熔断，超时比例过高，自动降级保护连接池资源。
流量突增问题不能盲目堆连接数，要做业务分层限流。入口层按业务优先级限流，非核心查询、报表类业务直接降级返回兜底数据，把有限连接留给支付、下单等核心链路。
数据库端设置连接数上限做保护，避免应用端无限制扩容拖垮数据库。
如果连接池完全打满且无法快速恢复，立刻触发服务入口熔断，拒绝新请求进入，防止请求持续堆积拖垮线程池，演变成服务雪崩。

讲到这里大家就明白了，面试官问连接池耗尽根本不是考你会不会调 maxactive 参数，核心考察三点：
能不能区分连接泄露、慢 sql、流量突增等不同故障场景。
知不知道不重启服务的应急止损方案。
有没有连接池治理、sql 管控、熔断、降级等工程落地经验。
普通后端只会调大连接数，一把梭，出了事故只会重启服务；大厂后端能从应急止损、根源定位到架构优化，形成完整闭环，扛得住流量、故障、代码缺陷各种极端场景。
