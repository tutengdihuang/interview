面试官：分布式 ID 怎么生成？ #java #java 面试 #后端 #后端开发 #程序员
今天刚面了一个四年后端，我问他分布式 id 怎么生成，他脱口而出用雪花算法，全区唯一有序递增性能还高，直接引入工具类就能用。
我点点头笑着问了个线上真实订单重复事故。
假设你们订单系统用标准雪花算法生成订单号，机器 id 按规范分配，线上平稳跑了一年多都没出问题。可某天机房做了一次服务器时钟校准后接连出现了好几笔订单号重复的情况，一笔支付记录对应了两条订单数据，财务对账直接对不上，用户也投诉下单后订单信息错乱。
已权限排查算法实现没有问题，机器 id 也没有重复，可就是时钟回拨后的几分钟里集中出现了 id 冲突，全程没有任何报错等，发现时已经产生了多笔脏数据。
面试官：问题出在哪？
面试者：可能是时钟回拨导致的。
面试官：对，可服务器较准时钟是常规操作，你总不能禁止运维同步时间吧？针线上遇到时钟回拨引发 id 重复，你怎么快速止损？怎么从根本上保证核心业务 id 绝对唯一？难道每次时钟调整都要停机维护？
他开始吱吱呜呜。
面试到这就结束了，这正是分布式 id 最隐蔽的幽灵陷阱。你以为套个雪花算法就能搞定全区唯一 id，却没想到时钟回拨、机器 id 冲突，实例扩容错位都会悄悄生成重复 id。表面看算法天衣无缝，实则生产环境一个常规运维操作就能击穿所有防护。
如果这道题目你也不会回答，我整理了让大家面试官沉默的必考题库，包含 java 基础、jvm 夺命连环问、spring 全家桶、mariocarkreddis 微服务、分布式实战等等。只要是我粉丝留下 pdf 直接打包带走。
为什么这个问题能晒出高手？因为他考察的不是会不会调用 id 生成工具，而是有没有生产环境视角下的异常容错与兜底思维。一个能稳住核心业务 id 体系的后端必须建立三层防御。
第一层，业务分级差异化 id 方案，核心订单支付流水等强唯一要求的业务采用号段模式作为主方案，预先生成 id 号段缓存在本地，批量申请批量使用，彻底摆脱对系统时钟的依赖。
非核心业务如日志 id、消息 id 可使用基础雪花算法兼顾性能，机器 id 统一由注册中心自动分配，禁止手动配置，避免实例扩容容器漂移时出现 id 重复。
第二层，兜底校验与异常容错，数据库层，给所有业务 id 加唯一索引作为最终防线，即使 id 生成逻辑异常也绝不会出现重复数据入库。搭建时钟偏移实时监控，服务器时钟回拨，超过阈值自动告警。id 生成器内置时钟回拨处理机制，小幅回拨自动等待恢复，大幅回拨自动切换到备用号段模式，绝不生成重复 id。
第三层，架构层优化，从根源降低风险，核心业务建设统一的分布式 id 服务，所有业务线统一调用标准化异常处理与兜底逻辑，避免各业务各自实现导致的覆盖不全高风险运维操作。
运维前可提前，切换为强保障号段模式，彻底规避时钟波动影响。大促等核心时段，开启 id 双重校验模式，生成后校验唯一性，宁可牺牲少量生成性能，也决不允许核心链路出现 id 重复，这个就叫专业。
所以这道题考的是什么？它考的是有没有从会用雪花算法生成 id 升级为设计高可靠分布式 id 体系的工程思维。普通开发以为随便引入个工具类就是分布式 id 的全部，而高级工程师知道在复杂的服务器运行环境面前，分布式 id 生成是一把双刃剑，一个时钟回拨的细节没考虑到就可能引发订单重复、数据错乱的严重线上事故。
