四年后端经验，被一个 “分层限流” 问题问懵了... #java #java 面试 #后端 #后端开发 #程序员
你说你做过高并发网关架构，那我问你，大促活动流量暴涨，大量请求涌入集群，如何设计分层限流体系，防止下游服务被突发流量打崩，引发雪崩？
刚刚面了一个四年经验的后端，我问他分布式限流看似简单，但要考虑集群、多实例、限流算法差异、流量突刺、恶意攻击、限流降级联动等场景，从网关限流到应用本地限流怎么设计？
他想了一下说，在 gateway 网关使用 redis 令牌桶限流，使用用户 ip 超过阈值直接返回限流提示，保护后端服务。
我顺着他的话说，如果多网关集群部署，如果只用单机本地限流，每个实例独立统计，整体限流一直会失控，集群限流不准，这个问题怎么解决？
如果活动瞬间出现流量尖峰，令牌桶来不及生成令牌，大量正常请求直接被拦截，你怎么平衡突发流量与限流阈值？
如果只在网关做限流，网关层限流规则出现 bug，海量请求穿透到业务服务，服务没有兜底策略，直接宕机，你如何搭建多层防护？
如果区分普通用户、付费、vip，不能一刀切限流，差异化限流怎么实现？
你有没有考虑过不用 redis 的限流方案，比如漏桶算法，它的优缺点是什么？
如果 redis 集群故障，分布式限流失效，你怎么办？
他瞬间慌了，说可以把限流一直设置大一些，然后说不行的话叠加 enesis 限流，但问到限流误杀优化、多级限流、权重设计、故障降级方案完全没思路。
面试到这里基本就可以结束了，这正是会配置网关限流和能设计完整流量防护体系的关键分水岭。
很多人以为配置好 redis 令牌桶就解决限流问题，但一遇到集群、技术不准、流量尖峰、组建故障、分级用户限流这些真问题就崩了。

nice，面试官问这个问题考察的不是你会不会配置 gateway 限流规则，而是流量洪峰下守住服务底线，区分正常流量与恶意请求，避免雪崩。真正能通过面试的限流体系设计必须吃透三层核心逻辑。
第一层，先明确限流的范围和失效场景。
限流不只是单纯拦截超额请求，核心目标是保护系统可用。活动突袭、流量爬虫、恶意刷接口、上游重试风暴极易耗尽服务线程池、数据库连接，单机本地限流无法适配集群，分布式限流依赖 redis，存在网络抖动风险，令牌桶容易被突发流量击穿，漏桶无法应对流量尖峰，单一网关限流缺少兜底，一旦规则失效，流量直接穿透，无差异化限流会误杀付费核心用户，造成业务损失。
第二层，选一套核心方案落地多种场景。
以 njs 前置限流加网关分布式限流加应用本地限流三级防护为最可靠基线。区分流量特性，匹配算法。接入层 ngx 采用漏桶算法实现 ip 粗力度限流，拦截爬虫、恶意高频请求，作为第一道屏障。网关层使用 redis 加 lua 实现集群令牌桶限流，支持接口维度、用户维度、ip 维度多维度限流，区分普通用户与 vip，配置不同阈值，预留突发流量缓冲容量。业务应用层开启本地限流作为兜底，防止网关限流失效后流量击穿。
流量管控策略，核心接口优先保障，非核心接口提前降级限流，返回标准化提示，同时记录限流日志，便于分析攻击行为。
第三层，生产落地的异常处理细节。
集群限流精度问题，总阈值按照网关实例数量均分，同时设置缓冲余量，避免集群限流过度误杀。redis 网络波动时自动切换为本地限流应急兜底。流量突增优化，合理设置令牌桶 burst 突发容量，允许短时间峰值流量通过，避免正常活动流量被误拦截。
限流与熔断联动，接口持续超时触发熔断，配合限流双重防护，阻断故障传播。长期运维，定期分析限流日志，区分恶意爬虫与正常业务流量，动态调整限流阈值。监控限流触发次数、网关 qps、接口错误率，设置多级告警。如果 redis 分布式限流组件整体故障，网关自动切为单机限流模式，同步降低局部阈值，优先保障核心业务接口通行。
讲到这里大家就明白了，面试官问分布式限流根本不是考你会不会配置令牌桶，核心考察三点：能不能识别集群技术偏差、流量监控组件故障等真实场景，知不知道多级限流、分层防护方案，有没有差异化限流、故障兜底、攻防识别等工程落地经验，这个就叫专业。
普通后端只会在网关配置一套 redis 限流，流量暴涨只会调大阈值。大厂后端能徒手设计一套三级分层限流防护架构，兼顾正常流量通行与恶意请求拦截，扛得住大促、风控、集群故障、爬虫攻击。
