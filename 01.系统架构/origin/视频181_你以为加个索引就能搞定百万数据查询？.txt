你以为加个索引就能搞定百万数据查询？
#后端开发 #后端面试 #程序员 #程序员面试 #程序员日常
刚面了个三年后端，说自己精通 SQL 优化能搞定大数据量查询。
我随手问了个场景，一张订单表过亿数据，用户按手机号加时间范围查订单，怎么设计才不崩？
张口就来给手机号和时间加联合索引肯定快。
接着抛了个让他当场卡壳的问题。
如果用户手机号经常变更，时间跨度跨好几年，同时还要关联用户表、商品表、物流表做联表查询，联合索引失效回表严重，磁盘 IO 爆炸。你怎么救？
他想了想说：分库分表。按用户 ID 哈希分片。
我再追问：分片后跨分片分页，跨时间范围统计，后台运营要导出全量订单，你怎么保证不卡死、不超时？
他直接沉默了，面试到这就结束了。
这就是后端 SQL 优化的常见误区。以为加索引就是万能药，完全没考虑真实业务的复杂度、数据量级和查询多样性。
如果这道题目你也不会回答，我整理了让大厂 HR 沉默的必考题库。JVM 夺命连环问、Spring 灵魂八股、高并发必杀场景、Redis 深度陷阱等等。
为什么这道题能区分普通开发和架构师？就是面对海量数据时有没有完整的查询优化与存储设计思路。
一个能扛住亿级数据查询的后端至少要做到这三层：
・第一层：精准索引 + 避免回表。联合索引严格遵循最左匹配，大表只建必要索引，用覆盖索引直接从索引取结果，杜绝 SELECT *，减少随机 IO。
・第二层：读写分离 + 冷热分离。热数据放缓存，近 3 个月订单走主库高性能查询，历史数据归档到从库或 ES，前台只允许查限定时间范围。
・第三层：分库分表 + 旁路查询。按用户 ID 水平分片，复杂统计、模糊查询、后台报表丢给 Elasticsearch，禁掉全表扫描，加 SQL 限流与执行超时保护。
所以这道题本质考的是：你是只会写 CRUD，还是真正懂海量数据下的查询性能，存储架构与风险兜底。很多开发背了八股文，却扛不住真实场景的连环追问。
