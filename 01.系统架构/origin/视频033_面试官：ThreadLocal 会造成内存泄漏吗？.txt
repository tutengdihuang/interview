面试官：ThreadLocal 会造成内存泄漏吗？
会。因为 key 是弱引用，value 回收不掉。为什么非得设计成弱引用？直接用强引用不行吗？这个问题答案不是简单的会或不会，而是看你懂不懂 ThreadLocal 背后的引用链设计。
这道题表面在问内存泄漏，实际上面试官想考的是你对 ThreadLocalMap 引用机制和线程生命周期的理解。如果这道题你也不会回答，我整理了让大厂面试官沉默的必考题库，包含 Java 基础、JVM 夺命连环问、Spring 全家桶、MyBatis、Redis、微服务、分布式实战等等。只要是我粉丝，留下 pdf，直接打包带走。
JVM 到底是怎么判断 ThreadLocal 对象能不能回收？很多人脑子里只有一个粗糙的印象，ThreadLocal 用完就会被 GC，但真实情况下细得多。会不会泄露取决于线程是不是长期存活，还取决于你有没有手动清理掉 value。能把这层讲清楚，你的并发和 JVM 功底就立住了。
先说默认情况下为什么会泄露？每个线程的线程内部都挂着一个 ThreadLocal，value 本身是我们存进去的业务对象。这里的 key 被设计成了弱引用，只要 ThreadLocal 没有外部强引用，下次 GC 的时候这个 key 就会被直接回收。但 value 是强引用，只要线程还活着，这条引用链就一直通着，value 永远不会被回收，就形成了内存泄漏。这就是大家最常说的 ThreadLocal 内存泄漏。
所以在线程长期存活的场景下，答案确实是会泄露。但是这里有个关键的转折，很多人搞反了因果。设计成弱引用恰恰是为了减少内存泄漏，而不是造成泄漏的根源。反过来想，如果把 key 设计成强引用，就算外部把 ThreadLocal 的引用置为 null 了，map 里的 key 还强引用着它，ThreadLocal 实例永远回收不了，连 key 带 value 一起彻底泄漏，问题反而更严重。而弱引用至少能保证 key 不会一起彻底泄漏，问题反而还有机会被清理。
还有一个很多人不知道的兜底机制，ThreadLocalMap 在调用 set、get、remove 方法的时候，会自动扫描那些 key 已经变成 null 的 entry，把对应的 value 也一并清掉，做一次自清理。但这个保护机制有个大前提，就是后续得再调用这些方法触发清理。如果用完再也不调用了，那 value 就一直泄露在里面。
这个问题在真实项目里坑有多大，意义非常大。像我们常用的线程池场景，线程是复用的，不会销毁。一个请求用完 ThreadLocal 没手动 remove，下一个请求过来还能读到上一个线程残留的值，轻则业务数据错乱，重则泄漏累积最后撑爆 OOM。这也是为什么开发规范强制要求 ThreadLocal 用完必须手动 remove 的根本原因。
所以你看会不会泄露不是弱引用的锅，而是线程长期存活加上你没手动清理，共同导致的坑。也在这儿，如果你只知道被弱引用导致内存泄漏，却分不清强引用更糟，也说不清楚自清理机制，面试官就知道你只是背了个结论。这种问题在高发并发场景里最容易踩到，所以面试的时候不能只回答会或者不会。
标准的思路是先分层讲，先讲底层引用链结构，Thread 持有 ThreadLocalMap，map 的 entry 中 key 是弱引用，value 是强引用。再讲泄露的核心前提是线程长期存活，key 被回收后 value 的引用链无法切断。
然后对比强引用和弱引用的设计取舍，点出弱引用是为了降低泄露的影响。
再补充 map 的自清理机制和它的局限性。
最后落回最佳实践，用完必须手动 remove。
最后点一句，判断会不会泄露的本质是看线程生命周期加上 value 的引用链有没有被切断。这样答就显得你是真的懂设计，而不是死背书。这种并发加 JVM 结合的题最容易暴露你是不是只停在表面，这就叫专业。
