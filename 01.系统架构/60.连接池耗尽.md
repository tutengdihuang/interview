# 连接池耗尽问题排查与解决

> **场景定位**：生产问题排查技术场景  
> **核心设计要点**：连接泄漏排查、慢 SQL 优化、连接池配置、监控告警

---

## 🎯 一句话定位

**连接池耗尽问题怎么排查？**
```
❌ 错误认知：增大连接池就行
✅ 正确认知：先定位根因（连接泄漏/慢 SQL/并发突增），再针对性解决
```

**生活化比喻**：
就像餐厅座位不够了：
- **增大连接池**：加座位（治标不治本）
- **连接泄漏**：客人吃完饭不走（占着座位不释放）
- **慢 SQL**：客人点菜后厨房做菜太慢（客人等太久）
- **并发突增**：突然来了 10 倍客人（座位不够）

不同原因，解法完全不同。上来就加座位，可能越加越堵。

---

## 💎 核心观点（5 分钟速览版）

> **快速概览**

### 核心观点（4 个排查方向）

**1. 连接泄漏（最常见）**
```
症状：连接数持续上升，最终耗尽
原因：代码没有正确关闭连接（finally 块没有 close）
排查：
- 查看连接池监控（活跃连接数 vs 空闲连接数）
- 查看应用日志（是否有未关闭连接的警告）
- 代码审查（检查所有数据库操作是否正确关闭连接）

解决：
- 使用 try-with-resources（Java）或 defer（Go）自动关闭连接
- 连接池配置泄漏检测（如 HikariCP 的 leakDetectionThreshold）
```

**2. 慢 SQL（最常见）**
```
症状：连接数正常，但活跃连接长时间占用
原因：SQL 执行时间过长（没有索引、全表扫描、锁等待）
排查：
- 查看慢 SQL 日志（执行时间 > 1 秒的 SQL）
- 查看数据库监控（活跃连接数、锁等待时间）
- 分析 SQL 执行计划（EXPLAIN）

解决：
- 添加索引（覆盖索引、联合索引）
- 优化 SQL（避免 SELECT *、减少 JOIN）
- 分页优化（避免深度分页）
```

**3. 并发突增**
```
症状：连接数瞬间飙升，最终耗尽
原因：流量突增（如秒杀活动、爬虫攻击）
排查：
- 查看 QPS 监控（是否有流量突增）
- 查看应用日志（是否有异常请求）
- 查看网络监控（是否有 DDOS 攻击）

解决：
- 限流降级（令牌桶、漏桶）
- 增大连接池（临时扩容）
- 优化应用性能（减少连接占用时间）
```

**4. 连接池配置不合理**
```
症状：连接池大小不够用
原因：连接池配置过小，无法满足业务需求
排查：
- 查看连接池配置（最大连接数、最小空闲连接数）
- 查看连接池监控（连接使用率、等待时间）

解决：
- 调整连接池大小（根据业务峰值 QPS）
- 配置连接超时时间（避免无限等待）
- 配置连接存活时间（避免连接老化）
```

## 一、连接泄漏：最常见的原因

### 1.1 什么是连接泄漏？

**定义**：
```
连接泄漏：应用程序从连接池获取连接后，没有正确关闭连接
导致连接一直被占用，无法释放回连接池
最终连接池耗尽，无法获取新连接
```

**生活化比喻**：
```
就像餐厅座位：
客人吃完饭不走，占着座位
新客人来了没有座位
最终餐厅无法接待新客人
```

### 1.2 连接泄漏的代码示例

**❌ 错误示例**（Java）：
```java
// 错误：没有关闭连接
public void queryData() throws SQLException {
    Connection conn = dataSource.getConnection();
    Statement stmt = conn.createStatement();
    ResultSet rs = stmt.executeQuery("SELECT * FROM users");
    
    while (rs.next()) {
        // 处理数据
    }
    
    // ❌ 没有关闭连接！
    // rs.close();
    // stmt.close();
    // conn.close();
}
```

**✅ 正确示例**（Java）：
```java
// 正确：使用 try-with-resources 自动关闭
public void queryData() throws SQLException {
    try (Connection conn = dataSource.getConnection();
         Statement stmt = conn.createStatement();
         ResultSet rs = stmt.executeQuery("SELECT * FROM users")) {
        
        while (rs.next()) {
            // 处理数据
        }
    } // 自动关闭 conn、stmt、rs
}
```

**✅ 正确示例**（Go）：
```go
// 正确：使用 defer 自动关闭
func queryData() error {
    db, err := sql.Open("mysql", "user:password@/dbname")
    if err != nil {
        return err
    }
    defer db.Close() // 自动关闭
    
    rows, err := db.Query("SELECT * FROM users")
    if err != nil {
        return err
    }
    defer rows.Close() // 自动关闭
    
    for rows.Next() {
        // 处理数据
    }
    
    return nil
}
```

### 1.3 连接泄漏的排查方法

**方法 1：连接池监控**
```bash
# 查看连接池状态（以 HikariCP 为例）
curl http://localhost:8080/actuator/metrics/hikaricp.connections.active
# 输出：活跃连接数 50（应该 < 20）

curl http://localhost:8080/actuator/metrics/hikaricp.connections.idle
# 输出：空闲连接数 0（应该有闲置连接）
```

**方法 2：泄漏检测**
```java
// HikariCP 泄漏检测配置
HikariConfig config = new HikariConfig();
config.setLeakDetectionThreshold(60000); // 60 秒未关闭则告警
```

**方法 3：代码审查**
```
检查所有数据库操作：
- 是否使用了 try-with-resources（Java）
- 是否使用了 defer（Go）
- 是否在 finally 块中关闭连接
- 是否有异常分支没有关闭连接
```

### 1.4 连接泄漏的解决方案

**方案 1：使用 try-with-resources（Java）**
```java
// 自动关闭连接
try (Connection conn = dataSource.getConnection()) {
    // 数据库操作
}
```

**方案 2：使用 defer（Go）**
```go
// 自动关闭连接
db, err := sql.Open("mysql", "user:password@/dbname")
if err != nil {
    return err
}
defer db.Close()
```

**方案 3：配置泄漏检测**
```java
// HikariCP 泄漏检测
config.setLeakDetectionThreshold(60000); // 60 秒未关闭则告警
```

## 二、慢 SQL：连接长时间占用

### 2.1 慢 SQL 的症状

**症状**：
```
连接数正常，但活跃连接长时间占用
连接池使用率 100%，但 QPS 很低
数据库 CPU 使用率低（在等待 IO）
```

**生活化比喻**：
```
就像餐厅：
客人点菜后，厨房做菜太慢
客人等了一小时还没上菜
座位被占着，新客人进不来
```

### 2.2 慢 SQL 的排查方法

**方法 1：慢 SQL 日志**
```sql
-- 开启慢 SQL 日志（MySQL）
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 1; -- 超过 1 秒的 SQL 记录到日志

-- 查看慢 SQL 日志
SELECT * FROM mysql.slow_log ORDER BY start_time DESC LIMIT 10;
```

**方法 2：数据库监控**
```bash
# 查看活跃连接数（MySQL）
SHOW PROCESSLIST;
# 输出：
# Id | User | Host      | db   | Command | Time | State | Info
# 1  | root | localhost | test | Query   | 120  | Sending data | SELECT * FROM users WHERE ...

# 查看锁等待
SHOW OPEN TABLES WHERE In_use > 0;
```

**方法 3：SQL 执行计划**
```sql
-- 分析 SQL 执行计划
EXPLAIN SELECT * FROM users WHERE age > 20;
# 输出：
# type: ALL（全表扫描）
# rows: 1000000（扫描 100 万行）
# Extra: Using where
```

### 2.3 慢 SQL 的解决方案

**方案 1：添加索引**
```sql
-- 优化前：全表扫描
SELECT * FROM users WHERE age > 20;
-- 执行时间：5 秒

-- 添加索引
CREATE INDEX idx_age ON users(age);

-- 优化后：索引扫描
SELECT * FROM users WHERE age > 20;
-- 执行时间：0.01 秒
```

**方案 2：优化 SQL**
```sql
-- 优化前：SELECT *
SELECT * FROM users WHERE age > 20;

-- 优化后：只查询需要的字段
SELECT id, name, age FROM users WHERE age > 20;
```

**方案 3：分页优化**
```sql
-- 优化前：深度分页
SELECT * FROM users LIMIT 1000000, 10;
-- 执行时间：10 秒（需要扫描 100 万行）

-- 优化后：基于索引分页
SELECT * FROM users WHERE id > 1000000 LIMIT 10;
-- 执行时间：0.01 秒
```

## 三、并发突增：流量瞬间飙升

### 3.1 并发突增的症状

**症状**：
```
连接数瞬间飙升，最终耗尽
QPS 突然增加 10 倍、100 倍
应用响应时间急剧上升
```

**生活化比喻**：
```
就像餐厅：
突然来了 10 倍客人
座位不够，客人在门口排队
最终餐厅无法接待
```

### 3.2 并发突增的排查方法

**方法 1：QPS 监控**
```bash
# 查看 QPS 监控（Prometheus）
curl http://localhost:9090/api/v1/query?query=rate(http_requests_total[1m])
# 输出：QPS 从 100 飙升到 10000
```

**方法 2：应用日志**
```bash
# 查看应用日志
tail -f /var/log/app/access.log
# 输出：大量请求涌入
```

**方法 3：网络监控**
```bash
# 查看网络流量
iftop -t -s 10
# 输出：带宽使用率 90%
```

### 3.3 并发突增的解决方案

**方案 1：限流降级**
```java
// 令牌桶限流（Guava RateLimiter）
RateLimiter limiter = RateLimiter.create(1000); // 每秒 1000 个请求

public void handleRequest() {
    if (!limiter.tryAcquire()) {
        // 限流，返回降级响应
        return "系统繁忙，请稍后重试";
    }
    
    // 正常处理
    return "success";
}
```

**方案 2：增大连接池（临时扩容）**
```java
// 动态调整连接池大小（HikariCP）
HikariDataSource ds = (HikariDataSource) dataSource;
ds.setMaximumPoolSize(200); // 从 100 调整到 200
```

**方案 3：优化应用性能**
```
减少连接占用时间：
- 异步处理（非核心操作异步化）
- 批量处理（减少数据库交互次数）
- 缓存（减少数据库查询）
```

## 四、连接池配置不合理

### 4.1 连接池配置的核心参数

**最大连接数（maximumPoolSize）**：
```
定义：连接池允许的最大连接数
默认值：10（HikariCP）
建议值：根据业务峰值 QPS 调整

计算公式：
最大连接数 = 峰值 QPS × 单请求占用时间（秒） × 1.5

示例：
- 峰值 QPS：1000
- 单请求占用时间：0.01 秒
- 最大连接数 = 1000 × 0.01 × 1.5 = 15
```

**最小空闲连接数（minimumIdle）**：
```
定义：连接池保持的最小空闲连接数
默认值：10（HikariCP）
建议值：与最大连接数相同（避免动态扩缩容开销）
```

**连接超时时间（connectionTimeout）**：
```
定义：获取连接的最大等待时间
默认值：30 秒（HikariCP）
建议值：5-10 秒（避免无限等待）
```

**连接存活时间（maxLifetime）**：
```
定义：连接的最大存活时间
默认值：30 分钟（HikariCP）
建议值：5-10 分钟（避免连接老化）
```

### 4.2 连接池配置示例

**HikariCP 配置**（Java）：
```java
HikariConfig config = new HikariConfig();
config.setJdbcUrl("jdbc:mysql://localhost:3306/test");
config.setUsername("root");
config.setPassword("password");

// 核心配置
config.setMaximumPoolSize(100);        // 最大连接数
config.setMinimumIdle(100);            // 最小空闲连接数
config.setConnectionTimeout(30000);    // 连接超时 30 秒
config.setIdleTimeout(600000);         // 空闲超时 10 分钟
config.setMaxLifetime(1800000);        // 最大存活时间 30 分钟

// 泄漏检测
config.setLeakDetectionThreshold(60000); // 60 秒未关闭则告警

HikariDataSource dataSource = new HikariDataSource(config);
```

五、技术深入探讨

### Q1: 连接池耗尽了，你第一反应怎么处理？
**答**：先定位根因，再针对性解决。看连接池监控：
- 活跃连接数持续上升 → 连接泄漏
- 活跃连接长时间占用 → 慢 SQL
- 连接数瞬间飙升 → 并发突增
- 连接池配置过小 → 调整配置

### Q2: 如何排查连接泄漏？
**答**：
1. 查看连接池监控（活跃连接数 vs 空闲连接数）
2. 配置泄漏检测（HikariCP 的 leakDetectionThreshold）
3. 代码审查（检查所有数据库操作是否正确关闭连接）

### Q3: 慢 SQL 导致连接池耗尽怎么解决？
**答**：
1. 查看慢 SQL 日志，定位执行时间长的 SQL
2. 分析 SQL 执行计划（EXPLAIN），找出性能瓶颈
3. 添加索引、优化 SQL、分页优化

### Q4: 如何合理配置连接池大小？
**答**：
- 最大连接数 = 峰值 QPS × 单请求占用时间（秒） × 1.5
- 最小空闲连接数 = 最大连接数（避免动态扩缩容开销）
- 连接超时时间 = 5-10 秒（避免无限等待）

## 六、方案总结

**方案总结**：

> **排查思路**：连接池耗尽不能上来就增大连接池，要先定位根因。看连接池监控：活跃连接数持续上升是连接泄漏，活跃连接长时间占用是慢 SQL，连接数瞬间飙升是并发突增，连接池配置过小是配置不合理。
> 
> **连接泄漏**：代码没有正确关闭连接，使用 try-with-resources（Java）或 defer（Go）自动关闭连接，配置泄漏检测。
> 
> **慢 SQL**：SQL 执行时间过长，查看慢 SQL 日志，添加索引、优化 SQL、分页优化。
> 
> **并发突增**：流量瞬间飙升，限流降级、临时扩容、优化应用性能。
> 
> **配置优化**：根据业务峰值 QPS 合理配置连接池大小，配置连接超时时间和存活时间。
