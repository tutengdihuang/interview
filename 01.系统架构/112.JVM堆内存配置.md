# JVM 堆内存配置

> **场景定位**：JVM 调优技术场景  
> **核心设计要点**：分代比例推导、存活对象计算、GC 停顿、回收器选型

---

## 🎯 一句话定位

**JVM 堆内存配置解决什么问题？**
```
场景提问：堆内存设了 4G，新生代和老年代 1:2 是怎么来的？
你：业界默认值，大家都这么配。

❌ 背答案的当场现原形！
核心要求是推导过程，不是"默认值"。
```

**生活化比喻**：
就像一个仓库——新生代是"快进快出区"（大部分货物来了就走），老年代是"长期存储区"（少量贵重物品长期存放）。1:2 的比例不是拍脑袋定的，而是基于统计规律——绝大多数对象朝生夕死，只有少数能活到老年代。

## 💎 核心观点（5 分钟速览版）

### 核心观点（4 个关键点）

**1. 内存比例的底层推导逻辑**
```
新生代:老年代 = 1:2 不是凭空定的！

基于分代回收的统计规律：
  → 绝大多数对象朝生夕死（存活率 < 5%）
  → 存活时间长的最终进入老年代
  → 老年代需要更大空间承载长生命周期对象
  → 1:2 是基于大量业务场景统计的通用最优解

Eden:S0:S1 = 8:1:1 的底层逻辑：
  → 新生代采用复制回收算法
  → 需要一块空的 Survivor 区作为周转空间
  → 两块 Survivor 保证始终有一块空闲
  → 8:1:1 既保障分配空间充足，又控制浪费在 10%
```

**2. 如何判断堆内存该设多大？**
```
核心看两个指标：
  1. 业务峰值下的存活对象大小
  2. 业务可接受的 GC 频率与停顿时间

计算方法：
  → 压测导出堆快照
  → 统计峰值稳定后老年代存活对象总大小
  → 老年代容量 = 存活对象 × 2~3 倍（给 GC 留缓冲）
  → 新生代根据对象生成速率调整

工具：jstat、GC 日志、MAT 分析堆内存对象分布
```

**3. 堆内存设置不当的后果**
```
堆太小：
  → 频繁触发 Young GC
  → 对象提前晋升老年代 → Full GC 频发
  → 严重时 OOM，服务不可用

堆太大：
  → 单次 Full GC 的 STW 停顿大幅上升
  → 几百毫秒的停顿 → 请求超时 → 链路堆积
  → 低延迟业务反而性能下降

行业实测：
  → 堆内存超过 32G，指针压缩失效，内存占用膨胀
  → 性能出现拐点下降，不是越大越好！
```

**4. 回收器与参数配套选型**
```
吞吐量优先 → ParallelGC
  → 调优堆大小和分代比例
  → 适合：后台计算、数据处理、离线任务

低延迟优先 → G1 / ZGC
  → 调优最大停顿时间、Region 大小
  → 适合：交易接口、电商服务、在线业务

不同回收器调优逻辑完全不同！
  → ParallelGC：手动调分代比例
  → G1：停顿时间目标自适应分代
  → 不能用同一套参数套所有回收器
```

## 一、内存比例的底层推导

### 1.1 为什么新生代:老年代 = 1:2？

**生活化比喻**：
```
想象一座酒店：
- 新生代 = 钟点房（大部分人来待 1 小时就走了）
- 老年代 = 长包房（少数客人住几个月）

统计发现：95% 的客人是钟点房，5% 是长包房。
但长包房客人住得久，需要更多房间。
所以钟点房:长包房 = 1:2 是合理的。

对象也一样——绝大多数朝生夕死，
少数存活时间长，需要更大的老年代。
```

### 1.2 为什么 Eden:S0:S1 = 8:1:1？

```
新生代 GC 用复制算法：
  → Eden 区放新对象
  → GC 时把存活对象复制到 Survivor 区
  → 需要一块空的 Survivor 作为周转

所以两块 Survivor 必须存在：
  → 一块放当前存活对象
  → 一块留给下次 GC 复制用

空间利用率：
  → Eden 占 80%（分配新对象）
  → S0 + S1 各占 10%
  → 总利用率 = 80% + 10% = 90%
  → 浪费 10%（另一块 Survivor 空着）

这就是 8:1:1 的由来——回收效率和空间利用率的折中最优解。
```

### 1.3 比例不是死的！

```
业务不同，比例应该调整：

短生命周期对象极多（如 Web 请求处理）：
  → 调大新生代占比
  → 如 1:1 甚至 2:1

长生命周期缓存对象多（如本地缓存应用）：
  → 调大老年代容量
  → 如 1:3

关键：结合业务对象生命周期调整！
```

## 二、如何判断堆该设多大？

### 2.1 核心计算方法

```
步骤：
  1. 压测模拟业务峰值
  2. 导出堆快照（jmap -dump:format=b,file=heap.hprof <pid>）
  3. 用 MAT 分析存活对象分布
  4. 统计老年代存活对象总大小

计算：
  老年代容量 = 存活对象大小 × 2~3 倍
  → 给 GC 回收留足缓冲空间

  新生代 = 根据单位时间对象生成速率调整
  → 保证 Young GC 不过于频繁
  → 对象不会提前晋升老年代
```

### 2.2 堆太大 vs 太小的后果

| 场景 | 表现 | 后果 |
|------|------|------|
| **堆太小** | 频繁 Young GC、对象提前晋升 | Full GC 频发 → OOM |
| **堆适中** | GC 频率合理、停顿可控 | ✅ 最佳状态 |
| **堆太大** | 单次 Full GC 停顿大幅上升 | 请求超时 → 链路堆积 |
| **堆 > 32G** | 指针压缩失效，内存膨胀 | 性能拐点下降 |

```
行业实测数据：
  堆内存超过 32G → 指针压缩（Compressed Oops）失效
  → 对象头从 12 字节膨胀到 16 字节
  → 实际可用内存反而减少
  → 性能出现拐点下降
  
  所以堆不是越大越好！
  一般在线服务 4G~16G 足够。
```

## 三、回收器选型

| 回收器 | 特点 | 适用场景 | 调优重点 |
|--------|------|----------|----------|
| **ParallelGC** | 吞吐量优先 | 后台计算、离线任务 | 堆大小 + 分代比例 |
| **G1GC** | 低延迟 + 高吞吐 | 交易接口、电商服务 | 最大停顿时间 + Region 大小 |
| **ZGC** | 超低延迟（<10ms） | 实时性要求极高的场景 | 堆大小 |

```
关键认知：
  不同回收器调优逻辑完全不同！
  
  ParallelGC → 手动调分代比例
  G1 → 停顿时间目标自适应分代
  → 不能用同一套参数套所有回收器
```

### 方案参考

> "堆内存参数不是拍脑袋定的。

## 五、总结

> **JVM 堆内存 = 存活对象 × 2~3 倍 → 分代比例基于统计规律 → 回收器看业务 → 堆 > 32G 性能拐点**

### 🧠 核心记忆点

1. **1:2 和 8:1:1 不是默认值，是推导出来的**——分代统计规律 + 复制算法空间利用率。
2. **堆大小靠压测算**——老年代 = 存活对象 × 2~3 倍，不是拍脑袋。
3. **堆超过 32G 性能反而下降**——指针压缩失效，内存膨胀。
