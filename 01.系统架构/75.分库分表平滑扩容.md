# 分库分表平滑扩容

> **场景定位**：数据库架构设计场景  
> **核心设计要点**：扩容方案、数据迁移、业务连续性、一致性校验

---

## 🎯 一句话定位

**分库分表平滑扩容解决什么问题？**
```
业务增长，单库数据量逼近瓶颈
从 8 库扩到 16 库
如何保证数据不丢、业务不停、查询不出错？
```

**生活化比喻**：
就像高速公路扩建：
- 8 车道 → 16 车道
- 不能封路施工（业务不停）
- 车辆要正常通行（数据不丢）
- 新旧车道要平滑切换（查询不出错）

---

## 💎 核心观点（5 分钟速览版）

### 核心观点（5 个关键点）

**1. 停机迁移是下策**
```
❌ 简单方案：停机 → 迁移数据 → 上线
✅ 高级方案：双写 → 迁移 → 灰度切流

业务不能停，数据不能丢
```

**2. 路由变更引发数据偏移**
```
8 库 → 16 库
hash % 8 → hash % 16
70% 数据路由位置变化
需要迁移 70% 数据
```

**3. 双写 + 灰度切流**
```
1. 预部署 16 个库
2. 开启双写（新旧库同时写）
3. 后台迁移历史数据
4. 灰度切读流量（10% → 50% → 100%）
5. 关闭双写，完成扩容
```

**4. 一致性校验**
```
迁移前后全量比对
主键与核心字段增量数据实时同步校验
漏迁错迁立即告警并自动补数
```

**5. 预留逻辑分片**
```
架构设计初期就预留足够逻辑分片数
如提前规划 64 个逻辑分片
初期仅部署 8 个物理节点
后续扩容只需迁移逻辑分片
```

---

## 🚀 一句话精华

> **平滑扩容 = 双写（新旧库同时写） + 灰度切流（10% → 50% → 100%） + 一致性校验（全量比对） + 预留分片（减少扩容次数）**

## 一、扩容数据偏移问题

### 1.1 路由变化分析

```
原方案：8 个库（hash % 8）
扩容后：16 个库（hash % 16）

数据路由变化：
- hash % 8 = 0 → hash % 16 = 0 或 8
- hash % 8 = 1 → hash % 16 = 1 或 9
...

70% 数据路由位置变化 → 需要迁移
```

### 1.2 迁移成本

```
1 亿数据量，迁移 7000 万条
按 1000 条/秒，需要 19 小时
业务能接受停机 19 小时吗？
```

## 二、平滑扩容方案

### 2.1 双写阶段

```go
type MigrationManager struct {
    oldDBs [8]*gorm.DB
    newDBs [16]*gorm.DB
    dualWrite bool // 是否双写
}

// 双写逻辑
func (m *MigrationManager) InsertOrder(order *Order) error {
    // 1. 写旧库
    err := m.oldDBs[order.UserID%8].Create(order).Error
    if err != nil {
        return err
    }
    
    // 2. 双写模式下，同时写新库
    if m.dualWrite {
        m.newDBs[order.UserID%16].Create(order)
    }
    return nil
}
```

### 2.2 历史数据迁移

```go
// 后台迁移历史数据
func (m *MigrationManager) MigrateHistoryData() {
    for i := 0; i < 8; i++ {
        oldDB := m.oldDBs[i]
        
        // 分批查询
        var lastID int64
        for {
            orders, _ := oldDB.Where("id > ?", lastID).
                Order("id ASC").
                Limit(1000).
                Find()
            
            if len(orders) == 0 {
                break
            }
            
            // 写入新库
            for _, order := range orders {
                newDB := m.newDBs[order.UserID%16]
                newDB.Create(order)
            }
            
            lastID = orders[len(orders)-1].ID
        }
    }
}
```

### 2.3 灰度切流

```go
// 灰度切读流量
func (m *MigrationManager) SwitchReadTraffic(percent int) {
    // 10% → 50% → 100%
    config := fmt.Sprintf("read_from_new_db_percent=%d", percent)
    configCenter.Update(config)
}

// 读请求路由
func (m *MigrationManager) ReadOrder(orderID int64) (*Order, error) {
    percent := configCenter.GetInt("read_from_new_db_percent")
    
    if rand.Intn(100) < percent {
        // 读新库
        return m.newDBs[orderID%16].First(orderID)
    } else {
        // 读旧库
        return m.oldDBs[orderID%8].First(orderID)
    }
}
```

### 2.4 一致性校验

```go
// 全量比对
func (m *MigrationManager) VerifyDataConsistency() error {
    for i := 0; i < 8; i++ {
        oldDB := m.oldDBs[i]
        
        var lastID int64
        for {
            orders, _ := oldDB.Where("id > ?", lastID).
                Order("id ASC").
                Limit(1000).
                Find()
            
            if len(orders) == 0 {
                break
            }
            
            // 比对每条数据
            for _, order := range orders {
                newOrder, _ := m.newDBs[order.UserID%16].First(order.ID)
                if !isEqual(order, newOrder) {
                    log.Error("数据不一致: %d", order.ID)
                    // 告警并自动补数
                    m.fixData(order)
                }
            }
            
            lastID = orders[len(orders)-1].ID
        }
    }
    return nil
}
```

## 三、预留逻辑分片

### 3.1 设计思路

```
架构设计初期就预留足够逻辑分片数
如提前规划 64 个逻辑分片
初期仅部署 8 个物理节点

扩容时：
8 物理节点 → 16 物理节点
逻辑分片重新分配，无需改动路由规则和业务代码
```

### 3.2 实现示例

```go
// 逻辑分片路由
func RouteToPhysicalNode(logicShard int) int {
    // 初期：8 个物理节点
    // logicShard 0-7 → 物理节点 0
    // logicShard 8-15 → 物理节点 1
    // ...
    
    return logicShard / 8 // 每个物理节点 8 个逻辑分片
}

// 扩容后：16 个物理节点
// logicShard 0-3 → 物理节点 0
// logicShard 4-7 → 物理节点 1
// ...
```

## 四、跨库查询适配

### 4.1 分页查询

```go
// 扩容前：8 库分页
func QueryOrdersPage(page, pageSize int) []Order {
    offset := (page - 1) * pageSize
    
    var allOrders []Order
    for i := 0; i < 8; i++ {
        orders, _ := db[i].Offset(offset).Limit(pageSize).Find()
        allOrders = append(allOrders, orders...)
    }
    
    // 内存排序
    sort.Slice(allOrders, func(i, j int) bool {
        return allOrders[i].ID < allOrders[j].ID
    })
    
    return allOrders[:pageSize]
}

// 扩容后：16 库分页（自动适配）
func QueryOrdersPage(page, pageSize int) []Order {
    dbCount := configCenter.GetInt("db_count") // 动态获取
    
    var allOrders []Order
    for i := 0; i < dbCount; i++ {
        orders, _ := db[i].Offset(offset).Limit(pageSize).Find()
        allOrders = append(allOrders, orders...)
    }
    
    sort.Slice(allOrders, func(i, j int) bool {
        return allOrders[i].ID < allOrders[j].ID
    })
    
    return allOrders[:pageSize]
}
```

五、技术深入探讨

### Q1: 分库分表扩容怎么保证业务不停？

**方案参考**：
> 平滑扩容分五步：
> 
> 1. **预部署**：部署新的 16 个库
> 2. **双写**：新旧库同时写入，保证数据同步
> 3. **迁移**：后台迁移历史数据，不影响业务
> 4. **灰度**：逐步切读流量（10% → 50% → 100%）
> 5. **校验**：全量比对，确保数据一致
> 
> 关键是双写和灰度，保证业务连续性。

### Q2: 扩容过程中数据不一致怎么办？

**方案参考**：
> 数据不一致是扩容的大问题，解决方案：
> 
> 1. **全量比对**：迁移完成后，全量比对新旧库数据
> 2. **增量校验**：双写期间，实时校验增量数据
> 3. **自动补数**：发现不一致，自动修复
> 4. **告警机制**：不一致立即告警，人工介入
> 
> 核心是双写 + 校验，保证数据零丢失。
