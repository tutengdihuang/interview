# 分布式事务数据一致性

> **场景定位**：分布式系统技术场景  
> **核心设计要点**：刚性/柔性一致、兜底机制、容错补偿、架构优化

---

## 🎯 一句话定位

**分布式事务数据一致性解决什么问题？**
```
跨服务下单链路
订单服务成功，库存服务失败
数据不一致，出现超卖
```

**生活化比喻**：
就像转账：
- A 扣钱成功
- B 加钱失败
- 钱凭空消失了

---

## 💎 核心观点（5 分钟速览版）

### 核心观点（5 个关键点）

**1. 框架不是万能的**
```
❌ 误区：加全局事务注解就完事
✅ 真相：网络抖动、服务宕机、超时
都会让数据出现偏差
```

**2. 业务分级**
```
刚性一致：支付、扣库存、资金转账
→ TCC 或同步强校验
柔性一致：发积分、发短信
→ 最终一致性方案
```

**3. 兜底机制**
```
事务日志 + 定时重试
人工补偿队列
熔断降级
```

**4. 本地消息表**
```
本地事务与消息发送绑定
消费端重试实现最终一致
```

**5. 异步解耦**
```
非核心操作全部异步化
不阻塞主事务流程
```

---

## 🚀 一句话精华

> **数据一致性 = 业务分级（刚性/柔性） + 兜底机制（日志重试/人工补偿/熔断） + 本地消息表 + 异步解耦**

## 一、业务分级

### 1.1 刚性一致场景

```go
// 核心交易链路：TCC 或同步强校验
func PaymentFlow(order *Order) error {
    // 1. Try：预留资源
    err := tccService.Try(order)
    if err != nil {
        return err
    }
    
    // 2. Confirm：确认提交
    err = tccService.Confirm(order)
    if err != nil {
        // 3. Cancel：回滚
        tccService.Cancel(order)
        return err
    }
    
    return nil
}
```

### 1.2 柔性一致场景

```go
// 非核心链路：最终一致性
func GrantPoints(order *Order) error {
    // 发送 MQ 消息
    msg := &Message{
        OrderID: order.ID,
        Type:    "GRANT_POINTS",
    }
    
    // 异步发放积分，短暂延迟不影响主业务
    return mq.Send(msg)
}
```

## 二、兜底机制

### 2.1 事务日志 + 定时重试

```go
// 记录事务分支执行状态
func ExecuteBranch(branch *Branch) error {
    // 1. 记录执行状态
    log := &TransactionLog{
        BranchID: branch.ID,
        Status:   "EXECUTING",
    }
    db.Insert(log)
    
    // 2. 执行业务
    err := doBusiness(branch)
    
    // 3. 更新状态
    if err != nil {
        log.Status = "FAILED"
    } else {
        log.Status = "SUCCESS"
    }
    db.Update(log)
    
    return err
}

// 定时重试失败分支
func RetryFailedBranches() {
    ticker := time.NewTicker(5 * time.Minute)
    for range ticker.C {
        failedLogs := db.Query("SELECT * FROM transaction_log WHERE status = 'FAILED'")
        
        for _, log := range failedLogs {
            // 重试，保证幂等
            retryBranch(log)
        }
    }
}
```

### 2.2 人工补偿队列

```go
// 无法自动回滚的异常事务进入待处理队列
func HandleExceptionTransaction(tx *Transaction) {
    // 进入人工补偿队列
    compensationQueue.Push(tx)
    
    // 运营后台人工兜底
    alert("异常事务待处理: %v", tx.ID)
}
```

### 2.3 熔断降级

```go
// 监控事务失败率
func MonitorTransactionFailure() {
    ticker := time.NewTicker(1 * time.Minute)
    for range ticker.C {
        failureRate := getTransactionFailureRate()
        
        if failureRate > 0.1 {
            // 失败率超标，暂停非核心链路
            disableNonCoreTransaction()
            alert("事务失败率 %.2f，已熔断非核心链路", failureRate)
        }
    }
}
```

## 三、本地消息表

```go
// 本地事务与消息发送绑定
func CreateOrder(order *Order) error {
    tx := db.Begin()
    
    // 1. 创建订单
    err := tx.Exec("INSERT INTO orders ...", order)
    if err != nil {
        tx.Rollback()
        return err
    }
    
    // 2. 插入本地消息表
    msg := &LocalMessage{
        OrderID: order.ID,
        Status:  "PENDING",
    }
    tx.Exec("INSERT INTO local_message ...", msg)
    
    tx.Commit()
    
    // 3. 异步发送 MQ 消息
    go func() {
        err := mq.Send(msg)
        if err != nil {
            // 发送失败，定时重试
            retrySend(msg)
        } else {
            // 更新消息状态
            db.Exec("UPDATE local_message SET status = 'SENT'")
        }
    }()
    
    return nil
}
```

```go
// 非核心操作全部异步化
func OrderPaid(order *Order) error {
```

六、技术深入探讨

### Q1: 分布式事务怎么保证数据一致？

**方案参考**：
> 分布式事务数据一致性三层保障：
> 
> 1. **业务分级**：核心交易用 TCC 或同步强校验，非核心用最终一致性
> 2. **兜底机制**：事务日志 + 定时重试，人工补偿队列，熔断降级
> 3. **架构优化**：本地消息表 + 异步解耦，减少长事务占比
> 
> 核心是根据业务场景选择方案，刚性一致和柔性一致结合。

### Q2: 如何设计分布式事务方案？

**方案参考**：
> 分布式事务方案设计：
> 
> 1. **刚性一致**：支付、扣库存用 TCC，保证同一时间点数据完全对齐
> 2. **柔性一致**：发积分、发短信用最终一致性，短暂延迟不影响主业务
> 3. **兜底机制**：事务日志 + 定时重试 + 人工补偿
> 4. **异步解耦**：非核心操作全部异步化，不阻塞主事务
> 
> 核心是权衡一致性与可用性。
