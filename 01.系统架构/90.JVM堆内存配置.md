# JVM堆内存配置

> **场景定位**：JVM 调优技术场景  
> **核心设计要点**：分代比例、参数推导、回收器选型、性能权衡

## 🎯 一句话定位

**JVM堆内存配置解决什么问题？**
```
堆内存设多大？
新生代、老年代比例怎么定？
为什么是 1:2 和 8:1:1？
```

**生活化比喻**：
就像仓库管理：
- 新生代：快速周转区（80% 物品几天就出库）
- 老年代：长期存储区（20% 物品长期存放）
- 比例基于统计规律，不是拍脑袋

---

## 💎 核心观点（5 分钟速览版）

### 核心观点（5 个关键点）

**1. 1:2 不是凭空定的**
```
基于分代回收的统计规律
绝大多数对象朝生夕死
存活长的对象进入老年代
老年代需要更大空间
```

**2. 8:1:1 的底层逻辑**
```
复制算法的空间利用率平衡
需要一块空 survivor 区周转
两块 survivor 保证始终有一块空闲
空间浪费控制在 10%
```

**3. 比例不是死的**
```
短生命周期对象多：调大新生代
长生命周期对象多：扩大老年代
结合业务对象生命周期调整
```

**4. 堆大小判断依据**
```
业务峰值存活对象大小
可接受的 GC 频率与停顿时间
压测导出堆快照统计
```

**5. 堆不是越大越好**
```
堆太小：频繁 GC，甚至 OOM
堆太大：Full GC 停顿时间长
超过 32G 指针压缩失效
```

## 🚀 一句话精华

> **JVM堆配置 = 分代比例（1:2/8:1:1 基于统计） + 业务适配（对象生命周期） + 堆大小（存活对象+GC容忍度） + 回收器选型（吞吐量/低延迟）**

---

## 一、分代比例底层逻辑

### 1.1 新生代 vs 老年代 1:2

```
统计规律：
- 绝大多数对象朝生夕死
- 存活时间长的对象最终进入老年代
- 老年代需要更大空间承载长生命周期对象

1:2 是基于大量业务场景统计出的通用最优解
```

### 1.2 Eden:S0:S1 = 8:1:1

```
复制算法原理：
- 新生代采用复制回收算法
- 需要一块空 survivor 区作为复制周转空间
- 两块 survivor 区保证始终有一块空闲可用

空间利用率：
- 8 份 Eden 用于对象分配
- 1 份 S0/S1 用于复制周转
- 空间浪费控制在 10%

是回收效率和空间利用率的折中最优解
```

## 二、业务适配调整

```go
// 短生命周期对象多（如 Web 请求）
type ShortLivedScenario struct {
    // 调大新生代占比
    youngGenRatio: 0.5,  // 新生代占 50%
    oldGenRatio: 0.5,    // 老年代占 50%
}

// 长生命周期对象多（如缓存）
type LongLivedScenario struct {
    // 扩大老年代容量
    youngGenRatio: 0.25, // 新生代占 25%
    oldGenRatio: 0.75,   // 老年代占 75%
}
```

## 三、堆大小判断

### 3.1 核心指标

```
1. 业务峰值存活对象大小
   - 压测导出堆快照
   - 统计峰值稳定后老年代存活对象总大小
   - 老年代容量建议设为存活对象的 2-3 倍

2. 可接受的 GC 频率与停顿时间
   - 新生代根据单位时间对象生成速率调整
   - 保证 Young GC 不会过于频繁
   - 对象不会提前晋升老年代
```

### 3.2 实战验证工具

```bash
# jstat 观察 GC 频率和耗时
jstat -gcutil <pid> 1000

# GC 日志分析
-XX:+PrintGCDetails -XX:+PrintGCTimeStamps -Xloggc:gc.log

# MAT 分析堆内存对象分布
# 导出堆快照：jmap -dump:format=b,file=heap.hprof <pid>
# MAT 分析对象分布
```

## 四、堆大小不当后果

### 4.1 堆太小

```
问题：
- 对象分配空间不足
- 频繁触发 Young GC
- 对象提前晋升老年代
- Full GC 频发
- 严重时直接 OOM

表现：
- CPU 使用率高（GC 开销）
- 响应时间长
- 服务不可用
```

### 4.2 堆太大

```
问题：
- 单次 Full GC 的 STW 停顿时间大幅上升
- 堆越大，垃圾回收器扫描和整理时间越长
- 低延迟业务：几百毫秒停顿导致请求超时
- 链路堆积，反而降低整体吞吐量

行业实测数据：
- 堆内存超过 32G，指针压缩失效
- 内存占用膨胀，性能拐点下降
- 不是堆越大性能越好
```

## 五、回收器选型

### 5.1 吞吐量优先：ParallelGC

```bash
# 适合场景
- 后台计算
- 数据处理
- 离线任务

# 核心调优
- 堆大小
- 分代比例

# 启动参数
-XX:+UseParallelGC
-XX:ParallelGCThreads=8
```

### 5.2 低延迟优先：G1/ZGC

```bash
# G1 适合场景
- 交易接口
- 电商服务
- 在线业务

# 核心调优
- 最大停顿时间
- 目标 Region 大小

# 启动参数
-XX:+UseG1GC
-XX:MaxGCPauseMillis=200
-XX:G1HeapRegionSize=8m

# ZGC 适合场景
- 超大堆（>32G）
- 极低延迟（<10ms）

# 启动参数
-XX:+UseZGC
-XX:+ZGenerational  # JDK 21+
```

## 六、配置示例

### 6.1 交易服务（低延迟）

```bash
# 堆大小：8G
# 新生代：2G（25%）
# 老年代：6G（75%）
# 回收器：G1

-Xms8g -Xmx8g
-XX:NewRatio=3  # 老年代:新生代 = 3:1
-XX:+UseG1GC
-XX:MaxGCPauseMillis=100
-XX:G1HeapRegionSize=4m
```

### 6.2 数据处理服务（吞吐量）

```bash
# 堆大小：16G
# 新生代：4G（25%）
# 老年代：12G（75%）
# 回收器：ParallelGC

-Xms16g -Xmx16g
-XX:NewRatio=3
-XX:+UseParallelGC
-XX:ParallelGCThreads=16
```

七、技术深入探讨

### Q1: 1:2 和 8:1:1 怎么来的？

**方案参考**：
> 分代比例基于统计规律和算法原理：
> 
> 1. **1:2（新生代:老年代）**：基于大量业务场景统计，绝大多数对象朝生夕死，存活长的对象进入老年代，老年代需要更大空间
> 2. **8:1:1（Eden:S0:S1）**：复制算法需要一块空 survivor 区周转，两块 survivor 保证始终有一块空闲，空间浪费控制在 10%
> 
> 不是死板的，要结合业务对象生命周期调整。

### Q2: 堆内存该设多大？

**方案参考**：
> 堆大小判断依据：
> 
> 1. **存活对象大小**：压测导出堆快照，统计峰值稳定后老年代存活对象总大小，老年代容量建议设为存活对象的 2-3 倍
> 2. **GC 容忍度**：根据业务可接受的 GC 频率与停顿时间调整
> 3. **验证工具**：jstat 观察 GC 频率，MAT 分析对象分布
> 
> 堆不是越大越好，超过 32G 指针压缩失效，性能反而下降。
