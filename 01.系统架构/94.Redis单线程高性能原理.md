## 一、IO多路复用模型

### 1.1 核心原理

```
传统模型：
- 一个连接一个线程
- 1000 连接 = 1000 线程
- 上下文切换开销大

IO多路复用：
- 单线程监听多个连接
- epoll/kqueue/select 机制
- 有事件才处理，无事件阻塞
- 1000 连接 = 1 线程
```

### 1.2 事件循环

```go
// 伪代码：Redis 事件循环
func eventLoop() {
    for {
        // 1. 监听所有连接的读写事件
        events := epoll.Wait()
        
        // 2. 处理事件
        for _, event := range events {
            if event.Readable {
                // 读请求
                handleRead(event.Conn)
            }
            if event.Writable {
                // 写响应
                handleWrite(event.Conn)
            }
        }
        
        // 3. 执行命令（单线程）
        executeCommands()
    }
}
```

## 二、为什么不用多线程？

### 2.1 单线程优势

```
1. 避免锁竞争
   - 多线程需要加锁
   - 锁竞争导致性能下降
   
2. 避免上下文切换
   - 线程切换开销大
   - 单线程无切换开销
   
3. 代码简单
   - 无需考虑并发问题
   - 易于维护和调试
```

### 2.2 单线程劣势

```
1. 无法利用多核CPU
   - 单线程只能用一个核心
   - 多核CPU利用率低
   
2. 慢查询阻塞
   - 一个慢命令阻塞所有请求
   - keys*、大集合运算等
```

## 三、Redis6.0多线程

### 3.1 设计思路

```
多线程只处理网络IO读写：
- 网络包解析并行化
- 利用多核CPU加速IO

核心命令执行依然单线程：
- 保证数据结构线程安全
- 避免锁竞争
```

### 3.2 架构演进

```
Redis < 6.0：
┌─────────────┐
│  单线程      │
│  IO + 命令   │
└─────────────┘

Redis >= 6.0：
┌─────────────┐
│  多线程IO    │ ← 网络包解析
├─────────────┤
│  单线程命令  │ ← 核心执行
└─────────────┘
```

## 四、真正拖垮Redis的因素

### 4.1 慢查询

```bash
# 危险命令
KEYS *          # 全表扫描，O(N)
SMEMBERS large_set  # 大集合运算
HGETALL large_hash  # 大哈希表

# 替代方案
SCAN            # 渐进式遍历
SSCAN/HSCAN     # 渐进式遍历
```

### 4.2 内存问题

```
1. 内存碎片
   - 频繁分配释放导致碎片
   - 使用率下降
   
2. 写时复制（COW）
   - RDB/AOF 触发 fork
   - 大内存 fork 阻塞主线程
   
3. 淘汰策略
   - 内存不足触发淘汰
   - 淘汰算法开销
```

### 4.3 持久化开销

```
1. RDB 快照
   - fork 子进程阻塞
   - 大内存 fork 耗时长
   
2. AOF 刷盘
   - always：每次写入刷盘，性能差
   - everysec：每秒刷盘，可能丢1秒数据
   - no：操作系统刷盘，不可控
```

## 五、性能优化建议

### 5.1 避免慢查询

```go
// ❌ 危险命令
redis.Keys("*")  // O(N)，阻塞

// ✅ 替代方案
redis.Scan(0, "pattern", 100)  // 渐进式遍历
```

### 5.2 控制内存

```
1. 设置 maxmemory
   - 避免内存无限增长
   - 选择合适的淘汰策略
   
2. 控制单实例内存
   - 建议 < 10GB
   - 避免 fork 阻塞
```

### 5.3 持久化优化

```
1. 主从分离
   - 主库关闭持久化
   - 从库负责持久化
   
2. AOF 策略
   - 核心数据：everysec
   - 非核心数据：no
```

六、技术深入探讨

### Q1: Redis单线程为什么快？

**方案参考**：
> Redis高性能的核心原因：
> 
> 1. **IO多路复用**：单线程同时监听多个连接，高效处理海量并发
> 2. **内存操作**：基于内存，读写速度快
> 3. **单线程优势**：避免锁竞争和上下文切换
> 
> 性能瓶颈是网络IO，不是CPU。单线程恰恰是解决网络IO并发最高效的方式之一。

### Q2: 为什么Redis6.0引入多线程？

**方案参考**：
> Redis6.0多线程设计：
> 
> 1. **瓶颈转移**：网络IO延迟降低，CPU消耗显现
> 2. **多线程IO**：只处理网络包解析，利用多核CPU
> 3. **单线程命令**：核心命令执行依然单线程，保证线程安全
> 
> 既利用了多核CPU加速IO，又保持了核心数据结构的线程安全性。
