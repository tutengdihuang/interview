# 数据库连接池优化

> **场景定位**：数据库架构场景  
> **核心设计要点**：业务分级、监控兜底、泄露治理、架构优化

---

## 🎯 一句话定位

**数据库连接池优化解决什么问题？**
```
高峰期连接池被彻底打满
所有请求排队等连接
没有慢查询，CPU正常，连接也规范关闭
但还是被占满
```

**生活化比喻**：
就像银行柜台：
- 窗口全部被占用（连接耗尽）
- 客户排队等待（请求排队）
- 但柜员没在办事（长事务占坑）

---

## 💎 核心观点（5 分钟速览版）

### 核心观点（5 个关键点）

**1. 参数配置不够**
```
❌ 误区：设好最大连接数就行
✅ 真相：长事务占用、异常漏释放
嵌套事务未提交都会耗光连接
```

**2. 业务分级隔离**
```
短事务核心场景：下单、支付、库存
严格收敛事务范围
执行完立即释放
长耗时场景：批量同步、报表导出
单独专用连接池
与核心交易物理隔离
```

**3. 监控兜底**
```
全维度监控：活跃连接数、等待队列、占用时间
连接泄露检测：自动打印调用栈，强制回收
事务超时回滚：全局最大执行时长
```

**4. 多池隔离**
```
核心交易、后台、管理、统计、分析
分别配置独立连接池
不同最大连接数与超时策略
互不影响
```

**5. 读写分流**
```
读请求走缓存库连接池
分摊主库连接压力
主库连接留给核心写操作
```

---

## 🚀 一句话精华

> **连接池优化 = 业务分级（短事务核心/长耗时专用） + 监控兜底（全维度监控/泄露检测/超时回滚） + 多池隔离（核心/后台/统计独立） + 读写分流（读走缓存库）**

## 一、业务分级隔离

### 1.1 短事务核心场景

```go
// 核心场景：下单、支付、库存扣减
func CoreTransaction() error {
    // 1. 严格收敛事务范围
    tx := db.Begin()
    
    // 2. 只包含必要的数据库操作
    err := tx.Exec("UPDATE inventory SET stock = stock - 1 WHERE goods_id = ?", goodsID)
    if err != nil {
        tx.Rollback()
        return err
    }
    
    err = tx.Exec("UPDATE orders SET status = 'PAID' WHERE id = ?", orderID)
    if err != nil {
        tx.Rollback()
        return err
    }
    
    // 3. 执行完立即释放连接
    return tx.Commit()
}
```

### 1.2 长耗时场景

```go
// 长耗时场景：批量同步、报表导出
var backgroundPool = &ConnectionPool{
    MaxConnections: 50,
    Timeout:        5 * time.Minute,
}

func BatchSync() error {
    // 单独分配专用连接池
    conn := backgroundPool.Get()
    defer conn.Release()
    
    // 与核心交易物理隔离
    // 避免长连接挤占核心资源
    return doBatchSync(conn)
}
```

## 二、监控兜底

### 2.1 全维度监控

```go
// 全维度连接监控
func MonitorConnectionPool() {
    ticker := time.NewTicker(1 * time.Minute)
    for range ticker.C {
        // 1. 活跃连接数
        activeCount := pool.GetActiveCount()
        
        // 2. 等待队列长度
        waitQueueSize := pool.GetWaitQueueSize()
        
        // 3. 单连接最长占用时间
        maxHoldTime := pool.GetMaxHoldTime()
        
        // 超标告警
        if activeCount > pool.GetMaxConnections()*0.8 {
            alert("活跃连接数过多: %d", activeCount)
        }
        
        if waitQueueSize > 100 {
            alert("等待队列过长: %d", waitQueueSize)
        }
        
        if maxHoldTime > 30*time.Second {
            alert("连接占用时间过长: %v", maxHoldTime)
        }
    }
}
```

### 2.2 连接泄露检测

```go
// 连接泄露检测
func DetectLeak() {
    // 1. 开启泄露检测开关
    pool.EnableLeakDetection(30 * time.Second)
    
    // 2. 超出阈值未释放的连接
    leakedConns := pool.GetLeakedConnections()
    
    for _, conn := range leakedConns {
        // 3. 自动打印调用栈
        log.Error("连接泄露: %v, 调用栈: %v", conn.ID, conn.StackTrace)
        
        // 4. 强制回收连接
        pool.ForceRelease(conn)
    }
}
```

### 2.3 事务超时回滚

```go
// 事务超时强制回滚
func ExecuteWithTimeout(tx *Transaction, maxDuration time.Duration) error {
    // 1. 设置超时
    ctx, cancel := context.WithTimeout(context.Background(), maxDuration)
    defer cancel()
    
    done := make(chan error, 1)
    go func() {
        done <- tx.Execute()
    }()
    
    // 2. 超时自动回滚
    select {
    case err := <-done:
        return err
    case <-ctx.Done():
        tx.Rollback()
        return errors.New("事务执行超时，已回滚")
    }
}
```

## 三、多池隔离

```go
// 多池隔离部署
type ServicePools struct {
    corePool     *ConnectionPool // 核心交易
    backgroundPool *ConnectionPool // 后台管理
    statsPool    *ConnectionPool // 统计分析
    reportPool   *ConnectionPool // 报表导出
}

// 各自独立，互不影响
func (p *ServicePools) GetCoreConnection() *Connection {
    return p.corePool.Get()
}

func (p *ServicePools) GetBackgroundConnection() *Connection {
    return p.backgroundPool.Get()
}
```

## 四、读写分流

```go
// 读写分流减负
var readPool = &ConnectionPool{
    // 缓存库连接池
    MaxConnections: 200,
}

var writePool = &ConnectionPool{
    // 主库连接池
    MaxConnections: 50,
}

// 读请求走缓存库
func ReadQuery(sql string) (*Result, error) {
    conn := readPool.Get()
    defer conn.Release()
    return conn.Query(sql)
}

// 写请求走主库
func WriteQuery(sql string) error {
    conn := writePool.Get()
    defer conn.Release()
    return conn.Exec(sql)
}
```

六、技术深入探讨

### Q1: 连接池被耗尽怎么排查？

**方案参考**：
> 连接池耗尽排查三层防御：
> 
> 1. **业务分级**：短事务核心场景严格收敛事务范围，长耗时场景单独专用连接池
> 2. **监控兜底**：全维度监控活跃连接数、等待队列、占用时间；连接泄露检测；事务超时回滚
> 3. **架构优化**：多池隔离，读写分流，大促降级
> 
> 核心是全生命周期治理。

### Q2: 如何避免连接泄露？

**方案参考**：
> 避免连接泄露：
> 
> 1. **泄露检测**：开启连接池泄露检测开关，超出阈值未释放的连接自动打印调用栈
> 2. **强制回收**：检测到泄露后强制回收连接
> 3. **事务超时**：设置全局事务最大执行时长，超时自动回滚
> 4. **规范编码**：使用defer确保连接释放
> 
> 核心是监控检测 + 强制回收。
