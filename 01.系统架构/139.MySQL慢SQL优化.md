## 🎯 一句话定位

**MySQL 慢 SQL 解决什么问题？**
```
电商订单库日常访问平稳，
大促高峰期多条件筛选订单的接口批量触发，
部分查询字段未见索引，触发全表扫描，
数据库 CPU 瞬间拉满至 100%，
所有新增订单、支付、入库接口全部堵塞、超时。

事后给查询字段新增索引，简单查询恢复正常，
但多字段联合查询依旧执行缓慢，
索引失效问题反复出现，频繁造成数据库雪崩。

技术追问：
- 问题出在哪？
- 从 SQL 编码、索引设计、架构层面完整治理慢查询？
- 难道遇到查询慢就无脑给所有字段建立索引？

90% 的人答不上来！
```

**生活化比喻**：
就像图书馆找书：
- **慢 SQL**：没有索引，一本书一本书找（全表扫描）
- **索引失效**：索引建了但没用到，还是全表扫描
- **CPU 满载**：图书管理员忙不过来，所有读者都等着

**核心特点**：单一加索引优化和真正从 SQL 规范、索引设计、存储架构多维度落地优化方案完全是两个技术维度！

- 月度账单、数据大盘、历史报表

生活化比喻：
就像图书馆：
- 实时查询：读者现场找书，必须快速找到
- 离线统计：整理书架、盘点库存，可以晚上做
```

**第二层：索引与 SQL 落地优化**
```
索引设计：
- 遵循最左前缀原则设计联合索引
- 无用索引及时清理，避免拖累插入更新性能

SQL 优化：
- 禁止类型转换、字段运算、like 左模糊等破坏索引的写法

- 深分页场景改用主键游标分页替代 limit 大偏移量查询
- 复杂多表关联 SQL 拆解拆分逻辑

生活化比喻：
就像图书馆：
- 索引设计：按类别、作者、出版年份分类
- SQL 优化：不要一次找所有书，只找需要的
```

```
读写分离：
- 搭建主从架构，实现读写分离
- 查询流量分流至从库
- 主库只负责新增、修改、热点高频查询

缓存拦截：
- 接入 Redis 缓存，拦截重复请求
- 直达数据库

慢查询监控：
- 开启慢查询日志
- 配合监控系统实时抓取超时 SQL
- 定时巡检优化

分库分表：
- 海量历史订单数据按年月分表
- 减小单表数据体量
- 从根源降低扫描开销

生活化比喻：
就像图书馆：
- 读写分离：借书和还书分开窗口
- 缓存：常用书放在前台，快速借阅

## 一、为什么 MySQL 慢 SQL 这么难？

### 🔍 核心问题（30 秒版）

**生活化比喻**：
```
MySQL 慢 SQL 的三大难题：
1. 索引失效：索引建了但没用到，还是全表扫描
2. SQL 写法糟糕：关联表过多、嵌套查询、select *
3. 参数不合理：连接数、缓存池设置不当

就像图书馆：
- 索引失效：分类标签贴了但没找到
- SQL 写法糟糕：一次找所有书，找不到
- 参数不合理：图书管理员太少，忙不过来
```

### 1.1 三大核心难题

| 难题 | 具体表现 | 线上后果 | 生活化比喻 |
|------|---------|---------|-----------|
| **索引失效** | 索引建了但没用到 | 全表扫描，CPU 飙升 | 分类标签贴了但没找到 |
| **SQL 写法糟糕** | 关联表过多、嵌套查询 | 查询缓慢 | 一次找所有书 |
| **参数不合理** | 连接数、缓存池设置不当 | 数据库性能下降 | 图书管理员太少 |

## 二、第一层：业务分级

### 2.1 实时联机查询（核心）

**适用场景**：
- 用户下单
- 订单详情
- 支付校验

**特点**：
- 耗时长：毫秒级
- 必须快速响应
- 用户体验敏感

**处理方式**：
```sql
-- ✅ 优先保证 SQL 高效执行
-- 严控查询耗时在毫秒级
SELECT id, order_no, status, amount 
FROM orders 
WHERE user_id = ? AND status = ?;
```

### 2.2 离线统计查询（非核心）

**适用场景**：
- 月度账单
- 数据大盘
- 历史报表

**特点**：
- 耗时长：秒级甚至分钟级
- 可以延迟执行
- 不是用户立即需要的

**处理方式**：
```sql
-- ✅ 避开业务高峰执行
-- 禁止直接在线主库运行
-- 在从库或专门的统计库执行
SELECT DATE_FORMAT(create_time, '%Y-%m') AS month, 
       SUM(amount) AS total_amount
FROM orders
WHERE create_time >= '2024-01-01'
GROUP BY DATE_FORMAT(create_time, '%Y-%m');
```

## 三、第二层：索引与 SQL 落地优化

### 3.1 索引设计

**最左前缀原则**：
```sql
-- ✅ 正确示例
-- 联合索引：(user_id, status, create_time)
-- 查询必须从最左列开始

-- 命中索引
SELECT * FROM orders WHERE user_id = ?;
SELECT * FROM orders WHERE user_id = ? AND status = ?;
SELECT * FROM orders WHERE user_id = ? AND status = ? AND create_time = ?;

-- ❌ 不命中索引
SELECT * FROM orders WHERE status = ?; -- 缺少 user_id
SELECT * FROM orders WHERE create_time = ?; -- 缺少 user_id 和 status
```

**索引失效场景**：
```sql
-- ❌ 索引失效场景 1：类型转换
-- 字段是 VARCHAR，但查询用数字
SELECT * FROM users WHERE phone = 13800138000; -- phone 是 VARCHAR
-- 应该用：
SELECT * FROM users WHERE phone = '13800138000';

-- ❌ 索引失效场景 2：字段运算
SELECT * FROM orders WHERE amount * 100 > 10000;
-- 应该用：
SELECT * FROM orders WHERE amount > 100;

-- ❌ 索引失效场景 3：函数运算
SELECT * FROM orders WHERE DATE(create_time) = '2024-01-01';
-- 应该用：
SELECT * FROM orders WHERE create_time >= '2024-01-01' AND create_time < '2024-01-02';

-- ❌ 索引失效场景 4：like 左模糊
SELECT * FROM users WHERE name LIKE '%张'; -- 索引失效
-- 应该用：
SELECT * FROM users WHERE name LIKE '张%'; -- 索引生效

-- ❌ 索引失效场景 5：or 条件
SELECT * FROM orders WHERE user_id = ? OR order_no = ?;
-- 如果 user_id 和 order_no 都有索引，可以改用 UNION：
SELECT * FROM orders WHERE user_id = ?
UNION
SELECT * FROM orders WHERE order_no = ?;
```

### 3.2 SQL 优化

**禁止 select ***：
```sql
-- ❌ 错误示例
SELECT * FROM orders WHERE user_id = ?;

-- ✅ 正确示例
SELECT id, order_no, status, amount, create_time 
FROM orders 
WHERE user_id = ?;
```

**深分页优化**：
```sql
-- ❌ 错误示例（深分页）
SELECT * FROM orders LIMIT 1000000, 10; -- 扫描 1000010 行

-- ✅ 正确示例（主键游标分页）
SELECT id, order_no, status, amount 
FROM orders 
WHERE id > ? 
ORDER BY id 
LIMIT 10;
```

**复杂多表关联拆分**：
```sql
-- ❌ 错误示例（复杂关联）
SELECT o.*, u.name, p.product_name
FROM orders o
JOIN users u ON o.user_id = u.id
JOIN products p ON o.product_id = p.id
WHERE o.status = ? AND u.city = ? AND p.category = ?;

-- ✅ 正确示例（拆分逻辑）
-- 1. 先查订单
SELECT id, user_id, product_id 
FROM orders 
WHERE status = ?;

-- 2. 再查用户（批量查询）
SELECT id, name 
FROM users 
WHERE id IN (?, ?, ?);

-- 3. 再查商品（批量查询）
SELECT id, product_name 
FROM products 
WHERE id IN (?, ?, ?);

-- 4. 在应用层组装数据
```

## 四、第三层：架构层优化

### 4.1 读写分离

**架构设计**：
```
主从架构：
- 主库：负责新增、修改、删除
- 从库：负责查询
- 读写分离：查询流量分流至从库

生活化比喻：
就像图书馆：
- 主库：借书窗口（写操作）
- 从库：还书窗口（读操作）
- 分开处理，互不影响
```

**配置示例**：
```yaml
# application.yml
spring:
  datasource:
    master:
      url: jdbc:mysql://master:3306/db
    slave:
      url: jdbc:mysql://slave:3306/db
```

### 4.2 缓存拦截

**代码示例**：
```java
// ✅ Redis 缓存拦截重复请求
@Cacheable(value = "order", key = "#orderId")
public Order getOrder(Long orderId) {
    return orderMapper.selectById(orderId);
}

// 写入时清除缓存
@CacheEvict(value = "order", key = "#order.id")
public void updateOrder(Order order) {
    orderMapper.update(order);
}
```

**生活化比喻**：
```
就像图书馆：
- 常用书放在前台，快速借阅
- 避免每次都去书架找
```

### 4.3 慢查询监控

**配置示例**：
```ini
# my.cnf
[mysqld]
# 开启慢查询日志
slow_query_log = ON
slow_query_log_file = /var/log/mysql/slow.log
long_query_time = 1  # 超过 1 秒的查询记录
```

**监控示例**：
```bash
# 查看慢查询日志
mysqldumpslow -s t -t 10 /var/log/mysql/slow.log
```

**生活化比喻**：
```
就像图书馆：
- 记录找书时间长的读者
- 分析原因，优化流程
```

### 4.4 分库分表

**分表策略**：
```sql
-- 按年月分表
orders_2024_01
orders_2024_02
orders_2024_03
...

-- 查询时根据时间路由到对应表
SELECT * FROM orders_2024_01 WHERE user_id = ?;
```

**生活化比喻**：
```
就像图书馆：
- 按年份分不同书库
- 减小单个书库的数据量
- 查找更快
```

五、技术深入探讨

### Q1: 怎么定位慢 SQL？

**答**：
> 定位慢 SQL 的步骤：
>
> 1. **开启慢查询日志**：记录超过阈值的 SQL
> 2. **使用 explain 分析执行计划**：查看是否命中索引、扫描行数
> 3. **查看数据库监控**：CPU、IO、连接数等指标
> 4. **使用性能分析工具**：如 pt-query-digest 分析慢查询

### Q2: 索引失效的常见场景有哪些？

**答**：
> 索引失效的 5 种场景：
>
> 1. **类型转换**：字段是 VARCHAR，但查询用数字
> 2. **字段运算**：WHERE amount * 100 > 10000
> 3. **函数运算**：WHERE DATE(create_time) = '2024-01-01'
> 4. **like 左模糊**：WHERE name LIKE '%张'
> 5. **or 条件**：WHERE user_id = ? OR order_no = ?

### Q3: 深分页怎么优化？

**答**：
> 深分页优化方案：
>
> **错误示例**：`LIMIT 1000000, 10`（扫描 1000010 行）
>
> **正确示例**：主键游标分页
> ```sql
> SELECT id, order_no, status, amount 
> FROM orders 
> WHERE id > ? 
> ORDER BY id 
> LIMIT 10;
> ```
>
> 原理：利用主键索引，直接定位到起始位置，避免扫描前面的数据。
