# 分布式事务搞崩订单系统

> **场景定位**：分布式系统高级技术场景  
> **核心设计要点**：Seata AT/TCC/SAGA、空回滚、悬挂、幂等、外部系统一致性、高并发优化

---

## 🎯 一句话定位

**分布式事务搞崩订单系统解决什么问题？**
```
你说你做过微服务架构，
线上突然出现：
- 订单支付成功但库存没扣减
- 用户下单成功但收不到物流通知

你怎么排查和解决？
```

**生活化比喻**：
就像交响乐团——指挥（Seata）让小提琴（订单服务）、大提琴（库存服务）、长笛（物流服务）同时演奏。如果指挥的麦克风坏了（注册中心挂了），或者某个乐手迟到了（服务宕机），整首曲子就乱了。更麻烦的是，还有"外援"（微信支付/顺丰物流）不听你的指挥——怎么保证整场演出不出错？

---

## 💎 核心观点（5 分钟速览版）

### 核心观点（3 个关键点）

**1. 第一层：事务分级，区分强一致与最终一致**
```
核心交易链路（支付-库存-订单）：
  → 必须保证强一致性
  → 选性能高、可靠性强的方案

非核心链路（积分/通知/日志）：
  → 最终一致性方案
  → 牺牲少量一致性换取性能和可用性
```

**2. 第二层：核心方案落地，多种场景适配**
```
Seata AT 模式：
  → 适合高并发核心交易场景
  → 精准控制事务粒度
  → 缺点：大锁行数据，高并发锁冲突

SAGA 模式：
  → 适合长事务 + 跨外部系统
  → 正向操作 + 反向补偿
  → 适合涉及微信/顺丰等外部系统

本地消息表 + 定时任务：
  → 适合简单异步事务场景
  → 实现成本低，稳定可靠
```

**3. 第三层：生产落地的异常处理细节**
```
幂等性：所有接口必须设计，防止重复执行

事务状态表 + 定时对账：
  → 自动发现并修复不一致数据

事务超时 + 分级重试：
  → 避免长事务占用资源

监控告警 + 应急预案：
  → 实时跟踪事务执行状态
  → 极端情况人工介入
  → 临时降级非核心功能
```

  3. 涉及微信支付、顺丰物流这种外部系统，怎么保证最终一致性？
  4. 出现"半成功"状态的脏数据，怎么快速定位和修复？

候选人：......可以把微服务合并成单体......用 MQ 异步处理......

## 二、五大致命问题详解

### 2.1 Seata 注册中心挂了

```
问题：
  AT 模式依赖 TC（Transaction Coordinator）协调全局事务
  TC 注册在注册中心
  注册中心挂了 → TC 不可用 → 所有进行中的事务阻塞

解决方案：
  1. TC 集群部署 + 多注册中心容灾
  2. 超时降级：TC 不可用时降级为本地事务 + 定时对账
  3. 关键链路不依赖 Seata，用 TCC 或本地消息表
```

### 2.2 长链路性能问题

```
问题：
  AT 模式全程大锁行数据
  跨 6 个服务、8 个数据库 → 锁持有时间极长
  → TPS 不足 100

解决方案：
  1. 拆分大事务为多个小事务
  2. 核心链路用 AT，非核心异步化
  3. 长链路改用 SAGA 模式（无大锁）
```

### 2.3 外部系统无法参与全局事务

```
问题：
  微信支付、顺丰物流不会参与你的 Seata 事务
  它们有自己的接口和逻辑

解决方案：
  SAGA 模式 + 补偿机制：
  1. 调用微信支付的"下单接口"（正向操作）
  2. 如果后续流程失败 → 调用"退款接口"（反向补偿）
  3. 定时对账：定期拉取微信/顺丰的数据做比对
  4. 异常人工介入
```

### 2.4 "半成功"脏数据定位

```
问题：
  订单已支付、库存已扣、但物流通知没发
  事务状态处于中间态

解决方案：
  事务状态表：
  → 记录每笔事务的执行阶段
  → 定时扫描"卡住"的事务
  → 自动重试或人工介入
  
  对账系统：
  → 每日 T+1 对账
  → 订单 vs 库存 vs 支付 vs 物流
  → 发现不一致立即告警
```

### 2.5 高并发秒杀死锁

```
问题：
  AT 模式大锁行数据
  秒杀场景 10 万 QPS 同时抢 100 个商品
  → 全局锁冲突 → 死锁 / 性能瓶颈

解决方案：
  1. 秒杀链路不走 AT，走 Redis 预扣 + MQ 异步
  2. 热点数据缓存化，不直接打到数据库
  3. 分桶库存：100 个商品分成 10 桶，每桶 10 个
     → 减少锁冲突概率
```

## 三、核心方案选型指南

| 方案 | 适用场景 | 优点 | 缺点 |
|------|----------|------|------|
| **Seata AT** | 内部服务、高并发核心交易 | 接入简单、自动补偿 | 大锁、长链路性能差 |
| **TCC** | 需要高性能的强一致场景 | 无大锁、性能高 | 开发成本高（写 Confirm/Cancel） |
| **SAGA** | 长事务、跨外部系统 | 无大锁、支持外部系统 | 补偿逻辑复杂、隔离性差 |
| **本地消息表** | 简单异步场景 | 实现简单、稳定可靠 | 需要定时任务、有延迟 |

五、技术方案

### 方案参考

> "分布式事务不是加注解就完事。我分三层：
> 1. **事务分级**：核心链路（支付-库存-订单）用 TCC 或 Seata AT 强一致；非核心（积分/通知）用 SAGA 或本地消息表最终一致。
> 2. **异常处理**：所有接口幂等设计，事务状态表记录阶段状态，定时对账发现不一致数据自动修复。空回滚——Cancel 前校验有无 Try 记录；悬挂——Try 前校验有无回滚记录。
> 3. **监控降级**：实时监控事务成功率，极端情况降级非核心功能保核心链路。涉及外部系统（微信/顺丰）走 SAGA + 定时对账兜底。"

## 六、总结

> **分布式事务 = 事务分级（AT/TCC/SAGA/消息表按场景选） + 异常处理（幂等/空回滚/悬挂/对账） + 监控降级（告警+降级+人工兜底）**

### 🧠 核心记忆点

1. **不是所有场景都用 AT**——长链路/外部系统用 SAGA，高并发秒杀用 Redis+MQ。
2. **空回滚和悬挂必须处理**——Cancel 前校验 Try 记录，Try 前校验回滚记录。
3. **对账是最后防线**——T+1 对账 + 人工兜底，保证数据最终一致。
