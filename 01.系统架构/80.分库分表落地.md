# 分库分表落地

> **场景定位**：数据库架构设计场景  
> **核心设计要点**：路由查询、跨片查询、异构索引、架构优化

---

## 🎯 一句话定位

**分库分表落地解决什么问题？**
```
把大表拆成多个小表后
如何保证查询性能？
如何避免跨库查询拖垮集群？
```

**生活化比喻**：
就像图书馆分馆：
- 按分片键查询 = 直接去对应分馆（快）
- 不带分片键查询 = 每个分馆都找一遍（慢）

---

## 💎 核心观点（5 分钟速览版）

### 核心观点（5 个关键点）

**1. 路由查询 vs 跨片查询**
```
路由查询：带分片键，直接定位到分片（快）
跨片查询：不带分片键，遍历所有分片（慢）
```

**2. 跨片查询是性能灾难**
```
运营导出订单：只带时间范围，没带分片键
→ 遍历所有库所有表
→ 连接池全被打满
→ 正常用户下单卡顿
```

**3. 跨片请求限流**
```
不可避免的跨片查询
设置严格的并发数和超时阈值
避免单条请求拖垮集群
```

**4. 冗余索引表**
```
高频非分片键查询场景
建立专用索引映射表
先查索引表，再路由到分片
```

**5. 异构数据同步**
```
通过 CDC 工具同步到 ES
多维度筛选、聚合统计走 ES
不碰业务主库
```

---

## 🚀 一句话精华

> **分库分表落地 = 路由查询（带分片键） + 跨片限流（严格并发） + 冗余索引（映射表） + 异构同步（ES 承接复杂查询）**

## 一、路由查询 vs 跨片查询

### 1.1 路由查询（推荐）

```go
// 带分片键查询（快）
func GetOrder(orderID int64) (*Order, error) {
    // 根据分片键路由到对应分片
    shard := orderID % 8
    return db[shard].First(orderID)
}
```

### 1.2 跨片查询（灾难）

```go
// ❌ 不带分片键查询（慢）
func ExportOrdersByTimeRange(start, end time.Time) ([]Order, error) {
    var allOrders []Order
    
    // 遍历所有分片
    for i := 0; i < 8; i++ {
        orders, _ := db[i].Where("created_at BETWEEN ? AND ?", start, end).Find()
        allOrders = append(allOrders, orders...)
    }
    
    return allOrders, nil
}
// 问题：全表扫描，性能极差
```

## 二、跨片请求限流

```go
// 跨片查询限流
var crossShardLimiter = rate.NewLimiter(10, 5) // 每秒 10 个请求

func ExportOrdersWithLimit(start, end time.Time) ([]Order, error) {
    // 限流
    if !crossShardLimiter.Allow() {
        return nil, errors.New("跨片查询限流，请稍后重试")
    }
    
    // 设置超时
    ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
    defer cancel()
    
    return exportOrders(ctx, start, end)
}
```

## 三、冗余索引表

```go
// 建立索引映射表
type OrderIndex struct {
    OrderNo string // 订单号
    ShardID int    // 分片位置
}

// 查询时先查索引表
func GetOrderByOrderNo(orderNo string) (*Order, error) {
    // 1. 查索引表
    index, err := dbIndex.First(orderNo)
    if err != nil {
        return nil, err
    }
    
    // 2. 路由到对应分片
    return db[index.ShardID].First(index.OrderNo)
}
```

## 四、异构数据同步

### 4.1 CDC 同步到 ES

```go
// CDC 工具实时同步
func SyncToElasticsearch() {
    // 监听 MySQL binlog
    binlog.Listen(func(event *BinlogEvent) {
        if event.Table == "orders" {
            // 同步到 ES
            es.Index("orders", event.Data)
        }
    })
}

// 复杂查询走 ES
func SearchOrders(condition SearchCondition) ([]Order, error) {
    return es.Search("orders", condition)
}
```

### 4.2 从库聚合查询

```go
// 轻量跨片查询走从库
func AggregateQuery(condition Condition) ([]Order, error) {
    // 从库集群执行
    return dbSlave.Where(condition).Aggregate()
```

六、技术深入探讨

### Q1: 分库分表后多维查询怎么处理？

**方案参考**：
> 分库分表后多维查询是核心难点，解决方案：
> 
> 1. **路由查询**：带分片键的查询直接路由到对应分片
> 2. **跨片限流**：不带分片键的查询严格限流，防止拖垮集群
> 3. **冗余索引**：建立索引映射表，先查索引再路由
> 4. **异构同步**：通过 CDC 同步到 ES，复杂查询走 ES
> 
> 核心是避免全分片扫描，尽量路由到单个分片。

### Q2: 运营导出报表拖垮集群怎么办？

**方案参考**：
> 运营导出是典型的跨片查询问题，解决方案：
> 
> 1. **离线数仓**：报表导出走离线数仓，不碰在线业务库
> 2. **跨片限流**：严格限制并发数和超时时间
> 3. **异构同步**：数据同步到 ES，导出走 ES
> 4. **核心开关**：大促期间关停导出功能
> 
> 核心是隔离在线业务和离线分析，不能混用。

## 七、总结

### 🎯 一句话总结

> **分库分表落地 = 路由查询（带分片键） + 跨片限流（严格并发） + 冗余索引（映射表） + 异构同步（ES 承接复杂查询）**

### 🧠 核心记忆点

1. **路由查询**：带分片键，直接定位
2. **跨片查询**：不带分片键，性能灾难
3. **冗余索引**：映射表，先查索引
4. **异构同步**：CDC 同步到 ES
