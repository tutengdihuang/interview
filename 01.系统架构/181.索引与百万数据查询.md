# 索引与百万数据查询

> **场景定位**：数据库优化技术场景  
> **核心设计要点**：联合索引、最左匹配、回表、覆盖索引、读写分离、分库分表、冷热分离、Elasticsearch

---

## 🎯 一句话定位

**索引与百万数据查询问题是什么？**
```
加了索引，但查询还是慢：
- 订单表过亿数据，按手机号 + 时间范围查询
- 联合索引失效，回表严重
- 磁盘 IO 爆炸，查询超时
- 关联查询、模糊查询、跨分片分页全卡死
```

**生活化比喻**：就像在图书馆找书，加了索引（目录）但目录太乱（索引失效），或者要找的书分散在多个图书馆（分库分表），每次找书都要跑遍所有图书馆（磁盘 IO），效率极低。

**核心特点**：索引不是"加了就万事大吉"，而是要考虑真实业务复杂度、数据量级、查询多样性的完整优化方案。

### 核心观点（3 层优化）

**1. 精准索引 + 避免回表：基础优化**
```
联合索引设计：
- 严格遵循最左匹配原则
- 等值查询在前，范围查询在后
- 避免索引失效

覆盖索引：
- 查询字段全部在索引中
- 直接从索引取结果，无需回表
- 杜绝 SELECT *，减少随机 IO

生活化比喻：
最左匹配 = 目录按字母顺序排列（快速定位）
覆盖索引 = 目录里就有答案（不用翻书）
```

**2. 读写分离 + 冷热分离：架构优化**
```
读写分离：
- 写操作走主库
- 读操作走从库
- 减轻主库压力

冷热分离：
- 热数据（近 3 个月订单）放主库/缓存
- 历史数据（3 个月前）归档到从库或 ES
- 前台只允许查限定时间范围

生活化比喻：
读写分离 = 借书（读）和还书（写）分开窗口
冷热分离 = 常用书放阅览室（快），不常用书放仓库（慢）
```

**3. 分库分表 + 旁路查询：终极方案**
```
分库分表：
- 按用户 ID 水平分片
- 单表数据量控制在 500 万以内
- 解决单表性能瓶颈

旁路查询：
- 复杂统计、模糊查询丢给 Elasticsearch
- 后台报表走专门的分析库
- 禁掉全表扫描，加 SQL 限流与超时保护

生活化比喻：
分库分表 = 把图书馆分成多个分馆（各管各的）
旁路查询 = 复杂问题找专家（ES 擅长模糊查询）
```

## 详细章节

### 一、问题本质：为什么加了索引还是慢？

#### 1.1 索引失效的常见场景

```
1. 联合索引失效
   - 不满足最左匹配原则
   - 范围查询后的字段无法使用索引
   - 索引顺序设计不合理

2. 回表严重
   - 索引字段不包含查询字段
   - 需要回表查主键，再查数据
   - 大量随机 IO，性能极差

3. 数据量过大
   - 单表数据过亿
   - 索引树过大，查询慢
   - 磁盘 IO 成为瓶颈

4. 查询复杂度高
   - 关联查询（JOIN）
   - 模糊查询（LIKE '%keyword%'）
   - 跨分片分页、统计
```

### 二、三层优化详解

#### 2.1 第一层：精准索引 + 避免回表

**联合索引设计（最左匹配）**：

```sql
-- ❌ 错误做法：索引顺序不合理
CREATE INDEX idx_phone_time ON orders(phone, create_time);

-- 查询：按时间范围查询
SELECT * FROM orders WHERE create_time BETWEEN '2024-01-01' AND '2024-01-31';
-- 索引失效（没有用到 phone 字段）

-- ✅ 正确做法：等值查询在前，范围查询在后
CREATE INDEX idx_phone_time ON orders(phone, create_time);

-- 查询：先按手机号（等值），再按时间（范围）
SELECT * FROM orders 
WHERE phone = '13800138000' 
  AND create_time BETWEEN '2024-01-01' AND '2024-01-31';
-- 索引有效（满足最左匹配）
```

**覆盖索引（避免回表）**：

```sql
-- ❌ 错误做法：查询字段不在索引中
CREATE INDEX idx_phone_time ON orders(phone, create_time);

SELECT id, phone, create_time, amount, status 
FROM orders 
WHERE phone = '13800138000' 
  AND create_time > '2024-01-01';
-- 需要回表查 amount、status 字段

-- ✅ 正确做法：查询字段全部在索引中
CREATE INDEX idx_phone_time_amount_status 
ON orders(phone, create_time, amount, status);

SELECT id, phone, create_time, amount, status 
FROM orders 
WHERE phone = '13800138000' 
  AND create_time > '2024-01-01';
-- 覆盖索引，直接从索引取结果，无需回表
```

**杜绝 SELECT ***：

```sql
-- ❌ 错误做法：查询所有字段
SELECT * FROM orders WHERE phone = '13800138000';

-- ✅ 正确做法：只查询需要的字段
SELECT id, phone, create_time, amount, status 
FROM orders 
WHERE phone = '13800138000';
```

#### 2.2 第二层：读写分离 + 冷热分离

**读写分离架构**：

```
写操作：
  ↓
主库（Master）
  ↓
同步到从库（Slave）
  ↓
读操作：从库（Slave）
```

**代码示例**（Spring Boot + MyBatis）：

```java
// 配置多数据源
@Configuration
public class DataSourceConfig {
    
    @Bean
    @Primary
    public DataSource masterDataSource() {
        return DataSourceBuilder.create()
            .url("jdbc:mysql://master:3306/orders")
            .build();
    }
    
    @Bean
    public DataSource slaveDataSource() {
        return DataSourceBuilder.create()
            .url("jdbc:mysql://slave:3306/orders")
            .build();
    }
}

// 动态数据源路由
public class DynamicDataSource extends AbstractRoutingDataSource {
    
    @Override
    protected Object determineCurrentLookupKey() {
        // 根据上下文判断走主库还是从库
        return DataSourceContextHolder.getDataSource();
    }
}

// 使用示例
@Service
public class OrderService {
    
    // 写操作走主库
    @Transactional
    public void createOrder(Order order) {
        DataSourceContextHolder.setMaster();
        orderMapper.insert(order);
    }
    
    // 读操作走从库
    public List<Order> getOrders(String phone) {
        DataSourceContextHolder.setSlave();
        return orderMapper.selectByPhone(phone);
    }
}
```

**冷热分离**：

```java
// 订单查询服务（限定时间范围）
@Service
public class OrderQueryService {
    
    @Autowired
    private OrderMapper orderMapper;  // 主库（近 3 个月订单）
    
    @Autowired
    private OrderHistoryMapper orderHistoryMapper;  // 历史库（3 个月前订单）
    
    public List<Order> queryOrders(String phone, Date startTime, Date endTime) {
        // 判断时间范围
        Date threeMonthsAgo = DateUtils.addMonths(new Date(), -3);
        
        if (startTime.after(threeMonthsAgo)) {
            // 近 3 个月，查主库
            return orderMapper.selectByPhoneAndTimeRange(phone, startTime, endTime);
        } else if (endTime.before(threeMonthsAgo)) {
            // 3 个月前，查历史库
            return orderHistoryMapper.selectByPhoneAndTimeRange(phone, startTime, endTime);
        } else {
            // 跨时间段，合并查询
            List<Order> hotOrders = orderMapper.selectByPhoneAndTimeRange(
                phone, startTime, threeMonthsAgo
            );
            List<Order> coldOrders = orderHistoryMapper.selectByPhoneAndTimeRange(
                phone, threeMonthsAgo, endTime
            );
            
            List<Order> allOrders = new ArrayList<>();
            allOrders.addAll(hotOrders);
            allOrders.addAll(coldOrders);
            return allOrders;
        }
    }
}
```

**定时任务归档历史数据**：

```java
@Scheduled(cron = "0 0 2 * * ?")  // 每天凌晨 2 点执行
public void archiveHistoryOrders() {
    Date threeMonthsAgo = DateUtils.addMonths(new Date(), -3);
    
    // 1. 查询 3 个月前的订单
    List<Order> oldOrders = orderMapper.selectBefore(threeMonthsAgo);

    orderMapper.deleteBefore(threeMonthsAgo);
}
```

#### 2.3 第三层：分库分表 + 旁路查询

**分库分表（按用户 ID 水平分片）**：

```
分片策略：
- 按 user_id % 16 分片（16 个库/表）
- 单表数据量控制在 500 万以内
- 每个分片独立数据库，避免单点瓶颈

分片后查询：
- 按 user_id 查询：直接路由到对应分片
- 跨分片查询：需要合并多个分片结果
```

**代码示例**（ShardingSphere）：

```java
// 分片配置
@Configuration
public class ShardingConfig {
    
    @Bean
    public DataSource shardingDataSource() {
        ShardingRuleConfiguration shardingRuleConfig = new ShardingRuleConfiguration();
        
        // 订单表分片规则
        TableRuleConfiguration orderTableRuleConfig = new TableRuleConfiguration("orders");
        orderTableRuleConfig.setActualDataNodes("ds_${0..15}.orders_${0..15}");
        orderTableRuleConfig.setDatabaseShardingStrategyConfig(
            new StandardShardingStrategyConfiguration("user_id", new UserIdModShardingAlgorithm())
        );
        orderTableRuleConfig.setTableShardingStrategyConfig(
            new StandardShardingStrategyConfiguration("user_id", new UserIdModShardingAlgorithm())
        );
        
        shardingRuleConfig.getTableRuleConfigs().add(orderTableRuleConfig);
        
        // 创建分片数据源
        return ShardingDataSourceFactory.createDataSource(
            dataSourceMap, shardingRuleConfig, props
        );
    }
}

// 分片算法
public class UserIdModShardingAlgorithm implements ShardingAlgorithm<Long> {
    
    @Override
    public String doSharding(Collection<String> availableTargetNames, Long userId) {
        // 按 user_id % 16 分片
        int shardIndex = (int) (userId % 16);
        return "ds_" + shardIndex;
    }
}
```

```java
@Service
public class OrderSearchService {
    
    @Autowired
    private ElasticsearchTemplate esTemplate;
    
    // 模糊查询
    public List<Order> searchOrders(String keyword) {
        QueryBuilder queryBuilder = QueryBuilders.multiMatchQuery(
            keyword, "phone", "orderNo", "productName"
        );
        
        SearchQuery searchQuery = new NativeSearchQueryBuilder()
            .withQuery(queryBuilder)
            .withPageable(PageRequest.of(0, 20))
            .build();
        
        return esTemplate.queryForList(searchQuery, Order.class);
    }
    
    // 复杂统计
    public OrderStatistics getStatistics(Date startTime, Date endTime) {
        BoolQueryBuilder queryBuilder = QueryBuilders.boolQuery()
            .must(QueryBuilders.rangeQuery("createTime")
                .gte(startTime)
                .lte(endTime));
        
        // 按状态统计
        TermsAggregationBuilder statusAgg = AggregationBuilders
            .terms("by_status")
            .field("status");
        
        // 按金额统计
        SumAggregationBuilder amountAgg = AggregationBuilders
            .sum("total_amount")
            .field("amount");
        
        SearchQuery searchQuery = new NativeSearchQueryBuilder()
            .withQuery(queryBuilder)
            .addAggregation(statusAgg)
            .addAggregation(amountAgg)
            .build();
        
        AggregatedPage<Order> results = esTemplate.queryForPage(
            searchQuery, Order.class
        );
        
        // 解析聚合结果
        return parseStatistics(results);
    }
}
```

```java
    private RateLimiter rateLimiter = RateLimiter.create(1000);
```

### 三、完整优化方案

```java
@Service
public class OrderQueryOptimizedService {
    
    @Autowired
    private OrderMapper orderMapper;  // 主库
    
    @Autowired
    private OrderSearchService orderSearchService;  // Elasticsearch
    
    @Autowired
    private SqlRateLimiter sqlRateLimiter;
    
    /**
     * 完整的订单查询方案
     */
    public PageResult<Order> queryOrders(OrderQueryRequest request) {
        // 1. 参数校验
        validateRequest(request);
        
        // 2. 判断查询类型
        if (isComplexQuery(request)) {
            // 复杂查询（模糊查询、多条件组合）走 ES
            return orderSearchService.searchOrders(request);
        } else {
            // 简单查询走数据库
            return queryFromDatabase(request);
        }
    }
    
    private boolean isComplexQuery(OrderQueryRequest request) {
        // 模糊查询、多条件组合、跨时间段等
        return request.getKeyword() != null 
            || request.getConditions().size() > 3
            || isCrossTimeRange(request.getStartTime(), request.getEndTime());
    }
    
    private PageResult<Order> queryFromDatabase(OrderQueryRequest request) {
        // 1. 限定时间范围（最多查 3 个月）
        Date maxStartTime = DateUtils.addMonths(new Date(), -3);
        if (request.getStartTime().before(maxStartTime)) {
            request.setStartTime(maxStartTime);
        }
        
        // 2. 限流保护
        return sqlRateLimiter.executeWithRateLimit(() -> {
            return orderMapper.selectByCondition(request);
        });
    }
    
    private void validateRequest(OrderQueryRequest request) {
        // 必须指定时间范围
        if (request.getStartTime() == null || request.getEndTime() == null) {
            throw new IllegalArgumentException("必须指定时间范围");
        }
        
        // 时间范围不能超过 1 年
        long days = DateUtils.daysBetween(request.getStartTime(), request.getEndTime());
        if (days > 365) {
            throw new IllegalArgumentException("时间范围不能超过 1 年");
        }
    }
}
```

技术深入探讨

### 考点 1：联合索引失效的场景有哪些？

**方案参考**（60 分）：
```
联合索引失效的常见场景：
1. 不满足最左匹配原则
2. 范围查询后的字段无法使用索引
3. 对索引字段使用函数、计算
4. 隐式类型转换（如字符串字段传数字）
```

**加分回答**（90 分）：
```
联合索引失效的完整场景：

1. 不满足最左匹配：
   CREATE INDEX idx_a_b_c ON table(a, b, c);
   - WHERE b = 1  → 索引失效（没有用到 a）
   - WHERE a = 1 AND c = 3  → 只有 a 用到索引

2. 范围查询后的字段：
   WHERE a = 1 AND b > 2 AND c = 3
   - a、b 用到索引
   - c 无法用到索引（b 是范围查询）

3. 对索引字段使用函数：
   WHERE DATE(create_time) = '2024-01-01'
   - 索引失效（对 create_time 使用了函数）

4. 隐式类型转换：
   WHERE phone = 13800138000  （phone 是 VARCHAR）
   - 索引失效（数字隐式转换为字符串）

5. LIKE 查询：
   WHERE phone LIKE '%138%'
   - 索引失效（前缀模糊）

避免方法：
- 严格遵循最左匹配
- 等值查询在前，范围查询在后
- 不对索引字段使用函数
- 注意类型匹配
- 前缀模糊用 LIKE '138%'
```

### 考点 2：什么是回表？怎么避免？

**方案参考**（60 分）：
```
回表是指通过索引找到主键，
再通过主键查到完整数据。

避免方法：
1. 覆盖索引（查询字段全部在索引中）
2. 杜绝 SELECT *（只查询需要的字段）
```

**加分回答**（90 分）：
```
回表的完整解释：

1. 什么是回表：
   - 索引树只存储索引字段和主键
   - 查询字段不在索引中时，需要回表查主键
   - 再通过主键查到完整数据
   - 产生大量随机 IO，性能差

2. 回表的性能问题：
   - 每次回表都是一次磁盘 IO
   - 大量回表导致性能急剧下降
   - 尤其是机械硬盘（随机 IO 慢）

3. 避免回表的方法：
   
   方法一：覆盖索引
   CREATE INDEX idx_phone_time_amount_status 
   ON orders(phone, create_time, amount, status);
   
   SELECT phone, create_time, amount, status 
   FROM orders 
   WHERE phone = '13800138000';
   - 查询字段全部在索引中
   - 直接从索引取结果，无需回表
   
   方法二：杜绝 SELECT *
   ❌ SELECT * FROM orders WHERE phone = '13800138000';
   ✅ SELECT phone, create_time, amount FROM orders WHERE phone = '13800138000';
   
   - 只查询需要的字段
   - 更容易构建覆盖索引

4. 覆盖索引的代价：
   - 索引占用空间更大
   - 写入时需要更新更多索引
   - 需要权衡查询性能和写入性能

推荐方案：
高频查询构建覆盖索引，
低频查询允许回表。
```

```
第四层：旁路查询（复杂场景）
- 模糊查询、多条件组合走 Elasticsearch
- 后台报表走专门的分析库
- 禁掉全表扫描，加 SQL 限流与超时保护

关键要点：
- 分库分表后跨分片查询要谨慎
- 分页查询要优化（避免深分页）
- 统计查询走 ES 或分析库

核心思路：
不是单一方案，而是多层优化组合。
从索引设计到存储架构到风险兜底，
构建完整的查询优化体系。
```

## 总结

### 一句话总结

**海量数据查询不是"加索引"那么简单，而是从索引设计到存储架构到风险兜底的完整优化体系。**

### 核心记忆点

```
1. 三层优化：
   - 精准索引（最左匹配、覆盖索引、避免回表）
   - 读写分离 + 冷热分离（主从架构、历史归档）
   - 分库分表 + 旁路查询（水平分片、ES 旁路）

2. 关键工具：
   - 联合索引：等值在前，范围在后
   - 覆盖索引：查询字段全在索引中
   - ShardingSphere：分库分表中间件
   - Elasticsearch：复杂查询旁路

3. 核心思维：
   - 索引不是万能的（要结合业务场景）
   - 单表数据量控制在 500 万以内
   - 复杂查询不要硬刚数据库

4. 技术要点：
   - 先说索引失效的场景
   - 再说三层优化方案
   - 最后说核心思路（完整优化体系）
```
