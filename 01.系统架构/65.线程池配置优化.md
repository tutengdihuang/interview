# 线程池配置与优化

> **场景定位**：后端性能优化技术场景  
> **核心设计要点**：参数配置、阻塞队列、资源隔离、监控告警

---

## 🎯 一句话定位

**线程池解决什么问题？**
```
复用线程，降低线程创建销毁开销
控制并发度，防止资源耗尽
```

**生活化比喻**：
就像银行柜台：
- 固定窗口（核心线程）： always open
- 临时窗口（最大线程）：高峰期开放
- 等候区（阻塞队列）：排队等号
- 拒绝服务（拒绝策略）：人太多不办了

**核心特点**：参数配置只是入门，资源管控才是核心。

---

## 💎 核心观点（5 分钟速览版）

### 核心观点（5 个关键点）

**1. CPU 核数 +1 只是入门公式**
```
❌ 误区：CPU 密集型 = N+1，IO 密集型 = 2N
✅ 真相：真实业务都是混合型
必须基于压测和监控动态调优
```

**2. 阻塞队列才是调优核心**
```
90% 的线上问题都出在队列：
- 无界队列 → OOM 宕机
- 队列过小 → 频繁拒绝
- 队列过大 → 请求超时
```

**3. 任务混用是隐形杀手**
```
快任务（10ms）和慢任务（1s）混用：
慢任务霸占线程 → 快任务排队 → 整体吞吐量骤降
必须按业务隔离线程池
```

**4. 监控比参数更重要**
```
必须监控：
- 活跃线程数
- 队列积压量
- 任务拒绝次数
- 平均执行耗时
```

**5. 动态调参是高级技能**
```
线上异常不能靠重启
要支持热修改核心线程数、队列长度
秒级扩容止损
```

## 一、为什么背公式会翻车？

### ❌ CPU 核数 +1 的局限性

**生活化比喻**：
```
公式说：CPU 密集型 = N+1（N 是 CPU 核数）
但真实业务：
- 30% 时间计算（CPU 密集）
- 50% 时间查数据库（IO 密集）
- 20% 时间调远程接口（IO 密集）

硬套公式 → 线程数太少 → 性能瓶颈
```

**真实场景分析**：
```go
// 典型业务接口
func HandleOrderRequest() {
    // 1. 参数校验（CPU 计算）
    validateParams()
    
    // 2. 查询数据库（IO 等待）
    order := db.Query("...")
    
    // 3. 调用风控接口（IO 等待）
    riskResult := rpc.Call("...")
    
    // 4. 业务计算（CPU 计算）
    result := calculate(order, riskResult)
    
    // 5. 写入数据库（IO 等待）
    db.Insert(result)
}
// 实际是混合型，无法简单归类
```

## 二、正确配置思路

### 2.1 基于压测动态调优

**核心方法**：
```
1. 压测环境测试不同参数组合
2. 找到吞吐量最高的参数
3. 观察 CPU、内存、IO 使用率
4. 线上灰度验证
5. 监控持续调优
```

**压测示例**：
```go
func BenchmarkThreadPool(b *testing.B) {
    configs := []ThreadPoolConfig{
        {CoreSize: 10, MaxSize: 20, QueueSize: 1000},
        {CoreSize: 20, MaxSize: 40, QueueSize: 2000},
        {CoreSize: 50, MaxSize: 100, QueueSize: 5000},
    }
    
    for _, config := range configs {
        pool := NewThreadPool(config)
        
        start := time.Now()
        var wg sync.WaitGroup
        
        for i := 0; i < b.N; i++ {
            wg.Add(1)
            pool.Submit(func() {
                defer wg.Done()
                handleRequest()
            })
        }
        
        wg.Wait()
        duration := time.Since(start)
        
        fmt.Printf("Config: %+v, QPS: %d\n", config, b.N/int(duration.Seconds()))
    }
}
```

### 2.2 阻塞队列选型

**三类队列对比**：
```
LinkedBlockingQueue（无界）：
- 优点：不会拒绝任务
- 缺点：任务堆积 → OOM
- 场景：任务量可控的后台任务

ArrayBlockingQueue（有界）：
- 优点：防止 OOM
- 缺点：队列满直接拒绝
- 场景：核心业务接口

SynchronousQueue（同步）：
- 优点：零延迟
- 缺点：不缓冲，直接创建线程
- 场景：低延迟要求
```

**推荐配置**：
```go
type ThreadPoolConfig struct {
    CoreSize    int           // 核心线程数
    MaxSize     int           // 最大线程数
    QueueSize   int           // 队列容量（必须有界）
    KeepAlive   time.Duration // 非核心线程存活时间
    RejectPolicy RejectPolicy // 拒绝策略
}

// 核心业务接口
config := ThreadPoolConfig{
    CoreSize:  50,
    MaxSize:   100,
    QueueSize: 2000, // 有界队列
    KeepAlive: 60 * time.Second,
    RejectPolicy: RejectPolicyCallerRuns, // 调用方运行
}
```

## 三、资源隔离（架构级优化）

### 3.1 按业务隔离

**问题场景**：
```
订单接口和导出接口共用线程池：
- 导出接口：单次处理 10s
- 订单接口：单次处理 50ms

导出任务霸占线程 → 订单请求排队 → 用户体验极差
```

**解决方案**：
```go
// 核心业务线程池（订单、支付）
orderPool := NewThreadPool(ThreadPoolConfig{
    CoreSize: 50,
    MaxSize:  100,
    QueueSize: 2000,
})

// 非核心业务线程池（导出、统计）
exportPool := NewThreadPool(ThreadPoolConfig{
    CoreSize: 5,
    MaxSize:  10,
    QueueSize: 100,
})

// 业务路由
func HandleRequest(req *Request) {
    if req.IsCoreBiz() {
        orderPool.Submit(req.Handle)
    } else {
        exportPool.Submit(req.Handle)
    }
}
```

### 3.2 超时控制

**问题场景**：
```
线程池任务卡死（调用第三方超时）：
- 线程被永久占用
- 队列堆积越来越多
- 最终线程池耗尽
```

**解决方案**：
```go
func (p *ThreadPool) SubmitWithTimeout(task Task, timeout time.Duration) error {
    ctx, cancel := context.WithTimeout(context.Background(), timeout)
    defer cancel()
    
    done := make(chan error, 1)
    
    p.Submit(func() {
        done <- task.Execute()
    })
    
    select {
    case err := <-done:
        return err
    case <-ctx.Done():
        // 超时，记录日志，触发告警
        log.Error("task timeout")
        return errors.New("task timeout")
    }
}
```

## 四、监控告警

### 4.1 核心指标

**必须监控**：
```go
type ThreadPoolMetrics struct {
    ActiveCount    int64 // 活跃线程数
    PoolSize       int64 // 当前线程数
    QueueSize      int64 // 队列积压量
    CompletedCount int64 // 完成任务数
    RejectedCount  int64 // 拒绝次数
    AvgExecuteTime int64 // 平均执行耗时
}

// 每秒采集
func (m *ThreadPoolMetrics) Collect(pool *ThreadPool) {
    m.ActiveCount = pool.GetActiveCount()
    m.PoolSize = pool.GetPoolSize()
    m.QueueSize = pool.GetQueueSize()
    m.CompletedCount = pool.GetCompletedCount()
    m.RejectedCount = pool.GetRejectedCount()
    m.AvgExecuteTime = pool.GetAvgExecuteTime()
}
```

**告警规则**：
```yaml
# Prometheus 告警规则
groups:
  - name: threadpool
    rules:
      - alert: ThreadPoolExhausted
        expr: threadpool_active_count / threadpool_max_size > 0.8
        for: 1m
        annotations:
          summary: "线程池活跃线程超过 80%"
          
      - alert: ThreadPoolQueueFull
        expr: threadpool_queue_size / threadpool_queue_capacity > 0.8
        for: 1m
        annotations:
          summary: "线程池队列积压超过 80%"
          
      - alert: ThreadPoolRejected
        expr: rate(threadpool_rejected_count[5m]) > 0
        annotations:
          summary: "线程池存在拒绝任务"
```

### 4.2 动态调参

**热修改配置**：
```go
type DynamicThreadPool struct {
    *ThreadPool
    configCenter ConfigCenter
}

// 监听配置中心
func (p *DynamicThreadPool) WatchConfig() {
    p.configCenter.Watch("threadpool.order", func(config string) {
        var newConfig ThreadPoolConfig
        json.Unmarshal([]byte(config), &newConfig)
        
        // 热修改核心参数
        p.SetCoreSize(newConfig.CoreSize)
        p.SetMaxSize(newConfig.MaxSize)
        p.SetQueueSize(newConfig.QueueSize)
        
        log.Info("threadpool config updated: %+v", newConfig)
    })
}
```

五、技术深入探讨

### Q1: 线程池耗尽怎么排查？

**方案参考**：
> 线程池耗尽是常见问题，排查分三步：
> 
> 1. **看监控**：活跃线程数、队列积压量、拒绝次数
> 2. **查日志**：是否有大量慢任务、超时任务
> 3. **分析原因**：
>    - 流量突增 → 扩容 + 限流
>    - 慢任务堆积 → 优化任务逻辑
>    - 下游超时 → 加熔断降级
> 
> 关键是要有监控，不能等用户反馈才发现问题。

### Q2: 为什么阿里禁止用 Executors 默认方法？

**方案参考**：
> Executors 默认方法有三大坑：
> 
> 1. **newFixedThreadPool/newSingleThread**：无界队列（LinkedBlockingQueue），任务堆积 → OOM
> 2. **newCachedThreadPool**：最大线程数 Integer.MAX_VALUE，创建大量线程 → OOM
> 3. **newScheduledThreadPool**：最大线程数 Integer.MAX_VALUE，同样有 OOM 风险
> 
> 必须手动创建 ThreadPoolExecutor，明确指定有界队列和最大线程数。

## 六、总结

### 🎯 一句话总结

> **线程池 = 参数配置（压测调优） + 队列选型（有界优先） + 资源隔离（业务分级） + 监控告警（动态调参）**

### 🧠 核心记忆点

1. **背公式会翻车**：真实业务是混合型，必须压测调优
2. **队列是核心**：90% 的问题出在队列选型
3. **资源隔离**：快慢任务分离，防止互相影响
4. **监控告警**：没有监控的线程池是定时炸弹
