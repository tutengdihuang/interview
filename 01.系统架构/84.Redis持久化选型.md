# Redis持久化选型

> **场景定位**：Redis 架构技术场景  
> **核心设计要点**：RDB/AOF选型、fork阻塞、性能权衡、架构优化

---

## 🎯 一句话定位

**Redis持久化选型解决什么问题？**
```
数据不丢 vs 性能影响
如何平衡？
```

**生活化比喻**：
就像写日记：
- RDB：每天拍张照片（快照，快但可能丢数据）
- AOF：每笔都记下来（日志，慢但数据完整）

---

## 💎 核心观点（5 分钟速览版）

### 核心观点（5 个关键点）

**1. RDB + AOF 混合不是万能的**
```
❌ 误区：开混合持久化就完事
✅ 真相：fork 进程阻塞主线程
高流量下周期性卡顿
```

**2. 业务分级匹配**
```
核心不可重建数据：高可靠持久化
可重建业务数据：关闭或降低频率
```

**3. 错峰持久化**
```
避开业务高峰期触发快照
高负载时自动暂缓
```

**4. 主从角色分离**
```
主库：关闭持久化，承接业务
从库：负责持久化与备份
```

**5. 实例拆分**
```
热点数据与冷数据分离
差异化持久化策略
```

---

## 🚀 一句话精华

> **持久化选型 = 业务分级（核心/可重建） + 错峰调度（避开高峰） + 主从分离（主库关闭/从库持久化） + 实例拆分（热点/冷数据分离）**

## 一、持久化机制对比

### 1.1 RDB 快照

```
优点：
- 文件紧凑，恢复速度快
- fork 子进程执行，不阻塞主线程（理想情况）

缺点：
- 可能丢失最后一次快照后的数据
- fork 大内存时阻塞主线程
```

### 1.2 AOF 日志

```
优点：
- 数据完整性高
- 支持多种刷盘策略

缺点：
- 文件体积大
- 恢复速度慢
- IO 开销大
```

### 1.3 混合持久化

```
优点：
- 兼顾速度和完整性

缺点：
- fork 阻塞问题依然存在
- 配置复杂
```

## 二、业务分级匹配

```go
// 核心不可重建数据：高可靠持久化
type CoreDataStrategy struct {
    rdbEnabled: true,
    aofEnabled: true,
    aofSyncPolicy: "always", // 每次写入都刷盘
}

// 可重建业务数据：关闭或降低频率
type RebuildableDataStrategy struct {
    rdbEnabled: false,
    aofEnabled: false,
    // 数据丢失后可从数据库回源
}
```

## 三、错峰持久化调度

```go
// 错峰调度
func SchedulePersistence() {
    // 避开业务高峰期
    if isPeakHour() {
        // 高峰期暂缓持久化
        return
    }
    
    // 低峰期执行快照
    if isLowPeakHour() {
        triggerRDBSnapshot()
    }
}

// 流量阈值联动
func PersistenceWithThreshold() {
    qps := getRedisQPS()
    
    if qps > 10000 {
        // 高负载暂缓持久化
        disablePersistence()
    } else {
        enablePersistence()
    }
}
```

## 四、主从角色分离

```go
// 主库配置：关闭持久化
masterConfig := RedisConfig{
    rdbEnabled: false,
    aofEnabled: false,
    // 全力承接业务读写
}

// 从库配置：负责持久化
slaveConfig := RedisConfig{
    rdbEnabled: true,
    aofEnabled: true,
    aofSyncPolicy: "everysec",
    // 负责持久化与备份
}
```

**优势**：
- 主库性能不受持久化影响
- 从库负责备份，故障时可快速切换

八、技术深入探讨

### Q1: Redis持久化怎么选？

**方案参考**：
> 持久化选型根据业务场景分级：
> 
> 1. **核心不可重建数据**：RDB + AOF 混合，高可靠策略
> 2. **可重建业务数据**：关闭持久化，从数据库回源
> 3. **主从分离**：主库关闭持久化，从库负责备份
> 4. **实例拆分**：热点数据关闭持久化，冷数据开启
> 
> 核心是平衡数据不丢和性能影响。

### Q2: 为什么开了持久化还是会卡顿？

**方案参考**：
> 卡顿原因：
> 
> 1. **fork 阻塞**：大内存 fork 子进程阻塞主线程
> 2. **AOF 刷盘延迟**：IO 开销导致性能下降
> 3. **全量重写**：AOF 重写期间性能下降
> 
> 解决方案：
> 1. 错峰持久化，避开业务高峰
> 2. 主从分离，主库关闭持久化
> 3. 控制单实例内存上限
> 4. 关闭透明大页，优化系统参数

## 九、总结

### 🎯 一句话总结

> **持久化选型 = 业务分级（核心/可重建） + 错峰调度（避开高峰） + 主从分离（主库关闭/从库持久化） + 实例拆分（热点/冷数据分离）**

### 🧠 核心记忆点

1. **业务分级**：核心数据高可靠，可重建数据关闭持久化
2. **主从分离**：主库关闭，从库负责
3. **实例拆分**：热点关闭，冷数据开启
4. **错峰调度**：避开业务高峰
