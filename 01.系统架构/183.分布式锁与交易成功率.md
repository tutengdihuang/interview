## 详细章节

### 一、问题本质：死锁是如何产生的？

#### 1.1 死锁的四个必要条件

```
1. 互斥条件（Mutual Exclusion）：
   - 资源一次只能被一个事务占用
   - 其他事务必须等待

2. 持有并等待（Hold and Wait）：
   - 事务持有至少一个资源
   - 同时等待获取其他资源

3. 不可抢占（No Preemption）：
   - 资源只能由持有者释放
   - 不能被强制抢占

4. 循环等待（Circular Wait）：
   - 多个事务形成环状等待链
   - A 等 B，B 等 C，C 等 A
```

#### 1.2 死锁场景示例

```sql
-- 事务 A
BEGIN;
UPDATE account SET balance = balance - 100 WHERE user_id = 1;  -- 锁住用户 1
UPDATE account SET balance = balance + 100 WHERE user_id = 2;  -- 等待用户 2

-- 事务 B（同时执行）
BEGIN;
UPDATE account SET balance = balance - 50 WHERE user_id = 2;   -- 锁住用户 2
UPDATE account SET balance = balance + 50 WHERE user_id = 1;   -- 等待用户 1

-- 死锁：
-- 事务 A 持有用户 1，等待用户 2
-- 事务 B 持有用户 2，等待用户 1
-- 循环等待，形成死锁
```

**根因分析**：

```
常见死锁原因：

1. 间隙锁冲突（Gap Lock）：
   - InnoDB 在 RR 隔离级别下使用间隙锁
   - 多个事务锁定相同的间隙
   - 形成死锁
   
   示例：
   BEGIN;
   SELECT * FROM orders WHERE status = 'pending' FOR UPDATE;
   -- 锁定 status='pending' 的间隙
   
   另一个事务：
   BEGIN;
   INSERT INTO orders (status) VALUES ('pending');
   -- 等待间隙锁释放

2. 索引缺失导致全表锁：
   - WHERE 条件字段没有索引
   - InnoDB 锁定全表
   - 多个事务互相等待
   
   示例：
   UPDATE account SET balance = 100 WHERE phone = '13800138000';
   -- phone 字段没有索引，全表锁

3. 事务执行顺序不一致：
   - 事务 A：先锁用户 1，再锁用户 2
   - 事务 B：先锁用户 2，再锁用户 1
   - 循环等待，形成死锁
   
   示例：
   -- 事务 A
   UPDATE account SET balance = balance - 100 WHERE user_id = 1;
   UPDATE account SET balance = balance + 100 WHERE user_id = 2;
   
   -- 事务 B
   UPDATE account SET balance = balance - 50 WHERE user_id = 2;
   UPDATE account SET balance = balance + 50 WHERE user_id = 1;
```

```java
// 死锁监控服务
@Service
public class DeadlockMonitor {
    
    @Autowired
    private DataSource dataSource;
    
    @Autowired
    private AlertService alertService;
    
    // 每 30 秒检查一次
    @Scheduled(fixedRate = 30000)
    public void monitorDeadlocks() {

            // 1. 查询当前锁等待
            ResultSet rs = conn.createStatement().executeQuery(
                "SELECT * FROM information_schema.innodb_lock_waits"

                lockWaitCount++;

                "SELECT trx_mysql_thread_id, trx_state, trx_started " +

                "WHERE TIMESTAMPDIFF(SECOND, trx_started, NOW()) > 10"
```

### 三、完整死锁处理方案

```java
@Service
public class AccountService {
    
    @Autowired
    private AccountMapper accountMapper;
    
    @Autowired
    private RiskService riskService;
    
    @Autowired
    private AsyncService asyncService;
    
    /**
     * 转账操作（避免死锁）
     */
    public void transfer(Long fromUserId, Long toUserId, BigDecimal amount) {
        // 1. 参数校验（不在事务中）
        validateTransferParams(fromUserId, toUserId, amount);
        
        // 2. 风控检查（不在事务中）
        RiskCheckResult riskResult = riskService.check(fromUserId, amount);
        if (!riskResult.isSafe()) {
            throw new RiskException("风控检查失败");
        }
        
        // 3. 核心事务（尽量短）
        doTransfer(fromUserId, toUserId, amount);
        
        // 4. 异步记录流水（不在事务中）
        asyncService.recordTransactionLog(fromUserId, toUserId, amount);
    }
    
    @Transactional(timeout = 5)  // 事务超时 5 秒
    protected void doTransfer(Long fromUserId, Long toUserId, BigDecimal amount) {
        // 按 user_id 排序，避免循环等待
        Long firstUserId = Math.min(fromUserId, toUserId);
        Long secondUserId = Math.max(fromUserId, toUserId);
        
        // 1. 锁定第一个账户
        Account firstAccount = accountMapper.selectForUpdate(firstUserId);
        
        // 2. 锁定第二个账户
        Account secondAccount = accountMapper.selectForUpdate(secondUserId);
        
        // 3. 执行转账
        if (fromUserId.equals(firstUserId)) {
            // fromUserId < toUserId
            accountMapper.deductBalance(fromUserId, amount);
            accountMapper.addBalance(toUserId, amount);
        } else {
            // fromUserId > toUserId
            accountMapper.addBalance(toUserId, amount);
            accountMapper.deductBalance(fromUserId, amount);
        }
    }
    
    private void validateTransferParams(Long fromUserId, Long toUserId, BigDecimal amount) {
        if (fromUserId == null || toUserId == null) {
            throw new IllegalArgumentException("用户 ID 不能为空");
        }
        if (amount == null || amount.compareTo(BigDecimal.ZERO) <= 0) {
            throw new IllegalArgumentException("转账金额必须大于 0");
        }
    }
}
```

### 考点 2：如何避免死锁？

**方案参考**（60 分）：
```
避免死锁的方法：
1. 控制事务时长（尽量短）
2. 按固定顺序访问资源（避免循环等待）
3. 使用索引（避免全表锁）
4. 降低隔离级别（如 RC）
```

**加分回答**（90 分）：
```
避免死锁的完整方案：

1. 重构事务边界：
   - 拆分大事务为小事务
   - 非核心操作移到事务外
   - 控制事务时长（如 5 秒内）
   
   示例：
   // ❌ 大事务
   @Transactional
   public void transfer(...) {
       riskCheck();  // 耗时
       deductBalance();
       addBalance();
       recordLog();  // 耗时
   }
   
   // ✅ 拆分事务
   public void transfer(...) {
       riskCheck();  // 事务外
       doTransfer();  // 核心事务
       recordLog();  // 事务外
   }

2. 按固定顺序访问资源：
   - 按 user_id 排序，先锁小的，再锁大的
   - 避免循环等待
   
   Long firstUserId = Math.min(fromUserId, toUserId);
   Long secondUserId = Math.max(fromUserId, toUserId);
   accountMapper.selectForUpdate(firstUserId);
   accountMapper.selectForUpdate(secondUserId);

3. 热点账户优化：
   - 队列化处理（串行化）
   - 乐观锁（CAS）
   - 避免悲观锁冲突

4. 死锁监控：
   - 开启精细化死锁监控
   - 配置自动告警
   - 及时发现和处理死锁

5. 索引优化：
   - WHERE 条件字段加索引
   - 避免全表锁
   - 减少锁范围

核心思路：
从事务设计、资源访问顺序、热点账户优化、
监控告警等多个维度，全方位避免死锁。
```

**方案参考**（60 分）：

```
生产环境死锁处理：
1. 立即查看死锁日志
2. 找到死锁事务的线程 ID
3. 果断 kill 死锁事务
4. 恢复核心业务
5. 事后分析根因，优化架构
```

**加分回答**（90 分）：
```
生产环境死锁的完整处理流程：

1. 紧急止血（10 分钟内）：
   - 立即查看死锁日志
     SHOW ENGINE INNODB STATUS;
   - 找到死锁事务的线程 ID
     SELECT trx_mysql_thread_id FROM information_schema.innodb_trx;
   - 果断 kill 死锁事务
     KILL thread_id;
   - 优先恢复核心交易链路
   - 发送告警通知相关人员

2. 根因分析（1 小时内）：
   - 提取死锁日志详细信息
   - 分析锁类型和等待关系
   - 判断根因（间隙锁、索引缺失、循环等待）
   - 测试环境复现问题

3. 架构优化（1-3 天）：
   - 重构事务边界，控制事务时长
   - 热点账户队列化处理或乐观锁
   - 按固定顺序访问资源
   - 开启死锁监控，配置告警

4. 验证上线：
   - 测试环境验证优化效果
   - 灰度上线
   - 监控死锁指标
   - 确认无死锁后全量上线

5. 复盘总结：
   - 分析死锁根因
   - 总结处理经验
   - 完善监控告警
   - 制定预防措施

核心思路：
生产环境死锁处理要快、准、稳。
先止血恢复业务，再定位根因，最后优化架构。
建立完善的监控告警体系，防患于未然。
```

## 总结

### 一句话总结

**死锁不是技术彩蛋，而是系统设计缺陷的放大镜，能快速解决生产突发死锁问题才是后端工程师的核心硬实力。**

### 核心记忆点

```
1. 死锁急救三步曲：
   - 紧急止血：锁定死锁链条，终止堵塞源头
   - 精准定位：提取死锁日志，根因分析
   - 架构优化：重构事务边界，热点账户优化

2. 死锁四大必要条件：
   - 互斥条件
   - 持有并等待
   - 不可抢占
   - 循环等待

3. 避免死锁的方法：
   - 控制事务时长（拆分大事务）
   - 按固定顺序访问资源（避免循环等待）
   - 热点账户优化（队列化、乐观锁）
   - 使用索引（避免全表锁）
   - 死锁监控告警

4. 关键工具：
   - SHOW ENGINE INNODB STATUS（查看死锁）
   - information_schema.innodb_lock_waits（查看锁等待）
   - information_schema.innodb_trx（查看活跃事务）

5. 技术要点：
   - 先说死锁产生的原因（四个必要条件）
   - 再说排查方法（日志、锁等待、活跃事务）
   - 最后说避免方法（事务设计、资源顺序、监控）
```
