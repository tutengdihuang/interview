## 💎 核心观点（5 分钟速览版）

> **快速概览**

### 核心观点（三大问题解决方案）

**第一层：索引失效五种核心场景**
```
场景 1：联合索引不满足最左前缀法则
- 联合索引 (a, b, c)
- 查询 WHERE b = ? 或 WHERE c = ? → 失效

场景 2：使用 select * 导致回表
- 无法命中索引字段

场景 3：索引字段出现隐式类型转换
- 字段是 VARCHAR，查询用数字 → 失效

场景 4：索引列使用函数运算
- WHERE DATE(create_time) = '2024-01-01' → 失效

场景 5：模糊查询前置百分号
- WHERE name LIKE '%张' → 失效

解决方案：
- 遵循联合索引最左前缀原则
- 禁止索引列做运算、函数、隐式转换
- 模糊查询后置百分号
- 少用 select *，只查需要字段
- or 条件两侧都加索引或改用 union

生活化比喻：
就像图书馆：
- 最左前缀：必须从第一级分类开始找
- 类型转换：书号是数字，但用字符串找
- 函数运算：找"今天归还的书"，但系统只能按日期找
```

**第二层：死锁四种核心场景**
```
场景 1：事务并发操作同一批数据，加锁顺序相反
- 事务 A：锁定行 1 → 锁定行 2
- 事务 B：锁定行 2 → 锁定行 1
- 互相等待 → 死锁

场景 2：事务持有锁不释放，长时间占用资源
- 事务执行时间过长
- 其他事务等待超时

场景 3：间隙锁、临间锁在范围查询时互相堵塞
- 范围查询锁定间隙
- 其他事务无法插入

场景 4：事务隔离级别过高，锁范围扩大
- RR 隔离级别比 RU 锁定范围更大

解决方案：
- 打破死锁四个必要条件
- 统一事务加锁顺序
- 缩短事务执行时间，避免长事务
- 合理设置事务隔离级别
- 核心业务用 RC 隔离级别
- 开启死锁检测，配置死锁超时时间
- 出现死锁后查看死锁日志，定位根因优化

生活化比喻：
就像两个人借书：
- 统一加锁顺序：都先借 A 书，再借 B 书
- 缩短事务：借书尽快完成
- 死锁检测：图书管理员发现死锁，强制一人归还
```

**第三层：慢查询三种核心原因**
```
原因 1：没有建立合适索引，全表扫描
- 查询字段没有索引
- 索引失效

原因 2：SQL 语句写法糟糕
- 关联表过多
- 嵌套查询
- select *

原因 3：数据库参数不合理
- 连接数设置不当
- 缓存池设置不当

解决方案：
- 开启慢查询日志
- 用 explain 分析执行计划
- 为高频查询字段建立合适索引
- 优化 SQL 语句，拆分复杂查询
- 减少关联
- 优化数据库参数
- 调整 innodb_buffer_pool_size
- 分库分表，减少单表数据量

生活化比喻：
就像图书馆：
- 建索引：给书分类，快速找到
- 优化 SQL：不要一次找所有书
- 优化参数：增加图书管理员，扩大书库
```

## 二、第一层：索引失效五种核心场景

### 2.1 场景 1：联合索引不满足最左前缀法则

**示例**：
```sql
-- 联合索引：(user_id, status, create_time)

-- ✅ 命中索引
SELECT * FROM orders WHERE user_id = ?;
SELECT * FROM orders WHERE user_id = ? AND status = ?;
SELECT * FROM orders WHERE user_id = ? AND status = ? AND create_time = ?;

-- ❌ 不命中索引
SELECT * FROM orders WHERE status = ?; -- 缺少 user_id
SELECT * FROM orders WHERE create_time = ?; -- 缺少 user_id 和 status
```

### 2.2 场景 2：使用 select * 导致回表

**示例**：
```sql
-- ❌ 错误示例
SELECT * FROM orders WHERE user_id = ?;
-- 需要回表查询所有字段，可能无法命中覆盖索引

-- ✅ 正确示例
SELECT id, order_no, status, amount 
FROM orders 
WHERE user_id = ?;
-- 只查询必要字段，可能命中覆盖索引
```

### 2.3 场景 3：索引字段出现隐式类型转换

**示例**：
```sql
-- phone 字段是 VARCHAR 类型

-- ❌ 错误示例（隐式转换）
SELECT * FROM users WHERE phone = 13800138000;
-- 数字会被转换为字符串，导致索引失效

-- ✅ 正确示例
SELECT * FROM users WHERE phone = '13800138000';
```

### 2.4 场景 4：索引列使用函数运算

**示例**：
```sql
-- ❌ 错误示例
SELECT * FROM orders WHERE DATE(create_time) = '2024-01-01';
-- 对索引列使用函数，导致索引失效

-- ✅ 正确示例
SELECT * FROM orders 
WHERE create_time >= '2024-01-01' 
AND create_time < '2024-01-02';
```

### 2.5 场景 5：模糊查询前置百分号

**示例**：
```sql
-- ❌ 错误示例
SELECT * FROM users WHERE name LIKE '%张';
-- 前置百分号导致索引失效

-- ✅ 正确示例
SELECT * FROM users WHERE name LIKE '张%';
-- 后置百分号可以命中索引
```

### 2.6 or 条件处理

**示例**：
```sql
-- ❌ 错误示例
SELECT * FROM orders WHERE user_id = ? OR order_no = ?;
-- 如果 user_id 和 order_no 都有索引，or 条件可能导致索引失效

-- ✅ 正确示例
SELECT * FROM orders WHERE user_id = ?
UNION
SELECT * FROM orders WHERE order_no = ?;
-- 改用 UNION，两个查询都能命中索引
```

## 三、第二层：死锁四种核心场景

### 3.1 死锁的四个必要条件

1. **互斥条件**：资源不能共享，一次只能被一个事务使用
2. **持有并等待**：事务持有至少一个资源，并等待获取其他资源
3. **不可抢占**：事务已获得的资源不能被强制剥夺
4. **循环等待**：事务之间形成循环等待链

### 3.2 场景 1：加锁顺序相反

**示例**：
```sql
-- 事务 A
START TRANSACTION;
UPDATE orders SET status = 1 WHERE id = 1; -- 锁定行 1
UPDATE orders SET status = 1 WHERE id = 2; -- 等待行 2

-- 事务 B
START TRANSACTION;
UPDATE orders SET status = 1 WHERE id = 2; -- 锁定行 2
UPDATE orders SET status = 1 WHERE id = 1; -- 等待行 1

-- 死锁：A 等待 B 释放行 2，B 等待 A 释放行 1
```

**解决方案**：
```sql
-- ✅ 统一加锁顺序
-- 事务 A 和 B 都先锁定行 1，再锁定行 2
UPDATE orders SET status = 1 WHERE id = 1;
UPDATE orders SET status = 1 WHERE id = 2;
```

### 3.3 场景 2：事务持有锁不释放

**示例**：
```sql
-- ❌ 长事务
START TRANSACTION;
-- 执行大量业务逻辑（耗时 10 秒）
UPDATE orders SET status = 1 WHERE id = 1;
-- 其他事务等待 10 秒
COMMIT;
```

**解决方案**：
```sql
-- ✅ 缩短事务执行时间
START TRANSACTION;
UPDATE orders SET status = 1 WHERE id = 1;
COMMIT;
-- 事务执行时间 < 1 秒
```

### 3.4 场景 3：间隙锁、临间锁

**示例**：
```sql
-- 事务 A
START TRANSACTION;
SELECT * FROM orders WHERE id > 10 FOR UPDATE;
-- 锁定 id > 10 的所有行和间隙

-- 事务 B
START TRANSACTION;
INSERT INTO orders (id, user_id) VALUES (15, 1);
-- 等待事务 A 释放间隙锁
```

**解决方案**：
```sql
-- ✅ 降低隔离级别到 RC
SET SESSION tx_isolation = 'READ-COMMITTED';
-- RC 隔离级别没有间隙锁
```

### 3.5 场景 4：事务隔离级别过高

**对比**：
```
RU（读未提交）：
- 锁范围最小
- 但会有脏读

RC（读已提交）：
- 锁范围中等
- 解决脏读

RR（可重复读）：
- 锁范围最大
- 解决脏读、不可重复读
- 但容易出现死锁
```

**解决方案**：
```sql
-- ✅ 核心业务用 RC 隔离级别
SET SESSION tx_isolation = 'READ-COMMITTED';
```

### 3.6 死锁排查与处理

**排查步骤**：
```bash
# 1. 查看死锁日志
SHOW ENGINE INNODB STATUS;

# 2. 查看当前锁等待
SELECT * FROM information_schema.innodb_lock_waits;

# 3. 查看当前锁
SELECT * FROM information_schema.innodb_locks;
```

**处理方案**：
```sql
-- 开启死锁检测
SET GLOBAL innodb_deadlock_detect = ON;

-- 配置死锁超时时间
SET GLOBAL innodb_lock_wait_timeout = 50; -- 50 秒
```

## 四、第三层：慢查询三种核心原因

### 4.1 原因 1：没有建立合适索引

**解决方案**：
```sql
-- 为高频查询字段建立索引
CREATE INDEX idx_user_id ON orders(user_id);
CREATE INDEX idx_create_time ON orders(create_time);
```

### 4.2 原因 2：SQL 语句写法糟糕

**解决方案**：
```sql
-- ❌ 错误示例
SELECT o.*, u.name, p.product_name
FROM orders o
JOIN users u ON o.user_id = u.id
JOIN products p ON o.product_id = p.id
WHERE o.status = ? AND u.city = ? AND p.category = ?;

-- ✅ 正确示例（拆分逻辑）
-- 1. 先查订单
SELECT id, user_id, product_id FROM orders WHERE status = ?;

-- 2. 再查用户（批量查询）
SELECT id, name FROM users WHERE id IN (?, ?, ?);

-- 3. 再查商品（批量查询）
SELECT id, product_name FROM products WHERE id IN (?, ?, ?);

-- 4. 在应用层组装数据
```

### 4.3 原因 3：数据库参数不合理

**解决方案**：
```ini
# my.cnf
[mysqld]
# 调整连接数
max_connections = 1000

# 调整缓存池
innodb_buffer_pool_size = 4G

# 调整日志缓冲
innodb_log_buffer_size = 64M
```

### 4.4 慢查询定位与优化

**定位步骤**：
```bash
# 1. 开启慢查询日志
slow_query_log = ON
slow_query_log_file = /var/log/mysql/slow.log
long_query_time = 1  # 超过 1 秒的查询记录

# 2. 查看慢查询日志
mysqldumpslow -s t -t 10 /var/log/mysql/slow.log
```

**优化步骤**：
```sql
-- 1. 用 explain 分析执行计划
EXPLAIN SELECT * FROM orders WHERE user_id = ?;

-- 查看：
-- type：查询类型（system > const > eq_ref > ref > range > index > ALL）
-- key：命中的索引
-- rows：扫描行数
-- Extra：额外信息（Using index, Using where, Using filesort 等）

-- 2. 根据执行计划优化
-- type 为 ALL：全表扫描，需要加索引
-- key 为 NULL：没有命中索引，需要检查索引
-- rows 很大：扫描行数太多，需要优化索引或分表
```

五、技术深入探讨

### Q1: 联合索引失效的规则有哪些？

**答**：
> 联合索引失效的 5 种规则：
>
> 1. **不满足最左前缀法则**：联合索引 (a, b, c)，查询 WHERE b = ? 或 WHERE c = ?
> 2. **使用 select ***：导致回表，无法命中覆盖索引
> 3. **隐式类型转换**：字段是 VARCHAR，查询用数字
> 4. **函数运算**：WHERE DATE(create_time) = '2024-01-01'
> 5. **模糊查询前置百分号**：WHERE name LIKE '%张'

### Q2: 死锁的四个必要条件是什么？

**答**：
> 死锁的四个必要条件：
>
> 1. **互斥条件**：资源不能共享，一次只能被一个事务使用
> 2. **持有并等待**：事务持有至少一个资源，并等待获取其他资源
> 3. **不可抢占**：事务已获得的资源不能被强制剥夺
> 4. **循环等待**：事务之间形成循环等待链
>
> 解决方案：打破其中一个条件即可。

### Q3: 慢查询除了加索引还要优化什么？

**答**：
> 慢查询优化三步走：
>
> 1. **开启慢查询日志**：定位慢 SQL
> 2. **用 explain 分析执行计划**：查看是否命中索引、扫描行数
> 3. **优化 SQL 语句**：拆分复杂查询、减少关联、避免 select *
>
> 还要优化数据库参数：调整连接数、缓存池等。
