# 数据库连接池优化

> **场景定位**：数据库性能优化技术场景  
> **核心设计要点**：连接池原理、参数调优、连接泄露排查、全链路治理

---

## 🎯 一句话定位

**数据库连接池解决什么问题？**
```
复用数据库连接，减少连接创建销毁开销
控制并发访问量，保护数据库不被冲垮
```

**生活化比喻**：
就像共享汽车：
- 不用每次都买车（创建连接）
- 用完还回去（释放连接）
- 限制同时用车的人数（控制并发）

---

## 💎 核心观点（5 分钟速览版）

### 核心观点（5 个关键点）

**1. 连接数不是越大越好**
```
❌ 误区：连接数越大性能越高
✅ 真相：超过最优值后，性能反而下降
数据库处理能力有上限
```

**2. 三类核心根源**
```
慢 SQL 占坑：执行几秒不释放
连接泄露：未关闭，只涨不跌
真实并发：业务量确实上来了
```

**3. 盲目加大连接数的危害**
```
连接数过多 → 线程争抢 CPU/IO
→ 上下文切换开销飙升
→ 整体吞吐量反而下降
```

**4. 监控比调参更重要**
```
活跃连接数、等待连接数
连接获取耗时、连接使用率
设置多级告警预警
```

**5. 前置防护机制**
```
禁止长事务、跨远程调用
规范 SQL 上线审核
设置连接最大存活时间
```

## 一、连接池核心原理

### 1.1 为什么需要连接池

```
没有连接池：
每次请求 → 创建连接（TCP 三次握手） → 执行 SQL → 关闭连接
创建连接耗时：几十毫秒 ~ 几秒

有连接池：
复用已有连接 → 执行 SQL → 归还连接
耗时：几毫秒
```

### 1.2 连接池参数

```go
type PoolConfig struct {
    MaxOpenConns    int           // 最大连接数
    MaxIdleConns    int           // 最大空闲连接数
    ConnMaxLifetime time.Duration // 连接最大存活时间
    ConnMaxIdleTime time.Duration // 连接最大空闲时间
}

// 推荐配置
config := PoolConfig{
    MaxOpenConns:    100,          // 根据业务量调整
    MaxIdleConns:    50,           // 空闲连接数
    ConnMaxLifetime: 30 * time.Minute, // 定期更换连接
    MaxIdleTime:     10 * time.Minute,  // 空闲超时回收
}
```

## 二、连接池耗尽的三类根源

### 2.1 慢 SQL 占坑

**特征**：
```
数据库 CPU/IO 负荷高
慢查询日志有明显耗时异常
连接数只涨不跌
```

**排查步骤**：
```sql
-- 1. 查看慢查询
SHOW VARIABLES LIKE 'slow_query_log';

-- 2. 查看当前执行的 SQL
SHOW PROCESSLIST;

-- 3. 分析慢 SQL
EXPLAIN SELECT * FROM orders WHERE user_id = 1;
```

**解决方案**：
```sql
-- 优化索引
ALTER TABLE orders ADD INDEX idx_user_id (user_id);

-- 拆分大查询
-- ❌ 一次性查询 100 万条
SELECT * FROM orders LIMIT 1000000;

-- ✅ 分批查询
SELECT * FROM orders WHERE id > ? LIMIT 1000;
```

### 2.2 连接泄露

**特征**：
```
数据库负载不高
连接数只涨不跌
慢慢耗尽
```

**排查步骤**：
```go
// 监控连接池状态
func MonitorPool() {
    stats := db.Stats()
    fmt.Printf("InUse: %d, Idle: %d, WaitCount: %d\n",
        stats.InUse, stats.Idle, stats.WaitCount)
}

// 输出：
// InUse: 100, Idle: 0, WaitCount: 1000
// 说明连接都被占用，没有释放
```

**常见泄露场景**：
```go
// ❌ 异常分支未关闭
func QueryData() {
    conn, _ := db.Conn()
    
    result, err := conn.Query("...")
    if err != nil {
        return err // Bug: 未关闭连接
    }
    
    conn.Close() // 正常分支才关闭
    return nil
}

// ✅ 正确写法
func QueryData() {
    conn, _ := db.Conn()
    defer conn.Close() // 无论如何都会关闭
    
    result, err := conn.Query("...")
    if err != nil {
        return err
    }
    return nil
}

// ❌ 事务未提交
func UpdateData() error {
    tx, _ := db.Begin()
    
    tx.Exec("UPDATE ...")
    
    // Bug: 忘记提交事务
    // tx.Commit()
    
    return nil
}
```

### 2.3 真实并发上涨

**特征**：
```
数据库负荷和连接使用率同步上升
没有异常慢查询
业务量确实在增长
```

**解决方案**：
```
1. 适度调大连接数（但不超过数据库上限）
2. 读写分离，分摊查询压力
3. 分库分表，分散连接压力
4. 限流降级，控制并发访问量
```

## 三、连接池参数调优

### 3.1 最优连接数计算

```
公式：
最优连接数 = ((核心数 * 2) + 有效磁盘数)

示例：
8 核 CPU，1 块 SSD
最优连接数 = (8 * 2) + 1 = 17

实际生产环境：
核心业务：50-100 个连接
非核心业务：20-50 个连接
```

### 3.2 连接数过多的危害

```
连接数 100：吞吐量最高
连接数 200：吞吐量下降 20%
连接数 500：吞吐量下降 50%

原因：
大量线程争抢 CPU/IO
上下文切换开销飙升
```

## 四、监控告警

### 4.1 核心指标

```go
type PoolMetrics struct {
    MaxOpenConns   int // 最大连接数
    OpenConns      int // 当前打开的连接数
    InUse          int // 正在使用的连接数
    Idle           int // 空闲连接数
    WaitCount      int // 等待连接的次数
    WaitDuration   time.Duration // 等待耗时
    MaxIdleClosed  int // 空闲关闭的连接数
    MaxLifetimeClosed int // 超时关闭的连接数
}

// 监控采集
func CollectMetrics() {
    stats := db.Stats()
    
    // 告警规则
    if stats.InUse > 80 {
        alert("连接池使用率超过 80%")
    }
    
    if stats.WaitCount > 100 {
        alert("等待连接次数过多")
    }
    
    if stats.WaitDuration > 1*time.Second {
        alert("获取连接耗时过长")
    }
}
```

## 五、前置防护机制

### 5.1 禁止长事务

```go
// ❌ 长事务
func ProcessOrder() error {
    tx, _ := db.Begin()
    
    // 执行 10 秒的业务逻辑
    tx.Exec("...")
    time.Sleep(10 * time.Second) // 模拟耗时
    tx.Exec("...")
    
    tx.Commit()
    return nil
}

// ✅ 短事务
func ProcessOrder() error {
    // 拆分多个短事务
    tx1, _ := db.Begin()
    tx1.Exec("...")
    tx1.Commit()
    
    // 中间逻辑
    doOtherLogic()
    
    tx2, _ := db.Begin()
    tx2.Exec("...")
    tx2.Commit()
    
    return nil
}
```

### 5.2 超时控制

```go
// 设置连接超时
config := PoolConfig{
    ConnMaxLifetime: 30 * time.Minute, // 定期更换
    ConnMaxIdleTime: 10 * time.Minute,  // 空闲超时
}

// SQL 执行超时
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()

err := db.QueryContext(ctx, "SELECT ...")
if err == context.DeadlineExceeded {
    return errors.New("SQL 执行超时")
}
```

六、技术深入探讨

### Q1: 连接池耗尽怎么排查？

**方案参考**：
> 连接池耗尽是表象，要找到根源。三类常见原因：
> 
> 1. **慢 SQL 占坑**：查看慢查询日志，优化索引或拆分大查询
> 2. **连接泄露**：检查代码是否有未关闭的连接，事务是否正常提交
> 3. **真实并发**：业务量增长，需要读写分离或分库分表
> 
> 排查步骤：先看监控（活跃连接数、等待次数），再看慢查询，最后查代码。

### Q2: 为什么连接数不是越大越好？

**方案参考**：
> 数据库处理能力有上限，连接数过多会导致：
> 
> 1. **CPU/IO 争抢**：大量线程争抢资源，上下文切换开销飙升
> 2. **吞吐量下降**：超过最优值后，性能反而下降
> 3. **数据库压力**：可能直接把数据库打挂
> 
> 推荐公式：最优连接数 = ((核心数 * 2) + 有效磁盘数)
