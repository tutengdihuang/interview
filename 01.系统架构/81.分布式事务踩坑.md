## 一、三大异常场景

### 1.1 空回滚

```
场景：
1. Try 请求超时，实际未执行
2. 协调器触发 Cancel
3. Cancel 执行时，Try 的资源还没预留

问题：Cancel 要释放不存在的资源
```

**解决方案**：
```go
func CancelWithProtection(orderID string) error {
    // 1. 检查 Try 是否执行
    tryLog := db.GetTryLog(orderID)
    if tryLog == nil {
        // Try 未执行，记录 Cancel 日志
        db.InsertCancelLog(orderID)
        return nil // 幂等返回成功
    }
    
    // 2. 执行 Cancel
    return doCancel(orderID)
}
```

### 1.2 悬挂

```
场景：
1. Try 执行成功
2. Confirm 请求超时
3. 协调器触发 Cancel
4. Cancel 执行成功
5. Confirm 请求实际到达，再次执行

问题：资源被释放两次
```

**解决方案**：
```go
func ConfirmWithProtection(orderID string) error {
    // 1. 检查事务状态
    status := db.GetTransactionStatus(orderID)
    
    if status == "CANCELLED" {
        // 已经 Cancel，不能 Confirm
        return errors.New("事务已取消")
    }
    
    if status == "CONFIRMED" {
        // 已经 Confirm，幂等返回
        return nil
    }
    
    // 2. 执行 Confirm
    err := doConfirm(orderID)
    if err != nil {
        return err
    }
    
    // 3. 记录状态
    db.UpdateTransactionStatus(orderID, "CONFIRMED")
    
    return nil
}
```

### 1.3 幂等失效

```
场景：
Confirm 被重复调用
库存被扣减两次
```

**解决方案**：
```go
func ConfirmWithIdempotent(orderID string) error {
    // 1. 查询 Confirm 记录
    record := db.GetConfirmRecord(orderID)
    if record != nil {
        return nil // 已执行，幂等返回
    }
    
    // 2. 执行 Confirm
    err := doConfirm(orderID)
    if err != nil {
        return err
    }
    
    // 3. 记录 Confirm 记录
    db.InsertConfirmRecord(orderID)
    
    return nil
}
```

## 二、数据对账系统

### 2.1 T+1 对账

```go
func DailyReconciliation() {
    // 1. 查询所有订单
    orders := db.QueryOrders("created_at >= ?", yesterday)
    
    for _, order := range orders {
        // 2. 检查库存是否扣减
        inventoryLog := db.GetInventoryLog(order.ID)
        if inventoryLog == nil {
            // 库存未扣减，触发补偿
            compensateInventory(order)
        }
        
        // 3. 检查余额是否扣减
        balanceLog := db.GetBalanceLog(order.ID)
        if balanceLog == nil {
            // 余额未扣减，触发补偿
            compensateBalance(order)
        }
    }
}

// 补偿流程
func compensateInventory(order *Order) {
    // 1. 告警
    alert("订单 %s 库存未扣减", order.ID)
    
    // 2. 人工介入或自动补偿
    tryDeductInventory(order)
}
```

三、技术深入探讨

### Q1: 分布式事务有哪些坑？

**方案参考**：
> 分布式事务有三大坑：
> 
> 1. **空回滚**：Cancel 时 Try 未执行，需要记录 Cancel 日志，防止后续 Try 到达时无法处理
> 2. **悬挂**：Confirm 超时，Cancel 先执行，需要检查事务状态，防止 Confirm 再次执行
> 3. **幂等失效**：Confirm 重复执行，需要记录 Confirm 记录，保证幂等
> 
> 关键是要有事务状态机，记录每个阶段的状态。

### Q2: 如何保证数据最终一致性？

**方案参考**：
> 数据最终一致性靠对账系统兜底：
> 
> 1. **T+1 对账**：每天对比各服务的数据，发现不一致立即告警
> 2. **补偿机制**：发现不一致后，自动或人工补偿
> 3. **事务超时**：长时间未完成的事务强制中断
> 4. **监控告警**：实时监控事务执行状态
> 
> 核心是对账系统，是数据一致性的最后防线。
