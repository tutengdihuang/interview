视频《别滥用 Agent! 这四种场景坚决不能用》完整内容总结
视频面向程序员面试，纠正很多开发者盲目崇拜 Agent 的误区，核心观点：不是 Agent 越智能就越适合所有业务；任务路径能提前梳理清楚就用 Workflow，只有路径千变万化、无法穷举全部分支，才使用 Agent。很多人只会跑 Demo、背概念，但分不清两者边界，直接把 Agent 套到所有业务，会出现输出不稳定、成本飙升的问题，面试也容易失分。
一、Workflow 和 Agent 的底层核心差异
很多人简单理解：Workflow 是写死的流程，Agent 会自主思考，这个理解只停留在表面。真正的区别是任务执行路径由谁来决定。
Workflow（固定工作流）
人工提前定义好全部步骤、分支、循环、异常兜底逻辑。
优点：输入固定时，输出稳定可控、结果可复现，token 开销可控；
缺点：灵活性差，遇到预设之外的任务就无法处理。
Agent 智能体
交给大模型在运行时动态做任务拆解、路径规划，由模型自己决定调用什么工具、执行几步、走哪个分支，不需要人穷举全部流程。
优点：擅长处理多变、开放、分支无法提前穷举的复杂任务；
缺点：天生有短板，模型会规划错误、重复调用工具、漏掉步骤；输出结果不确定；token 消耗高、耗时更长。
简单判断口诀：路径可以提前想清楚→Workflow；任务走向千变万化，人穷举不完所有情况→Agent。
二、4 种坚决不建议使用 Agent 的业务场景（面试高频考点）
场景 1：步骤完全固定，对结果稳定性要求极高
例子：文档摘要、格式转换、导出表格，只有固定 2‑3 步，没有可变分支。
问题：用 Agent 会画蛇添足，模型可能乱增加步骤、多余调用工具、打乱执行顺序，凭空引入错误；Workflow 可以稳定次次输出。
场景 2：对耗时、调用成本极其敏感的业务
Agent 会反复思考、多轮工具调用交互；同样任务 Workflow 一轮完成，Agent 来回多轮；
高并发场景会拉高预算、增加响应延迟；预算和时延约束严格，不要优先选 Agent。
场景 3：强规则约束，不允许模型自由发挥
例子：数据校验、合规过滤、固定模板生成。
业务有硬性校验规则，不能交给模型主观判断；Agent 自主规划存在风险，有可能绕过规则，产出不合规内容。
场景 4：任务逻辑简单清晰、变量很少
业务变化少，人完全可以梳理完整流程；强行上 Agent 只会增大系统复杂度；
故障排查困难，出 Bug 分不清是代码问题还是大模型规划出错。
三、面试高分标准回答模板（视频直接给出）
Workflow 和 Agent 最大的区别本质在于任务路径由谁决定。
Workflow 是提前把步骤、分支、判断逻辑全部定义好，执行路径固定，结果稳定可控，但灵活性差，无法处理预设以外的情况。
Agent 依靠大模型实时做任务规划，运行时才确定执行路径，擅长处理多变、无法穷举分支的复杂任务；代价是输出存在不确定性，容易规划失误，资源开销更高。
下面这些场景优先选择 Workflow，不使用 Agent：
1. 任务步骤固定，对输出稳定性要求高；
2. 对响应速度、资源开销敏感；
3. 业务有强硬规则，禁止模型自由发挥；
4. 任务逻辑简单，可以提前梳理完整流程。

《别滥用 Agent! 这四种场景坚决不能用》逐点完整版（全部原文要点、例子、结论不漏）
视频定位：面向程序员校招 / 社招面试，纠正行业普遍误区：很多人看完 Agent Demo 就觉得 Agent 更强、更先进，什么需求都上 Agent；面试一被追问 Workflow 和 Agent 边界就答不出来。核心主线：Agent 不是万能升级，二者选择标准是「任务执行路径由谁决定」
一、开篇引入（视频原话）
现状：现在网上大量教程鼓吹 Agent，很多开发者形成刻板印象：Agent > Workflow，只要沾 AI 任务，优先选 Agent。
痛点：盲目上 Agent，上线后遇到三类典型故障：
输出不稳定：同样输入，多次跑结果不一样；
Token 成本爆炸，远超预期；
链路不可控，排查问题极其困难。
面试坑点：只背定义 “Workflow 是固定流程、Agent 会自己思考” 属于浅层回答，面试官想听的是选型边界、什么时候坚决不用 Agent。
视频总论点：Workflow 和 Agent 没有高低之分，只有适配场景区别；下面 4 类场景，无论 Demo 多好看，业务里优先 Workflow，不要上 Agent。
二、Workflow 与 Agent 底层定义（视频完整对比）
1）Workflow（固定工作流）
核心本质：任务路径由人提前全部定义好。
设计动作：工程师预先写死所有步骤、分支判断、循环条件、异常兜底、重试策略。模型只负责执行当前分配的单步任务，无权自己决定下一步做什么、调用哪个工具。
优点（视频逐条列出）
① 输入一致时，输出稳定、可复现；
② Token 消耗可控，每一轮调用次数固定；
③ 时延稳定，没有不确定的多轮思考；
④ 链路透明，日志清晰，出问题好定位；
⑤ 容易加强校验、规则拦截。
缺点：灵活性差，一旦输入落在预设分支之外，流程就处理失败，不会自己变通。
视频举例：固定三步：读取文档→提取指定字段→写入 Excel。步骤固定，没有新分支。
2）Agent（智能体）
核心本质：任务路径在运行时由大模型动态决定。
设计动作：人只给最终目标、可用工具列表；模型自己做任务拆解、自己判断下一步动作、自主选择调用工具、自己判断是否完成、是否需要重试、是否换方案。人不提前穷举所有分支。
优点（视频逐条列出）
① 开放、复杂、未知场景可以自适应；
② 不需要工程师提前穷举海量分支；
③ 适合目标明确，但达成方式不确定的任务。
缺点（视频逐条列出，重点，面试必问）
① 规划幻觉：模型会想错步骤、顺序颠倒；
② 无效循环：反复调用同一个工具，原地打转；
③ 遗漏步骤：漏掉关键动作，任务半成品；
④ 结果非确定性：相同输入多次运行结果不一致；
⑤ Token 开销不可预估，多轮思考 + 多轮工具调用；
⑥ 链路黑盒：你不知道模型脑子里为什么选这条路径，故障难复现、难排查。
视频举例：帮用户调研一款新产品，用户需求多变，搜索、对比、整理、追问信息的路径无法提前全部写死。
✅ 视频给出的唯一判断标准（原话口诀）
路径可以提前梳理完整、所有分支能穷举 → Workflow
任务走向千变万化、人类无法提前穷举全部情况 → Agent
三、四类坚决不建议使用 Agent 的场景（每一条包含：场景描述、业务例子、风险细节、结论）
场景 1：步骤固定，业务对输出稳定性、一致性要求极高
场景描述：任务步骤很少、固定，不允许同一输入跑出不一样结果，结果要可复现。
视频例子：
文档固定摘要：统一模板摘要，每次摘要风格、提取字段要一致；
格式转换：markdown 转标准 JSON、结构化导出表格；
固定信息抽取：从合同里提取【甲方、金额、日期】三个字段。
如果强行上 Agent 会发生什么（视频原话）：
Agent 会自主发挥：有时候多提取字段、有时候少提取、有时候顺序打乱，甚至额外增加不需要的总结话术；模型自由规划引入不必要的随机性，破坏业务稳定性。
本场景结论：优先 Workflow，不要 Agent。稳定性优先的标准化任务，Agent 是画蛇添足。
场景 2：业务对响应耗时、调用成本高度敏感（高并发场景典型）
场景描述：接口 QPS 高、预算有限、有明确 RT 上限；用户不能接受长时间等待，单条请求成本有上限。
视频例子：面向 C 端用户批量内容过滤、实时标签打标，每秒上千请求。
如果强行上 Agent 会发生什么（视频原话）：
Agent 天然是多轮循环：思考→调用工具→观察结果→再思考；一轮任务可能 3~10 轮 LLM 调用；Workflow 往往单轮或者固定 2 轮就结束。
带来两个后果：
① RT 飙升，超时变多；
② Token 用量不可控，流量起来之后费用直接超出预算。
本场景结论：时延、成本敏感场景，坚决优先 Workflow。
场景 3：带有强硬性业务规则，不允许模型自主发挥、自主判断
场景描述：业务规则是刚性、合规要求，属于 “必须严格遵守，不能让模型权衡”，规则不允许模型解读、变通。
视频例子：
金融数据校验、风控规则拦截；
内容合规审核（固定敏感词、固定禁止项）；
固定模板生成（报销单、制式通知书，格式、字段位置不能改）。
如果强行上 Agent 会发生什么（视频原话）：
Agent 拥有自主规划权，存在绕过规则的风险。模型会自主权衡，有可能为了 “完成任务” 而弱化、跳过硬性校验；模型的价值判断不可信，规则交给大模型自主决策会带来合规风险。
本场景结论：强规则、合规类任务，规则判断交给代码 / Workflow，不要交给 Agent 自主决策。
场景 4：任务逻辑简单清晰、变量少，人力完全可以梳理全流程
场景描述：需求稳定、变化频率低，输入变量少，工程师花一点时间就能把全部分支、异常兜底写清楚。
视频例子：简单翻译、固定清洗文本、简单分类（3~5 个固定分类）。
如果强行上 Agent 会发生什么（视频原话）：
引入不必要的系统复杂度。
额外增加：Agent 规划层、思考日志、工具调用循环、停止条件判断。
后续维护坑：出 bug 的时候，你分不清：是提示词问题？模型规划问题？工具返回问题？还是业务本身逻辑问题？调试成本大幅上升。
本来几十行 Workflow 代码搞定，硬上 Agent，架构过重。
本场景结论：简单低变量任务，优先 Workflow，避免过度设计。
四、视频补充：反过来，哪些才是适合 Agent 的场景（用来对照理解）
视频没有长篇展开，但明确给出对照，用来面试配套回答：
满足下面任意多条，才值得考虑 Agent：
最终目标明确，但实现路径未知、分支无穷多，人写不完所有 case；
需要动态收集外部信息（多轮搜索、多文档读取、多源对比）；
需要动态试错：上一步结果决定下一步做什么；
用户输入高度开放、不可预测。
举例：个人研究助理、复杂方案调研、故障根因排查（日志五花八门，没法提前写死判断分支）
五、视频给的面试标准口述完整版（一字不差版本）
Workflow 和 Agent 本质区别，是任务执行路径由谁来决定。
Workflow 是我们提前定义好全部步骤、分支、判断逻辑，模型只负责执行单步，路径固定，结果稳定可控、开销可控，但灵活性差，处理不了预设之外的情况。
Agent 是交给大模型在运行时动态做任务拆解和路径规划，模型自己决定调用工具、步骤顺序，适合开放、分支无法穷举的复杂任务；代价是结果不确定，容易规划出错，Token 开销和延迟都更高。
有四类场景优先 Workflow，不适合 Agent：
第一，步骤固定，对输出稳定性、可复现要求高；
第二，对响应时间、调用成本敏感，高并发场景；
第三，业务有强合规硬规则，不允许模型自主判断发挥；
第四，任务逻辑简单、变量少，人工可以完整梳理流程，没必要增加 Agent 带来的复杂度。
六、视频收尾总结观点
很多 Demo 看着 Agent 很强，是因为 Demo 场景本身就是开放探索类，刚好匹配 Agent 优势；不要把 Demo 的感受平移到所有业务。
优秀 AI 应用工程师不是 Agent 堆砌师，而是做取舍：分清可控任务和探索型任务。
面试加分点：不要只说 Agent 的能力，主动讲清楚 Agent 的短板和禁用边界，拉开和只会背概念候选人的差距。
一句话收尾金句：Agent 是解决 “未知路径问题” 的方案，不是 Workflow 的升级版替代品。
