这是面向AI 面试 + Agent 工程落地的短视频，核心主题：多智能体协作最大坑不是单个 Agent 能力，而是上下文、状态传递设计不当导致上下文断裂、信息错乱、token 爆炸，讲解通信拓扑、消息契约、共享状态三大核心，同时给出面试答题思路与工程实践方案。
一、核心痛点：很多人对多 Agent 协作理解误区
很多人以为多 Agent 就是 Agent 之间互相发消息聊天。但工程实践中，多 Agent 系统崩溃大多发生在任务交接环节：上下文丢失、信息传多（token 暴涨）、信息传少（关键信息缺失）、各 Agent 看到的信息版本不一致，而不是单个 Agent 能力不足。
本质问题：上下文不是传得越多越好，要在信息完整性、token 成本、信息隔离三者之间做平衡。
二、多 Agent 协作通信设计三大关键点
1. 选对通信拓扑（谁和谁说话）
不要让 Agent 之间自由两两对话。主流两种拓扑：
1）主从编排模式（Orchestrator 调度器）：有一个主 Agent / 调度中心，统一拆任务、派任务、收结果；子 Agent 之间不直接对话，全部和调度器交互。
优点：全局可控，便于做权限、上下文裁剪、日志追踪；
适合绝大多数业务系统，生产环境最常用。
2）对等网络模式：Agent 之间直接点对点通信。
缺点：容易信息混乱，难排查，适合简单科研场景，不建议生产直接用。
2. 定义消息契约（传什么，输出格式）
相当于 Agent 之间的接口协议，不能让大模型自由发挥输出。派发给子 Agent 任务时，契约必须写清楚 5 项要素：
1）子 Agent 负责做什么；
2）子 Agent不负责做什么（边界）；
3）可以使用哪些工具、能访问哪些信息；
4）输出的格式、要交付的结果；
5）终止条件：什么情况算完成，什么情况直接报错返回。
参考 Anthropic 子 Agent 实践：委派子任务时，明确目标、输出格式、工具权限、任务边界，减少模糊空间，避免交接时上下文断裂。
子 Agent 返回时：只返回精简结论 + 证据指针，不要把全部思考过程完整回传。
不要把子 Agent 完整对话历史全部塞回主 Agent，否则会反向造成主 Agent 上下文窗口爆炸。把过程日志存外部，主 Agent 只拿结论，需要再去查阅原始过程。
3. 管好共享状态（全局信息怎么存）
解决 “所有 Agent 看到同一份真相”，两种主流方案：
方案 A：消息透传（点对点传递上下文）
把需要的信息放在消息体内，调用的时候直接传给下一个 Agent。
优点：简单直接，适合短链路、简单串行任务；
缺点：链路变长时消息越来越大；并行多 Agent 场景很难同步全局信息。
方案 B：共享黑板 / 共享状态 Shared Memory（LangGraph 就是这套思路）
一块公共结构化存储，所有 Agent 不直接互相发大段上下文；
Agent 把进度、中间结论、任务状态写到公共状态；
需要信息就从共享状态读取；
由编排调度器统一维护共享状态，保证全局视图一致，防止读写冲突、数据错乱。
优点：
子 Agent 不用来回传递大量消息，节省 token；
每个 Agent 本地上下文保持干净；
天然支持并行 Agent，大家读写同一份任务进度；
缺点：要处理并发写冲突，需要设计状态 Schema。
工程建议：不要每个 Agent 各自保存一份私有状态副本，很容易出现 “各说各话”。
三、两种状态传递方式怎么选型
表格
方式	适用场景	缺点
消息透传	短链路、简单串行、子任务高度独立	链路长后 payload 膨胀，并行协作不好处理
共享状态黑板	复杂工作流、多 Agent 并行、长任务流水线	需要维护状态存储，处理并发冲突
实践中经常混合使用：局部子任务用消息透传，全局任务进度使用共享状态。
四、面试标准回答模板（视频重点给的面试话术）
点本质：多 Agent 系统最容易出问题的不是单个 Agent 能力，而是 Agent 之间的任务交接与通信，因此通信和状态需要专门架构设计，不能简单互相发消息。
讲三点架构：
拓扑：优先主从编排拓扑，由 Orchestrator 做任务分发与汇总，减少 Agent 之间自由通信；
消息契约：委派子任务要有明确契约，明确职责边界、工具权限、输出格式，子 Agent 返回只上交结论与证据，不回传全部过程；
状态管理：复杂场景采用共享状态（公共黑板），由调度器维护全局状态，保证所有 Agent 信息视图一致，避免上下文断裂。
收尾：简单任务可以直接消息透传，复杂长流程优先共享状态；上下文传递原则是：只传必要信息，兼顾完整性、token 开销、可追溯性。
五、工程落地避坑要点
❌ 坑 1：把子 Agent 完整对话历史全部回传给主 Agent，引发上下文窗口爆炸；
❌ 坑 2：没有任务契约，全靠大模型自由输出，返回格式不可控；
❌ 坑 3：Agent 各自维护私有状态副本，没有统一全局视图，信息不同步；
✅ 正确做法：过程日志持久化在外层存储，工作流上下文只流转关键结论、任务状态、证据索引。

0. 开篇总前提（视频开头）
面试原题：多 Agent 协作的时候，上下文、状态该怎么传递？
视频核心立意：很多开发者会把上下文和状态混为一谈，直接无脑全量转发对话记录；真正要回答这道题，第一步是先分开定义两个名词，再分析两种极端方案的取舍，再区分串行 / 并行场景，最后给出信息裁剪原则。
1. 先严格区分两个核心定义（视频第一个重点）
上下文（Context）
内容：每一轮对话产生的对话历史、中间推理草稿、工具调用返回结果。
属性：临时对话信息，是 Agent 这一轮思考过程的副产品，不一定需要一路传给后面所有 Agent。
状态（State / 全局状态）
内容：任务全程固定、必须持续保留的全局信息：原始用户任务目标、已经完成的步骤清单、收集到的参数、各个 Agent 已经产出的结论。
属性：贯穿整条任务链路，是整个任务的 “真相快照”，不管多少个 Agent 接力、并行，都依赖这份状态。
视频原话重点提醒：绝大多数踩坑根源，就是把上下文和状态混在一起打包，不加筛选直接往下传。
2. 方案 A：全量原样传递上下文（所有人都能拿到完整对话历史）
✅ 优点（视频原文）
实现最简单，粗暴直接；
信息不会丢失，下游 Agent 可以看到上游全部思考、全部推理过程。
❌ 缺点（视频原文逐条列出）
轮数一多，冗余快速累积：无效草稿、废弃思路、之前出错的推理全部跟着往下带；
大量冗余挤占 Token 预算，成本持续上涨；
下游 Agent 注意力被无关内容稀释，被前面无效思考带偏，更容易出现幻觉；
链路越长，窗口越容易溢出，触达模型上下文上限。
3. 方案 B：只传精简最终结论，完全丢掉中间推理上下文
✅ 优点（视频原文）
Token 消耗很低；
消息干净，没有一大堆草稿、无效思考干扰下游 Agent；
消息体积小，传递快。
❌ 缺点（视频原文逐条列出）
可追溯性丢失：一旦下游 Agent 执行报错、卡住、结果异常，没有中间推理记录；
无法定位问题：不知道上游是基于哪些证据、哪一步推理得出这个结论；
任务卡死后很难恢复、重试、分支回滚。
视频在这里抛出核心矛盾：既不能无脑全量传，也不能只留结果丢掉一切中间信息，必须按任务形态区分方案。
4. 视频给出的场景例子 + 对应选型（视频里唯一的具象例子）
例子 1：简单串行流水线任务
场景特征：Agent 按固定顺序依次排队执行；后一个 Agent只依赖上一步输出结果，不需要同时读取多个并行分支的信息；线性流转。
👉 视频结论：适合精简传递
做法：只把上一步的最终结论写入流转信息；完整推理草稿、临时上下文不跟着往下传。
例子 2：并行多 Agent 任务
场景特征：多个 Agent 同时独立跑不同子任务；它们各自产出结果，最后统一汇总；所有并行 Agent 都需要读取同一份任务目标、全局参数；每个 Agent 的产出也要给其他协作方可见。
👉 视频结论：不能只用消息透传，必须统一全局状态容器（共享黑板）
配套约束：做好读写隔离；一个 Agent 修改状态的时候，不能覆盖别人正在读写的数据，防止状态错乱、版本冲突。
视频补充：并行场景如果还用串行那种 “消息挨个传”，会出现 A Agent 看不到 B Agent 的产出，信息割裂，协作失效。
5. 通用强制规则（信息流转前，不管串行还是并行都要遵守）
流转前必须做过滤、裁剪；剔除重复、无效、废弃分支内容；
严格控制消息总长度，不能超过模型的上下文窗口承载上限；
中间推理草稿不要塞进流转消息；草稿可以单独持久化存储（日志库），做成可按需查阅的证据记录，而不是默认跟着消息流转；
全局状态单独维护，不和临时对话上下文打包混杂。
6. 视频末尾四条总结（面试标准输出，一字不差对应视频）
上下文是对话里的临时推理记录；状态是任务全程保留的全局信息，二者不是一回事，不要混在一起不加筛选直接转发；
全量传递：不容易丢内容，但冗余持续累积、Token 变贵、容易幻觉；只传最终结果：轻量化省 Token，但缺少中间记录，异常时无法回溯排障；
串行 Agent 流水线：精简传递，只流转关键结论；并行多 Agent 场景：统一全局状态容器，做好 Agent 之间读写隔离，防止互相干扰；
所有信息流转前，必须做过滤裁剪，控制总长度，不超出模型上下文上限。
7. 视频最后的面试加分收尾句
面试官想听的不是死记两种方案名字，而是取舍思维：你知道什么时候传全量、什么时候精简、什么时候上共享状态，而不是写 Demo 的时候直接把全部对话无脑往下塞。
