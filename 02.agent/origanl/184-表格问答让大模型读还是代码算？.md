视频详细内容总结
该视频是面向大模型 / Agent 开发岗位的面试讲解视频，主题：表格问答，该让大模型直接读表计算，还是交给代码 / SQL 计算。核心观点：不要简单二选一，区分大模型的语义理解能力和代码的确定性计算能力，线上项目不能直接把表格丢给大模型做运算；这道面试题本质考察候选人是否懂工程落地，能不能把理解、解析、计算、校验、回答分层设计，而不是只会玩 Demo 效果。
一、核心底层认知
大模型适合做什么：理解用户问题意图、识别业务字段、翻译自然语言为查询条件、对计算结果做自然语言解释输出。
大模型不适合做什么：加减乘除、占比、排序、TopN、去重、同比环比、跨表聚合等数值运算。
风险点：不是模型完全算不对，而是大模型是概率输出，计算结果不可复现、不可审计、无法追责。同样问题多次提问，可能得出不一样数字，在财务、经营分析场景，错误数字比拒答的危害更大。
整体分工原则：大模型输出查询计划（过滤条件、字段、业务口径）；计数、求占比、分母、缺失值处理等确定性运算交给代码 / SQL 执行；最后再由大模型基于程序算出的结果做解释回答。
举例：查询 “华东区上季度达标人数占比”，模型识别 “华东区、上季度、达标” 过滤条件，但是计数、占比计算、空值处理交给代码完成。
二、线上表格问答系统 4 个关键工程步骤
1. 表格解析层
Excel、CSV、PDF 表格不能直接当普通文本切片喂给 RAG。
需要专门结构化解析：识别表头、单位、合并单元格、脚注、隐藏列、合计行。
常见线上 bug：单位 “元 / 万元” 混淆；合并单元格信息没有填充到每一行；合计行被当成普通业务行参与计算。
面试不能只回答向量检索，需要提到结构化解析、字段血缘，保证后续答案可以溯源到原始表格的具体行号。
2. 计算边界层
所有确定性计算交给代码、SQL，借助structured outputs让大模型输出符合规范的查询参数。
即使模型输出的参数格式正确，也不等于业务口径正确；
系统层面增加字段白名单、数据类型校验、异常值过滤；
分工总结：模型生成可执行的查询意图，程序算出可审计的结果。
3. 答案引用层（可审计可溯源）
返回给用户的不能只返回最终数字。输出结果要附带：过滤条件、参与计算的行数、数据排除原因、数据更新时间。
业务价值：当用户质疑结果，系统可以回放原始表格行号、中间计算过程；避免表头改动、新增合计行后系统输出错误结果。
4. 兜底策略层
遇到字段含义模糊、单位冲突、缺失值过多、用户提问缺少时间 / 范围等关键信息，不要强行计算。
处理方式：向用户追问信息，或者直接告知无法确定。
工程理念：靠谱的表格问答不是什么问题都要答出来，而是懂得什么时候停止计算。在财务、合同、经营指标场景，错误数字风险极高。
三、面试高分回答模板
“我会先对表格做结构化解析，由大模型抽取用户查询意图，生成查询计划；再交由代码 / SQL 执行确定性计算；计算完成后携带原始证据、口径信息，再交给大模型向用户解释答案。大模型不是计算器，它更像是一个把自然语言转化为受控查询计划的组件。”
四、系统验收指标（面试可以补充）
评估表格问答系统好坏重点看：
计算结果是否可以复现；
引用表格行来源是否正确；
单位是否统一；
异常值、脏数据是否做处理。

视频完整逐要点拆解（全部要点、例子、结论，无省略）
视频原题：运营数据表给大模型做问答，直接读表还是写代码 / SQL 算？
视频核心总纲（开篇第一结论）：
不要简单二选一；这道题表面问表格理解、Text-to-SQL 选型，本质考察你懂不懂业务口径一致性、可复现性、审计追溯能力；大模型是语义 / 推理引擎，不是计算引擎；凡是聚合、排序、比率、对比类计算，一律交给代码 / SQL 做确定性计算，大模型只负责理解意图、翻译自然语言查询、解释结果、补充业务语义。
一、先讲【错误回答以及为什么踩坑】
错误答案：直接把表格丢给大模型读、多模态识别截图表格，模型直接算出结果。
踩坑理由（视频明确强调：不是识别准确率问题，核心痛点是口径）
大模型是概率输出，不是确定性计算器；同一个问题，多次提问，可能给出不一样数字；
同一个问句，存在多种合法业务口径，模型会随机选一种，你无法控制它用哪一套口径；
计算过程黑盒：数字错了，你不知道它是拿哪些行、怎么算出来的，无法溯源、对账、追责；
性能与 Token 问题：行数多的时候，把整张表塞进上下文，Token 爆炸、延迟极高，生产不可用；
幻觉风险：数值幻觉，看起来像对的数字，实际是编出来的。
视频原话提醒：说 “直接读表就行”，面试官大概率直接扣分，代表你只玩过 Demo，没上过业务生产。
配套例子 1：口径歧义经典例子（视频重点）
用户提问：Q3 增长多少？
表格：按月存储销售数据，Q3=7、8、9 三个月
口径 A（同比口径）：三个月求和得到 Q3 总额，和去年 Q3 总额对比 → 同比增速
口径 B（环比口径）：三个月求和 Q3 总额，和 Q2 总额对比 → 环比增速
口径 C（月均口径）：先算 Q3 月平均值，再和去年同期月均值对比
视频结论：三个口径算出来三个不同数字，数字本身计算都没错，但业务含义完全不一样；直接交给大模型，它随机选一个口径回答，用户、财务、运营完全没法判断它用的是哪一套规则。
配套例子 2：渠道转化率（视频反复举）
用户提问：华东区上季度渠道转化率、达标人数占比、渠道排名
计算要素：分子（转化成功）、分母（总流量 / 总上报人数）、缺失值怎么处理（空数据要不要排除）、过滤条件（华东、上季度、有效样本）
视频结论：分子分母、空值过滤、计数、占比，全部不能交给模型算；模型只负责识别：用户要【华东、上季度、转化率】这个查询意图。
配套例子 3：排名、TopN、对比类
问句里出现：排名、最高、最低、前 3、大于、小于、占比、同比、环比、求和、平均值、去重、计数，只要出现这类关键词，强制走代码计算链路。
二、高频面试追问：小表（比如只有 10 行 3 列），也要走代码吗？
视频明确结论：数据量大小不是判断依据，计算类型才是判据。
哪怕只有 10 行，只要问题里面有排名、占比、对比、聚合，就必须走代码通道。
追问配套子问题：
面试官继续问：那为什么小表也要这么重？
视频回答：你要的不只是一个答案，你要的是可审计、可复现的答案；你要能区分：两天看到的排名变化，到底是真实业务数据变了，还是大模型这一次换了计算口径。
补充边界：什么场景可以让大模型直接读表？
纯读取、不计算：比如 “张三这一行的联系电话是多少？”“这张表里有没有备注写加急的记录？”，只是查表取字段、简单检索，没有任何聚合运算，才可以直接交给模型。
三、完整四层工程架构（视频标准四层，顺序严格）
第 1 层：表格结构化解析层（前置，很多人漏掉的一层）
输入源：Excel / CSV / PDF 表格、图片里的表格
需要解析识别的内容清单（视频逐条列出）：
表头、字段名、字段注释；
单元格单位（元 / 万元，最常见事故点）；
合并单元格，把合并值填充到每一行；
脚注、备注说明；
隐藏列、隐藏行；
合计行、小计行（最容易踩坑：合计行被当成普通业务行参与求和，结果翻倍）
视频结论：很多表格问答报错，根本不是模型算错，是表格解析阶段就脏了；不能简单 OCR 转纯文本切片丢给 RAG；解析后要保留【字段血缘、行号】，用来溯源。
第 2 层：意图 & 口径抽取层（LLM 在这里干活）
大模型职责：
理解用户自然语言，识别查询目标；
抽取结构化查询参数：指标名称、字段、时间范围、地区、过滤条件、业务规则（什么算达标）；
输出受控结构化参数（用 Structured Output / Function Calling），不是直接写自由文本；
校验模糊点：字段含义冲突、单位冲突、用户缺少关键条件（没给时间、范围）、缺失数据太多。
本层兜底规则：
一旦信息不足、口径模糊，禁止强行脑补计算；模型主动追问用户补充条件，或者直接返回 “当前信息不足，无法给出确定结果”。
视频理念：靠谱的表格问答系统，不是什么问题都硬答，而是知道什么时候拒绝计算。
本层禁止事项：大模型在这里不做加减乘除、求和、排序、占比。
第 3 层：代码 / SQL 确定性计算层（计算全部放在这里）
执行载体：Python 代码、SQL、数据沙箱、Code Interpreter
输入：上一层模型输出的结构化查询参数（过滤条件、字段、口径规则）
本层要处理的清单（视频逐条）：
条件过滤；
计数、求和、均值；
占比、比率（分子分母、空值剔除规则在这里固化）；
排序、TopN、分组聚合；
同比、环比；
异常值、脏数据、缺失值统一处理规则；
单位统一换算（万元 ↔ 元）；
输出：一份很小的结构化结果（JSON），附带元信息：参与计算的行数、被排除的行数、排除原因、数据更新时间、原始行号引用。
重点：传给后面大模型的，不再是整张原始表格，只是算完之后的简短结果 + 审计元信息。
安全补充：代码必须在沙箱运行，防止注入；配置字段白名单，限制可查询字段，不能随便读所有列。
第 4 层：答案生成 & 审计溯源层（LLM 再次出场）
大模型拿到【已经算好的数字 + 审计元数据】，只做这些事：
把冰冷 JSON 数字翻译成自然语言，给用户解释；
附带溯源证据：告诉用户，这个结果是基于多少条有效数据、哪些过滤条件；
标注边界：比如 “剔除了 2 条空值样本”；
可以附加业务解读、简单建议（比如该渠道转化率偏低）；
硬性约束：本层模型不能修改、重新计算数字，只能转述、解释数字。
额外加分闭环：二次校验（视频加分项，面试主动提）
把代码的计算逻辑、计算中间过程，作为上下文再次注入大模型，让模型去复核这套计算逻辑有没有违背业务口径；形成：【模型出查询计划 → 代码计算 → 模型审计算逻辑】的校验闭环。
如果校验发现计算逻辑和业务口径冲突，阻断结果输出，报错。
四、路由判断规则（视频给了硬路由逻辑，写在系统里）
系统先做判断，分流两条链路：
plaintext
if 问句包含【求和、占比、排名、TopN、对比、同比环比、平均值、计数、去重】：
    走【结构化解析 → LLM抽查询参数 → 代码计算 → LLM解释】链路
else 只是单纯查单条字段、检索有无备注（无计算）：
    直接LLM读结构化表格检索回答

视频原话：只要出现任意一个计算关键词，就切代码通道。
五、系统验收评估指标（视频明确列出，面试加分）
评判表格问答系统好不好，不看能不能回答，看这几条：
计算结果可复现：相同条件输入，每次数字一定一样；
来源可追溯：每一个数字，能定位到原始表格行号；
单位统一，不会万元元混用；
脏数据、空值、合计行有明确处理策略；
口径可沉淀：业务口径（达标定义、同比规则）沉淀成元数据，不是模型临场脑补；
异常场景可控，不会强行编造数字。
六、风险场景重点强调（财务、经营报表场景）
视频重点提醒：经营分析、财务、合同数据场景下，错误数字的危害，远大于答不出。
Demo 里错个数字无所谓；线上给运营、财务、管理层做决策依据，数字错了直接带来业务损失，所以确定性优先级最高。
七、面试标准高分口述模板（视频原文模板）
“我不会简单说直接读表或者全部写 SQL。我会先区分查询类型：纯字段检索可以由大模型直接读取结构化表格；只要涉及聚合、比率、排序、对比计算，就分层处理。首先对表格做完整结构化解析，处理合并单元格、单位、合计行，保留行号血缘；再由大模型理解用户意图，输出受控的结构化查询条件和业务口径，这里不做计算；再交给 SQL 或者沙箱代码做确定性运算，固化分子分母、缺失值、单位换算规则；代码输出结果附带审计信息之后，再交给大模型做自然语言解释和业务解读。大模型在这里是自然语言到查询计划的翻译器，而不是计算器。”
八、视频最后补充的 “坏路径提醒”
很多候选人会说：我用 Code Interpreter，让模型自己生成代码跑。
视频点评：Code Interpreter 这个方案本身可以用，但只说这个、不说清楚分工边界，依然是不完整答案。
缺陷：模型依然有可能写出错误口径的代码；所以上层必须有口径元数据、白名单、校验层约束，不能完全放任模型自由写任意代码。
