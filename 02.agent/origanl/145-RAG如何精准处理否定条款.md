视频完整内容总结
这是一道大厂 AI 面试题讲解视频，主题：RAG 在合同审查场景，如何处理 “不允许、除外、不得” 这类否定条款，避免把禁止条件理解反、输出错误结论。视频不只是讲简单识别否定词，而是完整讲解一套工程化解决方案、面试答题思路、踩坑点、评测方法和上线运维方案，面向准备大模型 / AI 工程面试的求职者。
一、题目本质考察点
题目表面问否定语义识别，实际考察对规则的完整理解：类似 “不得退款≠全部场景都不能退款”。一条否定规则，需要同时解析四要素：否定范围、例外条件、适用主体、生效时间。
举例：主合同写禁止退款，但售后政策规定质量问题可以退款。如果 RAG 只抓到 “禁止退款”，忽略例外，就会输出错误答案。
高频踩坑点
只做关键词 / 向量相似度召回，只命中核心名词（退款），丢失除非、但仅限、除外这类限定、转折、例外词汇；
文本切片把否定词和它修饰的对象切分开，破坏语义；
只看最终输出结果，没有保存链路中间状态，出问题无法定位哪里出错；
召回部分相关片段，就直接交给模型生成，不校验证据是否完整；
把局部片段的规则，当成全局通用规则。
排查原则：不要直接让模型反复猜答案；定位第一个出错节点，再选择调参、重试、降级处理，并且完整保留输入、模型版本、中间结果用于复盘。
二、完整工程解决方案：入库与查询分离治理
把整个 RAG 链路拆分为入库（索引构建阶段）、查询（用户提问阶段）、召回后证据校验、生成答案引用闭环四个环节处理否定条款问题。
1. 入库阶段（文档解析建索引）
不能只向量化文本，要补全结构化元数据标签：文档标题、页码、文档版本、生效时间、适用组织、权限标签等。
作用：时间、主体、版本这类约束，不要让大模型从文本里猜，提前存成元数据，避免被向量相似度淹没。
2. 查询阶段（用户提问处理）
将用户问题拆解：拆出主体、动作、条件、时间；
优先使用元数据做过滤（过滤版本、时间、适用对象）；
使用关键词 + 向量混合召回，而不是单纯向量检索；
单独做查询改写，处理业务别名、口语化表达。
3. 召回之后：证据充分性检查（非常关键）
召回得到很多相关片段≠证据已经足够回答用户问题：
校验召回片段是否覆盖问题全部条件（主体、时间、例外、否定约束）；
如果多条证据出现冲突：优先对比来源权威性、文档版本、适用范围；
证据无法裁决、证据不足时，系统不能强行作答，需要追问用户或者直接拒绝回答。
4. 答案生成：证据引用闭环
检索层要保留完整原文上下文窗口，不要做过度摘要压缩；
最终输出答案，每一条结论都必须逐条绑定原文位置、引用来源，做到答案可溯源；
禁止脱离检索到的原文自由发挥。
三、评测该系统该关注哪些指标
不要只看召回率 Recall，需要多维度评测：
切片完整性：文档切片是否没有破坏否定、例外语义；
召回相关指标（recall）；
命中复盘能力；
引用准确率、答案忠实度（Faithfulness）（重点，针对否定条款场景）。
做对照实验要求：固定输入数据、模型版本，只改变一个变量，对比修改前后正确性、边界 case 表现、延迟、token / 显存成本。原理类问题，要能讲出阶段耗时、资源开销，而不是只背定义。
四、面试答题策略与追问应对
推荐面试答题四段式模板
给出核心判断；
讲清楚整套技术链路核心思路；
分析失败路径、系统边界（什么情况下这套方案会失效）；
给出评测指标、兜底降级策略。
面试官进一步追问（方案取舍）回答思路
先讲业务目标指标与约束条件；
解释为什么选择该技术路径；
说明优化必须要有对照实验；
明确兜底：当证据不足、指标越界时，系统要有追问、降级、回溯、人工接管机制，说明什么时候系统不能自动输出结果。
五、上线后运维策略
将关键业务指标、版本信息做时间线记录；
出现错误，能够区分问题来源：是输入分布变化、配置修改、模型升级，还是外部依赖问题；
修复完一个 bug 之后，把该 case 加入回归测试集；同时要检查其他关联任务，避免修复 A 问题，把 B 场景搞坏。

回答该面试题，不能只讲做否定词识别，不能只谈向量数据库，必须完整覆盖：文档解析入库、元数据过滤、查询改写、混合召回、证据充分性校验、答案引用闭环，还要讲系统边界、评测指标、降级兜底机制。
真正可靠的合同 RAG，不是简单找到某个关键词，而是证明这条结论在什么样的约束条件下才成立。

完整逐点实录（视频原文全部要点、例子、结论，无省略）
面试原题：RAG 系统做合同审查，遇到 “不允许、不得、除外、禁止” 这类否定条款，怎么避免把禁止条件理解反、输出相反结论？
开篇总纲（视频第一句结论）：“不得退款 ≠ 所有场景下都不能退款。要正确解析一条否定规则，必须同时拿到四样东西：否定范围、例外条件、适用主体、生效时间。少一个，答案就容易反转出错。”
一、题目本质（面试官真正想考察的，不是简单否定词识别）
不是考你会不会写正则匹配「不得 / 禁止 / 不支持」关键词
不是考向量库调参、topK 调大一点
本质考察：语义极性 + 条件约束 + 证据完备性
核心认知：合同文本里，同一句话里有同一个核心名词（退款），但是极性可以完全不同：允许、禁止、有条件允许、仅流程说明、例外豁免，不能只靠关键词命中。
视频标准示例 1（贯穿全程的主例子）
主合同原文：会员卡一经售出，不得退款
配套售后附件原文：商品存在质量瑕疵，经甲方售后审批后，可以办理退款
问题：用户问 “这个会员卡能不能退款？”
错误 RAG 行为：只召回 “不得退款” 片段，直接输出【不能退款】，忽略例外条款
正确理解：默认禁止，但满足【质量瑕疵 + 审批】这个前置条件时，允许退款
补充小例子（视频里顺带举的）
句子 A：活动商品不支持七天无理由退款（禁止）
句子 B：退款流程请联系客服登记（仅描述流程，不代表允许或禁止）
句子 C：除质量问题外，其余情形不得退款（带例外的否定）
句子 D：符合条件用户可申请退款（正向许可）
视频原话：这四句话都包含 “退款”，向量相似度很高，纯向量召回很容易混在一起，直接喂给模型就会极性颠倒。
二、高频踩坑清单（视频逐条列出的 5 类线上故障根源，顺序和视频一致）
坑 1：只依赖关键词、向量相似度召回，只抓核心名词，忽略范围修饰词
被忽略词清单：除非、但是、仅限、除外、除… 之外、不、不得、未经… 不得、在 XX 前提下、不适用
故障现象：模型只记住动作，丢掉修饰限定，把例外当成全局规则，或者把全局禁止当成全部场景禁止
坑 2：固定长度机械切片（chunk），把否定词和它修饰的对象切分开，语义断裂
示例：长句「除产品质量问题外，已激活会员卡不得申请退款」
错误切片方式：前一段切 “除产品质量问题外”，后一段切 “已激活会员卡不得申请退款”
后果：单独拿到后半段片段的 RAG，看不到例外前提，直接判定永久禁止退款
视频结论：合同文档，不能按固定 token 硬切；切片边界要尊重条款编号、标题、段落、表格、附属注释，保证一个完整约束条款在同一个 chunk 内部
坑 3：召回到部分相关片段，证据没收集齐全，直接丢给大模型生成答案
误区：召回到命中关键词的片段 = 证据足够
视频结论：相关 ≠ 充分。RAG 最大幻觉来源之一就是证据集残缺，模型自行脑补缺失条件
坑 4：把局部片段的约束，当成全局通用规则
典型：某一条款只针对【线下购买版本】的会员卡，RAG 检索出来之后，没有识别适用主体，直接套用到线上会员卡
坑 5：链路没有中间状态留存，出问题无法定位
错误做法：输入问题 → 召回 → 直接生成答案，不留日志
排查原则（视频原话）：不要反复重试让模型猜答案；先定位整条链路里第一个出错的节点，再决定调参、重试、降级；全程保留：原始用户 query、文档版本、切片内容、召回列表、重排得分、模型版本、中间标注结果，用于复盘回归
三、完整工程方案：入库阶段、查询阶段、召回后校验、生成输出闭环（视频主体核心方案，严格顺序）
视频核心架构思想：入库（离线建索引）和查询（在线问答）分离治理
阶段 1：入库 / 文档解析、建索引阶段（离线，提前做）
文档解析优先还原文档结构：识别合同章节、条款编号、子条款、附件、表格、注释、引用关系（比如本条款详见附件 B）
分块策略（chunking）：面向法律合同的专属切片策略
优先语义切片、条款级切片，而不是固定长度切片
一个约束条款（包含主体、动作、否定、例外）尽量放在同一个片段内
超长条款可以拆，但必须携带跨块引用标记，关联配套例外段落
给每一个切片附加结构化元数据标签（非常关键，视频重点强调）
元数据清单：文档标题、文档版本号、生效日期、失效日期、适用主体、适用产品类型、权限标签、条款编号、页码、来源附件类型
设计目的：时间、版本、适用对象这类硬约束，不要交给大模型从自然语言里猜，提前结构化存储，后续用元数据过滤，优先于向量检索
向量化入库：片段原文 + 元数据，同时构建稀疏索引（关键词 / BM25）+ 稠密向量索引，为混合召回做准备
【入库可选前置标注（高阶优化）】：入库时用规则 / 小模型预标注每一条片段的条款极性标签，标签一共 5 类：
正向许可（允许做）
否定禁止（不得做）
条件例外（禁止，但 XX 情况除外）
流程描述（只讲怎么做，不规定能不能做）
无关
视频说明：标注不是必选，但在合同审查这种高风险场景，预标注可以大幅降低后面生成阶段极性反转概率
阶段 2：查询阶段（用户提问，在线链路）
Query 解析与拆解：把用户问题拆解成结构化字段
拆解字段：动作（退款 / 解约 / 开票）、主体（买家 / 卖家 / 代理商）、对象（线上会员卡 / 线下套餐）、时间范围、前置条件
查询改写：处理口语化表达、业务别名、同义改写；生成多条检索 query，兼顾关键词表达和自然语义
优先元数据过滤：先用元数据做粗筛，把过期版本、不适用主体、不属于该产品的文档直接过滤掉，减少后续召回噪音
召回策略：关键词（BM25 稀疏检索）+ 向量稠密检索，混合召回，不是只用向量
理由：否定词、除非、除外这类逻辑词，向量相似度经常抓不住；稀疏检索对逻辑修饰词命中更稳定
重排（Rerank）：对混合召回结果做重排，优先把同一个条款的配套上下文（主禁止条款 + 例外条款）排在一起
阶段 3：召回之后：证据充分性校验模块（视频反复强调，是解决否定条款问题的核心关卡，很多 RAG Demo 没有这一步）
视频原话：召回完成，不等于可以送进 LLM 生成答案，必须先做证据校验
校验分 3 个子步骤：
条件覆盖检查：校验当前召回的全部证据片段，有没有覆盖 query 拆解出来的全部要素：主体、对象、时间、否定约束、例外条件
例子：用户问线上会员卡能不能退款；召回只有线下会员卡的禁止条款，缺少线上对应的例外，则判定证据不足
证据冲突裁决：多条证据结论冲突时，按优先级判定
优先级规则（视频给出顺序）：新版本文档 > 旧版本；专项附件细则 > 主合同总则；专门针对该主体的条款 > 通用条款
证据结果分支处理（三分支，硬性规则）
分支 A：证据齐全、无冲突 → 放行，进入答案生成
分支 B：证据互相冲突，无法自动裁决 → 禁止强行输出结论，触发兜底策略
分支 C：证据缺失、关键条件找不到 → 禁止编造答案，不能让模型脑补例外或者禁止规则
兜底动作二选一：向用户追问补充信息；或者直接返回【依据现有文档无法给出确定结论，请人工审核】
阶段 4：答案生成、引用闭环
上下文窗口策略：检索层保留完整原文上下文，禁止提前做摘要压缩再送入模型；压缩会丢失细微的 “除非、除外” 修饰词
Prompt 约束（固定要求）：
要求模型不能脱离召回原文自由发挥
结论必须绑定原文片段、条款编号、页码、文档来源
区分：全局规则、例外规则、生效前提，分开陈述
输出格式强制要求：每一条结论都附带溯源引用，做到答案可审计、可核验；生产合同审查场景，不允许无来源结论
输出示例模板（视频给的样例输出）
结论：默认情况下会员卡不得退款；若商品存在质量瑕疵并且经过售后审批，则允许退款。

四、评测体系：该系统要测哪些指标（视频明确区分，不能只看召回率 recall）
视频原话：很多人评估 RAG 只看召回率、准确率，否定条款场景，重点要测忠实度
评测指标清单：
切片完整性指标：是否会切断否定 + 例外的绑定语义（专项测试集：带 unless / 除外的长约束句）
基础检索指标：Recall 召回率、Precision 精确率、重排 NDCG
引用准确率：输出结论的引用原文，是否真的支撑该结论（防幻觉）
Faithfulness 答案忠实度（本场景最高权重指标）：模型有没有违背原文极性、私自增删例外条件、反转禁止 / 许可语义
边界 Case 通过率：专门构造一批容易极性反转的测试用例回归
工程指标：接口延迟、Token 消耗、显存开销
评测实验规范：
对照实验要求：固定数据集、固定模型版本，每次只改动一个变量（比如只改切片策略，或者只改召回方式），对比忠实度、边界 case 通过率、成本
视频提醒：不要只看平均指标，重点看坏 case、否定类 case 的失败率，平均指标很好不代表否定条款不出错
五、面试官高频追问 + 标准应答思路（视频完整给出面试应答四段式模板）
四段式答题模板（背这个框架）
先给出核心判断结论（比如：不能简单识别否定词，核心是约束四要素完备性）
完整讲整条技术链路：入库元数据 + 条款切片 → query 拆解 + 混合召回 → 证据充分校验 → 溯源生成
讲清楚系统边界：什么场景这套方案依然会失效（边界列举在下面）
给出评测指标 + 降级兜底策略
边界失效场景（视频列出，面试主动说出来加分）
合同存在隐性交叉引用、跨多个附件多层嵌套例外（A
