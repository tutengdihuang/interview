核心观点
工具调用本身就是意图识别的一种；提示词分类、RAG 分类同时承担「意图识别 + 路由」两个功能；四种方案各有适用业务场景。
四种实现方案详解
方案 1：结构化 Function Call（工具调用）
原理：把可用工具列表交给大模型，大模型识别用户意图，选择对应工具，同时填充好调用所需要的参数，输出结构化调用结果。
举例：系统有查天气、做菜两个工具。用户提问 “帮我查北京今天天气”，大模型识别意图，选择查天气工具，填好参数：地点北京、日期，交给工具执行拿到结果。
特点：识别意图 + 输出参数一步完成，直接可以交给工具执行。
方案 2：提示词分类（一级路由）
原理：不使用 Function‑Call，在 Prompt 中列出 Agent 全部能力 / 全部意图类别，让大模型输出意图标签，根据标签路由到对应的子 Agent 处理。
举例：酒店 Agent，能力包含订房、退房、洗衣、就餐。用户说 “帮我订个房”，大模型识别意图标签是订房，就转发到订房子 Agent 执行；退房就走退房子 Agent。
适用场景：意图类别数量不多，全部类别可以塞进 Prompt 上下文，做一级路由。
方案 3：RAG 分类（二级路由，解决类别太多的问题）
背景痛点：大型客服系统（类似淘宝），意图多达几百种，无法全部塞进 Prompt，上下文会超限，这时用 RAG 做前置筛选。
原理：用户提问先做语义检索，召回相似度最高 Top‑K 少量候选意图，把精简后的候选给到大模型，由大模型最终判定真实意图，再路由到对应子 Agent。
举例：用户问 “查订单物流到哪了”。RAG 召回 3 条候选：订单查询、物流查询、数码 3C。大模型判定真实意图是物流查询，交给物流 Agent。
类比讲解：如同导航，先选省份（一级路由），再选城市县城（二级路由）。RAG 承担二级过滤，减少 Prompt 长度，防止上下文溢出。
重点：提示词分类、RAG 分类，既是意图识别，同时也是意图路由，二者概念要区分开。
方案 4：模型微调（独立意图识别小模型）
原理：准备大量标注样本（用户 query + 对应意图标签），微调专门的分类模型。用户输入先过这个微调模型，直接输出意图，再去调用 sub‑Agent。
适用场景：需要本地部署，不想频繁调用大模型 API 服务的业务；可以在本地完成意图识别，评估推理性能。
优势：可以脱离云端大模型，本地推理。

开篇总论点
业内工业落地、面试常说的意图识别一共 4 种主流方案；不能只简单回答 “意图识别就是判断用户想干嘛”，面试高分回答要把 4 套方案分别讲清楚原理、例子、适用场景，还要讲清楚意图识别和路由二者的关系。
方案 1：结构化 FunctionCall（结构化工具调用）
核心结论：工具调用本身就是意图识别的一种。
原理：提前把所有可用工具列表交给大模型；大模型读取用户提问，识别用户意图，自动选择匹配的工具，同时自动填充该工具所需要的入参，输出结构化结果，直接交给工具执行拿到结果。
视频原例子：系统配置两个工具：查天气工具、做菜工具。用户提问：“请帮我查一下北京今天的天气是什么？”
大模型从给到的工具列表里选中【查天气】工具；
自动填充参数：地点北京、日期；
交给天气工具执行，返回天气结果。
结构化含义：不仅识别意图，同步把调用参数一并生成，一步到位，可直接执行。
适用场景：Agent 需要直接调用工具完成动作的场景。
方案 2：提示词分类（一级路由）
原理：不使用 FunctionCall。在 Prompt 里，把当前 Agent 全部能力 / 全部意图类别全部写进去给到大模型；让大模型输出对应的意图标签；根据标签，分发路由到对应的子 Agent 执行。
视频原例子：酒店 Agent，能力包含：退房、订房、洗衣、就餐等一二十种意图。用户提问：“请帮我订个房。”
Prompt 上下文 = 用户问句 + 酒店全部能力清单；
大模型识别意图标签为【订房】；
路由分发到订房子 Agent 处理；退房就分发到退房子 Agent。
架构特点：一个子 Agent 对应一项独立能力，实现能力解耦。
定位定义：提示词分类 = 意图识别 + 一级路由。
适用场景：意图类别数量不多，全部意图可以放进 Prompt 上下文，不会超长溢出。
方案 3：RAG 分类（二级路由）
痛点背景：超大客服系统（类比淘宝客服），意图数量多达几百种；无法把几百个意图全部塞进 Prompt，会直接上下文超限。
原理：用户输入先做向量语义检索，召回相似度最高的 Top-K 少量候选意图；把筛选精简后的少量候选意图送入大模型；由大模型最终判定真实意图，再路由到对应子 Agent。
视频原例子：用户提问：“请帮我查一下这个订单物流到哪里了。”
RAG 语义检索召回 Top3 候选意图：订单查询、物流查询、数码 3C 咨询；
把这 3 条候选给到 LLM；
大模型判定真实意图是物流查询；
路由交给物流子 Agent 查询物流信息。
路由类比（视频原话）：和导航逻辑一致
提示词分类（一级路由）：先选省份；
RAG 分类（二级路由）：省份确定之后，再筛选城市、县城；
定位定义：RAG 分类 = 意图识别 + 二级路由。
核心价值：先通过向量检索做一轮过滤，大幅减少送入大模型上下文里的意图数量，防止上下文窗口撑爆。
适用场景：意图量级很大（几百个意图）的大型客服、复杂业务系统。
【视频重点区分结论】提示词分类、RAG 分类，这两个方案同时承担两件事：意图识别 + 意图路由；意图识别、路由本身是两个独立概念。
方案 4：模型微调（独立意图识别小模型）
原理：单独训练、微调一个专门用来做意图分类的小模型；训练数据集格式：用户 query + 对应的意图标签。
示例训练样本：query = 我要吃饭，标签 = 就餐；query = 我要洗澡，标签 = 洗浴。
执行流程：用户提问进来，先走这个微调好的分类模型；模型直接输出意图标签；拿到标签之后，再去调用对应的 subAgent。
视频点明的独有优势：前面三种方案大多需要调用云端大模型服务；微调小模型可以本地部署、本地推理完成意图识别，不需要反复调用 LLM 云端接口；同时可以自主评估推理性能。
适用场景：业务要求本地私有化部署、不想依赖云端大模型 API、线上流量大希望降低云端调用成本的场景。
