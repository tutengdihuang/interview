视频详细内容总结
视频主题：Agent 越用越乱，不要急着更换大模型，应当理清「项目、对话、子 Agent、Worktree」四层边界，解决 Agent 工作混乱问题。
核心观点
很多时候 Agent 输出跑偏、逻辑混乱，根源不是模型能力不足，而是四层工作边界没有划分清楚。应当先梳理四层边界，再评估模型本身。作者把四层做了生活化类比：项目 = 办公室，对话 = 桌上的公文，分别解决长期沉淀、会话上下文、任务隔离、文件隔离四类问题。
第一层：项目（项目文件夹）
场景：Agent 已经拥有目录访问权限，为什么还要单独建项目文件夹？
临时闲聊、一次性小任务，不需要项目文件夹；连续的系列长期工作，必须建立项目。
区分访问权限和工作环境：拥有全盘访问权限 ≠ 有规整的工作环境。项目文件夹是把工作需要的规则、工具、产出物集中存放。
两类内容沉淀到项目：
项目经验：项目规范、约定、踩坑记录；新开对话读取后，就可以接续历史工作，不用重复说明背景。
固定环境：项目专属技能 skill、素材、脚本、依赖配置；再次进入项目，环境直接就绪，不用每轮重新搭建。
作用：为长期任务提供统一规则、环境、经验沉淀载体。
第二层：对话（聊天会话）
类比：项目是办公室，对话是桌上单次处理的公文。
不同工作尽量分开不同对话；同一个任务也不要无限在同一个对话持续运行。
虽然模型上下文窗口很大，但不等于全部历史都能被准确利用。
自动上下文压缩会释放 token 空间，但压缩会做信息取舍，会丢失细节、约束条件，后续 Agent 行为就容易跑偏。
不要等到明显出错才新开对话；一个工作阶段结束就做交接，而不是完整复述全部历史。
交接需要整理内容：已完成事项、确认过的决策、必须遵守的规则、下一步工作。
可以把交接流程封装成 skill，到阶段节点自动提醒；是否新开对话、交接摘要怎么传递，取决于平台和授权条件。
第三层：子 Agent（Sub‑Agent）
核心价值：上下文隔离。
使用场景：任务需要翻阅大量资料、产生大量原始素材，交给子 Agent 独立处理。子 Agent 在自己独立上下文完成分析、信息精简，只把结论、依据、待确认问题返回主对话，主会话不会被海量原始信息污染。
重要提醒：子 Agent 不是免费加速手段。会增加模型调用成本，还带来任务分配、结果校验、结果汇总的额外工作量。
不适合强依赖的任务：任务之间强耦合、互相等待，拆分给子 Agent 会产生大量反复沟通。
使用原则：优先拆分边界清晰、可以独立验收的任务，不要为了多 Agent 而强行拆分子 Agent。
拓展用法：不同工作界面分工，主任务留在主会话，资料分析等放到独立子 Agent 上下文，完成后带回结果；要保证任务可独立执行、结果可追溯；多账户额度是否共享，要看产品本身规则，不是通用特性。
第四层：Worktree（工作树，文件隔离）
解决痛点：就算分开多个对话，多个会话同时修改同一份文件，依然会发生文件互相覆盖。
Worktree 给同一个代码仓库生成多个独立工作目录，不同任务在各自目录修改文件，之后再对比差异、合并结果。
使用时机：不要新建对话就无脑新建 Worktree。任务顺序串行推进，用同一个目录就足够。
真正适合场景：多个方案并行，需要同时修改同一个项目代码 / 文件，此时开启独立 Worktree 做文件隔离。
局限性：Worktree 只隔离文件，不会自动解决代码合并冲突，冲突仍然需要人工处理。
四层整体工作流程总结
长期系列工作：用项目沉淀规则、工作环境、项目经验；
工作阶段切换：对话会话做好阶段交接，避免上下文过长失真；
独立大信息量分析任务：交给子 Agent做上下文隔离，只回收关键结论；
多方案并行修改文件：启用Worktree隔离文件，防止文件互相覆盖。

第一层：项目（项目文件夹）
提出问题
既然 Agent 已经拥有访问很多目录的权限，为什么还需要专门创建项目？
不需要项目的场景（例子）：闲聊、一次性用完就结束的小任务，不必建立项目。
必须建立项目的场景：需要连续开展一系列工作，需要为规则、工具、产出物找固定存放位置。
关键区分（类比例子）：把访问权限和工作环境分开看待。
类比：手里持有整栋大楼门禁卡，不等于拥有一间专属办公室。
访问权限：能不能读取到这些文件夹；
项目（办公室）：把这项长期工作所依赖的全部信息组织集中存放。不是单纯靠目录做权限锁死，而是信息聚合。
两类要沉淀到项目中的内容
项目经验类：项目规范、业务约定、过往踩坑记录。
效果：新开对话读取项目内资料，就可以直接接续历史工作，不需要反复复述背景。
固定环境类：项目级技能 skill、素材文件、脚本、依赖配置。
效果：下次进入该项目，工具、说明全部就绪，不用每一轮对话重新搭建环境。
本层完整结论
项目文件夹面向长期连续任务，用来沉淀经验与运行环境，实现跨对话复用工作资产。
第二层：对话（聊天会话 / 线程）
类比：项目是办公室，对话就是桌面上正在处理的一份公文。
基础使用原则
不同的工作，尽量分开不同对话窗口；
同一件任务，不要无限期在同一个对话持续跑下去。
误区点：虽然模型上下文窗口容量很大，但窗口大≠全部历史信息都可以被模型准确使用。
上下文自动压缩的弊端（重点）
自动压缩作用：释放 token 空间；
本质：做信息取舍；
后果：反复总结压缩之后，任务细节、约束条件会丢失，Agent 后续动作就会发生偏离。
错误做法：等到 Agent 已经明显跑偏出错，才新开对话。
正确做法：阶段结束做交接，而不是完整复述全部历史再继续
交接摘要里面需要写清楚的内容清单：
①需要完成哪些内容；②已经完成哪些事项；③哪些决策已经确认；④必须遵守哪些规则；⑤下一步从哪里继续执行。
工程优化手段：可以把这套交接流程封装成 skill，到阶段节点自动提醒使用者做交接。
现实约束条件：是否新开对话、交接摘要如何传递，取决于使用的平台以及账号授权情况，不是所有平台都支持。
本层完整结论
对话管理解决上下文膨胀失真；不要无限拉长单条会话；阶段完成做结构化交接，避免全部历史丢失。
第三层：子 Agent
子 Agent 最核心价值：上下文隔离
适用场景（举例）：独立任务需要翻阅海量资料，会产生大量原始材料。
工作模式：交给子 Agent，在它自己独立的上下文里面完成资料处理、信息简缩、分析；只把结论、依据、待确认问题带回主对话。
收益：主对话不会被海量原始素材污染，主会话上下文不会爆炸。
重要反面提醒：多开子 Agent 不是免费提速
成本 1：会增加模型调用量；
成本 2：带来任务分配、结果检查、结果汇总的额外人力成本。
不适合使用子 Agent 的场景：任务之间强依赖、强耦合。拆出去之后会产生大量反复来回沟通，反而降低效率。
子 Agent 使用原则：优先拆分边界清晰、可以独立验收的任务；不要为了用多 Agent 而强行拆分子 Agent。
拓展用法：用于不同工作界面分工。主任务保留在主会话，资料分析类工作放到子 Agent 独立上下文，完成之后带回结果。
两个现实注意点
要求：拆分后的任务要可以独立执行，结果要能够追溯；
额度提醒：不同产品账号之间调用额度是否共享，要看产品实际账户规则，不能当成通用默认前提。
本层完整结论
子 Agent 用来隔离上下文，适合独立、低耦合任务；存在调用与校验成本，不可盲目滥用。
第四层：Worktree（工作树，文件隔离层）
底层痛点：就算分开多个独立对话，多个对话如果同时修改同一份物理文件，依然会发生文件内容互相覆盖。
Worktree 是什么：为同一个代码仓库提供多个互相独立的工作目录。不同任务分别在各自目录修改文件；完成之后人工对比差异，再合并结果。
错误做法：每新建一个对话，就直接新建 Worktree，属于过度使用。
不需要 Worktree 的场景：任务是顺序串行推进，只用一份工作目录就足够。
真正适合启用 Worktree 的场景：需要同时拿出多个方案，并行修改同一个项目的代码 / 文件。此时用独立工作目录做文件隔离。
明确局限性（重点）：Worktree 仅仅隔离文件，不会自动处理合并冲突；冲突依然需要人工处理。
本层完整结论
Worktree 隔离磁盘文件，解决多任务并行编辑同一套源码互相覆盖；串行任务不需要，冲突需要人工处理。
四层综合落地流程（视频最终完整总结）
长期系列工作：使用项目沉淀规则、固定环境、项目经验；
工作到达阶段节点：对话会话做结构化交接，防止上下文过长导致信息失真；
有独立、信息量大的分析任务：交给子 Agent做上下文隔离，只回收关键结论；
需要多套方案并行修改文件：启用Worktree隔离文件，防止文件互相覆盖。
最终总论断：当 Agent 越用越乱的时候，优先把四层边界梳理清楚；梳理完之后，再去判断是不是模型本身能力不足。很多 Agent 混乱问题，根源不是模型，而是四层边界没有划分。
