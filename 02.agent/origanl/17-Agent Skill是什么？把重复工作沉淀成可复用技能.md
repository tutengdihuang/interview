视频主题：Agent Skill 是什么，如何把重复工作沉淀为 Agent 可复用的技能，主讲人小哲，面向 Agent 开发学习者，核心讲清楚 Agent Skill 概念、和普通提示词区别、编写要点、加载机制、制作流程、使用外部技能的注意事项。
一、什么是 Agent Skill
Agent 相当于通用 AI 助手，能听懂人类语言，但并不天然熟悉你的专属业务流程（整理资料、写前端、处理文档都有各自专属流程）。
Agent Skill 就是一套可被 Agent 读取的任务说明：写清楚某一类任务怎么做、什么时候启用这个技能、需要用到哪些资源。
产生背景：如果同类任务每次都要重复交代规则、格式、背景资料，效率很低，Skill 就是把这套稳定流程沉淀下来复用。
和普通临时提示词的区别
临时提示词：只为单次任务写，用完即结束。
Skill：核心重点是复用，存入稳定流程、约束要求、参考资料，遇到对应场景就调用，省去反复交代。
误区：不是单纯把提示词写长，也不是光靠 Markdown 标题就能保证模型输出正确。
二、关于 Markdown 格式的作用与局限
很多 Skill 会用 Markdown 编写，原因是标题分段可以把用途、执行步骤、约束条件、参考资料做结构化拆分，既方便人维护，也便于模型识别信息。
重要局限：Markdown 只是排版组织文本，不能强制模型按顺序执行，也无法保证模型不漏读信息。
核心永远是内容本身：要明确写清：适用场景、输入格式、预期输出结果、硬性限制；
如果需求本身互相矛盾，无论怎么调整标题层级，都解决不了逻辑冲突。
三、Skill 的渐进加载机制
Skill 采用按需渐进加载的运行逻辑：
Agent 先读取技能名称、简短描述，判断当前任务要不要启用该技能；
确定选用之后，才去读取完整详细步骤，必要时再加载配套参考文件。
性能开销误区：这种模式只是减少无关内容常驻上下文，不会消除全部计算成本。当技能被真正调用时，详细文本、工具调用依旧会消耗 token 与算力，只是不用一开始就把全部内容载入上下文，不是 “长技能只消耗两行提示词的成本”，加载行为取决于你使用的 Agent 系统。
四、自己制作 Agent Skill 完整思路
不用一开始就手写一大堆复杂文件：可以告诉 Agent 你的工作目标，让 Agent 帮忙梳理任务步骤，再按照平台规范生成技能目录；平台自带技能生成工具就直接用，没有就遵循平台支持格式手动编写。
举例：做一份资料整理 Skill，需要写明处理什么材料、输出怎么组织、哪些信息必须保留，沉淀真实可落地流程。
⚠️风险提醒：AI 可以帮生成技能文件，但业务目标、质量标准需要人把控，不能 AI 提示 “创建成功” 就代表技能可用。
必须做实测验证：写完之后拿真实业务输入跑一遍，核对输出是否达标，排查缺失步骤；有 bug 就修改技能说明，反复测试同类任务。
制作 Skill 的本质：把个人工作习惯沉淀为可复用方法，不是单纯收集一堆好看的技能文件。
五、使用网上别人公开 Skill 的注意点
代码仓库、技能社区能下载他人写好的 Skill，可以参考对方的组织方式。
下载≠可以直接用：要校验依赖环境、可用工具、任务边界，别人的技能不一定适配你的运行环境。
不建议大批量导入一堆技能：优先针对高频重复、规则稳定、结果可以校验的工作制作 / 引入 Skill；先把单个技能调通跑稳，再慢慢搭建个人技能库，少追求数量，便于排查 bug 和维护。
六、环境与设备的边界
能不能新建、导入、运行 Skill，不由设备单方面决定，取决于产品功能、运行环境可访问的资源。
如果任务涉及本地脚本、本地文件，电脑端环境会更占优势；不同系统限制不一样，需要以实际平台为准。
七、核心总结观点
Agent Skill 本质：保存重复工作的处理方案，让 Agent 在匹配场景自动使用。
完整闭环：写清用途→梳理执行步骤→按需加载机制→真实业务数据反复验证。
AI 可以辅助生成技能文件，但评判 Skill 好坏的唯一标准：能不能稳定解决你的真实业务问题。

一、开篇提出大家普遍的痛点（视频开头引子）
很多人每次用 Agent 做同类任务，都要反复跟 AI 交代一遍规则、格式、约束、交付标准。
同样类型的工作，上一次刚讲清楚，下一次又要重新说一遍，效率很低、输出不稳定。
很多人听说 Agent Skill，但分不清它和普通提示词的差别，以为就是写一个更长的 Prompt。
大量新手误区：把 Skill 理解成 “写一个很长的 Markdown 提示词，丢进去就能自动稳定干活”。
二、核心定义：什么是 Agent Skill（视频原话）
Agent 本身是通用智能体，听得懂自然语言，但它不会自带你的业务 SOP、你的个人工作规范、团队内部的交付标准。
Agent Skill：是一套被 Agent 系统识别、封装好、可复用的任务处理包；包里写明：这个技能适用场景、触发条件、执行步骤、硬性约束、输出模板、配套参考资料、可以调用的工具。
Skill 本质 = 把你反复做的固定流程、验收标准提前沉淀下来；当任务匹配场景时，Agent 自动识别、加载这套方案，不用人每次重新说明。
一句话结论：Prompt 服务单次对话；Skill 服务一类重复任务的长期复用。
对比 1：临时提示词 VS Skill（视频重点对比）
临时提示词
生命周期：单次对话有效，对话结束就失效
触发方式：用户每一次手动粘贴、手动输入
存储：没有固定目录、系统不会自动识别
目标：解决当下这一条需求
例子：你直接发给 Agent 一段文字：“帮我整理这份纪要，按【要点 + 待办 + 责任人 + 截止时间】输出”
Skill
生命周期：持久保存在技能目录，长期存在
触发方式：Agent 自动判断任务是否匹配描述，自动路由调用
存储：固定文件夹 / 固定 SKILL.md 结构，系统可以扫描识别
目标：统一解决一整类同质任务
例子：一个叫「会议纪要整理」的 Skill；以后只要丢录音转写文本、会议原文，Agent 自动调用，固定格式、固定校验规则，不用每次重复写要求
对比 2：Tool（工具） VS Skill（视频里面顺带讲到的区分）
Tool：是执行动作，是 Agent 的手，负责 “能不能做”；调用接口、读文件、运行脚本、联网查询都属于 Tool，会产生副作用、改变外部状态。
Skill：是方法论、流程说明书，负责 “怎么做才对”；Skill 里面可以写明什么时候调用哪个 Tool、调用参数规范、调用之后怎么校验结果。
结论：二者不是替代关系，是组合关系；Skill 编排 Tool，Tool 提供执行能力。
三、Markdown 编写 Skill：作用 + 非常重要的局限（视频重点坑点）
为什么绝大多数 Skill 都用 Markdown（SKILL.md）写？
方便人阅读、维护、修改；
可以用标题层级把内容做结构化拆分：名称、描述、适用场景、不适用场景、执行步骤、输出规范、检查清单、参考资料；
模型更容易区分不同模块的信息块，降低理解混乱。
【高频误区，视频专门强调】Markdown 标题、分段没有强制执行能力！
❌错误认知：只要我用二级标题写步骤，Agent 就一定会按顺序一步步执行、不会跳步骤、不会忽略约束。
✅视频结论：Markdown 只是排版格式，只是文本；它不能强制模型顺序执行，不能保证模型读完所有段落、不漏掉限制条件。
根源问题：输出翻车，根源是规则本身写得模糊、互相冲突、边界不清，不是标题层级不够好看；换再多 markdown 排版也救不了逻辑矛盾。
实操建议：约束条件、禁止项、验收标准，要显性单独写，不要埋在大段文字里面。
四、核心机制：渐进加载 / 按需加载（视频重点，配有运行流程讲解）
Skill 在系统里分为三层信息，不是一次性全部塞进上下文：
第一层（常驻、永远加载，token 开销极小）：Skill Name + 简短 Description（描述），相当于技能的标签、简介。Agent 靠这一层判断：当前用户任务要不要启用这个技能。
第二层（按需加载）：当 Agent 判断匹配成功，才读取完整的指令、步骤、输出规则、检查清单。
第三层（延迟加载）：配套参考文档、素材、外部脚本、附件，只有步骤里面明确要求查阅的时候，才加载。
视频重点辟谣误区：
❌误区：按需加载 = 这个技能几乎不消耗 token，调用的时候也很便宜。
✅视频结论：只是平时不占上下文；一旦触发调用，完整指令、参考资料、工具调用照样消耗 token 和算力，不会凭空降低成本；它解决的是【大量 Skill 共存时，全部预加载把上下文撑爆】的工程问题，不是免费省 token。
工程价值：当你有几十上百个 Skill，不可能全部一次性塞给模型；靠这种机制，缩小候选集，避免上下文溢出、路由混乱。
举例辅助理解（视频举例）：你有 100 个 Skill，一开始模型只读取 100 条简短名字 + 一句话简介；当你说 “整理会议纪要”，模型匹配到纪要 Skill，才把纪要的完整流程、格式要求读进来，剩下 99 个技能的详细内容全程不加载。
五、从零制作 Skill 的完整流程（视频给出的实战全流程，每一步都讲到）
视频原话：不用一上来就写一个巨大、复杂的 Skill，优先小而稳定，迭代打磨
第一步：锁定一个高频、重复、规则稳定、输出可以校验的任务（不要选边界模糊、需求经常变的任务）
✅适合做 Skill 例子：会议纪要整理、代码评审检查清单、短视频脚本拆解、周报自动汇总
❌不适合例子：创意发散、无固定标准的自由文案、每次需求完全不一样的定制策划
第二步：梳理清楚这件事的完整人工 SOP，拆步骤；先自己平时怎么做，把隐性经验显性写出来
要写清楚 4 块信息：
① 适用场景：什么时候调用
② 反例 / 不适用场景：什么时候绝对不能调用（防误触发）
③ 分步执行流程
④ 硬性约束、禁止行为、输出模板、验收检查点
第三步：可以让 Agent 辅助生成初始 Skill 文档（很多平台自带 skill-creator 技能）
提醒：AI 生成只是初稿，AI 会自动省略很多你默认知道的业务细节；业务标准、质量底线，必须人来把控，不能 AI 生成完直接上线。
第四步：实测验证（视频强调这一步是绝大多数人跳过的）
拿真实业务样本去跑，而不是随便拿一个测试样例；
对照你的验收标准逐项核对输出；
记录翻车点：漏步骤、格式错、越界回答、调用错工具；
第五步：迭代修改 Skill 文本，补充约束、补反例、补检查清单；反复测试同类输入，直到同类输入稳定达标；
第六步：归档到技能目录，让系统扫描识别，自动路由。
视频一句话结论：Skill 不是一次性写好就永久不变，是持续迭代的，和代码维护一样。
六、导入网上开源 / 别人写好的 Skill：全部风险与使用要点（视频专门讲）
网上 Github、社区有大量公开现成 Skill 包，可以参考写法、参考结构；但是下载≠开箱即用。
需要逐项校验的内容：
依赖的工具、MCP 服务、接口环境，你这边有没有；别人 Skill 里面调用的脚本、API，你没有就跑不通；
它的业务边界是否和你的需求一致；别人的约束、验收标准是适配他自己的业务，不一定适配你；
权限风险：部分 Skill 自带脚本、文件读写、网络请求能力，导入陌生 Skill 有执行风险；
实操原则（视频强烈建议）：
不要一次性批量导入几十上百个 Skill；
优先单个引入，逐个调通、验证命中率、验证输出质量；
技能库追求稳定可控，不追求数量；Skill 越多，路由误命中概率越高。
误命中问题说明：Skill 多了之后，模型容易选错技能；只靠模型自己判断是不够的，好的 Skill 一定要写清楚【不适用场景、负向例子】，用来区分相似任务。
举例：一个 PPT 生成 Skill，要写明：只做演示文稿排版，不做数据清洗、不做财务计算，避免用户问数据的时候错误调用 PPT 技能。
七、运行环境、设备边界（视频讲到的边界结论）
Skill 能不能新建、导入、正常运行，不由电脑 / 手机硬件单方面决定，由你使用的 Agent 平台的功能规范决定。
如果 Skill 里面包含本地脚本、本地文件读取、本地工具调用：电脑端环境支持度远高于移动端；
不同平台规范不一样：有的平台支持标准 SKILL.md 目录结构、支持 references 引用附件；有的平台对 Skill 格式做了自定义限制，需要遵循平台文档。
结论：同一个 Skill 文件，换到另一个 Agent 平台，有可能无法识别、无法加载。
八、新手常踩的全部坑点汇总（视频单独拎出来提醒）
坑 1：把 Skill 写得非常长，把所有资料全部塞进主文档，不做拆分、不做引用，导致加载 token 爆炸。
坑 2：只写 “可以做什么”，不写 “不能做什么”，大量误触发。
坑 3：写完不实测，靠想象觉得逻辑没问题，上线之后同类任务输出波动巨大。
坑 4：一次性搭建几十上百个 Skill，不做分层路由，模型在一堆相似技能里乱选。
坑 5：混淆 Skill 和 Tool，想用 Skill 去直接执行接口、脚本（Skill 是流程说明，执行交给 Tool）。
坑 6：迷信 Markdown 格式，以为排版漂亮就能解决模型不稳定的问题。
坑 7：直接照搬网上开源 Skill，不看依赖、不做安全校验直接启用。
九、视频收尾总结观点 + 引流部分
核心总结论：Agent Skill 本质，就是把高频重复工作的稳定处理方案、验收标准封装起来，交给 Agent 在匹配场景自动调用。
完整闭环：定义场景 → 梳理 SOP、写明边界与步骤 → 结构化写成 Skill 文档 → 平台加载、渐进路由 → 真实样本测试 → 持续迭代维护。
权责总结：AI 可以帮你起草、生成 Skill 文件；但是，Skill 好不好用，评判标准只有一条：能不能稳定、可控地解决你的真实业务问题，这个判断权在人。
