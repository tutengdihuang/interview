面试题：为什么 Claude Code 这类代码 Agent，不把传统 RAG 向量检索作为主方案？
很多人学 RAG，就以为做代码 Agent，第一件事就是把整个代码库切片、向量化，丢进向量数据库。
但 Claude Code、Cursor 这类代码智能体，都没有把传统 RAG 当做主检索方案。这是一道高频面试题，面试官考的不是你背 RAG 定义，而是考察工程落地思维。
先简单回顾传统 RAG 怎么做：
把文档或者代码切成小段，用 Embedding 模型转成向量，存入向量库。用户提问的时候，把问题也转向量，用相似度检索召回语义相近的片段，再丢给大模型。
这个套路在普通文档场景很好用，但是代码仓库不一样。写代码、查 bug，我们要的不是 “意思差不多”，而是精准符号定位，文件、函数、行号必须完全正确，代码内容必须是最新版本。
先说核心结论：
不是完全不用 RAG。主路径用 Agentic Search 智能体式检索，RAG 只做补充兜底。
Agentic Search，就是让大模型像程序员一样，自己调用工具多轮迭代搜索仓库。
工具一般就三类：glob、grep、read。
下面讲传统 RAG 在代码场景的三大硬伤。
第一点：向量检索很容易误召回。
代码要找函数名、类名、报错堆栈，必须精确匹配。向量是语义相似度匹配，经常返回语义看着很像，但根本不是目标的代码片段。
这些错误片段会变成噪声，喂给大模型之后，AI 就容易改错代码。而 grep 文本检索，可以直接精确匹配字符串，定位到目标代码。
第二点：代码迭代速度太快，向量索引极易过期。
日常开发不停提交、文件改名、函数重构。一旦代码变动，预先构建好的向量索引就失效了。
想要保持索引实时，就要整套系统：增量切片、增量 Embedding、删除旧向量、更新向量库。这套系统很重，维护成本非常高。
第三点：安全与权限风险。
多维护一份向量索引，就多一份源代码泄露面。如果调用外部 Embedding 服务，源代码要离开本地环境，存在数据泄露风险。
而按需直接读取本地文件，链路短，权限体系更容易对齐。
接下来讲 Agentic Search 这套智能检索，是分层探索：
第一步 glob：遍历目录，扫文件名，低成本缩小候选文件集合。仓库很大的时候，先过滤掉无关文件夹和文件。
第二步 grep /ripgrep：拿函数名、报错信息、接口路径去搜索，定位相关代码片段。
第三步 read：确认目标文件之后，才读取完整文件，拿到完整上下文。
模型会根据上一轮搜索结果动态调整策略。搜出来太多，就增加条件缩小范围；搜不到，就换关键词重新搜索。
整个逻辑和程序员排查 bug 一模一样，不是把整个仓库全部塞进上下文，靠线索一步步逼近目标。再搭配大窗口和 token 缓存控制开销。
当然，Agentic Search 本身也有缺点，面试一定要提到，显得客观全面：
高频通用关键词，一搜返回成千上万条结果，模型筛选压力很大；
如果代码重构、函数改名，纯字符串精确搜索直接失效；
多轮工具连续调用，复杂任务延迟会变高，用户体感慢。
所以生产环境成熟方案是混合架构：
主干：Agentic Search，glob + grep + read，做精确检索，处理绝大多数日常编码、查 bug 场景。
补充：RAG 向量检索用来兜底。遇到超大仓库、概念类查询、大量重构改名场景，再启用语义向量检索，两者互补。
最后总结面试答题思路：
Claude Code 没有将传统 RAG 作为主路径，核心原因是代码检索对精确定位、实时性、权限安全要求很高。向量索引会带来索引过期、数据同步、维护成本高、容易误召回的问题。
主体方案采用 Agentic Search，模型调用 glob、grep、read 工具，先低成本缩小搜索范围，再读取目标文件，并且根据搜索反馈动态调整查询策略。
但该方案也存在短板：热门关键词命中结果爆炸、重构改名场景会搜不到、多轮工具调用带来延迟。生产上一般采用混合架构，精确搜索为主，语义 RAG 按需补充。
底层思想一句话：优先用本地确定工具解决问题，不要盲目引入一套沉重、需要长期维护的向量索引系统。
