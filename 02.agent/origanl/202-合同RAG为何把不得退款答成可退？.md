视频详细内容总结
这个视频是一道 AI 大模型 RAG 面试题讲解，核心问题：合同明确写 “不得退款”，但 RAG 系统却输出 “可以退款”，故障原因以及完整工程解决方案，专门针对合同这类法律文档知识库的 RAG 落地，不只是基础向量检索知识。
一、问题的本质
很多人会误以为是向量检索没搜到正确片段，但真正根源是：向量检索只看语义相关性，相关性≠事实支持。
“不得退款”、“仅质量问题可退”、“超时不能退款”，这些文本都包含 “退款” 关键词，在向量空间相似度很高。
如果直接把相似度高的文本片段丢给大模型，模型容易忽略否定词、前提例外条件，生成看似通顺、但业务完全错误的答案。
这道面试题考察的不是 embedding、向量库、top‑k 基础概念，考察候选人是否处理过否定语义、约束条件、证据边界，很多只做过简单 RAG 的人会在这里踩坑。
核心结论：合同场景 RAG 不能只做相关性召回，必须配套条款极性识别、适用条件解析、证据引用、答案校验整套流程。业务问题拆解三层：①找到相关条款；②判断条款是允许 / 禁止 / 有条件允许；③强制模型依据原文、引用原句生成回答。
二、三步工程解决方案
第一步：文档切片，不能用固定长度硬切，防止丢失否定和例外上下文
合同经常出现 “除非 XX 情况，否则不得退款” 这类句式：
如果切片把前后文拆开，只拿到后半句，回答会过于严苛；只拿到例外前半句，又会错误判定可以退款。
✅正确做法：按照条款编号、标题、条款上下级关系做切片，而不是固定字符长度切割。
组装上下文的时候，要一并带上例外条款、定义条款、附件补充协议，不能只取孤立片段。
第二步：召回之后做重排 + 结构化极性判断
初始召回可以放宽范围，把退款、解除合同、违约金、售后等相关片段全部捞出来；
重排不能只看相似度，要判断片段是否能够直接回答当前用户问题；
让模型输出结构化内部判断：是否允许退款、适用什么条件、证据对应哪一条原文；用规则 / 结构化输出做校验，杜绝 “文本相关就代表业务支持” 的错误逻辑。
第三步：答案兜底校验，缺少证据不能自行脑补业务口径
如果知识库只写了部分场景 “不得退款”，但用户提问的场景原文没有覆盖，严禁模型自己编造业务结论；需要如实告知：现有文档仅说明 XX 场景规则，未覆盖你的问题。
重点测试 4 类风险场景：否定条款、例外条款、多版本合同冲突、证据缺失。
三、容易忽略的工程细节
查询改写和答案约束要分离
用户问 “能不能退”，检索侧要扩展同义词：退款、解除合同、撤销订单、返还费用、违约金，保证证据找全；但是生成答案阶段不能随意等价替换概念，不能直接把 “解除合同” 等同于 “全额退款”。
报错要分类，不要盲目调大 top‑k
错误分为 4 类，处理方案各不相同：
①完全没召回；②召回了但是排序靠后；③排到最前面，但大模型误读原文；④多条证据本身互相冲突。
坑点：单纯加大 top‑k，会召回更多语义相近但立场相反的条款，反而让模型更加混乱，解决不了问题。
强证据绑定机制
所有输出结论必须可以回溯到合同条款编号。如果模型输出 “原则上可以退款”，但是引用原文全部都是 “不得退款”，这个回答要直接拦截，不对外输出。
四、面试答题参考话术
先说问题本质：语义相关性不等于事实支持，向量检索只会匹配相似文本，容易丢失否定、前置约束条件；
讲文档处理：合同文档不能固定长度切片，按条款切，保留完整上下文、例外、附件；
召回链路：初召回 + 重排，对条款做极性（允许 / 禁止 / 条件）识别；
输出层：强制引用原文证据，结论可回溯条款；
兜底：证据不足的时候拒绝生成确定答案，交给人工处理。

实际考察：不是考察 embedding、向量库、top‑k 这些基础概念；考察候选人是否理解语义相关性 ≠ 事实支持，有没有处理过否定词、条件约束、证据边界的真实合同知识库项目经验。

二、完整三步工程解决方案（每一步全部细节 + 案例）
第一步：文档切片（入库阶段，防止否定词、例外条件被切分丢失）
错误切片方式：固定长度硬切（按字符数切割）
典型合同句式案例：除非出现重大质量缺陷，否则不得退款
如果切片只截取后半句 “不得退款”：系统会认为任何情况都不能退，回答过严；
如果切片只截取前半句 “除非出现重大质量缺陷”：系统会误以为可以退款，回答过松；
两种情况都会丢失完整逻辑关系。
✅正确切片策略：
不要按固定字符长度切分；按照合同条款编号、标题、条款上下级关系做切片；
上下文组装的时候，必须一并带上：例外条款、定义条款、附件、补充协议，不能只拿孤立片段。
切片目标：保证每一个 chunk 保留完整规则 + 例外条件，不能把条件和否定结果拆到不同片段。
第二步：召回后重排 + 结构化极性判断（检索返回之后，生成答案之前）
初召回策略：可以放宽召回范围，把退款、解除合同、违约金、售后等语义近义片段全部捞出来，保证不漏材料。
重排的核心：不只用相似度打分，要判断片段是否可以直接回答用户当前问题，不能只看语义接近。
内部结构化判断（模型先做内部输出，不直接对外输出）：
强制模型输出内部字段：
是否允许退款
适用条件是什么
对应的证据是哪一条原文
实现手段：结构化输出或者业务规则校验。
关键目的：从机制上防止系统犯 “文本相关就等于业务支持” 的逻辑错误。
第三步：答案兜底校验（生成输出层，证据不足严禁脑补业务口径）
业务案例：知识库只有部分场景写明 “不得退款”，用户提问：培训还没开始能不能退，知识库没有覆盖这个场景。
❌错误做法：模型自己脑补业务规则，自信给出 “可以退 / 不能退” 确定结论；
✅正确做法：如实回复：目前命中文档仅说明某类情况下不得退款，未覆盖你询问的这个条件。
视频重要警告：线上系统真正危险的不是回答 “不知道”；而是证据不足时，模型自信编造业务口径。
专项评估用例，上线前必须单独测试四类场景：
1）否定条款；2）例外条款；3）多版本合同冲突；4）证据缺失场景。
三、容易被忽略的工程细节（全部原文要点）
1、查询改写 和 答案约束，两者必须分开
检索侧（查询改写）：用户问 “能不能退”，检索要扩展同义词集合：退款、解除合同、撤销订单、返还费用、违约金，保证把全部潜在相关证据找全。
生成侧（答案约束）：不能自动等价替换概念，禁止直接把 “解除合同” 等同于 “全额退款”。
检索负责找全；生成回答负责保守、严格依据原文做窄回答，两者逻辑分离，不能混在一起。
2、错误分类排查：不要盲目调大 top‑k
把 RAG 答错的问题分成 4 类，不同错误对应不同修复方案，不能一看到答错就直接加大 top‑k：
①完全没有召回目标证据；
②证据已经召回，但是排序靠后；
③证据排到前面，但大模型阅读理解误读原文；
④多条召回证据本身业务互相冲突。
明确坑点：单纯调大 top‑k，会召回更多语义相近、但是立场完全相反的条款，反而增加噪声，让模型更容易混乱，解决不了否定条款答错的根本问题。
