抖音视频《多智能体面试：执行器发现计划有误咋办》详细总结
视频围绕一道 Agent 开发高频面试题：执行 Agent 发现 Planner 生成的计划存在错误，是直接照做还是拒绝？展开，重点讲解这道题考察的真实工程能力，给出四层答题框架、业务案例、面试回答模板以及工程落地注意事项。
一、题目本质
表面问题：Planner（规划 Agent）与 Executor（执行 Agent）的分工协作。
真实考察点：计划服从关系、前提条件校验、异常反馈闭环。面试官不希望背诵名词概念，重点看候选人能否讲清楚：数据来源、状态确认逻辑、失败兜底策略、结果验证方式。
现实痛点：很多大模型线上故障，不是模型推理能力不足，而是检索、工具调用、上下文、权限、评测体系没有分层处理。
核心结论：Executor 既不能盲目服从计划，也不能私自替换高风险方案；要校验计划前置条件，校验失败就拒绝执行，把问题反馈给 Planner 做重新规划。
业务案例：Planner 下达删除旧索引的计划，但是 Executor 检测出新索引还没有预热完成。如果直接执行删除，就会直接引发线上事故。答题的时候可以引用这个案例，从问题本质→架构设计→故障的停止、排查、补救完整链条来讲，证明自己懂线上工程，不是只会做 Demo。
二、四层答题框架（面试作答核心）
1）执行契约：保障输入入口可靠
如果输入本身出错，后续模型能力再强，也是基于错误信息运算。
工程要求：对计划的字段、数据来源、版本、操作权限、执行时间完整记录，不能只靠大模型从自然语言文本中猜测信息。
常见踩坑：把 “信息相关” 当成 “证据充分”；把工具调用返回成功，等同于业务执行成功。
2）前提校验：保障流程可复现、可追责
不能只写抽象原则，需要明确校验字段、业务状态、阈值，支持操作回放；资金、合同、外发消息、删除资源等高风险操作，宁可多增加校验步骤，不能交给模型主观判断。
校验内容：工具是否可用、依赖资源是否就绪、权限是否满足、业务状态是否符合计划执行条件。
3）拒绝反馈：异常的闭环处理
Executor 拒绝不是简单一句 “无法执行”，要结构化输出哪里出错、约束是什么，回传给 Planner 触发重规划；Executor 禁止擅自替换高风险操作。如果反复规划失败，需要熔断，触发人工介入。
4）轨迹评测：异常路径的收敛与回归
不能只测试正常成功样本，必须针对坏路径做压测。
需要覆盖的 Bad Case：证据互相冲突、工具调用超时、权限不足、旧过期数据、格式正确但业务语义错误、用户中途取消任务。
目的：异常场景下系统可以及时停下，暴露报错原因；把故障案例回流评测集，防止同类 bug 再次上线。
三、面试加分要点
可追踪证据：所有关键判断，必须留下可追溯证据。
高危动作管控：所有修改外部真实状态的动作，需要权限分级、密级确认、完整审计日志。
回归测试：发现的问题、修复方案，全部纳入回归评测集合。
验收标准：上线验收不能只看单次演示成功，必须校验异常 case 全部被拦截、可回放修复。
四、面试参考回答模板
我会把问题拆分为执行契约、前提校验、拒绝反馈、轨迹评测四层。首先保证输入数据和证据可信，再管控执行路径，最后依靠评测、监控、回放机制保证系统稳定。Executor 服从经过校验的计划；一旦计划违反权限、业务状态、安全边界，则拒绝执行，结构化反馈问题给 Planner 重规划；多次失败就熔断请求人工。所有高危操作留审计日志，故障案例回流评测集。
五、视频核心工程思想
大模型能处理正常任务只是基础；真正的工程能力体现在系统不确定的时候，可以及时熔断、排查问题、兜底降级。执行契约和反馈不是单点技巧，是一套 “设计 - 执行 - 校验 - 复盘” 完整闭环。

二、四层完整架构作答框架（执行契约｜前提校验｜拒绝反馈｜轨迹评测）
原文表述：前两层保证正常路径稳定运行；后两层保证异常路径可以收敛闭环。
第一层：执行契约 —— 解决入口输入是否可靠
核心观点：如果输入入口本身就错了，后续模型再强，也是基于错误信息运算。
工程落地要求：
计划不能只是一段自然语言，必须完整记录：字段、数据来源、版本号、操作权限、执行时间；不能依靠大模型从自然语言文本里面猜测信息。
工程高频踩坑（两个明确坑点）
坑 1：把 “信息具备相关性” 直接当成 “充分证据”。
坑 2：把 “工具调用返回成功” 等同于 “业务执行成功”。
第二层：前提校验 —— 保障流程可复现、可追责
作用：让系统从 “看似正确的模型回答” 转变为一套可复现、可追责的业务流程。
答题不能只讲抽象原则，答题内容必须补充：具体校验字段、业务状态、阈值域值、支持回放、必要人工确认。
高风险操作范围：合同处理、资金操作、消息外发、资源删除。
风险原则：高风险场景下，宁可多增加一步校验，也绝不允许模型凭主观感觉继续往下执行。
校验内容：依赖资源就绪状态、工具可用性、权限匹配、业务状态是否满足计划执行条件。
第三层：拒绝反馈（视频原文没有展开大段，但给出行为约束）
Executor 拒绝不等于直接抛弃任务，禁止静默跳过步骤；
禁止 Executor 自己擅自替换高风险业务方案；
需要结构化输出报错信息：明确哪一步出错、违反了什么约束条件；
将错误信息回传给 Planner，触发重规划流程；
如果多次重规划依旧失败，系统要熔断，升级到人工介入兜底。
