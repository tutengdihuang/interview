该视频面向面试场景，讲解RAG 和 LLM Wiki 的异同、底层定位、优缺点、业务选型，解决很多开发者容易混淆两者的问题，同时应对面试官的场景追问。
一、引入问题
很多人误以为 RAG 和 LLM Wiki 差不多，都是把外部知识交给大模型参考回答，底层都是 “检索 + 生成” 流程；但面试经常会追问二者区别、分别适用什么业务场景，不少开发者在此处答不上来。
二、分别解释两个概念
RAG（检索增强生成）
核心逻辑：先检索，后生成。用户提问，系统去外部知识库检索匹配文本片段，把检索到的材料拼入提示词，交给大模型生成答案。文档不会修改、固化到大模型权重，每次请求时实时检索使用。
LLM Wiki
是 Agent 框架自带的轻量知识库组件。同样做文档切片、向量化存入向量数据库；用户提问时检索相关片段，拼入提示词给大模型生成回答。
表面上看两者执行流程几乎一模一样，但产品定位、可控能力差异巨大。
三、核心本质差异
1. 定位与可自定义程度
LLM Wiki：开箱即用的封装组件
整套链路高度封装，切片、召回过滤、重排全部使用默认参数，开发者可调空间很小。
适合：文档数量少、业务简单、提问模式固定；优点是搭建快、上手门槛极低。
完整 RAG：一整套检索增强链路，不是单一工具
完整链路包含：文档解析、切片规划、向量召回、多路检索、重排、过滤、提示词构建、答案校验。
每一个环节都可以自主修改调优，支持多轮检索、过滤噪声内容，可以应对复杂多变的用户提问；海量文档、跨文档信息融合场景，靠完整 RAG 才能保障回答质量。
通俗举例
几十份产品手册，只做简单问答 → 直接 LLM Wiki，上传文档即可使用。
上万份业务资料，用户问题复杂，需要融合多篇文档、剔除错误素材 → LLM Wiki 扛不住，必须搭建完整 RAG 链路。
四、面试官高频追问：能不能所有场景都用 LLM Wiki？
视频给出结论：不推荐全部场景使用。
LLM Wiki 内部逻辑被封装，当文档多、内容混杂，容易召回大量无关的文本片段；
开发者没办法手动干预过滤，无效内容塞进提示词，会消耗大量 token，还会误导大模型，产生错误回答；
它适合快速验证想法、做轻量 Demo；进入正式复杂业务，固化逻辑很难优化迭代。
五、提示词处理逻辑差异
LLM Wiki：固定模板，直接把检索到的内容塞到 prompt，几乎不做二次加工。
标准 RAG：支持自定义提示词，约束大模型如何使用检索素材；还可以做资料溯源，输出答案对应的文档来源。
六、二者从属关系：LLM Wiki 算不算 RAG？
LLM Wiki 是RAG 思想的轻量化子集实现，底层确实是检索 + 生成逻辑，但砍掉大量可调节环节；不等于完整 RAG，不能拿它替代正式业务的 RAG 系统。
七、四点面试总结（答题要点）
LLM Wiki 是开箱即用轻量问答组件，RAG 思路的简化版本，配置简单，自定义能力弱；适合小规模简单文档问答。
RAG 是完整检索增强链路，全环节可灵活调参，适合海量文档、复杂查询。
LLM Wiki ≠ RAG，只是 RAG 的子级，复杂业务不能直接用 LLM Wiki 替代完整 RAG。
选型策略：简单场景用 LLM Wiki 快速落地；文档量大、查询复杂，搭建完整 RAG 链路做可控优化。
面试讲清楚以上几点，可以体现自己不是只会调用现成组件，而是真正理解底层原理，不会什么需求都无脑使用 LLM Wiki。

面试高频问题：RAG 和 LLM Wiki 到底有什么区别？
很多开发者的误区：以为二者差不多，都是上传外部文档、检索内容交给大模型回答，底层都是 “检索 + 生成”，于是混为一谈。

【分别定义两个概念，视频第二个模块】
① RAG（检索增强生成）
基础流程：用户提问 → 系统去外部知识库检索匹配的文本片段 → 把检索片段拼进 prompt → 交给大模型生成答案
核心特点：文档不会修改、不会固化到大模型权重；每次请求的时候才实时检索、实时使用。
② 本视频语境下的 LLM Wiki（Agent 框架自带的轻量知识库组件，注意：不是 Karpathy 那个编译式 LLM Wiki，这个视频是面试简化组件版本）
基础流程：同样做文档切片、向量化存入向量库；用户提问，检索相关片段，拼入 prompt 给大模型生成回答
一句话铺垫：表面上执行流程几乎一模一样，但是封装程度、可调空间天差地别
【核心差异对比（视频重点，逐条）】
差异 1：定位、封装程度、自定义空间
LLM Wiki：开箱即用的封装好的组件
切片策略、召回过滤、重排逻辑全部写死，使用框架内置默认参数
开发者可修改、自定义、干预的空间很小
优势：搭建速度快、上手门槛极低
适配条件：文档数量少、业务简单、用户提问模式比较固定
RAG：一整套完整的检索增强链路，不是一个现成组件
完整链路清单（视频原文列出全部环节）：文档解析 → 切片规划 → 向量召回 → 多路检索 → 重排 → 过滤噪声 → 提示词构建 → 答案校验
每一个环节开发者都可以自主修改、调优
支持能力：多轮递进检索、主动过滤噪声、自定义召回逻辑
适配条件：用户问题复杂多变、海量文档、需要跨多篇文档融合信息、需要控制回答准确性
视频配套举例（视频原话例子，一字不差保留）
例子 A（适合 LLM Wiki）：只有几十份产品手册，只做简单的文档问答，上传文档就能跑，省事。
例子 B（必须完整 RAG）：上万份业务资料；用户提问五花八门；经常需要融合好几份文档里分散的信息；还需要主动剔除检索回来的错误、无关素材；这种场景 LLM Wiki 扛不住，必须自建完整 RAG 链路。
差异 2：Prompt 处理逻辑
LLM Wiki：固定模板，直接把检索拿到的片段塞进提示词，几乎不做二次加工、约束、校验
标准自建 RAG：可以自己写自定义提示词，明确约束大模型怎么使用检索素材；支持溯源，输出答案对应的原始文档来源
差异 3：可干预、可排查能力（隐含在视频追问环节）
LLM Wiki：黑盒。召回了什么、为什么召回、过滤规则是什么，开发者很难干预；召回噪声多的时候没有办法手动调优过滤策略
RAG：全链路白盒可观测，哪一步召回出错、哪一步切片不合理，都可以单独调试优化
【面试官高频追问：LLM Wiki 这么省事，所有场景全都用 LLM Wiki 行不行？（视频独立一节）】
视频给出明确结论：不推荐全部场景都用 LLM Wiki，列出三条原因：
文档一多、内容混杂的时候，LLM Wiki 默认逻辑很容易召回大量无关、噪声文本片段
开发者没有办法手动干预过滤逻辑；无效内容一股脑塞进上下文 prompt
两个直接负面后果：①消耗大量 token，成本变高；②噪声内容误导大模型，产生幻觉、错误回答
它的合理定位：适合快速验证想法、快速搭 Demo 原型；一旦进入正式、复杂的生产业务，固化的内置逻辑很难迭代优化
【从属关系结论：LLM Wiki 算不算 RAG？（视频单独一个要点）】
视频结论原文：
LLM Wiki 属于 RAG 思想的轻量化子集实现，底层确实是检索 + 生成的思路；
但是：LLM Wiki ≠ 完整 RAG，不能拿 LLM Wiki 替代正式业务里的完整 RAG 系统
【视频结尾：面试 4 条背诵总结（视频直接给的面试答题要点，全部 4 条）】
LLM Wiki 是开箱即用的轻量问答组件，属于 RAG 思路的简化版本，配置简单，自定义能力弱；适合小规模、简单文档问答场景。
RAG 是一整套完整检索增强链路，全环节可以灵活调参、自主控制，适合海量文档、复杂查询、跨文档信息融合场景。
LLM Wiki 只是 RAG 的子集，复杂生产业务，不能直接用 LLM Wiki 替代完整 RAG。
选型策略：简单 Demo、少量文档、固定提问模式 → LLM Wiki 快速落地；文档量大、查询复杂、对答案准确性可控性要求高 → 搭建完整 RAG 链路做精细化优化。
