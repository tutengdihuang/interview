视频完整内容总结
视频是面向程序员 / Agent 开发的面试讲解，核心面试题：MCP Tasks 和长连接（工具调用一直挂住等待）有什么本质区别，指出只回答 “异步” 是很浅的答案，题目真正考察长任务的可靠性设计。
一、两种方案核心差异
长连接（一直挂住调用等待）
任务状态完全依附网络连接本身。一旦客户端断网、进程重启、网关超时，任务状态直接丢失，无法找回任务执行情况。形象概括：长连接是 “我替你等着结果”，任务和连接生命周期绑定在一起。
MCP Tasks
核心不是单纯异步等待，而是把执行过程变成带 taskId 的持久状态机。概括：先登记一个可恢复任务，客户端拿凭证后续查询结果。任务状态持久保存在服务端，和连接解绑；就算断线、换机器、刷新页面，重连之后凭任务 ID 还能继续追踪任务进度、拿结果，适合批处理、构建、审批这类耗时任务。
关键区分：受理成功 ≠ 执行成功。创建任务返回句柄，只代表任务被接收，不等于业务执行完成；任务拥有多种终态：working（运行中）、completed（完成）、failed（失败）、cancelled（取消），同时保存错误信息、结果摘要。
二、MCP Tasks 完整工作流程
能力协商：客户端、服务端要互相声明支持 tasks 扩展，没有协商通过，不能擅自返回任务句柄。
任务创建：发起长耗时工具调用，服务端不阻塞等待，立刻返回任务句柄（taskId），给出建议轮询间隔。
客户端轮询：客户端按间隔拿着 taskId 查询任务状态。
获取结果：等到任务抵达终态，再读取最终结果。
断线恢复：网络断开后，重连依旧可以用 taskId 查询状态，不受连接中断影响。
三、工程上必须考虑的设计要点（面试加分项）
TTL 任务有效期：任务句柄不能永久生效，设置过期时间。任务过期标记为expired，不再返回旧结果，业务侧选择重新创建任务或者人工介入。
幂等设计：设置业务幂等键，防止用户重复点击，重复触发多个相同任务。
取消语义：取消不是直接杀死进程；很多外部作业是合作式取消，会存在 “已经发起取消请求，但底层还在收尾” 的中间过渡状态。
权限校验：不能拿到 taskId 就可以随意读取任务，要校验用户、租户身份，防止越权访问。
轮询的坑：查询不到任务，不一定是要立刻重试执行；有可能是网络异常，也可能是任务 TTL 过期，不能无脑重试写操作；轮询要做退避策略，服务端限制查询频率。
四、面试标准回答模板（视频给出）
短请求直接返回结果；长耗时请求返回任务句柄。服务端持久化保存任务状态，客户端按协议轮询查询；使用幂等键防止重复创建任务，TTL 管理任务生命周期，权限校验保护任务数据；严格区分请求受理成功和业务执行成功。MCP Tasks 价值就是长任务与连接生命周期解耦，客户端断线、重启依旧可以追踪任务进度。
五、面试官高频追问以及答题思路
问：为什么不直接用长连接？
答：长连接受网关超时、客户端进程、网络抖动影响；MCP Tasks 基于持久状态机，支持断线恢复、轮询、可控过期，可靠性更强。
问：任务过期了怎么办？
答：任务配置 TTL，过期标记 expired，不再返回旧任务结果，业务根据场景选择重新创建任务或者转人工处理。
问：轮询要注意什么？
答：客户端做轮询退避，服务端限制查询频率；获取结果时再次校验用户 / 租户权限；查不到任务不要直接重跑业务逻辑，区分网络问题和任务过期两种情况。
六、视频小结

一、视频开篇：面试原题与高频错误回答
面试原题：MCP Tasks 和让一次工具调用一直挂着（长连接阻塞等待）有什么本质区别？
面试大坑（绝大多数人的错误回答）：只简单回答 “就是异步”，到此结束。
视频核心判断：只回答 “异步” 会丢分；这道题表面考协议对比，本质考察长任务可靠性设计。
视频总论点：MCP Tasks 的价值不是把等待时间拉长，而是把长任务执行过程变成带任务 ID 的持久状态机，任务生命周期和网络连接生命周期解耦。
两句形象比喻（视频原文）
长连接（挂住等待）：“我替你等着结果”，任务状态绑定当前这一条网络连接。
MCP Tasks：“我先登记一个可恢复的任务，你之后拿凭证查询结果”。
二、长连接（一直挂住工具调用）全部缺点（视频原文）
任务状态完全依附当前这一条网络连接。
触发状态丢失的 3 种场景：
客户端断网；
客户端进程重启；
网关超时断开连接。
一旦发生以上情况：任务执行状态、中间进度、最终结果全部很难找回，客户端分不清服务端任务还在跑，还是已经失败。
底层本质：任务存活 = 连接存活；连接没了，任务上下文就丢了。
三、MCP Tasks 核心概念、协议职责、业务案例
核心概念：带 taskId（任务句柄）的持久状态机；任务状态保存在服务端持久存储，和网络连接完全解绑。
协议必须定义 4 套操作，不能靠客户端自己记忆请求：任务创建、状态查询、结果获取、任务取消。
视频举例业务案例：代码构建任务
场景：调用工具触发代码构建（耗时较长）
1）服务端不会阻塞等待构建结束，立刻返回任务句柄 taskId；初始状态为 working（执行中）；同时返回建议轮询间隔。
2）客户端拿着 taskId，按建议间隔轮询查询任务状态。
3）任务走到终态之后，客户端再获取最终结果。
4）中途发生断网，客户端重新建立连接，仅凭 taskId 就可以继续查询任务状态，不需要重新发起构建请求。
重要概念区分：受理成功 ≠ 执行成功（视频重点强调）
创建任务拿到句柄，代表请求被服务端受理成功；不等于业务执行成功。
以代码构建举例：拿到 taskId ≠ 代码构建通过。
MCP Tasks 定义的任务状态集合（视频原文）
working：运行中
completed：执行成功完成
failed：执行失败
cancelled：已取消
要求：每个任务需要保存错误信息、结果摘要。
协议能力协商硬性规则（视频原文结论）
客户端、服务端双方都要声明自己支持 tasks 任务能力扩展；
工具本身也要声明是否支持任务化调用；
如果没有声明支持任务能力，服务端不能自作主张返回任务句柄。
MCP Tasks 适合业务场景：批处理、审批、构建类长耗时任务；支持客户端换机器、断线重连、刷新页面之后继续追踪任务。
四、工程落地必须实现 4 大模块：TTL、幂等、权限、取消语义（完整原文细节）
1）TTL（任务生命周期过期控制）
任务句柄不能永久有效，必须设置 TTL 有效期。
任务到期之后标记状态为 expired。
过期之后不能继续返回旧任务结果。
业务侧二选一处理逻辑：重新创建任务 / 转人工介入处理。
2）幂等设计
问题场景：用户界面重复点击，触发两次相同请求，会启动两份完全一样的构建任务。
解决方案：请求携带业务幂等键。
作用：重复提交相同业务请求，不会重复生成任务。
3）权限校验
风险：如果只靠 taskId 访问任务，任何人拿到 taskID 就可以读取任务结果，发生越权。
要求：查询任务、获取结果的时候，必须校验用户身份、租户身份，做访问控制。
4）取消语义（合作式取消，视频重点坑点）
误区：很多人以为调用取消接口，进程立刻杀死结束。
视频结论：大部分外部作业，只能做合作式取消，不能瞬间杀死进程。
状态机必须要有过渡状态：已经收到取消请求，但是底层业务还在收尾处理。
不能调用取消就直接置为 cancelled 终态，要体现这个中间过渡阶段。
五、客户端轮询的致命常见错误（视频明确警告）
最常见错误：把轮询接口当成万能重试。
客户端查询找不到任务，存在两种可能性，不能混为一谈：
情况 A：临时网络异常；
情况 B：任务 TTL 过期，任务已经销毁。
禁止行为：查不到任务直接重新执行业务写操作（直接重跑构建，造成重复任务）。
轮询配套工程要求：
客户端轮询要做退避策略；
服务端需要限制客户端查询频率；
哪怕轮询拿到任务结果，返回结果阶段，再次校验用户、租户权限。
六、视频给出的面试完整口述标准答案（完整原文，一字不漏）
短请求直接返回结果；长请求返回任务句柄；服务端持久化状态，客户端按协议查询；用幂等键防重复，用 TTL 控制生命周期，用权限校验保护结果，最后把业务完成和请求受理严格分开。这样回答说明你理解的是可靠执行，不只是把 HTTP 改成异步。
MCP Tasks 的价值在于把长任务从连接生命周期里解耦出来。只要任务还有有效状态，客户端换机器、断线重连，重新打开页面，都能继续追踪。这才是批处理、审批和构建任务真正需要的异步能力。
