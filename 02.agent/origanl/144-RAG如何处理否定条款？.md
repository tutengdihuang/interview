视频详细内容总结
这是一道大厂 AI / 大模型方向面试题讲解视频，主题：合同审查场景下，RAG 如何处理 “不允许、不支持、除外” 这类否定条款，避免把禁止条件答反。视频不只讲识别否定词，完整讲解业务痛点、常见坑、工程闭环方案、面试答题思路、系统兜底、上线评测与回归方案。
一、题目本质，不是简单识别否定词
题目表面考否定语义识别，实际考察 RAG 能不能读懂规则的完整约束：“不得退款≠全部场景都不得退款”。
一份否定条款，要同时解析 4 个要素：否定范围、例外条件、适用主体、生效时间。
举例：主合同写禁止退款，但售后服务政策规定质量问题可以退款；如果 RAG 只抓到 “禁止退款” 或者只抓到 “可以退款”，忽略例外，就会答反。
二、核心业务坑点
向量相似度只抓关键词，忽略修饰限定词。只命中 “退款” 关键词，忽略除非、但仅限于、除外、不、仅这类范围、转折、否定修饰词，造成断章取义。
只输出一句结论，答案没有绑定原文证据，无法核验对错。
出问题直接让大模型重新猜一遍，不去定位到底是切片、召回、重排还是生成环节出错。
故障排查正确思路：保留输入、模型版本、中间全部中间结果，定位第一个出错节点，再选择调参重试、降级，而不是盲目重试大模型。
三、完整工程实现闭环：入库、查询分离治理
1）入库阶段（文档处理）
还原文档结构：恢复标题、条款、表格、附件之间的关联关系，不要粗暴按 token 一刀切切片。
给每一个文本片段打上丰富元数据：文档 ID、页码、版本号、生效时间、适用组织、权限标签。把规则的附加信息固化在元数据，不全部依赖向量语义。
2）查询阶段（检索链路）
用户问题拆解：把问题拆分为主体、动作、条件、时间几个要素。
先做元数据硬过滤，再做关键词 + 向量混合召回。避免纯向量相似度淹没否定词、编号、日期这类关键信息；业务口语、别名做单独改写处理。
3）召回之后：证据充分性校验
召回回来很多片段不等于就可以回答问题，必须校验：
检查召回内容是否覆盖用户问题全部条件。
如果多条证据互相冲突：优先对比文档权威等级、版本、适用范围；
冲突无法裁决、证据不足时，不能强行输出答案，选择拒答或者向用户追问信息。
4）答案输出层
输出的每一条结论，必须逐条绑定原文位置作为引用依据，做到可溯源。
四、评测指标怎么设计（面试重点）
不能只看召回率 recall，需要分开评测多个维度：
切片完整性、召回、重排、命中情况、引用准确率、忠实度（是否篡改原文语义）。
面试提醒：不要只说搭建向量库，要完整讲：文档解析→元数据过滤→召回→证据校验→引用输出完整链路。
五、面试答题方法论
1. 通用答题框架（评论区给到的四步答题模板）
①给出业务判断；②讲核心链路方案；③分析失败路径与边界；④给出评测指标和系统兜底策略。
2. 原理类 vs 应用类题目答题区别
应用题（例如合同 RAG）：固定模型配置、输入长度、数据版本，做对照实验，看修改前后正确性、延迟、token 成本变化；检查系统是否具备追溯、演练；证据不足时具备追问 / 停止回答的兜底。
原理题：要讲阶段、耗时、任务特征，不要只背诵定义。
3. 面试官追问方案取舍如何作答
先讲业务目标指标与约束条件；
解释选择这套方案的原因；
强调优化需要对照实验：固定输入与版本，只改变单一变量，对比正确性、延迟、成本、风险；
明确系统降级边界：证据不足、状态不明、指标越界时，要有追问、降级、回退、人工接管逻辑，说明什么场景系统不能自动运行。
六、上线之后运维保障
将关键业务指标和版本做时间线对齐；出现异常可以区分根因：是输入数据分布变化、配置改动、模型升级还是外部依赖故障。
修复完一类问题，把该案例加入回归测试集；同时检查相邻业务场景，避免修复 A 问题，导致 B 场景效果退化。

题目原文：RAG 在合同审查场景，遇到 “不允许、不支持、除外” 这类否定条款，如何避免把禁止条件答反？
视频核心总纲：不要只做简单否定词识别；“不得退款” 不等于全部场景不得退款，必须同时解析 4 要素：否定范围、例外条件、适用主体、生效时间。
一、题目本质（面试官真正考察的东西，不是表面问题）
表面问题：怎么识别否定词、怎么处理 “不、禁止、除外”
底层考察：约束语义的条件绑定能力；RAG 能不能读懂一条规则是【在什么前提下、对谁、什么时间、有什么例外】才生效，而不是孤立抓关键词
核心结论：否定是依附于条件的修饰关系，不是一个独立极性标签；否定词必须绑定它修饰的对象，不能单独提取
视频配套核心示例（反复用的退款案例）
示例原文：主合同条款约定【本合同项下商品不得退款】；配套售后服务补充规则【因产品质量缺陷导致故障的情形除外，可以办理退款】
错误理解：只抓到 “不得退款”→全部情况不能退款；或者只抓到 “可以退款”→都能退款
正确理解：默认禁止退款，存在明确例外；回答必须带上例外条件
视频强调：例子必须同时写清楚【输入条件 + 可核验依据】，不能只输出一句结论
二、RAG 处理否定条款的四大典型坑点（逐条）
坑 1：向量相似度只匹配核心名词，忽略修饰限定词
现象：向量召回只看 “退款” 这个关键词的语义相似度；对除非、但是、仅限于、除外、不得、禁止这类边界修饰词不敏感
后果：把局部片段直接当成完整规则，断章取义，极性反转（禁止变允许）
坑 2：输出只给一句结论，答案不绑定原文证据
现象：模型直接输出 “不能退款”/“可以退款”，不标注来自哪一条、哪一页、哪个版本合同
后果：业务方、法务无法核验对错；幻觉、答反之后无法定位依据，审计失效
坑 3：故障排查方式错误：出错直接让大模型重新生成一遍
视频明确反对这个做法
正确排查前提：链路全埋点，完整保留输入、模型版本、配置、所有中间环节结果
排查顺序：定位第一个出现错误的节点（切片？召回？重排？prompt 组装？生成？）；再选择调参、重试、降级；而不是无脑让模型重猜
坑 4：切片粗暴，按固定 token 长度一刀切，切断否定和它的条件、例外之间的关联
现象：一条完整的带例外的条款，被切到两个不同 chunk；一个 chunk 只保留 “不得退款”，另一个 chunk 单独放例外 “质量问题除外”
后果：召回时只命中其中一半，天然丢失约束关系
三、工程方案核心原则：入库阶段、查询阶段分离治理（离线 / 在线分开设计）
（A）入库阶段（离线文档处理，建库环节）
要点 1：文档还原优先，不要上来就切块
恢复文档原生结构：标题层级、条款编号、表格、附件、补充协议之间的关联关系
合同是结构化文档，条款、补充协议、附件之间有依赖，不能当成纯自由文本
要点 2：切片策略（合同场景专用，区别通用 RAG）
不使用固定 token 硬切；优先以完整条款、小节、编号段落作为切分单元
保证：否定词、它修饰的主体、例外从句，留在同一个片段窗口内
结论：合同 RAG 切片第一目标 ——保证约束关系不被切断，而不是追求 chunk 长度均匀
要点 3：给每一个文本片段强制打上全套元数据（元数据是硬过滤的基础，不放到向量语义里）
元数据清单：文档 ID、页码、条款编号、文档版本号、生效时间、失效时间、适用组织 / 适用主体、权限标签、文档优先级（主合同 > 补充协议 > 通知，优先级用于冲突裁决）
视频结论：关键规则信息固化在元数据，不全靠向量语义去猜
（B）查询阶段（在线用户提问，检索链路）
要点 1：用户 Query 结构化拆解
把用户问题拆解成 4 个要素，和入库抽取四要素对齐：主体、动作、约束条件、生效时间
示例 query：我买的这个商品能不能退款？
拆解：主体 = 我方采购方；动作 = 退款；条件 = 本次交易、当前版本合同；时间 = 当前生效周期
要点 2：检索顺序：先元数据硬过滤 → 再关键词 + 向量混合召回
先用元数据做筛选：过滤掉过期版本、不适用于该主体、不在生效周期内的文档片段
再做多路召回：关键词召回（专门捞否定词、除外、除非这类标记词）+ 向量召回
视频结论：纯向量召回不适合高风险合规场景；关键词召回用来兜底抓取边界修饰词
要点 3：召回后：证据充分性校验（这一步是防止答反的核心关卡，很多 RAG 直接跳过）
拿到召回片段之后，不能直接丢进 prompt 生成，必须做 3 项校验：
① 覆盖性校验：召回的全部证据，能不能覆盖用户 query 拆解出来的全部条件？缺条件 = 证据不足
② 极性 + 关系标注：对每一条召回片段做标注：这条是【允许、禁止、有条件允许、例外、仅流程说明、无关】
③ 冲突裁决：多条证据结论矛盾的时候
裁决规则：优先看文档权威等级、版本新旧、适用范围
无法裁决、证据互相打架：禁止强行输出结论，兜底策略：拒答，或者向用户追问补充信息
要点 4：答案生成层约束
两条硬性规则：
每一条结论，逐条绑定原文引用（文档 ID、页码、条款号），输出可溯源
Prompt 必须约束：结论只能基于已经校验通过的证据；证据不足直接说明信息不足，禁止模型凭常识补规则
四、评测体系（面试高频追问，不能只说召回率 recall）
视频明确：合同合规 RAG，评测指标必须拆成链路分环节评测，而不是只看最终答案对不对
分环节评测清单：
切片完整性指标：约束关系、否定 - 例外配对有没有被切散
召回指标：相关片段召回率、无关片段召回（噪声）
重排指标：正确证据是否排在高位
引用准确率：引用的原文，是否真的支撑给出的结论，有没有乱绑依据
忠实度指标：有没有篡改原文语义、颠倒否定极性（这个是本场景最重要指标）
视频结论：普通问答 RAG 看重召回率；合同 / 法务等高风险 RAG，忠实度、引用正确性优先级高于召回率
五、面试答题方法论（视频给的标准化答题框架，评论区配套模板）
框架：4 步标准回答模板（面试直接用）
① 先给出业务判断，点明问题本质（不是识别否定词，是条件约束绑定）
② 讲完整工程链路方案（入库治理 → 查询拆解 → 召回 + 元数据过滤 → 证据校验 → 带引用生成）
③ 梳理失败路径、边界 case、风险点
④ 给出评测指标 + 系统兜底降级策略
两类面试题的回答区分（原理题 vs 应用题）
应用题（本题属于应用题：合同 RAG 否定条款）
实验方法：固定模型版本、输入、上下文长度、知识库版本，做对照实验
观测维度：正确性、延迟、token 成本、幻觉率
必须讲：可追溯演练能力；证据不足时的停止 / 追问兜底逻辑
原理题
答题思路：按阶段讲、讲耗时、讲任务特征；不要单纯背诵定义
面试官追问【方案取舍、trade-off】的回答套路（视频原话）
先讲业务目标、指标约束、成本约束
解释为什么选这套方案，不选其他方案
优化必须靠单一变量对照实验：只改一个变量，固定其余所有条件，对比正确性、延迟、成本、风险
明确降级边界：什么场景系统不能自动回答（证据不足、冲突无法判定、版本不明确）；对应的兜底：人工接管、追问用户、拒绝输出结论
六、上线之后的运维、回归保障要点
要点 1：指标、版本、数据变更时间线对齐
出问题区分根因：是用户查询分布变了、文档数据更新、配置改动、模型升级、外部依赖故障，哪一环带来的错误
要点 2：回归测试集建设
每修复一类否定条款答错案例，把这个 case 加入回归测试集
回归验证要求：修复 A 问题时，必须检查相邻、同类场景，防止修复一处 bug，把其他场景做坏（退化）
七、视频最终总结结论（收尾原话）
可靠的合同 RAG，不是简单抓到否定关键词；而是证明这条结论是在哪些约束条件、哪些例外之下才成立
面试最大避坑点：千万不要只回答 “加否定词识别 / 否定词正则”，这是浅层方案；面试官要听的是：否定范围、例外、适用主体、生效时间抽取 + 完整证据校验、引用溯源整套闭环
底层理念：法律合同的规则，都是条件命题；RAG 不能脱离条件，单独输出布尔式的 “可以 / 不可以”
