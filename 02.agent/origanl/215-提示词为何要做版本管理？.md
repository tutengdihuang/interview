一、错误的现实情况：很多团队调提示词很随意
不少团队把 Prompt 当成普通文案，随手修改：今天改一条约束、明天增加示例、后天调整输出格式。
短期：看起来是优化模型回答效果。
长期隐患：线上模型输出结果发生变化时，没人能说清是什么改动导致；没有版本记录，排查线上问题只能靠猜测，完全不可控。
核心认知：生产环境下提示词不是普通文本，是会直接改变系统行为的配置代码。
二、提示词版本管理的核心目的
记录版本的总体目标：让每一次大模型输出，可以被解释、复现、对比。
四大核心价值（面试得分要点，不止回滚）：
复现输出：能够复现过去某一次模型的输入与回答结果。
定位排查问题：线上答案异常时，追溯是哪次 Prompt 改动带来的问题。
灰度发布：不直接全量上线新版本提示词，小流量验证风险。
效果对比：横向对比不同提示词版本在业务场景中的好坏差异。
三、版本记录里，至少要保存三类关键信息
只存提示词模板还不够，必须完整留存下面三类内容，否则无法真实复现模型当时接收的输入：
系统提示词、提示词模板原文。
变量填充完成后的最终 Prompt：模板相同，但传入业务变量不一样，模型行为也会不一样，只存模板无法还原真实输入。
该模板配套信息：使用的模型、调用工具列表、输出结果解析规则。
四、提示词变更的上线规范：要像代码变更一样灰度
禁止修改完提示词直接全量上线。
先分配一小部分流量跑新版本 Prompt。
观测业务指标：成功率、用户改写率、人工介入率、异常输出占比。
警惕风险：新版本整体平均指标变好，但部分关键业务场景效果偷偷变差，这种情况不能直接替换旧版本。大模型系统很容易出现这类隐性劣化问题。
五、重要工程实践：提示词版本要绑定评测结果
将每一个 Prompt 版本和对应的评测结果绑定沉淀。举例子：v12 版本，客服场景回答更简洁，但工单分类场景会遗漏边界条件。
如果评测信息不记录留存，后续团队再次修改提示词，会重复踩相同的坑。
有回放能力的系统，可以拿同一批历史用户请求，分别跑不同版本 Prompt，直观看到不同版本输出差异。
这套做法，把 “凭感觉调提示词” 的玄学模式，转变成可量化、可追溯的工程迭代。
六、面试标准答题话术（视频直接给出）
提示词版本管理不是为了存档好看，而是为了复现输出、定位问题、灰度发布和做效果对比。生产系统要保存模板、变量填充后的最终 prompt、模型配置和解析规则，让每次回答都有可追溯的版本链路。
