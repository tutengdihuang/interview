抖音视频《RAG 面试题：三份合同数字冲突信哪个？》详细总结
视频围绕一道大模型 RAG 高频面试题：三份合同同一业务数字不一致，RAG 应该采信哪一份？，重点指出：这道题不是考概念背诵，考察的是RAG 工程落地能力，核心是证据权威、字段口径、版本仲裁，看候选人是否懂可上线、可追踪、有兜底的真实业务系统，而不是 Demo 效果。
举例场景：主合同写 100 万，补充协议写 98 万，验收单写 95 万。用户问 “合同约定金额” 和 “实际验收金额” 需要给出完全不一样的处理逻辑。RAG 不应该自己主观选定某一个数字，要结合文档类型、签署时间、生效范围、字段口径、用户提问意图综合裁决。
核心四层架构解决方案
第一层：元数据治理（管好数据入口）
如果入库的原始资料本身不可靠，模型能力再强也只会基于错误材料输出结果。
文档入库阶段就要记录完整元数据：字段含义、文档来源、版本号、签署 / 生效时间、权限、业务状态，不能指望大模型从自然语言文本里面猜版本、猜权威性。
避坑：不要把 “检索召回相关片段” 等同于充分证据；不要把接口调用成功等同于业务功能可用。
第二层：口径识别（让流程可复现、可追责）
区分用户到底想问什么业务口径，高风险场景（合同金额、资金、权限、删除操作）不能让模型凭感觉输出。
明确具体业务字段、文档状态、阈值条件，支持回放、人工确认流程。
不同文档对应不同口径：主合同代表约定金额；验收单代表实际执行金额；补充协议代表变更约定。用户问题意图不同，采信的文档源就不同。
第三层：冲突暴露（异常情况不要强行给出单一答案）
当多份文档数字互相冲突，系统无法自动判定谁对谁错的时候，禁止模型强行合成一个确定数字，要主动暴露冲突事实：
把各个文档里的数字、文档来源全部列出来，告诉用户存在数据冲突，提示需要人工确认口径，规避大模型幻觉风险。
正常业务路径保证稳定，遇到冲突、不确定就停下来，而不是硬输出一个结果。
第四层：回归评测（保障异常路径也可控收敛）
上线不能只测试标准理想样例，必须做坏路径边界压测，构造大量 Bad Case：
证据互相冲突、工具调用超时、用户变更业务口径、权限不足、命中过期旧文档、格式错误等。
评判工程质量，重点看系统遇到异常能不能识别、拦截、暴露问题原因。
所有问题案例回流到评测集，后续版本发布必须过这批测试用例，防止新版本重新踩同类坑。
面试加分要点
可追踪证据：所有关键业务判断，输出结果必须附带证据来源，能够溯源。
外部操作安全：凡是会修改外部系统状态的动作，要做权限校验、幂等处理、二次确认、操作审计。
闭环思想：数字冲突仲裁不是单点 Prompt 技巧，是完整闭环：文档设计→执行检索生成→校验输出→问题复盘。
面试答题参考模板
“我会把问题拆解为元数据治理、口径识别、冲突暴露、回归评测四层。首先在入库环节做好文档元数据，保证输入证据可信；其次识别用户业务口径，按文档权威、时间、生效范围做裁决；遇到无法判定的冲突，就直接暴露冲突信息，不强行输出结果；最后通过评测集、线上监控、问题回放来保障系统长期稳定运行。”
视频核心观点总结
Demo 里大模型答对正常问题只是基础；生产级系统真正的工程能力，是在信息不确定、证据冲突的时候懂得停止、兜底、上报，而不是强行给出确定答案。发现的所有异常案例，要沉淀进评测集和监控指标，作为后续版本发布的门槛，避免同类问题反复出现。

视频标题：RAG 面试题：三份合同数字冲突信哪个？
主讲：小哲讲 agent 项目 / 小哲讲大模型面试
开篇定调（视频第一句话）
面试官问题：同一个业务数字，在三份文档里面数值不一样，RAG 应该信哪一份？
❌ 绝大多数候选人错误回答：召回更多文档、按相似度最高选、取最新时间的文档、交给大模型自己判断投票。
✅ 视频核心结论：这道题根本不是考检索、不是考 chunk、不是考向量相似度，本质考察生产级 RAG 的证据仲裁、口径治理、风险兜底、可追溯闭环能力；面试官想看你懂上线业务系统，而不是只会做 Demo。
面试官真正想看你讲清楚四件事：数据来源怎么管、状态怎么校验、异常失败怎么兜底、输出结果怎么验证。
一、视频里固定业务例子（全程贯穿）
三份文档，同一个项目金额数字各不相同：
主合同：100 万（双方约定的原始合同金额）
补充协议：98 万（变更协议，对主合同做修订）
验收单：95 万（完工验收，实际履约确认金额）
视频重点强调：这三个数字本身没有谁天然对、谁天然错，区别只在于用户问的是什么口径
用户问：这份合同约定的金额是多少？→ 优先采信【主合同 + 补充协议】（约定口径）
用户问：项目验收实际结算金额是多少？→ 优先采信【验收单】（履约执行口径）
延伸同类单据举例：付款申请单、发票、采购单，各自对应不同口径，不能全部扔进同一个事实池让模型随便混着理解。
补充反面示例（视频顺带提）：采购合同含税价、商品表录入价、邮件临时优惠价，数值冲突，也是口径问题，不是简单谁新谁旧。
二、第一层：元数据治理（数据入库阶段，源头层）
视频原文要点
一句话定位：入口治理，如果入库原材料本身信息不全、标签缺失，后面模型再强，也只是在错误证据上推理。
入库时，不能只存文本 chunk，每一条事实 / 每一个数字，必须绑定完整元数据，元数据清单（视频全部列出）：
文档类型：主合同 / 补充协议 / 验收单 / 发票 / 附件
版本号
签署 / 生效时间戳
失效时间、是否作废、是否归档下线
审批状态（是否经过双方盖章、审批留痕）
权限标签（哪些角色可以查看这份文档）
业务字段口径标签：约定金额 / 验收金额 / 应付金额、币种、单位、是否含税
来源链路、页码、条款位置（用于溯源）
重点踩坑点（视频反复强调的第一个大坑）
❌ 误区：只要检索召回了相关片段，就等于拿到充分证据；只要模型接口调用成功，就代表业务功能是正确可用的。
✅ 纠正：向量相似度 ≠ 业务可信度；召回相关 ≠ 证据有效。
核心约束：不要指望大模型从纯自然语言文本里面，自己猜版本、猜文档效力、猜字段口径。模型做语义理解，业务仲裁规则必须提前外部定义、结构化标注。
三、第二层：口径识别 + 权威仲裁规则（检索后、生成前，判断层）
视频原文要点
先识别用户问题的业务意图、对应口径，再启用对应的权威排序规则，而不是一套规则通吃。
仲裁判断的 4 个核心维度（视频明确列出，按优先级）
① 文档类型权威层级（业务效力权重）
示例权重逻辑：盖章正式协议 > 验收单据 > 内部录入单据；发票（税务背书）> 采购单 > 手工录入验收单
② 生效时间（后签协议优先变更前面协议，但是前提：是同口径、同一事项的变更）
⚠️ 视频重点提醒：单纯 “时间新” 不是万能准则！很多候选人只答 “取最新”，直接扣分。新文档如果是别的口径、别的业务事项，不能覆盖旧文档。
③ 签署与审批状态：是否双方确认、盖章、线上审批闭环；草稿、未审批扫描件权威度极低
④ 适用范围：这份文档是针对整个项目，还是某一期、某个分项的局部约定
规则运行逻辑：
检索拿到候选片段之后，先做结构化字段提取，把冲突数字、对应元数据捞出来，走预定义业务规则做交叉校验，而不是把一堆原文丢给 LLM 自由选。
高风险场景边界（视频点名）：
资金金额、合同条款、权限变更、删除操作、对外发函，全部属于高风险场景；高风险场景，不允许模型自由发挥，必须有显式规则、可回放、人工确认通道。
四、第三层：冲突暴露机制（规则无法自动裁决时，兜底层，视频最核心的亮点）
视频原文要点
触发条件：多个来源数字冲突，并且现有元数据、业务规则不足以稳定判定哪一个是当前问题对应的标准答案
❌ 绝对禁止行为：
禁止大模型自行加权、取平均值、主观选一个数字输出
禁止隐藏冲突，只返回其中一个数字
禁止模型自己编造一个折中数字
视频原话：宁可暴露冲突、不给出确定结论，也不要输出一个看似通顺、实则幻觉的确定答案
✅ 标准输出范式（视频给的固定输出样例）
【提示：检测到多份文档金额存在冲突】
主合同：100 万
补充协议：98 万
验收单：95 万
文档来源、签署时间附在每一条后面
说明：当前信息无法自动判定你询问的口径，请你确认查询目标（是合同约定金额，还是验收结算金额），或者提交人工复核。
系统定位转变：此时 RAG 不再是自动给答案的回答机，变成证据披露 + 风险提示工具。
风险价值：既规避金额类强事实的幻觉，同时把差异主动交给业务人员发现，而不是埋坑。
五、第四层：回归评测 + 线上监控闭环（验收、持续迭代层）
视频原文要点
上线验收不能只测理想正向 Case（文档统一、数字一致、口径清晰）。
必须批量构造坏 Case、边界 Case 做压测（视频列出全部 bad case 清单）
多文档事实冲突、数字打架
文档超时失效、旧版本没有下线，新旧文档混在知识库
工具调用超时、检索召回异常
用户提问口径模糊、意图不明确
权限不足，只能看到部分文档，证据不全
OCR 识别错误、表格数字识别错乱
评测闭环流程：
① 所有线上遇到的冲突异常案例，全部沉淀进评测集
② 后续每一次版本更新、模型切换、检索参数改动，必须跑完整这套冲突回归用例
③ 配套线上监控：增加【冲突命中指标】，统计系统触发多少次冲突告警、多少次进入人工复核
④ 支持全链路回放：用户一问、召回列表、元数据、规则判断逻辑、最终输出，全部可回放审计，方便定位是标注问题、规则问题还是检索问题
视频一句话总结这一层的作用：正常路径靠规则稳定输出；异常不确定路径靠评测、监控、人工链路收敛风险。
六、视频单独列出的加分补充要点（面试加分项，前面四层之外）
证据溯源：所有关键事实输出，每一个数字必须附带来源引用（文档名称、版本、时间、页码），满足合规审计、法务溯源要求，不能只给光秃秃数字。
写操作 / 外部系统联动的安全约束：
如果 RAG 结果要驱动下游动作（发起付款、修改合同状态、权限变更），除冲突校验外，额外增加：权限校验、幂等控制、二次人工确认、完整操作审计日志。查询类问答可以松一点，写操作必须严格上锁。
对常见错误回答的逐一批判（视频专门用来避雷）
❶ “召回更多文档就能解决冲突”：召回再多，没有元数据和口径规则，冲突依然存在，只会增加矛盾证据
❷ “交给大模型自己判断哪个是对的”：LLM 会根据文本语气、token 多少主观选择，不是业务真实效力，高风险场景不可控
❸ “直接取时间最新的文档”：忽略口径、适用范围，属于片面简化规则，面试直接减分
❹ “设置相似度权重，选分数最高的 chunk”：向量相似度和业务法律效力无关，相似度高不代表事实正确
七、视频给出的完整面试口述模板（一字不差原文）
我会把这个问题拆成四层闭环来做。首先在入库阶段做好文档元数据治理，给每一份文档标记类型、版本、生效时间、审批状态、业务口径，保证证据在源头可识别；第二层识别用户的查询口径，按照文档权威层级、生效时间、适用范围、审批状态预先定义仲裁规则做判定；第三层当规则无法自动裁决冲突的时候，不强行输出单一结论，完整列出全部冲突证据和来源，提示用户确认口径或者流转人工复核；第四层把冲突、边界坏样本沉淀到评测集，配合线上监控、链路回放做持续回归，保证新版本不会反复踩同类坑。同时高风险资金类场景，全部保留证据溯源，联动写操作时增加二次确认和审计。
八、视频最终收尾核心结论
Demo 级 RAG，只追求正常场景答对；生产企业级 RAG 真正的工程能力，不在于什么问题都给出漂亮答案，而在于当证据不确定、事实互相冲突的时候，懂得停止、暴露风险、兜底上报，而不是硬编一个确定结果。整套方案不是单一 prompt 技巧，是从文档入库、检索仲裁、生成输出、异常复盘的完整治理闭环。
