视频详细内容总结
视频是一道 Agent 开发高频面试题讲解：任务执行中途用户修改目标，Agent 如何判断哪些旧步骤、旧中间结果需要作废。
案例场景：用户原本要求做竞品价格报告，任务做一半，用户取消价格分析，改为竞品用户口碑分析。如果直接沿用旧计划、旧工具输出，会造成结果持续跑偏。
核心观点
误区纠正：很多人认为 Agent 记忆越多越好；但工程实践中，目标发生变更，旧计划、中间结果、工具缓存、用户确认记录会变成污染源，不能全部保留，也不能全部清空从头跑。
这道面试题表面考察上下文记忆、任务重规划，本质考察 Agent 的状态失效管理、版本与依赖体系，是长任务 Agent 的核心工程能力。
核心思路：不是简单清空上下文，而是精确作废。给任务目标做版本化，所有中间产出标记依赖关系；目标变更后，让依赖旧目标的步骤失效，只保留对新目标依然有效的事实、资源。
完整处理三步流程
第一步：精准识别用户意图变更的类型，差异化处理
区分用户修改的是什么，不同改动处理逻辑不一样，不统一重置全部任务：
修改格式：例如输出从表格改成要点。原始数据全部保留，仅调整输出形式。
修改范围：例如分析范围从华东区扩大到全国。基础实体名单保留，需要重新查询、计算对应范围的数据。
改变任务本质：例如价格分析改为口碑分析。旧的整套计划、计算结果作废，只复用无关的基础实体信息（如竞品名单）。
第二步：建立任务依赖关系
每一个中间产物（表格、报告片段、工具返回、待执行动作），都记录自己的来源：依赖哪一个目标版本、哪条用户指令、哪个文件、哪一次工具调用。
示例：“竞品价格表” 强依赖旧目标，口碑分析任务不能复用；但 “竞品名单” 属于基础事实，可以继续复用。
通过依赖关系，Agent 自动区分：保留、重算、需要重新向用户确认三类内容。
第三步：重新规划之前执行状态清理
目标变更属于工作流状态机的版本切换，不只是增加一段 Prompt：
取消排队还没执行的旧动作（高危写操作必须优先取消，例如原计划给销售发送价格报告，目标修改后该发送动作直接作废）。
旧工具缓存降低权重，不再优先使用。
过去的用户确认记录全部失效，涉及高危操作需要用户重新确认。
面试可直接使用的回答模板
我会把目标、中间结果和待执行动作全部做版本化记录。用户修改目标后，首先判断改动的类型，再依据依赖关系将旧计划、旧结果标记失效；只保留和新目标不冲突的客观事实。写操作、用户确认类高危动作必须重新校验，以此规避旧上下文污染新任务的问题。
面试官继续追问时，可以补充业务案例
报表任务场景：旧版本生成的缓存数据表、待发送邮件全部标记旧版本产物；新任务只复用原始数据源、已经确认好的实体列表。既不浪费已经完成的有效工作，又避免错误中间结果流入新计划。
工程落地的上线门禁（拔高回答，体现项目实战经验）
输出失效清单：每次目标变更后输出清单，明确哪些继续生效、哪些需要重跑、哪些高危动作已经取消。
回归评测体系：调整 Prompt、模型、检索策略等改动，都使用同一批回归样本重跑；校验正确率、路径安全、引用质量、成本、延迟。
线上观测：抽样采集真实运行 Trace，将线上新出现的失败样本回灌评测集；评估标准看整体任务稳定性，不是看单次输出结果是否通顺好看。
视频最终结论
Agent 处理目标变更的能力，决定长任务执行质量。只会无脑追加聊天历史的 Agent 看似记忆力很强，很容易被过期旧计划带偏。工程化 Agent 需要做到三点：上下文带版本、状态具备依赖关系、待执行动作支持取消机制，才能安全承接用户中途变更需求的场景。

视频完整逐要点整理（全部口播要点、例子、结论，无省略）
视频标题：Agent 面试：任务做到一半用户改目标，怎么判断旧步骤要不要作废
主讲：小哲 AI 面试
开篇钩子（视频第一句）
面试官高频面试题：用户让 Agent 做竞品价格报告，任务执行中途，用户说不要价格分析了，改成竞品用户口碑分析。Agent 怎么判断哪些旧步骤、旧中间结果要作废？
开篇先点破大量面试者的错误回答：很多人只会说 “把最新用户指令放到 prompt 最后面”。主讲明确：这个方案只能解决极简单场景，根本解决不了这个问题。
一、本题考察本质（视频第一个核心结论）
这道题表面考察：多轮对话、意图识别、任务重规划。
本质考察：Agent 结构化状态管理、任务目标版本化、依赖失效 / 污染传播机制，属于长任务 Agent 工程化核心能力，不是 Prompt 技巧题。
主讲原话：很多人误以为 Agent 越强 = 记忆塞得越多；这是最大误区。记忆多不等于可靠，过期状态是污染源。
两个极端错误方案，视频逐个批判
方案 A：全部保留历史，直接追加新指令继续跑
问题：旧计划、旧计算结果、待执行动作、之前用户确认记录全部留在上下文里，模型会继续基于旧目标推理，结果持续跑偏、污染新任务。
例子：已经算出竞品价格表，继续拿去做口碑分析，输出混杂价格结论。
方案 B：用户一改需求，直接清空全部上下文，从头重新执行
问题：浪费已经完成的有效工作，很多客观事实、基础实体信息是新任务依然可用的，全部丢弃成本高、效率低。
核心总纲领（视频核心论断）：既不能全留，也不能全删；要做精确作废。
精确作废定义：给目标做版本号；所有中间产出、待执行动作标记依赖关系；目标变更时，只把依赖旧目标的节点标记失效，和新目标无冲突的客观事实保留复用。
二、第一步：分类识别用户意图变更类型（视频完整四类变更，附带配套案例）
主讲强调：不能把所有 “用户改话” 当成同一种变更，不同变更类型，失效策略完全不一样。
类型 1：仅修改输出格式（语义目标不变）
例子：原本要求输出竞品价格表格，用户改成要点文本；或者从 markdown 改成 PPT 大纲。
依赖判定规则：原始数据、采集结果、查询到的信息全部有效，不需要作废；只作废输出格式化步骤，不需要重跑工具。不需要重新规划调研动作，只调整最后渲染环节。
类型 2：修改范围 / 参数（目标内核不变，约束条件变更）
例子：原本分析华东竞品价格，改成全国竞品价格；原本分析 Q3，改成 Q3+Q4；原本按日聚合报表，改成按周聚合报表。
依赖判定规则：基础实体列表、数据源链接不变；但和范围、粒度、时间窗口强绑定的聚合计算、汇总结果全部作废，需要增量补查数据、重新聚合。上游原始日志、原始明细数据可以保留。
补充例子：口径从 GMV 改成净收入，属于参数变更，旧的汇总指标作废，原始明细保留。
类型 3：局部补充信息（目标不变，增加约束）
例子：继续做竞品价格报告，额外增加一条：只看上市 3 年以内的品牌。
依赖判定规则：主目标版本不变，不需要升级目标版本；只在筛选环节增加过滤条件，已经拿到的竞品列表做过滤，前面查询动作大部分复用。几乎不需要作废已有结果。
类型 4：替换任务本质（目标语义完全变更，目标版本升级）【视频主案例】
例子：原目标：竞品价格分析报告；用户中途改成：竞品用户口碑分析。
依赖判定规则：旧目标对应的整套计划、价格计算、价格图表、价格汇总结果全部标记失效；排队中待执行的副作用动作优先取消；仅保留和新旧目标都无关的客观基础事实（竞品名单、公司主体、官网链接这类基础实体信息）。
视频这里重点提醒一个坑：不能只用语义相似度打分判断要不要作废。
反例：日报改周报，语义相似度很高，但是聚合粒度不匹配，旧中间表完全不可用，语义打分方法会误判为可用，造成错误继承。所以不能靠 LLM 打分，必须靠显式依赖 DAG。
三、第二步：给所有任务状态结构化分类，并且构建依赖 DAG（有向无环图）
主讲原话：不能把所有聊天历史混在一起当成一维文本，必须结构化拆分存储，每一条状态都打上【依赖来源标签】：依赖哪一个目标版本、哪一条输入指令、哪一个数据源、哪一次工具调用。
视频把 Agent 任务状态拆成 5 大类，每一类在目标变更时的处理规则单独说明：
客观事实类：竞品名称、主体、官网、行业分类、基础公开信息
依赖特征：不绑定本次任务目标；
变更策略：绝大多数情况可跨目标复用，极少作废。
临时中间计算结果类：价格统计表、环比计算、情绪得分、词云、汇总表
依赖特征：强绑定当前目标版本、统计口径、数据粒度；
变更策略：一旦上游目标 / 参数变更，沿着 DAG 向下污染传播，自身以及下游全部节点标记作废。
规划 / 计划节点类：Agent 自己拆解出来的待执行步骤清单、工具调用序列
依赖特征：直接依附目标；
变更策略：目标版本升级后，旧计划整体失效，需要重新生成新规划。
待执行副作用动作（高危动作）：发送邮件、推送报表、写入数据库、发起审批、调用写接口
依赖特征：风险最高；
变更策略：只要目标发生变更，不管是哪一类变更，只要动作是基于旧目标生成，排队未执行的写操作必须优先取消；已经向用户确认过的高危动作，确认记录同步失效，新目标下如果还要执行，必须重新向用户确认。
用户偏好类：用户固定偏好格式、固定输出语言、固定忽略品牌
依赖特征：属于长期偏好，不绑定单次任务目标；
变更策略：任务目标变更时一般保留，不受本次目标版本影响；单独一套生命周期。
DAG 依赖图工作机制（视频原话）
每一个节点记录输入来自哪些上游节点；当根节点（目标 / 参数）发生变更，从变更点开始 BFS 广度优先遍历下游所有节点，所有被污染节点标记作废；上游不受影响节点继续保留。
一句话：失效是沿着数据流向下传播，不是全局清空。
配套 DAG 示例（视频给的数据分析链路示例）
原始日志拉取 → 数据清洗去重 → 按日聚合中间表 → 生成报告
当用户把日报表改成周报表：
根参数（聚合粒度）变更 → 【按日聚合中间表】节点作废 → 下游【生成报告】跟着作废；上游【原始日志、清洗结果】不受影响，可以保留复用，只需要新建按周聚合节点。
四、第三步：目标变更后的完整执行流程（视频标准执行链路）
收到用户新消息，先做差异分析：判断属于上面 4 类变更里哪一种；判断是否触发目标版本升级；生成新版本 Goal。
把变更映射为参数 / 目标节点变更事件，写入 DAG 根节点。
沿着 DAG 做污染传播遍历，批量标记节点状态：【保留 / 需要增量重算 / 作废 / 待用户二次确认】。输出一份失效清单。
调度层动作：
取消队列里还没跑的、已经标记作废的副作用工具调用；
已经缓存的旧工具结果降低缓存优先级，新规划优先重新查询；
作废旧的规划链，基于保留的有效事实，生成新版本任务计划；
新计划开始执行；
全程保留 Trace 日志，记录版本切换、节点作废原因。
五、第四步：工程落地上线门禁 & 线上保障要点（视频拔高部分，面试加分项）
主讲强调：demo 层面做到依赖 DAG 不难，线上稳定运行必须配套这几项，只讲 DAG 不算工程答案。
每次目标变更必须对外输出失效清单
清单内容：哪些节点保留复用、哪些节点作废、哪些需要增量重跑、哪些高危动作已经取消。可用于审计、给用户透明展示、问题排查回放。
回归评测体系
所有策略改动（Prompt、依赖判断规则、DAG 遍历逻辑），使用同一批测试样本回归；评测指标不只是输出通顺度，重点评测：
是否错误复用失效中间数据
是否不必要地重复计算（浪费成本）
高危副作用动作是否正确拦截
任务最终结果正确性
线上观测与样本回流
线上采样抓取真实 Trace；把线上出现的错误失效 / 误复用样本持续回灌评测集持续迭代规则。
分层记忆生命周期（视频补充）
短期任务状态（本次任务 DAG、中间结果）绑定目标版本，任务结束 / 版本切换自动过期；长期用户偏好、知识库事实单独存储，独立过期策略；不要混在同一个上下文窗口。
六、视频给出标准面试口述模板（逐字原文）
我会把对话历史和结构化任务状态分开维护，给目标分配版本号，所有中间产出、步骤、待执行动作构建带依赖关系的 DAG 图。用户修改目标时，首先识别变更类型，触发目标版本升级或者参数变更；然后从变更根节点向下做污染传播分析，标记被旧目标依赖污染的节点作废，上游不受影响的客观事实保留复用；排队中的写类高危副作用动作优先取消，需要用户确认的操作重新确认；最后基于有效数据重新规划，而不是全部清空或者直接追加历史继续执行。
七、面试官追问延伸（视频里面预设追问和回答）
追问 1：如果已经执行完的副作用怎么办？比如邮件已经发出去了？
回答：已经落地的副作用无法回滚，只能在 Trace 里记录本次目标变更时间点，做审计告警；重点防护还没执行的排队动作。Agent 只能拦截未执行动作，不能撤销已经落地的外部系统变更。
追问 2：这个方案成本会不会很高？维护 DAG 会不会很复杂？
回答：不是所有轻量 Agent 都需要完整 DAG；短任务、一次性简单任务，简单版本标记就够用；只有长周期、多工具调用、带写操作副作用的复杂 Agent，才值得上完整依赖 DAG 和版本管理。
八、视频收尾最终结论（结尾原话）
很多 Agent 多轮越跑越歪，根源不是模型能力不足，是把对话聊天历史和任务执行状态混在一起，没有显式的失效机制。
长任务 Agent 的核心能力三点：
目标支持版本化
所有产出维护数据依赖关系 DAG
待执行动作支持取消、拦截机制
只有做到精确作废，而不是无脑堆记忆或者一刀切清空，才能安全承接用户中途变更需求的场景。
