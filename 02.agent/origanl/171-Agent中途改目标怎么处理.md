视频内容详细总结
视频是一道Agent 开发大模型面试高频题讲解：用户任务执行中途修改目标，Agent 如何判断哪些旧步骤需要作废。
1、面试坑点：错误回答为什么会被淘汰
很多候选人会直接回答：直接全部重新执行任务，这个答案面试会直接淘汰。
真实线上系统中部分操作存在副作用，例如已经发送出去邮件、调用外部接口、写入数据库，这些已经发生的行为无法撤回。全部重跑不仅浪费算力，还会造成重复发邮件、重复写数据等线上事故；同时全部清空又会丢掉可以复用的有效中间结果。
另外只靠大模型做语义相似度打分判断步骤是否可用也不行，语义看着相似，但数据粒度、计算口径已经改变，会出现漏判问题。
这道题不是考察简单重规划，本质考察 Agent 任务状态管理、依赖分析、增量失效的工程落地能力，区分只会跑 Demo 和做过线上 Agent 项目的候选人。
2、核心方案：任务状态依赖图 DAG（有向无环图）
原理
Agent 把拆解出来的每一个子任务作为 DAG 的节点；图的边记录数据依赖关系：记录每个节点的输入来自哪些前置节点，输出会被哪些下游节点消费；每个节点同时记录输入参数、输出数据粒度、执行状态（已执行 / 待执行、是否产生外部副作用）。
目标变更后的处理流程（污染 / 作废标记反向传播）
目标差异分析：识别新旧目标之间的改动，把用户自然语言的目标修改，映射为 DAG 图上的参数、条件变更事件，不是交给模型自由语义判断。
反向 / 向下传播作废标记：找到受变更影响的起始节点，把该节点，以及所有依赖该节点输出的下游全部节点标记作废；
保留无冲突节点：上游不受目标改动影响、输出仍然可以给新任务使用的已执行节点，保留、复用它的执行结果，不需要重新跑；
举例：数据分析任务：拉原始数据→清洗数据→按日聚合→生成报告。用户把日报改成周报。拉原始数据、清洗数据节点不受影响可以保留；按日聚合节点受影响作废，它下游生成报告一并作废，只需要从聚合节点开始重新执行，不需要从头拉取数据。
区分带副作用的节点：对于已经执行完成、产生外部副作用（发邮件、写库）的节点，无法撤销，只能做标记记录，不能删除；还未执行的排队工具调用，可以直接取消调度。
增量重执行：只针对被标记作废的节点重新调度执行，复用保留的节点结果，完成新目标，做到局部重跑，而不是整体推倒重来。
3、两种错误做法的弊端
全部从头重跑：已发生副作用不能撤销，算力浪费，重复操作风险；
不做失效分析直接接着旧流程往下跑：旧的中间数据口径不匹配新目标，继续计算会产出错误结果，造成数据混淆。
4、面试高分回答模板思路（视频给出答题框架）
当用户中途修改任务目标时，我不会直接全部重跑。Agent 在任务规划阶段构建任务状态 DAG 依赖图，每个子任务节点记录输入输出、数据粒度与依赖关系。
用户变更目标后，先做新旧目标差异解析，定位参数改动对应的节点；沿着 DAG 依赖链路做失效传播，将受影响节点及其下游标记作废；对没有依赖冲突的已执行节点保留结果进行复用；
区分已经产生外部副作用的步骤，这类操作无法撤回，仅做状态记录；尚未执行的任务取消调度；最后仅对作废节点增量重新规划执行，避免全量重跑带来副作用风险，同时节约计算资源，防止旧数据污染新任务结果。
5、视频小结
核心思想：不要非黑即白（要么全删、要么全留），基于数据依赖做精准的节点失效，增量复用、增量重算。

一、题干本质（视频开篇点明）
表象问题：用户任务跑到一半修改需求 / 目标，Agent 如何筛选旧步骤，哪些作废、哪些保留。
考察内核：不是考察简单任务重规划，是区分只会跑 Demo，还是具备线上 Agent 工程落地经验；考察任务状态管理、数据依赖分析、增量失效 / 污染传播、副作用处理的真实工程能力。
致命错误回答：直接全部重新执行任务，该回答面试会直接淘汰。
二、为什么 “全部重新执行” 会被淘汰（视频完整理由）
真实系统存在副作用操作，无法物理撤回
例子：已经发送出去的邮件、已经写入数据库、调用第三方外部接口、提交工单。这些动作一旦执行完毕，现实世界状态已经改变，程序不能撤销已经发生的外部行为。
全量重跑带来两类线上风险：
风险①：重复触发副作用，重复发邮件、重复写库、重复创建工单，制造业务事故。
风险②：算力浪费，大量已经正确、可用的中间计算结果被丢弃，白白重复计算。
补充：另外一个常见错误思路 —— 仅依靠大模型做语义相似度打分判断步骤是否可用。
缺陷：两段步骤语义看着很接近，但是底层数据粒度、计算口径已经变更，会出现漏判，把已经失效的步骤错误保留。
三、核心解决方案：构建【任务状态依赖图 DAG（有向无环图）】
3‑1 DAG 图中每个节点（每一个子任务）必须记录的元数据（视频要点，不能省略）
子任务输入参数；
子任务输出数据、输出数据粒度；
依赖边：记录输入来自哪些上游节点；输出会被哪些下游节点消费（数据依赖关系）；
执行状态：待执行 / 执行中 / 执行成功 / 执行失败；
副作用标记位：标记本节点执行后会不会产生外部不可撤销副作用（发邮件、写 DB 为 true；纯内存计算、读数据为 false）。
重要：Agent 任务拆解输出不是简单一维列表，而是带依赖关系的 DAG 图，支持表达串行、并行数据依赖。
3‑2 用户目标变更后的完整处理流程（视频完整 5 步，反向作废标记 / 污染传播）
步骤 1：新旧目标差异解析
将用户自然语言的目标修改，解析映射到 DAG 图的参数、条件变更事件；不是交给大模型自由语义脑补，定位是哪些参数、约束、业务口径发生改变。生成新版本任务目标。
步骤 2：反向传播作废标记（污染传播）
定位受改动直接影响的起始节点；沿着 DAG 的依赖边，把该节点，以及所有依赖该节点输出的全部下游节点打上作废标记。
逻辑：上游节点输出一旦失效，所有拿它输出作为输入的下游，全部被 “污染”，不能继续使用旧结果。
步骤 3：保留无冲突、不受影响的已执行节点
上游节点输入输出完全匹配新目标，没有被改动波及，直接复用已经执行完成的输出结果，不重复运行。
📌视频配套实例：数据分析任务
旧任务链路 DAG 节点顺序：①拉原始数据 →②清洗数据 →③按日聚合 →④生成日报报告
用户中途修改目标：把日报改成周报
节点①拉原始数据、②清洗数据：不受改动影响，保留复用，不用重跑；
节点③按日聚合：直接受改动影响，标记作废；
节点④生成报告：依赖③的输出，跟随下游传播一并作废。
最终只从作废的③节点开始重新执行（改成按周聚合，再生成周报），不需要从头拉原始数据。
步骤 4：区分两类节点，差异化处理副作用
已经执行完成，标记为有副作用的节点：现实行为无法撤回，不能删除节点，只做状态记录留存审计日志；
还处于排队、待执行，还没运行的节点：可以直接取消调度，不再执行。
步骤 5：增量重执行
只调度执行所有被标记作废的节点，复用保留节点的已有输出结果；完成新目标，做到局部重跑，拒绝整体推倒重来。
四、两种错误处理方案，完整弊端拆解（视频明确列出）
方案 A：全部从头重跑（错误）
弊端：
已经发生的外部副作用无法撤销，会造成重复操作业务事故；
大量有效中间结果丢弃，算力资源浪费。
方案 B：不做失效分析，直接沿用旧 DAG 继续往下跑（错误）
弊端：旧的中间数据口径、数据粒度不匹配新目标，继续运算，产出错误结果，发生数据混淆。
对应上面例子：拿 “按日聚合” 结果直接去生成周报，数据完全错误。
五、边界补充（视频隐含工程要点，面试会被追问）
不是所有节点都可以复用，判断唯一标准：节点输出是否还能满足新版本目标的输入口径，不是看语义像不像。
作废标记只向下游传播；上游不受影响，不向上污染。
DAG 除处理中途改目标，同样可以用于任务失败后的局部重跑。
