视频主题：大模型 Agent 面试题：当 Agent 工具 / API 数量很多，如何避免模型选错、乱调用工具。
核心观点：不要只回答 “优化 Prompt”；生产环境下工具选择是一套完整工具路由工程系统，分为召回、重排、约束、验证四层机制。
背景问题
工具少的时候靠 Prompt 还能应付；当工具达到几十、上百个，全部平铺丢给大模型，会出现：相似工具混用、不该调用工具时乱调用、上下文负担大。单纯改提示词治标不治本。
四层工程化方案
1️⃣ 工具描述规范（约束层）
写工具说明不能只写能干什么，必须写三件事：
什么时候使用本工具
需要哪些入参
什么场景绝对不能用（负样本）
示例：退款工具不能用来改收货地址；合同解锁工具不能查库存。负向场景描述可以显著降低误触发。
2️⃣ 业务域工具分层（约束层）
不要把全部工具一次性暴露给模型。
把工具按业务域分组：用户服务、订单履约、知识检测、数据分析、系统操作等。
模型第一步先判断任务属于哪个业务域，只把该域内少量工具交给模型选择，缩小候选池，类似 RAG 的分库思想，降低选择难度。
3️⃣ 召回 + 重排（召回、重排层）
工具选择本质变成检索问题：
召回：使用关键词、Embedding 向量、规则，先捞一批候选工具，目标是不漏掉正确工具；
重排 Re‑rank：交给大模型 / 小模型对召回结果打分排序，过滤无关，选出最合适工具。
例子：用户查询客户投诉记录，召回会返回客户档案、工单查询、订单查询等；重排后优先选工单查询工具。
4️⃣ 调用前校验（验证层，安全护栏）
选中工具不要直接执行，先做前置校验：
参数完整性校验
用户权限校验
风险等级判断；写操作（退款、删数据、改配置、发邮件）等高风险操作，增加人工确认、可回滚判断。
选对工具只是第一步，安全执行同等重要。

这样回答体现工程路由思维，而不是只会调 Prompt。

标题：面试官：Agent 工具太多怎么防选错？
作者：小哲大模型 AI
面试被问到：Agent 工具越来越多，怎么防止模型选错工具？
别再只回答优化 Prompt 了！
在真实的生产环境中，工具选择其实是一个完整的工程路由系统。
先给结论：Agent 工具路由不能只靠大模型自由选择，而要做成「召回、重排、约束、验证」四层机制。
工具少的时候，靠 Prompt 还能勉强应付。一旦工具达到几十、上百个，你把全部工具一次性丢给大模型，就会出现一堆问题：相似工具混用、不该调用的时候乱调用，同时上下文太长，Token 开销巨大。单纯优化提示词，只能治标，不能治本。
第一层：约束 — 工具描述规范
写工具描述，不能只简单写一句 “这个工具可以查订单”，必须写清楚三件事：
什么时候使用本工具
需要哪些入参
什么场景绝对不能用
尤其是「什么时候不能用」这部分负向描述，非常关键。
举例子：退款工具不能用来改收货地址；合同检索工具不能用来查实时库存。
把这些负样本写进去，可以明显降低模型误触发。
第二层：约束 — 业务域工具分层
不要把全部工具一次性暴露给模型。
我们把工具按照业务域分组：用户服务、订单履约、知识检索、数据分析、系统操作等。
模型第一步先判断，当前任务属于哪一个业务域，只把这个域里面少量的工具交给模型做选择。
思路和 RAG 分库是一样的，直接缩小候选工具池，降低模型选择难度。
第三层：召回 + 重排
工具选择本质上可以变成检索问题。
第一步召回：使用关键词、Embedding 向量、业务规则，先捞出来一批候选工具。召回目标是不漏掉正确工具，可以多捞。
第二步重排 Re-rank：交给大模型或者小模型，对召回出来的候选工具打分排序，过滤无关工具，选出最合适的那几个。
举个例子：用户查询客户投诉记录。
召回阶段，会返回客户档案、工单查询、订单查询等多个工具；
经过重排之后，优先给到模型工单查询工具。
第四层：验证 — 调用前校验
工具被模型选中之后，不要马上执行。
先做前置校验：
参数完整性校验
用户权限校验
风险等级判断
写操作，比如退款、删数据、改配置、发邮件这类高风险操作，增加人工确认、可回滚判断。
Agent 选对工具只是第一步，能不能安全执行是另外一回事。
面试标准回答话术
Agent 工具多以后，我不会把所有工具直接塞给模型选择。而是先做工具分层和描述规范，把触发场景、输入约束、反例都写清楚；然后用召回加重排筛选候选工具；执行前再做参数、权限和风险校验；最后把调用轨迹落盘，方便后续复盘迭代优化。
这样回答，面试官听到的不是 “我会 Function Calling”，而是你理解工具选择是一套工程路由系统，具备落地架构思维。
