视频内容详细总结
该视频是一道 RAG 大模型面试题解析：知识库新旧制度同时存在，RAG 如何判断哪个版本生效。
核心观点：这道题不能简单回答 “按时间排序取最新”，考察的不是向量检索能力，而是企业知识库系统化治理、元数据、过滤、证据仲裁的工程落地能力。向量检索只能做到语义相关，无法自动识别制度生效状态、适用部门、地区例外条款，不能让大模型自己猜哪个版本有效。
业务真实痛点
企业知识库中经常混杂：新版制度、旧版制度、子公司补充规定、地区例外条款。
举例：总部发布 2026 版差旅制度生效，但华南子公司存在补充条款；如果用户属于华南地区，不能只拿总部制度给出回答。
核心原则：把生效规则嵌入 RAG 全链路，入库时就记录业务属性，检索阶段用元数据做过滤，模型只负责基于筛选后的证据做回答。
整体方案分为四大工程层面：
1、文档入库治理（源头处理）
不能只做文档切片、Embedding 向量化，必须给每一份制度文档补充结构化元数据字段，从源系统继承业务属性，不能只依赖 PDF 标题文本：
需要记录字段：版本号、生效日期、失效日期、发布部门、适用组织范围、文档状态、版本替代关系。
旧版本不要直接物理删除，保留在库中用于审计、历史时间点回溯查询，但是要通过元数据控制，正常问答链路不召回旧版文档。
2、查询侧约束（检索前条件抽取）
用户提问自带很多隐含条件：员工部门、所在地区、业务类型、查询的业务时间点。
系统不能直接拿用户原始自然语言去做向量检索；需要先解析用户查询，抽取身份、场景、时间等条件，转化为元数据过滤条件，再执行检索，缩小候选证据池。
参考 LangChain 查询分析的工程思路，先明确查询需要哪些过滤字段，再检索召回文档片段。
3、冲突暴露与证据仲裁
当新旧制度同时命中检索条件，禁止让大模型强行融合冲突内容输出答案（制度类业务，模型自信输出错误结论会造成实际业务损失）。
正确做法：
明确告知用户采用哪个版本、选择依据；说明旧版为什么不适用（已经失效 / 不匹配适用范围）。
如果元数据没有明确版本替代关系、证据存在矛盾，直接向用户提示存在冲突，建议人工确认，不要强行输出确定答案。
输出答案需要可审计，返回使用的制度版本、生效时间、适用组织，同时说明被排除旧版本的原因，让用户看到决策依据，而不是只给最终结论。
4、回归评测与上线监控
知识库更新（切片改动、新增制度、索引重建）时，必须做版本冲突专项回归测试。
评测指标不能只看召回率；额外校验：版本过滤正确性、答案是否来自生效文档、冲突场景能否识别并暴露矛盾。需要专门构造版本冲突测试样本。
线上监控过期文档的命中率：如果失效制度频繁被召回，代表过滤逻辑、知识库治理存在 bug。
面试回答参考模板
“我会将制度版本问题拆解成入库元数据打标、查询条件抽取、元数据前置过滤、冲突仲裁、答案溯源引用这几个环节。RAG 不应该由模型猜测哪个版本生效，而是依靠业务元数据先缩小证据范围，模型只基于筛选后的有效证据生成回答。版本治理没做好，模型总结能力越强，越容易输出看似专业、实际过期错误的答案。”
补充延伸要点（面试官追问可以补充）
制度更新要走正式发布流程，新版本入库触发索引重建 + 回归测试。
系统既要回答 “当前应该执行哪版制度”，也支持查询 “某一个历史时间点执行的制度版本”。
制度类 RAG 可信度来源于可审计的版本依据，不是大模型回答语气是否肯定。
核心踩坑提醒
很多 Demo 简单依靠文档上传时间排序取最新版本，会遇到很多问题：子公司补充文件、试行版本、地区特例，上传时间新，但不能完全覆盖总部正式制度；单纯时间排序无法处理适用范围、废止替代关系，在企业制度知识库场景不可靠。

视频完整逐点整理（原样还原视频全部要点、例子、结论，无省略）
原题：面试官问：企业知识库里面新旧制度同时存在，RAG 怎么判断哪个版本生效？
视频开篇定调：千万不要上来就回答 “按时间排序，取最新文档”。这个答案只适合 Demo、干净数据集；企业真实知识库场景，这个回答是错的。本题不是考向量检索、召回算法，本质考察企业知识库治理、元数据体系、检索前置约束、证据仲裁、可审计闭环整套工程落地能力。
一、底层原理与原生缺陷（视频第一个结论）
向量 Embedding 只计算语义相似度，向量本身没有能力识别业务生效规则。
新旧制度文本高度相似，向量打分几乎一样，向量检索无法自动区分：正式版 / 草稿、试行版、总部制度、子公司补充条款、废止旧版。
大模型本身会做文本融合：拿到多条冲突片段，模型会自主揉成一段通顺、自信的文字，而不是做业务层面的裁决。模型越会润色，越容易输出混合了新旧规则、现实不存在的 “虚假制度”。
核心结论：生效判断不能交给模型猜，裁决逻辑必须前置到检索链路，在喂给模型之前就完成过滤。
配套业务例子（视频核心举例：差旅报销制度）
总部发布 2026 新版差旅制度，正式生效；但是华南子公司有单独的补充规定、例外条款。
如果提问人是华南员工：只召回总部最新版，忽略子公司补充规则 → 答案错误。
单纯按上传时间取最新：有可能子公司补充文档上传时间更早，但它对华南员工是有效的特例；或者一份试行文档上传时间比正式版晚，但试行版优先级低于正式制度。
衍生子例子：按职级区分的报销制度，新版只适用于 P5 及以上，P4 及以下仍然沿用旧版，新版发布不等于旧版全局失效。
二、模块 1：文档入库治理（源头层，视频完整字段 + 规则）
结论：切片、向量化、入库，不能只抽文本；每一个 chunk 切片，都必须绑定结构化元数据，元数据优先从业务源系统同步，而不是靠从 PDF 标题文本猜测。
需要维护的全部元数据字段（视频列出全部）
文档唯一编号
版本号
生效日期
失效 / 废止日期
发布主体（总部 / 某子公司 / 某部门）
适用组织范围（全公司、华南分公司、P5 + 职级等）
文档状态：草稿 / 试行 / 正式生效 / 已废止
版本替代关系：本版替代哪一个旧版本
文档权威层级：集团正式制度 > 部门通知 > 会议纪要 / 解读文档
事项标签：差旅、报销、考勤等业务事项
入库规则（视频明确）
旧版本文档不物理删除，保留在向量库，用于审计、历史回溯、历史时间点查询；
通过元数据状态控制：正常业务问答链路，默认过滤掉【草稿、已废止】；
新版本入库≠立刻上线：新版本构建索引后走校验流程，校验通过再切换线上可见；避免一半召回旧切片、一半召回新切片。
切片不能脱离文档元数据：每一小段 chunk，都继承父文档全套元数据，不能只存文本。
三、模块 2：查询侧：用户意图解析、条件抽取（检索之前，先做，不是直接向量化 query）
结论：不要直接拿用户原始问句去做向量检索，先解析查询，抽取隐含业务条件，生成元数据过滤谓词，再执行检索。
需要抽取的查询条件（视频列出）
用户身份：所属部门、所属子公司、职级
查询业务时间点：是问【现在执行的规则】，还是问【2025 年执行的历史规则】
业务事项：差旅、报销、采购等
用户是否明确要求查看历史版本、废止版本
例子
用户提问：我在华南出差，报销标准是多少？
解析得到过滤条件：组织 = 华南分公司、时间 = 当前、事项 = 差旅报销
先过滤，只保留满足这套元数据条件的候选文档，再做向量召回；而不是先召回一堆总部、其他地区、旧版文档，再交给模型自己筛。
延伸能力（视频提到）
支持时间点回溯查询：用户问 2025 年的报销标准，就把过滤条件里的时间改成 2025 时间窗口，召回当时生效版本，而不是固定拿今天生效版本。
四、模块 3：召回之后：硬过滤 → 权威排序 → 冲突仲裁（视频重点、强制约束）
链路顺序：元数据硬过滤（优先）→ 语义相似度重排（次要）
结论：语义分数只是在【已经满足业务生效条件的候选集里面】做排序；语义分数不能覆盖业务元数据规则。
分层仲裁规则（视频逐条）
第一步硬过滤：淘汰状态为草稿、已废止、适用范围不匹配、时间窗口不匹配的 chunk；
第二步权威层级排序（优先级从高到低）：集团正式制度 > 子公司正式补充制度 > 部门通知 > 会议纪要、解读材料；
第三步：如果过滤之后，仍然存在多份文档同时命中、规则互相冲突（元数据没有写明替代关系）：
✅ 禁止让大模型强行融合、强行输出一个确定答案；
✅ 正确做法：把冲突的多条证据全部列出，标注每份文档的版本、生效时间、发布部门、原文差异；
✅ 输出提示：当前多条制度存在冲突，无法自动裁决，请人工确认；
第四步：回答输出必须可溯源、可审计
输出内容固定附带：
本次回答采用的文档版本、生效时间、发布部门；
被排除文档的排除原因（已废止、适用范围不匹配、层级更低）；
用户可以明确看到裁决依据，而不是只看到最终答案。
视频举的冲突案例
总部制度写 “国内差旅住宿上限 800”，华南子公司正式补充制度写 “华南区域一线城市上限 1000”；两份都生效、权威层级是总部 + 子公司特例。
✅ 正确回答：说明总部基础标准，同时说明华南本地例外条款，两个规则同时生效，不是二选一；
❌ 错误做法：模型随便挑一条，或者取平均值合并成 900 这种不存在的规则。
五、模块 4：上线评测、回归测试、线上监控（视频收尾工程环节）
结论：版本治理是持续维护流程，不是一次性上线做完就结束。
知识库新增制度、版本变更、废止旧制度时，必须触发版本冲突专项回归测试；
评测指标不能只看召回率、相关性；必须额外增加专项校验 case：
是否只召回生效版本；
冲突场景能不能识别冲突、拒绝强行输出结论；
历史时间点查询能不能正确召回对应时期版本；
线上监控指标（视频重点）：监控【已标记废止 / 失效文档的召回命中率】；
如果失效文档频繁被召回，代表元数据过滤逻辑、索引更新链路存在 bug，需要告警；
制度发布流程绑定知识库更新：正式审批发布完成之后，才触发入库、索引构建、回归测试，避免审批未完成的草稿流入线上检索。
六、视频明确的所有踩坑点（反面结论）
❌ 坑 1：只按文档上传时间取最新；无法处理子公司特例、试行文档、按职级分版本场景；
❌ 坑 2：不打元数据，靠 Prompt 提示词约束模型自己分辨版本；Prompt 约束不可靠，高风险业务不能依赖；
❌ 坑 3：冲突时让模型自己调和矛盾；制度类业务，模型自信输出错误结论会带来财务、合规损失；
❌ 坑 4：旧文档直接删除；丢失审计、历史回溯能力；
❌ 坑 5：先向量召回 topK，再用模型过滤版本；把裁决权交给模型，顺序颠倒。

八、面试官追问的延伸补充点（视频末尾追加）
制度存在过渡期：例如 X 月 1 日之后新订单执行新版，老订单沿用旧版；元数据要支持业务对象（订单）维度的条件过滤；
权限和版本可以叠加：除了生效版本，还可以叠加用户权限元数据，控制哪些人能查看哪些文档；
这套方案可以复用：不限于差旅制度，HR 制度、采购流程、财务规范等强合规知识库都适用；
一句话总纲（视频收尾金句）：元数据先行，检索兜底；裁决前置，模型只负责解释证据，不负责业务规则判定。
