视频详细内容总结
视频是一道 Agent 开发面试题讲解：Agent 执行扣款、下单、发券，如何避免重试带来重复操作，核心观点：该题表面考察重试逻辑，本质考察幂等性、副作用控制；Agent 业务可靠性不依赖大模型本身，而是依靠工具接口与工作流设计。
一、问题背景
Agent 调用工具时，网络超时、响应丢失很常见，大模型会很自然地选择重试。
扣款、下单、发券属于带副作用的写操作，和查询天气这类只读接口不一样：盲目重试会引发重复扣款、多发券、重复创建订单事故。
重要前提：业务系统不能假设 “模型只会调用一次工具”，必须默认会出现重复调用、网络超时、返回结果丢失的情况。
错误示范：下单接口超时，Agent 直接再次调用下单接口，极易产生重复订单。
正确示范：第一次调用携带幂等键（requestID）；超时之后，先用幂等键查询业务状态；如果订单已经创建，直接复用已有订单；确认没有执行，才允许在重试预算内重试。
二、三大常见开发坑点
只给读操作做重试，写操作没有状态机
查询类只读接口失败可以安全重试；扣款、下单这类写操作失败，不能简单直接重试。
迷信 HTTP 200 返回成功
接口返回 HTTP200，有可能只是 “受理成功”，后续业务还会异步失败，不能当作业务最终完成，必须补充业务结果确认逻辑。
用户确认逻辑没有绑定幂等信息
退款这类高危操作，要把用户确认记录、订单号、金额、幂等键绑定在一起；设置操作时间窗口，确认过期之后，必须重新向用户确认，不能因为模型理解偏差，再次发起动作。
三、核心解决思路：工具分类 + 完整工作流
把 Agent 调用的工具分为三类：只读、可重复写、不可重复写。
扣款、下单、发券属于不可重复写操作，需要整套机制：幂等键、操作状态表、状态查询、重试预算、补偿流程、trace 追踪。
完整流程：
工具调用失败，优先查询业务状态，禁止直接重放动作；区分已执行、未执行、未知状态；
允许重试的场景，严格遵守重试预算（次数限制）；
多次失败无法处理，转入队列或者人工介入；
通过 trace 日志完整记录，幂等键记录在链路中，方便事后事故排查回放。
重点：线上系统要把未知状态（超时）作为一等状态处理，不能简单把超时直接判定为失败。最危险的不是明确失败，是不知道下游到底有没有执行。处理顺序：先查状态 → 做补偿 → 升级人工。
四、面试官追问的扩展回答要点
追问 1：幂等键如何设计？
幂等键不能简单随机生成。要绑定业务语义：组合用户标识、订单号、动作类型、金额、确认版本；
如果每次随机生成全新 key，同一个业务动作会使用不同 key，幂等防护直接失效。
追问 2：工具接口该怎么设计？
写操作接口建议返回operationID；后续所有查询、重试、取消动作，全部围绕这个操作 ID 开展。没有操作 ID，Agent 无法判断上一次业务执行到哪一步。
追问 3：重试策略怎么配置？
读、写操作不能共用同一套默认重试策略。只读接口可以正常重试；带副作用写操作，重试前必须先查询业务状态。
五、可直接使用的面试答题模板
我会把工具分为只读、可重复写、不可重复写三类。针对扣款、发券、下单这类不可重复写的副作用操作，要设计幂等键、操作状态表、状态查询、补偿流程。Agent 调用失败时优先查询业务状态，不直接重放动作；多次失败后进入队列或者人工处理，同时用 trace 保存完整链路日志。Agent 业务的可靠性不靠模型，依靠工具接口与工作流设计做保障。
六、视频核心结论

幂等性由业务服务来保证，不是靠大模型约束；
重试策略区分读写操作，高危写操作禁止盲目重试。

一、题目背景与业务现实（视频开篇全部原文要点）
Agent 工具调用场景：OpenAI 以及各类 Agent 框架，都允许大模型自主触发工具调用。
客观故障前提：业务系统绝对不能假设模型只会调用一次工具。必须预设三类问题：工具调用会重复发生、网络会超时、接口返回结果会丢失。
故障根源：当接口网络超时，大模型会本能选择重试工具调用。

扣款、下单、发券这类带副作用的写操作：盲目重试会产生严重事故：重复扣款、多发优惠券、重复创建订单。

视频举的业务实例：Agent 创建订单接口超时场景
❌【最危险错误做法】
用户指令让 Agent 下单，创建订单接口超时。模型直接再次调用下单接口，直接重放动作，造成重复订单。
✅【正确完整流程例子】
第一次调用接口的时候，就带上 requestID / 业务幂等键；
发生超时之后，不要直接重试，先用这个幂等 key 去查询下游业务，判断订单是否已经被创建；
如果查询发现订单已经创建：直接复用已经存在的订单，不再发起新调用；
如果查询确认操作确实没有执行：再在重试预算限制之内，才允许重试调用接口。
二、视频列出的 3 大类线上开发坑点（全部原文）
坑点 1：只给读操作配置重试策略，写操作没有状态机
查询类只读接口失败，是可以安全重试；
扣款、下单这类写操作发生失败，不能简单直接重试。很多开发只给读接口写重试逻辑，写操作缺少状态机，直接照搬读操作重试逻辑，造成重复副作用。
坑点 2：HTTP200 假象，把 HTTP200 状态码等同于业务执行完成
很多接口返回 HTTP 200，仅仅代表请求被系统受理成功，后续业务还会异步执行失败。
不能看到 HTTP200 就认为扣款、下单已经真正完成；必须补充业务层面结果确认逻辑，不能只看网络状态码。
坑点 3：用户确认动作没有和幂等信息绑定
典型场景：退款高危业务。
用户确认一次退款，系统需要把：用户确认记录、退款金额、订单号、幂等键四者绑定在一起；
不能后续对话中，因为大模型理解偏差，再次发起退款动作；
高危幂等动作，必须设置时间窗口；一旦用户确认过期，必须重新向用户二次确认，不能直接沿用旧确认继续执行。
三、视频核心解决方案：工具分类 + 完整工作流
工具分类标准：把 Agent 调用工具划分为三类：只读工具、可重复写工具、不可重复写工具。
扣款、发券、下单、退款，属于不可重复写高危操作，必须全套组件：幂等键、操作状态表、状态查询、重试预算、补偿流程、trace 链路追踪。
完整工作流步骤（视频原文流程）
当 Agent 调用高危写工具发生调用失败，优先查询业务状态，禁止直接重放动作；
需要区分三种业务状态：已执行、未执行、未知状态（超时）；
允许重试场景，严格遵守重试预算（限制最大重试次数）；
如果多次失败无法处理，转入队列处理，或者升级人工介入；
使用 trace 保存完整链路日志，幂等键必须暴露在 trace 链路里面，方便事故回放排查，确认是否发生重复提交。
重点工程理念（视频强调）：线上系统，要把未知状态（超时）当做一等状态处理。
最危险的业务情况，不是明确返回失败；而是你完全不知道下游外部系统到底有没有执行这个动作。
处理顺序固定：先查询状态 → 执行补偿逻辑 → 升级人工处理。绝对不能上来直接重试。
