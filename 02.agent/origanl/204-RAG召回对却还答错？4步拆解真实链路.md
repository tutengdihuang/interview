视频完整内容总结
视频是一道大模型 RAG 高频面试题讲解：RAG 已经召回了正确文档，但大模型最终输出答案依旧答错。核心观点：问题不一定是向量检索不准，失败会发生在检索、重排、上下文组装、生成约束整个链路，不能只盯着召回环节看。
核心总述：召回命中正确文档，仅仅代表第一步原料拿到手；不等于片段完整、不等于模型读到关键信息、不等于生成结果忠于原文。出错本质是证据在流转过程中被切碎、排错、被挤掉、被误读，或是缺少强制引用约束。
一、三大工程坑点（失败根因）
1. 切片与上下文组装问题（分块 Chunk 问题）
粗暴按固定字数切割文档，会把上下文语义切断，只保留半截证据。
举例：合同写 “可以申请退款，但企业定制版除外”，切片刚好切断，只保留 “可以申请退款”，排除条款丢失。文档虽然被召回，但给到模型的是残缺片段。
解决思路：做结构化切片，保留标题、章节、表格、脚注、相邻段落关联关系，拒绝简单固定长度切分。
2. 排序重排与多源证据冲突问题
Top‑K 召回列表里，会同时存在新旧版本制度、FAQ、客服话术等多份相关文档，但它们权威等级、生效时间、适用范围不一样。
直接全部平铺喂给模型，大模型会优先挑选语言通顺的内容输出，不一定选权威正确的。
解决思路：给文档带上元数据：生效时间、来源、文档层级、适用范围；重排、生成阶段都参考这些元信息，区分证据优先级，消解冲突。
3. 生成阶段缺少忠实性约束（幻觉问题）
大模型天生倾向补全文本，不会主动判断证据够不够，容易产生幻觉。即便上下文有正确材料，也会混入模型自身固有知识编造答案。
解决思路：强制答案绑定原文引用；关键结论必须溯源到召回片段；证据不足时输出 “不知道 / 需要人工确认”，而不是强行编答案；借助框架的忠实度评估指标（faithfulness）做校验。
二、面试标准四层答题框架
回答该面试题，分层排查链路：
第一层：确认召回是否真的命中目标文档；
第二层：检查命中的片段内容是否完整，有没有被切片破坏语义；
第三层：检查重排逻辑，权威、正确证据是否被排在优先位置，有没有被无关内容挤压；
第四层：检查生成输出，答案是否忠实引用证据，是否存在脱离原文编造内容。
补充：线上环境还要做 Bad Case 回放，完整记录用户问题、召回片段、重排分数、引用来源、最终答案，定位在哪一层出现错误。
三、如何做验证与测试
需要准备三类测试样本做验证：
证据正确，但文本容易被误读的样本；
多份证据互相冲突的样本；
证据不足，必须拒答的样本。
评估维度看：召回命中、证据引用覆盖率、答案忠实度、人工复核结果；上线后抽检高风险回答，把模型输出和原始引用片段并排展示给审核人员，专门抓 “文本相关，但结论越界编造” 的案例。
四、线上排障：快照倒查法（六步倒查）
RAG 调优不能只看单次回答结果，要保存完整请求快照，同一问题，知识库版本、权限、模型参数不同，结果会差异很大。
定位 Bad Case，按下面链路一步步倒查，在哪一步内容开始出错，问题就归属那一层：
用户原始问题 → Query 改写 → 召回列表 → 重排顺序 → 上下文拼装 → 最终引用与答案输出

视频标题：RAG 明明召回了正确文档，为什么大模型最后还是答错？
主讲人：小哲大模型 AI
核心总起句（视频开篇原话）：
这个问题表面问 RAG，实际考察你能不能把检索、重排、上下文组装、生成约束拆开来看。很多人简单理解 RAG = 搜到文档直接塞给模型，但线上生产系统不是这样。召回列表里存在正确文档，仅仅代表第一步命中成功；不等于给到模型的证据片段是完整的、不等于模型能读到关键信息、不等于模型输出忠于原文。一句话总结：RAG 召回正确但答案错误，一般不是单点检索问题，而是证据从知识库流转到最终答案的整条链路里，出现了被切碎、排错、被挤掉、被误读，或是缺少强制引用约束。
开篇面试提醒：
面试的时候，如果只回答 “向量检索不准”，属于踩坑低分回答；高分工程化回答，必须补充：上下文片段质量、证据优先级 / 冲突处理、生成忠实性约束、结果评估与 badcase 回放。
第一大问题：切片 & 上下文组装问题（Chunk 分块问题）
问题描述：采用固定字数粗暴切分文档（按字符硬截断），会把一句完整规则、带限定条件的语义切断，关键的例外、约束条款被切到别的 chunk 里。虽然正确文档被召回，但送入模型的只是残缺半截证据。
视频配套例子（原话）：
合同原文：可以申请退款，但企业定制版除外。
切片刚好切在两句中间，本次召回拿到的 chunk 只保留了半句：【可以申请退款】，“企业定制版除外” 这个限制条件被切到另外一个分片，没有进入本轮上下文。
现象：召回列表里确实有这份合同文档，但是模型拿到的片段是残缺的，模型看不到排除条件，直接输出 “可以申请退款” 的错误结论。
视频给出结论 & 解决方案：
不能只用固定长度硬切。生产环境要用结构化切片；切片时保留文档标题、章节层级、表格、脚注、相邻段落关联关系，按语义边界切割，保证单条 chunk 语义自洽，重要约束和主规则保存在同一个片段内。
第二大问题：重排与多源证据冲突问题
问题描述：Top-K 召回之后，返回的多条相关文档 / 片段，来源、生效时间、权威等级、适用范围不一样，互相冲突；直接全部平铺拼接送入 Prompt，大模型本身没有自带权威判断能力，它会优先选择读起来通顺、口语化的内容输出，而不是选择优先级最高、正式生效的权威文档。
视频配套例子：
知识库里面同时存在：旧版制度、新版制度、客服 FAQ 话术、临时通知。用户问同一个业务问题，召回同时拿到 4 份材料，内容互相矛盾。FAQ 话术简单顺口，排在前面；正式制度文本严谨冗长排在后面。模型优先采信 FAQ 里的说法，输出错误答案。
视频给出结论 & 解决方案：
入库时给每一条文档 / 片段挂载元数据：文档生效时间、来源类型（正式制度 / FAQ / 临时通知）、文档层级、适用业务范围。
重排阶段、生成阶段都要读取这份元数据，给证据设置优先级权重；自动消解新旧版本冲突、高低权威来源冲突，高优先级证据前置。
补充隐含子问题：Lost in the Middle（中间丢失效应）
模型注意力不均匀，对上下文开头、末尾关注度更高，放在中间位置的正确片段容易被模型忽略；就算正确片段在上下文里，也会被前面低质量、口语化的噪声内容覆盖。
第三大问题：生成阶段缺少忠实性约束（幻觉根源）
问题描述：大模型预训练知识是固化的，它天生有补全、编造的倾向；模型不会主动校验 “我当前的回答是不是全部来自给到的上下文证据”。哪怕上下文里面放了正确原文，模型依然会混入自己预训练学到的旧知识，篡改、延伸、脑补内容，产生幻觉。
视频配套例子：
知识库文档写着：会员优惠券有效期 7 天。模型自身预训练知识里印象里优惠券一般 3 天。上下文里虽然有 7 天的原文，但是没有强制约束，模型输出：优惠券有效期 3 天。
证据明明存在，但是模型优先采信自己内部知识，无视上下文。
视频给出结论 & 解决方案：
① 提示词增加强制规则：答案必须完全基于提供的参考片段；
② 强制溯源引用：输出答案时，关键结论必须标注对应的原文片段来源；
③ 证据不足降级策略：如果现有材料不足以回答问题，禁止强行编造答案，统一输出 “当前知识库没有足够信息，请人工确认”；
④ 上线评估指标：增加 Faithfulness（忠实度指标）专门校验答案和原文是否一致。
面试标准四层排查框架（视频原话的答题分层，面试口述模板）
面试官问这道题，你按四层依次排查：
第一层：确认召回环节 —— 校验召回列表里，是否真的命中目标正确文档；（这一步是很多人只停留在这一层）
第二层：校验片段完整性 —— 就算文档命中，要看取出来的 chunk 切片有没有切断语义、丢失限定条件；
第三层：校验重排与证据优先级 —— 多条召回片段有没有冲突、权威正确的证据有没有被排在合适位置，有没有被无关 / 低优先级内容挤压、淹没在中间；
第四层：校验生成输出忠实度 —— 模型输出有没有脱离原文、混入内部知识产生幻觉，有没有遵守引用约束。

核心结论：RAG 调优不要一上来就换 Embedding、调 TopK 参数；遇到 bad case，保存完整请求快照，沿着链路一步步倒查，在哪一步内容失真，问题就归属在哪一层。
链路顺序（从前往后）：
用户原始问题 → Query 改写（查询扩展 / 问题重写） → 召回列表（topk 结果） → 重排打分 & 顺序调整 → 上下文拼装（chunk 拼接、截断） → 引用校验 + 模型生成最终答案
快照要求：每一次请求全链路信息持久保存：用户问题、改写后的 query、召回全部条目 + 相似度分数、重排分数、送入大模型的完整 prompt 上下文、模型输出答案、引用标记、知识库版本、权限标签、模型参数。
视频原话：同一个问题，知识库版本变了、权限过滤变了、上下文窗口大小变了，答案都会不一样，没有快照根本定位不了。
测试集建设方案（视频讲的三类测试样本，用于评估 RAG 链路）
想要验证这套链路稳不稳定，必须提前构造三类 Case 做自动化 + 人工评测：
类型 1：证据原文正确，但是文本容易被误读、有限定例外条款的样本（对应切片问题）
类型 2：多条召回证据互相冲突、新旧版本混杂的样本（对应重排优先级问题）
类型 3：证据缺失、材料不足以回答问题的样本（用来验证模型会不会拒绝回答，不强行幻觉）
配套评估维度清单：
召回命中指标
证据引用覆盖率
答案忠实度 Faithfulness
人工复核结果
上线抽检规则：
重点抽检高风险回答；审核页面并排展示【模型输出答案】+【原始召回参考片段】，专门抓一类最难发现的 bad case：文本看起来相关，但是结论越界、脑补延伸。
视频结尾总结结论汇总
RAG 是一条链式系统，失败点分布在全链路，检索只是第一环；召回成功 ≠ RAG 成功。
遇到召回正确但是答错，优先顺序：快照回放 → 按六步链路倒查 → 定位是切片 / 重排 / 生成哪一环 → 针对性修复；不要优先去调向量检索参数。
工程 RAG 和 Demo 玩具 RAG 最大区别：Demo 只看召回；生产 RAG 要管切片结构、证据优先级冲突、忠实性约束、全链路快照、持续评测。
