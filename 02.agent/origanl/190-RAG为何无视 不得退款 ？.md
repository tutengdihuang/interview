视频详细内容总结
该视频是一道大模型 / RAG 算法面试题讲解，题目：合同明确写 “不得退款”，但 RAG 系统却输出 “可以支持退款”，是什么原因、该如何解决。
核心观点：这道题不是单纯考察向量检索、相似度召回，重点考察企业级 RAG 对否定词、例外条件、条款适用范围、证据冲突仲裁的工程落地能力。只回答向量相似度，说明只做过 Demo，没有做过真实业务知识库，合同、政策类场景最大风险就是把 “禁止” 理解成 “允许”。
一、出错的根源
向量检索只判断文本话题是否相关，无法天然识别语义极性。文档里出现 “退款” 关键词，不代表政策是允许退款。
合同文本大量存在：不得、除非、仅限、另有约定这类限定词；如果文本切片（chunk）把否定词和主体条款切碎割裂，大模型拿到残缺片段，很容易忽略禁止约束，直接输出正向结论。
很多 RAG 故障不是检索没找到文档，而是关键否定、限定信号被切片破坏丢失了。
退款类业务有三个关键问题：能不能退、谁能退、什么条件 / 时间可以退，这三者往往分散在不同文档片段，不能靠单条片段回答全部问题。
二、企业级 RAG 三层处理思路（面试答题核心框架）
1. 证据极性识别（语义立场判断）
不能仅仅保存原文片段，需要解析条款的立场：该条款是禁止、允许、例外补充。
看到 “不得退款”，不能只提取 “退款” 概念，要把否定关系、被禁止的对象一起抽取保存。
本质：RAG 做的是文本理解，不只是词频、相似度检索。
2. 识别生效范围、元数据信息
企业知识库经常有多份文档：主合同、分公司补充协议、活动规则，版本、生效时间、适用业务主体各不相同。
不能只靠大模型猜哪份文档优先级更高；每条知识库片段要绑定：时间戳、版本号、适用主体、文档权威等级。企业知识库的痛点经常不是缺少资料，而是有多份看起来都合理，但互相矛盾的资料。
3. 冲突仲裁处理
当出现证据冲突，例如主合同写 “不得退款”，补充协议写特定场景可退款。
不能交给大模型自行脑补判断。系统要先依据文档权威等级、生效时间做规则层仲裁；输出答案时，要把冲突证据显性展示给用户。
工程化合规回答，不能输出主观结论，必须写明：依据哪一份文档、哪个版本、哪条条款得到结果，做到答案可审计、可复盘。
三、面试标准回答模板
我会先做合同条款解析，识别否定词、例外条件；再结合文档版本、权威等级做证据优先级排序；最终只基于可引用证据生成回答；一旦出现证据冲突，直接说明冲突点在哪里，禁止大模型自行编造业务规则。把 RAG 从简单文档检索升级为合规业务判断系统。
四、进一步优化的高阶回答（面试官继续追问时补充）
业务逻辑交给规则层，不全交给大模型：不让模型直接输出能不能退款，模型只负责识别条款类型（禁止 / 例外 / 补充），退款的最终结论交由规则层仲裁。
好处：出现错误时，可以定位是哪一步条款抽取出错，而不是全部把问题归罪给大模型。
区分默认规则和例外规则：合同中经常有 “默认不得退款，但 XX 情况除外”，系统要把默认项、例外项分开存储，防止模型把默认拒绝当成允许。
五、上线后的评测指标
不能只看最终问答正确率。针对合同类 RAG，需要单独统计：
条款识别正确率
冲突条款发现率
拒答准确率
边界判断类问题，不能简单合并成单一的整体准确率指标。

一、问题现象、错误根源（全部要点 + 例子）
向量检索的缺陷
向量检索只看语义相似度，只会找到话题相关的文本片段，无法天然识别语义的立场（证据极性）。文档里面出现 “退款” 关键词，不等于文档语义是允许退款。
高危限定词举例
合同文本高频危险词汇：不得、除非、仅限、另有约定。这些限定词决定业务结论。
切片（Chunk）是重要故障来源
如果文本切片切碎，把否定词和它约束的主体条款拆开；大模型拿到残缺片段，就会丢掉否定约束，输出和原文相反的结论。
视频原话：很多 RAG 失败，不是检索没有找到文档，而是上下文里面关键否定、限定信号被切碎丢失。
退款业务的分布式证据案例（重点例子）
退款业务有 3 个独立问题：能不能退、谁能退、什么时间 / 条件可以退。
这三个问题，答案往往分散在不同文档、不同片段，不是单一条片段就可以完整回答。
不能看到 “退款” 这个关键词，就直接判定为 “支持退款”；真正决定业务结论的是限定词、适用边界，而不是关键词本身。
举例场景：主合同写 “本服务开通后不得退款，除非平台连续故障 72 小时以上可以退款”。如果切片只切到后半句 “平台连续故障 72 小时以上可以退款”，丢掉前面 “不得退款” 主约束，RAG 就会输出可以退款。
二、企业级 RAG 三层核心处理框架（逐条完整展开）
第一层：证据极性识别（语义立场判断）
不能只存储原始文本片段；入库、解析阶段，要对条款做立场解析：区分这条证据是禁止动作、允许动作、例外补充说明。
看到 “不得退款”，不能仅仅提取 “退款” 概念；必须把否定关系、被禁止的对象完整抽取、保留下来。
本质结论：RAG 做的是文本理解，而不是简单词频、相似度检索。
第二层：识别生效范围，绑定元数据
企业知识库现实案例：同时存在多份文档，总部主合同、分公司补充条款、线上活动规则；不同文档拥有不同时间、不同主体、不同业务线。
视频原话：企业知识库最怕不是没有文档，而是有多份看起来都正确，但是互相矛盾的文档。
不能把全部文档丢给大模型，让模型自己猜哪一份规则优先。
每一条知识库片段，都必须绑定元数据字段：时间戳、版本号、适用主体、文档权威等级。
面试提示：面试回答这里不要只简单说加 metadata，要讲清楚元数据包含的业务字段，以及业务价值。
第三层：冲突仲裁处理
冲突场景示例：主合同写明不得退款；补充协议写明特定场景是可以退款。两份证据同时召回。
工程约束：证据冲突的时候，绝对不能交给大模型自行脑补、自行做判断。
处理流程：系统先依据文档权威等级、生效时间，在规则层完成仲裁；输出答案时，同时把冲突证据显性展示给用户。
工程化合规结论：真正业务可用回答，不能输出主观的 “我觉得可以退款”。
输出必须做到可审计、可复盘，要写明：依据哪一份文档、哪一个版本、哪一条条款得到当前结论。
