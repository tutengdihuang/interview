抖音视频《面试题：RAG 文档切片为何不能只按字数》详细总结
该视频面向 RAG 面试场景，核心讲解为什么 RAG 不能只做固定字数切片，以及生产环境下完整的文档切片落地思路，核心观点：切片要服务语义与文档结构，字数只能当兜底方案，切片质量直接决定检索能不能拿到完整证据，是知识库问答效果的关键。
一、面试坑点：只回答固定字数切分是错误答案
错误认知：觉得切片越小越好，或者直接固定 500 字机械一刀切。
固定字数切分的致命问题：容易把完整语义、完整概念从中间切断。
举例：合同条款，前半段写适用条件，后半段写违约责任；如果切片刚好切在中间，检索只召回后半段，模型不知道责任成立的前置条件，就会出现答非所问。很多 RAG 知识库回答出错，不是大模型能力问题，而是切片把证据切坏了。
二、生产落地的三大核心步骤
1. 尊重文档本身的结构，不同内容用不同切分逻辑
不能所有内容一套切分规则，标题、段落、列表、表格、代码块、FAQ 处理方式要区分：
标题：需要和对应的正文绑定在一起，不要把标题和所属正文拆开；
表格：完整保留行列含义，不要拆散表格；
代码块：尽量完整保留函数、类的边界；
如果破坏文档结构，召回出来的片段字面看起来相关，但关键上下文缺失，模型只能靠猜测回答。
2. 合理设计切片重叠度（Overlap），不可滥用
重叠的好处：解决切片边界丢失信息问题，比如上一个切片末尾解释名词，下一个切片直接使用该名词，重叠可以把关联信息保留下来。
重叠的弊端：重叠太大，向量库就会存入大量重复内容，召回结果数量看着多，但有效信息增量很低。
调参思路：不能写死固定重叠，要结合段落长度、主题密度，配合召回评估结果动态调整。
3. 切片完成后必须做评测，不能凭感觉配置
切片策略不是配置一次就永久生效，需要拿真实业务问题做测试，重点检查 3 点：
正确的证据片段是否能够被成功召回；
召回回来的切片是否包含完整答案信息；
噪声片段占比高不高。
如果文档类型发生变化，切片策略也需要重新评估适配。
三、面试标准回答模板
RAG 切片优先按照语义边界和文档结构做切分，固定字数切分只能作为兜底方案；生产环境中，需要处理标题‑正文绑定、表格、代码块等特殊结构，设置合理的切片重叠，并且配合召回效果评测迭代切片策略。

视频完整逐要点整理（含原话要点、全部例子、全部结论，不漏）
视频核心总起句：RAG 效果 70% 问题都出在文档切片（chunk）这一步；固定字数一刀切是很差的做法，不能作为主策略，只能兜底。
面试原题：RAG 文档切片为什么不能只按字数切？
一、错误方案：固定字数切分（暴力按字符 /token 切）
操作方式：设定固定长度（比如 500 字），到字数直接切断，不管句子、语义、章节、业务规则。
致命缺陷 1：会把一个完整语义单元从中间劈开
视频例子 1（合同条款）：条款前半段是【适用前提、触发条件】，后半段是【违约责任】。一刀从中间切开；检索只召回后半段，模型看不到前置条件，不知道这个责任在什么情况下才生效，输出半对半错、看起来有理但前提缺失的答案。
例子延伸：一句话本身被拆进两个不同 chunk，召回只拿到半句，模型信息残缺，无法理解。
致命缺陷 2：丢失文档本身的结构关系，标题、正文脱离
标题和它对应的正文被拆开；单独召回正文片段，模型不知道它属于哪个章节、哪个主题。
致命缺陷 3：特殊内容（表格、代码、列表）被撕碎
表格表头在上一个 chunk、数据行落在下一个 chunk，行列对应关系直接丢失；
代码块（函数、类）中间切断，代码语义断裂。
补充定性：按字数切只是实现最简单、工程最好写，但是语义层面不智能。
二、正确核心原则（视频第一条大结论）
✅ 切片优先以【语义边界、文档结构边界】作为切分依据；字数 / Token 上限只是约束上限，不是切分触发条件。
一句话标准：一个 chunk 尽量是一个独立、完整的语义单元，单独拿出来可以被理解。
三、分文档类型的切分策略（视频分 3 大类讲，全部例子）
类型 1：结构化 PDF / 文档（有目录、一级 / 二级 / 三级标题、加粗标题、编号 1.1、1.2 这种）
核心手段：版面分析
提取文档元信息：字号、加粗、字体、章节编号；交叉验证（字号 + 编号一起判断标题，准确率更高）
还原文档目录树（层级树）：一级标题→二级标题→正文叶子节点
切分规则：以目录树叶子节点作为 chunk 边界
配套要求：每个 chunk 带上完整路径元数据（所属章节、父标题）
例子：召回一段正文，元数据标记【第二章 2.3 退货规则】，模型知道这段内容的归属上下文
结论：结构化文档是最好处理的一类，优先跟着章节标题切，而不是字数。
类型 2：无结构文档（扫描件、排版混乱文档、标题字号和正文无差别）
基础朴素方案：相邻句子向量相似度判断，相似度骤降的位置就是话题边界，在这里切一刀。
朴素方案的两个原生缺点（视频明确列出）
缺点 A：只对比单句太敏感，句子之间正常语义波动也会误判切分，噪声大，乱切；
缺点 B：代词指代丢失（例子：“张三是 CEO，他上任后股价上涨”，两句拆开，第二句 “他” 不知道指代谁，向量语义不准）
工业优化方案 1（滑动窗口相似度对比）：不是单句对比，把一组句子打包成窗口，窗口和窗口算整体相似度，信号更平稳，降低误切。
进阶高阶方案（LlamaIndex 的 Late Chunk，视频点名）
做法：整篇文档先送入模型，全文读完生成全局感知的 token 向量，再基于全局向量找边界、切片；
优势：从根源消解指代、上下文关联问题；
代价：算力成本很高；适用场景：少量、高价值、高精度要求文档，不适合海量批量文档。
扫描件前置步骤：OCR 识别；版面混乱、分栏、批注、页眉页脚混杂的复杂页，可以调用多模态大模型看图识别版面，区分标题 / 正文 / 表格（成本更高，一般只用在关键页面）。
类型 3：表格、图片、流程图这类特殊内容（翻车重灾区，视频重点强调）
表格硬性规则：表格是原子单元，无论长短，绝对不能从中间切开
错误后果：表头和数据行分到两个 chunk，含义完全失效；
推荐存储格式：HTML > Markdown，保留行列结构，纯文本很容易丢失结构。
图片 / 流程图 / 趋势图：图片本身不能被向量检索
处理方式：多模态模型读图，生成一段结构化文字描述，把描述文本入库参与检索；原图本身不进向量库。
四、Overlap（切片重叠）的完整讲解（视频里的全部观点，无省略）
Overlap 是什么：后一个 chunk 的开头，复用前一个 chunk 末尾一小段文本。
作用：用来缓解【边界语义被切断】的问题；解决上一段末尾名词，下一段直接引用的边界断层问题。
视频明确警告：Overlap 只是缓解手段，不是根治方案，不能靠重叠去修复错误的语义切口。
Overlap 的弊端：重叠比例太大，向量库重复内容爆炸；召回结果重复多、有效新信息少，浪费检索额度、干扰排序。
调参结论：不要写死固定重叠，要跟着文档主题密度、段落长度、评测结果动态调整。
五、两种极端切片问题：切太碎 vs 切太大（视频对比）
切的太碎（小 chunk）
问题：条件、例外、指代、前后步骤被打散分散在不同 chunk；单独一条信息不全，需要同时召回很多片段才能拼出完整答案，召回难度上升。
切的太大（超大 chunk）
问题：一个 chunk 里面混杂多个无关主题；向量表达主题不聚焦；召回的时候带进来大量无关噪声，挤占模型上下文窗口，答案容易跑偏。
结论：不存在越大越好、越小越好；核心标准：一个 chunk 主题集中、语义自洽完整，同时不混入大量无关信息。
六、切片之后，视频提到的必要后置动作（很多人漏掉）
切片做完不是直接入库，要做召回评测迭代：
拿真实业务问题去测试；
校验三点：
正确证据片段能不能被召回；
召回的 chunk 里面，信息是不是足够完整回答问题；
无关噪声片段占比高不高；
结论：文档类型一变，切片策略、参数就要重新评估、调整。
七、视频最终面试标准答案（视频口述版本）
切片不能只按字数一刀切；优先依据文档结构、语义边界切，字数 / Token 上限只做上限约束；结构化文档用版面分析、标题层级切；无结构文档用窗口相似度或者 Late Chunk；表格、图表作为完整原子单元；合理使用重叠缓解边界问题，最后必须用真实业务问题做召回评测迭代。

大模型 RAG 不是通读全文再回忆；是【根据问题检索少量 chunk → 把 chunk 塞进上下文 → 基于 chunk 生成答案】。
