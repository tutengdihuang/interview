业务词典是把自然语言和企业真实业务对象对齐的桥梁。

4、词典字段与各字段含义（视频原文列出字段，字段释义为视频文本体现的用途）

- 术语名称：业务术语本身

【工程补充】

① 同义词表

仅维护「术语 ↔ 别名」一对一 / 一对多文本映射，不存储业务定义边界、适用场景、结构化计算口径。

反例：同义词表只能记录转化率 = 转化比率，无法区分增长转化率、销售转化率；命中“转化率”只会返回固定映射，不存在按团队 / 场景切换词义的能力，直接口径错乱。

② 直接堆 Prompt（把业务词条全部塞进上下文）

将业务术语描述文本直接写入系统提示词。

缺陷 1：存在上下文窗口上限，词条量大时溢出、LLM 随机遗忘部分词条；

缺陷 2：LLM 存在文本脑补、语义融合倾向，多条相似口径并存时，模型会随机挑选、混合口径，结果不可确定；

缺陷 3：Prompt 是静态文本，没有版本管理、生效时间、变更审计；词条更新需要全量修改 Prompt，历史查询无法回溯当时使用的口径。

反例：Prompt 同时写入 7 日登录活跃、30 日交易活跃两条描述，用户提问时模型可能随机选用其中一个，没有确定性路由。

③ 单纯向量检索（RAG 向量召回）

基于文本语义相似度召回词条描述文本。

缺陷 1：向量是模糊相似度匹配，没有结构化路由规则；语义相似度高 ≠ 当前业务场景适用；多条近似词条会批量召回，交由模型自主挑选，存在不确定性；

缺陷 2：召回结果是纯文本描述，无法结构化提取计算口径，不能直接驱动 NL2SQL / 指标引擎生成可执行查询；

缺陷 3：缺少结构化过滤条件，无法按用户身份、业务场景、数据源做前置过滤。

三者共性短板：都只处理文本层面的语义匹配；业务词典是结构化、带生效条件的元数据，同时供给 LLM 做语义解释 + 指标引擎做确定性指标路由，这是三者不具备的。

1. 三种方案的真实能力边界（纠偏）

同义词表：只存「术语↔别名」映射。真实短板不是“不能存口径”，而是它没有定义层——同一别名可挂多个词义，表结构天然单义，无法表达“转化率因团队而异”。

直接堆 Prompt：纠偏——Prompt 完全可以做版本管理（配置中心 + hash + 灰度）。真实问题不在版本，而在把“定义”写进自然语言后，模型以概率方式择义，无确定性路由；且词条量大时受上下文上限约束、易混淆。

向量检索：纠偏——向量库能存结构化 payload、能做 metadata 过滤（team/scene/valid 时间窗），能做前置筛选。真实问题也不是“存不了结构”，而是相似度召回是近似匹配，无法保证命中的词条口径与当前场景严格一致；召回后仍需规则层做确定性裁决。

核心结论：三者都在做“文本 / 相似度匹配”，缺的是结构化、带生效条件、可被查询引擎直接消费的口径元数据 + 确定性路由层。

2. 增长 vs 销售转化率（工程补充）

增长口径：分子 = 完成注册的独立用户数（去重主体 user_id）；分母 = 落地页访问的独立 UV（去重主体 user_id，按会话 cookie+user_id 归并）。同一主体去重：注册与访问均按 user_id 去重，防止同人多次访问虚增分母。归因窗：访问后 24 小时内完成注册计入（转化归因到该落地页会话）；cohort 按“访问日”建群。

销售口径：分子 = 成功成交的独立客户数（去重主体 customer_id，同一客户多单只计 1）；分母 = 有效商机线索数（去重主体 lead_id，去重后保留状态 = valid）。归因窗：线索创建后 90 天内成交计入该线索转化；cohort 按“线索创建月”建群。

实例：增长侧，7 月 1 日落地页 1000 UV（去重后），其中注册 120 人→转化率 12%；同日同一用户注册后被销售跟进，8 月创建线索、9 月成交→归销售侧“线索转化”，与增长侧数字互不抵消。关键：同一个人可同时是两套口径的分子，因为主体与归因对象不同，口径不互斥。

3. 多词条冲突的确定性选择与追问；身份≠授权（工程补充）

选择优先级：①词条生效区间内（现在时间∈[生效起，生效止]）→②scope 匹配（team = 用户所属团队 且 scene = 上下文场景标签）→③仅剩 1 条则采用；≥2 条仍有效→禁止自动取默认，必须追问。

追问实例：用户无团队标签问“本月转化率”→“检测到『转化率』存在两套口径：A 落地页访问→注册（增长 / 投放）；B 有效线索→成交（销售 / 商机）。请选择，或提供业务场景。” 身份标签与场景标签冲突时同样追问，不猜。

身份≠授权：身份（组织标签）只用于选口径；能否读数是另一件事，分三层校验——

检索层：按身份 / 场景过滤词条，属于词典路由，不控制数据访问；

工具 / 查询层：NL2SQL 生成 SQL 时，按用户身份注入可访问的 schema / 数据域范围；

数据库层：数据网关 / 数仓做行级与列级权限（row/column-level ACL），无权限直接拒查返回空，与词典无关。

4. 版本、生效起止、历史回放、缓存、审批回滚（工程补充）

版本：每次变更生成新版本号（v1.0→v1.1），旧版本不覆盖。

生效起止：每条词条带 effective_start/effective_end，支持未来定时生效；历史查询按“当时生效版本”回放。

修改时间：updated_at 与 effective 分离，编辑时间≠生效时间。

历史回放：每次问答持久化「词条 ID + 版本号」；回溯 N 月前结果用当时的版本口径，而非当前口径。

缓存：缓存键 =词典ID+版本号+生效版本（含 scope）；词条发布→按词条粒度失效该键，不全局清空；TTL 兜底。

审批回滚：编辑人提交→负责人审批→重大指标二次审批→通过才发布（草稿不可被检索）。发布后若出错，回滚到上一已发布版本并重新生成版本号，缓存随新版本失效；变更留痕（谁编辑 / 谁审批 / 前后 diff / 时间）。

5. 精简可执行流程 + 60 秒面试答案（工程补充）

流程：①用户提问→②NER 识别术语并召回候选词条→③按生效区间 + team/scene 过滤→④若唯一则采用，多条则追问→⑤取该词条结构化计算口径→⑥按身份限定 schema→⑦数据库权限校验→⑧生成并执行 SQL→⑨结果附带词条版本 / 口径 / 负责人标注。

60 秒答案：“企业词汇同词多义，且口径依赖团队、场景和数据源。纯文本 / 相似度无法保证口径正确，所以用业务词典承载结构化的定义、别名、适用范围和计算口径。运行时按用户身份与场景做确定性路由，多条有效词条时交互确认；身份只决定选哪套口径，数据读取权限在数据库层校验。词典带版本与生效时间，支持历史回放、缓存按词条失效、负责人审批回滚，从而保证口径可追溯、可治理。”

本轮工程复核结束。

### 整理者复核：第四轮仍有错误，不可直接当实施规范

- 同义词表并非“天然单义”；可以映射多个 sense_id，缺的是适用范围与裁决机制，不是表一定做不到。
- 销售分母 lead_id、分子 customer_id 不能无条件相除；需先定义线索转化还是客户转化，并固定同一 cohort 和去重粒度。
- 当前生效时间与历史回放基准不是一回事；版本区间使用半开区间，历史查询还需区分当时口径与当前口径重算。
- 检索阶段也需要元数据访问控制；工具入口需要实际授权，不能仅把权限写入模型上下文。数据库拒绝必须明确报无权限，不伪装空结果。
- 原始记录缺失的第二轮未重新取得；第三轮重复覆盖部分问题，第四轮补充其余问题。该记录不能宣称完整逐字对话导出。
