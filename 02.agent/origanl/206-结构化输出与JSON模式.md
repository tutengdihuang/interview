视频完整内容详细总结
该视频面向 AI、后端开发面试，讲解Structured Outputs（结构化输出）与 JSON mode的区别，核心不只是稳定性差异，而是大模型生产环境下的接口契约、工程落地问题，针对大模型结果入库、审批、工具调用这类强约束业务场景，从 5 个工程维度拆解实践方案，同时给出面试答题思路与线上踩坑经验。
一、面试题核心考点：JSON mode 和 Structured Outputs 的本质区别
很多人只回答 “结构化输出更稳定”，这个回答过于表面。
JSON mode：仅保证输出是语法合法、可解析的 JSON 文本，但不约束字段、类型、枚举值，模型可以随便新增、缺失字段，数组为空、枚举乱写都允许。早期开发常只在提示词写 “输出 JSON”，配合正则兜底，demo 可以跑通，但线上极易出现字段漂移、缺失，导致下游服务报错。
Structured Outputs（结构化输出）：强制模型严格遵守开发者定义的 Schema。
本质差异：JSON mode 解决的是语法合法；结构化输出解决契约匹配。大模型作为数据生产者，业务系统作为消费者，需要靠 Schema 建立契约，不能只依赖模型自觉，必须配套服务端校验、降级逻辑。
二、五大工程实践层面（视频主体内容）
1. Schema 设计层面
不要盲目堆砌字段，讲究合理拆分：
优先使用枚举、分层结构；业务必填字段和展示字段做分离。
举例：抽取工单风险，不要只返回一大段描述字符串，拆分为risk_level风险等级、evidence证据、action_required需要执行动作、confidence置信度结构化字段。
需要考虑：字段语义、默认值、可选字段；Schema 不要追求复杂，字段越多模型越容易漏输出。
最佳做法：先保证最小核心必填字段完成业务主逻辑；解释、展示、调试类字段放到第二层，兼顾业务执行与产品展示需求。
2. 失败兜底策略
即便开启严格 Schema，也不能假设每次请求都成功。线上失败的诱因包括：安全策略拦截、输出截断、用户原始输入信息不足、Schema 设计过窄导致模型无法表达。需要设计三类兜底方案：
可自动修复场景：重试重新请求；
信息不足场景：向用户追问补充信息；
高风险业务场景：直接流转人工处理，或者返回不可执行状态。
线上坑提醒：不要把校验失败全部归罪于模型，失败原因可能是用户输入缺信息、Schema 本身不合理、安全策略截断，要做好错误分类，不然只会盲目调提示词，根因得不到修复。
3. Schema 版本管理
结构化输出一旦被下游系统依赖，不能随意改动字段：
Schema 增加版本号，保留旧版本兼容字段；
上线新 Schema 需要灰度；
请求日志记录：使用的模型版本、Schema 版本、原始输入样本。
风险：升级模型之后，评测看着没问题，但字段、枚举、空值逻辑发生隐性变化，引发下游线上事故。
4. 和工具调用（Function Calling）区分
很多开发者会把两者混淆，二者定位不一样，可以组合使用，但不能混用：
结构化输出：用于产出业务结果数据（例如风控结论、抽取结果），侧重输出结果格式；
工具调用 Function Calling：用于触发外部动作（查订单、发起退款），侧重执行动作。
重要安全原则：不能让模型输出的自然语言直接执行业务动作；参数必须经过服务端参数校验、权限校验、执行状态管控之后，才允许执行操作。
5. 结构化输出的评测维度
不能只简单判断 JSON 是否解析成功，需要多维度评测：
类型正确率、枚举合法性、断句完整率；
业务一致性：字段语法合法，但是业务逻辑矛盾也属于不合格（例如风险等级和给出证据互相冲突）；
下游业务实际成功率。
上线前准备测试样本：脏输入、超长输入、信息缺失输入、边界用例，压测 Schema 的稳定性。
三、面试完整回答模板
“我会把 structured outputs 当成大模型和业务系统之间的契约层。首先定义最小可用 Schema，同时在服务端做强制校验、精细化错误分类。普通文本总结场景可以宽松处理；入库、审批、工具参数这类强约束业务，必须启用严格结构化输出。配套 Schema 版本号、原始样本回放、多维度评测，防止模型升级静默破坏下游业务逻辑。”

视频主题：大模型面试题 ——JSON mode 和 Structured Outputs 的区别与生产落地工程方案
视频核心立意：这道题不是考 API 参数记忆，是区分只会写 Demo、没上过生产的开发，和真正做过大模型线上业务的工程师；核心视角是模型作为数据生产者、后端业务系统作为消费者，二者之间的接口契约问题。
开篇引入（视频开头）
面试常见低分回答：只说 “Structured Outputs 比 JSON mode 更稳定，不容易输出错 JSON”。
面试官真实评判：这个回答很浅，没有工程落地思维，直接扣分。
视频总论点：二者本质差异，不是稳不稳，而是约束层级不一样；JSON mode 只管语法合法，Structured Outputs 管契约匹配。
适用业务场景前置说明：凡是结果要入库、走审批流、作为工具参数、下游服务强依赖输出字段的场景，都属于强约束场景，必须严肃对待结构化输出；纯文本总结、给人看的文案，属于弱约束场景，可以宽松处理。
第一部分：JSON mode 详细定义、能力边界、坑点、例子
JSON mode 的能力：只保证模型输出一段语法合法、可以被 JSON 解析器正常 parse 的 JSON 字符串。
JSON mode 不做任何结构约束：
不校验必填字段是否存在；
不校验字段类型是否正确；
不校验枚举值是否在指定范围；
不阻止模型自己新增没定义的字段；
不阻止数组为空、字符串返回数字、数字返回字符串。
开发常见 Demo 写法：提示词写一句 “直接返回 JSON，不要多余文字”，配合 JSON mode，再加正则简单兜底。
Demo 表现：简单输入、简单任务下，大概率能跑通。
线上真实问题（视频原话）：极易出现字段漂移、字段缺失、类型错乱，下游代码直接抛异常、服务报错。
举例：工单风险抽取场景，业务期待输出 {"risk_level":"high","evidence":"xxx","action_required":"review","confidence":0.85}
JSON mode 下，模型有可能返回合法 JSON：{"note":"这个工单风险较高，需要人工看一下"}
这段 JSON 语法没问题，可以正常解析，但是业务需要的 4 个字段全部缺失，下游代码读取 risk_level 直接报错。
结论：JSON mode 解决的问题只有一个：语法合法。它是 “尽力输出 JSON”，没有契约约束力。
第二部分：Structured Outputs（结构化输出）详细定义、能力边界、坑点、例子
Structured Outputs：提前传入开发者定义好的 JSON Schema，开启 strict 严格模式后，模型生成阶段就受 Schema 约束。
约束内容：字段名、字段类型、必填 / 可选、枚举取值、嵌套结构、数组结构、禁止额外字段（additionalProperties=false）。
本质：建立一份模型和业务系统共同遵守的数据契约。
重点提醒（视频反复强调）：结构化输出≠结果一定业务正确。
它保证：输出一定符合 Schema 结构，可以正常反序列化；
它不保证：模型判断、抽取、分类的业务语义是对的。
例子：同样工单风险抽取，模型可以严格按 Schema 返回 {"risk_level":"low","evidence":"材料齐全","action_required":"pass","confidence":0.9}；但原文证据明显是高危工单，模型判错风险等级。结构没问题，业务结论错误，这是另外一类问题。
对比一句话结论：JSON mode 解决语法合法；Structured Outputs 解决契约匹配。
配套强制要求：就算开了结构化严格输出，服务端依然必须单独做校验逻辑，不能信任模型输出。
第三部分：五大工程实践模块（视频主体全部内容，逐条拆）
模块 1：Schema 设计规范（Schema 怎么写，配套例子）
核心原则：不要上来就堆砌所有字段，优先拆分，必填核心业务字段 和 展示 / 解释 / 调试字段分离。
设计思路：优先保证最小核心字段，支撑主业务链路跑通；解释性、备注类字段放到第二层，可选。
推荐组件：优先使用枚举约束，而不是自由字符串；枚举可以极大降低下游解析成本，减少模型自由发挥空间。
工单风险抽取完整 Schema 示例（视频例子）
核心必填字段（驱动业务流转）：
risk_level：枚举，只能是 high /medium/low
action_required：枚举，只能是 manual_review /auto_pass/reject
可选展示字段（给人看、用于排查）：
evidence：字符串，风险依据原文
confidence：float，置信度 0~1
Schema 设计避坑点：
字段越多、嵌套越深，模型越容易出现问题；
需要提前定义字段语义、空值规则、默认值；
不要把所有信息都塞进一个大对象里；
Schema 设计结论：Schema 是接口契约，不是大杂烩；最小可用优先。
模块 2：失败兜底策略（线上失败分类 + 三类兜底方案，全部列清）
前置结论：哪怕开启严格 Structured Outputs，也不能假设请求一定成功；线上一定会失败。
失败根因分类（视频重点：不要全部甩锅模型）：
原因 1：安全策略拦截；
原因 2：输出被截断（max_tokens 耗尽）；
原因 3：用户原始输入信息不足，模型没有足够信息填充 Schema；
原因 4：Schema 本身设计不合理，约束过窄，模型无法表达真实结论；
原因 5：模型本身生成异常。
三类兜底方案，按场景匹配：
① 可自动修复场景：重试，带上上一轮的错误信息，告诉模型哪里不符合 Schema，重新请求；适合截断、小概率结构异常；
② 信息不足场景：不要强行让模型编造内容，返回标记，向上游追问用户补充信息；
③ 高风险业务场景（资金、审批、处罚）：禁止重试硬跑，直接流转人工处理，返回不可执行状态。
踩坑结论：只写一个无脑重试循环是非常粗糙的做法；不做错误分类，只会反复调提示词，找不到真实根因。
模块 3：Schema 版本管理（生产最容易被忽略、最容易出事故的点）
风险描述：Schema 一旦被下游系统依赖，它就是接口，随意改动字段等于改接口，会引发下游故障。
落地做法：
给每一套 Schema 增加版本号；
升级新 Schema 必须灰度放量；
日志里强制记录三样东西：原始用户输入、使用的模型版本、使用的 Schema 版本；
典型线上事故例子：模型版本升级，评测集上看 Schema 通过率没问题，但枚举偏好、空值逻辑悄悄变了；灰度没做，全量上线之后，下游消费逻辑静默出错，属于很难排查的隐性事故。
结论：Schema 和 API 一样，需要版本管理、兼容策略、日志回放能力。
模块 4：Structured Outputs 和 Function Calling（工具调用）区分，很多开发者混淆
一句话区分（视频原话）：
Structured Outputs：产出业务结果数据，拿到这个数据可以直接入库、展示、走审批、做统计；它是结果。
Function Calling：产出执行指令参数，意思是 “我想要调用某个外部工具”；它只是待执行的参数，不是最终业务结果。
二者可以组合使用，但不能混用定位。
安全红线（视频重点强调）：
绝对不能把模型输出的参数直接拿去执行业务动作。
完整执行链路：模型输出工具参数 → 服务端参数合法性校验 → 权限校验 → 幂等控制 → 才允许执行动作。
举例区分：
结构化输出：工单风险判定结果，直接存入工单表；
Function Calling：模型输出调用 “发起退款” 工具，附带订单号、金额参数；这个参数不能直接调用退款接口，后端必须二次校验金额、权限、订单状态。
模块 5：结构化输出的评测维度（不能只看 JSON 解析成功）
底层误区：很多团队评测只统计 “能不能正常解析 JSON”，这个指标只是最低门槛，不代表合格。
完整评测指标清单（视频全部列出）
指标 1：类型正确率；
指标 2：枚举合法性；
指标 3：输出完整率（是否截断）；
指标 4：业务一致性（最重要！结构合法，但是业务逻辑自相矛盾，判定为不合格）；
指标 5：下游业务实际成功率（最终指标，看下游链路能不能正常跑完）。
评测用例准备要求：必须覆盖脏输入、超长输入、信息缺失输入、边界 case。
例子：风险等级返回 high，但是 evidence 写 “材料齐全无风险”；JSON 完全符合 Schema，枚举合法，但是业务逻辑冲突，属于不合格样本。
结论：语法、Schema 校验只是门槛，业务语义校验才是评测核心。
