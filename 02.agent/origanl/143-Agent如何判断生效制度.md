视频详细内容总结
这是一道大厂大模型 / Agent/RAG 高频面试题：RAG 知识库召回同时出现新旧两版制度，Agent 如何判断哪一版真正生效。
核心观点：制度生效不能依靠语义相似度判断，是元数据、发布 / 生效时间、适用范围、废止替代关系共同决定的状态判断，需要构建「入库元数据管理→查询过滤→召回证据校验」完整工程闭环，不能只靠向量检索解决问题。
一、审题：面试官真正考察点
题目不是考向量检索，考察企业知识库工程落地：制度存在试行稿、过渡期、补充通知、废止替代等复杂业务状态，向量相似度无法区分文档实际效力；很多候选人只回答拿最新文档，会出现严重业务错误（财务、合规制度场景风险极高）。
二、完整工程方案（入库、查询、召回校验三阶段）
1）入库阶段：做好元数据治理（源头处理）
解析文档，还原文档标题、条款、表格、附件之间的关联关系；
对每一个知识切片（chunk）绑定完整元数据：文档 ID、页码、版本号、发布日期、生效日期、废止日期、适用组织、替代废止关系、权限标签。
注意坑点：不能简单以文件上传时间当作生效时间。上传最新的文档可能只是试行稿、补充通知，不等同正式生效制度，直接按上传时间选文档会出错。
2）查询阶段：元数据前置过滤，再做向量召回
解析用户问题，拆解出：主体、动作、业务条件、查询时间；
优先做元数据硬过滤：用生效时间、适用组织先筛掉不匹配的文档，再做关键词 + 向量召回；
好处：避免精确编号、时间条件、否定词被纯语义相似度淹没；业务口语、别名单独做查询改写。
业务案例：差旅制度存在发布日、正式执行日、废止日，中间存在过渡期，要识别这种特殊时间状态，不能一刀切取最新。
3）召回后：证据充分性与冲突裁决校验
召回多条片段不等于答案正确，校验证据是否覆盖用户问题全部条件；
出现新旧制度证据冲突时，裁决优先级：权威来源 > 版本生效状态 > 适用范围；
如果元数据对比后仍然无法判定，不能让大模型自行猜测，要执行兜底：向用户追问信息，或者直接拒答；
输出答案时，回答内容逐条绑定原文来源位置，做到答案可溯源。
三、问题排查定位思路
线上出现版本判断错误，不能简单让模型重新生成一遍：
完整留存日志：输入 query、系统配置、模型版本、每一步中间结果；
定位第一个发生错误的节点，再选择调整参数、重试、降级策略。
四、评测指标体系（面试必须提到，不能只讲方案）
要做多维度评测，分开统计：切片完整性、召回率 Recall、重排命中效果、引用准确率、输出忠实度。
做对照实验规则：固定输入、模型、数据版本，只改动一个变量，对比修改前后的正确性、延迟、显存 /token 成本、边界 case 表现。
同时链路需要可追溯：检索过程、工具调用、状态、最终答案全链路可查；证据不足要有明确的追问、降级、人工接管逻辑。
上线运维层面：
关键指标和知识库版本做时间线对齐；
故障后区分根因：是输入分布变化、配置改动、模型升级，还是外部数据依赖问题；
发现 bug 之后，把该 case 加入回归测试集，同时检查相邻业务，防止修复 A 问题，造成 B 场景退化。
五、面试答题的四段式回答模板
先给出核心判断结论：制度生效不靠语义相似度，由元数据、时间、适用范围、废止关系共同决定；
讲完整链路：入库元数据打标 → 查询元数据前置过滤 → 向量召回 → 冲突证据校验、答案绑定来源；
讲风险、坑点与边界情况：比如过渡期、试行稿、冲突无法自动裁决的兜底降级策略；
讲评测、运维方案：用什么指标验证方案好坏、线上异常如何排查处理。
拔高观点：企业 RAG 高级能力不是存储一份静态答案，而是每一次回答，都能够解释清楚为什么这条规则在当前场景下是生效的。

视频完整逐点整理（全部要点、例子、结论，无省略）
视频原题：面试官问：企业 RAG 知识库召回同时出来新旧两版制度，Agent 该判断哪一版生效？
主讲人：小哲讲 Agent 系列，核心主线：这道题不是考向量检索，考企业级 RAG 工程落地、制度版本治理、证据裁决
【开篇：题面拆解 + 面试官考察本质】
表象问题：向量相似度召回，新旧两份制度语义接近，embedding 打分差不多，一起被召回；大模型会自行融合文本，而不是按业务规则裁决效力。
面试官真正考察的不是 “怎么召回”，而是：
是否理解：制度是否生效，不能依靠语义相似度判断；生效状态是元数据、时间、适用范围、废止替代关系共同决定的业务状态。
是否清楚企业知识库的复杂现实：知识库里面会同时存在正式稿、试行稿、征求意见稿、补充通知、过渡期文件、旧版废止文件、子公司特殊规定。
避坑：绝大多数面试者的错误回答 —— 直接取最新上传的文档。这个答案在业务场景下会出合规、财务事故，是典型错误答案。
核心前置结论（视频开篇第一结论）：上传时间 ≠ 生效时间。一份后上传的文档，有可能只是征求意见稿、试行稿、补充说明，并不具备正式效力；更早上传的文档反而才是现行有效制度。
【第一大块：入库阶段（源头治理，视频重点）】
视频原话：版本冲突问题，根源在入库，不是靠 Prompt 和后处理能兜底修好的。
文档解析动作：不能直接 PDF/Word 粗暴切片。先还原文档结构：标题层级、条款编号、表格、附件、内部交叉引用关系。
切片规则（视频明确强调）：
禁止单纯按固定 token 长度一刀切切片；
制度类文档优先按标题、条款边界、表格边界切分；
每一个 chunk（知识切片），保留父章节路径、相邻条款摘要、上下文条件，防止单条条款断章取义。
每一个切片强制绑定全套元数据字段（视频列出全部元数据）
文档唯一 ID
切片 ID、页码、位置
版本号
发布日期（发文时间）
生效日期（正式执行时间，和发布时间可以不一样）
废止日期
文档状态枚举：草稿 / 征求意见稿 / 试行 / 正式生效 / 已废止
适用组织 / 适用范围：集团总部、A 子公司、B 部门、全员等
废止 & 替代关系：本版本替代哪一份旧文档；本版本会被哪一份新文档替代（双向关联）
权限标签：哪些角色、哪些用户可以查看这份制度
入库阶段结论：把业务规则变成可过滤、可比较、可排序的结构化字段，而不是埋在自然文本里让模型自己读、自己猜。
【第二大块：查询阶段（检索链路，顺序：查询解析 → 元数据硬过滤 → 向量 + 关键词召回 → 重排）】
用户 Query 解析：拆解用户问题里面的 4 类要素
主体：是谁（哪个部门、哪个员工）
动作：要办什么业务（报销、差旅、请假）
业务条件：金额、级别等
查询时间点：用户想问【什么时候适用的规则】（重点：不一定是今天，支持回溯历史规则）
第一步：元数据前置硬过滤（视频强调顺序：先过滤，再召回，顺序不能颠倒）
先用元数据做数据库层面过滤，把不符合条件的 chunk 直接筛掉，不送入向量检索；
过滤条件：用户身份权限、适用组织范围、查询时间是否落在【生效日期～废止日期】区间；
例子（视频核心例子：差旅报销制度）
差旅制度场景：发文日是 5 月 1 日，过渡期 5.1–6.1，6 月 1 日才正式生效；
用户 5 月 15 日来问，此时新制度还在过渡期，不能直接按新制度执行；
还有一种情况：新制度发文，但写明 “7 月 1 日起执行，7 月 1 之前仍然沿用旧制度”；
向量检索看不到这个时间边界，会把新旧都召回。
第二步：过滤之后，在剩余候选池里面做混合检索：关键词 BM25 + 向量检索
第三步：查询改写处理：用户口语化提问、别名、简称，单独做 Query 扩展改写，避免否定词、编号、专有名词被语义相似度淹没。
本阶段结论：元数据过滤是硬约束，向量召回只是语义补充；先缩小候选池，再做相似度匹配，减少冲突样本进入后续环节。
【第三大块：召回完成后：证据校验、冲突裁决、兜底策略（视频最长的一段）】
视频原话：召回一堆相似片段，不等于答案正确，召回只是拿到候选证据，证据要做校验和裁决。
证据充分性校验：检查召回的证据，能不能完整覆盖用户问题里全部条件；缺少必要条件，判定证据不足。
冲突裁决优先级（视频给出固定优先级顺序，不能乱）
① 权威来源优先级 > 版本时间
② 生效状态（正式生效 > 试行 > 草稿）
③ 适用范围匹配度（用户所属组织匹配优先）
④ 生效时间
举例：总部下发通用制度，子公司后续发布补充细则；用户是这个子公司员工，两份都命中，优先适用子公司细则，而不是单纯看谁时间更新。
冲突无法自动裁决的兜底规则（视频明确禁止的行为）
❌ 禁止让大模型自行脑补、自行选一个版本融合输出；
✅ 方案 A：向用户追问补充信息（你是哪个部门、问的是哪个时间执行标准）
✅ 方案 B：证据冲突且无法判定时，直接拒答，同时标注冲突来源给人工审核
输出生成阶段强制约束：答案可溯源
最终回答里，每一条结论，都绑定对应的原文切片来源：文档 ID、版本号、生效时间、页码；
输出答案附带引用列表；没有证据支撑的结论，不能作为确定结论输出，降低置信度标注；
视频原话：企业合规场景，答案可溯源，比回答流畅自然优先级更高。
【第四大块：线上故障排查思路（视频独立小节）】
线上出现 “模型拿出旧制度回答错误”，禁止简单操作：直接重新调用模型生成一遍。
标准排障流程：
完整留存全链路日志：原始 query、用户身份、查询时间、系统配置、模型版本、每一步中间结果（过滤掉了哪些、召回候选列表、重排结果）
定位第一个偏离预期的节点：
是文档解析切片错了？
元数据抽取打标错误？
前置过滤条件写错？
向量召回把不该进来的召回进来？
重排模型排序错误？
生成阶段 Prompt 约束失效？
定位根因之后再选择修复动作：修正元数据、调整过滤规则、调整重排、降级、人工接管
故障复盘闭环：修复 Bug 之后，把这个 Bad Case 加入回归测试集；同时检查相邻、同类业务文档，防止修复 A 问题，引出 B 场景退化。
【第五大块：评测体系（面试必须讲，视频单独拎出来）】
不能只看最终答案对不对，要拆分成多维度分开评测指标：
切片完整性指标：条款、条件有没有被切断、丢失上下文
召回率 Recall：有效证据有没有被召回
重排命中效果：正确证据能不能排在靠前位置
引用准确率：引用来源是否确实支撑结论
输出忠实度：模型有没有幻觉脑补超出原文内容
对照实验规范：做 AB 实验时，固定输入、固定模型、固定数据集版本；每次只改动一个变量；对比改动前后的准确率、延迟、Token 成本、边界 case 表现。
【第六大块：运维与版本生命周期管理】
知识库指标、文档版本变更、上线时间线对齐，方便事后回溯；
监控告警：监控过期文档被召回、冲突证据召回频次突增；
旧文档保留策略：废止文档不能直接删除索引，需要保留，用于支持历史业务查询（查去年报销适用哪个版本）；只是默认查询场景下被元数据过滤拦截；
权限校验两层：召回前元数据权限过滤，召回后证据二次权限校验，防止越权看到保密制度。
【第七大块：面试四段式标准口述模板（视频结尾直接给的答题模板）】
先抛核心结论：制度生效不能靠语义相似度判断，由元数据、生效时间、适用范围、废止替代关系共同决定；不能简单取最新文档。
讲完整链路：入库结构化元数据治理 → 查询解析、元数据前置过滤 → 混合检索召回 → 证据冲突裁决
讲坑点与边界 Case：过渡期文件、试行稿、子公司补充文件、冲突无法自动判定时的追问 / 拒答兜底
讲评测、日志、回归运维方案，证明你是落地视角，不是只懂向量检索。
【视频收尾升华结论】
企业级 RAG 知识库，高级能力不是存一堆文本、搜相似句子；而是系统每一次给出规则结论的时候，能够解释清楚：为什么这条规则，在当前用户、当前时间、当前业务场景下，是生效可用的。版本治理本质是知识的业务状态治理，不是检索问题。
