抖音视频《Harness 的五要素：除了 Context 和 Tools，还要懂什么？》详细总结
视频面向 AI Agent 面试、Agent 工程开发，纠正一个常见误区：很多人误以为 Harness 五要素是 Context、Tools、Memory、Plan，视频指出 Memory、Planning 属于 Agent 能力，不是 Harness 顶层要素。Harness 五要素为：Context 上下文、Tools 工具、Guardrails 约束、Evaluation 验证、Recovery 纠错。
核心概念：Agent = Model + Harness。大模型像爆发力强的野马，Harness 就是马具，是模型之外整套运行治理环境，用来约束、管控模型，让模型受控稳定工作。VILA‑Lab 对 Claude Code 源码分析发现：Claude Code 里 98.4% 代码都在实现 Harness，仅 1.6% 是 AI 推理决策逻辑。
一、五大要素各自职责
前两项解决 “能不能做事”；后三项解决 “做错事、做错了怎么办”。
Context（上下文管理）
负责模型能够感知哪些信息；组装 System Prompt、会话历史、技能描述、工具返回结果，维护运行状态。目标保证模型每次决策拿到高质量信息。
Memory 不是独立要素：记忆最终都是包装成上下文送入大模型。
Tools（工具调用）
负责 Agent 和外部世界交互；包含工具注册、Schema 定义、MCP 协议适配、工具实际执行。
Planning 不是独立要素：规划只是一种任务执行模式，落在上下文与工作模式层面。
Guardrails（约束 / 护栏）
定义模型不能做什么，拦截高危操作（删除文件、执行脚本、访问敏感资源），防止越权、模型失控、产生不可逆破坏。
重点：高危操作需要 HITL 人机审批；危险判定逻辑硬编码在 Harness 底层，不能交给大模型判断，避免提示词注入被绕过。
Evaluation（结果验证）
客观判断任务有没有真正完成，不能相信模型自己说 “任务完成”。要依赖外部客观物证，而不是模型自我输出。
Recovery（错误恢复 / 纠错）
模型出错之后如何处理：把报错信息给到模型做反思重试；多次失败触发熔断，必要时把任务交给人工接管。
二、工程落地：以 Claude Code 源码为例
1）Context 上下文如何解决上下文膨胀（Token 越来越长）
发送给 LLM 前执行 5 个阶段处理，优先用确定性规则，尽量少调用 LLM 做摘要（摘要耗 Token 还有信息损失）：
预算削减：给单条工具返回结果设置大小上限；
历史裁剪：直接删除老旧无用对话；
微压缩：清理旧的工具执行返回；
上下文折叠：读取时做虚拟投影；
自动压缩：调用大模型生成摘要（最后才用）。
2）Tools 工具的工程坑点
工具输出可能极其长（如 git log 几万行），会把关键系统提示、会话历史淹没。
工程方案：超长工具输出强制截断，防止工具返回把上下文占满。
3）Guardrails 安全实现
Claude Code 提供 7 种权限模式。auto 模式启用独立的 Sonn 危险分类器：
分类器只看工具名和入参，看不到主模型思考推理文本；
避免主模型推理话术诱导分类器放行高危操作。
4）Evaluation 验证落地
只认客观证据：进程状态码、语法树差异、单元测试断言等。
模型声称 “代码修复完成” 不作数，必须实际跑测试。利用 27 个 Hooks 钩子，工具执行完成后先走 PostToolUse 钩子执行校验逻辑。
5）Recovery 纠错实现
清洗报错堆栈，过滤噪音，只保留定位问题的关键信息回填上下文，让模型看到真实错误；
重试上限最多 3 轮；
Token 用尽、上下文爆满时，先做折叠、压缩；还不行直接终止任务。
三、核心总结
Context、Tools 是 Agent 基础能力，让 Agent 可以干活；
Guardrails、Evaluation、Recovery 共同构成 Agent 的安全边界，保障生产环境稳定可控；
生产级 Agent 大量代码不是写 AI 推理，而是写 Harness 治理逻辑。

视频标题：Harness 的五要素：除了 Context 和 Tools，还要懂什么？
核心立论前置、误区纠正、定义、案例、分要素工程细节、底层结论、面试 / 落地观点全部按视频顺序整理。
一、开篇总起 + 核心定义（视频最开头）
大众普遍误区：很多讲 Agent 的材料会把 Memory 记忆、Planning 规划 列为 Agent 顶层要素；本视频明确：Memory、Planning 不是 Harness 顶层独立要素。
核心公式：Agent = Model + Harness
Model：负责推理、思考、决策，是 “脑子”；
Harness：模型之外，整套用来管控、运行、约束 Agent 的治理运行环境；
比喻：大模型 = 爆发力极强但是不受控的野马；Harness 就是马具（缰绳、马鞍、笼头），作用是把野马约束在可控轨道里奔跑。
核心调研案例来源：VILA-Lab 对 Claude Code 源码做了完整拆解统计
Claude Code 总代码约 51.2 万行 TS 代码、1884 个文件；
98.4% 的代码全部属于 Harness 脚手架 / 治理逻辑；
仅仅只有 1.6% 是大模型本身的决策推理逻辑；
结论：生产级 Agent 的工程重心根本不是写模型调用，而是写 Harness。
Harness 五要素清单：Context 上下文管理、Tools 工具调用、Guardrails 护栏约束、Evaluation 结果验证、Recovery 错误恢复
分组逻辑：前两项：解决 Agent 能不能干活；后三项：解决 Agent 做错、失控之后怎么办。
二、逐个要素完整拆解（视频逐项讲解）
1. Context 上下文管理
职责定义：决定模型每一轮思考能够看到、感知到哪些信息；负责信息组装与会话状态维护。
组装内容：System Prompt 系统提示词、历史对话轮次、Skill 技能描述、上一轮工具返回结果、任务状态。
目标：保证每一次给到模型的输入信息是高质量、够用、不冗余的。
视频关键判断：Memory 记忆不属于顶层要素
所有记忆（短期、长期、跨会话记忆）最终都要被包装、转化成一段上下文文本，塞进发给 LLM 的消息流里面；记忆只是上下文的一类数据源，不是独立组件。
工程痛点：上下文膨胀（token 持续变长，越跑越贵、越跑越容易失真）
Claude Code 落地方案：5 阶段上下文缩减流水线，优先级原则：优先用确定性规则裁剪，能不用 LLM 摘要就不用摘要（摘要本身消耗 token，还会丢失关键信息），顺序严格从前到后：
预算削减：给每一次工具返回结果设置 token 上限，单条工具输出不能超限；
历史硬裁剪：直接删除老旧、不再相关的对话轮次；
微压缩：清理已经完成、不再需要回看的旧工具返回原始输出；
上下文折叠：虚拟投影，原始数据保留，但不全部送入模型，按需读取；
模型自动摘要：兜底手段，只有前面 4 步做完还超限，才调用 LLM 做摘要压缩。
2. Tools 工具调用
职责定义：负责模型和外部真实世界交互，把模型的文字意图变成真实动作，拿到外部反馈。
包含模块：工具注册、工具 Schema 定义、MCP 协议适配、工具调度、工具执行、结果回传。
视频关键判断：Planning 规划不是顶层 Harness 要素
任务拆解、分步规划只是一种执行模式；规划文本本质是写入上下文交给模型，属于 Context 的内容，不是独立 Harness 组件。
典型工程坑点（视频重点举例）：
工具返回输出体量巨大（比如 git log、完整代码库、日志，几万字符），会直接淹没系统提示、关键历史，挤占有效 token，让模型看不到核心指令。
工程解法：超长工具输出强制截断，截断策略写死在 Harness 层，不由模型控制。
3. Guardrails 护栏 / 约束（安全红线层）
职责定义：明确划定模型绝对不能做什么，拦截高危、不可逆、越权操作。
需要拦截的典型高危操作例子：删除文件、无限制执行 shell 脚本、读取密钥 / 敏感配置、高危 git 强制推送、修改系统文件。
两条铁律（视频反复强调）：
高危操作必须触发 HITL 人工在环审批（Human-In-The-Loop）；
危险判定逻辑硬编码在 Harness 底层，绝对不能交给大模型自己判断；
理由：大模型容易被提示词注入、诱导、话术欺骗，让模型自己判断是否危险 = 防线失效。
Claude Code 落地：7 种权限模式 + 独立 Sonn 危险分类器（auto 模式启用）
7 个权限模式：plan、default、acceptEdits、auto、dontAsk、bypassPermissions、bubble；
plan 模式：只生成方案规划，完全不执行任何动作，全部等用户审批；
default（manual）：绝大多数写文件、跑命令动作都需要手动确认；
acceptEdits：仓库内文件编辑自动放行，bash 脚本仍然要人审批；
auto 模式：由独立 Sonn 分类器做安全判断；
Sonn 分类器的隔离设计（视频重点）：
分类器只能读取工具名称、入参，看不到主 LLM 的思考推理文本；
目的：防止主模型用内部思考话术哄骗、诱导分类器放行高危操作。
权限判断是多层优先级规则链：组织策略 > 命令行参数 > 功能开关 > 项目配置 > 用户本地配置 > 当前会话临时规则。
4. Evaluation 结果验证
核心观点（视频重点结论）：绝对不能相信模型自己说 “任务完成了”，模型会自我欺骗、幻觉式宣告完工。
职责定义：用外部客观证据，独立判断任务是否真的达成目标；是一套独立于主模型的校验机制。
判定依据，只认客观物证（举例）：进程退出状态码、单元测试断言结果、代码语法树 diff、编译是否报错、文件变更快照、接口返回码。
Claude Code 实现：27 个生命周期 Hook 钩子系统
分为两大类钩子：5 个安全类钩子、22 个流程编排 / 生命周期钩子；
典型：PostToolUse 钩子，每次工具执行结束之后，先走校验钩子执行 Evaluation 逻辑，再把结果给到模型；
校验失败 = 判定任务未完成，进入 Recovery 分支。
5. Recovery 错误恢复 / 自愈纠错
职责定义：当校验失败、工具报错、执行异常之后，定义重试、反思、熔断、人工接管的闭环策略。
三步处理流程（视频完整顺序）：
报错清洗：过滤堆栈里无关噪音，只保留能定位根因的关键报错信息，整理之后回填到上下文，给模型用来反思；
有限重试：有严格上限，Claude Code 最多重试 3 轮，不允许无限循环重试消耗 token；
熔断兜底：
重试次数耗尽 → 终止或者转人工；
token 耗尽、上下文塞满、压缩折叠策略全部失效 → 直接熔断停止任务。
三、视频里的横向对比：普通 Prompt Agent vs Harness 工程化 Agent
Prompt & Pray（提示词祈祷模式）：只靠 System Prompt 写一堆规则，把安全、校验、边界全部交给模型自觉；约束是概率性的，容易被绕开、幻觉、失控；
Harness 工程模式：确定性规则优先，校验独立、权限硬隔离、有熔断上限；约束在系统层面，不是靠模型 “听话”。
四、视频补充的几个关键推论 & 落地结论（收尾总结）
Context + Tools = Agent 的基础能力，保证 “能动”；Guardrails + Evaluation + Recovery = 稳定性底座，保证 “可控、可验证、出错不会崩盘”；
Planning、Memory 是 Agent 内部能力，是跑在 Context 里面的业务逻辑，不属于 Harness 顶层五要素；这是本视频和很多网上资料最大分歧点；
大模型能力越来越强的时候，模型本身的差异会收敛；最终区分生产 Agent 好坏的核心，是 Harness 工程质量，不是模型本身；
一个标准 Agent 循环链路（隐含在讲解中）：
模型决策 → Harness 权限检查 Guardrails → 调用 Tools → 拿到返回 → Evaluation 校验 → 通过则结束；不通过进入 Recovery 重试 / 熔断。
五、视频隐含的面试考点（视频旁白专门点出来，面向 Agent 面试）
面试官问 Harness/Agent 架构，如果直接说五要素是 Context、Tools、Memory、Plan、Safety，就是错误；正确答法：五要素是 Context、Tools、Guardrails、Evaluation、Recovery；Memory 和 Plan 是内部能力，由 Context 承载。
