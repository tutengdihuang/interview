1、为什么要做请求去重（不要只回答“防止扣费”）

大模型接口推理耗时很长，容易出现：用户疯狂连点按钮、页面刷新、网络超时自动重试，导致同一个任务被反复调用。

① 成本层面：防止重复调用模型带来重复扣费、浪费算力；

② 业务副作用（重点，面试加分）：尤其 Agent 场景，重复执行会出现重复发消息、重复建工单、重复写数据库，破坏业务数据一致性，不只是体验问题；

③ 用户体验：保证返回结果稳定，避免多条重复输出。

普通查询重复只是浪费资源；Agent 带工具调用的写操作，重复执行会直接搞脏业务数据。

2、工程实现方案：幂等键（request_id /idempotency_key）

客户端发起请求时带上唯一幂等 key；

后端拿到 key 先查任务状态：

如果任务正在执行：不再新建模型调用，直接返回「执行中」状态；

如果任务已经完成：直接返回已经生成好的旧结果，不再重新跑大模型。

3、面试高频踩坑点（加分回答）

不要拿请求文本字符串相似度做去重；判断重复必须依靠外部传入的唯一任务 ID（幂等 key）。

用户修改输入内容，就算文本很像，也是全新任务，不能被错误去重拦截。

4、面试标准答题话术

“大模型请求做请求去重，目的是防止重复生成、重复扣费，规避 Agent 工具调用带来的各类重复业务副作用。线上生产系统应当使用幂等 key 绑定任务状态做管控，而不是用户每点击一次就调用一次大模型。”

面试官问你：大模型应用为什么要做请求去重，而不是用户点一次就跑一次？如果你回答“防止重复扣费”，只说到一部分。

大模型请求通常很慢，用户可能连续点击、刷新页面、网络自动重试。如果后端不做去重，同一个任务可能被重复执行好几次。

我是小哲，点赞收藏加关注，我们马上开始！

先给结论：大模型请求去重，是为了控制成本、避免重复副作用，并保证用户看到稳定结果。

普通查询重复一次，最多浪费一点资源。但如果是 Agent 任务，重复一次可能会重复发消息、重复创建工单、重复写入数据库。这就不是体验问题，而是业务一致性问题。

怎么做比较稳？客户端提交任务时带一个 request_id 或 idempotency_key，后端发现同一个 key 已经在执行，就不要再创建新任务，而是返回原任务状态。如果原任务已经完成，就直接返回已有结果。

还要区分“相同请求”和“相似请求”。同一个用户连点按钮，可以去重；但用户改了输入内容，就不能因为文本相近而强行合并。去重依据应该来自明确的任务 ID，而不是简单比较 prompt 字符串。这点面试里说出来很加分。

所以这题你可以这样答：大模型请求要做去重，是为了防止重复生成、重复扣费，规避 Agent 工具调用带来的各类重复业务副作用。线上生产系统应当使用幂等 key 绑定任务状态做管控，而不是用户每点击一次就调用一次大模型。
