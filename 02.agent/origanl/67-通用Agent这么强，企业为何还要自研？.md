视频《通用 Agent 这么强，企业为何还要自研？》详细总结
视频核心议题：市面上已经有豆包、扣子等能力很强的通用 Agent，还可以通过 MCP 协议对接企业内部系统，为什么很多企业依然要自研 Agent，这也是面试、架构设计、企业老板经常会提出的现实问题。
1、通用 Agent 看似好用，但业务关键流程存在可靠性硬伤
视频举了差旅费报销的业务案例：
通过 MCP 把报销系统 API 开放给通用 Agent，理论上 Agent 就可以提交报销表单。但真实报销业务逻辑非常复杂：发票查重、大额金额二级审批、校验月度预算余额、驳回原因通知等一堆业务规则。
即便把全部业务规则写到 MCP 工具描述里面，简单场景可以跑通，但大模型是概率模型，不是确定性程序：一万笔报销里，哪怕 99% 执行正确，1% 出错就会产生上百笔业务故障，可能跳过发票查重、流程顺序错乱，甚至导致无法付款；同样输入，大模型这次走对流程，下次可能出错，结果不可控。
核心矛盾：企业核心业务（报销、审批等）要求 100% 确定执行，而通用 Agent 的大模型天生带有概率不确定性，不能直接拿来跑关键业务。
2、正确的业务架构思路：确定性 Workflow 为主，Agent 做辅助
针对报销这类高准确度要求场景，不能完全交给 Agent：
Workflow 工作流才是主体：用传统代码写死完整业务流程，覆盖全部业务分支，严格确定性执行，保证业务不出错；
Agent 只做辅助环节：只交给 Agent 处理每笔情况都不一样的部分，利用 Agent 做意图识别，判断业务该触发哪一套固定 Workflow。
通用 Agent 的短板：没有企业私有业务上下文，缺少可控的决策机制，很难做到生产级可靠，这就引出企业自建 Agent 的必要性。
3、企业自研 Agent 重点不是重复造底层轮子，而是三大工程建设
直接拿开源 Agent 框架简单改改、加 Function 调用、删减功能，解决不了业务可靠性问题。自研 Agent 的工作量集中在三项工程：上下文工程、工具工程、防护 / 边界工程。
① 上下文工程（不是简单写一段提示词）
编写 System Prompt：定义 Agent 角色、业务规则、行动边界；
设计 Few‑shot 示例：给 Agent 业务样例，教会它企业内部业务如何判断；
上下文窗口管理：对话过长时做信息取舍、信息压缩，管理内存窗口。
这是一套需要反复调试验证的工程实践，不是简单写一段文字。
② 工具工程、安全边界工程
管理 Agent 调用的工具、接口，划定安全红线，限制 Agent 哪些操作绝对不能执行。
4、哪些部分不用自研？
React 循环、工具调度这类底层基础框架能力，企业完全可以直接复用现成开源框架，不需要从零造轮子。
真正需要投入人力成本的，是上面提到的上下文、工具、安全边界等面向企业业务的定制工程。
5、视频最终结论
通用 Agent 适合简单场景，但企业核心生产业务，不能依赖大模型概率输出；
业务主干靠确定性 Workflow 代码保障正确性，Agent 负责意图识别、分支判断这类灵活部分；
自研 Agent≠全部从零开发底层，底层框架拿来用，把重心放在业务适配的三大工程；
通用 Agent 缺少企业私有上下文和可控决策，想要生产可用，自建 Agent 是很多企业的现实选择。

《通用 Agent 这么强，企业为何还要自研？》完整逐条拆解（原文全部要点、案例、观点、结论无省略）
视频讨论的问题：市面上通用 Agent 能力很强，还可以 MCP 对接企业内部系统，为什么很多企业仍然选择自研 Agent。该问题既是面试高频题，也是高级开发、架构师、企业管理者（老板）会面对的现实拷问。
一、视频开篇提出的现实现象
市面上成熟通用 Agent 举例：豆包、扣子、codex、workbody。
通用 Agent 能力表现：能力强大；通过 MCP 协议就可以对接公司内部业务系统；给 Agent 下发指令，它就能够调用各类企业内部数据。
抛出核心疑问：既然通用 Agent 已经可以做到这些，为什么企业还要投入资源自己开发 Agent？
问题受众：面试会提问；高级开发、架构师工作中绕不开；属于老板的灵魂拷问。
二、业务案例：差旅费报销（视频唯一业务示例，完整细节）
理想情况（Demo 层面能跑通）
使用通用 Agent 搭配 MCP 协议做差旅费报销：MCP 把报销系统的 API 对外暴露，大模型 LLM 直接调用 API 提交报销表单，看起来任务就完成了。
真实业务下的复杂现实条件（报销真实业务约束）
真实报销业务远不止 “提交表单”，必须同时处理下面全部业务逻辑：
校验发票是否重复提交；
金额达到 5000 元，必须触发二级审批流程；
校验该员工本月差旅费预算剩余额度；
报销申请被驳回后，要把驳回原因告知申请人。
尝试补救方案：把全部业务规则写进 MCP 工具描述
操作：在 MCP 的工具描述中写清楚每一步操作，第一步做什么、第二步做什么。
效果：简单流程场景确实可以跑通 Demo。
根本缺陷：LLM 是概率模型，不是确定性程序
统计举例：一万笔报销处理，哪怕 99% 都遵守业务流程，依然会有 1%（100 笔）出现故障；
故障具体表现：跳过发票查重、业务执行顺序颠倒；最坏情况直接导致财务无法付款；
复现不稳定：完全相同的输入，大模型这次执行正确，下一次执行就可能出错；
总结现象：整套业务执行结果具备不可靠性，不能用于生产业务。
三、视频给出的正确架构思路：确定性 Workflow 为主，Agent 为辅
针对报销这种对结果准确性要求严苛的业务场景，不能完全交给 Agent 处理。
Workflow（工作流）才是业务的核心主体程序
实现方式：用传统代码穷尽全部业务场景，硬编码写死业务逻辑；
特性：严格确定性执行，一步都不能出错，保障业务结果可靠。
Agent 只负责特定类型环节，不接管完整业务
Agent 适用场景：每一笔业务情况都各不相同的场景；
Agent 的职责：做意图识别，判断当前业务应该去触发哪一套已经写好的 Workflow 工作流。
为什么这部分场景倾向自建 Agent：
通用 Agent 不具备企业私有业务上下文；
通用 Agent 缺少可控的决策机制；
如果要达到生产环境可用的可靠程度，往往要做自建 Agent，需要落地三类工程：上下文工程、工具工程、Garros 工程。
反面现实：简单拿开源 Agent 框架做轻度改造，仅仅固定一部分上下文、增加 Function 调用、屏蔽部分不需要的功能，无法达成生产可靠性目标。
四、详细拆解三大工程（自研 Agent 真正要投入精力的地方）
1. 上下文工程（重点强调：不是简单写一段 Prompt 文字，是一套工程实践，需要反复试错调优）
包含完整工作项：
编辑 System Prompt：定义 Agent 角色、业务规则、Agent 行动边界；
设计 Few‑shot examples（少样本示例）：提供业务样例，教会 Agent 在本企业业务下如何做业务判断；
上下文窗口管理：对话上下文变长之后，确定哪些信息保留、哪些信息丢弃，何时做上下文压缩。
定性：这不是写一段话的工作，是完整工程实践，需要反复试错迭代。
2. 工具工程
对 Agent 可以调用的工具、接口进行完整管控治理。
3. Garros 工程（安全边界工程）
给 Agent 划定安全边界，管控风险，限制 Agent 哪些操作绝对不允许执行。
五、明确区分：哪些需要自研投入，哪些不需要重复造轮子
不需要自己从零开发（直接复用现成框架）
React 循环、工具调度等 Agent 底层基础能力，可以直接使用现成框架，不需要重复造轮子。
真正要花钱、投入人力精力的部分
上下文工程、工具工程、安全边界 / Garros 工程，这些业务适配层面的工作，更多依靠自建 Agent 来落地解决。
六、视频全部最终结论（逐条原文观点）
即便 MCP 可以打通系统，通用 Agent 受限于大模型概率属性，在企业核心业务上天然存在不确定性风险；
高可靠业务不能把全部业务交给 Agent；业务主干交给确定性 Workflow 代码保证正确性，Agent 只承担意图识别、分支判断这类灵活部分；
企业自研 Agent ≠ 全部底层从零造轮子，底层运行框架可以直接复用；核心工作量是面向企业业务做上下文、工具、安全边界三大工程；
通用 Agent 缺少企业专属业务上下文、可控决策机制；要做到企业生产环境可用，自建 Agent 是很多企业的现实选择；
简单修改开源 Agent 框架、加 Function 调用，不足以支撑企业真实业务生产要求。
