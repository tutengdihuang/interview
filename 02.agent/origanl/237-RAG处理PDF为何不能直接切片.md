三类 PDF 各自的坑
原生文本 PDF
不能只抽文字，要保留页码、标题层级、章节、列表、表格边界。否则问 “第二章的适用范围”，召回文本却不知道属于哪一章。

表格 / 图文混排 PDF

面试题：RAG 处理 PDF，为什么不能直接导出纯文本、按字数硬切片？
很多新手做 RAG，拿到 PDF 第一件事：提取全部文字，固定长度切 chunk，丢进向量库。
这个方案在 Demo、纯文字单栏简单文档里能跑通，但生产级业务绝对不能这么干。面试官听到这个答案，就知道你只跑过 Demo，没碰过真实企业文档。
PDF 本质是版式描述文件，不是结构化文档。
Word 保存的是逻辑结构：标题、段落、表格。PDF 存的是坐标指令：在 x,y 位置画什么文字。
文字在 PDF 内部是一堆散落的带坐标的字符碎片，顺序不一定连续；双栏论文、合同、报告直接抽取文本，会出现左右栏文字交叉错乱，语义直接废掉。
表格在 PDF 里只是线条 + 零散文字，没有 “表头 - 单元格” 的关联关系。
业务 PDF 分三类，各自有坑：
原生文本 PDF（可复制文字）
直接导出纯文本会丢失：章节层级、标题、页码、阅读顺序、列表、表格边界。
一旦丢失结构，当用户问 “第二章的适用范围”，召回的文本片段不知道属于哪个章节，没法溯源出处，也无法做引用。页眉、页脚、页码、水印会混进正文，变成无效噪声。
扫描件 PDF（图片版 PDF，纸质扫描生成）
页面本质就是图片，没有文本层。直接提取文字是空的，必须 OCR + 版面分析。
版面分析用来区分标题、正文、图片、表格、页眉页脚；OCR 识别错字、串行会直接污染切片，后续 Embedding 和召回全部受影响。
图文混排、带复杂表格 PDF
企业文档里的核心信息大量放在表格：参数、价格、审批条款、规格清单。
暴力导出纯文本再硬切片，表头和对应单元格直接断开，数据对应关系丢失。
正确做法：把表格识别出来，转为 Markdown/JSON 结构化格式，再参与切片。
生产级完整链路
第一步：文档分流路由
先判断文档类型：原生文本 PDF / 扫描件 PDF / 图文混排复杂 PDF。
原生 PDF：提取文字 + 版面信息，保留层级、页码、坐标；
扫描件 PDF：OCR + 版面检测，区分图文、表格；
含大量表格：表格结构化解析。
第二步：切片策略，禁止固定字数硬切
按文档结构 + 语义单元切片。
以章节、段落、完整表格为边界，保证单个 chunk 语义完整；跨页表格、大图单独处理，不要强行截断。
第三步：元数据（metadata）必须随 chunk 一起入库
文件名、文档版本、生效时间、章节名、页码、文本坐标、表格编号、文档访问权限。
元数据的作用：
① 答案可以附带原文页码来源，支持溯源；
② 过滤过期版本文档；
③ 权限过滤，防止越权召回涉密内容。
第四步：检索与生成
向量检索 + 关键词检索混合召回，配合重排；生成答案时强制引用召回片段的元数据出处。
核心结论
RAG 的瓶颈很多时候不是向量检索，而是文档解析。
垃圾输入，垃圾输出。PDF 处理不是简单格式转换，是多模态文档理解流水线。
如果第一步解析把文档结构、出处、表格关系破坏，后面 Embedding、向量检索、大模型生成再强，答案依旧不可靠。
面试完整版回答（可直接背诵）
PDF 不能直接导出纯文本并按固定字数硬切片。PDF 是版式文件，存储的是文字坐标，不是段落结构。
业务场景里 PDF 分为原生文本 PDF、扫描件 PDF、图文混排 / 带表格 PDF。原生 PDF 直接提取文本会丢失标题层级、页码、阅读顺序；扫描件没有文本层，需要 OCR 加版面分析；业务表格直接转文本会丢失表头与单元格的映射关系。
工程上，首先要对文档分流处理；原生文档保留结构与页码，扫描件做 OCR 版面分析，表格转为 Markdown 等结构化形式。切片不能固定字数硬切，需要基于文档结构和语义单元切分。每个切片入库时附带元数据，包含文件名、版本、章节、页码、权限等信息。
这套链路保证召回内容可溯源、过滤过期和无权限文档。PDF 解析是 RAG 的地基，解析质量直接决定最终答案可靠性。
