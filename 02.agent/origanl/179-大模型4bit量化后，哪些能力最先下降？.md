一、对这道面试题的底层解读
题目的假象与真实考点
表面是问量化会损坏模型哪些能力；本质考察低成本部署之后的任务验收、系统闭环能力。面试官希望听到：数据来源怎么确认、异常状态怎么识别、失败如何兜底、结果如何验证，而不是单纯罗列名词。
真实项目现象：很多线上故障，看上去是模型变笨，实际是评测没有分层、工具链路、上下文、权限流程出问题，不完全是模型本身问题。
答题总原则
4bit 量化不能只看通用评测分数，要重点验收：结构化输出、工具调用、长上下文、数学、代码、边界样本。
举业务例子：客服 Agent 日常聊天对话表现正常，但是工具调用参数会出错，比如写错金额单位、遗漏必填字段。普通对话能力完好，工程执行类能力先变脆弱。
答题要遵循三步：说明问题本质 → 讲架构设计思路 → 异常场景如何停机、排查、补救，体现是做线上项目，不是跑 Demo。
二、4‑bit 量化后能力退化四层顺序（从最先受损到后续受损）
第一层：结构化输出（入口可靠性，最先出问题）
结构化输出是整个 Agent 系统的入口，一旦格式、字段出错，后续流程全部建立在错误数据之上。
工程注意点：要记录输出字段、数据来源、版本、权限、时间，不能完全依靠模型从自然语言猜测提取信息。
高频踩坑：把 “工具调用返回成功” 等同于 “业务执行成功”；把信息相关当成信息充分可用。
第二层：工具调用（系统执行能力）
决定 Agent 能否形成可复现、可追溯的业务流程。
答题不能只讲抽象道理，需要补充字段取值、状态记录、日志回放、人工校验确认。
高风险场景（资金、合同、权限删除）原则：宁可增加校验步骤，不能放任模型自主判断执行。
第三层：长上下文能力
长上下文决定系统遇到异常路径的时候能否收敛正常。
上线前必须用大量边界样本做压测，样本包含：证据冲突、工具超时、用户修改需求、权限不足、旧历史数据、格式错误等。
一次演示成功没有工程意义；工程质量看异常情况下能不能停止执行、暴露错误原因、并且把错误样本回流评测集。
第四层：任务路由
负责不同子任务分发，在前面几层退化之后，路由逻辑也会出现不稳定。
通俗理解：闲聊对话这类通用语言能力，往往保留较好；对格式严谨、数值准确、多轮状态、长记忆有强约束的工程类能力率先崩坏。

二、4‑bit 量化能力退化四层顺序（由最先受损到后续受损，每一层完整拆解：定位、风险、踩坑点、工程做法）

第一层：结构化输出（最先下降，系统入口可靠性）
定位作用：这一层是整个 Agent 系统的入口。入口一旦出错，后续模型再强，也只能基于错误的数据继续处理。
工程落地要求
真实业务中，要完整记录：输出的字段、字段来源、版本信息、权限信息、时间戳；不能完全依靠大模型直接从自然语言文本里面猜测提取信息。

面试答题注意点：不能只讲抽象原则，回答要落地，需要补充：具体字段、输出状态、取值域、取值校验、日志回放、人工确认机制。

宁可多增加一步校验流程，也绝不允许模型仅凭自身感觉直接执行操作。
第三层：长上下文能力
定位作用：保证系统遇到各类异常路径的时候，业务逻辑可以收敛。
上线测试硬性要求：上线前必须拿边界样本做压测

第四层：任务路由
在前三层能力受损之后，任务路由能力开始出现不稳定。负责各个子任务分发调度。
