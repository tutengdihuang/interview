这是一道大模型后端 / 推理面试题讲解视频，主题：为什么评估大模型响应速度，不能只看总耗时。

核心知识点

大模型流式生成要拆 3 个核心指标，不能只看从发请求到全部输出完毕的总耗时：

首 Token 延迟（TTFT）：发送请求后，用户看到第一个字输出要等待的时间。

用户感知：决定用户会不会觉得系统卡死、没反应。

慢的原因：请求排队、RAG 检索慢、输入上下文过长、Prefill 预填充推理慢。

每秒 Token 数（生成速度，token/s）：后续输出文字的速度。

用户感知：输出文字流是否顺滑，会不会断断续续。

慢的原因：模型规格大、GPU 显存带宽瓶颈、服务器负载高。

完整响应总耗时：从请求发出到全部内容输出结束的总时间。

慢的原因：输出文本很长、工具调用 / 检索链路复杂。

举例说明（视频里的例子）

场景 A：总耗时 10 秒，前 8 秒完全不出字，最后 2 秒一次性输出全部内容。

场景 B：总耗时同样 10 秒，1 秒就输出第一个字，之后持续流式吐字。

两者总耗时一模一样，但用户体验天差地别。场景 A 用户会认为系统卡住了，场景 B 体验流畅。

只看总耗时，分辨不出是“开头卡住”还是“输出过程慢”，无法定位到底是排队、检索、还是推理解码环节出问题，也就没法针对性优化。

面试答题参考（视频给出的回答话术）

大模型速度不能只看总耗时，要拆解为首 token 延迟、生成吞吐（token/s）、完整完成时间。不同指标对应不同系统瓶颈，也对应不一样的用户体感。首 token 影响用户是否感知到系统已开始处理；token/s 决定流式输出的流畅；总耗时代表整体任务结束时间。只看总耗时会掩盖不同阶段的性能问题。

补充小背景

首 Token 主要对应推理的 Prefill 预填充阶段（处理用户输入 prompt）；

每秒 token 对应 Decode 解码阶段（一个字一个字生成输出），两个阶段瓶颈不一样，优化方案完全不同。

面试官问：评估大模型响应速度，为什么不能只看总耗时？

很多同学回答这个问题的时候，只会说总耗时，这是典型的错误答案。

大模型是流式输出，我们要拆成三个指标来看。

第一个，首 Token 延迟，TTFT。就是你发完请求之后，多久能看到第一个字。

这个指标，直接决定用户会不会觉得你的服务卡住了、没有反应。

首 Token 慢，一般是请求排队、RAG 检索耗时、输入上下文太长、Prefill 预填充推理慢导致的。

第二个，每秒 Token 数，token/s。也就是模型后续生成文字的速度。

它决定流式输出顺不顺畅，会不会断断续续。

这个慢，大多是模型参数量大、GPU 显存带宽瓶颈、服务器负载高造成。

第三个，完整响应总耗时。从请求发出去，到所有文字全部输出完毕的时间。

这个受输出文本长度、工具调用、检索链路复杂度影响。

举个例子，两个场景，总耗时都是 10 秒。

场景 A：前 8 秒一个字都不出，最后 2 秒一次性把所有内容全部吐出来。

场景 B：1 秒就返回第一个字，之后持续不断流式输出文字。

两个的总耗时一模一样，但是用户体验天差地别。

场景 A，用户会直接以为系统卡死了，刷新重试；场景 B，体验非常流畅。

所以只看总耗时，根本区分不开，到底是开头预处理阶段慢，还是后面逐字生成阶段慢。

定位不了是排队、检索，还是 Prefill、Decode 环节的瓶颈，也就没法针对性做优化。

评估大模型响应速度，不能只看总耗时，需要拆解为首 token 延迟、生成吞吐 token/s、完整完成时间三个指标。

不同指标对应不同系统瓶颈，也对应不一样的用户体感。

首 token 延迟影响用户感知系统是否开始处理；token/s 决定流式输出流畅度；总耗时代表整个任务结束时间。

只看总耗时，会掩盖不同阶段的性能问题。
