抖音视频详细总结
视频主题：AI Agent 点击停止之后任务依旧后台运行的问题，完整的任务取消机制，拆解成四大核心环节：取消信号、工具执行、会话处理、补充指令。
核心痛点：仅仅做前端停止按钮、断开网络请求是不够的。前端输出停止，但后台命令、文件修改、子进程还会继续跑，产生残留副作用。
一、取消信号的传递
❌ 两种错误做法
使用全局变量标记停止：无法打断正在阻塞 / 等待的网络请求；多子 Agent 并发时，分不清要终止哪一个任务。
直接杀掉整个 Agent 进程：会丢失全部会话状态。
✅ 正确方案：层级式向下传递取消信号
主任务创建父级取消信号，子任务派生属于自己的子信号；父取消，连带子任务全部取消；单独取消某个子任务，不会影响父任务。
JS 中使用 AbortController，Java 对应Future.cancel中断机制。
在 Agent 循环（Agent Loop）设置多处取消检查点：下一次工具调用前、重试等待间隙检测是否取消；网络请求本身要接入可中断接口。
注意：如果业务代码本身不响应中断信号，就算发出取消信号，任务也停不下来。
二、正在运行工具的终止处理
工具类型不同，停止逻辑不一样：
网络请求类工具：直接取消网络请求即可。
系统命令 / 进程类工具（例如运行npm run dev）
仅仅杀掉外层 shell 不够，它会衍生子进程，子进程依旧存活、占用端口；需要按进程组 / 进程树整体管理。
终止策略：优先发送SIGTERM优雅退出，给程序机会自行清理资源；超时之后，再发送SIGKILL强制杀死进程。超时时间不能写死，根据业务场景调整。
子 Agent 生命周期管理
属于当前任务的前台子 Agent：主任务取消时必须一并终止。
独立后台子 Agent：使用独立取消信号；UI 界面必须明确告知用户该任务还在运行。否则用户点停止，以为全部结束，后台还在修改文件，造成逻辑错乱。
三、任务停止后的会话历史处理
任务被打断后，不能直接丢下残缺的会话消息：
工具调用和返回结果必须成对：已经发起、但没跑完的工具调用，要手动补充一条结果消息，标记本次操作被用户终止，补齐接口需要的数据结构。
半截回答如何留存，由消息协议、业务恢复策略决定，残缺执行不能标记为成功。
⚠️ 重点：任务取消 ≠ 自动回滚
有可能命令已经执行一半、文件已经写入、外部 API 请求已经提交。不能只靠一条 “已取消” 消息就认为外部改动消失。后续恢复执行前，Agent 要重新校验真实外部状态，再决定从哪里继续。
四、区分：用户是取消任务，还是下发补充指令
很多场景用户不是要停止，只是中途追加新要求，不能粗暴当成取消处理：
新的补充消息需要排队，在安全执行边界注入，留给 Agent 下一轮决策读取。
已经发起还没结束的工具调用，要先把现有调用结果收拢，不能强行把新消息插入正在运行的调用流程。
区分两类新消息，分开队列管理：
方向调整：当前这件任务，按照新需求继续往下做；
后续任务：先做完手头这件事，再执行新的需求。
系统要明确规则：新指令是立即生效，还是本轮执行结束后生效。
总结完整的 Agent 取消机制
一个可靠的停止能力，不只是页面上的停止按钮：
层级传递取消信号；
把后台工具、进程、子 Agent 真正收拢终止；
补齐会话消息，修复残缺调用记录；
校验已经发生的副作用；
区分 “真正取消” 和 “中途补充指令” 两种用户行为。

视频完整逐点整理（全部要点、例子、结论，无省略）
视频核心命题：绝大多数 Agent Demo 里的 “停止按钮” 只是断开前端流式输出，无法终止后台工具、子进程、子 Agent 执行；用户点停止之后，副作用依然会发生。可靠的取消是一套完整生命周期机制，不是一个布尔标记。
开篇例子：前端点停止，页面文字停了，但 Agent 在后台继续执行npm run dev、修改文件、调用 API、发邮件；用户以为停了，文件被改、端口被占用、消息重复发送，出现脏数据。
一、取消信号的传递（协作式取消 / Cancellation Token）
1. 两种错误实现，视频明确批判
❌ 方案 A：全局布尔标记（isStop = true）
缺陷 1：阻塞的异步请求、长耗时工具调用不会主动去轮询这个标记；标记改了，正在跑的代码感知不到。
缺陷 2：多并发、多层子 Agent 场景下，全局 flag 分不清 “取消哪一个任务”，一停全停，互相干扰。
结论：布尔 flag 只能在循环边界做检查，不能单独作为取消机制。
❌ 方案 B：直接杀死整个 Agent 主进程
缺陷：直接销毁内存里全部会话上下文、任务状态、未完成工具调用记录；后续无法查看中断现场、无法恢复、无法做善后回滚 / 补偿。
结论：进程强杀是兜底，不是常规取消手段。
2. 正确方案：层级派生式取消令牌（父信号 → 子信号，树状结构）
核心模型：每一个任务（主任务、子任务、子 Agent、单次工具调用）拥有独立的取消信号，子信号由父信号派生。
传递规则：
父任务触发取消 → 所有派生出来的子信号全部触发取消（级联取消）
单独取消某一个子任务 → 只影响该子任务，父任务、其他兄弟子任务不受影响
代码示例对照：
JS / TS：AbortController，把 signal 传给模型流式请求、fetch 工具调用
Java / Go：Future.cancel()、context.Context
检查点（安全点）规则：取消信号只在预设检查点生效，不能任意打断正在原子执行的底层逻辑
检查点固定放在这 4 个位置（视频原文列出）：
Agent 循环下一轮，准备调用 LLM 之前
准备发起一次新工具调用之前
工具返回结果之后，进入下一轮思考之前
重试等待、sleep 延迟间隙
重要边界结论：如果底层工具、三方 SDK、系统命令本身不支持监听 / 响应取消信号，就算发出 Abort 信号，任务依旧跑到底；取消能力向下受限于被调用组件。
二、正在执行中工具的终止处理（按工具类型分开策略，视频分 3 大类）
类型 1：只读网络请求类工具（网页搜索、查询数据库只读查询）
例子：调用搜索 API、SELECT 查询、读取文件
处理：直接 Abort 网络请求即可；没有持久副作用，中断后不需要回滚。
结论：这类是最简单、风险最低的可中断工具。
类型 2：系统 Shell 命令、本地进程（重点例子：npm run dev、编译脚本、bash 脚本）
坑点重点强调：只杀掉外层 shell 进程 PID，它 fork 出来的子进程、孙进程会变成孤儿进程，继续占用端口、读写文件。
正确策略：按进程组 / 进程树整体管理，而不是单 PID
两步递进终止顺序（优雅优先）：
先发 SIGTERM（优雅终止信号）：给程序预留时间自行清理临时文件、释放句柄、关闭端口
设置超时窗口（不写死，按业务最长耗时配置），超时之后发送 SIGKILL 强制杀死整个进程树
Windows 对应例子：taskkill /T /F，/T 代表杀死进程树
类型 3：子 Agent（多智能体嵌套场景）
视频划分为两类子 Agent，处理逻辑完全不同：
前台从属子 Agent（当前主任务的一部分）
例子：主 Agent 让子 Agent 单独写一个页面、跑单元测试，属于本次任务内部分工
规则：主任务取消时，必须同步下发取消信号终止这类子 Agent，属于级联取消范围
独立后台子 Agent（脱离当前会话的后台任务）
例子：后台异步批量爬取、长时间视频渲染、定时生成报告
规则：拥有独立取消信号，不能跟着主任务一起取消；UI 必须明确区分展示，告诉用户：这个任务还在后台跑，需要单独点停止。
反面事故例子：用户点停止以为全部结束，后台独立子 Agent 继续修改仓库代码，产生不可预期变更。
本章节总结论：工具没有统一停止公式，必须按工具的副作用模型、是否有子进程、是否从属当前任务分类设计。
三、任务停止之后，会话历史、消息结构的收口处理（非常容易遗漏）
前提背景：主流工具调用协议（OpenAI FunctionCall、Anthropic ToolUse）强制要求：工具调用请求消息，必须配对一条工具返回结果消息，消息结构成对，否则大模型 SDK 直接抛异常、会话损坏。
对于已经发起、但是被取消打断、没有返回结果的工具调用：
必须手动插入一条 ToolResult 消息，固定标记：本次工具调用被用户取消，未完成执行
例子：Agent 已经发起文件写入工具调用，还没拿到返回，用户点停止；后端不能直接丢弃这条调用记录，必须补齐这条结果消息写入会话上下文。
半截流式回答的留存策略：
没有强制统一方案，由产品恢复策略决定：可以保留半截回答、清空、或者标记作废；但是中断任务绝对不能标记为【执行成功】状态。
视频最重要的警示结论：任务取消 ≠ 自动回滚！！
举例清单（视频原文例子）：
✘ 已经发出去的邮件，取消拦不住
✘ 已经提交的支付 / 订单请求
✘ 已经写入磁盘的文件、已经 commit 到 git 的代码
✘ 数据库事务已经 commit 的写操作
区分三种情况的善后路径：
事务内写操作、还未提交：可以回滚
已经提交到外部系统：无法回滚，进入补偿流程（补偿邮件、人工工单、对账）
不确定外部状态：Agent 恢复执行时，优先重新校验真实外部世界状态，不能只依赖会话里的历史消息继续往下跑
推论：设计工具时，强烈要求工具调用具备幂等性，携带全局唯一调用 ID，防止重试 / 恢复时重复执行。
四、区分两种用户行为：【取消任务】VS【中途追加补充指令】（最容易混淆的边界）
视频指出大量产品 bug 来源：把用户中途发的新消息，一律当成取消，粗暴中断当前执行。
场景例子：Agent 正在写一份方案写到一半，用户发一句：“再加一个预算章节”。用户不是要停掉写方案，只是调整需求。
两类用户消息分开队列管理
方向调整类消息（修改当前正在做的任务要求）
规则：不直接取消正在进行的工具调用；等待当前这一轮工具调用、当前回合执行边界（检查点），再注入新指令进入上下文，下一轮 Agent 决策读取新需求。
例子：正在调用工具读取文档，不能直接掐断这次读文档请求，读完返回后，再把用户新增要求交给 Agent。
全新后续任务消息（先做完手头这件，再做新事）
规则：消息排队，放入等待队列，当前任务完整结束之后再调度执行。
产品规则二选一，必须明确写死（二选一，不能模糊）
A 模式：新消息立即生效（本轮边界就切换目标）
B 模式：新消息排队，等当前任务全部完成再执行
参考对标例子：Pi 的 Steer 机制、扣子 Coze 的消息队列设计。
五、视频最后的完整汇总结论（收尾总结）
一个生产级可用的 Agent 停止机制，包含 5 个强制模块，缺一不可：
树状层级取消令牌，逐级传递取消信号，在 Agent 循环安全检查点校验；
差异化终止逻辑：网络请求、shell 进程树、前台 / 后台子 Agent 分开处理，进程优先 SIGTERM 超时后 SIGKILL；
会话消息补齐，保证工具调用成对，避免协议报错；
副作用收口：能回滚则回滚，不可回滚走补偿流程；恢复前校验外部真实状态，不能假设取消等于撤销；
区分用户意图：区分 “终止任务” 和 “中途修改需求”，消息队列隔离管理，不在工具执行中间强行注入新指令。
额外视频隐含的面试 / 工程推论（口述提到）
Demo 版本只做前端断流，是假停止；
取消属于协作式中断，不是抢占式中断；底层原子操作无法被中途劈开；
子 Agent 生命周期必须注册在任务注册表，防止后台僵尸 Agent 无限占用资源。
