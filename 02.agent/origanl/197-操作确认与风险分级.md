视频完整内容总结
视频主题是Agent 面试真题：Agent 每一步都让用户确认太烦，全自动又危险该如何处理，以企业报销 Agent（查制度、生成报销单、上传发票、提交审批）作为业务案例，指出这道题看似考用户体验，本质考察Agent 权限控制、风险分级与工程落地能力。核心观点：Agent 不能简单只有 “全自动” 和 “人工确认” 两档，要做多维度风险分层，平衡安全和用户体验，避免确认疲劳。
一、核心解题总思路
借鉴 OpenAI SDK 的设计思想：低风险读操作自动执行；高风险写操作需要确认；产生关键外部副作用的动作做强确认；由系统策略自动判断何时打断用户，不能简单粗暴到处弹窗确认，需要搭建风险分级矩阵。
报销 Agent 实例：
✅自动执行：查询报销制度、生成发票、生成报销草稿；
⚠️必须用户确认：提交审批、修改报销金额、绑定银行卡。
风险判断不看工具名称，看动作带来的实际后果，同一个工具（例如 update），修改草稿风险低，修改线上业务数据就是高风险操作。
二、三大风险判断维度（分层依据）
1. 动作性质（读写、数据敏感度、副作用）
低风险：读取公开资料、文档总结、生成草稿；
中等风险：读取个人隐私、财务敏感数据；
高风险：写数据库、发对外消息、提交审批、付款退款，会产生外部业务副作用。
2. 可回滚性（动作是否可以撤销、撤销成本）
容易撤销：生成报销草稿，出错直接删除，确认要求低，可以自动执行；
不可撤销 / 撤销代价极高，必须强确认：报销提交审批，一旦提交就进入正式业务流程、留下审计记录，无法随意撤回。
重点：确认弹窗必须展示真实执行参数，而不是模型的自然语言描述，用户确认的是具体参数，不是笼统的 “是否同意”。
3. 上下文信心（动态升级确认）
即便动作本身属于中等风险，如果系统证据不足、工具返回结果冲突、用户意图模糊不清，就要升级为人工确认。
举例：用户说 “帮我报上次那个费用”，系统找不到唯一匹配的发票，不能自动提交报销，需要询问用户确认信息。
风险不是静态写死配置表，要结合当前任务状态动态变化判断。
三、面试标准高分回答模板
我会搭建一套风险分级策略，按照工具动作读写属性、外部副作用、数据敏感度、业务金额、可回滚性做分层；低风险动作自动执行；高风险动作展示完整参数，交由用户确认；当证据不足、任务状态冲突时，动态升级人工确认。
四、工程落地补充要点（加分项）
确认本质是对动作 + 具体参数的授权：不能只记录一句 “用户已同意”，必须校验：用户确认的参数，和后续工具实际执行参数必须保持一致，防止参数被篡改。
审计日志留存：确认动作全部记入审计日志，记录操作人、时间、调用工具、入参、风险等级，用于事后问题追溯，同时用来迭代优化确认策略，减少不必要确认。
策略需要线上迭代，不是一次性写死
如果某一类低风险确认，用户几乎全部无脑点同意，说明确认冗余，可以降低风险等级改为自动；
如果某一类自动执行的动作，线上经常被用户撤销，就要提高风险等级，增加确认步骤。
五、面试追问：这套方案如何验证？
整理边界 case、容易出错的样本，做成回归测试用例；
上线后采集 trace 链路、业务指标、用户反馈；
发现异常先降级或者转人工兜底；
将线上真实错误案例回灌评测体系，优化策略，不可以单纯依赖 Prompt 做临场控制。

一、开篇核心认知与总原则
错误思路：只有全自动、全部人工确认两档；全部弹窗→用户确认疲劳；完全自动→越权、业务风险。
参考思想：OpenAI SDK 设计思路，让高风险动作停在安全边界之前，避免用户陷入细碎弹窗的确认疲劳。
总纲领一句话：低风险读操作自动执行；高风险写操作需要确认；带来关键外部副作用的动作做强确认；系统依靠策略动态判断什么时候打断用户。
面试提醒：不能只回答 “重要操作加弹窗确认”，必须要输出风险分级矩阵。
报销 Agent 直接示例：
✅自动执行：查询报销制度、识别发票、生成报销单草稿
⚠️必须确认：提交审批、修改报销金额、绑定银行卡。
重要底层结论：风险判断不看工具名字，看动作实际后果。
举例：同样是update工具；修改报销草稿风险低；修改线上正式业务数据属于高风险操作。
二、三大风险判断维度（全部要点 + 配套例子）
维度 1：动作性质（读写类型、数据敏感度、外部副作用、金额大小）
把动作划分低、中、高三档风险：
低风险：读取公开资料、文档总结、草稿生成
例子：查询企业公开报销制度，生成报销草稿
中等风险：读取个人隐私、访问财务敏感数据
例子：Agent 读取员工个人财务报销历史记录
高风险：写数据库、发送对外邮件、提交业务审批、付款、退款；动作会产生真实外部业务副作用
例子：报销提交审批、财务退款操作。
补充：读操作不等于一定低风险，如果读取的是隐私财务数据，风险升为中等风险。
维度 2：可回滚性（动作能否撤销、撤销成本高低）
容易撤销、撤销成本低：确认要求低，允许自动执行。
例子：生成报销草稿，做错直接删除即可。
不可撤销 / 撤销代价极高：必须强确认。
例子：报销单提交审批；一旦提交，流程流转到领导，生成审计留痕记录，无法随意撤回。
交互硬性要求：确认弹窗必须展示工具真实执行参数，不能只展示大模型的自然语言解释。用户确认的是参数，不是笼统一句 “是否同意该操作”。
维度 3：上下文信心，动态升级确认（动态风险，不是静态写死配置）
结论：即便动作本身风险等级中等，如果上下文证据不足、工具返回结果冲突、用户意图模糊，动态升级到人工确认。风险不能完全靠静态工具配置表，要结合当前任务状态实时判断。
业务案例：用户说 “帮我报一下上次那个费用”；系统找不到唯一匹配的发票，意图模糊，禁止自动提交报销，需要询问用户确认信息。

四、工程落地细节（面试加分项，视频逐条讲到，含全部结论）
注意：确认不等于仅仅记录 “用户点击同意”，确认本质是对具体动作 + 具体参数的授权。
参数一致性校验：用户确认的参数（例如报销金额 100 元），工具实际执行的时候，参数必须保持一致；防止中间环节参数被篡改。
审计日志强制留存
日志记录字段：操作人、操作时间、调用的工具、工具入参、本次操作风险等级。
两个作用：①发生事故可以完整追溯；②拿到线上数据，迭代优化确认策略，减少不必要的确认弹窗。
确认策略不能写死，要随线上业务、用户行为迭代优化
场景 A：某一类确认弹窗，线上用户几乎全部无脑点同意，代表确认冗余，可以降低风险等级，改为自动执行。
场景 B：某一类自动执行动作，线上频繁被用户撤销，代表风险预判不足，需要提高风险等级，增加确认步骤。
