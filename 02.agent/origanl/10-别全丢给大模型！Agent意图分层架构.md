视频详细内容总结
这个抖音视频主题是Agent 意图分层漏斗架构，核心观点：做 Agent 的意图识别，不要把所有用户请求全部直接丢给大模型；要做分层处理，把低成本能力用在简单请求，高成本大模型只留给复杂长尾请求，以此平衡识别准确率、响应延迟、资源成本三个指标，解决生产落地的工程问题。
一、视频先指出两种极端的错误实现方案
纯规则方案（全靠关键词、正则、映射表）
初期开发快、资源消耗低。但用户换表达方式，就要新增规则；时间久了规则数量爆炸，规则优先级互相冲突，系统维护难度急剧升高，泛化能力很差。
全部请求直接交给大模型处理
理解能力强，几乎不用人工维护规则。但是存在三大工程痛点：
每次调用都有大模型推理延迟；
Token 消耗大，运行成本高；
大模型输出存在随机性，意图识别一旦出错，后续整个路由逻辑全部跑偏。
当线上 QPS（每秒请求量）升高，延迟、成本、稳定性问题会集中爆发。
类比比喻：这套分层架构就像医院分诊。常见病普通门诊处理；复杂病历交给专家；危重情况多科室会诊。算力资源优先处理简单请求，昂贵的大模型算力留给真正复杂的任务。
二、三层漏斗式意图识别架构（从上到下依次流转，上一层处理不了才进入下一层）
第一层：规则层（入口第一层，追求高效率、低消耗）
处理对象：表达固定、歧义很小的高频指令，示例：打开设置、查询余额、转人工客服。
实现手段：关键词匹配、正则表达式、有限状态机。毫秒级完成处理，资源开销极低。
重要设计约束：不能无限制增加规则。只保留明确稳定的高频需求，避免规则库无限膨胀带来冲突与维护灾难。
第二层：上下文状态层（承接规则层无法处理的常规流量）
业务背景：真实对话中用户经常省略信息，只看单句无法判断意图。例如 “那个退款到哪了”、“那取消吧”，单独看这句话含义模糊，必须结合历史对话。
核心工作：维护会话完整状态，包含当前任务、已经收集的槽位、历史操作记录。槽位就是完成任务需要收集的信息。收到用户新消息，先更新会话状态，再判断用户是继续旧任务，还是开启新任务。
技术选型：可以搭配轻量模型、领域分类模型、语义向量匹配，在识别能力和延迟之间做平衡。
风险提醒：会话状态过期、多个任务状态混杂，就算模型再好，也依然会识别错误。
举例：上一轮用户在查询订单，下一句用户说 “那取消吧”，依靠上下文才能知道要取消的是刚刚的订单；如果单独拿 “取消” 二字去识别，会丢失关键对象信息。
第三层：大模型 + 工具层（兜底层，处理长尾复杂请求）
处理对象：前面两层搞不定的请求：表达模糊、跨领域、需要调取外部数据才能完成的任务。
工作方式：大模型不再只是输出一个意图标签，而是解析用户最终目标，拆解任务，通过 Function Calling 函数调用输出结构化指令，交给系统执行工具，打通意图理解和实际业务动作。
举例：用户说 “帮我分析上个月最大一笔消费，按类别导出报表”，需要查询账单、筛选交易、分类统计、生成报表，单纯打意图标签无法完成，需要大模型做任务拆解 + 工具调用。
架构定位：理想情况下，流转到本层的请求占比要很低，高成本大模型专门用来处理复杂长尾，不承担主流量。
三、三层分工总结
规则层：效率优先，搞定高频简单指令；
上下文状态层：承接绝大多数常规对话流量，解决多轮对话指代、信息不全问题；
大模型工具层：兜底复杂长尾请求，能力最强，但延迟、成本最高。
四、落地实践建议
做 Agent 意图识别设计时，不能只追求识别准确率，要同时权衡准确率、响应延迟、资源成本，不能为了优化某一项指标，导致另外两项失控。
落地步骤建议：
先梳理全部用户请求，分成三类：意图明确简单的、依赖对话上下文的、复杂长尾需要模型规划的；
根据请求分类，再为每一层选定对应的技术方案；
通过分层漏斗，让系统更容易维护、可控，适配线上真实流量场景。

完整逐点整理（原视频全部要点、例子、比喻、数据、结论、工程提醒全部收录，无省略）
视频标题：工业级 Agent 意图识别的分层漏斗
核心总纲前置：
意图识别是 Agent 整个链路的总闸门；意图一旦识别错误，后面整条路由、工具调用全部跑偏。所以它的评价指标不是只看准确率，是三个指标同时权衡：识别准确率、响应延迟、算力成本。这三者构成一个不可能三角；分层漏斗就是工业上落地这个三角的解法。
核心思路：按请求复杂度分层，流量从上向下流转；上一层置信不足、无法处理，才流入下一层；越下层能力越强、延迟越高、成本越贵；绝大部分流量在上浅层消化，昂贵大模型只留给极少数长尾疑难请求。
类比贯穿全程：医院分诊模型。分诊台快速筛常见病→普通门诊处理；复杂症状交给专科医生；危重、多病因病例才启动多学科会诊。不会所有病人进门直接找专家。
一、视频开篇：两种极端错误方案（全部反面要点、痛点、例子）
错误方案 1：纯规则方案（全 if-else、关键词、正则、映射表）
优点：开发上手快、几乎没有算力消耗、响应极快。
硬伤：泛化能力极差。用户换一种表达方式，规则就失效。
长期工程灾难：规则越写越多，规则之间优先级冲突、覆盖冲突；规则库膨胀之后没人敢改、没人敢加，维护成本非线性爆炸。
例子：写一条规则匹配 “我要转人工”，但用户说 “帮我接客服”“我找真人”，这条规则直接失效，必须新增规则。
视频结论：纯规则只适合少量固定指令，不能扛全部线上流量。
错误方案 2：所有用户 Query 全部直接丢给大模型（新手 Demo 最容易写的方案）
表面优点：理解能力强，不用大量写规则，demo 看着效果很好。
三大线上致命硬伤（视频逐条列出）
痛点 1：延迟失控。单次推理延迟通常 2000ms 起步；QPS 上来之后请求排队，P99 延迟持续恶化，排队等待时间成倍放大。
痛点 2：成本线性爆炸。GPU、Token 开销跟着请求量同步上涨；高频简单话术（谢谢、打开主页、查余额）也要消耗一次大模型调用，高并发场景账单完全不可控。
痛点 3：输出不稳定、链路容易崩。大模型存在幻觉、输出格式漂移、标签随机性。下游路由逻辑依赖固定结构化输出，一旦格式不对、意图标签错，后续工具调用直接报错。
例子：用户一句简单的 “谢谢”，也要走一轮大模型推理，属于典型算力错配。
视频结论：全量大模型只适合 Demo，不适合工业生产上线。
二、三层漏斗架构完整定义、流量占比、延迟指标、技术选型、示例、约束（视频给出固定流量分配数字）
整体流量分配（视频原文数据）：
第一层【规则层】：承接 60% 线上流量，响应 <1ms，算力几乎为 0
第二层【上下文状态层】：承接剩下里面的 35% 流量，响应约 100ms，轻量模型成本很低
第三层【大模型 + 工具层】：只处理剩余 5% 的长尾复杂请求，延迟高、成本最高
漏斗流转规则：每层有置信阈值，命中且置信达标直接在本层闭环；置信不够、识别失败，才往下一层透传，不是固定必须走完三层。
第一层：规则层（漏斗入口，宽口第一层）
定位：拦截表达高度固定、无歧义、高频稳定的显性指令。
实现手段：关键词匹配、正则表达式、有限状态机，不使用任何模型。
视频示例：打开设置、返回首页、查询余额、转人工客服、退出会话。
最重要工程约束（视频反复强调）：规则层必须主动做减法、严格控制准入范围，不能无限堆规则。
原因：每新增一条规则，就要处理优先级、匹配顺序、和老规则的冲突；规则库膨胀后，冲突风险和测试成本急剧上升，最后变成 “谁都不敢动的规则泥潭”。
准入标准：只有大量用户反复用几乎一模一样句式表达的意图，才放进规则层；口语变体多、表达方式分散的，一律不进这一层。
本层判定标准：完全命中、无歧义，直接输出意图标签、走预设工作流，直接返回用户，不再向下流转。
第二层：上下文状态层（整个漏斗的流量主力承载层）
定位：承接规则层识别失败、没有命中的绝大多数常规对话；专门解决多轮对话指代省略、信息不全、语义延续的问题。
核心底层问题：很多单句孤立看语义模糊，意图信息不在这句话里面，而在历史对话里。脱离上下文，单句识别一定会错。
本层维护对象：会话状态对象（视频明确列出里面字段）
当前激活的任务类型
已经收集填充好的槽位（完成这个任务需要的参数）
历史交互动作记录
处理流程：收到用户新消息 → 先更新会话状态 → 判断用户是延续上一个已有任务，还是发起全新的任务 → 输出意图 + 槽位结果。
视频原话例子（两个）
例 1：用户单独一句：“那个退款到哪了？”。单独看不知道是哪一笔退款；依赖历史对话才能锁定订单。
例 2：上一轮用户正在查询订单；本轮用户只说一句：“那取消吧”。只有状态层知道，取消对象是刚才的订单；单独识别 “取消” 二字，会完全丢失目标实体。
技术选型（视频明确：这一层不上大模型）
方案：领域微调轻量分类小模型 / 文本 Embedding 向量相似度匹配
延迟：约 100ms，成本远低于大模型
本层额外风险提醒（视频单独拎出来）：会话状态过期、多任务状态混杂，就算模型再好，依然会识别跑偏。必须做会话生命周期管理，超时自动清理过期状态，防止状态堆积错乱。
流转规则：本层置信达标，直接闭环；置信度低于阈值、语义极度模糊、跨任务复合需求，才放行到第三层兜底。
第三层：大模型 + 工具规划层（兜底层，漏斗最下端）
定位：前两层全部识别失败、置信不足的长尾、边缘、复杂请求，是最后一道防线。流量占比只有 5%，禁止用来扛主流量。
进入本层的请求特征（视频分类）
用户表达模糊、开放式描述；
复合意图，一句话里面包含多个串行 / 并行子任务；
需要查询外部业务数据、多步骤执行才能完成；
跨领域、不在前面两层预设意图库内的域外请求。
和新手用法的区别：不是让大模型只输出一个意图标签。生产级用法是Function Calling（函数调用），做任务拆解，输出结构化工具调用序列，打通意图理解和业务执行。
视频完整示例：用户说：“帮我分析上个月最大一笔消费，按类别导出报表”
拆解步骤：①查询上个月账单数据 ②筛选金额最大单条记录 ③全账单按消费类别分组统计 ④生成报表文件
大模型输出结构化的工具调用参数、执行顺序，交给系统调度各个工具执行，而不是单纯给一句自然语言回答。
本层代价：推理延迟高、Token 消耗大、GPU 成本最高，所以严格限制入口。
三、三层分工一句话总结（视频原话总结）
规则层：效率优先，吃掉高频固定指令，毫秒级零成本；
上下文状态层：主力承载常规多轮对话流量，解决指代省略，平衡速度和灵活性；
大模型工具层：兜底长尾疑难，能力最强，成本最高。
四、视频给出的落地实施步骤（工程落地顺序）
第一步：梳理业务全量用户 Query，做流量分层归类：
A 类：句式固定、高频无歧义 → 交给规则层
B 类：口语变体多、依赖对话历史、省略指代 → 交给上下文轻量模型层
C 类：模糊、复合、多步骤、域外长尾 → 进入大模型兜底层
第二步：给每一层设定置信度阈值，作为向下流转的开关；阈值需要线上数据调优。
第三步：每层独立配置路由、工作流、返回模板；上层闭环就不再走下层。
第四步：配套会话状态管理、状态过期清理机制，防止第二层状态污染。
第五步：埋点监控，统计每层流量占比、每层识别准确率、每层耗时、调用量；持续回流数据，把稳定高频新句式沉淀到上层（可以把符合标准的 Query 升级加到规则层，持续降低大模型调用量）。
五、视频最终全部结论（收尾观点）
做 Agent 意图识别，不是单纯追求越高越好的准确率，而是工程取舍，平衡准确率、延迟、成本这个不可能三角；单一技术路线（纯规则 / 全大模型）都无法同时满足三者。
分层漏斗的本质：算力按需求复杂度分级分配，贵算力只给疑难问题，避免算力错配。
这套思路具备通用性，不只客服 Agent 能用；搜索、审核、机器人交互类系统都可以复用这个分层分流思想。
面试 / 评审核心一句话答案（视频结尾给出）：高频走规则，多轮走上下文，昂贵算力留给疑难长尾。
