面试官问：Agent 执行到一半，用户突然点了取消，系统该怎么处理？

很多人第一反应是直接停掉，但在真实项目里，这会导致状态混乱、脏数据甚至权限事故。

真正的高分回答不能只提中断模型调用，而是要从任务生命周期出发。

我是小哲，关注我，继续用大白话拆大模型工程化面试题。

这个问题表面在问取消任务，实际在考有没有做过长任务 Agent。

因为 Agent 不是一次简单问答，它可能已经查了数据库，写了文件，调用了支付、发货、邮件、审批系统。

如果用户点取消时只是把模型请求断掉，外部工具可能已经执行成功了，前端看起来是取消，后端其实已经把事情做完一半。

这类问题在线上特别危险，因为用户会重复提交，系统会重复执行，最后变成脏数据、重复通知、重复扣费，甚至全线事故。

所以面试的时候不能只说支持 cancel token，那只是很小的一层。

更好的回答是 Agent 的取消要按任务生命周期设计，而不是按模型请求设计。

第一层是可取消点，系统要把任务拆成多个步骤，每一步执行前检查任务状态。

比如准备资料、生成计划、调用工具、写入结果、通知用户，每一步都要能判断当前任务是不是已经被取消。

第二层是幂等，工具调用不能默认调用一次就成功，而要有任务 id、步骤 id 去做去重。

同一个步骤重复执行时要么直接返回上次结果，要么明确拒绝重复写入，否则用户一刷新 Agent 就可能把同一封邮件发三遍。

第三层是补偿，有些操作已经发生就不能假装没发生。

比如已经创建了工单就要把工单标记为取消，而不是硬删。

已经生成了文件就要记录文件状态，而不是让用户找不到。

已经调用了外部 api 就要保存响应和错误码，方便后面排查。

这也是为什么长任务 Agent 通常要有状态机，状态不能只有进行中和完成，至少要有待执行、执行中、取消中、已取消、失败、部分完成、待人工确认。

听起来麻烦，但这就是线上系统和演示系统的区别。

第四层是用户反馈，取消按钮不是点完就消失，系统应该告诉用户当前取消到了哪一步，哪些操作已经完成，哪些操作不会继续执行。

如果任务涉及外部系统还要给出可追踪记录，比如报告已停止生成，已创建的临时文件将在稍后清理，或者审批单已提交，无法撤回，需要人工处理。

这类提示能减少用户误判，也能减少客服和运营的排查成本。

面试可以这样答：Agent 的取消不能只理解成中断模型调用，而要按任务生命周期做。

我会先把任务拆成可观测的步骤，每一步执行前检查取消状态。

然后为工具调用设计幂等键，避免重复提交。

对已经产生副作用的操作补偿状态，而不是暴力回滚。

最后把取消进度和已发生动作明确反馈给用户。

一句话总结：Agent 取消的核心不是停，而是停的可控、可追踪，不会把系统状态弄脏。
