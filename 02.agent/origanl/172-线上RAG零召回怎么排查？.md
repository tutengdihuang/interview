抖音视频《面试官：线上 RAG 零召回怎么排查？》内容详细总结
视频是一道大模型 RAG 面试题讲解：线上 RAG 突然出现大量零召回该如何排查。
核心观点：遇到大量零召回，不要一上来就调大 topK。这道题目考察的不是检索参数，而是对 RAG 完整数据管道的工程理解；正确方式是沿着数据流向，从下游往上游逐段验证定位故障点，而不是跳跃式排查向量库、模型。
很多人面试只回答检查向量数据库、Embedding 模型、检索参数，属于浅层答案，很难拿到高分。
四层逐层排查方案（从下游→上游）
第一层：检索入口确认（查询侧）
排查查询请求本身是否异常：
用户输入乱码、空请求；
Query 改写模块出错：把用户原始问题改写成完全无关的内容，生成错误向量。
只要查询输入本身坏掉，后续不管向量库、参数怎么调，结果都是零召回。排查方式查看接口日志原始 query 字段。
第二层：索引状态检查（高频故障点，数据入库管道）
这是生产环境最容易出现的故障：上游同步任务静默失败，没有告警，任务显示执行成功，但索引没有有效数据。
典型场景：定时同步 Job 拉业务库文档构建索引；DBA 修改数据表结构，抽取接口没有同步适配；ETL 任务跑完显示成功，但拉取到的文档全部是空内容，向量索引没有有效知识库数据。
排查手段：直接统计向量索引内文档总数量。如果索引为空，直接定位是上游数据同步链路故障，优先修复同步链路。
第三层：过滤条件排查（元数据过滤误杀候选集）
RAG 检索完成后，经常附带元数据过滤逻辑：例如只召回近 7 天、指定类目、已发布状态文档。
故障现象：向量检索本身能查到数据，但是过滤条件把全部候选结果剔除，最终返回 0 条。
排查技巧：对比过滤前原始 TopK 结果 vs 过滤之后结果；如果过滤前有数据，过滤后为空，说明过滤逻辑误杀。
常见坑点：时区不一致、枚举值大小写不匹配、过滤用到的字段在 Schema 中已经废弃。
定位方法：将过滤条件与索引存储的元数据字段做 diff 比对。
第四层：Embedding 版本一致性校验
该故障多出现在模型升级窗口期：
写入知识库文档向量用的是 v1 版本 Embedding 模型；但是线上查询服务切到 v2 模型。
两个模型向量空间完全不兼容，向量距离计算结果全部错乱，直接零召回。
向量库本身没问题，但是写入、查询两端 Embedding 模型版本不统一。
面试答题组织建议
先总述思路：零召回排查，沿着 RAG 数据管道从下游向上游逐层验证；
依次讲四层：检索入口 → 索引状态 → 过滤条件 → Embedding 版本一致性；每一层带上简单的排查操作；
补充生产环境错误操作禁忌：
❌ 不要直接重启服务：零召回大多属于数据链路问题，不是服务进程问题；重启不仅无效，还可能冲掉故障现场日志。
❌ 不要盲目重建索引：如果根因是上游 ETL / 同步管道坏掉，重建索引得到的依旧是空索引，故障复现。

简单梳理面试回答话术参考
遇到线上 RAG 大量零召回，我不会直接调大 topK。会按照从下游到上游的链路逐层排查：

一、面试题背景与反面错误回答
面试场景：面试官提问：线上 RAG 突然大量零召回，应该按什么顺序排查？
错误回答：一上来就说调大 topK
视频结论：说出这个答案，面试官就判定候选人没有生产环境实操经验。
底层原因：大量零召回几乎不是检索参数 topK 的问题；根源可能是解析管道断裂、索引构建为空、过滤条件把全部候选杀掉。调大 topK 解决不了链路类故障。
其他低分常见回答：直接回答检查向量数据库、检查 Embedding 模型、检查检索参数。
视频结论：面试官听腻这类浅层答案，不能加分。
本题考察本质：不是单纯考调参、考检索算法；考察候选人对RAG 完整数据管道的理解，是否清楚文档入库一直到结果返回，整条链路有哪些节点、每个节点如何发生断裂。
核心总原则（视频原文一句话结论）
0 召回排查必须沿着数据管道的流向，从下游往上游逐段验证数据是否存在，不能跳着查。
二、四层排查体系（从下游→上游，每一层包含：故障现象、业务实例、排查操作、结论）
第一层：检索入口确认（查询侧，最下游）
故障根源：查询请求本身异常，上游知识库、索引全部正常，但输入的查询坏掉，后续所有步骤都返回 0 召回。
具体故障场景 2 个例子
用户原始输入本身是乱码、空请求；
Query 改写模块出错：改写逻辑把用户正常自然语言，改写为完全无关的内容，生成错误向量。
排查动作：查看接口原始日志，确认原始 query、改写之后输出的 query 内容。
本层结论：只要检索入口输出异常，向量库再正常也一定会零召回。
第二层：索引状态检查（视频强调：最常见管道断裂点）
故障根源：上游知识库同步 ETL 任务静默失败；任务执行状态显示成功、无告警，但没有产出有效文档写入索引，索引是空的。
真实业务案例（视频原文例子）
每天凌晨运行定时同步 Job，从业务数据库拉取新增文档构建向量索引；DBA 修改数据表结构，但是数据抽取接口没有同步更新适配；同步 ETL 任务照常跑完、不报任何错误告警，但拉回来的文档全部是空列；向量索引里面没有一条有效业务数据。
排查操作：直接查询统计向量索引内部的文档总数量。
判断与结论
如果索引文档总数为 0，直接锁定故障点：上游数据同步链路损坏；
优先修复同步链路，而不是修改检索参数。
第三层：过滤条件排查（元数据过滤误杀候选集）
故障根源：向量检索本身可以检索到候选 chunk，但是检索后的元数据过滤逻辑，把全部候选结果排除，最终对外返回 0 条。向量检索有结果，过滤之后归零。
业务场景例子（视频原文）
RAG 系统增加业务过滤规则，例如：只召回近 7 天文档、只召回指定类目文档、只召回状态为 “已发布” 的文档。当查询触发的过滤条件和索引元数据全部不匹配，全部候选被剔除。
排查核心技巧（视频原文）
对比查看过滤前的 TopK 原始结果 和 过滤之后返回结果。
如果过滤前有数据，过滤后是 0：确定是过滤逻辑误杀候选集。
定位手段：拿查询携带的过滤条件，和向量索引中实际存储的元数据字段做 diff 比对。
高频坑点例子（视频列举 3 类）
时区字段比对不一致；
枚举值大小写不匹配；
过滤条件用到的字段，在 Schema 中已经废弃不存在。
本层结论：索引有数据，向量检索拿到候选，过滤层可以直接造成对外零召回。
第四层：Embedding 版本一致性验证（高发于模型升级窗口期）
故障根源：写入知识库时用一套 Embedding 模型版本；线上查询检索时使用另一套 Embedding 模型版本。
原理说明：不同版本 Embedding 模型生成的向量，属于完全不同向量空间；向量距离计算全部变成随机无效数值，导致召回归零。向量数据库本身、索引数据本身没有损坏。
发生时机例子：做 Embedding 模型版本升级切换的时候，容易出现两端版本没有对齐。
排查动作：核对文档入库向量化使用的模型版本，对比线上检索服务推理使用的模型版本。
本层结论：向量库数据完好，但读写两端 Embedding 版本不一致，直接大量零召回。
三、视频明确警示：生产环境禁止的两个错误操作（坏路径，重点面试得分点）
❌错误操作 1：直接重启服务
视频原文结论：零召回绝大多数是数据链路问题，不是服务进程问题；重启服务解决不了故障；更严重的是重启可能冲掉故障现场日志，丢失排查证据。
❌错误操作 2：盲目直接重建索引
视频原文例子：如果根因是上游 ETL / 数据同步管道已经坏掉；就算重建索引，重建出来的依旧是空索引，故障复现，问题没有解决。
