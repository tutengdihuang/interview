一、开篇现象：反直觉的使用体验
使用 DeepSeekHarness 会出现一个反常现象：
对话不断变长，理论上输入 token 变多，推理应该更慢、费用更高；但实际后续对话首字秒出，账单出现 “缓存命中”，输入费用可以低至原价 1‑2 折。
核心原因就是服务端开启了Prefix Caching 前缀缓存，视频抛出面试高频题：KVCache 和 Prefix Caching 的关系；如果修改输入开头第一个 token，前缀缓存会发生什么。
❌错误认知：只失效改动的部分，后面内容还能缓存
✅正确结论：前缀缓存要求从第一个 token 开始完整匹配，开头一旦改动，整条缓存直接失效。
二、基础概念：KVCache 和 Prefix Caching 的区别
普通 KVCache
是大模型推理的显存中间数据，存储注意力计算的 Key、Value，用来加速单次请求内部生成；传统推理中，一次对话请求结束，这份 KV 缓存会立刻清空销毁，只服务当前这一次请求。就算下一个请求 90% 文本一样，也要全部从头重新计算 Prefill 预填充。
Prefix Caching（前缀缓存）
打破不同请求之间的隔离。当请求完成，只要显存没占满，不会直接丢弃 KV 数据，会把公共前缀对应的 KV 存入共享缓存池。
新请求进来，如果开头一大段 token 和缓存完全匹配，直接复用显存里已经算好的 KV，跳过消耗算力最重的 Prefill 预填充阶段，实现降低首字延迟、减少输入 token 计费。
本质：KVCache 是单次请求内复用；Prefix Caching 是跨请求、跨会话复用 KV Cache。
三、底层怎么实现快速查找缓存（vLLM、SGLang RadixAttention）
大量并发请求下，引擎要毫秒级判断哪些前缀可以复用，依靠Token 分块 + Radix Tree（基数树 / 前缀树）：
把文本切为固定大小 token 块（例如 16/64 个 token 为一块），每一块计算哈希；
将这些块组织成一棵前缀树索引放在显存。
企业 Agent 场景举例：100 个用户共用同一个知识库助手，一万 token 的系统提示词、工具定义就是树的主干，GPU 只计算、保存一份；每个用户的提问是主干分出的不同分支。
显存不足时，使用LRU 淘汰策略，清理很久没有访问的冷门分支，优先保留热门公共前缀，提升系统并发吞吐。
四、实际开发踩坑：为什么你的 Agent 没有享受到缓存红利？
很多开发者写 Agent，明明场景适合前缀缓存，但是延迟没降、费用居高不下，根源是前缀污染。
前缀缓存匹配规则极其严苛：必须从第一个 token 起 token 完全一致，不认语义相似。
典型错误写法
把动态变化内容放在 Prompt 最开头：比如时间戳、会话 ID、动态用户 ID 放在提示词第一行。
哪怕只改动开头一小部分，前缀树根部直接断裂，后面上万字静态文档、系统指令全部无法命中缓存，全部重新计算。
✅黄金实操铁律
静态固定内容放在 Prompt 最开头；所有动态变量（时间、会话 id、用户状态）全部挪到 Prompt 末尾。
五、全文核心总结
KV Cache：负责同一个请求内部的生成加速，请求结束就销毁；
Prefix Caching 前缀缓存：实现跨请求、跨用户复用 KV 缓存；
底层依靠 Token 分块 + RadixTree 前缀树做索引，显存紧张用 LRU 淘汰旧缓存；
坑点：开头任意 token 改动，整个前缀缓存失效；
Agent 开发最佳实践：固定 system 提示词、工具定义放在最前面，动态可变参数放到 prompt 最后，避免前缀污染，最大化缓存命中率，降本提速。

视频标题：Prefix Caching 前缀缓存：长对话为什么能降本提速？
主讲：小哲讲 agent 项目，配套引擎：vLLM / SGLang RadixAttention
【0 开篇引入：反直觉现象 + 抛出 2 道面试题】
现象：在 DeepSeekHarness 上使用，对话越聊越长，按常理输入 token 越来越多，Prefill 计算量变大，应该更慢、更贵；真实体验却是后面几轮对话首字秒出，账单上出现缓存命中，输入 token 计费降到原价 1~2 折。
核心解释引子：背后机制就是服务端开启了 Prefix Caching（前缀缓存，也常叫 Prompt Caching）。
直接抛出两个大厂面试原题：
面试题 1：KVCache 和 Prefix Caching 的关系是什么？二者是不是同一个东西？
面试题 2：如果我修改输入 Prompt 开头的第一个 token，前缀缓存会发生什么？
先给出判断题的正误对比：
❌ 误区答案：只失效改动的这一小段，后面剩下的文本对应的 KV 还能继续复用
✅ 标准答案：前缀缓存要求从第 1 个 token 开始完整连续匹配；只要开头任意一处 token 改动，整条前缀缓存直接全部失效。
【1 基础定义：KVCache（普通 KV 缓存）】
通俗比喻：KVCache 是大模型推理时写在显存里的 “计算笔记”，存的是 Attention 计算出来的 Key、Value 张量。
传统推理里 KVCache 的生命周期：只属于单次请求内部。
生命周期细节：一次请求 Prefill+Decode 生成完回答之后，这份 KV 笔记立刻被清空、释放显存。
局限例子：下一个新请求，哪怕和上一个请求 90% 文字都一模一样，只要是独立请求，引擎依然要从头走一遍完整 Prefill，全部重新算 KV，不能拿上一轮的 KV 来用。
作用边界：KVCache 解决的是同一个请求内部，生成后续 token 的时候不用重复算前面的 Attention（也就是加速 Decode 阶段）；它不支持跨请求、跨会话共享。
【2 基础定义：Prefix Caching 前缀缓存（Prompt Caching）】
核心突破：打破请求和请求之间的显存隔离。
缓存留存规则：一个请求跑完、生成结束之后，只要 GPU 显存没有被占满，引擎不会立刻销毁这条请求的 KV；而是把其中公共前缀部分的 KV 数据，存入全局共享缓存池。
命中逻辑：新请求进来，引擎做前缀匹配；如果新请求的开头一长串 token，和缓存池里某一条前缀 token 序列完全一致 → 直接复用显存里已经算好的 KV，直接跳过代价最高的 Prefill 预填充阶段。
带来两个直接收益：
收益 1：首 token 延迟大幅下降（首字秒出）
收益 2：输入侧 token 计费降低（平台命中缓存后，这部分命中的前缀不再按原价计费）
重要限定结论（视频原话）：收益不是固定的，取决于三个因素：缓存命中的前缀长度、推理引擎本身的实现、服务商的计费规则；不是开了前缀缓存就一定省钱提速。
一句话概括 Prompt Caching 的意义：消除大量重复公共前缀的重复 Prefill 计算。
【3 底层索引机制：怎么做到上万并发下毫秒级查找可复用前缀？（RadixAttention / Radix Tree 基数树）】
引擎代表：vLLM、SGLang 的 RadixAttention 就是这套实现。
分块策略：不会以单个 token 为索引单元；先把连续 token 切成固定大小的 token 块，例子里给的块尺寸：16 token / 64 token 每一块。
索引构建：对每一个 token 块计算哈希值；把这些块 + 哈希，在显存里组织成一棵Radix Tree（基数树 / 前缀树）。
树结构业务例子（企业 Agent 场景，视频重点举例）：
场景：100 个并发用户，都在使用同一个知识库问答 Agent。
固定主干：长达 10000token 的 System 系统提示词、工具调用定义、知识库固定摘要，是整棵树的主干。
缓存效果：主干这一万 token 的 KV，GPU只计算一次、显存里只存一份，所有 100 个用户共享。
分支：每个用户各自的提问、对话历史差异部分，是主干上分叉出去的叶子分支。
缓存淘汰策略：GPU 显存是有限的，不能无限存所有前缀；使用 LRU（最近最少使用）淘汰算法。
规则：很久没有被新请求命中访问的冷门前缀分支，优先被清理释放显存；热门、高频命中的公共前缀长期保留，最大化命中率。
【4 开发大坑：前缀污染（视频重点，Agent 开发最容易踩的坑）】
现象：很多开发者本地写 Agent，明明场景非常适合前缀缓存（有很长固定 system prompt），上线之后发现：延迟一点没降、账单也没有缓存折扣，缓存命中率几乎为 0。
根因总结：前缀污染。
污染根源：前缀缓存是严格的token 序列全匹配，只认 token 字节，不认语义相似；必须从第一个 token 连续完全对上。
典型错误写法（反面例子）：
把动态、每次都会变的内容，写在 Prompt 的最开头：比如时间戳、session 会话 ID、动态 user_id、每次变化的用户状态放在 Prompt 第一行。
后果：哪怕只是开头几个 token 每次都变，Radix Tree 的树根直接对不上，后面跟着的上万字固定 system、工具描述、知识库全部连带无法命中缓存，每一次请求都要完整跑 Prefill。
✅ 视频给出的唯一黄金布局铁律（工程最佳实践结论）：
所有静态、固定不变的内容，全部放在 Prompt 最前面；所有动态、每次请求会变化的变量，统一挪到 Prompt 的末尾。
正确布局示例：
Prompt 头部（固定，用来做缓存主干）：System 角色设定、工具 Schema、固定知识库文档、固定规则。
Prompt 尾部（动态，不污染前缀）：当前时间、session id、用户 id、本轮用户提问、动态会话状态。
【5 全知识点汇总结论（视频收尾总结，逐条）】
KV Cache：服务同一个请求内部，加速 Decode 生成阶段；请求结束就释放，不跨请求共享。
Prefix Caching（前缀缓存）：在 KV Cache 基础之上，实现跨请求、跨用户、跨会话共享 KV 前缀。
底层检索方案：token 分块 + 显存内 Radix Tree 前缀树索引；显存不够用 LRU 淘汰冷门分支。
硬性匹配规则：前缀匹配是严格从第 1 个 token 开始连续匹配；开头任意 token 改动，整条缓存失效。
Agent 工程落地核心原则：静态内容前置，动态变量后置，规避前缀污染，最大化缓存命中率，实现降本 + 降首字延迟。
【6 视频隐含面试延伸点（视频口述附带）】
区分：Prefix Caching 不等于 KVCache，Prefix Caching 是复用 KVCache 数据的上层调度 / 索引机制。
适用场景：大批量请求共用长固定 system prompt 的 Agent、知识库 bot、多轮长对话。
不友好场景：每一次请求开头都在变、几乎没有稳定公共前缀的业务，开了前缀缓存收益很低甚至没有收益。
