视频详细内容总结
这是一道大模型 Agent 开发、系统架构方向的程序员面试题解析视频，核心题目：AI 客服可以回答退款政策，为什么不能直接执行退款操作。
一、常见错误回答
很多人会回答 “给大模型加一个退款工具接口就可以”，视频指出这个答案代表工程经验不足。这道题不是考察会不会调用工具，本质考察大模型 “信息读取回答” 和 “业务写操作执行” 之间的权限边界。
回答政策属于只读信息输出；退款是会修改资金、订单数据的高风险写操作，二者风险、证据、责任完全不一样，不能全部交给大模型调用接口完成。
二、为什么不能让 AI 直接执行退款（技术 & 业务风险点）
并发 / 竞态问题
用户一边跟 AI 对话申请退款，同时网页端也发起退款。两个渠道同时请求，若模型只看对话上下文，无法判断订单实时状态，会出现重复退款。必须由业务服务通过版本号、数据库条件更新保证只有一次退款执行成功，不能信任大模型对话上下文里的旧数据。
幂等性风险
退款接口超时，大模型误以为调用失败，重复发起退款请求，造成重复退款。退款接口必须具备幂等设计，订单要有明确状态：处理中、成功、失败、待补偿，不能靠大模型来做状态判断。
异步流程问题
退款提交后是异步队列处理，不能由 AI 直接承诺用户到账时间，只能返回受理编号、当前处理状态，避免虚假承诺用户。
大模型本身不可靠
大模型会幻觉，可能自由拼接错误参数；对话上下文信息是旧的，不能代表此刻订单真实状态；自然语言意图明确，不等于业务条件全部满足。模型理解意图≠拥有执行权限。
三、正确架构思路：职责分离
大模型负责理解、解析、生成建议；确定性业务服务负责校验、执行高风险动作。不可逆的写操作，必须过授权、状态校验，必要走人工审核。
1、意图分成三类：查询、建议、执行
查询（只读）：读取订单、退款政策，AI 可以自动调用，无副作用。
建议：AI 解析用户诉求，生成退款原因、建议退款金额、整理证据，产出退款草稿。
执行（写操作）：真正提交退款。不能复用之前查询拿到的旧数据，业务服务要重新读取此刻最新订单状态，重新校验：用户身份、退款资格、退款金额上限、订单是否已经处理完成。哪怕前面 AI 已经查过一遍，执行阶段必须全部重新校验一遍。
2、工具分级 + 权限网关保护写操作
查询政策、生成退款草稿可以让 Agent 自动调用；
真正提交退款，要经过权限网关；
网关只接收严格结构化参数，拒绝大模型自由拼接的脚本；校验订单归属、幂等键、审批记录、业务状态；
Agent 只可以 “申请动作”，不能越过网关直接执行退款，把大模型和高危写操作隔离开。
四、面试标准回答模板
AI 客服可以自动做政策查询、退款资格理解判断；但退款属于高风险写操作，不能由大模型直接执行。真正退款提交，交由后端业务服务，重新校验用户身份、实时订单状态、退款金额、幂等键，完成之后再执行退款。模型答对、识别出退款意图，不等于拥有执行退款的权限。成熟 Agent 不是让模型什么都能干，而是不可逆动作前，模型没有最终决定权。
五、面试官追问：用户明确说要退款，为什么还要二次确认？
回答要点：
用户表达明确退款意图 ≠ 满足全部业务退款条件；
两个事情要区分：给用户确认展示退款金额与后果、系统校验身份与实时业务状态授权，两者缺一不可；
退款要做分级：自动退款、部分退款、异常退款，根据金额、用户风险、订单状态流转到不同审批流程；
所有拒绝、超时、转人工接管，都要完整记录原因，方便后续评估 Agent 效果，判断是 Agent 保护风险，还是规则太严苛导致大量转人工。
六、视频核心结论
读操作和写操作要严格分开；
高风险写操作做工具分级、权限网关保护；
不能信任大模型上下文里的历史数据，执行阶段业务层必须重新校验；
并发、幂等、异步状态是 Agent 工程面试的重要得分点；
Agent 定位是理解意图、生成建议，高危变更交给确定性业务系统处理。

视频完整逐点整理（全部要点、例子、结论，无省略）
原题：AI 客服可以回答退款政策，为什么不能直接执行退款操作
视频核心主线：这道题不是考 “会不会调用工具”，是考 Agent 工程里【读 / 写操作分离、风险边界、谁拥有最终裁决权】
一、开篇：先讲常见错误答案 & 误区
错误回答：给大模型加退款接口工具，让模型调用接口就可以退款
视频判定：这么答代表缺少线上工程落地经验，是 Demo 思维，不是生产级 Agent 思维。
核心区分定义（视频开篇第一组定义）
回答政策、查询订单：只读操作，没有副作用；就算模型说错，重新解释、纠正即可，损失很小。
提交退款：高风险写操作，会修改资金流水、订单状态，是不可逆、带资金责任的动作；一旦出错就是资金损失、对账问题、合规问题。
一句话前置结论：能看懂意图、能回答规则 ≠ 具备执行权限
二、逐条拆解：为什么不能交给大模型直接执行退款（4 大类风险，附带对应例子）
风险 1：并发竞态问题（多渠道同时发起退款）
场景例子：用户一边在 AI 对话窗口说要退款，同时自己在订单页面手动点退款；两个请求同时打到系统。
问题根源：大模型只依赖对话上下文里拿到的旧订单快照数据，它不知道此刻订单实时状态。模型看到上下文里订单 “可退”，就发起退款；但另一个请求已经抢先把订单改成退款中 / 已退款。
后果：不做状态强校验，出现重复退款。
视频结论：订单状态不能信任模型上下文缓存的数据，执行写动作前必须重读最新状态；靠数据库版本号、条件更新（update ... where status=待退款）来做状态保护，这个校验逻辑不能交给 LLM。
风险 2：幂等性风险（超时重试造成重复退款）
场景例子：Agent 调用退款接口，网络超时、响应丢包；大模型拿到超时，判定 “调用失败”，自动重试调用退款工具。
真实情况：后端其实已经收到请求、退款已经受理成功，只是响应没传回来。
后果：重试就重复退款。
视频要点：
幂等不是模型自己控制的能力；
幂等键、业务唯一流水号由业务网关 / 后端生成和校验；
幂等校验放在业务层硬编码，不能交给大模型判断 “我刚才有没有成功”。
风险 3：异步流程认知偏差（接口返回 200 ≠ 退款到账）
场景例子：Agent 调用退款接口，HTTP 返回 200，模型理解为退款完成，直接告诉用户 “钱马上到账”。
真实情况：退款提交只是进入异步队列，后面还要走风控复核、清算、支付渠道对账，是延迟到账，几小时甚至几天。200 只是【受理回执】，不是业务终态。
后果：AI 给用户虚假承诺，用户后续投诉、客诉上涨；并且 Agent 上下文可能提前销毁，后续排查没有链路。
视频结论：Agent 拿到受理流水号之后，只能告知用户 “已受理，给你受理编号，我们后续处理”；不能承诺到账时间；需要轮询流水号查询终态，这个轮询逻辑由业务调度层负责，不是模型自己判断。
风险 4：大模型本身固有的不可靠性（幻觉、参数拼接错误、意图漂移）
细分 4 个小点：
幻觉：模型自由生成退款金额、订单号、退款原因，拼错参数；比如用户要退 50，模型幻觉成 500。
上下文数据陈旧：对话一开始查的订单状态，聊了 10 分钟之后订单状态已经变了，但模型还在用老数据判断。
意图理解≠业务条件满足：用户明确说 “我要退款”，只代表意图明确，不代表满足全部退款规则（超过售后时效、商品已经签收、是特殊不可退商品、用户风控黑名单等）。
Prompt 提示词是软约束：提示词、系统 prompt 限制模型不要乱退款，属于软限制，可以被 prompt 注入、对话诱导绕过，不能作为资金安全的屏障。
视频结论：软约束（提示词）只能用来引导模型，高危动作的拦截必须是硬编码的代码校验。
三、正确架构方案：职责分离（视频核心架构设计，分三层意图）
总原则：模型负责理解、提议；确定性业务系统负责校验、裁决、执行
3 类意图分级
查询意图（只读，允许 Agent 自动调用）
例子：查退款政策、查订单当前状态、查售后时效；
权限：默认开放，只读工具，无副作用。
建议 / 草稿意图（半可控，Agent 可以自动生成）
例子：AI 整理用户诉求、生成退款草稿、填写退款原因、自动计算预估可退金额、整理用户上传凭证；
产出物：一份退款申请草稿，不是真正提交退款；草稿返回给用户确认，同时交给业务网关。
执行意图（写操作、高危，Agent 无权直接执行）
动作：真正提交退款；
强制规则：哪怕前面 Agent 已经查询过一遍订单，执行阶段业务服务必须重新读取一次最新订单快照，全套重新校验。
校验清单（视频明确列出，全部是代码硬校验，不是模型核对）：
用户身份校验：是不是订单归属人
订单实时状态校验：是否还在可退款状态
退款金额校验：不能超过可退上限
时效校验：是否还在售后窗口期
风控校验：用户历史退款频次、是否在风险名单
幂等键校验：本次动作唯一业务 ID，防重复
审批路由校验：判断走自动放行、人工审核
配套机制：工具分级 + 权限网关（安全闸）
工具打上标记：needs_approval（需要审批）
查询类工具：不需要审批；
退款提交这类高危写工具：标记为需要审批；
Agent 一旦想要调用标记工具，Agent 调度暂停，不能直接发请求。
权限网关能力：
只接收严格结构化参数，拒绝模型自由拼接的非结构化内容；
统一做权限、风控、幂等、状态校验；
路由分流：
小额、低风险、全部条件命中：自动放行执行；
大额、异常订单、风控命中、条件不满足：拦截，转人工审核；
人工审核通过之后，由网关发起退款，不是 Agent 发起。
审计链路要求（视频强调，合规必做）
全链路留痕：模型看到了什么上下文、模型输出的退款草稿、用户确认记录、网关校验的每一项结果、审批人、最终执行流水；所有记录可回溯，用于对账、客诉复盘、审计。
四、面试官追问：用户已经明确确认同意退款了，为什么还要二次校验？（视频完整回答）
用户确认动作，只代表【用户同意本次退款的金额与后果】；用户确认 ≠ 业务条件自动满足，两件事分开：
用户侧确认：展示退款金额、原路退回渠道、到账周期，让用户知情确认；
系统侧校验：独立重读数据、跑全部业务规则、风控、权限校验，不受用户确认影响。
退款分级流转规则：
自动退款通道：风险低、金额小、规则全部命中；
人工审核通道：高金额、异常售后、风控预警、证据不足；
拒绝通道：不符合退款规则，返回明确拒绝理由，告知用户。
兜底机制：所有被拦截、转人工、拒绝的案例，都要回流做指标统计；用来区分两种情况：
是 Agent 识别能力不足（意图识别错）；
是安全规则太严苛，导致大量正常退款都走到人工，需要调优规则阈值。
五、视频给出的标准面试口述模板（原文）
AI 客服可以自动做政策查询、理解用户退款诉求、生成退款申请草稿；但退款属于高风险写操作，不能由大模型直接执行。真正提交退款，要交给后端业务服务，在执行那一刻重新读取实时订单数据，校验用户身份、订单状态、退款金额、风控条件、幂等键，校验通过之后才执行退款。模型识别出退款意图，不等于模型拥有退款的最终执行权限。成熟 Agent 的设计思路，不是让模型什么都能干；凡是不可逆、带资金风险的变更动作，模型都没有最终决定权。
六、视频收尾总结（全部结论汇总）
读操作、写操作必须严格职责分离；
高危写操作要做工具分级、权限网关隔离保护；
任何写动作执行，不能信任模型上下文缓存的旧数据，业务层必须重读、全量重新校验；
Agent 天然要面对并发竞态、幂等、异步终态三大工程问题，这是面试高分要点；
Agent 正确定位：理解意图、信息收集、生成提议草稿；裁决权、最终执行权交给确定性业务系统；
提示词属于软约束，资金安全必须依靠代码层硬校验、状态机、数据库约束；
异步场景里：接口 200 受理回执 ≠ 业务终态完成，必须依靠业务流水号追踪真实结果；
高风险动作默认 Fail Closed（关闭自动执行），宁肯转人工，不要自动放行。
