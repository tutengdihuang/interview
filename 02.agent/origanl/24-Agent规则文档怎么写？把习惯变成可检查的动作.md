视频内容详细总结
这个视频主题是如何编写 Agent 规则文档，把人的工作习惯转化成 Agent 可以执行、可以检查的动作，属于提示词工程、AI 智能体 Agent 实操内容。
一、提出核心问题
很多时候 Agent 可以把任务做完，但输出做事方式不符合使用者的习惯。模型本身能力没问题，问题出在任务过程中的选择逻辑。
Agent 在复杂任务中会连续做大量判断：查什么资料、保留删除哪些内容、调用哪个工具、要不要二次修改。一次性问答约束不住一连串的决策，这就是规则文档要解决的痛点。
二、什么是 Agent 规则文档
规则文档是提前写给 Agent 的一套稳定工作要求（例如回答用大白话、修改项目前先读说明、交付前自查结果），一般存放在指定位置，Agent 工具会自动加载进上下文，不用每次对话重复输入一遍要求。
为什么不直接每次对话口头交代？
简短任务口头交代可行；但长任务对话内容越来越多，人为要求容易被上下文淹没，人也会忘记重复提醒。
规则文档的价值：把反复要用的工作习惯固定，提供统一、可维护、自动加载的入口。
重要提醒：规则文档不是万能的
长期保存≠绝对生效，不能靠一句 “这条最重要” 就无限提高权限。
不同 Agent 工具，规则文件加载时机、生效范围、优先级、文件长度限制都不一样，要先看工具文档确认：文件放哪个目录生效、冲突如何处理。
别人写好的规则只能参考，需要结合自己业务逐条适配。一般用 Markdown 格式编写。
三、规则文档内容怎么写（核心方法论）
1. 区分通用要求 和 业务专属工作习惯
通用要求：跨任务都能用，例如回答通俗易懂中文。
业务习惯：不同任务动作完全不一样。
做视频：关注配音、字幕、完整交付数据；
数据分析：关注统计口径、数据来源、结果校验。
规则越贴合真实业务场景，Agent 越知道该干什么。
2. 关键原则：把抽象期待，改成可观察、可检查的具体动作
判断一条规则写得好不好的标准：这条规则能不能指导 Agent 做出具体决定，能不能看到执行结果。如果只是表达态度，就要继续细化改写。
举例对比：
表格
不好的抽象描述（只有态度）	改写后可执行的动作规则
设计要高级，要有审美	开始设计前先参考知识库里已有的配色和构图
你要认真负责	交付前检查文件是否完整，打不开的文件先修复
抽象形容词 Agent 无法理解；改写之后，有执行时机、动作对象，事后还能核验有没有做到。
3. 不要一次性写一大堆规则
新手误区：一开始就写几十上百条规则。
弊端：很多凭空设想的规则并不是真实会遇到的问题；规则太多加重 Agent 理解负担，多条规则互相冲突，Agent 会无所适从。
正确迭代思路：规则从真实问题里慢慢生长出来
第一次 Agent 没达到预期，先口头纠正；
同一类问题反复出现 2‑3 次之后，再把这个约束写进规则文档；
工作习惯发生变化后，要及时删除过时、合并重复的旧规则，不能只增加不删减。
4. 区分不同层级规则的生效范围
要结合工具的域机制划分作用域：
全局规则：通用习惯，全局生效；
项目规则：整个项目的约定；
子目录规则：局部文件夹的特殊要求。
不同范围的规则放到对应层级，不要全部堆在一起。
四、视频最终结论
一份高质量 Agent 规则文档不是越长越好，核心目标是：把反复使用的工作方式，转化成可执行、事后可检查的动作，并且持续迭代维护这份文档。

1、什么是 Agent 规则文档
定义：一份提前交代给 Agent 的工作要求。
举例要求：回答优先用大白话；修改项目之前先阅读说明；做完任务之后检查结果。
存储与加载：保存在约定位置，Agent 工具依靠自身加载机制，自动带入任务上下文，不需要用户每一次任务都重新输入一遍要求。
2、为什么需要规则文档（痛点解释）
Agent 处理复杂任务，会连续做出很多次决定。
视频举例场景：制作视频任务。一连串决策：先查什么资料；哪些内容保留；哪些内容删除；调用哪一个工具；完成之后要不要修改。
这类长链条决策，不是一问一答就能约束住的，前面的工作要求会影响后续一连串选择。
反驳疑问：“每次任务开始前口述一遍要求行不行？”
短任务：口头交代可以生效。
长任务缺陷：对话内容越来越多，工作要求会被上下文淹没丢失；同时人自己也容易忘记重复交代约束。
规则文档核心价值：把反复需要遵循的工作习惯固定下来，提供一个稳定的维护、自动加载的入口。
3、重要现实提醒：规则文档不是万能的（容易踩坑认知）
“长期保存 ≠ 绝对优先生效，不等于模型一定照做”。
各个 Agent 工具之间存在差异：不同工具，规则文件的加载时机、作用范围、优先级设计全部不一样。
不能只写一句 “这条规则最重要” 就无限拔高某条规则权限。
使用前必须确认工具信息：
工具支持哪些规则；
规则文件放在哪个目录才会生效；
是否存在文本长度限制；
多条规则冲突的时候如何处理。
规则文件定位方法：
最直接：阅读当前工具官方说明文档；
替代方式：直接让 Agent 帮忙定位规则文件位置。
文件格式：普遍使用 Markdown，编辑操作本身难度低。难点不在编辑，在于内容怎么写。
参考他人规则的注意点：别人写好的规则只能用来理解写法；能不能适配自己业务任务，必须逐条做判断，不能直接照搬全套。
4、内容撰写第一点：区分【通用要求】和【业务专属工作习惯】
通用要求：可以跨多个任务复用。
例子：回答时使用通俗易懂的中文。
业务专属工作习惯：不同工作，需要规定的动作完全不一样。视频给出两组业务案例：
做视频任务：重点约束配音、字幕、完整交付数据；
做运营 / 数据分析任务：重点约束统计口径、数据来源、经验校验。
原则：规则内容越贴近真实业务工作，Agent 执行的时候越容易判断自己该做什么动作。
5、核心写作方法论：把抽象期待，改写为【可观察、可检查的动作】
核心判断标准（视频明确给出）：一条规则写进去之后，能不能指导 Agent 做出一个具体决定，能不能观察到实际执行结果。如果仅仅是表达态度，无法改变实际动作，就必须继续细化改写。

6、新手常见错误：一次性写几十上百条规则
弊端：
①凭空脑补出来的很多规则，并不是真实任务会遇到的实际问题；
②规则条目过多，增加 Agent 阅读理解负担；
③多条规则互相冲突，Agent 会混乱，不知道该遵循哪一条。
视频给出迭代模式：规则要从实际工作问题里面慢慢 “长出来”，不要一次性写完。
第 1 次 Agent 输出不符合预期：口头纠正本次即可，不要立刻写进文档；
同一类问题反复出现第 2 次、第 3 次的时候，才把约束整理写入规则文档；
后续维护：当自身工作习惯发生变化，要主动删掉过时规则、合并重复要求；不能只不断新增，不做删减清理。
7、规则分层：区分不同规则的作用域（生效范围）
要结合工具本身的域机制，划分层级，不要全部堆在一起：
全局规则：放通用、全场景都适用的习惯；全局生效；
项目规则：整个项目统一约定；
子目录规则：只针对局部文件夹的特殊要求。
不同范围的约束放到对应层级下面执行。
