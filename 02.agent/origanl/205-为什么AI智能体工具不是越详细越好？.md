视频内容详细总结
这个抖音视频围绕AI Agent 工具调用（Tool Calling）展开，同时也是一道 AI 开发面试题讲解，核心观点：Agent 的工具 Schema 并不是写得越详尽、暴露工具越多效果就越好，过度膨胀反而带来很多线上问题。
核心认知误区纠正
很多人误以为工具描述越细致、接口全部开放，大模型就会变得更聪明。
但工程现实恰恰相反：工具 Schema 不是给开发人员阅读的接口文档，而是供大模型做决策的操作菜单。菜单工具过多、工具名字相近、参数没有约束，会造成模型在多个工具之间摇摆，出现选错工具、参数填错，甚至误调用不该开放的能力。
本质不是模型智商不够，而是工具本身边界设计得很差。
总体设计原则：工具要少而准，围绕业务任务意图来设计，不要直接把底层内部 API 原样暴露给大模型。
做法：给到模型高层业务动作（例如 “创建退款申请”），底层复杂逻辑交给后端服务处理；大模型只需要负责选动作、补全必要参数。
五层工具 Schema 实战设计要点
1. 工具命名与描述，明确互斥边界
工具名称要直接体现业务结果，拒绝handleprocessquery这类模糊万能名称。
工具描述要写清楚：什么时候用、什么时候绝对不能用、调用前置需要什么信息。
区分动作边界：查询、写入类工具不能混为同一个工具。例：查询订单、创建退款不能封装成同一个ordertool，否则模型极易混淆读操作和写操作。
2. 参数约束，减少模型自由发挥
优先使用枚举值，尽量避免让模型自由输出字符串；能后端自动推导的值，不要交给模型猜测填写。
金额、用户 ID、时间、权限范围，增加格式约束，后端必须做校验。
高危操作，增加追踪字段：reason执行原因、evidenceid证据 ID、confirmtoken确认令牌，实现调用行为可追溯。
3. 工具分组 + 动态暴露工具集
不要把全部工具一次性全部给到每一轮对话、每一类用户。
举例：客服智能体不需要看到财务结算工具；普通使用者不能访问管理员工具。
根据用户身份、业务场景、对话任务阶段、审批状态动态裁剪可用工具。
可用工具越少，模型选择越稳定，系统安全风险也会降低，攻击面更小。
4. 定义失败语义：不光定义成功，还要定义错误如何处理
Schema 不能只写接口成功返回的格式，要告诉模型遇到各类错误之后该如何行动：
参数缺失 → 向用户追问补齐信息
权限不足 → 停止操作，向用户解释原因
接口超时 → 有限次数重试
返回结果数量过多 → 引导缩小查询筛选条件
5. 线上观测指标，用真实数据优化工具
工具好坏不靠主观评审，依靠线上统计指标：
工具命中率、工具误调用率、参数校验失败率、人工确认取消率、调用之后任务整体成功率。
重要：如果频繁出现工具选错，优先怀疑 Schema 设计缺陷（名字宽泛、描述重叠、参数自由度过大），优先修改 Schema，而不是归咎于模型能力差。
面试追问：如何控制工具总量，做好工具目录治理
新增工具之前，优先评估是否可以复用现有的业务工具动作，避免随意新增。
下线旧工具要检查 prompt 样本、调用依赖；修改工具参数要保证版本兼容。
如果不加管控，会堆积大量废弃历史接口，造成工具膨胀，线上稳定性持续恶化。
线上踩坑提醒
不要在 Schema 写模糊夸大的描述，例如 “该工具可以处理全部订单问题”，模型会把这个工具当成万能入口。
重点：模型做工具选择，最需要的是清晰的边界（能干什么、不能干什么），这远比长篇大论的描述更加关键。
面试标准答题模板
不会直接把底层内部 API 丢给大模型；而是抽象成少量业务层级工具；为每个工具明确适用场景、参数约束、权限边界、失败处理逻辑；依据身份、任务动态暴露可用工具；最后依靠线上数据持续评估、优化工具选择准确率。

抖音视频完整逐条拆解（全部要点、例子、结论无省略）
视频主题：为什么 AI 智能体 Agent 的工具 Schema 不是写得越详细、暴露接口越多就越好，同时是一道大模型开发面试题，来源：抖音 @小哲大模型 AI，视频号 7667219308115985061。
视频核心总定位：这道题表面考 Tool‑Calling 工具调用，本质考察候选人是否会设计模型可理解、可执行、可治理的工具接口。
一、大众普遍误区（视频开篇）
错误认知：Agent 工具描述写得越详细、暴露内部接口越多，大模型就越聪明。
半对答案：很多面试者回答 “描述写详细模型就会正确使用工具”—— 视频判定这个回答只对一半。
工程现实问题（工具膨胀带来 3 类故障）
模型选错工具
模型填错参数
意外暴露不该对外开放的内部能力
关键比喻结论：
工具 Schema不是给人类开发看的接口文档，而是给大模型做决策的操作菜单。
菜单太长、工具名字相似度高、参数自由度太高；模型会在多个相似工具之间摇摆。
现象看上去是 “模型笨、模型不行”，本质是工具边界设计得差，不是模型能力问题。
总设计原则（视频核心总结论）
工具 Schema 要做到少而准，围绕任务意图来设计，不要把内部 API 原封不动直接暴露给大模型。
实操示例
✅ 推荐做法：给模型提供高层业务动作，例如 create refund request（创建退款申请）
❌ 不推荐：直接丢十几个底层订单数据表接口给模型
底层复杂业务逻辑、数据库操作全部交给后端服务；
大模型只负责两件事：选择要执行什么业务动作、补齐必要入参。
二、五层实战设计框架（视频主体全部五层，每层包含要点、示例、结论）
第一层：工具命名 + 工具描述，明确互斥边界
命名规则：工具名字要直接体现业务结果；禁止使用模糊万能名称。
❌反面例子：handleprocessquery（万能处理查询，看不出业务行为）
描述必须写清楚三件信息
① 什么时候应该调用这个工具；
② 什么时候绝对不能调用这个工具；
③ 调用该工具之前，必须要具备哪些前置信息。
边界重点：区分互斥动作，读写不能混在一起
反面示例：把【搜索订单（查询读操作）】和【创建退款（写入高危操作）】封装在同一个工具ordertool。
后果：模型极易混淆查询动作、写入修改动作，乱触发写操作。
面试答题提示：不要只回答 “把描述写清楚”，一定要补充互斥边界这一点。
第二层：参数约束设计
参数设计总口诀：能用枚举，就不要让模型自由填写字符串；能后端推导出来的值，不要交给模型猜测填写。
重点管控字段示例：金额、用户 ID、时间范围、权限范围；
必须加上格式约束，并且后端一定要做校验，不能只靠模型保证参数正确性。
高危动作特殊参数设计（可追踪字段）
高危操作的参数建议增加：
reason：执行本次操作的原因
evidenceid：证据 ID
confirmtoken：确认令牌
目的：每一次高危工具调用，都能够完整追踪为什么执行该操作，实现行为溯源。
第三层：工具分组与动态暴露工具集
核心观点：不是每一个用户、不是每一个任务、不是每一轮对话，都应当看到全部工具。不能一次性把所有工具全部给到模型。
业务举例
客服 Agent，不需要看到财务结算类工具；
普通用户使用绘画 Agent，不应该看到管理员专属管理工具。
动态暴露的判断维度：根据用户身份、业务场景、当前任务阶段、审批状态，动态收缩裁剪可用工具列表。
结论：给到模型的可用工具越少，模型选择工具越稳定；同时缩小系统攻击面，安全性提升。
第四层：失败语义定义（很多工程师会漏掉）
Schema 不可以只定义接口成功返回的数据格式；必须定义各种失败场景，告诉模型失败之后应该做什么动作。
区分 4 种典型错误，对应模型后续处理动作（视频完整枚举）：
参数缺失 → 向用户追问，补齐缺少信息
权限不足 → 停止执行操作，向用户解释原因
接口超时 → 允许有限次数重试
查询返回结果太多 → 引导模型缩小查询筛选条件
不同错误类型，后续处理逻辑完全不一样，需要在工具体系中预先定义。
第五层：线上观测指标（工具好坏不靠开会评审，看线上真实数据）
需要持续统计的 5 个线上指标：
工具命中率
工具误调用率
参数校验失败率
人工确认取消率
调用工具之后的端到端任务成功率
重要工程结论
如果线上经常出现工具被错误选择，优先怀疑是 Schema 设计缺陷（工具名字定义太宽泛、多个工具描述语义重叠、参数自由度过大）；优先修改 Schema，而不要归咎于大模型本身能力不足。
三、面试官追问：如何控制工具数量？工具目录治理（视频专门回答追问）
新增工具管控：新增一个工具之前，首先评估现有业务动作能不能复用，不要随意新增工具。
下线旧工具注意点：工具下线前，要检查依赖：prompt 评测样本、日志调用依赖关系，不能直接粗暴删除。
修改工具参数：修改工具参数必须保障版本兼容。
风险后果：团队不加管控随意新增工具，会不断堆积大量历史废弃接口垃圾；工具集合持续膨胀，线上整体稳定性必然持续下降。
四、线上踩坑提醒（视频单独补充的实战坑）
❌不要在 Schema 写模糊夸大承诺话术。
反面例子描述文案：“这个工具可以处理所有订单问题”。
问题：大模型会直接把该工具当成万能入口，什么请求都调用它。
✅正确写法：明确写清楚输入条件、输出字段，同时写明这个工具不能处理哪些情况。
关键结论：模型做工具选择决策的时候，最需要的不是广告式的功能吹嘘文案，而是清晰的能力边界；这件事，远比写一大段长长的描述更加重要。
五、视频给出的面试完整标准回答模板（可以直接复述给面试官）
我不会直接把内部底层 API 直接丢给大模型；而是先抽象为少量业务层级工具。给每一个工具设计清晰的适用条件、参数约束、权限边界以及失败语义。然后根据用户身份、当前任务阶段动态暴露可用工具集合。最后依靠线上日志、统计指标持续评估、优化工具选择准确率。
