视频内容详细总结
这个视频主题：全自动 AI 漫剧 Agent，仅仅对接剧本、文生图、文生视频接口并不等于项目完成，真正稳定可用，还需要额外的工程设计，作者小哲提出整套系统核心分为三大关键环节：锁定需求、拆分模块、搭建检查‑修复闭环，如果缺少任意一环，系统出错就只能全部流程重新运行，无法局部修复。
一、提出核心疑问
很多人以为把写剧本、文生图、文生视频 API 接口接通，AI 漫剧 Agent 就开发完成。但实际会遇到两个现实难题：
用户需求变更后，剧中人物形象、设定能不能保持统一；
如果最终成片效果不合格，系统能否分清是剧本的问题，还是分镜的问题，精准修改，而不是全部重跑。
观点：调用接口只是起点，“能跑出一次结果” 和 “稳定持续完成任务” 中间，是工程设计的差距。
二、环节 1：锁定并统一需求（结构化需求文档）
用户给出的原始需求通常模糊笼统，比如同样是漫剧，都市修仙、古风虐恋，对故事风格、角色、场景要求完全不一样。
解决方案：把用户需求整理成一份结构化需求文档，故事大纲、剧本、分镜、提示词全部模块共用这一份文档；
作用：避免各个模块各自解读、猜测用户需求；文档作为统一约束，后续每一步产出都可以对照这份文档校验；
需求变更处理：一旦需求改动，优先更新这份文档，再判断哪些产出会受影响，而不是只修改某一步提示词，其他模块继续沿用旧需求逻辑工作。
三、环节 2：拆分职责单一的模块节点
把完整的漫剧生成链路拆成独立节点：需求分析、故事大纲、角色场景设计、剧本生成、分镜拆解等。
每个节点明确定义输入、输出数据；
好处：系统出错时，可以精准定位是哪一个环节出问题，不用整体排查整套系统故障。
专门解决：角色一致性问题
维护角色卡、场景卡，记录角色外貌、服饰、体型、场景特征，作为系统状态记忆；
每次生成画面，把角色 / 场景卡片信息灌入提示词，用来约束生成效果；
注意：角色卡只能降低跑偏概率，AI 模型依然会出现画面偏移，角色卡不能替代结果校验检查步骤。
四、环节 3：搭建分职责的检查 + 自动修复闭环
不能只有一条单向固定流水线，要做反馈控制回路，实现局部修复，拒绝全部推倒重来。
评估器做职责拆分：剧本评估器校验剧本内容，分镜评估器校验分镜内容；
评估输出必须是结构化检查报告：不能简单输出 “好 / 不好”，要写清楚哪些项合格、哪些项不合格，问题属于哪一份产出物；
根据问题定向回退修复：
如果角色设定冲突，回退到角色设定或者剧本模块做修改；
如果分镜描述模糊，交给分镜模块重新处理；
修改完成后，复查被影响的产出，做到问题可追踪、定向修复，而不是整条链路从头运行。
五、视频最终结论
创作类 AI Agent（AI 漫剧）系统好坏，看三个关键点：
是否有统一的需求来源；
故障是否可以定位到独立节点；
检查结果能不能驱动定向修复。
单纯对接各类生成接口，只是整个工程的起点，不等于产品落地完成。

视频标题：全自动 AI 漫剧 Agent，接通接口后还缺哪些工程设计？
主讲：小哲
核心总纲前置：接上剧本生成、文生图、文生视频接口 ≠ 完成全自动 AI 漫剧 Agent；能跑出一次结果，和稳定持续交付，中间差一层工程设计。整套系统必须要有三大环节：锁定需求、拆分模块、搭建检查 + 修复闭环；三个环节缺任意一个，一旦出错，系统只能整条链路全部重跑，无法局部修复。
【开篇抛出两个核心拷问（视频开头设问）】
如果用户需求发生变更，漫剧里的角色形象、人物设定能不能保持统一？
如果最终成片效果不合格，系统能不能分清问题根源：到底是剧本问题，还是分镜问题？能不能定向修改，而不是全部重跑？
开篇观点：很多人误以为把几个生成 API 对接串联起来，这个 Agent 项目就做完了，这是误区。调用接口只是起点。
第一大环节：锁定需求（结构化需求文档）
1. 为什么要先锁需求（理由）
用户原始口头需求天然模糊、笼统。不同题材漫剧，整套约束完全不一样。
✅ 视频举例：同样是做漫剧，都市修仙题材 VS 古风虐恋题材，在故事基调、角色人设、美术画风、场景氛围上要求完全不同。
2. 方案：产出一份【结构化需求文档】
下游所有模块：故事大纲模块、剧本模块、分镜模块、提示词拼装模块，全部读取同一份需求文档作为统一基准。
核心目的：避免每一个子模块各自独立理解、各自猜测用户需求，避免理解偏差。
文档作用：作为全链路统一约束标准，后续每一步产出物，都可以拿着这份文档对照校验。
3. 需求变更的处理规则（重点细节）
当用户需求改动时：
优先更新这份结构化需求文档
再去判断：哪些下游产出物会受到本次变更影响
❌ 禁止做法：只单独修改某一步的提示词，其余模块继续沿用旧的需求逻辑运行（会造成全链路矛盾）
第二大环节：拆分职责单一的模块节点
1. 拆分方式
把漫剧完整生产链路，拆成一个个职责单一、边界清晰的独立节点，视频列出节点清单：
需求分析 → 故事大纲 → 角色场景设计 → 剧本生成 → 分镜拆解
（后续隐含：提示词拼装、文生图、文生视频、成片合成）
2. 每个节点强制规范
每一个节点，都明确定义：输入数据、输出数据、交给下一个节点传递的数据。
收益：系统出故障时，可以精准定位故障落在哪个环节；不需要盲目的排查整条链路。
3. 子问题：角色一致性怎么解决（视频单独拿出来讲）
方案：维护角色卡、场景卡，作为系统持久化状态记忆
卡片内记录内容：角色外貌、服装、身高、体型；场景固定特征
运行规则：每次调用文生图 / 文生视频生成画面时，把角色卡、场景卡信息灌入提示词模板，用来约束生成
⚠️ 重要限定结论（视频重点提醒，不可省略）：
角色卡、场景卡只能降低画面跑偏的概率；AI 生成模型本身依然有概率出现形象漂移。角色卡不能替代后置的结果检查步骤。
第三大环节：搭建分职责的检查 + 自动修复闭环（Agent 核心，反馈回路）
1. 检查器也要按职责拆分，不能一个大评估器全包
剧本评估器：专门校验剧本内容
分镜评估器：专门校验分镜内容
2. 评估输出硬性要求
评估器不能只简单输出 “合格 / 不合格、好 / 不好”。
必须输出结构化检查报告：逐条写明：哪些检查项通过、哪些检查项不通过；并且标注清楚：这个问题归属哪一份产出物（剧本产出 / 分镜产出 / 角色设定产出）。
只有结构化的问题报告，才具备驱动自动修复的能力。
3. 定向回退修复的两个视频举例
评估发现：角色设定前后矛盾 → 定向回退到【角色场景设计节点】或者【剧本节点】修改，不需要重跑大纲、分镜、绘图
评估发现：分镜描述模糊、画面描述不可执行 → 定向交给【分镜拆解节点】重新处理
4. 修复后的动作
修改完成后，只复查本次修改所影响到的产出内容。
核心目标：问题可定位、可追踪、局部修复；拒绝每次效果不好就整条流水线推倒重来。
5. 架构补充说明
只有单向顺序流水线（串行跑一遍），也能跑出成片；
但如果想要系统具备 “判断问题位置、自主选择回退到哪个节点修改” 的能力，就必须增加这套反馈控制回路（闭环），这才是 Agent 和普通流水线脚本的区别。
视频收尾：作者给出的最终评判标准（评估创作类 Agent 的 3 条标准，最终结论）
判断一个 AI 漫剧这类多模态创作 Agent 工程做得好不好，只看三点：
是否存在一份统一、唯一的需求来源（结构化需求文档）；
链路节点是否解耦，故障能不能精准定位到独立节点；
质量检查输出的结果，能不能驱动定向、局部修复。
收尾一句话总结：仅仅对接各类生成接口，只是这套工程的起点，不等于产品落地完成。
