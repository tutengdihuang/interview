视频详细总结
该视频是一道大厂 RAG 面试题讲解，核心问题：在合同审查场景下，RAG 遇到 “不允许、不支持、除外” 这类否定条款，如何避免把禁止条件理解反、输出错误答案。重点指出不能简单做否定词关键词识别，要完整处理语义边界，搭建完整 RAG 闭环。
一、题目本质与核心认知
场景限定：合同审查。举典型例子：“不得退款” 不等于全部场景都不能退款，合同往往存在例外情形。
系统必须同时解析 4 个要素：否定范围、例外条件、适用主体、生效时间，只识别否定词会大量出错。
基础处理思路：把否定词和它修饰的对象绑定之后再抽取业务条件；检索环节保留完整原文片段，输出答案必须逐条附上原文依据。
举例：主合同写明禁止退款，但售后政策约定质量问题可以退款；如果仅检索 “退款” 关键词，忽略 “除非、但、仅限、不” 这类限定词，就会得出完全错误结论。
问题排查原则：保存输入、配置、模型版本、中间链路结果，定位第一个出错环节，选择调参 / 重试 / 降级，不能直接让模型重新猜一遍。
二、工程实现方案：入库、查询、召回后分阶段治理
1. 文档入库阶段
恢复文档结构，还原标题、合同条款、表格、附件之间关联；
给每一个文本片段附加元数据标签：文档 ID、页码、版本号、生效时间、适用组织、权限标签。
2. 用户查询阶段
对用户提问做拆解，拆分出：主体、动作、条件、时间；
先依靠元数据做原始数据过滤，再结合关键词召回 + 向量召回混合检索。
好处：避免纯向量相似度把否定词、条款编号、时间信息淹没；业务口语、别名可以单独做改写处理。
3. 召回之后：证据充分性校验（关键环节）
召回很多相关片段≠已经覆盖用户问题全部条件，要校验证据是否完整；
如果多条文档证据互相冲突：优先对比文档权威性、版本、适用范围；依旧无法判定，则追问用户或者直接拒答，不强行编造答案；
输出答案必须绑定原文出处位置；
评测指标拆分：切片完整性、召回率、重排命中率、引用准确率、内容忠实度。
面试提醒：不要只讲向量数据库，要完整讲解析→过滤→召回→证据校验→原文引用完整闭环。
三、面试答题方法论、方案取舍、上线运维
方案验证要做对照实验
固定模型、配置、输入长度、数据版本，仅改动单一变量，对比修改前后：正确性、边界 case 表现、延迟、显存 / Token 开销。
应用型题目：链路要可追溯；证据不足时要有停止、追问逻辑；
原理类题目：用张量、耗时、任务实例说明，不要死记定义。
回答方案的时候，要同时说明假设条件、实现代价、评测手段，证明方案在业务场景下可行。
方案取舍应答思路（面试官追问时）
先讲业务目标指标与约束，再解释选型理由；
系统要预设兜底逻辑：证据不足、信息模糊、指标异常时，支持追问、降级、回退、人工接管，明确什么场景不能自动输出结果。
上线之后运维
关键指标、版本信息做时间线记录；故障发生可以区分根因：是输入数据变化、配置改动、模型升级还是外部依赖问题。
修复完 bug，把该案例加入回归测试集；同时检查相邻业务，防止修复 A 问题，导致其他场景效果变差。
四、核心观点总结
合同类 RAG 最大坑：只抓取局部词汇，忽略完整规则。
可靠 RAG 目标不是简单检索到关键词，而是证明得出的结论是在哪些约束条件下才成立。

一、面试原题
面试官提问：RAG 遇到 “不允许、不支持、除外” 这类否定条款，怎么避免把禁止条件答反？
1、题目表层 vs 真实考察点
表层问题：否定条款的语义边界识别
真实考察点：“不得退款不等于所有场景都不得退款”；合同规则普遍带有约束条件、例外，不能只看字面否定词，系统必须同时解析四要素：否定范围、例外条件、适用主体、生效时间。
面试开场总起回答（可以直接复述给面试官）：不得退款不等于所有场景都不得退款。系统要同时理解否定范围、例外条件、适用主体和生效时间。
2、业务示例（视频唯一业务案例）
案例：主合同明确禁止退款，但是售后政策约定，质量问题场景可以退款。
错误行为：仅仅把 “退款” 作为关键词检索命中，忽略不、除非、但、仅限这类边界限定词。会造成 RAG 输出结果完全颠倒。
正确处理逻辑：
1）先把否定词和它真正修饰的对象绑定，再做业务条件抽取；
2）检索层保留完整原文窗口，不做碎片化截断；
3）输出答案必须逐条引用原文依据；
4）回答要给出输入条件 + 可验证结果，不能只输出一句结论。
3、故障排查原则（链路出问题时怎么做）
坑：很多人出问题直接让大模型重新生成猜答案。
正确排查：完整保存输入、配置、模型版本、全部中间链路结果；定位第一个偏离预期结果的节点；根据根因选择：调整参数 / 重试 / 降级。禁止直接让模型再猜一遍。
二、工程实现：入库、查询、召回后三阶段分开治理
核心工程思想：入库治理和查询治理要分开，不要全部丢给向量检索。
阶段 1：文档入库环节
恢复文档原始结构：还原标题、合同条款、表格、附件之间的关联关系；
给每一个切片片段追加元数据标签：文档 ID、页码、版本、生效时间、适用组织、权限标签。
元数据作用：后续可以做过滤，防止纯向量相似度淹没编号、否定词、时间信息。
阶段 2：用户查询处理环节
对用户原始提问做拆解，拆解 4 个维度：主体、动作、条件、时间；
优先使用元数据做原始数据过滤；
使用混合检索：关键词召回 + 向量召回；
专门预留入口处理业务口语、别名改写。
价值：避免纯向量只看语义相似度，把否定词、条款编号、日期信息稀释丢失。
阶段 3：召回完成之后：证据充分性检查（高风险核心步骤）
重要结论：召回得到很多相关片段 ≠ 已经完整覆盖用户问题的全部条件。
校验召回证据是否完整覆盖用户问题的全部条件；
多条文档证据互相冲突的处理逻辑：
第一步：对比文档权威来源、版本、适用范围；
第二步：如果对比之后依旧无法裁决，则对用户追问，或者直接拒答，不强行编造结论；
输出答案强制约束：答案每一条结论，都绑定原文位置出处；
评测指标要拆开，不能只看最终答案：切片完整性、Recall 召回率、重排命中、引用准确率、内容忠实度。
面试提醒：不要只讲向量库，要完整讲述链路：解析 → 过滤 → 召回 → 证据校验 → 原文引用闭环。
三、面试答题的方法论：方案验证、方案取舍、原理题 / 应用题区分
核心思想：回答方案的时候，要同时讲清楚假设条件、实现代价、评测手段，证明这套方案在业务场景中真正成立。
1、做方案验证必须做对照实验
实验约束条件：固定模型、配置、输入长度、数据版本，只改动一个主要变量。
对比改动前后下面指标的变化：正确性、边界样本表现、延迟、显存消耗、Token 成本。
两类题目答题区分
1）应用型题目（例如合同 RAG）
链路必须可追溯；
必须校验检索、工具调用、状态、最终答案整条链路；
定义兜底行为：证据不足时，系统要具备追问、停止输出的逻辑。
2）原理类题目
不要死记硬背定义；
使用张量形状、各阶段耗时、代表性任务实例来辅助说明原理。
2、面试官追问方案取舍时的应答思路
先讲业务目标指标与业务约束；
再解释为什么选择当前实现路径；
明确系统兜底边界：遇到证据不足、状态不明、指标越界，系统要有明确的策略：追问、降级、回退、人工接管；
必须说明：这套方案在什么情况下不能自动运行，不能输出自动答案。
四、上线之后运维要点
将关键业务指标、版本信息放在同一条时间线上记录；
故障定位：区分问题根因：输入分布变化、配置调整、模型升级、外部依赖问题；
修复完问题之后：把该异常案例加入回归测试集；
同时检查相邻业务任务：防止修复 A 问题，造成其他场景效果退化。
