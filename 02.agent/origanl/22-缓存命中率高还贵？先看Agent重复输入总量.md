视频详细内容总结
视频主题：Agent 开发，为什么缓存命中率很高，但 Token 账单依然很贵，讲解 Agent 上下文管理与成本优化思路。
一、核心现象：缓存命中率高≠成本低
很多人做 Agent 时，监控看到缓存命中率很高，但实际接口账单开销依旧很大。
关键点：缓存只是打折计费，不是免费。一份很长的历史上下文，每一轮请求都会重复发送；哪怕全部缓存命中，每一轮都会产生费用，反复累积之后总开销依旧很高。
1、Agent 无状态调用的计费原理
Agent 接口大多是无状态调用：每一次 API 请求，都要把全部历史对话、工具返回结果、当前用户指令完整打包传给模型。
举个例子：用户只输入 “继续” 两个字，但发给模型的请求，会附带全部过往历史，不只是两个字。
重复的前缀历史：命中缓存，按缓存折扣价计费；
新增内容、无法复用的部分：按正常输入 Token 价格计费；
模型输出内容，单独算输出 Token 费用。
注意：各家大模型厂商缓存规则、计价不一样，不能拿一家规则套全部，成本核算要以自己账单和接口用量为准。
2、算账示例（示例价格，非真实报价）
历史上下文共 70 万 Token，缓存命中每百万 Token 0.21 元。
单次调用：即使全部缓存命中，这一轮就要花费 0.21 元；
如果连续多轮，每一轮都携带这份完整历史，这笔开销每轮都会重复产生。
所以命中率高，仅代表很多内容享受折扣，不代表总花费就低。
二、两种主流降本方案：上下文压缩、任务换新对话（任务交接）
目标：减少不必要重复输入 Token，同时保证 Agent 任务可以正常执行完成，不能为省钱把关键信息弄丢。
方案 1：上下文压缩（摘要总结历史）
做法：把很早之前的任务过程，整理成简短事实摘要；保留近期有用的原始消息，后续请求不再携带全部完整历史，以此缩小输入 Token 规模。
压缩存在两面风险
生成摘要本身就要消耗 Token，会带来额外成本；
如果摘要写得不好，丢失用户约束、关键信息，Agent 后续任务会出错返工，返工产生的开销，会把压缩省下来的钱全部吃掉。
压缩的两个常见误区
误区 1：模型窗口很大，就硬扛，每次把上下文直接用满；
误区 2：压缩触发太早，隔几轮就频繁做一次总结，频繁生成摘要带来额外成本。
压缩策略没有固定标准答案：需要调整触发长度、保留消息范围，同时观察 Agent 任务是否还能正常跑通。
哪些信息必须保留，不能被压缩掉
不能简单按比例截取消息，优先保留：
当前任务目标、已经做出的关键决策；
还没有做完的待办事项；
用户确认过的硬性要求；
当前文件 / 环境状态；
未解决的问题。
已经执行完毕、不再需要的工具完整日志可以精简。
认知纠正：不是摘要越短就越省钱。要对比完成同一个完整任务的整体总成本，而不是单轮调用的开销。
方案 2：合适节点开启新对话，做任务状态交接
思路：旧对话历史太多，就开启全新会话窗口；但是不能直接开新对话就完事，要手动保存任务状态，把必要信息迁移到新会话。
需要提前记录：已经完成工作、下一步要干什么、所有不能丢失的约束条件；
新对话按需读取这份保存好的状态，不再携带旧会话全部冗余历史。
外部记忆 / 任务交接的成本
状态写入需要整理信息；读取检索信息之后，取回的内容依然要占用上下文 Token。
如果交接信息不全，Agent 会重新查询资料、重做步骤。
只有当记忆复用价值足够高、任务状态恢复可靠的时候，换新对话才可以降低整体成本，否则只是把消耗从一处转移到另一处，没有真正省钱。
三、怎么评估优化效果（重要评估指标）
不要只盯着缓存命中率这一个指标，需要统计观测完整数据：
缓存命中输入 Token、未命中输入 Token；
输出 Token；
压缩执行次数、任务交接带来的额外开销；
Agent 任务最终完成质量。
重点认知：
对比完整任务的总账单，不要只看单轮调用是否变便宜；
不要看到缓存命中率下降，就直接判定优化失败。
有时候经过压缩之后，总输入 Token 总量大幅下降，哪怕缓存命中率有所降低，整体总费用依然是下降的。
四、视频最终核心结论
Agent 降本的核心目标：削减不必要的重复输入 Token，同时保证任务所需关键信息不丢失，保证任务质量；
缓存命中率只是一个中间观测指标，不是最终结果，不能当作优化好坏的唯一判断标准；
上下文提前压缩、任务状态交接是两套可测试的优化策略，要结合模型定价、任务长短、状态恢复效果去选择，不存在固定的节省比例。

一、第一层核心认知：缓存是打折计费，不是免费（视频第一大板块）
很多人的误区：缓存命中率高 = 省钱、账单低
主讲核心原话：缓存通常是打折，不是免费；一份很长的历史反复发送，就算是折后单价，金额也会一轮一轮持续累积
无状态 API 调用底层逻辑（Agent 默认调用模式）
大模型 API 是无状态：每一次独立请求，都要把模型本次需要看见的全部上下文打包传给模型
打包内容包含：全部历史对话、过往工具返回结果、用户当前最新指令
直观例子：用户只发 2 个字「继续」，发给模型的请求 payload，不是只有 “继续”，而是附带前面所有轮次完整历史
一轮请求内 Token 计费拆分（三类分开计费）
重复的前缀历史、和上一轮完全一致的部分：命中 KV 缓存，按缓存折扣单价计费
新增内容、发生变化、无法被缓存复用的部分：按正常输入 Token 原价计费
模型输出内容：输出 Token 单独计费，不走缓存，每一轮输出都要花钱
厂商规则提醒：不同服务商计价项目、缓存规则不一样，核算成本必须以自己的账单、接口返回用量为准，不能拿一家厂商规则套全部模型
视频内置算账示例（纯演示示例价格，不是真实报价）
条件：历史上下文合计 70 万 Token；缓存命中输入单价：每百万 Token 0.3 元
单次本轮开销计算：70 万 × 0.3 元 / 百万 = 单次 0.21 元
重点：只要下一轮继续携带这份完整 70 万历史，这 0.21 元这一笔开销会再次产生，每一轮重复收取
配套结论：命中率高，仅仅代表大量内容享受折扣价，完全不能代表总账单低
二、方案一：上下文压缩策略（第二大方案，完整正反面、误区、保留规则）
压缩做法：把很早之前的任务过程，整理成简短事实摘要；保留近期还在生效、有用的原始消息；后续调用不再携带全部原始长历史，缩小每一轮输入 Token 规模
压缩带来的收益：降低后续每一轮请求的输入 Token 基数，减少重复发送的历史内容
压缩自带两项风险（视频重点强调，不可忽略）
风险 1：生成摘要这个动作本身就要消耗 Token，带来新增成本
风险 2：摘要写得不好、丢失约束信息 → Agent 后续执行出错、反复返工；返工产生的 Token 开销，会直接把压缩省下来的钱全部吃掉
压缩触发策略没有固定标准答案
误区 1：模型窗口很大，就无脑硬扛，每次直接把窗口塞满全量历史
误区 2：压缩触发太早、太频繁，隔几轮就总结一次，摘要本身开销越堆越高
调参方式：同时调整两个参数 ——触发压缩的 Token 阈值（触发长度）、需要保留原始消息的范围；调完之后观测 Agent 任务是否还可以正常跑完
消息保留规则：不能简单按比例截断消息，优先级判断，下面这些内容绝对不能被压缩丢失
✅ 当前任务的目标
✅ 已经做出的关键决策
✅ 还没有做完的待办事项
✅ 用户确认过的硬性约束、要求
✅ 当前文件 / 环境状态（例如文件路径）
✅ 尚未解决、待排查的问题
可以精简压缩：已经执行完毕、不再需要回看的完整工具尝试日志（举例：长任务里面一次失败、已经放弃的工具调用记录，不需要完整保留原文）
压缩的重要结论：不是摘要越短就越省钱。对比好坏，要看完成同一个完整任务的总成本，而不是单轮调用开销
三、方案二：合适节点开启新对话 + 任务状态交接（第二个降本方案，完整边界）
方案思路：旧会话历史膨胀到很大之后，新开一个全新对话窗口；但不能直接开新对话就完事，必须手动持久化保存任务状态，把必要信息迁移到新会话
交接之前，必须记录保存的状态清单：
已经完成了哪些工作
下一步需要执行什么
所有不能丢失的约束条件、用户硬性要求
新会话的读取逻辑：新对话按需读取这份保存好的状态摘要，不再携带旧会话全部冗余历史
外部记忆 / 任务交接本身自带成本（视频明确指出，交接不是零成本）
写入成本：整理、生成交接状态摘要，消耗 Token
读取成本：检索召回状态之后，取回的内容依然要放进上下文，占用输入 Token
交接失败风险：交接信息不全、关键状态丢了 → Agent 会重新查询资料、重做之前已经做完的步骤
方案最终判断结论：只有记忆复用价值足够高、任务状态恢复可靠的时候，换新对话才能降低整体 Token 用量；否则只是把开销从会话 A 转移到会话 B，没有真正省钱
四、优化效果评估体系（视频第三板块：怎么判断优化好不好，观测指标）
核心原则：不要盯着缓存命中率单一指标判断优化好坏
需要统计、记录的全部观测项：
缓存命中输入 Token 量
缓存未命中输入 Token 量
输出 Token 总量
压缩执行次数、压缩带来的额外开销
任务交接带来的额外开销
Agent 任务最终完成质量（是否出错、是否返工）
两条关键评估结论
对比基准：对比同一个完整任务的总账单，不要只看单轮调用有没有变便宜
不要把命中率下降直接判定优化失败：很多时候压缩之后，整体输入 Token 总量大幅下降，哪怕缓存命中率数值变低，最终总费用依然下降
五、最终总结论、底层心法（收尾总结）
两套方案定位：上下文提前压缩、任务状态交接，是两套可测试的策略；没有通用固定节省比例，需要结合三点选择：模型定价、任务长短、状态恢复效果
成本优化底层第一性原理：
✅ 核心目标：削减不必要的重复输入 Token
✅ 约束前提：保住任务继续执行所必需的关键信息，不能破坏任务交付
指标定性结论：缓存命中率只是中间观测指标，不是优化好坏的最终结果

长会话自带持续成本，只要每轮全量携带历史，高命中率也会持续累积账单
