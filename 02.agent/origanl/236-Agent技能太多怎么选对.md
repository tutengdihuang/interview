视频主题：AI 面试题：Agent 技能（Skill）数量很多时，如何保证大模型正确选择工具 / 技能。
核心观点
当 Agent 技能从十几个扩张到上百个，只靠优化提示词没用。问题本质不再是 prompt 写得好不好，而是技能选择变成检索路由问题，要搭建一套「召回‑筛选‑确认‑反馈」的工程路由系统，不能把全部技能都塞给大模型让它硬选。技能越多，越容易选错，重点是快速缩小候选集合。
四大工程方案
给技能加上结构化元数据
不只写一段文字描述，为每个技能标记：适用任务、输入输出格式、前置条件、禁用场景、示例问题。系统可以直接按字段过滤，避免全部技能灌入上下文。
两级召回策略
粗召回：标签、关键词、规则，快速剔除完全无关技能，追求速度；
精召回：Embedding 向量 / 小模型做语义相似度匹配，保证准确度。
不建议直接全量向量召回，容易混淆名字相近但功能不一样的技能。
要求模型输出选择解释
不要只输出选中的技能名字，强制输出推理：任务需要什么能力、各个候选技能匹配点、选它的理由。这个解释用于系统可观测、排查错误，不是给终端用户看。
失败反馈闭环机制
频繁误选时，排查技能描述、标签、负例样本、不同技能之间的职责边界。很多错误不是模型能力差，是多个技能职责重叠。把线上误选样本沉淀为评测数据集，不要每次出问题就临时改提示词。
额外优化：技能分层加载
不要一次性把全部技能暴露给模型。先识别当前属于哪个任务领域（代码修复、文档处理、数据分析等），只加载该领域的技能，减少上下文干扰。
面试标准回答话术
Agent 技能变多之后，本质上要把技能选择设计成检索路由问题。每个技能维护结构化元数据，明确前置条件与禁用场景；路由阶段先用标签规则粗筛，再用语义召回 + 模型做精排；模型输出选择理由，便于观测复盘；线上将误选样本沉淀评测集，迭代优化技能描述和职责边界。
这套回答体现你是做系统工程治理，而不是只会堆提示词，更容易获得面试官认可。

Agent Skill 太多如何保证模型选对？
面试官问：Agent 的 Skill 太多以后怎么保证模型还能选对？很多人一听 Skill 命中率下降就想着把提示词写得更详细。但 Skill 一旦从十几个涨到上百个，问题就不再是描述不清楚，而是路由系统本身变成了检索问题。
我是小哲，点赞收藏加关注，我们马上开始。
先给结论：Skill 太多时不能再靠模型在一大堆说明里硬选，而要把 Skill 管理成一套 "召回、筛选、确认、反馈" 的路由系统。也就是说 Skill 不是越多越好，真正关键的是当前任务能不能快速缩小候选范围，并且让模型知道为什么选这个 Skill。如果没有这层路由设计，Skill 库越丰富，模型反而越容易选错。
・第一步是给 Skill 做结构化元数据。不要只写一段自然语言描述，而要给每个 Skill 标上适用任务、输入类型、输出格式、前置条件、禁用场景和示例问题。这样系统才能先按字段过滤，而不是把所有 Skill 都丢进上下文让模型自己猜。
・第二步是做两级召回。先用关键词、标签或规则把明显不相关的 Skill 排除掉，再用 Embedding 或小模型判断语义相似度。第一层解决快，第二层解决准。如果一上来就全量向量召回，很容易把名称相似但能力不同的 Skill 混在一起。
・第三步是让模型做选择解释。不是只让它输出 Skill 名称，而是让它说明任务需要什么能力、候选 Skill 分别匹配在哪里、为什么最终选择这个。这个解释不是给用户看的，而是给系统做可观测性和错误分析用的。
・第四步是建立失败反馈。如果某个 Skill 被频繁误选，就要回看它的描述、标签、负例和相邻 Skill 的边界。很多命中率问题不是模型笨，而是几个 Skill 的责任重叠。工程上要把误选样本沉淀成评测集，而不是每次临时改 Prompt。
还有一个很重要的点：Skill 不要一次性全暴露。可以先让模型判断任务域，再只加载这个域下的候选 Skill。比如代码修复、文档处理、视频审核、数据分析，本来就是不同能力空间。分层加载能显著降低上下文干扰。
面试里可以这样答：Agent 的 Skill 变多以后，本质上要把 Skill 选择设计成检索路由问题。每个 Skill 需要结构化元数据，前置条件和禁用场景。路由时先用规则或标签做粗筛，再用语义召回和模型判断做精排。模型选择时最好输出选择理由，方便观测和复盘。线上还要把误选样本沉淀成评测集，持续优化 Skill 描述和边界。
这样答，面试官会知道你不是把 Skill 当提示词堆叠，而是在按工程系统治理。
