视频详细内容总结
视频是一道大厂系统设计面试题：大模型 Agent 上线突然涌入十万请求，如何扛住流量同时控制模型成本，并且故障时可以安全收住请求。
核心观点：这道题不考八股组件堆砌，考察完整 Agent 生产链路的容量评估、流量管控、职责划分、缓存、降级、故障恢复整套方案；Agent 和普通接口不一样，一次 Agent 请求会消耗模型并发、上下文窗口、多个外部工具调用，不能单纯靠大模型本身硬扛，需要把配额、队列、路由、缓存完整纳入 Agent 执行链路，明确正常流程、异常失败、降级逻辑。
一、第一步：不要直接加机器，先建立容量模型
同样十万请求，不同业务对系统消耗完全不同，要拆解流量类型：
用户登录：压力在认证服务
查询类（课表、公告）：压力在缓存、数据库
上传资料：消耗带宽、对象存储
提交报名等写操作：涉及事务、库存、数据竞争
容量模型要统计：每个接口峰值并发、平均 / 最大响应时间、一次请求调用哪些下游、单机承受吞吐。
价值：把入口流量映射到底层真实资源，判断该扩容应用、加大缓存命中率、调连接池，还是拆分耗时调用；盲目扩容只会把瓶颈转移到数据库、模型侧，不能真正解决问题。
二、多维限流策略（网关层做，而不只是应用内部开关）
多维度限流：按 IP、租户、接口、请求类型做差异化规则
读请求（查询课表、查公告）：允许更高并发
写请求（提交报名、修改资料）：限流要严格，避免大量事务、数据竞争把数据库打垮
限流的目的：系统过载时主动拒绝部分流量，保护核心链路可用。
用户体验处理：被限流要返回清晰提示（“当前人数较多，请稍后重试”），不能页面无限转圈；防止前端自动重试放大流量。
配套防护：增加幂等、短时间请求去重，避免用户重复点击造成重复提交业务数据。
三、厘清 Agent 大模型与后端确定性服务的职责边界
大模型 Agent 职责：理解用户意图、生成任务候选计划、决定下一步该调用什么工具。
后端确定性服务职责：维护真实业务状态、执行最终业务约束、完成数据修改。
⚠️风险：如果边界模糊，Agent 错误规划、重复调用、读到过期状态，会直接引发真实业务故障。
降级优先级：优先保护核心 Agent 任务；按照租户、成本、风险等级做分级降级，不能一刀切全部降级。
四、缓存合理使用，区分强一致性场景
热点读请求依靠缓存抗洪峰，降低下游压力。
重要提醒：强一致业务不能只依赖缓存。
例：报名名额库存判断，缓存只做前置查询，真正扣减必须落到数据库 / 专门库存服务，防止缓存数据过期带来业务错误。
五、完整降级方案（业务可有损，核心链路尽量保住）
可以关闭 / 延后的非核心能力：推荐内容临时关闭、报告生成延后、图片处理降低画质规格。
必须尽力保住核心链路：登录身份校验、报名结果确认等。
降级时的用户交互原则：不能直接抛出错误；明确告知用户三件事：①请求是否已经收到；②什么时候可以查结果；③是否需要用户重新操作。
六、压测不能只用平滑平均流量，要模拟真实故障场景
压测场景要覆盖现实中容易出现的组合问题：
批量用户集中登录，接着大量查询；
用户疯狂重复点击提交；
下游某个服务突然变慢；
高峰期缓存大批量同时过期。
观测方式：网关、应用、缓存、数据库、消息队列放在同一个时间线排查，快速定位最先出现的瓶颈点。
七、面试答题完整逻辑框架（面试输出话术）
洪峰到来前：做好容量模型、完整压测，提前识别瓶颈；
洪峰到来时：网关多维限流守住入口，缓存承接热点流量，队列异步消化耗时任务；
资源耗尽时：执行分级降级，关闭非核心功能，优先保障核心业务；
后续动作：依靠监控指标，判断是否执行扩容。
整套系统设计目标：最差情况下核心请求依然可用；失败的请求要有清晰、可恢复的处理路径，不要直接崩盘。
八、面试加分收尾思路（跳出组件八股）
回答的时候不要只罗列 Redis、MQ 这些组件，要按照这个结构表述：
先讲系统设计目标；
讲各个关键组件在 Agent 整条执行链路中承担什么角色；
补充超时控制、合理重试、版本、权限校验、失败恢复逻辑。
这样呈现出：你理解如何把大模型的智能决策，对接上稳定可靠的业务执行系统，是工业生产级方案，而不是 Demo 方案。

原题：面试官提问 —— 十万用户同时发起 AI Agent 任务，你怎么设计系统？
一、开篇：先讲【错误回答 & 为什么不行】（视频开头第一个重点）
很多人的直觉错误方案：来一个请求，就启动一条 Agent 全链路；每一个用户请求独立走：理解意图 → 模型规划 → 检索记忆 / RAG → 调用工具 → 模型总结，一个请求走完全部流程。
主讲人的结论（核心警示）：这个方案在线上十万并发下等于灾难
表面是十万请求入流量；但 Agent 和普通 HTTP 接口完全不一样：一个 Agent 会话会触发多轮模型推理 + 多次工具调用。
举例：1 个 Agent 任务平均要调用 3 次大模型、2~4 次外部工具；十万并发进来，下游会瞬间膨胀成几十万、上百万次模型 + 工具调用。算力、Token 成本会指数上涨。
额外负担：每个 Agent 都要维护独立状态、对话上下文、中间执行日志；如果每一步都同步写库，数据库直接被日志、对话记录打崩，成为瓶颈。
视频开篇核心判断句：不能一个请求绑定一条独立执行链路，不能串行隔离执行，否则流量一上来直接雪崩，成本失控。
二、第一步：先做【容量建模，不要上来就扩容加机器】（视频第一大模块）
主讲观点：扩容是最后手段，不是第一手段；先算清楚每一类请求到底消耗什么资源。
前提：同样 10 万入口请求，不同业务类型，资源消耗完全不一样，不能统一看待
例子 1：登录类请求：压力集中在身份认证、权限服务；模型几乎不消耗
例子 2：纯查询类（查课表、查公告、查知识库）：压力集中在缓存、检索、数据库；Agent 规划轮次少，Token 消耗低
例子 3：上传文件、资料解析类：消耗带宽、对象存储、文档解析算力
例子 4：提交报名、修改表单、库存扣减这类写操作：有事务、锁、数据竞争，是高危链路
例子 5：复杂 Agent 任务（多步骤规划、多工具连环调用、长文档分析）：消耗模型推理、大量 Token、多次下游接口调用，成本最高
容量模型要统计的指标清单（视频列出）
每个接口 / 每类 Agent 任务的峰值并发
单任务平均 RT、最大 RT
单次请求会触发多少次模型调用、多少次工具调用
单任务平均 Token 消耗（输入 + 输出）
下游依赖：数据库、缓存、对象存储、第三方工具接口的单机吞吐上限、连接池上限
结论：容量模型的价值，是把入口 QPS 映射到底层真实资源瓶颈
算完才知道：瓶颈是应用服务、数据库、Redis、模型推理配额，还是第三方工具接口
反面坑：盲目加机器扩容，只会把瓶颈转移，解决不了根本问题；比如模型配额满了，扩业务节点毫无用处。
三、第二步：网关层多维流量管控、配额、限流（视频第二模块）
主讲：限流放在网关，而不是放在业务应用内部；网关是第一道闸门。
限流维度（视频明确列出多维度令牌桶）
IP 维度限流：防单用户疯狂刷请求
租户 / 账号维度限流：企业客户单独配额，防止一个大客户吃光全平台算力预算
接口 / 任务类型维度限流：区分读、写、复杂 Agent 任务
差异化限流规则（配套例子）
读类查询 Agent：允许更高并发，宽松配额
写类、会修改业务状态的 Agent（报名、下单、库存变更）：限流严格，防止事务、锁竞争打爆 DB
重度多步 Agent（代码分析、长文档复盘、多工具循环检索）：配额最紧，按 Token 预算做配额，而不是只按请求数
限流之后的用户体验规范（视频重点强调，很多人忽略）
禁止静默失败、页面无限转圈 loading
返回明确提示：“当前任务较多，请稍后重试”
前端必须关闭自动无限重试；自动重试会把洪峰放大几倍，形成雪崩正反馈
配套防护手段：幂等 + 请求去重
例子：用户连续多次点击提交，前端重复发请求；如果没有去重、幂等，Agent 会重复执行任务、重复扣库存、重复烧 Token
结论：限流 + 去重 + 幂等必须绑定在一起做。
补充：预算配额和限流绑定（Agent 独有，普通接口没有）
除了按 QPS 限流，还要增加Token 预算限流：租户 / 项目设置日、小时 Token 上限；达到预算，直接对该租户降级，而不是继续跑任务烧钱。
四、第三步：职责边界拆分：Agent 规划层 ≠ 业务执行层（视频非常重要的一个要点，区分新手和工程方案）
两个模块的职责严格切分：
Agent Planner（规划层，依赖大模型）：只负责理解用户意图、生成任务计划、决定下一步调用哪个工具、整理中间结果。它没有权限直接修改真实业务数据，不持有最终业务状态。
后端确定性业务服务（工具网关、业务服务）：持有真实数据、业务规则、权限、库存、事务；所有写操作、状态变更，全部由确定性服务完成。
主讲举的风险例子：边界模糊的灾难
如果让 Agent 直接决定扣库存、提交订单、修改数据库；模型幻觉、规划出错、读到过期缓存状态，就会产生脏数据、超卖、重复下单这类不可逆业务故障。
Agent 输出的只是【调用指令】，指令必须交给工具网关做参数校验、权限校验、业务规则校验之后，才允许执行。
降级分级逻辑（按租户、成本、风险等级分级，不能一刀切全降）
高优先级：付费大客户、核心业务链路的 Agent 任务，优先保留配额
低优先级：免费用户、非核心辅助任务（摘要、推荐、美化），高峰期优先降级、排队、延后执行
结论：Agent 的降级不是 “能用 / 不能用” 二元开关，是按风险、价值、成本分级。
五、第四步：缓存策略，并且严格区分【强一致场景 vs 弱一致场景】
热点读请求依靠缓存扛洪峰，减少 RAG 检索、模型调用、DB 查询。
例子：相同问题、相同检索条件的查询 Agent，缓存结果，直接返回，不再重复调用模型和工具，大幅降 Token 成本、降延迟。
重点红线（视频反复强调）：强一致性业务，不能信任缓存作为判断依据
举例：报名名额、库存扣减
缓存只做前置预判断（快速返回大概还有没有名额，优化体验）
真正的扣减、名额判断，必须落到数据库 / 独立库存服务，以数据库为准
风险：缓存过期、缓存脏数据，如果直接拿缓存结果做扣减，直接超卖。
缓存的适用边界：适合无副作用、只读、允许短暂过期的查询类 Agent 结果。写链路、资金、库存、订单，缓存只能做旁路优化，不能做决策源。
六、第五步：异步队列 + 分层调度，拆分思考和执行，控制并发槽位（视频核心架构方案）
这是视频里面的核心架构解法，用来解决 Agent 循环调用爆炸问题
把 Agent 链路拆成【思考阶段】和【工具执行阶段】两个独立队列，状态机驱动
Planner 思考：模型输出工具调用计划 → 写完状态，立刻释放模型推理资源，不等工具返回
工具队列：工具网关去调用下游接口，拿到结果回写状态机 → 再唤醒 Agent 进入下一轮思考
令牌桶 / 并发槽管控：不是无限放行
按算力、模型并发配额设置总执行槽位；每一个时间窗口（比如 100ms）只放行当前算力能承载的任务进入执行层
视频原话：不是技术上做不到瞬时全量跑，而是产品和系统不需要瞬时全部响应；要保住系统可用，而不是算力被无效请求淹没
分层调度架构：调度服务层 + 执行节点层
调度服务：接收网关放行后的合法任务、按优先级分发、管控配额、记录任务状态；不直接调用模型和工具
执行节点：拿到任务包，批量调用大模型、复用工具连接、复用公共 RAG 记忆；做批量推理优化
收益：原来十万请求带来百万级下游调用，经过分层 + 批量 + 复用，把压力收敛
任务分级调度策略：
高优先级任务：抢占调度，优先分配执行槽位，同步流式返回结果给用户
低优先级任务：进入长队列，后台异步跑，不阻塞用户前端；前端展示 “任务已提交，后台处理完成通知你”
客户端交互配套方案：
高优任务：流式输出中间结果，给用户感知
低优任务：不阻塞页面，后台排队，完成后推送通知；甚至可以合并同类任务、延后执行
七、第六步：熔断、循环刹车、超时、重试控制（专门针对 Agent 特有风险：死循环）
主讲点明：普通接口很少有无限循环问题，Agent 最大的隐性风险是工具调用死循环，Token 持续烧穿
三重刹车，任何 Agent 循环必须配置（视频硬性结论，生产上线必备）
最大轮次限制：单次 Agent 任务，最多允许 N 轮工具调用；超过直接终止，返回降级结果
单任务 Token 上限：一个会话总消耗 Token 到达阈值，强制停止，防止无限思考
全局超时熔断：单任务总执行超时，直接终止，释放所有资源
工具独立熔断（每个工具单独熔断器）
例子：搜索工具、文件解析工具、数据库查询工具，各自独立滑动窗口熔断
规则：短窗口内错误率超过阈值，直接熔断该工具；不再调用，返回降级结果，故障不会传染整条 Agent 链路
重试规则约束：
禁止无限制自动重试
区分错误类型：幂等错误可以有限重试；业务失败、参数错误、权限错误，不重试
每次重试依然计入 Token 消耗，重试次数写进配额预算
八、第七步：降级方案（业务可以有损，核心链路不能有损）
视频核心一句话：普通任务可以有损，系统容错性不能有损
可关闭、可延后的非核心能力（降级清单举例）
临时关闭内容推荐、美化总结、长报告生成、复杂图表生成
文档解析降低解析精度、关闭多轮润色
关闭非必要的 RAG 深度检索，改用摘要检索
必须死守、不能降级的核心链路：
用户身份鉴权、权限校验、最终业务结果确认、订单 / 库存写校验
降级的时候，和用户交互的标准话术三要素（视频明确给出）
告诉用户：你的请求已经收到、任务已经落盘
告知什么时候可以查看结果
明确要不要用户重新操作
❌ 禁止：直接返回 500、空白报错、用户不知道任务有没有提交成功，反复提交加剧流量。
九、第八步：压测方案（视频重点：不要只用平滑平均流量压测）
绝大多数团队的错误压测方式：匀速、平稳的流量，测出来的指标是假的，上线遇到真实洪峰直接崩
必须模拟的真实故障组合场景（视频列出全部场景）
批量用户集中登录，紧接着并发查询
用户重复点击、疯
