视频内容详细总结：RAG 零召回怎么排查？千万别只调 topK
视频核心观点
线上 RAG 出现大量零召回故障，面试时如果第一反应就是调大topK属于典型踩坑。零召回问题不只是检索参数问题，是整条 RAG 工程链路的故障，问题可能出现在文档解析、切片、向量、索引、元数据过滤、查询改写、权限等上游环节，需要顺着数据流，从上游到下游分层排查，而不是直接调检索参数。该题目考察的是工程落地思维，不是 Demo 级别的向量库使用。
区分两类零召回：
知识缺口（真没有答案）：知识库本身就没有该问题答案，属于业务问题；
检索事故（系统没搜到）：知识库有答案，但链路故障导致拿不到结果，是需要排查修复的线上故障。
完整端到端排查顺序（从上游到下游）
第一层：数据入库环节（知识是否真正进库）
很多故障是页面显示上传成功，但异步处理半失败，向量库根本没有数据，此时调任何检索参数都无效。
排查要点：
确认原始文件上传状态；
文档解析是否异常：例如 PDF 表格格式变动，只提取标题丢失正文；
切片（chunk）：切片数量是否为 0，解析后文本长度是否异常；
ID 是否重复覆盖旧数据；
向量是否成功写入向量数据库；
工程要求：依赖监控指标做判断，不依靠人工肉眼看页面状态。
第二层：索引与 Embedding 健康检查
向量维度是否匹配，写入与查询使用的 Embedding 模型版本是否一致；
索引构建任务是否执行成功，索引有无损坏。
坑点：升级 Embedding 模型之后，旧向量没有重刷，写入、查询向量空间不一致，直接造成零召回。
第三层：查询处理环节（用户提问侧）
查询改写、query 分析逻辑出错，把问题关键实体、意图删掉，导致检索关键词跑偏。
举例：用户问 “年假还能攒吗？”，查询改写错误变成 “请假流程”，完全偏离原始意图。
正确的查询改写原则：改写必须保留实体、时间、对象、用户意图，不能随便替换近义词。参考 LangChain 的 Query Analysis 思路。
第四层：元数据 & 权限过滤（高频踩坑点）
大量零召回不是向量检索没结果，而是过滤条件把全部候选文档误杀。
场景示例：员工权限过滤地区、部门、文档有效期、发布状态，只要任意一个元数据字段缺失、字段值异常，就会把本该命中的文档全部过滤掉。
排查手段：控制变量法，依次关闭全部过滤、单条过滤、多条组合过滤，定位到底是哪一条条件导致结果为空；权限逻辑要记录过滤原因，不能简单返回空列表。
第五层：召回参数、多路召回
确认 topK、相似度阈值、多路召回（向量 + 关键词）配置，这一步放到最后排查，而不是第一步。
面试标准回答模板
我会先确认文档解析、切片任务是否正常完成；再检查向量索引健康、Embedding 维度与版本一致性；接着检查查询改写、多路召回逻辑是否破坏原始问题意图；最后逐项关闭元数据过滤、权限过滤条件，定位误杀来源。同时区分是知识库本身缺少答案，还是链路故障导致检索不到。
线上工程化保障方案（修复后 + 长期防故障）
链路漏斗监控：持续监控入库成功率、切片数量分布、向量写入失败率、检索空结果率、过滤命中率；故障发生可以直接定位是数据、索引还是查询问题，避免盲目排查。
零召回样本监控告警：把零召回 case 做分桶统计，按文档类型、用户、过滤条件统计失败率；某一类样本零召回突然升高，自动告警，必要时暂停知识库发布变更，避免故障扩大。
构建回归测试集：把零召回 bad case 沉淀为回归用例；后续修改解析器、更换 Embedding、调整过滤规则，自动跑一遍回归集，防止修复旧 bug 又引出新的零召回问题。
故障现场保留：零召回大多属于数据链路故障，不要盲目重启服务，避免冲掉排查现场。
视频总结
RAG 零召回问题不要上来归咎大模型、调 topK；线上系统要把 RAG 当成完整数据流水线看待，从数据入库、索引、查询改写、过滤权限到检索参数逐层定位，配合监控指标和回归测试，做到事前告警，而不是出问题后救火式排查。

下面是逐点完整还原、无省略版本，把这条 RAG 零排查视频里面所有原话要点、例子、区分定义、坑点、排查动作、面试话术、工程落地结论全部拆开列出，严格按照视频讲述顺序：
开篇定调（视频开头第一句话）
面试或者线上遇到 RAG 零召回，第一反应直接去调大 topK，是典型错误、典型踩坑。
核心结论：零召回不是简单的检索参数问题，它是整条 RAG 数据流流水线故障，故障点分布在从文档上传、解析、切片、向量化、入库、索引、query 改写、过滤、检索、多路召回全链路。
这个问题考察的是线上工程落地思维，不是 demo 玩向量库的思维；demo 只会调 topK、调相似度阈值，线上不能这么干。
第一步：先做分类 —— 先分清两种完全不一样的 “零召回”（必区分，视频重点强调）
这一步是所有排查的前置，不区分后面全白查
类型 A：知识缺口（真没有答案，业务问题，不是故障）
定义：知识库里面本身就不存在这个问题对应的内容，不管链路怎么调都召回不到。
例子：知识库只上传了 2024 年假制度，用户问 2026 年假政策，库里根本没有，属于知识缺失，不是 bug。
处理结论：不用排查检索链路，走知识库新增文档流程。
类型 B：检索事故（库里有答案，但是链路坏掉拿不到，属于线上故障，是我们要排查的对象）
定义：知识库已经存在对应 chunk、对应内容，但是链路中某一环拦截 / 丢失，最终返回 0 条。
例子：文档已经上传、内容存在，但是解析失败、过滤条件误杀、embedding 版本不一致导致搜不到。
处理结论：进入自上游向下游的漏斗式排查流程。
视频原话提醒：很多工程师上来直接排查检索，连 “库里到底有没有这份资料” 都不确认。
完整排查链路：严格顺序【上游入库 → embedding & 索引 → query 处理 → 元数据 / 权限过滤 → 检索参数多路召回】
视频明确要求：顺序不能颠倒，上游坏了，下游怎么调参数都无效。
链路 1：数据入库环节（知识到底有没有真的进库，最高发隐性故障点）
视频原话：很多页面提示【上传成功】，但实际是异步任务半失败，前端状态写成功，后台异步处理流程中间崩了，向量库根本没有写入 chunk 和向量。
排查要点逐条：
校验原始文件上传状态：文件有没有完整落盘，有没有上传中断、文件损坏、文件是空文件。
文档解析环节校验：
坑点例子：PDF 带复杂表格，解析器只抓到标题，正文表格内容全部丢失；扫描件 PDF 没有 OCR，解析后文本为空。
检查指标：解析后文本长度、解析文本非空校验。
Chunk 切片环节校验：
检查：切片任务有没有执行成功，最终生成 chunk 数量是否等于预期，有没有出现 chunk=0。
坑：切片代码异常、特殊符号导致切片逻辑直接跳过文档，文档上传成功，但是一个 chunk 都没产出。
chunk ID 校验：
坑点例子：同一个文档、同一个批次使用重复 ID，新 chunk 直接覆盖旧 chunk，或者批量入库时主键冲突直接丢弃数据，页面不报错。
向量写入校验：
检查 embedding 调用是否成功、向量有没有正常写入向量库；
坑点：embedding 服务超时、限流、鉴权失败，文本 chunk 生成了，但是向量没写进去，这条数据在向量库里不存在。
视频结论：入库环节必须靠监控指标判断，不能靠人工看前端页面状态，前端状态不可信。
链路 2：Embedding 与索引健康检查（第二高频坑，升级模型必踩）
排查要点逐条：
写入时 embedding 模型、查询时 embedding 模型必须完全一致。
向量维度匹配校验：入库向量维度、检索 query 向量化输出维度一致。
索引构建任务状态：索引任务有没有跑完、索引是否损坏、索引是否是增量更新失败。
重点经典坑（视频重点举例）：
业务升级 embedding 模型，新模型用来做 query 向量化，但是库里存的还是旧模型产出的向量，没有全量重刷向量。新旧向量不在同一个向量空间，相似度计算全部失效，直接大面积零召回。
结论：只要更换 embedding，必须配套存量向量重刷，否则大概率出现批量零召回。
链路 3：查询处理环节 — Query 改写、Query 分析逻辑
排查要点逐条：
检查原始用户 query，经过 query 改写、扩展、压缩、实体抽取之后，输出的检索 query 是什么。
反面例子（视频原例）：
用户原始提问：年假还能攒吗？
query 改写逻辑错误，把实体、意图删掉，错误改写为：请假流程。
改写后的 query 完全偏离原始意图，自然召回不到年假相关文档。
视频给出的改写硬性原则：
✅ 合格改写：必须保留【实体、时间、对象、用户核心意图】；近义词扩充可以加，但不能把原始关键信息删掉。
❌ 不合格改写：粗暴精简、泛化，丢掉核心实体和约束条件。
补充：如果有 query 分类、路由逻辑，也要检查路由是否把这个问题路由到了错误的知识库集合。
链路 4：元数据过滤 + 权限过滤（视频强调：线上零召回最高发元凶，很多人忽略）
视频原话：大量零召回，向量检索本身是能查出候选结果的，是后面的过滤条件，把所有候选全部误杀掉了。
排查要点逐条：
过滤条件的常见字段举例：部门、地区、用户角色、文档有效期、文档发布状态、文档版本、可见范围。
故障例子：
文档元数据里的有效截止时间字段为空，过滤代码写了 end_time > now()，空值在数据库 / 向量库过滤逻辑里直接判定不满足，全部过滤掉，召回结果为空。
或者：权限字段归属错误，普通员工的查询带上部门过滤，只允许看 A 部门文档，但是目标文档归属 B 部门。
视频给出标准排查手段：控制变量法
① 先关闭全部过滤条件，执行检索，看能不能召回内容；
② 再逐个打开单条过滤条件，定位是哪一条过滤规则把结果清空；
③ 再测试多条过滤组合，排查组合逻辑 bug。
工程规范结论：权限、元数据过滤逻辑必须记录过滤原因日志，不能只简单返回空列表；日志要写清楚：哪些候选 chunk 因为哪个字段、哪条规则被过滤。没有日志就没法定位。
链路 5：召回参数、多路召回（放在最后排查，不是第一步！）
排查要点逐条：
检查 topK 配置：是不是 topK 设置过小（但视频反复说：这是最后一步，不要上来就改）
相似度阈值：阈值设置过高，所有候选相似度都低于阈值，直接丢弃全部结果。
多路召回逻辑检查：向量召回 + 关键词召回（BM25）的合并、去重、权重逻辑有没有 bug；比如关键词召回链路异常，并且配置成只取关键词结果，向量召回结果被丢弃。
结论：只有前面入库、embedding、query 改写、过滤全部确认正常，才来调整 topK、相似度阈值、多路召回策略。
面试标准口述模板（视频里直接给的标准答案，一字不差版）
我会先确认文档解析、切片任务是否正常完成；再检查向量索引健康、Embedding 维度与版本一致性；接着检查查询改写、多路召回逻辑是否破坏原始问题意图；最后逐项关闭元数据过滤、权限过滤条件，定位误杀来源。同时区分是知识库本身缺少答案，还是链路故障导致检索不到。
故障修复之后：长期工程化保障方案（视频后半段全部落地方案，逐条）
保障 1：搭建链路漏斗监控
监控指标清单：
文档上传成功率
文档解析成功率
切片产出数量分布
embedding 调用失败率
向量写入失败率
检索空结果（零召回）率
作用：故障发生时，看漏斗在哪一层掉量，直接定位是数据侧、索引侧、查询侧、过滤侧问题，不用盲查。
保障 2：零召回样本专项监控、告警
对零召回 case 做分桶统计：按文档类型、用户身份、过滤条件、知识库分组统计零召回率。
告警规则：某一类样本零召回率突然飙升，触发告警。
变更熔断：知识库发布、embedding 升级、过滤规则上线变更后，如果零召回指标恶化，可以暂停发布，阻止故障扩大。
保障 3：沉淀回归测试集
把已经出现过的零召回 bad case，全部沉淀成回归用例。
变更触发回归：只要修改文档解析器、更换 Embedding 模型、调整过滤权限规则、修改 query 改写逻辑，自动跑一遍回归用例。
目的：防止修好一个零召回 bug，改代码又引入新的零召回问题。
保障 4：故障现场保留规范
视频原话：零召回绝大多数是数据链路类故障；故障刚出现的时候，不要盲目重启服务、清理任务队列，重启会冲掉日志、任务现场、原始参数，直接丢失排查线索。先保留现场，再开始排查。
视频最终收尾总结（收尾原话）
RAG 零召回问题，不要第一时间怪大模型、不要上来就调 topK。线上 RAG 要当成一条完整的数据流水线看待，严格从上游数据入库、索引、query 改写、权限过滤，再到检索参数逐层定位。配合漏斗监控、bad case 告警、回归测试，做到事前提前感知，而不是故障爆发之后救火式排查。
