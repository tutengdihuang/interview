视频完整内容总结
视频主题：面试题 ——为什么 AI 代码工具（Codex）不默认使用 RAG 向量检索写代码，考察的不是概念背诵，而是大模型工程落地实战能力。
一、题目考察本质
表面问题：产品选型，为什么不用 RAG 做代码库检索
真实考察点：Agent 工程落地思维，是否清楚代码场景的痛点、不同方案的成本、可靠性、安全隐私，拒绝只会背 RAG、Embedding 名词。
背景：OpenAI 早期 Codex 其实试过 RAG + 本地向量库，实际落地发现效果不好，转向Agentic Search（主体式检索 / 智能体检索）。
二、代码场景下 RAG 的三大核心短板
1. 需求错配：代码优先要精确匹配，不是语义相似度
RAG 靠向量语义相似度召回；但代码查找函数名、变量名、类名讲究精确存在与否。向量检索经常召回语义看着像、实际无关的代码片段，带来干扰。Grep 精确匹配更适合代码符号查找。
2. 索引维护成本高，时效性差
代码仓库持续迭代修改；RAG 需要做切片、Embedding、更新向量索引。代码一改，旧向量索引就过期失效，要持续同步重建，带来很重的持续运维负担。
3. 额外系统带来安全、成本问题
引入向量库等于新增一套完整系统：存储、同步、权限管理；做 Embedding 过程源码有离开本地、造成代码泄露的风险。
三、Agentic Search（主体式检索）工作原理
让大模型模仿人类程序员查代码的行为，分层调用工具，按 token 成本由低到高执行，迭代缩小搜索范围，不需要预构建向量索引：
Glob：文件名通配筛选候选文件，几乎不消耗 token；
Grep / ripgrep：关键词、正则做代码内容检索，定位匹配行；
Read：确认相关后，才读取完整文件送入上下文（开销最大的步骤）。
模型循环：思考→调用工具看结果→再缩小范围。
配合百万级大上下文窗口 + 前缀缓存，降低重复提示开销，大代码库也具备可行性。
亚马逊相关研究证明：仅关键词迭代搜索，就能达到 RAG90% 以上效果，省去向量库整套维护工作。
四、Agentic Search 本身存在 3 个明显坑（面试要讲出短板，证明做过工程）
Token 容易超标：搜索短符号（如 useS）命中几百处，要么读取大量内容，要么多次细化搜索，速度慢、消耗 token 贵。
语义盲区：代码重构、函数改名之后，Grep 旧名字完全搜不到；这个场景向量语义检索反而能找到。
工具调用延迟：每轮工具调用 1‑2 秒，如果迭代 20 轮，整体耗时会达到半分钟，响应慢。
五、生产环境兜底：混合架构，不是非此即彼
不彻底抛弃向量检索，Agentic Search 做主干，向量检索按需补充：
多关键词三角定位：原名搜不到，就搜索关联关键词（比如 auth、session、token）；
将语义向量检索作为 MCP 插件挂载；遇到概念查询、完全陌生大型代码库时启用向量检索做补充召回。

二、RAG 在代码场景下三大劣势（全部原文要点 + 例子）
劣势 1：场景需求错配：代码优先精确匹配，而非语义相似度
业务逻辑：查找函数、变量、类名是确定性需求：存在就是存在，不存在就是不存在。
Grep 精确匹配可以直接确认目标；向量检索是模糊语义相似度，经常捞出来语义看着像、实际完全无关的代码片段，对写代码形成干扰。
劣势 2：代码频繁变更，向量索引时效性差，维护负担重
现实情况：代码仓库每天都被开发者修改；
RAG 代价：一旦文件改动，旧向量索引立刻过期失效；
必须持续重复执行：文件切块、Embedding 生成、向量库同步更新整套流程，带来持续不断运维工作量。
劣势 3：引入向量库带来额外系统成本与代码泄露安全风险
新增一整套独立系统：向量存储、数据同步、权限管控全部需要维护；
安全风险：做 Embedding 向量化处理过程，源码有可能离开本地环境，产生源代码泄露隐患。
对比 Agentic Search：直接读取本地文件，复刻程序员日常排查代码的行为。
三、Agentic Search（主体式检索）完整工作机制
核心思想：分层执行工具调用，按照 token 开销从低到高执行，迭代缩小搜索范围，不需要提前构建向量索引。
分层三步：
Glob 工具：文件名通配模式筛选候选文件；几乎不消耗 token（成本最低）。
Grep /ripgrep 高速文本检索工具：使用关键词、正则表达式，在文件内容中定位匹配代码行。
Read 读取文件：当模型确认结果具备相关性之后，才把完整文件读取送入上下文窗口；这一步 token 开销最高，放在最后。
运行循环流程：模型思考 → 调用工具拿到结果 → 再次缩小检索范围 → 循环往复逼近目标；行为和人类翻阅大型代码库完全一样。
配套硬件 / 模型能力支撑：
百万级大上下文窗口；
前缀缓存技术，降低重复提示词的 token 开销；
以上两点让这套迭代搜索在大型代码库下具备经济可行性。
第三方研究论据（亚马逊研究）：仅靠关键词迭代搜索，就可以达到 RAG90% 以上效果，同时完全省去向量库整套维护工作。
四、Agentic Search 三大原生缺陷（面试必须讲短板，证明真实做过工程）
视频强调：不要把 Agentic Search 讲成万能完美方案；说出踩坑点，面试官才认为你做过落地。
坑 1：Token 容易超标，速度慢、成本高
实例：React 大项目搜索符号useS，一次性命中几百处代码位置；
后果：模型要么读取大量内容消耗巨额 token，要么反复多次细化搜索；整体又慢又贵。
坑 2：语义盲区，重构改名之后关键词完全失效
举例：原来函数名叫createD1HttpClient，开发重构后改成全新名字；
Grep 用旧函数名字检索，什么都找不到；
对比：向量语义检索此时反而有机会依靠语义关联找到这段代码。
坑 3：工具调用带来响应延迟
单次工具调用耗时 1‑2 秒；
如果任务需要跑 20 轮工具循环，整体耗时会达到半分钟，用户体验差。
五、生产环境兜底方案：混合架构，不是二选一
视频明确观点：不是彻底抛弃 RAG 向量检索；主干用 Agentic Search，向量检索按需做补充。
两套兜底手段：
多关键词三角定位法
场景：直接搜函数名搜不到；
做法：切换一组关联关键词多角度定位；
示例：找认证模块搜不到目标，就搜auth、Session、Token、中间件，多个关键词交叉锁定目标代码模块。
MCP 插件挂载语义向量检索
将语义向量检索封装为 MCP 插件外挂；
触发时机：遇到概念级查询，或者面对完全陌生超大代码库的时候，才启用向量检索做补充召回。
最终工程共识：Agentic Search 作为主干，向量检索按需补充，构建混合架构。
