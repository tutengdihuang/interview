视频详细内容总结
视频主题：RAG 面试题 —— 用户输入简称、别名、错别字，RAG 如何正确召回知识库内容，面向大模型、算法面试，核心不是背诵概念，考察企业级 RAG 工程落地能力，不能单纯依赖向量相似度检索。
一、题目本质解读
表面问题：召回鲁棒性，用户输入有错别字、内部简称、口语别名时检索不准。
真实考察点：查询预处理、业务语言理解、工程链路设计。面试官想看：数据来源、状态确认、失败兜底、结果验证整套流程，而不是只讲理论概念。
现实痛点：只靠向量相似度会翻车。举例：员工把 “费用审批系统” 说成简称 “费审” 还打错字，直接送入向量检索，会返回大量无关文档。很多线上问题，根源不是模型不够聪明，而是检索预处理、权限、评测分层做得差。
答题思路：先点明问题本质，讲架构分层，再讲异常场景兜底方案，证明是可上线的生产系统，而不是 Demo。
二、核心四层架构方案（视频核心框架）
第一层：实体词典（保证输入入口可信）
如果输入入口出错，后续模型再强也没有意义。
作用：维护业务实体、别名、简称映射词典，把口语叫法、别名统一映射成知识库标准实体。
工程要求：词典不能只靠大模型从文本猜测生成；要记录词典字段来源、版本、权限、更新时间，可追溯。

视频完整逐要点整理（全部例子、原话要点、结论不漏）
视频标题：面试必考：RAG 如何处理简称与错字？
主讲：小哲大模型 AI
题目：面试官问：用户输入简称、别名、错别字的时候，RAG 怎么正确召回知识库内容？
开篇总起（视频原话）
这道题表面问召回鲁棒性，不是考背诵概念，是考企业级 RAG 工程落地能力。面试官想看的不是你说向量相似度，而是：数据来源、状态确认、失败兜底、结果验证的整套链路。
很多线上 RAG 故障，表象是模型不聪明，根因其实是检索预处理、权限、评测没有分层。很多 Demo 跑起来很好，上线就崩，因为 Demo 只测正常样本，不测坏样本：简称、别名、错别字、过期文档、权限隔离、信息冲突。
核心例子 1（视频反复举）
例子 A：费用审批系统，内部简称 “费审”，用户还打错字，打成 “飞审”，直接丢进向量检索，向量会按语义相似度乱匹配，召回一堆无关文档，检索直接跑偏。
例子 B：采购系统标准名叫 “采买通”，用户说成简称 “采通”，提问：采通报销怎么走。如果没有实体归一，向量检索很容易匹配到无关的采购制度文档。
视频核心方案：四层架构（视频原话顺序，一层一层拆解）
第一层：实体词典（别名 / 简称 / 错字映射层）
核心定位：入口可信层。如果入口就错了，后面重排、提示词、模型再强，都只是在脏输入上包装，没有意义。
词典里面存：业务标准实体名、内部简称、口语别名、常见错别字、谐音叫法。
工程硬性要求（视频重点强调，面试加分）
词典不能交给大模型自动生成、自动猜映射关系；
每一条映射记录，必须带上字段：实体来源、版本号、归属权限、更新时间、负责人；
必须可追溯，支持审计、回滚。
本层最经典踩坑点（视频原话）
两个高频错误：
① 把 “文本相关” 当成事实证据；
② 把接口调用成功，等价于业务逻辑成功。
本层目标：把用户五花八门叫法，统一映射成知识库唯一标准实体名，给下游链路一个干净、确定的输入。
第二层：受控查询改写（Query Rewrite，有约束改写，禁止自由改写）
核心定位：让系统从 “单次碰巧答对”，变成可复现、可回放、可追责的流程。
视频重点提醒：不要上来就说 “用大模型改写 query 做多 query 扩展”，这是 Demo 思路，生产环境有巨大风险。
改写的边界规则（视频原话）
✅ 允许做：错别字修正、别名替换（取自上面实体词典）、补全对话上下文缺失的实体、拆分多子问题；
❌ 禁止做：大模型自由脑补用户不存在的条件、擅自替换编号 / 合同号 / 工单号等硬主键。
工程留痕要求
每一次改写，必须持久留存：原始 query、改写后 query、改写理由、命中词典条目、状态字段、域值；支持回放这条请求链路，支持人工复核。
高风险业务强制策略（视频重点）
涉及合同、资金、支付、删除操作、权限变更、对外发消息等高风险场景：宁可多加一层人工校验拦截，也不能放任大模型凭自己理解改写用户意图。
一句话区分 Demo 写法 vs 生产写法
Demo：交给 LLM 自由改写，生成一堆相似 query；
生产：词典优先改写，LLM 只做受控辅助，改写动作全程留痕、有审计。
第三层：混合召回 + 重排层
核心定位：不依赖单一向量检索，多路结果融合解决不同检索的短板。
三路召回组成（视频列出）
向量检索（Embedding）：擅长语义相似匹配；缺点：专有名词、简称、错别字容易跑偏，硬编号不准；
BM25 关键词检索：擅长字面精确命中；缺点：语义泛化弱；
元数据前置过滤：权限过滤、文档版本过滤、生效时间过滤、部门隔离过滤（提前把用户没有权限看的文档直接筛掉，减少无效召回）
召回之后步骤：多路结果合并、去重、冲突标记，送入 Reranker 重排模型做相关性打分排序。
视频结论：向量只能解决语义相似，解决不了企业内部黑话、简称、别名、错别字的归一问题；必须前面实体词典 + 受控改写打底，混合召回才能发挥价值。
第四层：反馈闭环、坏样本回流与评测体系（生产稳定层）
视频强调：前面三层是正向处理链路；第四层是系统持续收敛、防止旧问题复现的保障。
分为上线前、上线后两块：
上线前：坏样本压测集建设
不能只用正常问答样本做评测。评测集必须批量构造边界坏 case：
用户简称、错别字、口语别名；
知识库文档互相冲突；
工具调用超时；
用户需求中途变更；
用户没有文档权限；
命中过期旧版本文档；
格式正确但是答案错误（隐性幻觉，最难排查）。
系统设计原则：遇到不确定场景，优先拦截、兜底提示，而不是强行编造答案输出。不能为了好看的演示效果强行输出。
上线后：线上回流机制
收集线上 Bad Case：用户反馈答案错误、召回不对的对话；
把这些失败样本，回流进评测集、回归测试集；
修复问题（补充词典、调整改写规则、调整召回权重）之后，每次版本迭代自动跑回归评测，防止新版本把修好的问题重新引入；
配套监控：监控召回相关性指标、幻觉率、别名类 query 失败率；
回放能力：线上任意一条问题 query，可以拉全链路日志复现当时的词典命中、改写内容、多路召回结果，定位根因。
视频给出的【标准面试口述模板】（原话原文）
我会把这个问题拆解为实体词典、受控改写、混合召回、反馈闭环四层架构。先保证用户输入与证据可信可控，再管控检索执行路径，最后依靠评测、监控、回放机制保障系统长期稳定运行。
视频逐条列出的面试加分要点（全部）
证据可追踪：所有关键判断动作留痕，链路可追溯；
高风险动作审计：资金、合同、权限类操作增加权限确认和审计日志；
回归测试：所有 bug 修复样本纳入回归集，版本迭代自动验证；
坏路径优先设计：上线验收重点校验异常路径，而不是只看正常回答效果；
区分 “链路跑通” 和 “业务正确”：调用成功≠结果正确。
视频末尾核心结论（3 条，原话）
结论 1：查询规范化、别名治理不是一个单点小优化技巧，它是一套完整闭环：从设计、执行、校验、复盘持续迭代。
结论 2：生产级 RAG，答对正常案例只是基础能力；在不确定、异常场景懂得拦截、兜底、可排查，才是区分 Demo 和线上系统的工程能力。
结论 3：不要迷信向量检索。向量擅长语义，但它天然不擅长处理企业内部约定俗成的简称、别名、错别字。这类问题的解法核心在检索前的输入治理，而不是调向量、调重排。
