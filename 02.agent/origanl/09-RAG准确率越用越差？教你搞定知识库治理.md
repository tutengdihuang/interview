视频详细内容总结
视频主题：RAG 准确率越用越差？教你搞定知识库治理
核心现象：很多 RAG 系统上线一段时间后，在大模型、提示词 Prompt 都没改动的情况下，回答准确率持续下滑，比如案例从 85% 跌到 60%；日志看检索出来还是原有文档，很多人误以为多新增文档就能解决，实际上问题根源是知识库腐化，只追加不治理会让系统越跑越差。
一、先讲 RAG 基础工作流程
用户提问 → Query 转为 Embedding 向量 → 向量库检索相似文档 → 检索片段拼接到 Prompt → 交给大模型输出答案。
流程跑通只是代表知识库搭建完成，持续维护治理才是长期可用的关键。如果文档入库之后没人管理，新文档直接追加，旧文档不标记、不淘汰，知识库就会慢慢腐化：同一主题存在多版本、多部门产出重复文档、过时政策依旧保留在库内。
知识库腐化带来的问题
向量检索 Top‑K 只看语义相似度，相似度高≠内容正确、≠版本最新。
当大模型拿到互相冲突的多份参考资料时：
有可能错误选用旧版本信息；
也会把不同文档内容强行拼凑，产出逻辑通顺、但事实错误的回答。
二、解决方案分为两大块：文档本身治理 + 检索后质量监控
1、文档治理（入库阶段就要做好）
每一篇文档入库时，必须带上元数据：版本号、生效时间、失效时间、来源部门。
检索的时候优先按时间过滤，直接排除已经失效的内容；同一主题多个版本，优先选取当前生效版本；
过期文档不用物理删除，标记为历史版本，普通检索降权或者屏蔽，做归档留存，避免旧资料干扰回答；
两个重要注意细节：
只记录时间，不记录来源：不同部门发布冲突内容，系统无法判断采信哪一份；
失效时间完全靠人工填写、后期无人维护，旧文档依旧会被当成有效知识；
版本管控不能只靠增加字段，需要跟随业务实际更新迭代。
2、检索质量监控，建立反馈闭环
需要监控每次调用的：返回的 Top‑K 文档列表、相似度分数、最终回答正确性。
当某主题准确率持续下跌，反向排查根因：文档过时？内容大量重复？知识库缺少该类知识？
知识缺失：补充新文档；
重复内容多：做合并、去重；
内容失效：淘汰旧文档；
处理完成之后，再验证同类问题效果是否改善，形成完整反馈闭环。
业务举例
企业客服场景：产品价格、政策会定期更新，如果旧价格没有失效标记，向量检索依旧会召回旧数据；增加时效版本管理后，检索优先返回当前生效价格。
参数文档冲突：不同部门维护多份互相矛盾的产品参数文档，此时继续新增文档无效，要优先处理冲突、合并重复文档，之后验证准确率恢复情况。
金融、医疗等高风险行业，知识库资料有效性直接决定业务答案是否可用。
三、常见诊断误区
只看最终答案对错，不去区分错误来源：分不清是检索拿到错误资料，还是检索资料正确但大模型生成出错，会导致问题定位跑偏；
只收集错误案例（bad case），不去深挖背后原因，同类错误会反复复现；
简单文本字面去重：只比对文字表面相似度，同义不同表述的文档识别不出来，依旧挤占检索结果空间。
四、评判知识库治理是否有效的 4 个校验标准
文档是否具备版本、时效元数据标记；
检索流程是否实际利用了版本、时效这些元数据做过滤；
回答质量下滑时，能否快速定位到问题根源；
反馈机制能不能真正推动知识库文档更新优化。
五、视频核心结论
RAG 准确率下降，不要第一时间调整大模型和 Prompt，优先排查知识库，看是否旧、冲突信息还在干扰检索。把版本管理、时效过滤、检索监控、问题反馈闭环组合起来，RAG 系统才能越用越好，而不是越用越差。

一、拆解完整 RAG 回答流程（原文完整描述）
用户提出问题
系统把用户 Query 转换成 Embedding 向量
使用向量去向量库里面检索查找相关文档
将检索得到的文档片段拼接进 Prompt 提示词
交给大模型，生成最终答案
重要判断结论：这个流程能够跑通，仅仅代表知识库搭建完成，知识库后续必须持续维护，不等于可以一劳永逸。
二、知识库腐化是怎么产生的（成因）
错误运维做法：文档一旦录入知识库，就不再过问；新文档直接追加入库；旧文档既不做标记，也不做淘汰。
经过一段时间累积，知识库内部会出现三类脏数据：
同一个业务主题，存在五个不同版本文档
不同部门各自产出，出现多份内容重复的文档（案例：三个部门各写一份）
已经过时失效的政策文件，依旧保存在知识库中
向量检索本身的固有局限（重点要点）
Top‑K 筛选机制，只做语义相似度匹配。
核心原文结论：相似度再高，并不等于内容正确，更加不等于版本最新。
知识库腐化带来两种负面结果
当大模型拿到互相冲突的多份参考材料：
大模型错误选择旧版本信息作为回答依据；
大模型把多份冲突文档拼凑，产出逻辑通顺、但是事实两边都不对的答案。
定义：把旧文档、重复、过时信息持续累积，持续干扰回答质量的现象叫做知识库腐化。
三、整套解决方案：分成两大板块
作者拆分：知识库维护分为两大部分，①文档本身治理；②检索之后表现的监控。
板块一：文档治理（入库阶段就要完成）
入库强制附加元数据字段：每一篇文档入库，必须携带：版本号、生效时间、失效时间、来源部门。
检索阶段利用元数据过滤
检索的时候，优先按时间过滤，直接排除已经失效的内容；
同一主题多个版本，根据版本关系，选取当前处于生效状态的文档。
过期文档处理策略：不直接物理删除
过期文档做标记，设置为历史版本；在普通业务检索中做降权，或者直接排除；旧文档保留归档留档，不会和新文档一起干扰回答。
文档治理的两个重要细节（原文提醒，不可忽略）
① 如果只记录时间，不记录来源部门：出现两个部门发布不一样的冲突内容，系统没有依据分辨该采信哪一份资料。
② 如果失效时间完全依靠人工填写，后期没有人持续维护更新，系统依旧会把旧文档识别成有效资料。
③ 补充结论：版本控制不能仅仅只是在数据库增加几个字段，版本管控机制要跟随业务真实更新迭代。
板块二：检索质量监控，搭建反馈闭环
需要持续监控的指标：每一次调用，记录返回的 Top‑K 文档列表、每一份文档相似度分数、最终回答的对错情况。
问题排查链路：当某一个业务主题的回答准确率持续下降，反向回溯定位根因：
是不是文档已经过时？
是不是知识库重复内容太多？
是不是这个问题本身知识库就完全没有覆盖？
对应不同根因的处理手段
知识缺失：补充录入新文档；
重复内容过多：文档合并、执行去重；
内容已经失效：做淘汰 / 降权处理。
闭环动作：问题处理完成之后，复盘验证同类问题回答表现是否改善。到此完成完整反馈闭环。
四、视频中列举的全部业务实例（2 个完整业务例子 + 行业提示）
实例 1：企业客服场景
业务特点：产品价格每个月发生变动；业务政策每个季度更新。
不做治理的后果：旧价格文档没有失效标记，向量检索依然能够召回旧价格，输出错误报价。
治理之后效果：通过版本 + 时效管理，检索优先匹配当前正在生效的价格资料。
实例 2：多部门文档冲突场景
现象：某产品问答准确率下降；排查后发现三个部门分别维护三份产品参数文档，文档内容互相矛盾。
原文结论：这种场景继续往库里面补充资料没有作用，必须优先解决内容冲突，归并合并重复文档，完成之后再验证准确率是否恢复。
行业风险提示
金融、医疗这类知识密集的高风险业务场景，知识库资料是否有效，会直接决定输出答案是否可以投入业务使用。
五、RAG 问题诊断里面的三类典型误区（原文完整三条）
背景：很多团队做 bad case 分析，容易踩坑，导致无法真正修复问题。
误区 1：只盯着最终答案的对错，不区分错误来源
后果：分不清错误是「检索拿到了错误的参考资料」，还是「检索拿到的资料本身正确，但是大模型生成环节出错」；问题归因会直接跑偏。
误区 2：仅仅收集 bad case 错误案例，但是不去深度剖析底层产生原因
后果：相同类型错误会反复重复出现，问题得不到根治。
误区 3：简单只做文本字面去重
问题：只比对文本表面文字相似度；对于同一含义但是换表达方式的文档识别失效。
后果：两份看似不一样、实际信息完全一样的文档继续保存在库内，持续挤占检索返回结果的名额。
六、评判知识库治理是否真正有效的 4 条校验标准（原文完整 4 条）
想要评估一套 RAG 知识库有没有做到有效治理，核对四件事：
文档是否已经带上版本、时效相关标记元数据；
检索流程中，是否充分利用了版本、时效这些元数据做过滤筛选；
回答质量下滑的时候，系统能否快速定位到问题根源；
整套反馈机制，是否能够实实在在推动知识库文档更新迭代。
小结：把以上 4 件事全部串联打通，知识库才算具备长期维护运行的能力。
七、视频最终核心总结结论
RAG 出现准确率下降，不要第一时间怀疑、修改大模型和 Prompt 提示词；优先检查知识库，确认旧信息、冲突信息是否还在被检索调用。
只有把版本管理、时效过滤、检索监控、反馈闭环全部结合在一起搭建完成，RAG 系统才可以做到越用效果越好，而不是越用效果越差。
