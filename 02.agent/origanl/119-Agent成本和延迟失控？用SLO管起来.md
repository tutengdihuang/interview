视频详细总结：Agent 成本和延迟失控？用 SLO 管起来
该视频核心主题：AI Agent 上线后容易出现成本、延迟不受控的问题，不能只看单次模型调用指标，要结合成本、延迟、业务质量三者，借助 SLO（服务等级目标）做治理，把 Agent 变成可预测、可控的线上生产系统。
一、核心痛点：只看单次调用指标会产生误判
很多团队为了降本，把大模型换成小模型，单次模型调用费用下降，但任务成功率降低，用户侧出现大量重试。表面单次调用更省钱，但完成一次完整业务任务的整体成本反而更高。
结论：评估 Agent 健康度，不能只看单次模型调用开销，成本、延迟、业务质量要统一考量，不能割裂看待。
二、正确的指标统计方式
1. 成本：按成功完成的业务任务核算，而非单次模型调用
Agent 完成业务（订机票、解析财报等）不是一次大模型调用就能完成，会包含多轮思考、多次工具调用、出错重试，甚至失败后转人工。
完整成本需要统计：
1）全部模型请求、输入输出总 Token；
2）外部工具 / 插件调用费用；
3）模型出错带来的重试成本；
4）任务失败转人工接管的成本。
结合任务成功率，才算真实业务成本。
2. 延迟：看端到端总耗时，不要看首字延迟，重点关注长尾 P95、P99
首字延迟：只是大模型 API 返回第一个字符的速度，不等于用户体验。
端到端总耗时：用户发指令到 Agent 完整交付业务结果的全部时间。
不要只看平均值：平均值会掩盖大量慢请求的恶劣体验。
P95：95% 请求在此时间内完成；
P99：99% 请求在此时间内完成；
管控 P95、P99，才能保证绝大多数用户（包括慢请求用户）体验合格。
三、降本增效的正确优化顺序：先挤掉系统无效工作，再做模型降级
❌错误做法：一上来直接把大模型换成小模型做降级，容易直接搞崩系统业务质量。
第一步：工程优化，消除无效工作（优先做）
精简上下文：清理冗余重复历史，不要每次把几万字全部喂给模型；
按需加载工具：不要一次性把几百个 API 描述全部放进提示词；
缓存机制：缓存稳定的系统提示词、短期不变的检索结果；
并行执行：互相独立的只读任务（查天气、查酒店）并行跑，不要串行排队；
死循环拦截：识别 Agent 原地打转、没有进展的逻辑，强制终止，避免 Token 无限消耗。
第二步：模型路由分层（工程优化做完之后再执行）
简单任务（意图分类、摘要提取）：交给便宜快速的小模型；
复杂任务（多步推理、逻辑规划、高风险交易操作）：交给能力强的大模型；
不能为了省少量 API 费用，牺牲工具调用兼容性和业务质量底线。
四、生产级关键手段：给 Agent 任务设置 SLO 与预算红线
预算不只是人民币，是一套硬性约束红线，每个任务要规定：
最大对话轮次；
Token 消耗上限；
外部工具最大调用次数；
总耗时上限；
硬性成功率、人工接管率目标。
1. 接近预算上限：系统自动自救
压缩对话上下文；
降级非关键搜索步骤；
请求用户缩小问题范围、提供更明确指令。
2. 彻底超出预算：受控停止，严禁模型瞎编结果
不能让 Agent 后台牺牲正确性，输出编造的错误答案糊弄用户。
正确行为：明确告知用户任务过于复杂，无法自动完成，转交人工处理。
业务事故的代价，远高于多调用几次大模型的开销。
五、视频最终核心观点
生产环境真正的降本，不是单纯压低单次模型调用价格，而是依靠架构设计，减少系统无效步骤，稳定完成更多真实业务任务。
成本、延迟、质量三者必须放在同一套体系算总账，才能支撑 AI Agent 真正商业化落地。

第一大块：成本的正确统计方式
核心观点
Agent 成本核算，必须按成功完成的业务任务来算，不能统计单次模型调用开销。
业务举例
Agent 帮用户订机票、总结长篇财报，不会只调用一次大模型就结束；后台会持续思考、调用外部工具，出错之后反复重试拉扯。
完整任务成本包含全部以下开销（全部要计入）
模型全部请求次数、输入 + 输出总 Token 数量
外部插件、外部工具调用产生的费用
大模型输出出错带来的内部重试成本
任务彻底无法完成，呼叫人工客服接管的人工成本
完整业务真实成本 = 上述全部开销叠加，再结合任务成功率综合计算。
第二大块：延迟的正确统计方式
核心观点
延迟不能看 API 首字返回速度，要看用户端端到端总耗时；不能只看平均值，要盯住长尾百分位指标。
❌首字延迟：只是大模型 API 吐出第一个字符的速度，不是用户真正关心的体验指标。
✅端到端总耗时：从用户发出指令，到 Agent 完整完成业务、把结果展示在屏幕上的全部时间。
例子：用户让 Agent 订机票，从提问到订单信息完整展示出来的全部时长，才是有效延迟。
为什么不能看平均值
平均值会掩盖大量极端慢请求的恶劣体验。
两个关键指标定义
P95：95% 的用户请求，可以在该时间阈值以内完成；
P99：99% 的用户请求，可以在该时间阈值以内完成。
视频结论：管控住 P95、P99 长尾延迟，才能保证绝大多数用户（包括遇到慢请求的那部分用户）体验仍然可控。
第三大块：降本增效的正确执行顺序
❌非常普遍错误做法：一上来直接做模型降级，直接把大模型替换成小模型，最终造成线上系统业务质量直接崩溃。
✅正确顺序：第一步先消除系统内部无效工作（工程优化挤水分）；做完工程优化之后，第二步再做模型路由分层。
阶段一：工程优化，消除全部无效工作（优先执行）
视频列出 5 条全部工程手段，附带对应例子：
清理冗余上下文：不要每一轮都把几万字全部历史记录塞给大模型，删除重复、无用历史内容。
按需加载外部工具：不要一次性把几百个 API 工具描述全部塞进提示词，只加载当前任务真正需要用到的工具。
缓存机制：缓存稳定不变的系统提示词前缀；缓存短期内不会发生变化的外部检索结果，减少重复调用。
独立任务并行处理
例子：同时查天气、查酒店，两个互相独立只读任务，不要串行排队，改成并行执行，节约总耗时。
死循环强制拦截
场景：识别 Agent 陷入原地打转、逻辑没有任何进展的循环；必须主动强行终止，防止无限消耗 Token 与时间。
阶段一结束前提：把系统里所有工程层面的无效消耗全部挤干净之后，才允许进入模型路由环节。
阶段二：分层模型路由（工程优化完成后再做）
根据任务难度分配不同能力模型，给出明确任务案例：
交给廉价快速小模型的任务：简单意图分类、文章摘要提取这类低复杂度任务。
必须交给强能力大模型的任务：复杂逻辑规划、多步推理、高风险业务判断。
业务例子：涉及真金白银的交易操作，必须使用能力最强的大模型。
硬性告诫结论：不能为了节省少量 API 调用费用，破坏工具调用兼容性，更不能触碰业务质量底线。
第四大块：生产级核心手段：给 Agent 任务设置 SLO 与任务预算红线
重点：这里的预算不是单纯人民币金额，是一套硬性约束红线（SLO 服务等级目标）。
每个 Agent 任务，需要规定的全部红线指标
该任务允许最大对话轮次上限
Token 消耗最大上限
外部工具最多调用次数上限
任务总体耗时最大秒数上限
硬性业务成功率目标
人工接管率目标
作用：配置这套约束之后，系统具备自动调控自救的能力。
场景 1：任务运行接近预算上限（还没彻底超限）→系统自动自救行为
视频列举 3 种自救动作：
主动压缩历史对话上下文，减少 Token 消耗；
降级、关闭非关键搜索步骤；
主动向用户请求：请缩小问题范围，提供更加明确的指令。
场景 2：任务彻底超出全部预算红线 →受控停止，严禁模型乱输出
❌禁止行为：后台悄悄牺牲正确性，编造虚假答案糊弄用户，回避失败。
✅必须执行动作：明确告知用户，当前任务复杂度太高，无法自动完成，任务转交人工处理。
视频重要结论：一旦发生业务事故，事故带来的损失代价，远远高于多调用几次大模型产生的开销。
