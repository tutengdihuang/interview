视频内容详细总结
视频主题：AI 总被带偏？搞懂提示词与上下文工程，主讲人小哲，面向大模型、AI Agent 开发场景，解释一个常见现象：提示词指令完全没变，但 AI 仍然被旧资料、无效信息带偏给出错误答案，问题根源往往不是指令写得不好，而是模型推理阶段读到的上下文信息出了问题。
一、抛出核心现象
明明已经在提示词里要求 AI 只分析当前版本，但检索返回的旧方案、过时资料不断干扰结果。很多人会反复修改提示指令，但问题不在指令措辞，而在于：每一轮推理时，到底把哪些信息给到了模型。
由此引出两个核心概念：提示词工程、上下文工程，二者分工不同、互相配合。
二、提示词工程是什么
提示词工程是大家更熟悉的部分，核心工作是把任务要求说清楚。
关注点：指令怎么表达，写清任务目标、输出格式、角色、约束条件。
类比：相当于给助手定下工作规范，告诉它要做什么事。
特点：偏向静态，主要解决 “任务要怎么做” 的规则说明。
三、上下文工程是什么
上下文工程是动态管理模型推理时能看到的全部业务信息，是视频讲解的重点。
Agent 运行时，模型看到的上下文不只有系统提示词，还包含：对话历史、程序运行状态、工具说明、外部检索回来的参考资料等。
这些信息会随着任务推进持续变化：调用工具、查询文档都会改变信息集合。
❗误区：不是任务开始前一次性把所有资料全部塞进去就完事。每一轮新推理，都要根据任务进度，重新挑选、过滤喂给模型的信息。
举例：Agent 排查软件报错时，当前错误日志、软件版本、已经尝试过的无效修复方案，优先级远高于大量无关的历史聊天记录。
实操思路：当前上下文只放入本轮决策最关键片段；保留完整资料的检索入口，如果模型判断信息不足，可以主动调用工具读取更多内容。
目的：减轻模型负担，避免大量无关杂音稀释模型注意力，减少被无关信息带偏。
四、上下文构建的重要原则：标记信息来源
长线 Agent 任务中，上下文里信息来源混杂：用户要求、工具返回的客观事实、网页抓取的观点、模型上一轮未经证实的猜测。
不能把不同来源的信息揉成无标记的大段文本。
风险：文档示例命令会被误当成执行指令；模型上一步未验证的猜测，会被后续步骤直接当成既定事实继续推导。
解决方法：关键信息带上来源、状态、有效范围，区分事实、观点、猜测、用户指令。
五、开发的平衡误区：不是上下文越短越好
视频明确反对两个极端：不是信息越多越好，也不是一味精简、越少越好。
如果为了节省 token，删掉关键业务约束，模型依然会做错。
做代码检索时，如果只截取极小片段，会丢失外部依赖、相邻条件，造成判断错误。
工程实践：需要结合任务实际表现，动态平衡信息的精简度与完整性。
六、总结二者关系
提示词工程：负责把任务要求、规则说清楚。
上下文工程：负责让合适的证据、在合适的时机给到模型。
二者是互补关系，不是替代关系；出现上下文工程新概念，不代表提示词工程失去价值，做 Agent 开发两者都要重视。

视频完整逐点拆解（作者：小哲，标题：别再给 AI 塞满资料了！搞懂上下文工程）
全部内容按视频叙事顺序，所有抛出现象、例子、反例、原则、方案、结论全部保留，无省略
【0. 开篇抛出核心痛点现象（视频第一个论点）】
现象：系统提示词、指令一字不改，但 AI 输出结果依然跑偏、出错、被旧信息干扰
大家的常规错误应对：反复修改、打磨提示词措辞，不断调 prompt
视频核心判断：问题根源大多不在指令本身，而在每一轮推理时，打包送给模型的那一大包上下文信息
一句话总起：提示词工程大家都在学，但 Agent 开发真正容易被忽略、决定稳定性的是上下文工程。
【1. 定义：提示词工程 Prompt Engineering（静态部分）】
核心关注点：怎么清晰表达任务要求、约束
包含内容：角色设定、任务目标、输出格式、禁止事项、评判标准
类比：相当于给 AI 写一份静态的岗位说明书、工作规范
性质：偏向一次性、静态的规则描述；它规定 AI “应该怎么做这件事”
边界：它只管指令本身，不负责管控模型能看到哪些背景资料、历史记录、工具返回数据
【2. 定义：上下文工程 Context Engineering（视频重点，动态部分）】
范围远大于提示词工程；它管理每一轮推理，模型能看见的全部信息集合
上下文包里面包含的全部组件（视频逐条列出）：
系统提示词（prompt 本身）
多轮对话历史、过往交互记录
长期记忆、用户信息
RAG / 向量库检索回来的文档片段、业务资料
工具定义、工具返回结果（数据库、接口查询返回内容）
当前任务运行状态、执行进度
核心工作：对上面这一堆信息做选择、过滤、排序、标记、动态拼装、按需加载
性质：动态，每一轮 Agent 推理，上下文都要重新组装一次，不是一次性塞完就不管
本质类比：管理大模型每次做决策前，它 “脑子里加载的全部参考材料”
【3. 第一个反面案例：盲目全量塞入资料（RAG 朴素做法）】
案例场景：任务是核对某一条接口的限制条件
错误做法：直接把整套完整产品文档全部塞进去，文档里还混杂多个版本的接口文档，没有版本标记
错误带来两个后果：
① 文档量大，无关内容占绝大多数，token 成本很高
② 模型注意力被大量无关文本稀释，找不到当前版本真正有效的那条约束；旧版本文档内容会污染结果
视频结论：不是资料给得多，AI 就看得准；塞满资料反而更容易答错
【4. 第二个反面案例：数据库查询返回海量记录】
案例场景：调用数据库工具，返回上万条记录
错误方案 A：全部直接喂给模型 → token 爆炸，关键异常数据淹没在海量数据里，模型漏掉重点
错误方案 B：粗暴截断，只取前 N 条（比如前 50 条）→ 高风险、关键异常数据很可能排在后面，直接丢失
视频结论：简单 “全塞” 或者粗暴截断，都属于上下文工程的反模式
【5. 推荐方案：目标 + 索引 的按需加载模式（视频主推方案）】
组装进本轮上下文的内容：当前任务目标 + 可信资料索引清单，而不是一次性塞入全文
运行逻辑：
第一轮只告诉模型：现在要做什么、有哪些文档 / 条目可以查阅（索引、ID、标题、版本）
模型自己判断：缺少哪一部分细节
模型主动调用读取工具，按需拉取对应的片段原文
优势：
本轮上下文干净、噪音极少
只在真正需要的时候，才加载详细原文，节约 token
避免大量无关文档持续干扰模型判断
【6. 强制原则：信息必须标记来源、状态、有效范围（视频重点强调）】
痛点：很多系统把不同来源的文本揉在一起，不加任何标签，模型分不清信息是什么类型
信息的 4 类来源，必须区分，不能混为一谈：
用户指令（用户的要求）
客观事实资料（文档、接口返回、日志，可信事实）
模型上一轮自己生成的猜测、推理结论（未经验证，不是事实）
观点、参考示例（文档里的示例、样例代码）
不打标签的两大风险（视频明确列出）
风险 1：文档里的示例命令、样例代码，会被模型误当成现在需要执行的真实指令
风险 2：模型上一步未经核验的猜测，在后序推理里被模型直接当成既定事实继续推导，幻觉链式放大
落地要求：每一段材料附带元信息：来源、版本、生效时间、可信度标记、是否为示例
【7. 破除一个重大误区：上下文不是越短越好，也不是越长越好（视频单独一节）】
两种极端错误认知：
误区 A：上下文越长、资料越多，AI 越准
误区 B：为省 token，上下文压得越短越好，疯狂删减
反例说明 “不能一味缩短”：代码检索场景
如果为了压缩，只截取极小一段代码片段
丢失依赖定义、上下文变量、前置判断逻辑、相邻业务条件
模型看不懂完整逻辑，给出错误修改方案
视频结论：取舍标准不是长度，而是相关性 + 决策必需性
保留：当前这一步推理，做判断必须用到的关键信息
剔除：和本轮子任务无关的噪音信息
平衡目标：在 token 预算内，保留足够的决策证据，同时隔离干扰杂音
【8. 订单客服辅助例子（生活化例子辅助理解）】
场景：用户查询一笔订单的发货状态
错误上下文组装：把近半个月全部对话历史全部打包送入上下文（里面包含之前另一笔退款订单记录）
问题：模型容易抓取旧退款订单信息，混淆订单，给出错误答复
正确做法：本轮只携带【当前查询订单的最新状态 + 和这笔订单相关的少量最近对话】，无关历史不加入本轮窗口；长期历史做成摘要索引，需要再调取
【9. 提示词工程 和 上下文工程 的完整关系结论（视频收尾总结）】
二者不是替代关系，不是有了上下文工程，提示词工程就没用了；互补配合
分工一句话对照：
提示词工程：规定模型该遵守什么规则、输出长什么样（规则层、静态指令）
上下文工程：控制模型每一步能看到哪些证据材料（信息供给层、动态管理）
视频最终核心结论：
单轮问答场景，提示词工程影响更大
多步骤、长任务、带工具调用、带 RAG 的 Agent 智能体，上下文工程才是稳定性的核心瓶颈
Agent 效果不稳定，优先排查上下文组装逻辑，而不是上来就死磕 system prompt
【10. 视频最后给出的上下文工程评估标准（隐性结论）】
判断一轮上下文组装好不好，看三点：
相关性：里面每一条信息，是否服务于当前这一步子任务
可溯源：信息来源、版本、有效期清晰可查
可控加载：非必要的大篇幅资料，走索引按需读取，不常驻上下文窗口
视频所有反模式汇总（视频里点名的坏做法）
RAG 朴素模式：检索到文档块直接全部塞进窗口，不做筛选、不做索引化
全量历史灌入：不管当前任务，把全部对话历史持续挂在上下文
无标记拼接：事实、猜测、示例、用户指令混在一起，无来源标注
粗暴截断：超长列表直接切前 N 条，丢弃后面内容
静态上下文：上下文组装逻辑写死，每一轮都是一模一样的材料，不随任务进度动态变更
