## 主题

Agent 的长期记忆不一定非要向量数据库 + RAG。视频讲的是**文件式本地记忆方案**，并对比向量库方案的优劣、实现思路与适用边界。

对标参考：Claude Code 的文件记忆方案。

## 一、痛点：传统 Agent 记忆方案的问题

**先区分两件完全不一样的事**（全篇分界线）：

- ✅ **外部知识库记忆**：大量文档、参考资料、产品手册、PDF，目标是从海量资料里检索信息 → 适合向量 RAG
- ✅ **Agent 自身记忆**：决策、踩过的坑、用户偏好、任务进度 → 文件就够

Agent 天然无状态：重启、新开会话就失忆，记不住历史决策、踩过的坑、用户偏好、未完成任务。

行业惯性做法：一做长期记忆就直接上向量数据库 + Embedding + RAG 检索。视频判断：这在很多轻量场景属于**过度设计**。

向量库的弊端：

- **组件重**：额外部署向量库服务，增加运维、部署成本；小项目、本地 Demo、轻量 Agent 不划算
- **记忆黑盒**：向量是数字，人无法直接阅读、编辑记忆内容，排查问题麻烦
- **有检索误差**：语义召回会出现召回不准、漏记，Agent 重要决策可能检索不到
- **备份迁移麻烦**：向量库数据迁移、版本管理不方便

## 二、什么是文件式记忆方案

核心思想：把记忆直接保存在本地可读文件（Markdown / jsonl），用文件系统充当记忆存储，不依赖向量数据库。

### 文件分工

| 文件 | 作用 |
|---|---|
| `MEMORY.md` | 核心精炼长期记忆。不是完整聊天日志，而是提炼后的精华：重要决策与理由、踩坑教训、用户偏好、项目关键上下文。每次会话启动读取载入上下文 |
| 按日期日志（如 `2026-10-25.md`） | 原始流水日志，记录当天完整执行过程、对话、动作，作为原始备份。不会全部塞进上下文，需要时按需读取 |
| 配置 / 人格文件（`SOUL.md` / `RULES.md`） | Agent 角色、约束规则、行为设定，每次会话加载 |

### 完整运行流程

1. **会话启动**：Agent 读取核心记忆文件，把关键记忆加载进上下文窗口
2. **会话运行中**：一边工作，一边把重要事件、新学到的信息写入当日日志文件
3. **记忆合并（记忆沉淀）**：定时或会话结束后，大模型回顾日志，把真正长期有用的信息提炼更新到 `MEMORY.md`，过滤临时无效信息，避免记忆无限膨胀
4. **需要回溯历史**：通过文件名、关键词检索对应日志文件读取内容，不做向量嵌入

## 三、文件式方案优势

- **极简部署**：只靠本地文件系统，不需要向量库、数据库，写 Demo、做本地 Agent 门槛极低
- **记忆完全透明可读**：Markdown 用任意编辑器就能打开，人可以手动修改、补充、删除记忆，方便调试
- **便于版本管理**：整个记忆文件夹可以放 Git 做版本备份、回滚、迁移，换机器直接复制文件夹
- **无向量召回错误**：直接读原文，不会出现语义检索漏掉关键记忆的问题
- **适配超大上下文窗口**：Claude、GPT-4o、Gemini 的百万 token 上下文，足够容纳精炼后的记忆文件

## 四、短板（客观说明，不是全盘否定向量库）

- **记忆不能无限膨胀**：`MEMORY.md` 直接读进上下文，内容太多会消耗大量 token，必须定期压缩、淘汰过时信息
- **不适合几十万以上海量外部文档检索**：这种场景依然要 RAG + 向量库
- **原始日志多了之后纯关键词检索语义能力弱**：可搭配轻量 SQLite-FTS 全文检索补充，依旧不用重型向量库

## 五、选型边界

✅ **优先选文件式记忆**

- 个人 Agent、本地 Demo、小型业务智能体
- 记忆主体是 Agent 自身的决策、经验、用户习惯、任务进度
- 希望记忆可读、方便调试、不想维护额外数据库组件

✅ **还是要用向量数据库 RAG**

- 需要处理几十万、百万级外部文档资料
- 多租户隔离、企业级大规模知识库检索场景
- 原始资料庞大，无法全部放进上下文窗口

## 六、最终结论

做 Agent 记忆不要思维定式直接上向量库，先评估业务规模。

轻量场景优先尝试 Markdown 文件记忆架构，组件少、调试简单，很多生产场景已经在使用（Claude Code 等产品就是文件优先记忆思路）。

**文件记忆和向量库不是对立，可以混合使用**：Agent 自身经验用文件，外部海量知识库再接入向量 RAG。
