该视频是面向程序员大模型面试的讲解视频，主题为面试题：RAG 系统如何处理 Word、扫描版 PDF（例如合同文档），核心观点：很多面试者只会回答切片 + 向量检索，但真实工程落地最大难点不在检索，而在于前置的文档解析；解析做差，后续所有环节都是无效输入。
一、面试题的考察本质
不是考察背诵 RAG 流程，考察是否做过真实脏文档的落地；
很多候选人只懂 Demo 流程，没有处理双栏排版、乱表格、扫描件的实战经验；
核心得分点：文档解析、结构感知切片，而不是向量检索。
一句话总框架：RAG 处理 Word/PDF 是完整流水线：文档解析提取内容（扫描件做 OCR）→结构感知切片→向量化入库→多路召回 + 重排→组装上下文 + 来源引用。
二、第一阶段：文档解析（整条流水线最大难点）
Word 和 PDF 解析难度差异巨大：
1）Word 文档
优势：原生自带结构信息，标题、段落、表格有标记，提取相对简单。
坑点：文档内嵌入图片、公式、文本框、内嵌 Excel 对象，很容易丢失信息，需要专门处理这些内嵌对象。
2）PDF 文档（真正硬骨头）
PDF 是版式描述格式，只记录每个文字在页面的坐标，没有标题、段落、章节这种语义概念，会遇到大量问题：
双栏排版：直接提取文本会左右栏文字交叉错乱，生成乱码；
表格：跨页、合并单元格、不规则表格，普通抽取行列直接错乱；
扫描版 PDF：本质就是图片，不做 OCR 完全拿不到文字内容。
工程解决方案
版面解析工具：Unstructured、Docling，识别页面区块：标题、正文、表格，还原正确阅读顺序；
复杂表格、扫描件进阶方案：使用多模态大模型，直接把页面当成图片输入，靠视觉能力理解版面，效果更稳定。
关键点：先把文档转成结构清晰的内容，再谈切片。
三、第二阶段：切片（反对粗暴按固定字数切割）
反直觉认知：切片不是切的越碎越好，不能简单固定 500 字一刀切割。
粗暴按字数切的坏处：把完整句子、整张表格、完整逻辑从中间切断；召回回来残缺片段，大模型就会答错。
正确做法：结构感知切片
顺着标题层级、段落边界切；标题和它下属的内容绑定在一起；
表格、代码块尽量整块保留，不要拆散；
实测：专业领域场景，结构感知切片可以提升 40% 以上准确率。
工程实践配置
递归切片：400‑800token，设置约 20% 重叠，避免上下文断裂；
语义切片：按照语义边界切分，效果更精细，但成本会提升 3‑5 倍，需要权衡收益再决定是否使用。
四、第三阶段：入库 + 检索（多路召回，拒绝单向量检索）
将切片内容做 Embedding，转为向量存入向量库；
查询阶段，不能只用向量检索单路：
向量检索：负责语义相似匹配；
关键词检索：精准匹配专有名词、编号；
将两路召回结果合并，交给重排模型（Reranker）做二次排序，把相关性最高的片段前置，对最终回答质量影响很大。
五、第四阶段：上下文组装、兜底策略
把重排后的片段组装成 Prompt 上下文交给大模型；必须附带来源引用，标注答案来自哪个文件、第几页，这是 RAG 可信度的关键。
线上兜底工程坑点：
扫描文档质量差，OCR 会有错别字、表格解析偶尔错乱；
做置信度判断：识别效果差的内容不要强行喂入，要么人工介入，要么用多模态兜底；
平衡召回率与准确率：不要一味追求高召回，把噪声塞进来会降低回答质量；也不能太保守漏掉关键信息，需要依靠评估指标反复调参。
六、面试精简版回答模板（时间紧张时直接口述）
RAG 处理 Word 和 PDF 是完整流水线，难点不在检索而在解析。Word 自带文档结构相对好提取，但内嵌对象要处理干净；PDF 属于版式格式，没有原生语义，会遇到双栏排版、异常表格、扫描件问题，要做版面解析还原阅读顺序，扫描件走 OCR 或者多模态模型。解析完成后使用结构感知切片，保证标题、表格完整性，再向量化入库；检索采用多路召回加重排；组装上下文附带来源引用；解析环节做置信度兜底，平衡召回率和准确率。

铁律结论（视频原话）：解析没做好，后面切片再好、向量模型再强、大模型再好，喂进去的都是垃圾，召回回来的也都是垃圾（GIGO，垃圾进垃圾出）。

二、第一大模块：文档解析（整条流水线修罗场，视频重点最长部分）
2.1 Word 文档解析（原生带结构）
优势：Word 文件内部原生标记了标题、段落、表格层级，自带语义结构信息，文本提取难度低。
Word 明确坑点（视频举例）：文档里面嵌入的图片、公式、文本框、内嵌 Excel 对象；普通解析器会直接跳过、丢失内容。
风险后果：合同、技术方案里的内嵌表格、备注放在文本框里，直接抽文本就丢失关键条款，RAG 回答缺信息。
2.2 PDF 文档解析（真正硬骨头，视频重点，大量举例）
PDF 本质定义（原话）：PDF 是版式描述格式，只记录每一个文字在页面上的 XY 坐标，文件本身不存在标题、章节、段落这种语义概念。它只管字画在哪，不管文字是什么逻辑关系。
原生 PDF（可选中文字的 PDF）典型翻车案例（视频举的 3 个例子）
例子 1：双栏排版文档（学术论文、招标书、合同附件、技术规范）
问题：直接按顺序逐行提取文本，左栏一行、右栏一行交替交叉，文字顺序完全错乱，拼接成完全不通的乱码。
例子 2：复杂表格
包含：跨页表格、合并单元格、不规则斜线表头、多行备注单元格。普通文本抽取只能拿到零散文字，行列关系全部丢失。
例子 3：带图注、侧边备注、页眉页脚、脚注的文档，直接抽取会混入主文，变成噪声。
扫描版 PDF（合同扫描件、纸质档案拍照 PDF，视频重点案例）
本质：PDF 容器里面放的是图片，不存在任何可直接复制的字符文本，直接解析拿不到一个字。
基础方案：OCR 光学字符识别，把图片像素识别成文字。
OCR 天然缺陷（视频提到）：纸张褶皱、字迹淡、公章压字、底色发黄、倾斜、反光，会出现错别字、漏字、行顺序错乱；OCR 只出文字，不知道哪里是标题、哪里是表格。
2.3 文档解析工程工具方案（视频明确点名工具）
版面解析工具：Unstructured、Docling、LlamaParse、Marker
作用：不是单纯抽文字；版面区块识别，识别页面区块类型：标题、正文段落、表格、图注、页眉页脚；还原人类正常阅读顺序，解决双栏乱序问题；优先输出 Markdown 格式（视频结论：Markdown 是 RAG 语料黄金格式，大模型对 Markdown 理解最好）。
进阶兜底方案（复杂表格、低质量扫描件）：多模态大模型视觉解析
做法：直接把整页 PDF 当成图片喂给多模态模型，让模型视觉理解整张页面布局、表格结构、文字逻辑。
视频结论：对于极度复杂合同、模糊扫描件，这个方案稳定性高于传统 OCR + 规则版面解析；成本更高，适合高价值文档场景。
解析层总结（视频原话）：解析的目标不是拿到一堆纯文本，而是拿到保留层级、阅读顺序、表格结构、区块分类的结构化文本。
三、第二大模块：切片 Chunking（反直觉重点，视频专门纠正误区）
3.1 网上 Demo 的错误做法（视频点名批评）
错误方式：固定 token / 固定字数一刀切（比如固定 500 字一刀、固定 700token 切割）
错误认知误区：很多人觉得切得越碎，召回越精准。
视频明确结论：切片不是切得越碎越好。
错误方案带来的问题（举例）：
一句完整条款、一个完整表格、一段连贯逻辑，从中间被一刀切断；
检索召回回来只有半句话、半截表格；
大模型拿到残缺片段，信息不全，直接答错、产生幻觉。
3.2 视频主推方案：结构感知切片（得分核心点）
核心规则：顺着文档识别出来的标题层级、段落边界切，而不是按字数硬切
硬性切片规则（视频逐条）
标题必须和它下属对应的内容绑定在同一个 chunk 里面，标题不能单独切出去；
整张表格、列表块、代码块尽量整块保留，不允许拦腰拆分；
只有单个语义块超长，超过 token 上限，才在内部语义断点递归拆分。
视频给出实测数据结论：专业领域文档（合同、技术规范、标书），结构感知切片相比固定长度切片，答案准确率可以提升 40% 以上。
3.3 落地两套可选择的切片策略（视频讲对比）
递归切片（工程最常用，优先推荐）
配置参数：单块 400 ~ 800 token；重叠窗口约 20%
作用：少量重叠，避免同一个逻辑段落被切在边界、召回丢失；性价比高，速度、成本可控。
语义切片（LLM 语义边界切分）
原理：调用大模型判断语义主题变化，在主题切换点切分；
优缺点：切分粒度最贴合人类理解；成本会提升 3~5 倍；
视频建议：不要默认上语义切片，评估业务收益之后再选用，普通知识库递归切片足够。
四、第三大模块：入库 + 检索环节（多路召回，拒绝单向量检索）
建库阶段：把经过结构切片后的每一个 chunk，做 Embedding，转为向量存入向量数据库；同时保留原文、来源元数据（文件名、页码、区块类型）。
检索阶段：禁止只用向量检索单路召回（视频明确踩坑点）
向量检索（稠密 Dense 检索）：负责语义相似匹配；适合意思相近、用词不一样的查询；缺点：对精确编号、专有名词、合同条款编号召回不稳。
关键词检索（BM25 稀疏检索）：精准匹配关键词、合同编号、条款号、专有名词；适合合同、法规场景。
两路召回融合：把向量召回结果 + BM25 关键词召回结果合并（常用 RRF 融合）
重排 Reranker（视频强调对最终质量影响很大）
作用：粗召回会带回来很多相关度低、噪声片段；Reranker 模型对合并后的候选片段重新打分排序，把真正相关性最高的片段排到前面，过滤噪声。
面试加分点：不能只说向量检索，要讲「BM25 + 向量双路召回 + Reranker 精排」。
五、第四大模块：上下文组装、生成、线上兜底策略（工程线上环节，面试容易漏）
上下文组装要求：把 Reranker 排序后的高相关 chunk 拼接进 Prompt 交给大模型。
强制要求（合同类场景重中之重，视频原话）：回答必须附带来源引用，标注答案来自哪个文件、第几页；是合同 RAG 可信度、可溯源的核心，方便人工核对。
线上天然存在的解析缺陷（视频举例脏数据情况）
扫描件原稿质量差、盖章遮挡，OCR 持续有错别字；
部分复杂表格版面，版面解析偶尔识别错乱；
置信度兜底策略（视频落地方案）
给解析结果、OCR 结果增加置信度打分；
置信度低于阈值的劣质片段，不要强行喂给大模型；
兜底分支：要么提示用户该文档识别质量差，人工复核；要么走多模态图片页面二次校验。
召回平衡原则（视频结论）：召回率和准确率是矛盾的。
不要一味拉高 TopK、追求全召回，大量无关噪声进上下文，会稀释有效信息、引发幻觉；
也不能阈值太保守，漏掉关键合同条款；
优化方式：基于业务测试集反复调参、做评估集验证。
