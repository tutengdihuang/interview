MCP 架构评审视频完整内容总结
该视频面向Agent 开发、大模型系统设计面试，讲解面试高频题：MCP‑Server 反向发起模型采样请求时，权限边界如何设计。
背景常识：常规 MCP 流程是：模型（客户端）调用 MCP‑Server 提供的工具；而反向采样是 MCP‑Server 主动向客户端请求调用大模型做生成，很多开发者只熟悉工具调用，忽略这个反向路径带来的安全信任风险。
核心总观点：MCP 只是连接的标准化协议，协议本身不解决安全权限，Server 不能默认继承用户全部权限，不能随意构造模型上下文，必须由客户端做显式授权、资源裁剪、用途管控、结果隔离、安全审计，形成工程闭环。
一、题目的考察本质
题目表面问 MCP 采样接口怎么做，实际考察系统信任边界设计。
MCP 只标准化模型与外部工具的通信，接入的 MCP Server 不一定可信；一旦 Server 可以反向调用模型，就存在越权读取敏感数据、提示注入、借采样结果触发高危操作的风险。面试答题不能只讲协议调用，要讲清楚：请求是谁发起、权限来源是什么、审批边界在哪里。
举例场景：文档分析 MCP‑Server 需要调用模型总结一份敏感合同。如果不做权限管控，Server 除了拿到本次需要的合同片段，还可能越权读取用户整个知识库的全部文档数据。
二、三大维度权限边界设计
1. 请求身份维度：可审计的请求溯源
每一次 Server 反向采样，必须完整记录身份元数据：是哪一个 MCP Server、哪一个工具函数、属于哪个业务任务、基于哪个用户的授权发起。
业务权限控制权保留在客户端 / 宿主系统，不能因为接入 MCP 协议就默认信任外部 Server；
如果缺少身份标记，发生越权、数据泄露事故之后无法追溯定位问题源头。
2. 资源范围维度：最小必要原则做上下文裁剪
采样传给模型的上下文，严格只提供当前任务必需的片段资源。
MCP Server 返回的提示内容属于不可信外部输入；外部内容只能作为任务材料，不允许覆盖系统提示、篡改用户顶层目标，用来抵御间接提示词注入攻击；
不能直接把用户完整知识库、全部会话历史、其他工具返回的敏感数据一股脑交给采样请求；
例子：只传给模型需要总结的合同片段，而不是用户全部知识库文档。
3. 结果用途维度：区分风险等级，高危动作二次确认
采样输出只是中间结果，采样生成完成≠获得执行权限，要根据用途风险分级管控：
低风险：仅做摘要、阅读类输出，风险较低；
高风险：采样结果后续会触发写操作、发送邮件、删除文件、调用其他修改状态的工具，必须抬高安全门槛；
高风险链路必须配置防护护栏（guardrail），必要时增加人工确认，完整链路埋 trace 追踪；
风险：如果没有管控，恶意或者存在漏洞的 MCP Server，可以借一次采样请求诱导模型，进入越权执行工具的路径中。
面试简短答题模板
将 MCP sampling 设计为受控能力，先校验请求身份与使用用途；再按照最小必要裁剪输入资源；采样结果限定在授权范围内使用；一旦涉及会改变外部状态的副作用操作，必须再次确认校验权限，同时留存完整审计日志。
三、真正可上线 MCP 系统的工程要点
只跑通正常业务流程不算完成，必须处理各类异常坏路径，形成完整闭环。
1. 准备 bad‑case 测试样本
上线不能只验证演示场景，要覆盖故障异常用例：证据冲突、工具调用延迟、用户中途取消任务、权限不足、旧任务状态继续执行、输出格式正确但是业务语义错误。
系统要可以识别、拦截异常，支持问题回放，有对应的修复方案，才算具备上线条件。
2. 线上持续治理（面试加分三句话，拔高回答深度）
关键业务判断要有可追踪证据，不能让模型凭主观生成的内容直接下业务结论；
所有修改外部状态的动作，必须同时满足：权限校验、幂等处理、确认机制、完整审计；
问题修复后，case 要回流进入回归评测集，不能只修复当下这一条样本，避免新版本复现同类漏洞。
核心工程认知：模型能正确回答正常问题只是基础能力；系统在不确定的时候可以停下来、做检查、执行兜底逻辑，才是 Agent 大模型应用真正的工程能力。故障案例持续回流评测与监控指标，持续治理风险，而不是一次性开发完就结束。
四、视频核心总结
MCP 解决的是连接协议标准化，不会自动提供权限、安全、审计能力；
上线生产级 MCP 系统，必须理清用户、MCP Server、资源、模型采样四者之间的信任边界；
大模型 Agent 项目难点不在于单次生成效果好看，而在于上线后的持续安全治理、异常兜底、回归测试闭环。

视频标题：面试必考：MCP Server 反向请求模型采样，权限边界怎么设计
主讲：小哲讲 agent 项目
核心题干：面试官问：MCP Server 反向发起 sampling/createMessage 采样请求时，权限边界该怎么设计？
开篇一句话提醒：很多人只答 “加中间件”，这个回答是不够的，踩分点不全。
0、前置基础概念（视频开篇必讲）
常规正向 MCP 流程：用户→客户端（Host）→模型→调用 MCP Server 工具，模型主动调用 Server 拿数据、执行工具，绝大多数开发者只熟悉这个正向链路。
反向 Sampling 流程（本题场景）：MCP Server 在执行工具的中途，主动发 sampling/createMessage 请求给客户端，向客户端借宿主侧的大模型做生成；Server 自己不持有模型 Key、不单独付费，复用客户端已有的模型能力。
反向采样典型业务例子（视频原话例子）：
文档分析 MCP Server，对外暴露工具：summarise this contract（总结这份合同）
Server 逻辑：拉取 PDF、提取原文，然后发起 sampling 请求：“帮我提炼这份文本里的义务条款”
为什么要这么做：如果 Server 自己接入大模型，就要单独维护密钥、单独计费、绑定固定服务商；反向采样把模型能力交给宿主统一管控。
视频第一重要定性结论：MCP 只是通信标准化协议，协议本身不带权限、安全、审计、隔离能力；协议只定义调用格式，不定义信任关系。
风险根源（视频原话）：权限流向反转了。正向是模型去访问工具资源；反向是外部 Server 变成请求方，来调用模型，模型变成了 Server 的下游。一旦不设防，不可信 Server 就有机会注入提示、窃取上下文、诱导模型越权。
面试考察本质（视频原话）：这道题表面考 MCP 协议，本质考察系统信任域边界、数据最小化、权限溯源、副作用隔离，不是考 API 调用。
1、第一层防线：请求身份与溯源（可审计）
要点逐条：
每一条 Server 发出来的采样请求，必须带上完整的溯源元组，缺一不可：
是哪一个 MCP Server 实例（服务标识）
当前是哪一个工具函数
归属哪一个用户、哪一个会话、哪一个父任务 ID
控制权归属：权限主体永远在客户端 / 宿主，Server 不继承用户的全部权限，Server 本身默认不可信，哪怕这个 Server 是你自己开发的，也要按不可信组件处理。
反例（视频例子）：不能写死配置 “这个 Server 全部允许采样”；同一个 Server，不同任务、不同用户的权限范围不一样。
例子：合同分析 Server，处理内部员工合同 和 外部供应商合同，采样允许访问的数据范围不一样；外部供应商合同场景，采样不能带入公司内部定价表、内部保密台账。
审计强制要求：所有采样请求、入参、返回结果、放行 / 拒绝理由、消耗 Token、时间戳、操作人，全链路日志持久化。出事之后要能定位：是谁、哪个 Server、哪个工具、什么时候、拿了什么内容请求模型。
结论：信任不是静态绑定在 Server 维度，是【Server + 用户 + 任务类型】三维动态信任评估。
2、第二层防线：输入上下文裁剪、最小必要原则（数据层，采样进模型之前拦截）
要点逐条：
核心规则：Server 提交给 sampling 的 prompt 内容，属于不可信外部输入。
禁止行为清单（视频原话）：
禁止 Server 直接覆盖、篡改顶层系统提示词
禁止 Server 直接拿到用户完整会话历史
禁止 Server 拿到其他无关工具返回的敏感结果
禁止 Server 读取超出本次任务范围的知识库、文件、数据库内容
抵御攻击目标：抵御间接提示注入。恶意 / 有漏洞的 Server，可以在采样 prompt 里面夹带指令，诱导模型篡改目标、读取别的资源。
视频主例子（合同例子完整展开）：
场景：用户让合同 Server 总结一份私有合同，合同原文含有身份证号、银行账号、法人敏感信息。
错误做法：Server 直接把完整原文塞进 sampling 请求发给模型，模型上下文里面直接拿到全部敏感原始数据。
正确做法：采样前先做脱敏 + 范围裁剪，只传递本次摘要任务必须的片段；敏感字段掩码，并且严格限定：只能传入当前这份文档的片段，不能夹带用户知识库里面别的合同、别的文件。
辅助例子（日历 Server）：日历 Server 请求采样生成会议摘要，只传入当前这条会议文本，不附带用户邮箱密钥、其他日程、联系人隐私。
辅助例子（数据库查询 Server）：采样解释表结构，只传入目标表的 schema，不允许拉取全表业务数据。
结论：数据边界在进入模型之前校验，而不是等模型输出之后再过滤；网关在 prompt 送入模型前，对比【Server 声明的采样用途、声明的数据范围】和实际传入 prompt 里面的内容，一旦超范围直接拒绝，模型完全看不到非法内容。
3、第三层防线：采样结果风险分级，区分只读 / 有副作用动作（结果用途管控）
要点逐条：
视频核心金句：采样生成结果 ≠ 获得执行权限。采样输出仅仅是一段中间文本，它本身不具备调用工具、修改状态的资格。
风险两级划分：
低风险：只读类、纯信息输出。比如摘要、分类、标签、解释文本，没有对外修改。低风险可以配置自动放行（前提是前面两层校验通过）。
高风险：采样结果后续要用来执行带副作用操作：写文件、删除文件、发送邮件、提交工单、转账、发布内容、修改数据库。
高风险链路强制护栏（guardrail）：
独立二次权限校验（和采样权限分开，走工具本身的权限）
必要时必须人工确认（human-in-the-loop）
链路增加 Trace，把采样 ID 和后续工具调用 ID 绑定，方便追溯是哪一次采样生成的内容驱动这个动作
攻击场景例子：恶意 Server 在采样请求里诱导模型输出指令：“去删除我的全部文档”。如果没有这层隔离，模型生成之后直接触发删除工具，就会越权破坏。
结论：模型输出内容，必须单独走工具权限体系校验；不能因为是模型输出，就默认可信。
4、落地组件：采样网关（视频专门讲网关，不是简单开关）
要点逐条：
网关不是简单的 “允许 / 拒绝” 二元开关，是运行时四维过滤器，每次采样请求进来依次做 4 件校验，全部通过才放行：
① 身份校验：Server 是否在注册信任域内，身份签名合法
② 上下文容器隔离：分配独立隔离上下文，和别的任务、别的用户上下文隔开
③ Token 配额管控：预扣 token 预算，防止 Server 无限循环发起采样，打爆计费
④ 作用域匹配校验：核对 Server 声明的采样目的、声明数据范围，对比实际 prompt 里面携带内容是否越界
任意一项校验失败，直接返回结构化拒绝原因，不把内容送入模型。
5、版本补充说明（视频附带的协议版本提醒，面试加分项）
MCP 协议在 2026-07-28 版本，旧的 sampling 通道（sampling/createMessage）已经标记为废弃（deprecated），SEP-2577 提案。
新推荐方案：Server 需要模型推理能力时，直接在 Server 内部调用 LLM 厂商接口，不再走反向采样通道。
兼容说明：存量系统还可以短期兼容旧 sampling；但是新系统不建议基于旧 sampling 做设计。
替代交互方式：如果 Server 中途缺信息，改用 elicitation（向用户追问信息），而不是借宿主模型采样；但最小权限、用户授权、审计的安全原则完全不变。
6、上线工程闭环：坏 case、异常治理、回归评测（视频后半段工程化部分，很多人漏答）
要点逐条：
只跑通正常 demo 流程，不代表可以上线生产；上线必须覆盖坏路径测试用例。
需要准备的 bad case 清单（视频原话列出）：
证据冲突的场景
工具调用超时、延迟
用户中途取消任务，但是已经发起的采样还在继续
权限不足场景
旧任务残留状态继续执行
格式输出正确，但是业务语义是错误、诱导性内容
系统兜底能力：遇到不确定、高风险、证据不足的时候，系统要主动停下来、拦截、触发检查、兜底降级，而不是硬跑模型生成结果。
视频结论：模型答对正常问题，只是基础能力；Agent 工程真正难点，是系统在不确定的时候知道刹车、检查、兜底。
线上持续治理闭环（三句拔高结论，视频原话）：
① 关键业务判断，必须绑定可追踪证据，不能仅凭模型主观生成内容下业务结论；
② 所有会修改外部状态的副作用动作，四个条件同时满足：权限校验 + 幂等处理 + 确认机制 + 完整审计日志；
③ 修复完漏洞 / 异常 case 之后，这个 case 回流进入回归评测集，持续回归，防止新版本迭代把安全护栏冲掉，漏洞复现。
工程总结论：安全治理不是一次性开发完就结束，是持续监控、持续回流 case、持续评测的长期过程。

8、视频最终收尾总总结（视频结尾原话）
MCP 解决的是连接协议标准化，不会自动提供权限、安全、审计能力；
生产级 MCP 系统，必须理清四者信任边界：用户、MCP Server、资源、模型采样；
Agent 大模型项目难点不在于 demo 效果好看，而在于上线后的持续安全治理、异常兜底、回归测试闭环。
