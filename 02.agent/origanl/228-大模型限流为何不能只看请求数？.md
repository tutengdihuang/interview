视频内容总结

这是一道后端 / 架构面试题讲解：为什么大模型接口限流不能只靠 QPS（请求次数），生产环境该怎么做限流。

核心观点

只限制请求数 QPS 是网关层面的浅层做法。同样是 1 次接口调用，资源消耗差距巨大：简单提问只消耗几百 token；上传长文档生成报告可以消耗几万 token。

如果仅按请求数限流：简单小请求被误拦截，大算力消耗的重型请求依然能打垮服务，算力成本不可控。

生产环境三层限流指标

请求频率 (QPS)：基础防护，避免短时间大量请求直接刷爆网关。

Token 配额：管控真实算力与成本，是大模型最核心的资源指标。

并发槽位：限制同时执行推理的任务数，防止耗时很长的生成请求长期占用 GPU，造成大量用户排队阻塞。

重要细节：输入、输出 token 分开统计

输入 token：长输入主要消耗预填充、上下文内存资源；

输出 token：长输出消耗解码生成算力，拉长请求耗时。

两者对系统压力不一样，要分开管控。工程上还会配套：最大输入 / 输出长度限制、用户每日 token 额度、高峰期动态降额等手段。

面试参考回答模板

大模型限流不能只依赖请求次数 QPS，需要综合请求频率、token 配额、并发槽位，区分输入输出 token，结合用户等级做限流。只控制请求数，只能管住表面调用量，管不住底层 GPU 算力和业务成本。

面试官问你，大模型接口限流为什么不能只按请求次数来算？

如果你回答每个用户一分钟最多调用多少次，这个答案只说到网关层。大模型服务真正消耗资源的不是请求个数，而是 token、上下文长度、输出长度和并发占用时间。

先给结论：大模型限流应该按资源消耗来设计，而不是只按 QPS。两个请求看起来都是一次调用，但成本可能差十倍。一个用户问一句短问题，只消耗几百 token；另一个用户上传文档，让模型生成报告，可能直接吃掉几万 token。

如果你只按请求次数限流，轻请求会被误伤，重请求反而可能把系统拖垮。

生产级限流至少要看三层指标：

第一是请求频率，防止短时间内流量被刷爆；

第二是 token 配额，控制真实算力成本；

第三是并发槽位，防止长请求长期占住推理资源，导致其他用户排队。

这三层缺一层，系统都会出现偏差。

还有一个细节：输入 token 和输出 token 最好分开算。输入很长，主要影响预填充阶段和上下文内存成本；输出很长，主要影响生成解码阶段，拉长等待时间。两个阶段对服务压力不一样，限流策略也不应该完全相同。

所以有些系统会设置最大输入长度、最大输出长度、单用户日 token 额度，以及高峰期的动态降额。

所以这题你可以这样答：大模型限流不能只看请求次数，要综合请求频率、token 配额、并发槽位，区分输入输出 token，结合用户等级做限流。只控制请求数，只能管住表面调用量，管不住底层 GPU 算力和业务成本。
