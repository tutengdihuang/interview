面试官问：做 AI 大模型应用，为什么要做调用链 Trace 追踪，而不是只监控接口成功率？

很多人第一反应只会回答：方便监控、方便排查问题。这个答案很浅，面试拿不到高分。

传统后端接口，一次请求就是一次 RPC，返回 200 基本代表业务成功。

但大模型 RAG、Agent 链路完全不一样。一条用户请求，会串起很多步骤：

意图识别、Query 改写、Embedding 向量化、向量库检索、重排 Rerank、工具调用、大模型生成、输出 JSON 解析、结果组装。

HTTP 返回 200，只代表网关服务没崩，完全不等于业务结果是正常的。

哪怕接口返回成功，依然会出现很多问题：

向量检索召回的文档是错的、不相关，模型基于错误资料回答，答案跑偏；

Agent 反复重试调用工具，多次轮次，耗时暴涨、成本翻倍；

大模型输出格式不对，生成无效 JSON，解析失败，最后给用户空答案；

整体响应很慢，但你不知道时间耗在哪一步，分不清是向量库慢、模型推理慢，还是业务代码慢。

只看接口成功率，会严重误判系统真实健康状态。

接口成功率指标，只能看服务活没活着，看不出中间环节的质量问题。

而调用链 Trace，就是把整条 AI 请求链路拆成一个个独立可观测的阶段：

网关耗时、Query 改写耗时、向量检索耗时、重排耗时、首 Token 延迟、模型生成总耗时、解析结果状态、每一步输入输出摘要。

Trace 的价值有两点：

第一，定位性能瓶颈。用户觉得慢，通过 Trace 一眼看到耗时堆积在哪，是向量数据库排队，还是大模型推理，或是业务预处理。

第二，定位业务质量问题。用户反馈回答不对，不一定是大模型本身不行。有可能是上游 Query 改写错了，或是检索召回的文档不对。没有 Trace，只能盲猜；有 Trace，可以直接定位出错的环节。

面试标准答案：

大模型系统做调用链追踪，目的是把一次 AI 请求拆解为可观察、可定位、可优化的多个阶段。接口成功率只能判断服务有没有存活，而 Trace 才能回答：系统为什么慢、为什么结果错误、错误发生在哪一个环节。
