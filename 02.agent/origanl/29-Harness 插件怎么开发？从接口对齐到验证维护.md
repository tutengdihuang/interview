视频内容详细总结：Harness 插件怎么开发？从接口对齐到验证维护
视频作者：小哲，主题围绕AI Agent（Harness）插件完整开发流程，核心观点：插件开发不等于让 AI 生成代码、装上就完事，要做好需求、接口对齐、逐项验证、版本维护完整闭环。
一、区分插件使用者 vs 插件开发者
普通使用者：只关心插件怎么安装、启用、配置。
插件开发者：需要重点关注：插件如何接入宿主平台、调用哪些接口、插件生命周期处理。
插件安装来源可以是软件包、代码仓库、本地目录，但具体支持哪种方式，必须遵守宿主平台的插件规范，不能凭空开发。
二、前期准备：不要直接让模型随便写代码
不要直接丢想法给 Agent 就开始写代码，要做好前置输入：
提供宿主官方开发文档、对应版本的示例代码、清晰完整需求。
如果文档不全，参考官方源码、已经成熟的现有插件。
核心：对齐真实接口与平台约定，禁止让 AI 凭脑补猜测接入方式。
需求描述不能只靠截图，要写清楚业务动作：比如技能市场插件，要写明白搜索、列表展示、详情页、安装的业务逻辑；数据来源、安装之后文件存放位置。参考已有代码，但最终必须和宿主接口对齐。
三、搭建最小可运行闭环（先跑通基础流程）
以技能市场插件举例：
最小闭环目标：查看技能列表、打开详情页、安装测试技能，确认宿主真正识别加载插件。
⚠️重要提醒：页面显示 “安装成功” 仅仅是前端 UI 提示，必须去检查实际文件、真实加载状态，不能只看页面反馈。
页面上每一个按钮交互，都要有对应的可验证行为。
四、逐项功能测试与问题修复
要逐条验证全部业务功能：
搜索关键词是否真的过滤变更结果
“加载更多” 是否正确追加数据
详情页面渲染是否正常
安装完成后插件能否在会话中正常使用
遇到功能失败：把预期行为、实际运行结果、报错信息交给 Agent 去修复，修复完成再重新验证该功能；不要只让 AI 口头回复 “已经完成”。
补充：开发阶段的热重载、本地加载可以加快调试速度，但不等于达到发布质量。
五、后期维护、版本管理、发布注意事项
问题定位：出 bug 要区分三类原因：①自己业务逻辑写错；②多个插件之间互相冲突；③宿主平台升级，接口发生变更不兼容。
版本管理：第一个可用版本提交代码仓库，后续迭代更新；新开会话继续开发时，让 Agent 先读取现有代码，避免把已经正常的功能改坏。
宿主平台升级之后，要重新校验依赖接口、原有测试用例，防止兼容性损坏。
分发发布：按照宿主要求选择分发方式，可以开源代码仓库，也可以打包软件包。
发布材料必须写清楚：使用说明、配置步骤、插件兼容的宿主版本。
本地机器跑通只代表本地验证通过，不等于所有用户环境都可以正常运行。
六、视频核心总结观点
评价插件开发质量，不要看生成多少代码文件、开发耗时。重点看三件事：
需求是否真正落地、对齐平台接口规范；
全部功能是否做过逐项验证；
版本迭代、宿主更新后，能不能定位、修复问题。
Agent 可以辅助写代码，但是验证、维护的闭环流程需要人建立，插件才可以长期稳定使用。

视频标题：Harness 插件怎么开发？从接口对齐到验证维护
主讲：小哲
核心主线：不要把插件开发简单理解为让 AI 生成代码装上就完事；插件开发是一套从需求输入、接口对齐、最小闭环、逐项验证、故障分类、版本维护、发布交付的完整闭环流程
一、开篇基础区分：两类角色对插件的关注点完全不一样
插件使用者（普通用户）：只关心插件怎么安装、启用、配置，不关心底层接入逻辑。
插件开发者：核心要关注三件事：插件如何接入宿主 Harness 平台、调用哪些宿主接口、插件完整生命周期处理逻辑。
补充前提结论：插件支持的安装来源（软件包、代码仓库、本地目录）不是自己随便定的，必须严格遵守宿主平台官方插件规范，不能凭空自己设计接入方式。
二、前置阶段：需求准备，禁止直接丢想法给模型写代码（视频重点强调）
错误做法：直接给 Agent 一个想法，让它从头写插件代码。
正确前置输入材料（必须一次性提供）：
宿主 Harness 官方开发文档，必须和宿主版本一一对应
官方配套示例代码
清晰、可落地的文字需求
文档不全时的参考方案：查阅官方源码、已经上线、成熟的现有插件实现作为参考。
这个阶段第一优先级结论：对齐真实接口与平台约定，禁止让 AI 凭脑补、猜测来写接入逻辑。
配套实战例子：技能市场插件需求
❌ 错误需求写法：只给一张 UI 截图，只给页面布局
✅ 完整需求必须写清楚：
① 业务动作：搜索、列表展示、打开详情页、安装技能，每个动作要做什么
② 数据来源：列表数据从哪里获取
③ 持久化规则：技能安装之后，文件存放位置
补充结论：已有插件代码只能用来参考，最终实现必须对齐当前宿主真实接口，不能照搬旧插件。
三、第二步：先搭建最小可运行闭环，而不是一次性写完所有功能
例子仍然是：技能市场插件
最小闭环目标（只做最少必要功能）：
可以正常加载、看到技能列表
可以点开、渲染技能详情页
可以发起安装、安装一条测试技能
确认宿主 Harness真实识别并加载了这个插件
非常关键的一条避坑结论：页面上显示 “安装成功”，仅仅是前端 UI 的提示文字，不等于插件真的安装、加载成功。
验证动作（最小闭环验收动作）：必须手动检查底层文件、检查宿主内部的插件加载状态。
配套规则：页面上每一个可见的交互按钮，都要有对应的、可核验的后台行为，不能只有 UI 反馈。
四、第三步：全功能逐项测试、迭代修复（视频核心流程）
承接技能市场插件例子，逐条验证清单：
搜索功能：输入关键词之后，返回的列表结果是否按关键词正确过滤变更
分页功能：点击 “加载更多”，是否追加新数据，而不是覆盖原有列表、重复加载
详情页：详情信息渲染正常，无缺字段、无报错
安装后可用：技能安装完成，回到 Agent 会话里面，这个技能能不能正常调用、使用
Bug 修复标准流程：
单项测试失败时，整理三样信息交给 Agent：【预期行为】【实际运行结果】【完整报错信息】
修复完成之后，重新单独验证这一项
硬性禁令：不要只看 Agent 口头回复 “已经做完、修复好了”，口头说明不算交付完成
关于开发调试工具的补充结论：
热重载、本地目录加载插件，作用仅仅是缩短调试验证的循环，开发的时候方便快速改代码看效果
重要区分：能本地热重载跑通 ≠ 插件达到可以对外发布的质量标准
五、第四步：问题根因分类（上线 / 迭代出 bug 时用来定位）
宿主 Harness 插件 bug 一共只有三类来源，排查时优先区分：
自己插件业务逻辑代码写错（自身代码问题）
插件之间冲突：多个插件注册了同一个事件、抢占同一个界面入口，互相干扰
宿主平台升级：Harness 本身版本更新，原有接口变更、废弃，出现兼容性失效
例子补充：不同插件监听同一个宿主事件，就很容易出现互相覆盖、冲突
六、第五步：版本管理、迭代维护规则
第一个稳定可用版本：提交到代码仓库，作为基准版本
后续迭代开发：新开 Agent 会话继续改插件时，第一步先读取、导入已经存在的完整代码
目的：防止 AI 无意识把已经稳定、正常的功能改掉（经典的改好一处、弄坏别处）
宿主升级后的强制动作：宿主版本升级之后，要重新跑一遍全部测试用例，重新校验依赖接口，防止兼容性损坏
七、第六步：分发发布、交付材料要求
分发渠道二选一，遵守宿主规范：开源放到代码仓库；打包成平台要求的软件包分发
发布包里面必须附带交付文档，缺一不可：
使用说明
详细配置步骤
兼容范围：写明适配哪些宿主 Harness 版本（哪些版本支持、哪些不支持）
重要结论：在开发者自己本地机器全部跑通，只代表本地环境验证通过，不能保证所有用户的环境都正常运行。
八、视频末尾的总评判标准（最终结论，视频反复强调）
评判一个插件开发质量好不好，不看代码文件数量、不看开发耗时长短，只看三点：
需求有没有真正落地、所有调用逻辑对齐宿主官方接口规范
全部功能点，都做过逐项、可复现的验证
具备长期维护能力：宿主升级、出 bug 之后，可以定位根因、持续修复
最终总结论：Agent 可以帮人写代码、做实现，但是整套验证、回归、维护闭环，必须由人来建立，插件才可以长期稳定给别人使用
