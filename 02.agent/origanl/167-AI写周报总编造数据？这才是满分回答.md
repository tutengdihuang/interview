视频内容详细总结
视频主题：面试题 ——AI 写周报频繁编造虚假数据该如何解决。
核心观点：只在 Prompt 写 “请勿编造数据” 是无效解法。这道面试题表面考提示词工程，本质考察大模型工程化、数据生产闭环的设计能力。大模型编造数字不是主观故意，是它本身没有真实数据源，靠概率输出内容。正确思路：不让大模型回忆、计算数据；由 SQL、Python 负责取数、运算；大模型只做语言文字组织。
三大闭环解决方案
1、数据源闭环（源头杜绝幻觉）
周报业务指标（新增客户、成交金额、转化率）存储在 CRM 等业务数据库中。
不要拿历史周报文本喂给模型，让模型猜测本周数据；而是写 SQL 查询本周真实业务数据，Python 计算环比、完成率，输出 JSON 结构化数据，注入 Prompt。给模型的指令附带现成真实数据，而不是空泛的 “帮我写周报”。
风险点：字段改名、数据源迁移、统计口径变更，会导致 Agent 复用旧数据产生幻觉。
工程校验手段：每次生成周报之前校验数据新鲜度，检查查询时间戳、数据行数是否符合预期，从源头切断编造可能性。
2、计算逻辑闭环（不让大模型做数学运算）
大模型做数学是概率性，计算存在出错概率，业绩数据不能交给模型运算。
所有聚合、占比、增长率计算全部交给 SQL、Python 代码完成。大模型只接收已经算好的最终数字，仅负责润色成通顺的业务描述文字。
实现方式：在 System Prompt 明确划分职责边界，严格区分 “数据计算” 和 “文本表达” 的分工。
3、模板结构闭环（限制模型自由发挥空间）
周报结构固定：概况、数据回顾、重点事项、下周计划。不要让模型自由创作。
使用严格分段模板，明确每个段落允许写什么内容，规定数字必须取自指定字段，禁止模型修改数值。
后置校验步骤：生成周报后，用正则提取文本中全部数字，和原始 JSON 数据逐项比对；一旦数字不匹配，直接回退、重新生成。
完整落地四步流程（面试可以直接使用）
梳理周报需要用到的全部指标字段清单；
编写 SQL、Python 脚本，查询并且计算指标，输出 JSON 结构化数据；
将 JSON 数据 + 固定周报模板一起注入提示词；
输出后做数字比对校验，数值不一致则重生成。
面试加分回答（应对面试官追问）
追问 1：如果 SQL 查询出来的数据本身就有错怎么办？
回答：上游 ETL 流程增加行数校验、空值监控；周报生成之前，原始数据已经完成质量校验，过滤脏数据。
补充 2 个隐蔽坑点（拉开和普通面试者差距）
缺少时间戳标注：模型会错把上个月数据当作本月数据填入周报；
API 返回空结果却不报错：Agent 调用接口返回空，没有抛出异常，模型只能自行脑补补齐数字。
视频核心结论
AI 幻觉治理不能单纯依赖提示词约束，需要搭建完整工程链路：数据查询、数据校验、代码计算、结构化输入、输出校验，整套闭环，才能彻底解决 AI 周报编造数字的问题。

视频主题：面试题 ——AI 写周报老是编造虚假数据该怎么办

一、视频开篇背景、错误解法、题目的真实考察点
面试原题：AI 自动写周报的时候老是编数字怎么搞？
绝大多数人的错误回答：在 Prompt 里面增加一句话「请勿编造数据」。
视频观点：面试官表面点头，心里已经判死刑。只靠 Prompt 禁止编造是远远不够的。
底层原理（为什么加 “请勿编造” 没用）：模型不是主观故意要编造数据；它根本没有真实数据源，输出是概率生成，没有事实依据就会瞎编。
这道面试题真实考察内容：表面考提示词工程（Prompt Engineering）；本质考察你是否懂得把 LLM 大模型输出闭环接入真实的数据生产工程链路。
视频总核心答案（一句话）：不要让大模型回忆数据；搭建数据获取逻辑，SQL 做取数、Python 代码做计算，大模型只负责语言文字组织。
博主原话：不要让模型回忆数据，让模型去执行数据获取逻辑，由 SQL 取数代码计算，模型只负责语言组织。
二、第一大闭环：数据源闭环（从源头切断幻觉）
业务场景例子：周报需要指标来自 CRM 业务系统：本周新增客户、成交金额、转化率。
❌错误做法：把历史周报（上上周周报文本）喂给大模型，让模型自己推测、预测本周业务数据。
✅正确做法：
1）写 SQL 查询数据库拿到本周真实原始业务数据；
2）用 Python 脚本计算环比增长率、指标完成率；
3）把全部结果封装成JSON 结构化数据，直接注入 Prompt。
Prompt 输入对比示例（视频原文例子）
差的 prompt：请帮我写一份本周周报。
正确输入 prompt：以下是本周真实数据：新增客户三十七个，环比增长百分之十二。请基于此生成周报段落。
隐藏工程风险点（非常关键）
取数链路不是一次性写完就万事大吉。
发生：字段改名、数据源迁移、统计口径调整，只要其中一项发生变化，但 Agent 还继续复用旧的数据，幻觉就会悄悄出现。
闭环校验手段（每次生成周报之前必须执行）
校验数据新鲜度：检查 SQL 查询出来数据的时间戳，确认是否是最近五分钟内的结果；
校验数据行数：对比返回行数和业务预期量级是否匹配；
目的：从数据源源头，彻底切断模型编造数字的可能性。
三、第二大闭环：计算逻辑闭环（不让大模型做数学运算）
❌错误偷懒行为：给一堆散乱原始数字，交给大模型自己算增长率、占比、完成率。
视频原文警示：大模型做数学是概率性的；算一百次有五次会算错。业绩业务数字，不能拿业务去赌模型计算正确率。
✅正确分工：
SQL 负责数据聚合；
Python 负责算比例、环比、完成率等全部数学运算；
大模型只接收已经全部算完的最终结果，不做任何计算工作；模型的任务仅仅是把冰冷数字润色成通顺业务文字。
原文实例（模型仅做语言扩写）
输入给模型现成结果：环比增长12%
模型输出自然语言文本：本周新增客户三十七个，相比上周的三十三个有了明显回升。
实现手段：在 System Prompt 里面，明确给大模型划清职责边界。明确区分：数据查询计算属于代码，文字润色属于大模型。
视频附带广告提示：System/User Prompt 分工的案例，在橱窗课程提示工程章节；想要系统学 Agent 开发看橱窗课程。
四、第三大闭环：模板结构闭环（限制模型自由发挥空间）
周报固定章节结构：概况、数据回顾、重点事项、下周计划。
❌错误：完全放开，允许大模型自由发挥、自由创作周报全部内容。
✅正确做法：提供严格分段 section 模板：
每个章节 section 严格规定允许写什么类型的内容；
明确每个数字必须取自哪一个 JSON 字段；
明确哪些字段数值，模型禁止修改；
效果：就算模型想要编造，也没有可以发挥修改的语言空间。
后置输出校验步骤（生成完周报之后做）
使用正则表达式，提取生成周报文本当中所有数字；
将提取出来数字，和原始 JSON 结构化数据逐项对比校验；
如果任意一个数字不匹配原始 JSON，直接回退，触发重新生成周报。
五、完整落地四步执行流程（面试可以直接背诵使用的模板）
视频原文 4 步流程：
第一步：梳理定义本周周报需要用到的全部指标字段清单；
第二步：编写 SQL 查询脚本 + Python 计算脚本，算出全部指标，输出 JSON 结构化数据；
第三步：将 JSON 结构化数据 + 固定周报段落模板，一同注入 Prompt；
第四步：生成周报后正则提取全部数字，与原始 JSON 逐项比对，数字不一致就回退重生成。
博主原话：这套流程完整跑通之后，周报不会出现任何一条大模型捏造出来的数字。
六、面试官追问场景、加分回答、隐蔽坑点（拉开和只会写 Prompt 的候选人差距）
追问 1：面试官提问，如果 SQL 查询出来的数据本身就是错的怎么办？
✅回答：上游 ETL 环节增加行数校验、空值监控；数据还没有流入周报生成流程之前，就已经完成数据质量门槛校验，拦截脏数据。
两个视频重点强调的隐蔽坑（很多人忽略）
坑 1：缺少时间戳标注。例子：模型直接拿上个月成交金额填充进本月周报。根源：Prompt 没有强制携带、校验数据对应的时间戳。
坑 2：Agent 调用 API，接口返回空结果，但是接口不会抛出报错；模型拿到空数据没有来源，就只能凭印象脑补补齐数字。
面试时主动说出这两个坑，直接拉开和只会写 prompt 的面试者差距。
七、视频全部最终结论汇总
仅仅依靠 Prompt 写一句 “请勿编造数据”，无法解决 AI 周报编造数字的幻觉问题。
大模型幻觉治理不是单点提示词技巧，要搭建完整数据生产工程闭环链路。
链路分层逻辑：数据源取数 → 数据质量 & 新鲜度校验 → 代码完成全部数学计算 → 结构化 JSON 输入给大模型 → 大模型仅做语言组织润色 → 输出后数字二次校验。
核心思想：事实数据交给工具与代码；大模型只负责表达，不能负责事实与计算。
底层认知：大模型写周报容易出问题，不是它写得不好；恰恰是它 “太擅长写通顺文本”，哪怕没有事实依据，也可以生成看起来非常真实的虚假数字。
