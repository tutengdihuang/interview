视频内容完整总结：Agent‑RAG 如何处理 PDF（面试题讲解）
视频核心观点：面试回答该问题，不能只简单说 “提取文本 + 切片 + 入库”，这只是 Demo 级做法；真实生产环境 PDF 包含扫描件、多栏排版、表格、图表，需要一套完整四层流水线，再加可追溯引用、评测机制，才是生产级方案。
背景痛点
普通 Demo 做法：PDF 抽文本、固定长度切块、存入向量库。
现实业务 PDF 存在大量复杂情况：扫描件、多栏排版、表格、流程图、截图、页眉页脚、合同条款。直接粗暴转纯文本，会出现文本错乱、信息丢失、上下文断裂，RAG 召回一堆无效碎片，答案不可信。
生产级 PDF 处理四大层级
第一层：多模态解析（文档类型识别与解析）
先区分 PDF 类型，不同类型走不同解析路径：
原生文本 PDF（论文、说明书）：直接抽取文本；
扫描版 PDF（合同扫描件、纸质拍照）：使用 OCR 识别图片内文字；
图文混排 PDF（财报、报告，含图表、复杂表格）：引入多模态 / 视觉大模型，理解图片、图表，不只是提取文字。
如果这一步判断错误，后续切片、检索、问答全部出错。
第二层：文档结构还原
不要把 PDF 变成一大坨无差别文本，需要还原文档骨架：
保留：页码、标题层级、章节、段落、表格、图片说明、脚注；
过滤 / 标记：页眉、页脚、水印等噪声；
每个信息带上定位元数据：例如合同某条属于第几章、第几页；财报数字来自哪张表格、哪个年份。
意义：为后续溯源打基础；如果丢掉结构，模型输出的答案无法核对来源，在合同、财报等合规场景是致命缺陷。
第三层：语义切片 + 上下文补充，构建索引
摒弃固定字数机械切分，改为按语义单元切片：
同一个标题下的段落作为一个 Chunk；
表格转为 Markdown 结构化，不打散成零散文字；
图表生成摘要，图表和图注绑定为一个单元；
每一个 Chunk 携带元数据：文档 ID、页码、章节、图表描述、版本信息。
上下文增强（参考 Contextual Retrieval 方案）：
给每一个切片额外生成一小段背景描述，说明该片段在全文的位置。例如：“本段来自第三章风险因素，讨论汇率波动对营收的影响”，该描述和原文一起向量化入库。
解决痛点：防止切片脱离原文后，模型只看到局部片段，缺失全局背景。
索引同时构建：向量索引 + 关键词索引，兼顾语义检索和精确词条检索。
第四层：Agent 工具链调用（Agent‑RAG 核心）
Agent 不要把整个 PDF 全部塞进 Prompt 上下文，而是把 PDF 能力封装成一组工具，由 Agent 根据用户问题动态选择调用：
search_pdf：向量检索获取相关文本片段；
read_page：读取指定页码完整内容；
extract_table：抽取解析表格；
analyze_chart：分析图表；
quote_source：输出原文引用来源。
调用策略：
用户简单事实类问题：直接走向量检索；
需要多章节对比的复杂问题：Agent 规划阅读顺序，调用多工具，读取多个章节；
涉及表格、图表：调用表格 / 视觉分析工具处理。
额外两个生产级落地细节（面试加分点）
1）可追溯引用 Citation
输出答案附带来源：页码、章节、原文片段。
目的：降低大模型幻觉，方便人工核验，满足合规业务要求，不能只输出答案却不知道信息出自 PDF 哪里。
2）评测闭环
评测不只看最终答案是否正确，还要多维度校验：
检索的片段是否命中关键信息；
引用页码、章节是否准确；
表格、图表解析结果是否正确；
是否存在漏字、信息丢失。
面试标准回答总结（视频给出的答题模板）
处理 PDF 不是简单转文本切片入库。先识别 PDF 类型做对应多模态解析；接着还原文档章节、页码、表格等文档结构；之后做语义切片，给 Chunk 补充上下文，构建向量 + 关键词索引；再由 Agent 调用 PDF 工具按需检索、读页、抽表、解析图表；最后输出附带页码章节的可追溯引用，并建立多维度评测机制，保障 PDF‑RAG 生产可用。

一、开篇：Demo 方案的问题（视频先讲反面案例）
Demo 方案（绝大多数初学者的回答）
流程：PDF → 抽取纯文本 → 按固定 token / 字数切 Chunk → Embedding → 向量库入库 → 用户提问向量召回 → 丢给大模型生成答案。
视频列出 Demo 方案对应的全部痛点 + 业务例子
真实业务 PDF 不是干净纯文字文档，会遇到下面所有情况：
扫描件 PDF：纸质合同扫描、纸质档案拍照 PDF，没有文本层，直接抽文本是空的；
多栏排版 PDF：学术论文、技术手册双栏，直接抽文字会左右栏错乱，阅读顺序颠倒；
表格：财报、报价单、审批表，直接打散成普通文本，行列关系丢失，数字归属混乱；
流程图、截图、插图：产品手册、架构图、截图，文字提取拿不到图里信息；
页眉、页脚、水印、页码重复文字：每页重复，切片后大量噪声，召回一堆重复无效片段；
合同类长文档：条款跨段落、跨页，固定切分把同一条合同规则拆成两块；
最终后果：RAG 召回断裂、缺上下文、错乱的垃圾碎片；模型拿着错误碎片，自信输出幻觉答案，并且无法核验来源。
视频一句话结论（开篇）：直接粗暴转纯文本，是整个链路最开始就埋下的错误，后面召回、重排、生成再怎么做都救不回来。
二、生产级完整四层流水线（视频主体，逐层拆解、附带例子）
第一层：多模态解析层（文档类型识别 + 分流解析）
核心原则：拿到 PDF 第一步不是抽文字，先识别 PDF 类型，不同类型走不同解析链路。
视频划分 3 类 PDF，每一类对应方案、例子：
原生文本 PDF（电子导出 PDF）
例子：Word 导出说明书、普通电子文档、不带图片的报告
处理：直接抽取文本、文字坐标、阅读顺序；工具举例：PyMuPDF、pdfplumber
扫描版 PDF（图像型 PDF）
例子：纸质合同扫描件、纸质单据拍照、老档案影印 PDF
处理：OCR 识别；
图文混排复杂 PDF
例子：上市公司财报、技术白皮书、论文、带架构图 / 流程图的方案
处理：不能只抽文字，调用视觉多模态大模型做版面理解，识别图、表、示意图内容；
视频对标案例：Anthropic Claude PDF Support，Claude 对 PDF 的能力不是只读文字，原生支持理解页面内表格、图表、插图。
本层视频结论：解析分流是整条链路的第一道关口，分流判断错，后续所有步骤全部失效。
第二层：文档结构还原层
核心原则：不要把 PDF 抹平成一整坨无差别字符串，要还原文档骨架，保留位置元信息；区分有效内容和噪声。
需要保留的结构信息（视频逐条列出）
标题层级（一级标题、二级标题……）
章节、段落边界
页码、页面内坐标
表格、图注、脚注
图片 / 图表编号、说明文字
需要标记 / 过滤的噪声内容
页眉、页脚、水印、重复页码文字
视频配套业务例子
合同 PDF：解析后，每一条条款要标记：属于第几章、第几条、在第几页；
财报 PDF：一个营收数字，必须标记：来自哪一张表格、哪一行、哪一列、对应哪个年份指标。
本层视频结论
如果丢掉结构与位置元数据：Agent 回答看起来有理有据，但无法溯源；在合规、审计、金融、法务场景，这是致命缺陷 —— 你无法证明答案来自原文哪里。
第三层：语义切片 + 上下文增强 + 双索引构建
核心：摒弃固定字数机械切分（固定 512token 一刀切这种做法），改为按文档语义结构切片。
视频给出的切片规则（逐条）
同一个标题下关联的连续段落，打包成一个 Chunk；
表格单独作为独立 Chunk，不打散；长跨页表格识别表头、续表，合并为一张结构化表格，转为 Markdown / 结构化文本；
图片、流程图：不把图片塞进向量库，由多模态模型生成图表摘要，【摘要 + 原图注】绑定成独立 Chunk；
相邻 Chunk 保留合理 overlap，防止语义边界切断；
每一个 Chunk 强制绑定全套元数据 Metadata：文档 ID、文档版本、页码、章节标题、表格编号、图片描述、页面坐标。
上下文增强（视频明确引用：Anthropic Contextual Retrieval 方案）
操作：入库阶段，调用 LLM，给每一个 Chunk 额外生成一小段全局背景描述，描述这个片段在整篇文档里的定位。
视频举例：
原文 Chunk 是一段 “汇率波动对公司营收影响” 的文字；
自动生成补充上下文：本段来自财报第三章风险因素章节，阐述外汇汇率波动给海外业务收入带来的不确定性。
原文片段 + 这段补充描述一起 Embedding 入库。
解决痛点：单独召回一小块片段，脱离全文背景，模型 “只见树木不见森林”。
索引构建策略：混合索引（向量索引 + 关键词索引）
向量索引：负责语义模糊检索（用户问同义转述问题）
关键词索引：负责精确词条、条款编号、指标名称检索（法务查条款号、财报查固定指标）
视频结论：单向量索引在企业文档场景召回稳定性不足，混合检索是生产标配。
第四层：Agent 工具链调用（Agent-RAG 核心，区别于普通 RAG）
核心原则：Agent 不要一次性把整份 PDF 全部塞进 Prompt 上下文；PDF 阅读能力封装成独立工具，由 Agent 自主规划、判断、按需调用工具。
视频明确定义 5 个标准工具：
search_pdf：向量混合检索，召回相关语义切片
read_page：读取指定页码完整页面内容
extract_table：抽取并结构化解析指定表格
analyze_chart：调用多模态模型解析图表、流程图
quote_source：输出原文引用片段 + 来源元信息
Agent 三种调用分支（视频分场景举例）
简单事实类问题
例子：这份合同的生效日期？财报 2024 年营收是多少？
Agent 决策：直接调用search_pdf向量召回，拿到片段直接生成答案。
多章节对比、跨位置综合问题
例子：对比这份招股书里主营业务风险和行业竞争风险的差异；
Agent 决策：第一次检索发现证据分散、信息不足，自主规划阅读顺序，多次调用检索工具，读取多个章节内容，汇总信息再回答。
涉及表格、图表的问题
例子：解释这张利润表里面费用变动原因；解读架构图的数据流；
Agent 决策：不依赖文本检索，主动调用extract_table / analyze_chart视觉工具。
视频核心区分结论：
普通 RAG：检索流程是固定写死的，用户提问就走一次检索；
Agentic RAG：Agent 拥有循环判断：拿到证据 → 判断证据够不够 → 不够就重新改写 query、换工具、继续读，直到证据充足，再生成答案。
三、两大生产级必加模块（视频单独拿出来，面试加分项）
模块 A：可追溯引用 Citation（溯源）
要求：模型输出答案的时候，附带来源：页码、章节、原文片段。
视频给出价值：
抑制大模型幻觉；
支持人工核验，审计、法务、金融场景合规要求；
用户可以直接点开定位到原文对应位置核对。
视频补充：只输出答案不给引用，在企业文档 RAG 里属于不可上线版本。
模块 B：评测闭环（重点，很多面试者漏掉）
视频强调：评测不能只看【最终答案是否正确】，要做多维度全链路评测，逐条评测维度：
检索召回的 Chunk，有没有命中真正关键信息（召回质量）
输出的引用页码、章节定位是否准确
表格解析结果，行列数值、关系是否正确
图表摘要理解是否符合原图含义
是否出现文字丢失、OCR 识别错误、上下文断裂
视频结论：PDF RAG 上线不是一次性开发完成，需要持续评测集迭代，持续发现解析 / 切片缺陷，迭代优化解析器、切分规则。
四、视频末尾：面试标准口述完整版总结（视频原话模板）
处理 PDF 不能简单转文本切片入库。先识别 PDF 类型做对应多模态解析；接着还原文档章节、页码、表格等文档结构；之后做语义切片，给 Chunk 补充上下文，构建向量 + 关键词混合索引；再由 Agent 调用 PDF 工具按需检索、读页、抽表、解析图表；最后输出附带页码章节的可追溯引用，并建立多维度评测机制，保障 PDF-RAG 生产可用。
