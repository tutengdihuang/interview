抖音视频内容详细总结
视频是一道 Agent / 大模型工程化面试题讲解：面试官问：大模型工具调用的参数 Schema 为什么不能随便修改？，指出只回答 “会报错” 这个答案太过浅显，从工程契约、线上坑点、最佳实践、面试答题话术完整讲解 Function‑Calling 工具 Schema 管理。
一、核心观点：Schema 是一份多方契约
上线后的工具参数 Schema，不只是给开发看的参数定义，是大模型、工具服务、日志系统、评测回放系统之间的契约。
提示词里写了字段；评测数据集存储旧参数字段；历史日志留存旧格式；老的会话、老版本逻辑还在按旧 Schema 调用工具。
开发阶段随便改名、修改类型没问题；一旦上线，随意改动 Schema，模型不会自动感知变更，工具层也无法兼容，就会出现部分任务成功、部分任务失败的不稳定现象，不是简单的直接报错。
举例：参数今天叫user_id，明天改成1_id；status 今天是数字类型，明天改成字符串，线上就会出问题。
二、把 Schema 当做 API 合同管理，四条实操准则
1. 字段命名保持稳定
不要随意变更字段名，比如一会叫query，一会叫keyword。大模型对参数字段的理解，高度依赖字段名、字段描述、历史上下文，频繁改名极易让模型生成错误参数。
2. 参数字义尽量明确，拒绝模糊定义
不要笼统写time，拆成start_time、end_time；
amount金额参数，写明币种、单位、是否含税。
参数越模糊，大模型越容易 “猜参数”，后续系统很难兜底处理错误输出。
3. Schema 变更做版本化管理
区分风险等级：
✅新增字段：风险低；
❌删除字段、修改字段类型、修改枚举值：属于破坏性变更。
稳妥方案：新旧版本并存，例如search_order_v1保留给老任务，search_order_v2做功能升级；观察日志确认没有业务再依赖旧版本，再下线旧工具，保障历史任务可以正常跑完。
4. 工具层强制参数校验 + 模型可读错误反馈
不能指望大模型每次严格遵守 Schema 生成参数。工具后端必须校验：必填项、参数类型、取值范围、权限。
报错不能只返回 500 等服务端错误，需要输出大模型看得懂的提示，例如：“缺少 start_time，请向用户补充时间范围”，让模型知道要向用户收集信息，而任务直接失败。
三、线上极易踩的隐蔽大坑：Schema 与自然语言描述不一致
代码 Schema 和描述文本互相矛盾：
代码标记字段optional选填，但描述文字写为必填；
枚举值代码是pending、done，但提示词引导模型输出中文 “待处理”、“已完成”。
代码本身没有报错，但模型会稳定输出错误参数，这类问题排查难度极高。
配套要求：只要修改 Schema，必须同步更新工具描述、系统提示词、测试用例、评测样本，全部联动修改，不能只改代码里的 JSON 结构。
四、面试标准答题模板
工具调用 Schema 不能随意修改，因为它是大模型与整套业务系统之间的稳定契约。我会把 Schema 按照 API 合同来治理：保证字段语义清晰，类型、枚举严格明确；Schema 变更执行版本化策略；工具层做参数校验，返回模型可理解的错误信息；同时同步更新提示词、评测样本、回放用例，保证新版本不会破坏历史任务。

完整逐条整理（原视频全部口播要点、例子、结论，无省略）
视频原题：面试官问：大模型工具调用的参数 Schema 为什么不能随便修改？
开篇先点破：很多人的回答只停留在 “改了会报错”，这个答案很浅，面试官要的是工程层面的理解。
0. 核心总论点（视频第一句核心结论）
Schema 不是单纯给程序解析用的 JSON 结构，它是多方之间的稳定契约，签约方包含：大模型、后端工具服务、日志存储系统、评测回放系统、存量会话任务。
开发阶段，Schema 随便改没问题；
一旦上线，Schema 变更的影响不是一次性报错，而是会出现间歇性、部分成功、部分失败的不稳定现象（静默失败），排查难度极高。
一、契约包含的所有依赖链路（视频逐条列出的依赖项）
只要 Schema 上线固化，下面这些地方全部绑定这份 Schema：
发给大模型的系统提示词、工具描述文本；
评测数据集、测试样本、回归用例（数据集里存的是旧版本字段）；
历史调用日志，日志持久化存储的参数结构是旧格式；
还没跑完的长会话、历史会话，模型记忆里记住的是旧字段；
后端工具入参解析逻辑、参数校验逻辑。
配套例子：
今天参数叫user_id，上线后直接改成uid；或者 status 原来是数字类型，直接改成字符串。
模型不会自动感知到这个变更，它会继续按照它学到的、提示词里写的旧 Schema 生成参数；后端已经改成新字段，两边对不上。
现象：一部分新会话刚好蒙对能跑，老会话、历史回放、评测样本批量异常，不是全量报错。
二、四条工程实操准则（视频分 4 条逐条讲解，每条带例子）
准则 1：字段命名一旦上线，保持稳定，不要随意改名
问题：频繁修改字段名称，大模型对字段的理解高度依赖字段名 + 描述 + 历史上下文，改名会直接误导模型生成错误参数。
例子：同一个查询参数，一会叫query，一会改成keyword。模型会混乱，时而填对时而填错。
结论：字段名是契约标识，优先不改名；非要改，走版本化，不能原地覆盖。
准则 2：参数字义要明确，拒绝模糊定义，不能让模型猜业务含义
反面例子 1：只写一个字段叫time，不区分开始、结束。模型不知道是起始时间还是截止时间。正确做法：拆成start_time、end_time。
反面例子 2：金额字段只写amount，不说明币种、单位（元 / 分）、是否含税。模型很容易单位搞错，传成分，后端按元解析，业务结果完全错误，但 JSON 格式本身合法，不会报 JSON 解析错误。
结论：Schema 里的 description，必须写清楚业务语义、单位、取值范围、格式要求；不要把业务规则藏在开发脑子里，必须写进契约里。
准则 3：Schema 变更必须做版本化管理，区分变更风险等级（视频重点）
风险分级（视频明确划分）
✅ 低风险变更：新增可选字段
旧逻辑、旧模型不传这个字段，后端给默认值，老任务不受影响。
❌ 破坏性高危变更（严禁原地直接改）：
删除原有字段
修改字段类型（数字 ↔ 字符串、布尔 ↔ 数组）
修改枚举值集合、枚举含义变更
把原来选填字段改成必填字段
配套方案例子：
原来查询订单工具叫search_order_v1，现在要改 Schema，新增必填筛选字段，不直接覆盖 v1，新建search_order_v2。
老会话、老评测、老日志继续走search_order_v1；
新业务、新提示词使用search_order_v2；
持续观察日志，确认线上已经没有任何业务、会话、评测再调用 v1 之后，再下线旧版本。
视频结论：Schema 不能原地热更覆盖，工具名带上版本号，新旧并行，平滑淘汰。保证历史任务可以完整跑完、可以回放复现。
准则 4：工具后端层，必须强制参数校验，并且返回大模型可读的结构化错误反馈
前提结论：绝对不能指望大模型每次都严格遵守 Schema 生成参数，模型天生会幻觉、漏填、填错枚举。校验不能放在模型侧，后端必须兜底。
校验内容清单（视频列出）：必填项是否存在、参数类型是否匹配、取值范围、枚举白名单、权限校验、参数互斥 / 依赖关系。
反面错误做法：后端直接返回 500、一段开发者看的堆栈报错、模糊文本 “参数错误”。模型看不懂这个报错，不知道哪里错，直接任务终止，不会重试补参数。
正面例子（视频原文示范的报错文案）：
“缺少 start_time，请向用户补充查询的开始时间范围。”
“status 仅允许传入 pending /done，您传入了‘待处理’，不符合枚举要求。”
结论：报错本身也是契约的一部分，错误信息要面向大模型设计，告诉模型：哪个字段错了、期望是什么、该怎么向用户追问收集信息，给模型修复参数、重试调用的机会。
三、线上最隐蔽、最难排查的大坑：Schema 代码 和 工具自然语言描述不一致（视频单独重点一段）
这是最容易踩、最难复现的坑：JSON Schema 代码和写在 description、system prompt 里面的说明互相矛盾。
两个典型例子：
代码里标记字段optional: true（选填），但是描述文字写的是 “该字段必填”；
代码枚举定义是英文pending、done，但是提示词描述里写让模型输出中文 “待处理”、“已完成”。
现象：JSON Schema 语法校验不会报错，代码本身没有异常，但是模型会稳定、持续输出错误参数，属于稳定的静默错误。
排查难点：日志看 JSON 结构是合法的，很难第一时间定位是 “描述和 Schema 代码不一致”。
这条坑对应的硬性配套要求（视频原话）
只要修改 Schema 里任意一处（字段、类型、枚举、是否必填），下面全部内容必须联动同步更新，缺一不可：
JSON Schema 定义本身
工具 description 描述文本
系统提示词里对这个工具的说明、示例
所有相关测试用例、评测数据集
回放脚本
结论：Schema 是一组整体，不是单独一段 JSON，改一处，全链路文档和样本同步更新，否则描述和代码分家。
四、视频的面试标准答题模板（逐字原文）
工具调用 Schema 不能随意修改，因为它是大模型与整套业务系统之间的稳定契约。我会把 Schema 按照 API 合同来治理：保证字段语义清晰，类型、枚举严格明确；Schema 变更执行版本化策略；工具层做参数校验，返回模型可理解的错误信息；同时同步更新提示词、评测样本、回放用例，保证新版本不会破坏历史任务。
五、视频收尾的底层本质结论（结尾升华）
很多新手以为 Function Calling 的难点，是让模型成功调用一次工具；
但工程上真正的难点，是长期稳定、可迭代升级、可回放、可回归地持续调用工具。
Schema 治理就是为了解决长期迭代稳定性，而不是单次跑通。
