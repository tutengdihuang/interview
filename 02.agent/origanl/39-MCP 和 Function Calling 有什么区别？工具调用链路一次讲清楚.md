视频定位：面向大模型 AI Agent 面试讲解，核心澄清 MCP 与 Function Calling 的层级、分工、误区、生产链路，提醒面试答题要点。
核心总观点
MCP 与 Function Calling不是替代、二选一关系，而是上下游协作关系：
Function Calling（函数调用）属于 LLM 大模型层能力：负责大模型选择工具、生成调用参数。
MCP 属于应用层协议：负责工具的发现、接入、标准化暴露。
1、两者分别工作在哪一层？
Function Calling（LLM 模型侧）
调用大模型 API 时，把工具定义以 JSON Schema 传给模型；大模型输出结构化结果，决定调用哪个工具、填什么参数。解决大模型怎么做工具决策、输出调用参数的问题。
MCP（应用 / 框架侧协议）
规定工具提供方如何把工具暴露给 Agent 框架。解决工具如何被框架发现、连接、标准化调用的问题。
通俗类比：Function Calling 是大模型的 “手”，负责发出操作指令；MCP 是工具的 “标准化说明书”，说明书不能替代手。
2、常见误区：为什么很多人误以为 MCP 会取代 Function Calling？
媒体宣传 MCP 实现工具接入标准化，造成 “以后不用 Function Calling” 的错觉。
实际情况：
MCP 只标准化工具描述、工具发现；MCP Server 输出工具元信息后，还需要框架把它转换成 Function Calling 需要的 JSON Schema，再传给大模型。MCP 自动生成工具定义，但不能替代模型侧 Function Calling 能力。
3、MCP 到底解决了什么工程痛点
没有 MCP 的旧模式
对接每一个工具，开发者需要手写 JSON Schema 工具定义、手动处理输入输出格式、手动管理工具生命周期。有 N 个工具，就要写 N 套定义和适配代码，定制开发工作量巨大。
MCP 的解决方案
工具提供方实现 MCP Server，按 MCP 协议对外暴露工具；支持 MCP 的 Agent 框架就可以自动发现、自动适配、自动调用工具，把工具接入从定制开发变成即插即用。
⚠️ 视频提醒坑点：
MCP 本身不解决权限、安全管控。例如一个 MCP Server 暴露 10 个工具，Agent 是否可以全部调用、谁有权限调用、责任归属，这些需要上层框架额外实现。
4、生产环境完整三层协作链路（面试重点）
完整工具调用分为三层，依次流转：
工具层：各个业务工具实现 MCP Server，按照 MCP 协议对外暴露工具描述。
Agent 框架层
① Agent 框架通过 MCP 协议，自动拉取、发现全部可用工具；
② 将 MCP 格式的工具描述，转换为大模型能识别的 Function‑Calling 的 Schema 格式。
LLM 大模型层
① 调用大模型 API，传入转换完成的工具定义；
② 大模型依靠 Function Calling 能力，选择工具并生成调用参数；
③ Agent 框架拿到模型输出的调用请求，再次通过 MCP 协议，把请求下发给对应 MCP Server 执行真实工具逻辑。
一句话记忆：MCP 管工具发现与连接；Function Calling 管大模型工具决策，两者配合完成完整工具调用。
5、面试官真正考察的 3 个能力点
分层认知：分清层级，MCP 在应用层做工具发现连接；Function Calling 在 LLM 层做工具决策和参数生成，二者不属于同一层面。
关系理解：不是互相替代，上下游关系；MCP 输出工具元数据，自动产出 Function Calling 所需要的工具 Schema。
工程落地认知：掌握三层架构流转，同时意识到 MCP 协议本身不带权限、鉴权，安全管控依赖上层框架实现。

【0. 开篇引入，面试原题】
面试官经典提问：Agent 开发里，到底是用 MCP 还是 Function Calling？
❌ 最常见错误回答：二选一、MCP 替代 Function Calling。
✅ 视频开篇总论点：二者不是替代、不是同级二选一，是上下游协作关系，分工在链路不同位置，缺一不可。
视频核心目标：讲清各自在哪一层、各自负责什么、中间怎么转换、整条调用链路怎么走、落地坑点、面试官到底想考察什么。
【1. 第一层：Function Calling（函数调用）完整定义、职责、例子】
定位：LLM 大模型层原生能力（模型能力）
工作方式：调用大模型 API 时，把工具描述（JSON Schema）传给模型；大模型经过推理，输出一段结构化 JSON，里面写明：调用哪个工具、每个参数填什么值。
只解决单一问题：大模型怎么判断要不要调用工具、选哪一个工具、生成正确调用参数。
视频举例：
用户提问：查询今天北京天气。
预先给模型传入工具 schema：get_weather(city: string)
模型识别意图，输出 Function Calling 结构化结果：工具名get_weather，参数city="北京"
注意：模型本身不会执行这个函数，只输出调用意图和参数；执行动作交给外面的宿主 / Agent 框架。
边界（视频明确强调）：Function Calling不关心工具在哪、怎么连接、服务怎么启动、怎么通信；它只负责输出调用请求。
【2. 第二层：MCP（Model Context Protocol，模型上下文协议）完整定义、职责、类比例子】
定位：应用层通信协议（不是模型能力，是接入标准）
工作方式：规定一套标准，让工具 / 数据源的提供方，把自己包装成 MCP Server；任何支持 MCP 的 Agent 客户端 / 框架，都可以按这套协议去连接、拉取工具信息、发起调用、拿到返回结果。
只解决单一问题：工具如何被 Agent 框架自动发现、连接、标准化通信调用。
视频类比（视频原话例子）：
Function Calling 是人的手（手知道要去抓螺丝刀、抓哪个、抓的力度参数）；
MCP 是统一的 USB‑C 接口标准。
USB-C 不负责 “手决定拿什么工具”；USB-C 只规定插头、通信方式，不同设备都能插上即用。
MCP 同理：它是工具的统一插口标准，不是工具本身，也不是模型决策能力。
MCP Server 向外暴露三类资源（视频提到）：
Tools：可执行操作（查询订单、查天气、读写文件）
Resources：只读上下文数据（文件内容、数据库单条记录）
Prompts：预设好的提示模板（固定审查模板、固定报告模板）
【3. 重点误区拆解：为什么网上很多人误以为 MCP 会干掉 Function Calling？（视频单独一段）】
误区来源：大量宣传文案只强调 MCP“工具即插即用、不用手写工具定义”，很容易让人理解成：有 MCP 之后，就不需要 Function Calling 了。
视频纠正结论：
MCP 只是自动产出工具元信息（工具描述、入参 schema）；
MCP 输出的这套元信息，不能直接喂给大模型。
必须经过 Agent 框架做一层转换：把 MCP 协议里的工具描述，翻译成 LLM 能识别的 Function Calling JSON Schema 格式，再传给模型。
一句话视频原话：MCP 自动帮你生成 FC 需要的工具定义，但 MCP 本身不能替代模型的 Function Calling 决策能力。
【4. 没有 MCP 之前：原生 Function Calling 方案，痛点详解（视频完整例子）】
旧模式：每新增一个外部工具，开发者手动写一套 Function Calling 的 JSON Schema，硬编码到代码 / 系统提示词里。
视频举业务例子：企业 Agent 要对接 CRM 系统、物流查询、订单查询、内部知识库 4 套系统。
旧做法：4 个工具，手写 4 套独立 schema；如果换一个大模型（不同厂商 FC 格式有差异），Schema 经常要改；
扩展痛点公式（视频重点）：N 个 Agent 应用 × M 个外部工具 = N×M 份适配代码。工具一多，适配、维护、测试成本爆炸；
额外痛点：工具是静态注册，新增工具要改代码、改提示词、重新部署，不能热加载。
【5. MCP 带来的工程收益，视频原话结论】
引入 MCP 之后：每个外部能力只实现一份 MCP Server；所有支持 MCP 的 Agent 框架，统一按协议拉取。
复杂度变化：N+M，而不是 N×M；
能力：工具动态发现、热插拔；新增工具只需要启动一个 MCP Server，Agent 客户端刷新工具列表即可，不需要修改大模型侧、不需要重写 FC Schema；
好处：工具跨 Agent、跨 IDE、跨不同大模型客户端复用，生态互通。
⚠️ 视频明确划清边界：收益只在【工具接入、发现、复用】这一层，模型选工具、出参数这一步，依然靠 Function Calling。
【6. 整条完整三层流转链路（视频核心大图对应的分步流程，面试必背，顺序不能乱）】
链路角色：【工具层 MCP Server】→【Agent 框架 / Host（MCP Client）】→【LLM 大模型】
完整步骤，视频逐步骤讲解：
工具层：业务能力包装成 MCP Server（例如天气服务 MCP Server、订单 MCP Server），按照 MCP 协议对外暴露工具列表、参数说明、资源、模板；
Agent 框架（Host/MCP Client）主动和 MCP Server 建立连接，动态拉取全部可用工具的元数据；
Agent 框架做转换：把 MCP 的工具描述，翻译成当前 LLM 兼容的 Function Calling JSON Schema；
Agent 把转换好的 Schema + 用户提问，一起发给大模型；
LLM 依靠原生 Function Calling 能力，推理判断：是否要调用工具、调用哪一个、填充入参，输出结构化 FC 调用请求；
Agent 框架拿到模型返回的 FC 调用请求；
Agent 框架再通过 MCP 协议，把调用请求转发给对应的 MCP Server 执行真实业务逻辑；
MCP Server 执行完成，把结果通过 MCP 协议回传给 Agent；
Agent 把工具返回结果，拼接进上下文，再次发给 LLM；
LLM 结合工具返回数据，生成自然语言答案，返回给用户。
视频一句话总结链路记忆口诀：MCP 负责拉工具、传调用；FC 负责模型做决策、出调用意图。
【7. 视频重点踩坑提醒（非常容易答错的点）】
坑点：MCP 协议本身不带权限、鉴权、访问控制、审计、参数校验。
视频举例说明：
一个 MCP Server 暴露了 10 个工具（包含查客户敏感手机号、删除订单、查询公开库存）；
MCP 协议本身不会区分：这个 Agent 能不能调用删除订单工具、用户有没有权限查手机号。
✅ 责任归属：权限、黑白名单、参数校验、调用日志、风险拦截，全部要在上层 Agent Host 框架里面额外实现，MCP 只负责通信和工具暴露，不做安全管控。
很多面试者错误回答：MCP 自带权限管控，视频明确指出这个是错误。
【8. 视频：面试官真正考察你的 3 个能力点（面试评分标准）】
不是背名词，面试官要确认你懂工程落地，三点依次：
分层认知：分清层级边界。MCP 在应用层，负责工具发现、连接；Function Calling 在 LLM 模型层，负责工具决策和参数生成；二者不在同一层；
关系认知：上下游配合，不是替代；MCP 产出元数据，框架转成 FC Schema 喂给模型；模型输出 FC 调用意图之后，框架再走 MCP 去执行；
落地认知：知道 MCP 的短板，清楚安全、权限、校验不在 MCP 协议内，需要上层 Host 补齐；能说出完整调用链路。
【9. 适用场景对比（视频隐含结论，配合例子）】
适合只用原生 Function Calling：工具数量很少、固定不变、单应用自用，不想引入 MCP 额外组件。比如个人小助手，只调用 1~2 个工具（查日历）；简单、轻量化，不需要生态复用。
适合引入 MCP：企业级 Agent、多工具、多数据源、多个 Agent 客户端共用一套工具池、需要工具动态插拔、希望工具跨平台复用（IDE、不同 Agent、不同模型都能接同一套 MCP Server）。
【10. 视频最终收尾总结（原话浓缩）】
Function Calling：解决模型怎么表达 “我想要调用某个工具，参数是 XX”；
MCP：解决工具从哪里来、怎么被发现、怎么跨客户端标准化调用；
二者共存、上下游配合；MCP 是接入层标准，Function Calling 是模型侧工具决策能力。
没有 MCP，FC 要手写大量 Schema，工具很难复用；没有 FC，MCP 拿到一堆工具列表，大模型不知道什么时候、调用哪一个。
