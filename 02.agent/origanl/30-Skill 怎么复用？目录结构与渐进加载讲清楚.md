视频详细总结
这个抖音视频主题是AI Agent 开发中 Skill（技能）的复用、技能包目录结构、渐进加载机制，作者小哲，用旅游攻略作为案例讲解 Agent 技能工程实践。
1、提出问题：为什么需要 Skill
日常使用 Agent 做任务，比如生成上海一日旅游攻略，每次都要重复输入偏好、预算、输出格式，非常麻烦。
案例需求：2 人上海一日游，预算 500 元，输出文字攻略、费用核算、路线图。Agent 要完成查资料、规划行程、校验预算、产出结果整套流程。
Skill（技能）就是用来解决重复配置的问题：不是复制某一次对话记录，而是把任务里稳定不变、可以复用的逻辑打包成技能包。
案例中：城市可以换成北京，但是游玩偏好、预算校验规则、输出格式是固定可复用的，这部分就封装进 Skill 里，城市作为可变输入。
2、Skill 技能包的目录与文件结构
一个 Skill 技能包由说明文档、可选的资料目录、脚本目录组成，不是所有目录都必须，按需添加。
SKILL.md（核心入口文件）
头部：技能名称 + 描述，用于 Agent 识别、匹配什么时候该调用这个技能；
正文：写清楚执行步骤、约束条件、输出标准，告诉 Agent 具体怎么做这件事。
reference 参考资料文件夹（可选）
存放业务文档、知识库、样例模板。案例里存放路线图样例。
scripts 脚本文件夹（可选）
存放可重复运行的代码脚本。案例里放预算核算程序，专门处理计算类逻辑。
分工模式：
脚本：处理确定性计算；
大模型：负责理解需求、组织内容；
工具系统：负责实际执行读写、运行脚本。
仅仅建好文件夹和文件不等于技能可用，需要运行时把资源和 Agent 流程关联起来。
3、核心概念：渐进式加载
目的：不要一次性把所有技能全部塞进上下文，减少上下文冗余消耗。运行流程：
只向模型提供精简的技能清单，只包含技能名、简短描述；
Agent 判断当前任务匹配某一个 Skill 之后，才去读取完整的 SKILL.md；
按需加载资源：需要校验预算才运行 scripts 脚本，需要样例才读取 reference 里的资料，不用的内容不加载进上下文。
重要要点：加载技能、运行脚本本身都属于 Agent 工作循环。模型发出读取 / 执行请求，主程序去执行，执行结果返回给大模型上下文。Skill 只是提供方法和素材，本身不能独立运行；如果缺少权限、依赖环境，文档写得再好也会失败。
4、Skill 的开发和验证流程
不能只是创建文件就完事，完整开发步骤：
先把真实业务任务完整跑通；
从中提炼出可以复用的步骤、约束，整理打包为 Skill 技能包；
做验证测试：新开对话，输入同类型但是参数不同的任务（比如把上海换成北京），校验三点：①技能能否被正确加载；②脚本是否正常调用；③输出是否遵守约定格式。
只有文件生成成功不算完成，必须看实际运行输出结果。
5、渐进加载的局限与评判标准
好处：减少无关内容占用上下文；
局限：资源读取量、执行工作量依然会消耗 token；不会自动把文档直接变成专家能力，脚本和参考资料本身依然需要人工检查正确性。
作者评判一个好 Skill 的标准：稳定逻辑可以复用，信息在真正需要的时候才被加载，用实际运行结果证明技能有效。

完整示例任务
原始任务：两个人去上海玩一天，总预算五百元，希望输出三样东西：①文字攻略；②核算后的费用；③一张路线图。
Agent 完整执行链路：查询信息 → 规划行程 → 检查预算 → 生成最终结果。
痛点：如果下次做同类任务，城市换成北京，但游玩偏好、费用检查逻辑、输出格式要求不变，每次对话要重复输入全部条件，非常繁琐。

例子区分可变 / 不变项
可变输入：目的地（上海 / 北京），每次任务会变化；
可复用、存入 Skill：游玩偏好、预算校验方法、输出标准格式。
二、Skill 技能包目录结构、每个文件 / 文件夹职责（完整）
核心前提：不是所有文件夹必须存在，按需创建。SKILL.md 是必备入口文件，reference、scripts 为可选目录。
1. SKILL.md（技能入口，必选）
内部分为两大部分，分工明确：
1）头部元信息：技能名称 + 技能描述
名称：用于 Agent 识别该技能；
描述：用于 Agent 做任务匹配，判断当前任务要不要启用这个 Skill。
2）正文内容：写清楚执行步骤、约束条件、输出标准，告诉 Agent 具体怎么做任务。
三者分工原文结论：名称帮助识别，描述帮助匹配，正文负责把怎么做讲清楚，几部分各有自己的职责。
2. reference 目录（参考资料，可选）
存放业务说明文档、知识库材料、样例模板。
旅游案例对应：存放路线图样例文件。
3. scripts 目录（可执行脚本，可选）
存放可以重复运行的代码程序，专门处理确定性计算逻辑。
旅游案例对应：存放预算核算程序脚本。
4. 文件之间协作规则（重点细节）
关键要求：SKILL.md 必须写明指令，告诉 Agent：什么时候读取哪一份 reference 参考资料；什么时候调用执行 scripts 下的哪一个脚本。
旅游案例完整分工演示：
游玩偏好、输出格式标准 → 写进 SKILL.md 说明文档；
预算核算校验规则 → 交给 scripts 目录下的脚本代码；
路线图输出样式参考 → 放在 reference 目录的样例文件。
5. 三类能力的分工（模型、脚本、工具）
scripts 脚本：负责可以明确计算的确定性工作；
大模型：负责需求理解、内容组织；
Agent 工具系统：负责真正执行读文件、运行脚本等动作。
重要提醒结论：仅仅把文件建好放进文件夹，不等于 Skill 就可以运行；运行的时候需要按照 SKILL.md 的指令，把各类资源和 Agent 运行流程关联接通。缺少权限、缺少运行依赖，哪怕文档写得再好，Skill 也跑不通。
三、核心概念：渐进式加载（全部运行流程，完整细节）
核心目的：不要一次性把全部 Skill 所有资料、脚本、说明全部塞进上下文，避免无关内容占用上下文窗口。
完整运行步骤（严格原文顺序）
第一步：仅加载精简技能清单
会话启动，只把所有 Skill 的「名称 + 简短描述」给到大模型。只有摘要信息，完整文档、脚本、参考资料此时不加载进上下文。
第二步：任务匹配触发加载完整 Skill 文档
模型分析用户当前任务，判断匹配某个 Skill；通过文件读取 / 加载工具，读取完整 SKILL.md 正文，把完整任务步骤、约束加载进上下文。
第三步：第三层按需加载附属资源
需要做预算检查的时候，才调用 scripts 里面的预算核算脚本；
需要参照路线图样式的时候，才去读取 reference 目录的样例资料；
当前任务用不到的文件，完全不加载。
以上整套流程，就叫渐进式加载。
非常重要的底层机制结论（原文重点）
「读取 Skill 文件、执行脚本，本身都属于 Agent 工作循环之内」：
是模型先发出读取文件 / 执行脚本的请求；
由主程序实际完成读文件、跑脚本操作；
将执行结果返回给大模型的上下文。
Skill 只是提供方法与资源包，Skill 本身不能脱离 Agent 工具系统独立行动。没有权限、依赖缺失会直接执行失败。
四、Skill 完整开发、验证流程（实操步骤，原文完整）
重点警示：仅仅看到文件夹、文件创建成功，不能算作 Skill 验证完成。
完整开发测试步骤：
第一步：先用真实业务任务完整跑通一遍（案例就是两个人上海一日游）；
第二步：从成功运行的任务中，提炼可以复用的步骤、约束规则，整理打包成 Skill 技能包；
第三步：新建干净对话，输入同类型、但参数不一样的任务（例子：目的地换成北京），执行三项校验：
① 该 Skill 能不能被 Agent 正确识别、加载；
② 配套 scripts 脚本有没有被正确调用；
③ Agent 输出结果是否遵守 SKILL.md 约定好的输出标准。
最终标准：必须看实际运行输出结果，验证 Skill 是否真正生效。
五、渐进加载的收益、局限性、作者评判 Skill 好坏标准
1、收益
渐进加载可以降低无关资料对上下文 token 的占用。
2、明确局限（不要神化渐进加载）
实际 token 消耗，依旧取决于：真正读取了多少文件内容、执行多少工作；不是开启渐进加载就完全没有开销。
渐进加载不会自动把文档变成专家能力：reference 参考资料、scripts 脚本本身内容依然需要人工检查正确性，如果资料 / 脚本本身有 bug，加载出来依旧会出错。
3、作者给出 Skill 合格的评判标准（视频最终结论）
能够把稳定的业务方法实现复用；
信息只有在真正任务需要的时候，才被加载进入上下文；
以实际运行结果，验证这个 Skill 确实有效。
