视频详细内容总结
该视频是一道 RAG 大模型开发面试题讲解，核心问题：合同写 “不得退款”，为什么 RAG 经常错误理解成支持退款。
一、错误根源：不要简单归罪 Embedding 模型
很多面试者会回答 “换更好的 Embedding 向量模型”，但这是错误答案。
原因：向量检索高度依赖关键词词频，“不得退款” 与 “客户可申请退款” 都包含 “退款” 这个高权重词，即便语义完全相反，二者在向量空间相似度依然很高。Embedding 很难单靠向量区分带否定词反转含义的句子。
这道面试题本质考察：是否在 RAG 完整链路中做否定语义的显式处理，而不是单纯依赖向量模型能力。
核心解决思路：在文档入库、查询检索链路增加否定词定位、语义翻转标记，让否定条款和肯定条款在向量上可区分；召回之后再加二次校验过滤。
二、三层架构解决方案（完整工程链路）
第一层：入库阶段 —— 否定词锚点检测
在合同文档入库切片时，扫描文本中的中文否定词：不得、禁止、不予、无权、不适用等；
一旦命中否定词，给文本片段打上否定语义标签，同时识别否定词的作用范围；
示例：乙方不得在合同期内单方面终止服务，标记为【否定语义‑权利限制】，否定词 “不得” 作用整句话。
效果：后续查询 “乙方可以终止服务吗”，可以主动压低这条否定片段的检索权重，避免算出高相似度错误召回。
第二层：查询侧 —— 用户意图反推
解析用户查询的期望，例如用户问 “我能退款吗” 带有肯定期望（希望获得允许）；
针对带有肯定期望的查询，把已经打上否定语义标签的片段做检索降权；
技术实现：把否定标签作为负向过滤，也可以给查询向量叠加反向偏移向量，让查询向量在向量空间主动远离否定条款聚集区域。
第三层：召回之后 —— 语义翻转验证（最后一道校验）
即便前面两层过滤，依然要对已经召回回来的文本片段做校验，不能直接喂给大模型生成答案：
使用小模型或者规则引擎做二分类：对召回条款判定输出三种类别：允许 / 禁止 / 无提及；
举例：用户问如何退款，分类器判定召回内容为【禁止】，系统就输出：“根据合同第 X 条，本服务不支持退款”，而不会把禁止条款误解读为支持退款。
面试答题模板：
1）合同入库扫描否定词，打上否定语义标签；
2）查询解析用户意图，正向期望的查询对否定标签做向量负向偏移降权；
3）召回结果使用语义翻转分类器，做允许 / 禁止的最终判定。
三、面试加分点：处理无否定词的隐性禁止场景
有些句子没有 “不、不得” 这类否定词，但实际是限制、阻碍权利，例如：退款需经董事会审批、以XX为前提。
处理方案：维护隐性禁止模式库，用规则匹配这类句式，识别实质限制，不能只依赖显式否定词扫描。
四、踩坑反例：只在 Prompt 里加一句 “请注意否定词”
这属于纸上谈兵，无法稳定解决问题。
原因：大模型预训练语料中，“不得退款”“支持退款” 经常出现在同一文档不同段落；仅靠提示词提醒，模型经常丢失否定条件，依然会理解错误，必须靠检索链路显式处理，不能只交给生成阶段处理。

一、面试原题场景（视频开篇案例）
面试官提问场景：合同文档内容写的是“不得退款”，但 RAG 系统经常召回该片段，并且错误解读成 “支持退款”，问是什么原因。
错误面试回答示范：向量检索只看词频不看语义关系，换个更好的 Embedding 模型就好了。
视频描述：说出这个答案之后，面试官叹气、放下笔，代表这个回答不合格。
1、错误答案背后的真实原因（视频原文结论）
问题根源不是 Embedding 模型性能不够先进。
实例对比句子：
否定句：不得退款
肯定句：客户可申请退款
现象：两个句子共享高权重关键词「退款」；哪怕语义完全相反，在向量空间中距离非常接近（向量相似度很高）。Embedding 很难仅凭向量本身区分前面带不带 “不得” 这种否定修饰。
这道面试题真正考察点：不是考 Embedding 的语义能力；考察候选人是否知道要在 RAG 检索全链路引入否定语义的显式处理机制。
2、视频给出的总纲领结论（一句话核心方案）
在文档入库和查询检索两个环节都加入否定词定位和语义翻转标记，让包含否定结构的条款与肯定条款在向量空间中形成可区分的距离，并在召回后做二次过滤。
二、三层架构完整方案（第一层、第二层、第三层，包含全部例子、技术做法）
第一层：入库时 —— 否定词锚点检测
背景：中文否定句式类型丰富；
视频列举否定词集合：不得、禁止、不予、无权、不适用；
业务意义：上面每一类否定词，都会直接翻转整句话的法律效力；
入库操作流程：
1）对每一份合同文档做否定词扫描；
2）一旦命中否定词，对该段切片文本打上否定语义标签；
3）同时提取识别否定词的作用范围。
视频完整示例：
原始文本：乙方不得在合同期内单方面终止服务
系统标记结果：【否定语义‑权利限制】
否定作用范围：否定词 “不得” 作用覆盖整句话。
处理后效果案例：
用户查询：乙方可以终止服务吗？
如果没有标签：会算出高达 0.92 的高相似度，发生错误召回。
有否定标签之后：可以依靠标签主动压低这条片段的检索权重，避免错误召回。
第二层：查询侧 —— 意图反推
用户查询示例：我能退款吗；句中 “能” 代表用户带有肯定期望（期望得到许可、允许的结果）。
检索前的解析动作：解析用户查询意图，判断用户是在询问：是否有权利、是否允许、是否存在例外。
逻辑规则：如果检测到用户查询是肯定期望，在检索阶段，对所有已经打上否定语义标签的文本片段做降权。
两种具体技术实现方式：
① 将否定标签当做向量检索的负向过滤条件；业务含义等价于告诉检索系统：跟 “禁止退款” 语义接近的内容我不要。
② 在查询向量（query embedding）上叠加反向偏移向量，让查询向量在向量空间主动远离否定条款聚集的区域。

第三层：召回之后 —— 语义翻转验证（最后一道门禁）
前提约束：哪怕第一层、第二层已经过滤掉绝大多数错误否定片段；已经召回回来的片段，仍然必须校验，不能直接丢给大模型生成。
实现工具：使用小模型 OR 规则引擎，逐句对召回片段做判断。
判断任务：识别召回文本到底是支持该行为，还是禁止该行为。
判定输出三分类结果：允许、禁止、无提及。
业务实例：
用户问题：怎么退款？
分类器输出结果：禁止
系统输出回答示例：根据合同第 X 条，本服务不支持退款
避免问题：不会把禁止退款的条款，错误解读成支持退款。

召回结果送入语义翻转分类器，完成允许 / 禁止的最终判定。
三、面试加分追问：隐性禁止问题（没有显式否定词，但实际是限制）
面试官追问场景：否定词以外的隐性禁止该如何处理？
视频示例句子：退款需经董事会审批
现象：句子中没有 “不、不得、禁止” 任何显式否定词，但是业务上实质是设置障碍、属于实质禁止 / 限制。
视频给出另外一类句式模式：以 YY 为前提（实质限制类表达）。
解决方案：维护隐性禁止模式库，依靠规则引擎做模式匹配，匹配 “需经 XX 审批”、“以 YY 为前提” 这类句式，识别无否定词的实质限制。
四、反面案例：错误的偷懒方案（坏路径，视频明确否定）
错误做法：仅仅在 Prompt 提示词里面增加一句话：“请注意否定词”。
视频定性：典型纸上谈兵，无法解决问题。
底层原因：大模型预训练语料中，“不得退款” 和 “可以退款” 经常会出现在同一篇文档的不同段落；仅仅依靠 Prompt 提醒，模型无法稳定识别、保留否定条件，依旧会理解出错。
核心结论：否定语义问题不能只交给生成阶段处理，必须在检索链路显式处理。
