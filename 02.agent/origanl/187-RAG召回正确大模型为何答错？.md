抖音视频《RAG 召回正确大模型为何答错？面试解析》详细总结
视频面向 AI 算法面试，解析高频面试题：RAG 已经召回正确文档，但大模型依旧输出错误答案。核心观点：该题目不是考察向量检索知识，而是考察真实项目落地经验、证据链完整性、答案充分性，不能只盯着召回结果，要完整拆解从文档处理、检索重排、生成回答、兜底校验的全工程链路。视频以会员退费政策业务举例讲解工程落地思路。
一、题目的底层考察点
很多 Demo 环境效果很好，上线就出错，常见问题：字段缺失、文档版本冲突、过期内容、权限变更；
误区：把 “召回命中文档” 等同于 “结论可以成立”；召回到正确片段，不等于模型会基于该证据输出正确答案；
答题思路要拆分：能不能回答 → 怎么回答 → 回答之后校验回收，还要说明数据来源、链路约束、失败兜底方案。
二、三层链路拆解问题根源以及对应的工程做法
第一层：文档结构化解析（输入源头）
问题：很多系统只粗暴按字数切分文档，没有做结构化处理。
错误做法：简单把文本切小块，忽略正文、表格、附件、注释、版本号、例外条款；分不清主规则和例外规则（例如退费主政策和套餐特殊例外）；
带来后果：给到模型的是残缺、混乱的证据片段，后续调重排、调提示词都属于在脏输入上做修补；
工程要求：
将版本、状态、适用边界、例外条款拆解为独立证据块；
留存三样东西：原始证据、处理后的结构化内容、系统选择该证据的理由，方便线上问题复盘定位。
第二层：检索与重排阶段（证据筛选）
问题：虽然召回了正确文档，但证据链断裂，混入大量噪音。
需要加入过滤条件：别名、否定词、时间范围、适用主体做过滤；否则表面命中相关文本，但关键约束条件缺失；
工程上要记录候选结果、过滤原因、最终选择的证据，这样故障时可以区分：到底是召回、规划、执行还是生成环节出错；
评估方式：不能只看最终回答文本像不像，要设置可量化指标：成功率、时延、人工介入量、回滚次数、异常样本占比，同时评估证据链完整度。
第三层：回答生成阶段（门禁、约束与兜底）
问题：没有设置回答门禁，直接放任大模型自由发挥、自行脑补规则。
核心原则：只要现有证据不能覆盖问题的主体、条件、例外情况，就要澄清或者拒答，不能让模型自行编造规则补全信息；不能单纯把大模型当做文本生成器，否则业务线上极易翻车。
上线验证手段：小流量、灰度发布、轨迹回放；重点测试边界异常样本，而不是只测试演示用例。
降级策略：高风险问题直接降级；证据不足向用户追问信息；状态不确定就走人工查证补偿。
三、面试高分回答模板
我会先做文档结构化解析，之后做证据过滤和重排，生成前校验证据是否覆盖全部条件，最后检查输出的每一条答案，都能够回指到对应的原始证据条款。
四、闭环系统和迭代方案
RAG 的胜利不是 “搜到文档”，而是每一句输出结论都可以回溯到对应的证据；证据链是判断、执行、校验、兜底的完整闭环，不是单点 prompt 技巧；
面试官追问延伸回答：补充监控指标、故障复盘机制，将证据链、答案充分性纳入评测用例，而不是仅仅写在提示词中；
这样方案具备可上线、可排障、可持续迭代的工程能力，而不是背诵理论概念。
五、视频的关键提醒
面试不要只描述表象，要补充数据口径、失败路径、回滚边界，否则容易被面试官深度追问难住；
如果只看到输出结果通顺，但没有留存中间证据、状态记录、异常日志，在线上环境这套系统不能判定为可用。

0. 开篇定调（面试题的本质，视频第一句话）
面试原题：RAG 明明召回了正确文档，为什么大模型最后还是答错？
高频错误回答（面试官反感的回答）：上来就说 “换 embedding、调向量检索、提高召回率”。
视频核心结论 1：这道题根本不是考察向量检索能力；考察的是线上 RAG 全链路工程落地能力、证据链治理意识、区分「召回成功」和「答案可信」的能力。
核心定义区分（视频反复强调）
召回命中：只是候选池里面存在相关片段；≠ 证据完整、≠ 模型能读到关键约束、≠ 模型会按原文回答、≠ 答案忠实于证据。
很多 Demo 效果很好，上线就翻车，根源就是 Demo 只测简单正向 case，没有处理边界条件、例外条款、版本冲突、权限、截断、注意力偏差。
视频贯穿全程的业务例子：会员退费政策知识库，后面所有坑、方案都复用这个例子。
1. 第一层：文档预处理 & 切片（Chunking / 文档结构化解析环节，源头问题）
视频观点：绝大多数线上事故根源，是文档切分环节破坏了语义边界，不是检索。
1.1 错误做法（视频反面案例）
固定长度粗暴切分：按 token 数 / 字数一刀切，不理解文档结构。
只抽纯文字，丢掉标题、章节号、表格内容、备注、脚注、生效时间、适用对象、例外条款。
把【主规则】和【例外条款】切到两个完全独立的 chunk。
配套退费例子（视频原文案例）
文档原文：普通会员购买 7 天内可申请退费；企业定制版套餐不支持退费。
一刀切切片结果：ChunkA：普通会员 7 天内可以退费；ChunkB：企业定制版套餐不支持退费。
用户提问：我买了企业定制会员，能不能退费？
向量检索召回命中了这两段文档（召回是对的），但两个片段分开。
后续如果排序、过滤没做好，模型只看到第一段，就会输出：7 天内可以退费 → 答案错误。
1.2 视频给出的正确工程做法
不要纯固定大小切分，优先语义边界切分、结构化分块：按章节、条款、表格、独立规则单元切割。
每一个证据块（chunk）必须绑定元数据（视频明确列出元数据清单）
文档来源 ID、文档版本号、生效时间、失效时间
适用主体：个人用户 / 企业用户 / 特定套餐
类型标记：主规则 / 补充说明 / 例外条款 / 作废历史版本 / FAQ 客服话术
原始位置、页面、表格标识
保留关联关系：强绑定的主规则 + 例外条款，尽量做邻接关联标记，方便检索时配套召回。
入库时保存三份原始材料：原始文档原文、结构化解析后的证据块、本次结构化处理的日志，用于线上问题快照复盘。
1.3 本层结论
切片的目标不是 “分出小块方便向量检索”，而是保证每一条业务规则的前提条件、约束、例外，不会被物理拆分丢失。脏的切片输入，后面再怎么调重排、调 prompt 都属于修补下游，治标不治本。
2. 第二层：检索、过滤、重排（召回之后，喂给模型之前的证据治理环节）
视频原话：召回只是海选；重排、过滤、优先级划分才是复试。哪怕 topk 里面包含正确片段，这一步做错照样翻车。
2.1 本层会出现的 4 类问题（视频逐条列出）
问题 A：候选池混入多版本冲突证据（退费例子）
知识库里面同时存在：旧退费规则、新版退费规则、客服临时口头话术、FAQ 简化版。它们语义上都和 “退费” 相关，全部被召回进来，全部塞进上下文。模型会优先选择读起来通顺、简短的版本，不一定是当前生效正式政策。
问题 B：没有业务维度过滤，只靠语义相似度
只靠向量相似度召回，不叠加业务过滤条件：时间过滤（是否已经过期）、用户身份过滤（个人 / 企业）、套餐类型过滤。相似度高，但是适用人群不对。
问题 C：注意力偏差（视频重点讲的「中间丢失效应」）
大模型上下文注意力不是均匀分布：开头、末尾的内容更容易被模型关注；放在中间位置的正确证据，被前后一堆噪声片段包裹，模型直接忽略它。
例子：topk=10，第 7 条才是正确退费条款，前面 6 条都是相似但无关的 FAQ，模型读的时候优先采信前面 6 条，忽略第 7 条正确内容。
问题 D：候选证据没有权威等级，直接平铺拼接给模型
不区分优先级：正式制度 > 补充细则 > FAQ 话术 > 历史旧文档；全部同等地位塞进去，模型自由挑选。
2.2 视频给出的工程方案
多路过滤层（在重排之前先过滤）
时间过滤器：过滤已经失效、过期作废的文档版本
属性过滤器：根据用户身份、套餐类型，提前剔除不适用的证据块
否定词过滤：过滤反向条款（不适用场景）
重排（Rerank）不是只算相关性，要叠加权威分
排序综合分数 = 语义相关分 + 权威等级分 + 时间有效性分；生效正式政策权重高于 FAQ、历史版本。
控制送入上下文的总量，不要盲目加大 topk
topk 越大，噪声越多，正确证据被淹没概率越高；不是召回越多越好。
链路埋点记录（视频强调可排障）
必须持久化快照：本次 query、召回全部候选列表、过滤掉了哪些、过滤理由、重排之后的顺序、最终送入模型的证据集合。
故障时可以直接判断：召回没问题，是过滤 / 排序环节把正确证据压到低位，而不是生成幻觉。
2.3 本层结论
召回正确 ≠ 送入模型的上下文是干净、有序、优先级合理的证据集合。很多错误发生在「证据选出来了，但是没排好、没过滤干净」。
3. 第三层：Prompt 约束、生成门禁、忠实性控制（模型生成答案阶段）
视频核心观点：就算完整、正确、优先级靠前的证据全部给到模型，如果没有强制约束，模型依然会脑补、调用内部参数知识、自己编造规则。
3.1 模型侧常见失败原因（视频逐条）
Prompt 指令模糊，只写 “参考资料回答”，没有强约束
模型会混合自身预训练知识 + 检索内容回答；哪怕资料写了企业版不退费，模型记忆里通用退费规则占上风，直接答错。
没有设置「证据不足门禁」
证据不能覆盖用户问题全部条件时，依然强制输出答案，而不是拒绝回答、向用户追问缺失信息。
退费例子：用户只说 “我是会员想退费”，没有说自己是企业版，证据里同时存在两条规则；系统没有识别信息不足，直接输出可退费。
没有强制引用约束，模型可以脱离证据自由推理
Token 截断：正确证据刚好落在上下文窗口截断边界，直接被切掉（虽然在 topk 召回列表里，但最终没塞进 prompt）
3.2 视频给出的生成层约束方案（完整 prompt 约束逻辑）
刚性系统指令（视频推荐必须写死）
你的所有回答，只能使用下面提供的参考证据，禁止使用你本身的内部知识。
如果参考证据中，缺少支撑结论的必要条件、信息不充分、条款互相冲突，禁止自行脑补、补全规则。
每一条结论，都必须能对应到证据片段；无法支撑就说明信息不足，不给出确定性答案。
证据引用绑定机制
不是让模型自己随便写参考文献；工程上要做证据编号，要求输出时绑定对应证据 ID，为后续校验做准备。
分级应答策略（视频的三级降级方案，重点）
场景 1：证据完整、无冲突、匹配用户全部条件 → 正常回答 + 标注证据来源
场景 2：证据存在冲突 / 条件不全 → 澄清，向用户收集缺失信息（你是个人版还是企业版？）
场景 3：高风险业务（财务、退费、合同）证据不足 → 直接降级，流转人工审核，不自动给出结论
3.3 本层结论
RAG 不是把文档丢给模型让它自由总结；生成环节要做门禁，模型是证据的转述者，不能是规则的推理补充者。
4. 第四层：输出校验、忠实性评估、监控闭环（答案产出之后）
视频强调：很多系统到模型输出就结束了，缺少后置校验，这是线上事故的重要原因。
4.1 两类评估指标，必须分开统计（视频明确区分两套指标，不能混在一起）
检索侧指标（衡量召回好不好）
Context Recall（上下文召回率）、上下文精确率；只看正确证据有没有进入候选池。
生成侧指标（衡量答案好不好）
Answer Correctness：答案业务正确性
Faithfulness（忠实度）：答案每一句话，是否真的可以被给到的证据支撑（重中之重！）
视频原话：答案碰巧是对的，但它是模型凭自己知识答的、不是来自检索文档，这个属于忠实性失败，依然是故障。
4.2 校验实现方式
裁判模型校验（后校验）：把【回答内容 + 对应证据片段】送入校验模型，检查有没有超出证据范围、编造内容。
规则硬校验：针对退费这类结构化业务，写规则判断：输出结论是否和例外条款冲突。
人工抽样标注 + Badcase 回流：把答错样本回流，迭代切片策略、过滤规则、重排权重。
4.3 上线灰度和观测方案（视频工程落地要求）
小流量灰度发布，不直接全量上线
轨迹快照回放：任意用户的一次问答，可以完整复现当时召回、过滤、重排、输入 prompt、模型输出全链路，定位根因
重点监控边界 case，而不是简单正向 case（简单 case 随便怎么做都能答对，看不出问题）
5. 完整链路故障排查顺序（视频给的标准化排查流程，面试可以直接按这个顺序说）
当出现：召回文档正确，但答案错误，按顺序排查，不要乱调 embedding：
确认快照：先拉本次请求完整快照，确认正确证据是不是真的进入最终送入模型的上下文里（有没有被过滤、被截断、排到最后被丢掉）
如果正确证据根本没进 prompt：问题在过滤、重排、截断环节
如果正确证据确实在上下文里面：往下走
检查切片：这条证据对应的规则，前提、例外、约束是不是完整保存在 chunk 里面，有没有被切散
检查排序和上下文组装：位置是不是被大量噪声包围，注意力被抢占
检查 prompt 约束：有没有禁止模型使用内部知识、有没有证据不足拒答的指令
检查模型输出忠实性校验：是否模型无视证据，自主幻觉
6. 面试高分标准答案模板（视频原文给的口述模板，一字不差）
我会先做文档结构化解析，按业务规则单元切片，绑定版本、适用对象等元数据；检索之后叠加业务过滤、按权威等级重排，控制送入上下文的证据集合；送入模型前设置强忠实性约束，证据不全或者冲突时拒答、追问或者走人工；输出之
