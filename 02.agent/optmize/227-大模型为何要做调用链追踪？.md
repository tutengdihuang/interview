## 核心结论

接口成功率反映请求的部分运行状态；Trace 将一次大模型请求拆为多个可观测阶段，用于定位耗时与业务质量问题。HTTP 200 不等于回答正确、格式合规或延迟达标。

## 为什么只看成功率不够

一次 RAG / Agent 请求可能经过意图识别、Query 改写、Embedding、检索、重排、工具调用、模型生成、结果解析与组装。

即使请求返回200，也可能存在：

- 检索召回不相关资料，导致回答偏离问题。
- 工具反复重试，延迟和成本上升。
- 模型输出无法解析的 JSON，无法交付有效结果。
- 整体响应慢，但无法从总耗时判断瓶颈所在。

## Trace 应观察什么

| 阶段 | 豆包回复提到的观察点 |
| --- | --- |
| 网关与预处理 | 网关、Query 改写耗时 |
| 检索与重排 | 向量检索、重排耗时及召回内容 |
| 工具调用 | 重试与调用异常 |
| 模型生成 | 首 Token 延迟、生成总耗时 |
| 输出处理 | 解析状态、关键输入输出摘要 |

价值有两类：定位性能瓶颈，以及沿链路追溯错误输入、检索或输出，避免把所有问题归因于模型。

## 面试口述

大模型请求往往包含检索、重排、工具调用、生成和解析多个环节。接口成功只能说明部分请求处理正常，不能证明回答正确或延迟达标。调用链追踪把这些阶段关联起来，记录耗时、状态与关键输入输出，帮助判断系统为什么慢、结果为什么错，以及故障发生在哪一环节。
