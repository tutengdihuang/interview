## 核心结论

请求去重不只是节省模型费用，更重要的是避免 Agent 重复执行写操作，维持业务一致性，并让重试、刷新和结果恢复指向同一个任务。

## 重复请求从哪里来

- 用户连续点击提交。
- 页面刷新或断线后重新提交。
- 客户端、代理或服务端因超时自动重试。

重复生成会浪费推理成本；重复发消息、创建工单、扣款或写数据库还会造成业务副作用。

## 基本流程

1. 为一次业务意图创建稳定的幂等键，重试时复用。
2. 服务端按幂等键关联任务与状态。
3. 正在执行则返回已有任务标识及进度，不创建第二个任务。
4. 已完成则返回已有结果，不重新执行。
5. 用户修改输入或主动发起新任务时使用新键，不按语义相似度擅自合并。

## 工程补充（非原片核验内容）

- “先查再创建”有并发竞态。需要数据库唯一约束、事务或原子占位来确保只有一个请求获得执行权。
- key 应限定租户、用户和操作类型等作用域，并绑定请求参数摘要；同键不同参数应拒绝冲突，而不是返回别人的结果。
- 每次重试都换 request_id 无法去重。链路追踪 ID 和跨重试稳定的业务幂等键应区分。
- 网关或任务入口去重不能独自保证外部副作用只发生一次。每个关键写工具也需业务唯一键、事务约束或下游幂等支持。
- 执行失败、进程退出、租约过期、结果保留期都需要明确策略；不能把永久卡在“执行中”当成成功去重。
- 文本完全相同也可能是用户主动发起的两次业务；请求幂等与结果缓存是不同概念。

## 面试口述

大模型请求去重是为了防止重复推理和重复计费，更是为了避免 Agent 重复调用写工具，破坏业务一致性。应使用跨重试稳定的幂等键，原子关联任务状态和结果：执行中返回原任务，完成后复用结果。同时在工具写操作边界实现幂等，不能只靠比较 prompt 或前端禁用按钮。
