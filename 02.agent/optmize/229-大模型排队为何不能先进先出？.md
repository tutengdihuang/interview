# 229. 大模型排队为何不能先进先出？

> 视频：https://www.douyin.com/video/7662760862251615951
> 豆包来源：https://www.doubao.com/chat/38451516806250754
> 基于两轮豆包回复整理，未独立核验原片；不是逐字字幕。

## 核心结论

不能仅依据到达顺序安排大模型任务。不同请求的输入长度、输出长度及工具调用耗时不同，共用简单FIFO队列时，长任务可能阻塞大量短请求。

## 为什么会阻塞

- 短问答只需生成少量文本，长任务可能读取长文档、生成长答案或调用工具。
- 按到达顺序公平，不等于按资源使用公平，也不等于用户体验公平。
- 豆包用“普通接口耗时差不多”进行对比，这是简化叙述，并非所有Web接口均如此。

## 调度思路

| 任务类别 | 豆包回复中的处理建议 |
| --- | --- |
| 短在线问答 | 高优在线队列，尽快响应 |
| 长文本生成 | 与短请求隔离，考虑异步处理 |
| 后台批处理 | 低优先级或低峰运行 |
| 付费、重要业务 | 按业务规则设置优先级 |

队列划分依据包括任务类型、预估token、业务优先级，而不只是到达时间。

## 背压与过载保护

观察队列长度、等待时间、token预算等指标。超过阈值时，不应无限接单再让用户久等后失败，可选择提前拒绝、引导异步处理，或在业务允许时降级模型。小模型不应被当成无条件等价替代。

## 面试口述

大模型不同请求的资源消耗和执行时间差异很大，简单FIFO容易造成长任务阻塞短请求。我会按预估token、任务类型和业务优先级分层调度，隔离在线短请求与长任务，并设置队列等待和容量阈值，通过拒绝、异步导流或符合业务要求的降级实施背压。到达顺序公平不能替代资源和体验层面的治理。
