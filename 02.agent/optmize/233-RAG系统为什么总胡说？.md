# 233. RAG系统为什么总胡说？

## 核心观点

RAG稳定性不是单靠向量库或top-k参数决定，而取决于端到端工程链路。主题相关的材料不一定能回答问题，正确证据也可能被噪声、冲突资料和不受约束的生成过程淹没。

## 六个环节

| 环节 | 回复指出的问题 | 整理后的改进方向 |
| --- | --- | --- |
| 知识切片 | 太小丢条件，太大混噪声 | 按标题、段落、业务对象和语义边界切分，必要时保留父子关系 |
| 混合召回 | 向量易漏编号，关键词易漏同义表达 | 结合BM25精确匹配和向量语义召回 |
| 重排 | top-k只是候选，不等于可直接使用 | 用reranker及业务规则筛选版本、正式来源和权限范围 |
| 上下文拼装 | 正确答案与无关材料混杂 | 处理排序、去重、来源、时间、层级及引用关系 |
| 生成约束 | 把猜测混成确定结论 | 要求基于证据回答，证据不足拒答，高风险场景带引用 |
| 效果评测 | 少量肉眼测试无法支撑调参 | 覆盖高频、边界、同义、跨文档和无答案问题 |

## 评测关注点

按豆包回复，重点看召回率、证据命中率、答案准确率和拒答能力。调优应能定位具体环节，并支持观察与回放，而不是只调top-k后凭感觉判断。

## 面试口述整理

我不会把RAG胡说简单归因于向量库。会沿切片、混合召回、重排、上下文拼装、生成约束和评测闭环逐层检查：材料是否完整、是否召回正确证据、噪声和冲突是否处理、回答是否受证据约束，以及无答案问题能否拒答。每层能观察、能回放、能评测，才有条件稳定迭代。
