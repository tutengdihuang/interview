# 224. 响应速度为何不只看总耗时

> 视频：https://www.douyin.com/video/7663514634599677114
> 豆包独立会话：https://www.doubao.com/chat/38450988321285890
> 根据豆包两轮回复整理；未独立核验原片字幕，不将其自称的“完整台词”认定为逐字稿。

## 核心结论

总耗时相同，不代表用户体验相同。需要同时观察首次输出等待时间、持续生成速度和任务最终完成时间。

## 三个指标

| 指标 | 定义 | 用户感知 | 排查方向 |
| --- | --- | --- | --- |
| TTFT | 发出请求到收到第一个 token | 是否一直没有反应 | 排队、检索、网络、长上下文和 Prefill |
| 生成速率 token/s | 生成阶段单位时间输出的 token 数 | 文字输出是否流畅 | Decode、模型规模、批处理和资源负载 |
| 端到端耗时 | 请求发出到整个响应完成 | 任务多久完成 | 前置步骤、输出长度、工具调用和推理链路 |

豆包举例：两个请求都用10秒，一个前8秒没有输出，另一个1秒就开始持续输出；仅看总耗时无法区分两者。

## 工程理解补充（非原片核验内容）

- 应用端 TTFT 不等于纯 Prefill 时间，还包括网络、排队、检索、工具前置步骤和传输缓冲。
- 生成阶段平均 token/s 与整个服务的系统吞吐量不是同一指标；必须声明测量范围。
- 粗略拆解：总耗时约等于 TTFT 加上后续 token 的生成耗时。统计生成速率时要明确是否排除首 token 等待。
- 平均速率可能掩盖停顿；还应看 token 间延迟及 P95/P99 等分位数。
- Prefill 常偏计算密集、Decode 常受显存带宽限制，但具体瓶颈受批大小、硬件和模型实现影响，不能当绝对规律。
- 应先确定交互型或离线型场景与 SLO，再决定优先优化哪个指标。

## 面试口述

评估大模型响应速度不能只看总耗时。TTFT 衡量首次反馈等待时间，生成速率衡量持续输出速度，端到端耗时衡量整个任务完成时间。总耗时相同也可能有完全不同的用户体验，因此要拆分链路阶段并观察尾延迟，才能定位排队、检索、Prefill、Decode 或工具调用的瓶颈。
