# 多 Agent 任务拆分的硬性边界是什么？

> 面向生产环境的多 Agent 系统设计 · 第 2 问

---

## 核心问题

多 Agent 任务拆分的硬性边界是什么？什么情况下拆分会导致系统性劣化？

---

## 核心结论

**硬性边界**指一旦越过，拆分反而导致系统性劣化的条件。最硬的边界是**共享上下文依赖**——拆分本质是"压缩 + 传递"，压缩必然有损（传话游戏）。判断标准：子任务的正确执行是否需要其他子任务探索过程中的**中间发现**，而不仅是最终结论。

---

## 七大硬性边界

### 1. 共享上下文依赖（最硬的边界）

**问题**：子任务若依赖"全体成员对同一份完整上下文的理解"，拆开会造成信息丢失。

**判断方法**：
- 子任务的正确执行是否需要其他子任务探索过程中的**中间发现**（而不仅是最终结论）？
- 如果是 → 不能拆

**例子**：
- ❌ 不能拆：多个 Agent 需要理解同一份长文档的上下文关系
- ✅ 可以拆：1000 份独立报告的分析（彼此无依赖）

---

### 2. 强顺序耦合

**问题**：B 的输入大部分来自 A 的输出，且 A 的输出不可预先声明 Schema。

**后果**：拆开后协调开销（fan-in 时的对齐、重试、等待）远超并行收益。

**判断方法**：
- A 的输出能否预先定义 Schema？
- B 是否依赖 A 的中间状态而非最终结果？

---

### 3. 原子性/事务性

**问题**：必须作为一个整体成功或失败的操作。

**例子**：
- 一次数据库事务
- 一次需要全局视角的文件重构

**后果**：拆分即破坏原子性语义。

---

### 4. 可验证性边界

**问题**：子任务输出若无法被**独立验证**（有明确 ground truth 或可执行的校验手段），拆分等于放大幻觉传播面。

**关键概念**：
- 不可验证的中间产物是下游 Agent 的"污染源"
- 幻觉会随链路传递变形洗白（详见第 8 题）

---

### 5. 粒度下限——单一职责三元组

**定义**：一个子任务应对应一个清晰的（目标 + 输出格式 + 工具/来源指引）组合。

**Anthropic 的教训**：
- 早期 Agent 会对简单查询 spawn 50 个子 Agent
- **任务复杂度不足以支撑拆分就是越界**

**判断方法**：
- 能否用一句话说清这个子任务的目标、输出格式、工具来源？
- 不能 → 粒度太细

---

### 6. MECE 边界

**定义**：拆出的子任务应"相互独立、完全穷尽"（Mutually Exclusive, Collectively Exhaustive）。

**违反后果**：
- 子任务输出重叠 → 重复劳动和结论冲突
- 对应第 4、5 题的治理

---

### 7. 上下文窗口边界

**问题**：每个子任务所需的输入 + 工具返回必须装得进独立窗口，否则拆分无效。

**判断方法**：
- 估算子任务所需的 token 总量
- 超过模型上下文窗口限制 → 需要进一步拆分或压缩

---

## 拆分决策的量化方法

### 协调 token 预算估算

```
协调 token 占比 = 协调 token 预算 ÷ 总 token 预算
```

**经验法则**：
- 超过 **~45%** → 说明拆分过细或依赖过重
- 需要重新评估拆分策略

### 区分两种拆分

| 拆分类型 | 切割维度 | 边界不同 |
|---------|---------|---------|
| **任务拆分** | 按流程切 | 关注顺序和依赖 |
| **角色拆分** | 按专业能力切 | 关注工具和专业性 |

---

## 面试加分项

1. **量化拆分决策**：估算"协调 token 预算 ÷ 总 token 预算"，超过 ~45% 说明拆分过细或依赖过重

2. **区分"任务拆分"与"角色拆分"**：
   - 前者按流程切
   - 后者按专业能力切
   - 两者边界不同

---

## 一句话总结

> 任务拆分的硬性边界是：**一旦越过，拆分反而导致系统性劣化**。最硬的边界是共享上下文依赖——拆分本质是"压缩 + 传递"，压缩必然有损。记住：**拆分决策可以量化**——协调 token 占比超过 45% 就是越界。
