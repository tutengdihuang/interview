# 多 Agent 常见架构有哪些？Manager-Worker 和对等协作，在项目当中会如何做选择？生产项目里哪些场景适合多 Agent？

> 面向生产环境的多 Agent 系统设计 · 第 1 问

---

## 核心问题

1. 多 Agent 常见架构有哪些？
2. Manager-Worker 和对等协作，在项目当中会如何做选择？
3. 生产项目里哪些场景适合多 Agent？

---

## 核心结论

**架构选择本质是协调成本与全局一致性需求的权衡**。生产环境默认推荐"分层 + 严格通信限制"的混合架构，纯对等协作只用于小规模封闭场景。多 Agent 本质是**用 token 换能力**——只有任务价值足以覆盖成本时才划算。

---

## 常见架构全景

| 架构 | 协调方式 | 适用场景 | 主要风险 |
|---|---|---|---|
| **Pipeline（流水线）** | 固定顺序，无自主决策 | 可预测的串行流程（理赔处理、数据加工） | 脆弱，无法应对动态任务 |
| **Manager-Worker（编排器-工人）** | 中央协调者拆解任务、分发、汇总 | 可分解为独立子任务、需要单一责任出口 | Manager 成为瓶颈/单点故障 |
| **Hierarchical（层级式）** | 多级 Manager 树 | 大规模系统，子域再分治 | 层级信息失真 |
| **Peer-to-Peer / Swarm（对等协作）** | Agent 直接互发消息，无中心 | 快速变化的局部协调（辩论、协商） | O(n²) 消息爆炸，全局一致性差 |
| **独立并行（Map-Reduce）** | 零通信，各自处理后聚合 | "尴尬并行"任务（1000 份报告分给 10 个 Agent） | 单点错误无人捕获 |

---

## Manager-Worker vs 对等协作的选型依据

核心是**协调成本与全局一致性需求的权衡**：

### 1. 任务可分解性
- **Manager-Worker**：子任务彼此独立、输出可静态汇总（本质是 Map-Reduce 变体）
- **对等协作**：子任务需要运行时协商、互相触发调整

### 2. 协调成本
- 对等网络的消息量随 Agent 数**平方增长**
- 经验法则：**协调 token 占总预算超过约 45% 时，质量开始下降**
- 全连接 Swarm 会因消息爆炸提前崩溃
- **生产环境默认推荐"分层 + 严格通信限制"的混合架构**

### 3. 一致性与可审计性
- **中心化（Manager-Worker）**：需要全局状态、清晰审计链、可预测行为
  - 每个动作都可追溯到 Manager 的决策，易调试
- **去中心化（对等协作）**：需要局部快速自适应、容忍最终一致

### 4. Manager 自身能力
- Manager 若缺乏领域知识无法正确拆解任务，中心化架构就会**系统性跑偏**
- misrouting 会破坏整个流程

### 项目实践选择

生产中大部分团队从 **Manager-Worker 起步**（Anthropic 的 Research 系统就是 Orchestrator-Worker 模式），在 Manager 成为瓶颈时下放部分局部协调权形成混合式。

**纯对等协作**一般只用于辩论/互评（MAD，Multi-Agent Debate）这类**小规模、封闭轮次**的场景。

## 生产中适合多 Agent 的场景（判据）

Anthropic 生产数据给出的判据很明确：

### ✅ 适合的场景

1. **广度优先、可并行的探索型任务**
   - 如深度研究（同时查多个方向）、全量代码库分析
   - Opus 4 主控 + Sonnet 4 子 Agent 比单 Opus 4 在内部研究评测上**高出 90.2%**

2. **信息量超出单一上下文窗口**
   - 各子 Agent 有独立 context window，天然实现"分治 + 压缩"

3. **需要不同工具集/提示词的专业分工**
   - 检索 Agent、分析 Agent、写作 Agent 各配各的工具
   - 避免单 Agent 塞 12 个工具后选择准确率跌破 90% 的"复杂度之墙"

4. **任务价值足够高**
   - 多 Agent 烧 token 极快——Anthropic 数据显示 Agent 比普通对话多耗约 4 倍 token，多 Agent 约多耗 **15 倍**
   - 只有任务价值足以覆盖成本时才划算

### ❌ 不适合的场景

- 所有 Agent 必须共享同一份上下文的任务
- Agent 间存在大量依赖的任务
- 大部分编码任务（真正可并行的子任务比研究类少得多）

## 面试加分项

1. **引用数据**："token 用量解释了 BrowseComp 评测 80% 的性能方差"——多 Agent 本质是用 token 换能力

2. **提出选型决策树**：
   - 先问"单 Agent + 好工具能不能解决"
   - 能就不上多 Agent
   - **复杂度不是功能，是负债**

---

## 一句话总结

> 多 Agent 架构选型的核心是：**在协调成本与全局一致性之间找平衡点**。生产环境默认从 Manager-Worker 起步，只有任务价值足以覆盖 token 成本时才上多 Agent。记住：**能单则单，复杂度是负债**。
