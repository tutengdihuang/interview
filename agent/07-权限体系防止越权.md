# 上线后如何设计权限体系，防止子 Agent 越权操作？

> 面向生产环境的多 Agent 系统设计 · 第 7 问

---

## 核心问题

上线后如何设计权限体系，防止子 Agent 越权操作？

---

## 核心结论

越权的典型路径：**静态高权限服务账号**（所有 Agent 共享 admin 凭证）、**多跳委派中权限静默扩大**（confused deputy 问题）、**prompt 注入劫持 Agent 意图**。设计原则是**三层解耦**：身份（Authentication）→ 授权（Authorization）→ Agent 执行范围（Agent Scope）。OWASP Agentic Top 10 将其列为 **ASI03（身份与权限滥用）**。

---

## 越权的典型路径

| 路径 | 描述 | 风险 |
|------|------|------|
| **静态高权限服务账号** | 所有 Agent 共享 admin 凭证 | 一个 Agent 被攻破，全部权限泄露 |
| **多跳委派中权限静默扩大** | confused deputy 问题 | 权限在委派链中逐渐扩大 |
| **prompt 注入劫持** | 恶意 prompt 控制 Agent 行为 | Agent 执行非预期操作 |

---

## 设计原则：三层解耦

```
身份（Authentication）
    ↓
授权（Authorization）
    ↓
Agent 执行范围（Agent Scope）
```

### 1. 认证（Authentication）
- **OIDC/OAuth2** 验证发起用户
- **mTLS/JWT** 验证后台服务主体

### 2. 授权（Authorization）
- **RBAC**（角色）+ **ABAC**（属性：命名空间、环境、信任分）
- 判定"该身份全局能做什么"

### 3. Agent 执行范围（Agent Scope）
- 回答"用户 U 的这次任务 T 中，Agent A 的这次工具调用应激活哪部分权限子集"
- **这是传统 IAM 没有的动态层**

---

## 生产落地的关键机制

### 1. 按 Agent 粒度的最小权限凭证

**方法**：
- 每个子 Agent **独立凭证** + **工具白名单**
- API 限制到**幂等端点**
- 数据库只暴露**只读视图/参数化存储过程**
- **绝不用万能服务账号**

**效果**：单个 Agent 被攻破，爆炸半径最小

---

### 2. 委派链上的三层策略校验（AWS Cedar 参考模型）

| 层级 | 校验内容 |
|------|---------|
| **L1 Agent→工具** | Agent 信任分、命名空间、生命周期阶段是否匹配 |
| **L2 Agent→Agent 委派** | **委派跳数硬上限**（如 ≤5），且请求的任务必须是目标 Agent 注册能力声明的**子集**（防权限升级） |
| **L3 溯源用户** | 发起人角色/MFA/允许的委派深度，用户上下文经**密码学签名**随链传递防篡改 |

**核心**：每一层都校验，防止权限在委派链中扩大

---

### 3. 身份透传（identity propagation）

**方法**：
- 子 Agent 以"**代表用户 U 执行**"的形式携带签名 token
- 保证审计日志能还原"谁授权了什么"
- 租户边界不失效

**为什么重要**：
- 审计可追溯
- 多租户场景下不混淆

---

### 4. 高危操作 human-in-the-loop

**方法**：
- **删除、支付、外发**等敏感动作
- 强制**人工审批** + **速率限制**

**为什么重要**：
- 防止 Agent 自主执行高危操作
- 人工是最后的安全网

---

### 5. 预算即安全原语

**方法**：
- 每 Agent **日/月美元硬上限**
- 超限**熔断该 Agent**而非整个系统

**三大价值**：
1. **失控循环止损**：最坏损失 = cap
2. **拒绝钱包攻击防御**：被注入的 Agent 最坏损失被锁定为预算额
3. **成本上界可预测**：N 个 Agent 的日开销上界 = N × cap

---

### 6. 执行隔离

**方法**：
- **容器/沙箱级隔离**（独立文件系统、网络策略）
- **MAC/信息流监控**阻断横向数据外泄

**为什么重要**：
- 即使 Agent 被攻破，也无法横向移动
- 限制爆炸半径

---

### 7. 审计

**方法**：
- 每次权限判定写 **append-only 日志**
- 可回放整条委派链

**为什么重要**：
- 事后追溯
- 合规要求

---

## 面试加分项

1. **强调根本差异**：
   > "控制流由随机模型输出决定"——传统应用的爆炸半径可静态审查，Agent 的执行路径运行时才确定，所以**权限必须在工具调用点动态执行（policy enforcement point），而非依赖提示词约束**。

2. **提到强制访问控制研究**：
   > MAC 研究（如 SEAgent）：用信息流图监控 + 实体属性标签做策略，可覆盖多 Agent 特有的委派升级场景。

---

## 生活化比喻

把多 Agent 权限体系想象成**银行授权系统**：

| 权限机制 | 银行类比 |
|---------|---------|
| **三层解耦** | 身份验证 → 账户权限 → 单笔交易限额 |
| **最小权限** | 柜员只能操作自己负责的账户 |
| **委派链校验** | 转授权需要多级审批，且不能超过原权限 |
| **身份透传** | 代办业务需要携带委托人签名 |
| **高危操作审批** | 大额转账需要行长审批 |
| **预算上限** | 每日转账限额 |
| **执行隔离** | 不同业务在不同隔离区域 |
| **审计日志** | 所有操作留痕，可追溯 |

---

## 一句话总结

> 权限体系设计的核心是：**三层解耦（身份 → 授权 → Agent Scope）+ 七个关键机制（最小权限、委派校验、身份透传、高危审批、预算上限、执行隔离、审计日志）**。记住：Agent 的执行路径运行时才确定，所以**权限必须在工具调用点动态执行，而非依赖提示词约束**。
