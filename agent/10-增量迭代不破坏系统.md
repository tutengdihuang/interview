# 多 Agent 如何做增量迭代，新增 Agent 组件不破坏原有系统？

> 面向生产环境的多 Agent 系统设计 · 第 10 问

---

## 核心问题

多 Agent 如何做增量迭代，新增 Agent 组件不破坏原有系统？

---

## 核心结论

核心思路：**把"Agent 组件化"——稳定的是契约，可变的是实现**。五层保障：契约层（版本化 Schema）→ 注册与发现层（即插即用）→ 发布层（灰度 + 影子 + 回滚）→ 质量层（评测作为合并门槛）→ 兼容性策略（加法演进）。

---

## 增量迭代：五层保障

### 第 1 层：契约层——版本化的强类型接口

**目标**：Agent 间只通过 Schema 通信，不感知彼此内部实现

**方法**：

#### 1. 版本化 Schema
- 每个 Agent 声明**版本化的输入/输出 Schema**（含能力描述）
- Agent 间只通过 Schema 通信

#### 2. 契约测试（consumer-driven contract testing）
- **消费方 Agent** 对提供方的期望固化为测试
- 任何破坏契约的改动在 **CI 阶段被拦截**

**为什么重要**：
- 这是"新增不破坏"的**技术保证**
- 契约变更可追溯、可回滚

**例子**：
```yaml
Agent A (v1.2):
  input:
    query: string
    context: object
  output:
    result: string
    confidence: float
```

---

### 第 2 层：注册与发现层——新组件即插即用

**目标**：新 Agent 上线无需修改既有 Agent

**方法**：

#### 1. Agent 注册表
- 新 Agent 上线只需**注册能力声明**
  - name + 能力描述 + Schema 版本
- 编排器从 **roster 动态选择**
- 无需修改既有 Agent

#### 2. 能力路由
- 任务分发按**注册能力匹配**（同第 9 题）
- 新 Agent 自然承接新任务类型
- 存量 Agent 路径不变

**效果**：新 Agent 即插即用，存量 Agent 无感知

---

### 第 3 层：发布层——灰度 + 影子 + 回滚

**目标**：安全发布，快速回滚

**方法**：

#### 1. 影子模式（shadow）
- 新 Agent 与旧逻辑**并行跑同一流量**
- **只记结果不生效**
- 对比输出差异

#### 2. 金丝雀路由
- 按**流量百分比**把任务路由给新 Agent
- 观察**质量/成本/延迟**指标
- 再逐步放量

#### 3. 特性开关
- 新 Agent 整体挂 **flag**
- 出问题**秒级回退路由**
- **不回退代码**

**效果**：发布风险可控，回滚快速

---

### 第 4 层：质量层——评测作为合并门槛

**目标**：防止单点改进造成全局劣化

**方法**：

#### 1. 端到端评测集
- 多 Agent 系统的"单测"是**端到端评测集**
  - 任务成功率
  - 结论一致性
  - 成本基线
- 新组件合入**必须通过全链路评测**

#### 2. 集成预演
- 用**模拟器/回放流量**做集成预演
- Anthropic 强调在 Console 用完全相同的提示词与工具"像 Agent 一样思考"来调试

**效果**：新组件质量可验证

---

### 第 5 层：兼容性策略——加法演进

**目标**：优先新增，避免修改

**方法**：

#### 1. 加法演进
- **优先新增字段/新增 Agent**
- 避免修改既有语义
- Schema 演进遵循"**宽容读取、严格写入**"

#### 2. 共享状态迁移
- 共享状态（黑板）的 Schema 变更需要**迁移策略**
- 消费旧版本的 Agent 给予**过渡期**

#### 3. 编排器作为稳定层
- **编排逻辑**（DAG/路由策略）与 **Agent 实现**解耦
- Agent 替换不动编排

**效果**：系统演进稳定

## 面试加分项

1. **指出多 Agent 迭代的独特风险**：
   > **改动是行为级的不是功能级的**——提示词一个字的改动就等于改了组件的全部行为，所以**灰度 + 评测比传统软件更重要**。

2. **提出"Agent 团队的 CI"概念**：
   > 注册表 schema 校验 + 契约测试 + 影子对比三件套

---

## 生活化比喻

把多 Agent 增量迭代想象成**手机 App 更新**：

| 迭代层 | App 类比 |
|-------|---------|
| **契约层** | API 接口文档，版本化 |
| **注册与发现层** | App Store，新 App 即插即用 |
| **发布层** | 灰度发布、AB 测试、一键回滚 |
| **质量层** | 应用商店审核 + 自动化测试 |
| **兼容性策略** | 向后兼容，旧版本继续可用 |

**关键**：
- **契约测试** = API 兼容性测试
- **影子模式** = 新功能灰度测试
- **特性开关** = 功能开关，随时关闭

---

## 一句话总结

> 增量迭代的核心是：**把 Agent 组件化——稳定的是契约，可变的是实现**。五层保障：**契约层（版本化 Schema）→ 注册与发现层（即插即用）→ 发布层（灰度 + 影子 + 回滚）→ 质量层（评测作为合并门槛）→ 兼容性策略（加法演进）**。记住：提示词一个字的改动就等于改了组件的全部行为。
