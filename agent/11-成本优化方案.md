# 多 Agent 整体成本高，落地有哪些成本优化方案？

> 面向生产环境的多 Agent 系统设计 · 第 11 问

---

## 核心问题

多 Agent 整体成本高，落地有哪些成本优化方案？

---

## 核心结论

成本现状：多 Agent 约为普通对话 **15 倍** token 消耗，4-Agent 工作流单任务成本可达 $5-8；但 token 用量解释了 80% 的性能方差——**成本是能力的对价**，优化目标是**单位任务成本**而非绝对成本。七大优化方案：**模型分层路由 > Prompt 缓存 > 输出控制 > 批处理 > 语义缓存 > 微调 SLM > 预算体系**。

---

## 成本现状

| 指标 | 数值 |
|------|------|
| 多 Agent vs 普通对话 | **15 倍** token 消耗 |
| 4-Agent 工作流单任务成本 | $5-8 |
| token 用量解释的性能方差 | **80%** |

**核心洞察**：
> 成本是能力的对价，优化目标是**单位任务成本**而非绝对成本。

---

## 七大成本优化方案

### 方案 1：模型分层路由（最大单一杠杆）

**原理**：按任务复杂度分配模型档位

**方法**：
| 任务类型 | 模型档位 | 节省比例 |
|---------|---------|---------|
| 分类/抽取/格式化 | 小模型（Haiku 级） | - |
| 中等推理/摘要 | 中档 | - |
| 复杂综合/多步规划 | 前沿模型 | - |

**Anthropic 的生产形态**：
- **Opus 做主控**（少而关键）
- **Sonnet 做子 Agent**（多而廉价）
- Haiku 替代 Opus 单次调用可省约 **84%**

**进阶方案**：
- **路由分类器**（如 RouteLLM 思路）自动判定难度
- **混合架构**：前沿模型只做路由决策，任务执行交给按小时计费的微调小模型（SLM）GPU 端点
- token 成本转为固定成本

**实测参考**：
- 多模型路由普遍带来 **50-80%** 成本削减
- Databricks Genie 报告 **61%**

**优先级**：⭐⭐⭐⭐⭐（最高）

---

### 方案 2：缓存体系

#### Prompt Caching
- 系统提示词、工具定义等**稳定前缀**走服务商缓存
- 缓存读价格最多便宜 **90%**
- 多 Agent 的提示词高度重复，此杠杆尤其有效

#### 语义缓存
- 历史"查询-结果"向量召回
- 相似度 **>0.95** 直接复用（配合第 5 题的工具结果缓存）

**优先级**：⭐⭐⭐⭐⭐（最高）

---

### 方案 3：上下文与输出控制

#### 上下文控制
- **子 Agent 摘要回传**而非原始转储
- 黑板模式传引用本身就是成本优化
- **LLMLingua 类压缩**可再砍 **70%** 上下文

#### 输出端控制
- 输出 token 比输入贵 **3-5 倍**
- 强制**结构化输出 + 简洁指令**
- 砍掉寒暄与重复

**优先级**：⭐⭐⭐⭐

---

### 方案 4：批处理与调度

**方法**：
- 非实时负载（夜间分析、批量评估）走 **Batch API**
- **半价**

**适用场景**：
- 不要求实时响应的任务
- 可以延迟处理的工作负载

**优先级**：⭐⭐⭐⭐

---

### 方案 5：架构级节流

**方法**：

#### 1. 按需启动多 Agent
- **路由器先判复杂度**
- 简单任务单 Agent 解决（"**能单则单**"）
- 动态决定 fan-out 数量

**Anthropic 的教训**：
- 简单查询 spawn 50 个子 Agent → 严重浪费

#### 2. 缩短协调链
- 限制消息量（第 3 题的治理同时是成本治理）
- **协调 token 占比 <45%**

**优先级**：⭐⭐⭐⭐

---

### 方案 6：预算硬上限（成本即安全）

**方法**：
- 每 Agent **日/月美元 cap**
- 超限**只熔断该 Agent**

**三大价值**：
1. **失控循环止损**：最坏损失 = cap
2. **拒绝钱包攻击防御**
3. **成本上界可预测**：N 个 Agent 的日开销上界 = N × cap

**FinOps**：
- 按 Agent/任务做**成本归因（chargeback）**
- 监控**单位任务成本趋势**而非只看总账单

**优先级**：⭐⭐⭐⭐⭐（虽不直接省钱，但它是止损底线，应最先上线）

---

### 方案 7：高频任务微调小模型

**方法**：
- 对高频、模式固定的子任务（SQL 生成、分类、抽取）
- 用前沿模型**蒸馏数据**微调开源小模型
- 可去掉大量 few-shot 模板
- 单调用 token 降 **80%**
- 达到或超过前沿模型效果

**适用场景**：
- 高频任务
- 模式固定
- 数据充足

**优先级**：⭐⭐⭐

---

## 落地优先级建议

```
模型路由 > Prompt 缓存 > 输出控制 > 批处理 > 语义缓存 > 微调 SLM > 预算体系
```

**特别说明**：
> 预算体系虽不直接省钱，但它是**止损底线**，应最先上线。

## 生活化比喻

把多 Agent 成本优化想象成**公司运营管理**：

| 优化方案 | 公司类比 |
|---------|---------|
| **模型分层路由** | 不同难度工作分配给不同级别员工 |
| **缓存体系** | 常用资料放手边，避免重复查找 |
| **上下文控制** | 汇报精简，不啰嗦 |
| **批处理** | 非紧急工作集中处理 |
| **架构级节流** | 简单工作不需要开会 |
| **预算上限** | 部门预算控制 |
| **微调小模型** | 高频工作培训专属员工 |

## 一句话总结

> 成本优化的核心是：**七大方案——模型分层路由（最大杠杆）> Prompt 缓存 > 输出控制 > 批处理 > 语义缓存 > 微调 SLM > 预算体系（止损底线）**。记住：成本是能力的对价，优化目标是**单位任务成本**而非绝对成本。
